# 部署状态持久化同步队列方案 [20260418-1645已采用]

## 1. 目标

本轮只解决上一个版本仍然保留的最后一个风险点：

1. 部署状态后台同步不能只靠进程内 `Map + setInterval`。
2. API 重启、进程崩溃、短时多会话并发部署时，部署状态同步必须可恢复、可重试、可收敛。

本方案不引入新的外部队列中间件，不新增 Redis 强依赖，不保留“内存队列为主、持久化只是旁路记录”的双轨方案。

## 2. 现状问题

上一轮实现已经把部署面板改成后台同步模型，但同步任务仍然放在进程内：

1. `deploymentSyncQueue: Map<string, DeploymentSyncRequest>`
2. `startTaskSessionDeploymentSyncJob()` 定时消费
3. API 启动时靠扫描 `sandbox_execution_environments.metadata` 做 backlog 恢复

这个实现已经能跑通真实链路，但仍有三个缺口：

1. **进程级易失**：enqueue 后如果进程立刻退出，任务会丢。
2. **状态可观察性弱**：看不到任务是否 pending/running/failed，以及当前重试次数。
3. **并发收敛不稳定**：同一会话重复 deploy/redeploy/rollback 时，最新同步目标只能靠内存覆盖，无法保证跨重启延续。

## 3. 设计原则

1. 同步队列状态必须入库。
2. 同一 `taskSessionId` 在任意时刻只允许存在一条活跃 deployment sync job。
3. 新的 deploy/redeploy/rollback 不创建平行 job，而是覆盖同一 job 的最新 payload。
4. 启动恢复仍保留，但职责收敛成“把旧 metadata 补录成 job”，不是继续依赖 metadata 扫描执行主链。
5. 读请求仍然禁止直接触发 Railway 查询。

## 4. 数据模型

新增表：

- `task_session_deployment_sync_jobs`

字段最小集合：

1. `id`
2. `task_session_id`
3. `orchestrator_session_id`
4. `sync_key`
5. `job_type`
6. `status`
7. `attempt_count`
8. `last_error`
9. `payload_json`
10. `next_retry_at`
11. `started_at`
12. `completed_at`
13. `created_at`
14. `updated_at`

约束：

1. `sync_key` 唯一，格式固定为 `deployment_sync:<taskSessionId>`
2. `status` 只允许：
   - `pending`
   - `running`
   - `completed`
   - `failed`

`payload_json` 内容最小包含：

1. `selectedDeploymentId`
2. `reason`
3. `requestedAt`

## 5. 运行机制

### 5.1 enqueue

`enqueueTaskSessionDeploymentSync()` 改成数据库 upsert：

1. 以 `sync_key` 定位 job
2. 若不存在则创建 `pending`
3. 若已存在则覆盖：
   - `orchestratorSessionId`
   - `payload_json`
   - `status = pending`
   - `last_error = null`
   - `next_retry_at = null`
   - `started_at = null`
   - `completed_at = null`

这样同一会话连续触发多次部署时，后台始终只追最新目标。

### 5.2 runner

部署同步 runner 保留单进程消费，但消费来源改成数据库：

1. 周期性 `listRunnable()`
2. 取 `pending / failed(next_retry_at<=now) / running`
3. 对同一 `taskSessionId` 仍做进程内并发互斥
4. 成功后 `markCompleted()`
5. 仍需 follow-up 时直接再次 `upsertPending()`
6. 失败时 `markFailed()` 并写指数退避 `next_retry_at`

### 5.3 启动恢复

API 启动时做两件事：

1. 优先消费数据库里已有 runnable jobs
2. 再扫描旧的 `deploymentState/deploymentPanel`，把满足条件但尚未存在 job 的会话补录为 job

补录条件保持不变：

1. `bindingState=provisioning`
2. `bindingState=repair_required`
3. 已有 Railway project/service 信息，但缺少 `deploymentPanel`

### 5.4 收敛规则

后台同步完一次后：

1. 若 `panel.activeDeploymentPending=true`，继续 upsert `pending`
2. 若 `panel.bindingState=provisioning`，继续 upsert `pending`
3. 若 `analytics.status=pending_domain` 且已有公网 URL，继续 upsert `pending`
4. 否则 job 标记为 `completed`

## 6. 为什么不直接上 Redis / 外部队列

本仓库明确要求 Redis 只能在显式启用时使用，且当前部署主链已经以 DB / metadata 为主。

因此本轮不采用 Redis / BullMQ / 外部任务平台，原因是：

1. 会引入新的基础设施开关与运维面
2. 会让“部署后台同步”成为唯一依赖 Redis 的核心链路，和现有主链风格不一致
3. 当前问题的核心是“可恢复、可观察、可重试”，DB job 表已经足够解决

## 8. 验收口径

必须满足：

1. enqueue 后即使 API 重启，job 仍能继续被 runner 消费
2. 同一会话连续多次部署时，数据库里只保留一条活跃 deployment sync job
3. 任务失败后能按 `next_retry_at` 重试
4. job 完成后，`deploymentState` 与 `deploymentPanel` 一致收敛
5. 真实 E2E 主链仍通过

## 9. 与 14 号方案的关系

14 号方案解决的是“读写职责切分”和“多形态部署基线”。

15 号方案是在其基础上，把后台同步从“进程内可工作”升级成“持久化可恢复”。

两者关系是：

1. 14 定义同步职责边界
2. 15 定义同步任务载体
