# 20260502 会员与Agent权益管理技术方案 [尚未采用]

## 1. 目标

在不改动现有任务创建主链结构的前提下，引入一层“会员权限控制”，让平台能够按会员类型控制：

1. 默认积分发放
2. Agent `lite/pro/max` 可用范围
3. 用户当前会员状态展示
4. 管理后台对会员类型、用户归属和权益的配置

本方案只规划技术实现路径，不展开代码细节。

## 2. 设计边界

1. 会员体系与积分体系分离，会员只负责“默认权益”和“能力开关”
2. Agent 权限由服务端最终判定，前端只做展示与预拦截
3. 默认先覆盖任务创建主链与后台管理，后续再扩展到其他 Agent 场景
4. 会员类型先固定三档 Agent 级别：`lite`、`pro`、`max`
5. 会员不接支付，不接订单，不接自动续费

## 3. 现有链路判断

### 3.1 用户侧

当前任务创建主要通过以下链路完成：

- `apps/web/client/src/pages/Home.tsx`
- `apps/web/client/src/components/TaskCreationChat.tsx`
- `apps/web/client/src/hooks/useTaskCreationAgent.ts`
- `apps/api/src/routes/task-creation-routes.ts`
- `apps/api/src/agents/task-creation/*`

会员权限最关键的切点有三个：

1. 任务创建页的 Agent 选择
2. 会话/任务发起前的服务端校验
3. Agent runtime profile 的解析与暴露

### 3.2 管理侧

管理后台当前已有结构化管理路由与服务层：

- `apps/admin_management/server/routes/*`
- `apps/admin_management/server/services/*`
- `apps/admin_management/web/src/App.tsx`

会员管理建议复用当前管理后台的信息架构，不单独起新系统。

## 4. 技术架构

### 4.1 新增领域层

建议新增一组独立的会员领域对象：

- `membership_plans`
- `user_memberships`
- `membership_grants`
- `membership_audit_logs`

职责划分：

1. `membership_plans`：会员类型定义
2. `user_memberships`：用户当前归属
3. `membership_grants`：默认积分/权益发放记录
4. `membership_audit_logs`：后台操作审计

### 4.2 服务层拆分

建议在 `apps/api/src/services/` 新增以下服务：

1. `membership-plan-service`：会员类型 CRUD、启停、排序、生效期
2. `user-membership-service`：用户当前会员查询、分配、到期处理
3. `membership-benefit-service`：会员权益解析、Agent 级别判断、默认积分发放触发
4. `membership-access-service`：统一做权限判定，供路由和 Agent 层调用
5. `membership-audit-service`：记录后台变更、人工发放、降级等操作

### 4.3 API 层拆分

建议新增两类路由：

1. 用户侧查询路由：`/api/membership/*`
2. 管理侧配置路由：`/api/internal/membership/*`

用户侧只暴露只读信息，例如：

- 当前会员类型
- 可用 Agent 等级
- 剩余有效期
- 默认权益摘要

管理侧暴露写接口，例如：

- 创建/编辑/停用会员类型
- 分配用户会员
- 手动补发默认权益
- 查看变更记录

## 5. 权限判定链路

### 5.1 判定原则

Agent 权限判定遵循“先查会员、再查例外、最后放行/拒绝”的顺序：

1. 解析用户当前会员类型
2. 判断该会员是否包含目标 Agent 级别
3. 检查是否存在管理员手动授予的更高权限覆盖
4. 通过则继续任务创建或 Agent 切换
5. 不通过则返回明确错误码和可读文案

### 5.2 权限决策点

建议在以下位置同时做判定：

1. 前端 Agent 选择器：隐藏不可用项并给出原因
2. 任务创建接口：作为首个强校验点
3. 任务启动/切换接口：防止绕过前端
4. Agent runtime profile 解析：最终兜底
5. 管理后台用户详情：用于查看与修正归属

### 5.3 错误语义

建议定义稳定错误类型：

- `membership_required`
- `membership_level_forbidden`
- `membership_expired`
- `membership_plan_inactive`
- `membership_grant_conflict`

前端只展示可读文案，后端保留机器可识别错误码。

## 6. Agent 等级接入

### 6.1 现有等级

当前代码中已经存在统一的 Agent runtime tier：

- `lite`
- `pro`
- `max`

见 `apps/api/src/services/agent-runtime-profile-service.ts`。

这意味着会员权限最适合直接对接现有 tier，而不是新造一套平行枚举。

### 6.2 接入方式

建议把会员表里的可用 Agent 配置直接映射为：

- `allowedAgentLevels: ['lite']`
- `allowedAgentLevels: ['lite', 'pro']`
- `allowedAgentLevels: ['lite', 'pro', 'max']`

后端在需要调用 Agent 时，只判断用户会员允许的最高 tier 是否覆盖当前目标 tier。

### 6.3 与 runtime profile 的关系

`agent-runtime-profile-service.ts` 现在只负责从环境变量解析 runtime 配置，不关心用户权限。下一步应增加一层权限过滤：

1. 先算出系统可提供的 runtime profile
2. 再用会员权限过滤掉用户不可见的 tier
3. 前端只展示过滤后的结果

这样可以避免把会员逻辑直接塞进环境变量解析器里。

## 7. 数据流设计

### 7.1 会员创建与分配

流程：

1. 管理员创建会员类型
2. 配置默认积分、Agent 级别、权益项
3. 管理员将会员类型分配给用户
4. 系统写入 `user_memberships`
5. 若配置默认积分，触发积分发放交易
6. 写入 `membership_grants` 和 `membership_audit_logs`

### 7.2 用户访问

流程：

1. 用户进入任务创建页
2. 前端请求当前会员信息
3. 后端返回会员类型与可用 Agent 列表
4. 前端只渲染允许的 Agent
5. 用户发起任务时，后端再次校验
6. 校验通过后继续任务创建链路

### 7.3 会员变更

流程：

1. 管理员在后台修改用户会员
2. 后端更新 `user_memberships`
3. 写入审计日志
4. 如果是首次绑定或补发，写积分交易
5. 刷新用户侧缓存与前端状态

## 8. 缓存与一致性

### 8.1 缓存对象

建议缓存以下内容：

- 用户当前会员归属
- 会员类型定义
- 用户允许的 Agent tier 集合

### 8.2 缓存策略

1. 会员配置变更后主动失效缓存
2. 用户会员变更后按 `userId` 精准失效
3. 会员查询允许短 TTL，但权限判断必须支持实时回源

### 8.3 一致性要求

1. 前端展示可以短暂滞后
2. 服务端权限判断不能依赖过期展示数据
3. 会员变更与积分发放必须同事务或通过可靠补偿保持一致

## 9. 管理后台技术方案

### 9.1 页面结构

建议新增独立模块：

- 会员类型列表
- 会员类型编辑页/弹窗
- 用户会员列表
- 用户会员详情抽屉
- 权益矩阵视图
- 会员变更审计页

### 9.2 数据交互

后台页面应通过统一 service 层访问：

- 列表分页
- 详情查询
- 创建/编辑/停用
- 用户分配
- 默认积分补发
- 审计日志查询

### 9.3 与现有后台的整合

建议在 `apps/admin_management/web/src/App.tsx` 的导航中增加“会员管理”分组，和现有“计费管理”并列，而不是塞进同一张大表。

## 10. 实施顺序

### Phase 1: 数据与服务

1. 新增会员表结构
2. 新增会员服务层
3. 新增会员权限判定服务
4. 先补测试

### Phase 2: 用户侧展示与拦截

1. 接入 Agent 可用性查询
2. 任务创建页过滤 Agent 选项
3. 任务创建接口加强校验

### Phase 3: 管理后台

1. 新增会员管理导航
2. 做会员类型 CRUD
3. 做用户会员分配与审计

### Phase 4: 贯通积分发放

1. 会员默认积分发放接入积分体系
2. 补偿与审计补全
3. 做回归测试

## 11. 风险

1. **越权风险**：只在前端拦截不够，必须把校验放在任务创建与 Agent 切换后端。
2. **重复发放风险**：会员绑定和补发要区分，必须有发放记录幂等键。
3. **缓存失效风险**：用户会员变更后，必须主动清缓存。
4. **现有链路耦合风险**：不要把会员逻辑散落到多个 Agent 文件里，统一走 membership-access-service。
5. **模型层混淆风险**：会员是权限层，不是模型定价层，不要和现有计费 runtime config 混用。

## 12. 本次结论

建议采用“会员领域服务 + Agent tier 映射 + 双重校验”的实现方式：

1. 会员模型独立建表
2. 服务端统一判定 Agent 权限
3. 前端只展示可用范围
4. 积分发放走现有积分账本
5. 管理后台负责配置与审计

## 16. 事务边界

### 16.1 会员分配事务

建议单事务完成：

1. 写 `user_memberships`
2. 若需要则写积分交易
3. 写 `membership_grants`
4. 写 `membership_audit_logs`

任何一步失败都回滚，避免“会员已变更但积分没发”的半成品状态。

### 16.2 权限校验事务

权限校验本身不需要强事务，但需要保证：

1. 读取的是最新会员状态
2. 失效后能快速回收缓存
3. 出错时拒绝放行，不做静默降级

## 17. 实现分层

建议按以下层次推进：

1. `db`：表结构与索引
2. `service`：会员类型、用户会员、权益、审计
3. `route`：用户侧查询与管理侧配置
4. `ui`：管理后台与用户侧 Agent 选择器
5. `guard`：任务创建、启动、切换的服务端校验
