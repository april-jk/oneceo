# 部署编排 Skill 与自动挂载方案 [20260418-1612已采用]

## 1. 背景

当前 OneCEO 的部署能力已经具备：

- `deploy_application`
- `redeploy_application`
- `rollback_application_deployment`
- `get_application_deployment_status`

以及模板基线检查、自动注入、Railway 发布与状态同步。

但这条链路现在主要靠系统 prompt 约束 Altus 在部署时如何处理修复、重试和不同项目形态。对于以下场景，缺少一个明确、可复用、可扩展的“部署工作流知识面”：

- 纯 HTML 项目
- 前端静态 / JavaScript 项目
- Node.js 项目
- Python 项目
- Java 项目
- PHP 项目

目标不是把所有语言的发布都硬编码到平台基线服务里，而是先把“部署时的识别、修复、验证顺序”封装成平台 skill，并在使用部署功能时自动挂载给当前 managed run。

## 2. 目标

本次方案的目标只有两点：

1. 新增一个平台内置 skill，专门描述部署编排规则与多运行时处理路径。
2. 当用户发起部署相关请求时，后端自动把该 skill 附加到 managed run，无需用户手动勾选。

## 3. 非目标

本次不做：

- 新建一套独立 deployment agent runtime
- UI 强制新增 skill 选择步骤
- 一次性把 Java / PHP / Python / JavaScript / HTML / Node 的所有模板基线都下沉到平台自动补全服务

也就是说，这次做的是“skill 编排层 + 自动挂载层”，不是把所有运行时改成平台硬编码。

## 4. 方案设计

### 4.1 新增平台 skill：`deployment-orchestrator`

新增 seed skill：

- slug: `deployment-orchestrator`
- name: `部署编排`
- category: `deployment`

skill 需要覆盖以下内容：

1. 先识别项目形态，再决定修复和发布顺序。
2. 对部署请求，优先使用 managed deployment tools，不允许先给用户纯文本建议。
3. 当 deploy tool 返回 `retryable_repair_required` 时：
   - 若 `repair.category=template_compliance / deployment_configuration / workspace_missing`
     - 允许回到 workspace 修复
   - 若 `repair.category=resource_binding`
     - 禁止继续改本地模板
     - 应优先继续平台资源修复
4. 明确各类项目常见入口与应补齐的发布契约：
   - HTML / 静态 JS
   - Node.js
   - Python
   - Java
   - PHP
5. 明确发布前验证清单：
   - 构建入口
   - 启动入口
   - `oneceo.manifest.json`
   - 健康检查
   - analytics 注入入口
6. 明确发布完成后的验证顺序：
   - deploy tool success
   - deployment status / URL
   - 不再把本地 debug 预览误判为线上发布成功

### 4.2 Skill 资源拆分

skill body 保持简洁，只写工作流规则。

按运行时拆分参考资源：

- `references/runtime-classifier.md`
- `references/static-html-js.md`
- `references/nodejs.md`
- `references/python.md`
- `references/java.md`
- `references/php.md`
- `references/deploy-repair-loop.md`

这样 Altus 只在需要时加载对应运行时说明，不把所有 runtime 细节一次性塞进上下文。

### 4.3 自动挂载触发点

在 `AltusManagedInputService.submit(...)` 内增加自动 skill 选择逻辑：

1. 读取用户原始输入内容
2. 判断是否属于部署相关意图：
   - deploy / publish / go live / 上线 / 发布 / 部署
   - redeploy / republish / 重新部署 / 重发
   - rollback / revert deployment / 回滚
   - deployment status / 发布状态 / 部署状态
3. 若命中部署意图：
   - 从当前用户 `availableSkills` 中查找 `deployment-orchestrator`
   - 若用户未显式选择该 skill，则自动追加到 `metadata.skills`
4. 再走原有 `resolveSelectionsForSession(...)`

这样技能最终仍走现有用户态 skill 解析链，不引入新的 skill 注入通道。

## 5. 为什么要放在 managed input，而不是 prompt 层硬编码

因为 skill 有两个平台价值：

1. 它是可治理资产：
   - 可在 skill 管理后台查看、升级、发布 revision
   - 可随版本演进，不必持续膨胀系统 prompt
2. 它是可组合能力：
   - 后续可以和“需求拆解”“测试清单”等平台 skill 叠加
   - 部署 run 能明确知道自己带了什么 skill，而不是只有隐式 prompt

## 6. 验收标准

满足以下条件即通过：

1. 平台 skill catalog 中存在 `deployment-orchestrator`
2. 用户发送“帮我部署当前项目”时，即使未手动选择 skill：
   - `metadata.skills` 会自动包含该 skill
   - `managedSkillContext` 会解析出该 skill
3. 非部署类普通消息不会自动挂载该 skill
4. 显式已选择该 skill 时，不重复注入
5. 现有附件上传、手动 skill 选择链路不回归

## 7. 风险

风险主要有两项：

### 7.1 误判普通消息为部署请求

解决方式：

- 只匹配明确部署动词
- 优先覆盖“部署、发布、重部署、回滚、状态查询”这些高置信词
- 不对泛化的“上线文案、发布说明”做宽松匹配

### 7.2 自动 skill 与用户手动 skill 重复

解决方式：

- 自动挂载时按 `skillId + revisionId` 去重
- 若用户已显式选择，自动逻辑不再重复追加

## 8. 结论

这次改动的本质是把部署知识从“分散在系统 prompt 和零散判断里”收敛成一个平台 skill，并在部署入口自动挂载。

这样做以后：

- 部署能力更可治理
- 多运行时场景更容易扩展
- 部署请求能默认走统一的 skill 编排链
- 不需要用户每次手动选“部署 skill”
