# 20260328 发送后用户消息偶发不可见问题与修复方案

## 1. 现象

用户发送消息后，偶发看不到自己刚发出的那条消息。

该问题不是“消息一定没有发送出去”，而是前端消息列表存在竞态和错误去重，导致本地刚插入的 user message 被覆盖或被误判为重复消息。

## 2. 根因

本次排查确认有两个原因叠加：

### 2.1 历史同步覆盖了尚未落库的本地 user message

前端在 `sendChatInput(...)` 中会先乐观插入一条本地 `user_input` 消息，但 `sessionId` 一旦变化，就会立即触发 `loadHistory(sessionId)`。

而 `loadHistory(...)` 内部原先有多处直接覆盖：

- `setMessages(cached.messages)`
- `setMessages(normalized)`

如果此时后端还没有把刚发送的 `user_input` 持久化到 recent/history 接口，这次历史同步就会把本地那条消息冲掉。

### 2.2 连续两次发送相同文本时，会被前端误去重

`mergeRealtimeMessage(...)` 里原先对 `user_input/user_response` 做了“按内容去重”的逻辑：

- 只要上一条也是同类型 user message
- 且文本完全相同

就直接判定为重复，不再插入。

这会误伤正常场景，例如连续两次发送“继续”、“好的”、“收到”。

## 3. 修复目标

最短正确路径：

- 历史加载时保留尚未持久化的本地 user message
- 不再按“文本内容相同”去吞掉有明确 messageKey 的用户消息

## 4. 修复方案

### 4.1 保留 pending local user messages

在 `apps/web/client/src/hooks/useTaskCreationAgent.ts` 中新增：

- `resolveExplicitAgentMessageKey(...)`
- `isPendingLocalUserMessageForSession(...)`
- `mergePendingLocalUserMessages(...)`
- `messagesRef`

核心规则：

- 只保留当前 session 下的 `user_input / user_response`
- 且这些消息尚未带 `sessionEventSeq / timelineCursor`
- 说明它们还是前端本地乐观消息，尚未被历史接口正式回放

随后把这层保护接入到：

- `applyHistoryState(...)`
- `loadHistory(...)` 读取 cached messages 的阶段

这样历史同步再回来时，不会把本地刚发出的用户消息直接覆盖掉。

### 4.2 修正错误的用户消息去重规则

在 `mergeRealtimeMessage(...)` 中，把 `user_input / user_response` 的重复判断收紧为：

- 只有在新旧两条消息都 **没有显式 messageKey**
- 且文本完全相同

才认为是重复。

这样带明确 `messageKey` 的两次合法发送，即使文本相同，也会正常显示。

## 5. 修改位置

- `apps/web/client/src/hooks/useTaskCreationAgent.ts`

## 6. 预期效果

- 新 session 发送第一条消息时，本地 user message 不会再被历史回放冲掉
- 历史 reconcile 期间，刚发送的用户消息不会再偶发消失
- 连续两次发送相同文本时，两条消息都会保留

## 7. 验证

- `pnpm --filter web check` 通过
- 从代码链路上看，历史覆盖点已经改为“先合并 pending local user messages，再更新消息列表”
- 用户消息去重逻辑也不再按纯文本粗暴去重，而是优先依赖显式 `messageKey`
