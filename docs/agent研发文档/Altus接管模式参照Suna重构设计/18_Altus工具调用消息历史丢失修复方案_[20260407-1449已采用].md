# 18_Altus工具调用消息历史丢失修复方案_[20260407-1449已采用]

日期：2026-04-07  
关联现象：用户在 managed run 中观察到多条工具调用日志，但 run 结束后历史仅保留 assistant 文本与 `managed run 已完成`，工具调用日志全部消失。

## 1. 问题现象与复现

复现场景（与用户反馈一致）：

1. 在 Altus managed 模式发起任务，期间出现多个 `tool_call_*` 事件。
2. 运行中可看到工具调用卡片/日志。
3. run 结束后（或刷新/重进会话后），历史中不再显示工具调用日志。

表现为“工具调用消息丢失、未被正确保存”。

## 2. 结论摘要（确定性根因）

根因是**主链数据落点不一致**：

1. `tool_call_started / tool_call_progress / tool_call_completed / tool_call_failed` 仅写入 `task_session_run_events`（run event 流）。
2. 历史接口 `messages/recent` 与 `messages/history` 的 managed 主事实源是 `conversation_messages`。
3. run 终态后前端触发 `managed_recovery`，用历史接口结果重建消息列表；该列表不包含 `tool_call_*`，从而把运行中看到的工具日志整体替换掉。

因此不是“偶发渲染问题”，而是**后端未将 managed 工具事件投影到会话历史表**导致的确定性丢失。

## 3. 代码级证据链路

### 3.1 工具事件仅写 run event

- 文件：`apps/api/src/services/altus-run-coordinator.ts`
- 现状：`tool_call_*` 全部走 `eventWriter.appendRunEvent(...)`，未调用 `persistTimelineMessage(...)` 写入 `conversation_messages`。

### 3.2 run event writer 不写 conversation timeline

- 文件：`apps/api/src/services/altus-run-event-writer.ts`
- 现状：`appendRunEvent(...)` 仅写：
  - `task_session_run_events`
  - redis run state（启用时）
  - SSE publish
- 未写 `taskCreationSessionDAO.addMessage(...)`。

### 3.3 历史读取来自 conversation timeline

- 文件：`apps/api/src/routes/task-creation-routes.ts`
- 现状：
  - managed 会话在 `resolveRenderableTimelineMessages(...)` 走 DB timeline（`conversation_messages`）作为主事实源。
  - `messages/recent` / `messages/history` 最终都基于该 timeline 输出。

### 3.4 前端终态重放会覆盖实时态

- 文件：`apps/web/client/src/hooks/useTaskCreationAgent.ts`
- 现状：
  - `run_completed / run_failed / run_stopped` 后调用 `loadHistory(..., { reason: 'managed_recovery' })`。
  - `applyHistoryState(...)` 用历史结果 `setMessages(...)`。
  - `mergeWithPendingLocalMessages(...)` 只保留 pending user message，不保留 managed 工具流临时消息。

## 4. 与近期两次改动的关系

### 4.1 与“吞消息修复（Issue #31）”的关系

- 该次改动将 managed history 收敛为 DB 事实源，是正确方向。
- 但 `tool_call_*` 未同步纳入 conversation timeline，导致“history 事实源收敛后”工具日志缺口被放大并稳定暴露。

### 4.2 与“补充信息重复修复”的关系

- `clarification_requested` 的 `messageKey` 对齐与去重逻辑不涉及 `tool_call_*` 落库路径。
- 该改动不是本问题根因。

## 5. 修复目标

1. managed `tool_call_*` 在 run 结束后仍可从历史接口稳定回放。
2. 同一会话跨刷新、跨设备，工具调用日志可见性一致。
3. 不引入兼容补丁分支，直接修正主链持久化口径。

## 6. 修复方案（最短路径）

## 6.1 在 run event 写入点同步投影工具事件到 conversation timeline（先写库，再推流）

实施点：

- 文件：`apps/api/src/services/altus-run-event-writer.ts`
- 在 `appendRunEvent(...)` 内，对以下事件增加会话消息投影：
  - `tool_call_started`
  - `tool_call_completed`
  - `tool_call_failed`
  - `tool_call_progress`（按需，默认可不入库，仅保留 started/completed/failed）

落库目标：

- `taskCreationSessionDAO.addMessage(...)`
- `role='agent'`
- `messageType='executor_event'`
- `content=payload.content`（缺省回退事件描述）
- `metadata` 至少包含：
  - `executionMode='managed'`
  - `executor='altus'`
  - `eventType`
  - `runId`
  - `toolName`
  - `toolCallId`
  - `arguments` / `outputPreview` / `error`（若存在）

`messageKey` 规则：

- 有 `toolCallId`：`managed:<runId>:tool:<toolCallId>`
- 无 `toolCallId`：`managed:<runId>:<eventType>:<sequence>`

说明：

- 同 `toolCallId` 事件会按同 key upsert，保留该工具调用最新状态；多工具调用保持多条可见。
- 为避免 `run_completed` 先到前端、工具事件尚未入库导致的恢复竞态，必须保证顺序为：
  1. 写 `task_session_run_events`
  2. 写 `conversation_messages` 投影
  3. 发布 SSE 事件

## 6.2 补齐 metadata 白名单，避免落库后字段被裁剪

实施点：

- 文件：`apps/api/src/db/dao/task-creation-session.dao.ts`
- 文件：`apps/api/src/routes/task-creation-routes.ts`

补充字段白名单（最少）：

- `toolCallId`
- `arguments`
- `error`
- `executionMode`

（`toolName`、`outputPreview` 已在现有链路中处理，但需复核）

## 6.3 保持前端合并策略不变

本问题根因在后端持久化缺失，不在前端“同 key 合并”规则；前端无需再加补丁式豁免逻辑。

## 7. 验收标准

1. 单次 run 含多个工具调用时，run 完成后历史中仍可看到对应 `executor_event`（managed tool）条目。
2. 刷新页面后、重进会话后、跨端打开会话，工具日志条目数量与顺序一致。
3. `messages/recent` 与 `messages/history` 返回的最后一条 managed tool 记录 `messageKey`、`eventType` 一致。
4. 现有澄清去重、assistant 分段、run 状态胶囊行为不回归。

## 8. 测试计划

   - 断言 `tool_call_*` 进入 `conversation_messages`。
   - 断言同 `toolCallId` upsert 语义正确。
2. 覆盖 `messages/recent` / `messages/history` 在 managed 会话下可返回 tool 事件。

前端：

2. `Home` 渲染用例断言 `managed_tool` 卡片可从 history 数据重建。

## 8.1 历史数据回填（避免“修完代码但旧会话仍缺日志”）

为确保用户当前已发生的问题能立即恢复，需要补一条历史回填任务：

1. 从 `task_session_run_events` 筛选 `tool_call_started/completed/failed`。
2. 按本方案 `messageKey` 规则投影写入 `conversation_messages`（upsert）。
3. 回填后触发对应 session 的 recent window 重建（或通过现有 DAO 自动重建）。

回填范围建议：

1. 先按用户反馈会话和近 7 天 run 执行。
2. 校验通过后再扩到全量历史区间。

## 9. 风险与边界

1. 本方案只修复 managed 工具事件历史持久化，不调整 direct mode。
2. 本方案不新增降级/兼容分支；若落库失败应按现有错误路径直接暴露，避免“看似成功但历史缺失”。
3. 若启用 Redis recent cache，需确认该投影写入后缓存刷新策略可见（避免旧缓存掩盖新落库）。

## 10. 20260526 联网工具时间线展示优化

背景：用户在接管会话中看到 `web_search` / `web_extract` 这类内部工具名，无法直接理解当前任务正在做什么。联网搜索类工具应以用户语言呈现当前动作和目标内容，而不是暴露底层 tool id。

前端展示约束：

1. `web_search` 在运行中显示为 `正在联网搜索：{query}`；完成后显示为 `已联网搜索：{query}`。当无法从工具参数或输出预览读取 query 时，回退为 `正在联网搜索内容` / `已联网搜索内容`。
2. `web_extract` 在运行中显示为 `正在解析网页内容`；完成后显示为 `已解析网页内容`。若能读取 URL，则追加主域名；多 URL 时显示 `等 N 个页面`。
3. `web_search` 与 `web_extract` 运行中左侧图标使用旋转状态图标；完成后恢复各自静态工具图标，避免用户误以为任务已停滞。
4. 展示层必须同时读取 `metadata.arguments` 与历史消息中的 `metadata.rawArguments`，确保实时 SSE 与历史重放一致。
5. 该优化只改变用户可见时间线文案与图标状态，不改变 managed run event 的落库、messageKey、upsert 或工具执行语义。

验证：

1. `apps/web/client/src/tests/managed-run-status-dialogue.test.ts` 覆盖 `web_search` 运行态/完成态文案，以及 `web_extract` 多 URL 运行态文案。
2. `pnpm --filter web exec vitest run src/tests/managed-run-status-dialogue.test.ts`
3. `pnpm --filter web check`
