# 20260403 Sandbox 管理动作与会话关联方案 [20260403-2108已采用]

更新时间：2026-04-03

## 1. 背景

当前 `apps/admin_management` 的 `执行环境管理` 已经具备：

1. `runtime-registry` 首屏总览与风险筛选
2. Sandbox 详情查看
3. 手工新建 Runtime
4. `pause / resume / close / archive / restore / connectivity-check`

但还缺少以下管理闭环：

1. 管理员无法在首屏明确看到 “sandbox 属于哪个 task session / 对话会话”
2. 缺少面向机器治理的统一动作区，当前动作分散且语义偏运行态排障
3. 缺少“重启”能力
4. 缺少“归档历史”列表，管理员只能看到当前 archive 状态字段，无法查看历次快照/归档记录

## 2. 目标

本轮目标：

1. 在后台把 E2B sandbox 与 task session / 对话会话明确关联起来
2. 在 `执行环境管理` 中提供统一的机器管理动作
3. 增加归档历史查看能力
4. 保持当前 `runtime-registry` 首屏性能，不回退到全量 metadata 拉取

## 3. 范围

本轮包含：

1. sandbox 与 session 关联展示
2. 开机
3. 关机
4. 重启
5. 手动归档
6. 归档历史列表

本轮不包含：

1. 新的自动归档策略
2. 新的 archive 存储格式
3. 主站通用 `/api/sandbox/environment` 返回结构重构
4. 脱离现有 E2B / OSAC / archive 链路的新实现

## 4. 关键现状

### 4.1 已有动作

当前后台已经具备以下动作：

1. `pause`
2. `resume`
3. `close`
4. `archive`
5. `restore`

对应链路：

1. 管理后台路由：`apps/admin_management/server/routes/sandbox-management-routes.ts`
2. 管理后台服务：`apps/admin_management/server/services/sandbox-management-service.ts`
3. 主站 sandbox 路由：`apps/api/src/routes/sandbox-routes.ts`
4. 归档服务：`apps/api/src/services/sandbox-archive-service.ts`

### 4.2 缺失能力

当前缺失：

1. `restart`
2. 归档历史列表
3. 首屏明确的 session 关联卡片或关联列

### 4.3 e2b 语义限制

当前 `e2bConnector` 已暴露：

1. `createSandbox`
2. `killSandbox`
3. `pauseSandbox`
4. `resumeSandbox`

没有现成的原子 `restartSandbox`。

因此“开机/关机/重启”不能照搬 KVM 语义，必须按当前 E2B 实际语义设计。

## 5. 推荐语义

### 5.1 开机

推荐把“开机”定义为：

1. 对 `paused` sandbox 执行 `resume`
2. 对已归档但当前 sandbox 已失活的 session，执行 “restore + 重新拉起 runtime”

不推荐把“开机”定义成：

1. 对 `closed / killed` sandbox 原地开机

原因：

1. E2B 当前没有 KVM 式“已关机机器原地上电”的稳定语义
2. 对已关闭 sandbox，更接近“恢复会话运行态”而不是“给同一台机器上电”

### 5.2 关机

推荐把“关机”定义为：

1. `pause` 为优先推荐动作
2. `close` 为强动作
3. 管理后台的 `close` 必须走主站 `closeEnvironment` 主链，不能只在管理端直连 E2B `kill`

页面上需要明确区分：

1. `暂停`：保留当前 sandbox，可恢复
2. `关机`：关闭当前 sandbox，不保证原实例继续存在

### 5.3 重启

推荐把“重启”定义为：

1. 若 sandbox 当前为 `running / paused`
2. 执行：
   `archive current workspace` -> `close current sandbox` -> `restore archived workspace` -> `start runtime` / `resume session runtime binding`
3. 若当前状态已经是 `ready / closed`
   - 不再对旧 sandbox 做 `archive / close`
   - 直接按已绑定 `task session` 执行 `start runtime`
4. 若 `runtime start` 复用旧 `orchestratorSessionId` 时命中 E2B “实例不存在 / 已停止 / not running anymore / failed to connect” 类错误
   - 必须统一视为旧 sandbox 已失效
   - 先标记旧环境 `closed`
   - 再走新的 runtime provision

不采用“先 kill 再 connect 同一 sandbox”这类伪重启语义。

原因：

1. 这不符合 E2B 当前稳定能力边界
2. 会导致管理员误以为自己管理的是同一物理实例
3. 对业务真正需要的其实是“保留工作区状态后重建可运行环境”

### 5.4 归档

“归档”继续复用现有 `archiveSandboxWorkspace()` 链路，不新建平行实现。

补充约束：

1. 仅 `running / paused` 允许触发新的手动归档
2. `ready / closed` 若当前 archive 已是 `up_to_date / archived`，应返回明确 no-op，而不是继续对不存在的 sandbox 执行归档

## 6. UI 设计

### 6.1 Runtime 列表新增会话关联信息

首屏主表调整：

1. `Task Session` 列保留
2. 在次级行增加：
   - 会话标题
   - 会话状态
   - 若存在对话 session id，则支持复制
3. `Task Session` 本身必须可点击，允许管理员直接跳到 `对话管理 / 任务创建会话` 的对应详情
4. 对同 `taskSessionId` 下已被新实例接管并自动收口的历史记录：
   - 保持 `closed` 状态展示
   - 在状态区追加 `已收口` 治理标记
   - 明确展示“已由哪个 replacement sandbox 接管”与收口时间
   - replacement sandbox 必须可点击，允许管理员直接跳转到接管中的新实例详情
   - 不得把该治理信息混入风险标签，避免稀释真正异常信号
5. `操作` 列直接暴露机器动作：
   - 详情
   - 开机 / 暂停
   - 关机
   - 重启
   - 归档

### 6.2 详情页新增“会话关联”区块

详情页增加固定区块：

1. Task Session ID
2. Task 标题
3. Task 状态
4. orchestratorSessionId
5. sandboxId
6. executor
7. 最近活跃原因

如果能拿到对话消息摘要，则显示：

1. 最近一条用户消息时间
2. 最近一条用户消息摘要（截断）

补充约束：

1. 若当前记录属于“同任务新实例接管后自动收口”的历史记录，详情页 `Overview` 必须展示治理时间线卡片
2. 至少明确展示：
   - 收口原因
   - replacement sandbox id
   - 收口时间
3. replacement sandbox id 必须可点击并直接打开该 sandbox 的详情弹层
4. `Task Session` 必须可点击并直接切到 `对话管理 / 任务创建会话` 中对应会话
5. `对话管理` 中的 `编排 Session` 也必须可点击，并能反向跳回 `执行环境管理` 中对应 sandbox 的详情
6. 该信息属于治理轨迹，不得塞回风险标签或调试原始 JSON 区块

补充约束：

1. `对话管理` 内的 `Sandbox 环境记录` 不允许默认以整块原始 JSON 作为主展示
2. 首屏必须先展示：
   - primary environment 摘要
   - related environments 数量与聚合摘要列表
   - replacement sandbox 接管信息（若存在）
3. 原始 `primaryEnvironment / relatedEnvironments` 只能放到可展开区域，作为调试补充信息
4. related environments 默认按 `status + executor + archive status` 聚合展示，每组再展开具体实例
5. 在实例分组之前，必须先提供一层“治理原因聚合”摘要，按 `dedupeReason` 聚合显示数量与最近更新时间，便于管理员先判断这些历史记录为何被收口
6. 治理原因聚合卡必须可点击，点击后仅显示该治理原因下的实例分组，并提供显式“清除治理筛选”入口
7. 实例分组卡也必须支持二级筛选；点击某个分组后仅显示该分组，并默认展开其具体实例，同时提供显式“清除实例组筛选”入口
8. 管理后台面向管理员的可见 UI 文案必须默认中文化；允许保留品牌名、接口名和调试 JSON 原始字段，但标题、按钮、页签、状态标签、卡片说明和表头不允许继续直接暴露英文产品词或英文状态枚举

## 7. 后端设计

### 7.1 sandbox 与 session 关联

当前 `runtime-registry` 已经通过：

1. `tracked environment.metadata.taskSessionId`
2. `taskSession.runtime.orchestratorSessionId`

建立弱关联。

本轮要求把该关联提升为页面一等信息，而不是只用于后台计算。

补充约束：

1. 同一个 `taskSessionId` 在任一时刻只能保留一个 active tracked sandbox
2. 当 `runtime-start` 成功绑定新的 active sandbox 后，系统必须自动将同任务下其余 tracked sandbox 收口为 `closed`
3. 若旧实例仍可连接，应同步关闭旧实例，避免后台因为历史重试或异常重绑保留多台重复机器

### 7.2 restart 动作

新增后台动作接口：

1. `POST /api/sandbox-management/environments/:sandboxId/restart`

推荐服务实现：

1. 先解析当前 runtime detail
2. 若存在 sandbox workspace，先手动归档
3. 关闭当前 sandbox
4. 若可从 archive 恢复，则恢复 workspace
5. 重新启动运行态
6. 刷新 metadata 与 runtime registry

注意：

1. 重启不是直接调用新的 E2B 原子 API
2. 必须沿用现有 archive / restore / runtime-start 主链
3. 管理后台触发 `runtime-start` 时不得直接走用户态 `/api/task-creation/.../runtime/start`
4. 必须通过内部管理态接口启动，避免伪造 `X-User-Id` 或丢失会话归属校验语义
5. 管理后台对 `runtime-start` 这类非幂等动作不得使用通用超时重试；必须改成单次请求并给足启动超时窗口，避免重复拉起多台 sandbox

### 7.3 归档历史

新增主站内部接口：

1. `GET /api/internal/sandbox/archive-history?taskSessionId=...`
2. 或 `GET /api/internal/sandbox/archive-history?sandboxId=...`

数据来源优先级：

1. R2 metadata manifest
2. 当前环境 metadata 中的 `r2ArchiveKey / r2ArchiveSnapshotKey / r2ArchiveMetadataKey / r2ArchiveSha256`

如果当前系统尚未持久化完整历史表，则本轮先做“基于 manifest + 当前 metadata 的只读历史视图”，不额外引入新表。

## 8. 验收标准

1. 管理员能在详情页明确看到 sandbox 与 task session 的关联关系
2. 管理员能从后台触发开机、关机、重启、归档动作
3. 重启动作不会绕开现有 archive / restore 主链
4. 旧 sandbox 已失效时，`runtime start` 不得把 E2B 原始英文错误直接暴露给管理端；必须转成“旧实例失效并重建”的主链处理
5. 归档历史至少能展示当前可追溯的 snapshot/archive 记录
6. `runtime-registry` 首屏性能不能回退到整份 metadata 拉取
7. `runtime-registry` 使用的内部摘要接口在做 metadata 裁剪时，必须保留治理展示必需字段：
   - `dedupeReplacedAt`
   - `dedupeReason`
   - `dedupeReplacementSandboxId`
   否则后台列表无法正确显示“已收口”历史记录

## 9. 风险与约束

1. “开机”在 E2B 语义下不是 KVM 式电源管理，文案必须明确
2. “重启”本质是“归档后重建运行态”，不能误导成原实例热重启
3. 归档历史如果现阶段没有独立持久化表，只能先做只读聚合视图
4. 若你要求“原地重启同一台机器”，需要先确认 E2B 是否存在稳定的官方能力，否则本方案不采用伪实现
