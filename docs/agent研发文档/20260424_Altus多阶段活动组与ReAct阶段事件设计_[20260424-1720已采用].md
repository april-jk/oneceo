# 20260424_Altus多阶段活动组与ReAct阶段事件设计_[20260424-1720已采用]

## 1. 背景

用户反馈 Manus 的执行流不是单个大工具组，而是会出现多个连续阶段：

1. 每个阶段有明确标题，例如“升级项目为全栈架构”“设计数据库模型并创建迁移”；
2. 阶段标题左侧有完成态图标，阶段内部有一条竖向时间线；
3. 阶段内先显示自然语言过程说明，再显示若干工具胶囊；
4. 一个任务会拆成多个阶段，每个阶段可以包含多条工具调用和多段说明。

当前 OneCEO 已经具备“工具调用 + 中间 run_status + 活动组”的第一层展示能力，但仍偏事件流折叠，不是真正的阶段化执行。

## 2. 现状定位

### 2.1 后端事件层

当前 managed run 的事件写入集中在：

- `apps/api/src/services/altus-run-event-writer.ts`
- `apps/api/src/services/altus-run-coordinator.ts`
- `apps/api/src/services/altus-managed-tool-executor.ts`

现有事件类型主要包括：

1. `run_status`
2. `tool_call_started`
3. `tool_call_progress`
4. `tool_call_completed`
5. `tool_call_failed`
6. `assistant_delta`

`altus-run-event-writer.ts` 会把 `tool_call_*` 投影为 `conversation_messages.executor_event`，把非 starting 的 `run_status` 投影为 `status_update`。

### 2.2 执行循环层

`AltusRunCoordinator.runModelLoop()` 当前以“模型轮次 + 工具结果”推进：

1. 每轮模型调用前写入一个 `run_status`；
2. 模型返回工具调用后，逐个执行工具；
3. 工具执行完成后把结果追加回 messages；
4. 下一轮再由模型决定继续调用工具还是 `complete_task`。

这接近 ReAct 的基本形态：

`reasoning/status -> action/tool -> observation/result -> next action`

但现在的 ReAct 状态是隐式的，只存在于模型上下文与工具事件里，没有显式的“阶段对象”。

### 2.3 Todo 层

`todowrite` 当前是平铺 Todo 快照：

- schema 只有 `content / status / activeForm`
- 规则要求运行中 exactly one `in_progress`
- 前端可以显示 Todo，但 Todo 没有阶段 ID、阶段标题、阶段摘要、阶段内工具归属

这使得 Todo 更像任务清单，不足以直接驱动 Manus 那种多段 UI。

### 2.4 前端展示层

当前前端在 `apps/web/client/src/pages/Home.tsx` 做了展示层分组：

1. 连续的 `managed_status` 与 `managed_tool` 会合并成 `managed_activity_group`；
2. 组标题从最近状态或工具摘要中推导；
3. 组状态按最后一个工具结果判断；
4. 工具行展示用途摘要，详细信息留在 replay / hover / diff。

这解决了单段流水账问题，但分组边界仍是“连续事件”推导，不是后端权威阶段。

## 3. Manus 能做到多段的原因判断

Manus 图里的多段结构不是 React 组件自然产生的，也不是单纯前端把工具列表分块。

更可能是运行时有明确的阶段模型：

1. Agent 在开始一段工作前，先声明阶段标题和目标；
2. 阶段内的工具调用都归属到当前阶段；
3. 阶段完成后，运行时发出阶段完成事件或更新阶段状态；
4. 下一阶段开始时再创建新的阶段节点。

也就是说，关键不是“React 模式”，而是 ReAct / planning loop 中有显式的 `phase` 或 `activity` 边界。

前端只负责把这些边界渲染成时间线。

## 4. OneCEO 的目标能力

目标不是复刻 Manus 的 DOM，而是实现同等信息结构：

1. 一个 managed run 可以包含多个 activity stage；
2. 每个 stage 有：
   - `stageId`
   - `title`
   - `status`
   - `summary`
   - `startedAt`
   - `completedAt`
   - `order`
3. 每个 `run_status` 和 `tool_call_*` 可以归属到某个 `stageId`；
4. 前端按 `stageId` 分组，而不是按连续事件猜测；
5. 刷新、恢复、历史加载后仍能稳定还原多段结构。

## 5. 推荐方案

### 5.1 新增轻量阶段事件，不改工具协议

新增 managed run 事件类型：

1. `activity_stage_started`
2. `activity_stage_updated`
3. `activity_stage_completed`

事件 payload：

```json
{
  "stageId": "stage-1",
  "title": "设计数据库模型并创建迁移",
  "summary": "升级为全栈架构，添加数据库支持，准备创建表结构与 API。",
  "status": "running",
  "order": 1
}
```

同时给现有事件可选增加：

```json
{
  "activityStageId": "stage-1"
}
```

### 5.2 阶段来源优先用 `todowrite`

不建议第一步新增 `activity_stage_start` 工具让模型手动维护阶段，因为这会增加模型负担和误调用概率。

更稳的方式是复用现有 `todowrite`：

1. 当 `todowrite` 成功完成时，后端读取最新 Todo；
2. 找到当前 `in_progress` todo；
3. 如果当前 in_progress todo 与上一个活动阶段不同，则自动创建或切换 `activity_stage_started`；
4. 后续工具事件默认归属到当前 stage；
5. 当 Todo 状态变为 completed 时，后端更新对应 stage completed。

这样可以用已有模型行为驱动阶段，而不是引入一个新工具让模型额外学习。

### 5.3 增强 Todo schema，但保持兼容

当前 Todo schema：

```ts
{
  content: string;
  status: 'pending' | 'in_progress' | 'completed';
  activeForm?: string;
}
```

建议扩展为：

```ts
{
  content: string;
  status: 'pending' | 'in_progress' | 'completed';
  activeForm?: string;
  stageTitle?: string;
  stageSummary?: string;
}
```

兼容规则：

1. 没有 `stageTitle` 时使用 `activeForm || content`；
2. 没有 `stageSummary` 时使用最近一条语义 `run_status`；
3. 旧历史 Todo 不需要迁移。

### 5.4 后端维护当前 stage 状态

在 `AltusRunLoopSnapshot` 或 Redis run state 中增加：

```ts
currentActivityStageId: string | null;
currentActivityStageTitle: string | null;
activityStageOrder: number;
```

工具事件写入时：

1. 读取当前 stage；
2. 给 `tool_call_started/progress/completed/failed` payload 注入 `activityStageId`；
3. 给 `run_status` payload 注入 `activityStageId`；
4. `complete_task` 触发前，把最后一个 running stage 标记 completed。

### 5.5 前端按 stage 分组

前端 `groupManagedActivityItems()` 从现在的“连续事件分组”升级为：

1. 如果事件有 `activityStageId`，按 stage 分组；
2. `activity_stage_started/updated/completed` 作为 stage header 的权威来源；
3. 没有 `activityStageId` 的旧历史继续走当前连续分组逻辑；
4. stage 内继续使用当前的用途摘要工具胶囊。

这样可以兼容旧数据，又能支持 Manus 式多段结构。

## 6. 不推荐方案

### 6.1 只靠前端按 Todo 文本猜阶段

问题：

1. 刷新后可能因为消息裁剪导致阶段丢失；
2. 工具和 Todo 之间没有稳定归属；
3. 多个 Todo 文案相似时容易错分。

### 6.2 让模型每次手写阶段 Markdown

问题：

1. 不可稳定回放；
2. 容易和最终答复混在一起；
3. 工具归属无法结构化。

### 6.3 新增重型 plan/task 子系统

问题：

1. 改动面过大；
2. 会和现有 `todowrite`、run event、replay drawer 重叠；
3. 当前目标只是执行流展示，不需要先重构任务系统。

## 7. 分阶段实施建议

### Phase 1：后端活动阶段事件

范围：

1. 扩展 `AltusRunLoopSnapshot`；
2. 在 `todowrite` completed 后生成或切换 activity stage；
3. 给后续 `run_status` 和 `tool_call_*` 注入 `activityStageId`；
4. 投影 `activity_stage_*` 到 timeline。

验证：

1. 一个复杂任务多个 Todo 会产生多个 stage；
2. 每个 stage 内工具归属稳定；
3. `complete_task` 前最后 stage 被标记 completed。

### Phase 2：前端按 stage 权威分组

范围：

1. `ChatItem` 增加 managed activity stage item；
2. `groupManagedActivityItems()` 优先按 `activityStageId` 分组；
3. stage header 用后端 stage title/status；
4. 旧历史继续 fallback 到连续分组。

验证：

1. 多 stage 截图接近 Manus 结构；
2. 中途失败后恢复的 stage 状态正确；
3. 刷新后阶段数量和标题不变化。

### Phase 3：优化 prompt 与 Todo schema

范围：

1. `todowrite` schema 增加 `stageTitle/stageSummary`；
2. managed prompt 要求复杂任务的 Todo 采用用户可读阶段标题；
3. 工具用途摘要继续由平台生成，禁止模型把原始日志塞进标题。

验证：

1. “2048 游戏升级数据库支持”应出现：
   - 升级项目为全栈架构
   - 设计数据库模型并创建迁移
   - 实现后端 API 接口
   - 接入前端与验证
2. 每段都有过程说明和工具胶囊。

## 8. 风险与控制

### 8.1 模型不稳定更新 Todo

控制：

1. 仍保留当前连续事件 fallback；
2. 只有 `taskIntentProfile.todoRequired=true` 时强阶段化；
3. 简单任务不强制拆阶段。

### 8.2 阶段过多导致噪音

控制：

1. stage 数量建议 2-8；
2. 每个 stage 至少包含一个工具或一条过程状态；
3. 空 stage 不投影到前端。

### 8.3 与 replay drawer 重复

控制：

1. 主对话展示用户可理解进度；
2. replay drawer 展示工具级详情；
3. 两者用同一批 event，只是投影视图不同。

## 9. Claude Code 源码对照结论

对照路径：`referance/claudecode_src`。

结论：Claude Code 的设计理念与 Manus 截图高度接近，但它不是靠 React 渲染层临时切分消息，而是把“阶段进度”和“工具调用详情”拆成两条数据轴：

1. Todo / task state 是阶段进度轴；
2. tool use / tool summary 是执行细节轴；
3. UI 再把两条轴组合成用户可读的进度展示。

### 9.1 Todo 是一等执行状态

`referance/claudecode_src/utils/todo/types.ts` 定义 Todo item：

```ts
{
  content: string;
  status: 'pending' | 'in_progress' | 'completed';
  activeForm: string;
}
```

其中 `content` 是命令式任务标题，`activeForm` 是进行时展示文案。这说明 Claude Code 已经把“列表标题”和“正在执行的阶段文案”分开建模。

`referance/claudecode_src/tools/TodoWriteTool/prompt.ts` 对模型有强约束：

1. 复杂多步骤任务必须主动使用 Todo；
2. 开始任务前先把对应 Todo 标记为 `in_progress`；
3. 一次理想情况下只有一个 `in_progress`；
4. 完成后立即标记 `completed`，不能批量延迟；
5. `content` 和 `activeForm` 都必须提供。

`referance/claudecode_src/tools/TodoWriteTool/TodoWriteTool.ts` 在 tool call 成功后把 Todo 写入 `AppState.todos`，key 使用 `agentId` 或 session id。全部完成时会把 UI 状态清空；复杂任务完成但缺少验证项时还会追加 verification nudge。

这说明 TodoWrite 不只是给模型看的 checklist，而是运行时进度状态源。

### 9.2 Todo 状态可恢复，不依赖前端猜测

`referance/claudecode_src/state/AppStateStore.ts` 把 todos 作为 AppState 的顶层字段：

```ts
todos: { [agentId: string]: TodoList }
```

`referance/claudecode_src/utils/sessionRestore.ts` 会从 transcript 里倒序扫描最后一个 `TodoWrite` tool_use，并恢复 Todo 状态到 AppState。`referance/claudecode_src/tasks/RemoteAgentTask/RemoteAgentTask.tsx` 也会从 SDK message log 中抽取最新 TodoWrite，更新 remote task 的 `todoList`。

这点对 OneCEO 很关键：阶段状态应当能从事件流或快照稳定恢复，而不是刷新后由前端重新猜。

### 9.3 远程任务进度直接读取 Todo，而不是读取工具详情

`referance/claudecode_src/components/tasks/RemoteSessionProgress.tsx` 的普通 remote task 进度逻辑非常轻：

1. completed 显示 `done`；
2. failed 显示 `error`；
3. 没有 todoList 时显示当前 status；
4. 有 todoList 时显示 `completed/total`。

也就是说，任务级进度视图不关心 raw tool input/output，而是读取 Todo 状态。这支持 OneCEO 把“Altus 正在处理...”升级为“当前阶段 + 完成计数”的原子状态消息。

### 9.4 工具调用有单独的分组与摘要层

Claude Code 对工具调用也做了专门降噪：

1. `referance/claudecode_src/utils/groupToolUses.ts` 会把同一个 assistant message 中同类型、支持 grouped rendering 的多个 tool_use 合并成 `grouped_tool_use`；
2. `referance/claudecode_src/components/messages/GroupedToolUseContent.tsx` 再把 grouped tool use 与对应 tool_result 组装后交给 tool 的 `renderGroupedToolUse`；
3. `referance/claudecode_src/entrypoints/sdk/coreSchemas.ts` 定义了 `tool_use_summary` 消息，字段包括 `summary` 和 `preceding_tool_use_ids`；
4. `referance/claudecode_src/services/toolUseSummary/toolUseSummaryGenerator.ts` 会把一批工具调用生成短标签，目标是单行、约 30 字符、类似 commit subject，例如 “Read config.json” 或 “Ran failing tests”；
5. `referance/claudecode_src/components/tasks/RemoteSessionDetailDialog.tsx` 里的 `formatToolUseSummary()` 也明确只取工具名和第一个有意义的字符串参数，避免展示完整 raw input。

这说明工具调用在 UI 中应该显示“用途摘要”，不是显示命令输出、HTML、JSON 或完整 tool payload。

### 9.5 对 OneCEO 方案的修正

原方案中“新增 `activity_stage_*` 事件 + 工具归属 `activityStageId`”仍然成立，但阶段来源应更明确：

1. 第一阶段不要新增一个让模型手写阶段的工具；
2. 以 `todowrite` 快照作为阶段状态源；
3. `content` 作为阶段标题，`activeForm` 作为运行中文案；
4. 后端在 Todo 的 `in_progress -> completed` 变化中投影 `activity_stage_started/updated/completed`；
5. 工具调用进入当前 `activityStageId`；
6. 工具行显示平台生成的用途摘要，必要时引入类似 `tool_use_summary` 的短标签事件；
7. replay drawer 保留详细工具信息，主对话只显示摘要胶囊。

因此，Manus / Claude Code 这类多段展示不是纯 React 模式，也不是单纯 prompt 文案问题。正确实现应是：

```text
TodoWrite snapshots
  -> Activity stage projection
  -> Tool events assigned to current stage
  -> Tool summary labels
  -> Frontend grouped timeline
```

## 10. 结论

OneCEO 现在已经有工具事件、run_status、todowrite 和前端活动组，距离 Manus 式多段执行流缺的是一个稳定的“活动阶段”事件模型。

但从最小化改动和隐藏 bug 风险控制看，第一步不应直接新增后端 `activity_stage_*` 事件，也不应立刻扩展 Todo schema。当前系统已经把 `todowrite` 的 `tool_call_completed` 投影到了对话消息，并且前端已经能从 `metadata.arguments.todos` 或 `outputPreview.todos` 读取 Todo。因此可以先做一个更窄的前端投影版本。

## 11. 最小改动收敛版

### 11.1 第一阶段只改前端分组，不改后端协议

范围限定在 `apps/web/client/src/pages/Home.tsx`：

1. 保持 `ChatItem` 类型不变；
2. 保持后端 `run_status` / `tool_call_*` 事件不变；
3. 保持 `todowrite` schema 不变；
4. 只增强 `groupManagedActivityItems()` 的分组逻辑。

新的分组规则：

1. 遇到普通 `managed_status` / `managed_tool` 时，仍按现有逻辑进入当前 buffer；
2. 遇到 `toolName === "todowrite"` 且能读到 active todo：
   - 先 flush 前一个 buffer；
   - 把 `activeTodo.activeForm || activeTodo.content` 作为新的阶段标题；
   - 后续工具和状态归入这个阶段，直到下一个 active todo 出现；
3. 遇到 all-completed 的 `todowrite`：
   - 不创建新阶段；
   - 保持最后一个阶段，等待 `complete_task` 收尾；
4. 如果没有有效 `todowrite`，完全走现有连续分组逻辑。

这样不会引入新的服务端状态机，也不会影响 run event 写入、Redis、stream、历史 replay。

### 11.2 默认展开策略

2026-04-24 追加 UI 优化：

1. Todo 驱动的活动组默认不再全部展开；
2. 同一 managed run 中，只默认展开最后一次 `todowrite` 快照仍包含 `in_progress` Todo 的活动组；
3. 当新的 Todo 活动组出现后，前一个 Todo 活动组自动折叠；
4. 当最后一个 Todo 活动组也完成后，所有 Todo 活动组默认折叠；
5. 非 Todo fallback 活动组保持原来的默认展开行为，避免影响旧历史和无 Todo 场景；
6. 用户仍可以手动点击标题展开任意历史活动组查看工具调用明细。

这样默认视图只保留 Todo 阶段标题和最终输出，工具细节按需展开。

### 11.3 暂缓的内容

以下内容先不做：

1. 不新增 `activity_stage_started / updated / completed`；
2. 不给所有 `tool_call_*` 注入 `activityStageId`；
3. 不改 `AltusRunLoopSnapshot`；
4. 不扩展 Todo schema；
5. 不引入 LLM 生成 `tool_use_summary`。

原因：这些都属于协议面或状态面改动，容易影响恢复、历史消息、stream 投影和测试面。第一阶段先验证 UI 体验和阶段切分是否成立。

### 11.4 为什么这个版本风险最低

1. 事件顺序已经存在：`todowrite` 通常在阶段开始前被调用，后续工具天然跟在它后面；
2. 数据已经持久化：`todowrite` 的 completed 事件已经进入对话消息，刷新后仍能重新分组；
3. 前端已有解析函数：`readManagedTodoItems()` 已经能读取 `content / status / activeForm`；
4. 前端已有摘要函数：工具行已经使用 `getManagedToolPurposeSummary()`，不需要展示 raw payload；
5. 失败回退自然：模型不调用 `todowrite` 时，UI 保持当前行为。

### 11.5 必须补的回归测试

只需要扩展 `apps/web/client/src/tests/managed-run-status-dialogue.test.ts`：

1. `todowrite` active todo A 后的工具进入阶段 A；
2. 新的 `todowrite` active todo B 会 flush A 并创建阶段 B；
3. all-completed `todowrite` 不创建空阶段，`complete_task` 留在最后阶段；
4. 没有 `todowrite` 的旧消息仍保持原来的单组行为；
5. Todo 活动组只默认展开最后一个仍有 `in_progress` Todo 的阶段，完成后全部默认折叠；
6. 工具行标题仍使用用途摘要，不显示 HTML / shell stdout / JSON payload。

### 11.6 后续升级条件

只有当第一阶段验证出以下问题，再进入后端阶段事件：

1. 工具调用跨阶段归属不稳定；
2. 模型遗漏 `todowrite` 的比例较高；
3. 需要在 stream 层实时显示阶段，而不仅是对话消息投影；
4. 需要跨页面、跨组件复用阶段状态。

如果没有这些问题，就不需要新增后端 `activity_stage_*`，避免过度设计。

## 12. 最终建议

当前最短正确路径调整为：

1. 不新增重型任务系统；
2. 复用 `todowrite` 作为阶段来源；
3. 第一阶段只改前端 `groupManagedActivityItems()`，用 `todowrite` active todo 切分阶段；
4. 继续复用现有工具用途摘要，主对话展示短标签，详细 payload 留在 replay drawer；
5. 旧历史和无 Todo 场景继续走当前连续分组 fallback；
6. 后端 `activityStageId` 和 `activity_stage_*` 作为第二阶段预留，不在第一版实现。

## 13. 追加修复：最终总结消息顺序

2026-04-24 发现一个偶发错位：`complete_task` 的最终总结有时会显示到工具活动组之前。

根因判断：

1. 流式 assistant delta 使用 `managed:{runId}:assistant`；
2. `complete_task` 最终总结也复用同一个 messageKey；
3. DB 的 `conversation_messages` 按 `(sessionId, messageKey)` upsert，更新内容时保留原 timeline cursor；
4. 如果前面已经有流式 assistant 占位，最终总结会回填到旧位置；
5. 同时最终总结持久化早于 `complete_task` 的 `tool_call_completed` 投影，也会增加刷新后顺序不稳定的风险。

最小修复原则：

1. `complete_task` 最终总结使用独立 key：`managed:{runId}:assistant:final`；
2. 先写入 `complete_task` 的 `tool_call_completed`，再持久化最终总结；
3. SSE 的 `assistant_message` 也使用同一个 final key；
4. 前端保留已有 duplicate stream cleanup：如果 final 内容与早期流式占位一致，移除旧占位，最终总结留在工具之后；
5. 不改普通纯文本会话完成路径，避免影响无工具问答。

回归要求：

1. 实时流：streamed assistant -> complete_task -> final assistant，最终显示顺序必须是 complete_task 后跟 final assistant；
2. 历史恢复：cached streamed assistant + persisted final assistant，恢复后也必须保留工具在前、final 在后；
3. 旧的同 key 兼容测试保留，避免破坏历史数据恢复。

本方案已于 2026-04-24 17:20 采用，并进入最小改动实现阶段。
