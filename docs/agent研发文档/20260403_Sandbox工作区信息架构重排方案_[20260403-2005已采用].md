# 20260403 Sandbox 工作区信息架构重排方案 [20260403-2005已采用]

更新时间：2026-04-03

## 1. 背景

当前 `apps/admin_management` 的 Sandbox 工作区已经具备运行态总览、风险队列、Runtime 列表和手工创建入口，但实际首屏存在以下问题：

1. Sandbox 同时出现在 `KVM 管理` 和 `执行环境管理` 两个入口下，导航边界不清
2. 总览指标、工作区切换、主表、风险队列、新建 Runtime 同屏堆叠，首屏优先级混乱
3. 风险队列按实例平铺，重复项过多，管理员无法先判断“哪类问题最值得处理”
4. 主表缺少面向排障的筛选、搜索和排序，长 ID 与长模板名导致扫读成本高

## 2. 重排目标

本轮只做 Sandbox 工作区的信息架构重排，不扩展新的业务动作。

目标：

1. 让管理员进入首屏后先判断“系统是否健康”
2. 再判断“哪类风险最紧急”
3. 最后进入具体 Runtime 列表和详情处理
4. 降低重复信息和长文本对首屏注意力的争抢

## 3. 页面结构

### 3.1 一级定位

建议把 Sandbox 工作区从 `KVM 管理` 的二级切换中移出，归入独立的 `执行环境管理`。

原因：

1. Sandbox 的治理维度已经不只是 VM/KVM 资源，还包括 task session、archive、OSAC、executor connectivity
2. 把 Sandbox 挂在 KVM 下，会误导管理员把它理解成 KVM 的附属资源页
3. 当前侧边栏已存在 `执行环境管理`，继续保留 `KVM > Sandbox` 属于重复入口

## 4. 首屏布局

建议首屏改成三段式：

### 4.1 健康总览区

展示：

1. 总环境
2. 运行中
3. 已暂停
4. 待归档
5. 风险项
6. 当前服务状态

当前实现要求：

1. 只放健康判断所需的聚合指标
2. 不在该区域混入工作区说明文案和次级操作
3. `已暂停` 必须与 `运行中` 分开展示，不能继续只作为运行态筛选值存在
4. `已暂停` 的展示语义应明确表达“保留实例、可恢复、通常不参与计费”

### 4.2 风险聚合区

把当前“风险队列”从实例平铺改成按风险类型聚合：

1. `inactive_but_running`
2. `missing_osac_endpoint`
3. `missing_opencode_base_url`
4. 其他风险

每类展示：

1. 风险名
2. 受影响实例数
3. 最近出现时间
4. 进入实例列表按钮

这样管理员先判断“处理哪一类”，再进入具体实例。

### 4.3 Runtime 列表区

主表保留，但首屏只承担“定位目标实例”的职责。

建议默认列：

1. Task Session
2. Sandbox
3. Executor
4. 状态
5. 风险摘要
6. 最近活跃
7. 操作

以下信息降级到详情或次级行：

1. 模板全名
2. archive 文本枚举
3. 事件来源文案

在主表上方补充一层“状态分类”聚合区：

1. 全部
2. 运行中
3. 已暂停
4. 已关闭

要求：

1. 每类展示数量
2. `已暂停` 必须附带“不参与计费”或等价语义提示
3. 点击状态分类后直接回写首屏状态筛选
4. 该区属于治理定位辅助，不替代原有筛选器

## 5. 交互规则

### 5.1 风险优先

列表默认排序：

1. 有风险优先
2. 风险数量多优先
3. 最近活跃优先

### 5.2 首屏筛选

首屏必须补齐：

1. `sessionId / sandboxId` 搜索
2. executor 筛选
3. 状态筛选
4. 风险标签筛选
5. 明确显示“已加载 N 条 / 当前筛选命中 M 条”，避免管理员误判列表是否已完整展开
6. 当 `paused` 占多数时，管理员应能在 1 次点击内切换到“只看暂停实例”

首屏列表加载约束：

1. 首屏默认只加载当前工作区排障所需的 Runtime 数量
2. 不允许为了“可能的后续浏览”在首屏默认放大到明显高于当前展示需求的取数规模
3. 需要查看更多历史 Runtime 时，使用显式“查看更多 Runtime”二段加载，而不是回退到隐式首屏大批量加载
4. “查看更多 Runtime”是否显示，必须由服务端明确返回是否仍有更多记录，前端不允许仅依赖 `当前条数 >= limit` 推断

### 5.3 长文本处理

1. 长 ID 默认截断显示
2. 提供复制按钮
3. 风险标签默认只展示前 2 个，剩余显示 `+N`
4. 模板名放次级行，避免主信息列被模板名挤占

### 5.4 工作区切换加载

`执行环境管理` 的一级工作区切换必须遵循“进入即加载当前工作区数据”的规则：

1. 切到 `总览` 或 `运行环境` 时，立即加载 Sandbox 概览与 Runtime Registry
2. 切到 `模板` 时，立即加载模板列表与模板治理所需数据
3. 不允许切到 `模板` 后继续沿用 Runtime 列表请求，导致页面先空白再依赖自动刷新补数据
4. 自动刷新只作为兜底更新机制，不能替代首次进入工作区时的即时加载

## 6. 次级操作区

“新建 Runtime”不再和风险区并列占首屏主注意力，当前实现为：

1. `Sandbox 工作区` 顶部右侧提供 `新建 Runtime` 主按钮
2. 点击后从右侧拉出抽屉承载创建表单
3. 创建成功后自动关闭抽屉并刷新 Runtime 列表

这样处理的原因：

1. 新建是低频动作
2. 风险排障和运行态观测是高频动作
3. 低频动作不应与高频决策区抢首屏位置

## 7. 详情面板要求

详情面板打开后，信息顺序建议固定为：

1. 基本身份信息
2. 当前运行状态
3. 风险与恢复建议
4. 连接性检查
5. 文件/进程/端口等调试能力

补充约束：

1. `会话绑定` 信息应收敛为仅 `会话标题` 并入 `基本身份信息` 区块展示，不再保留独立“会话绑定”卡片；`会话 ID`、`会话状态`、`编排会话` 不在该卡片展示，避免信息冗余。
2. `基本身份信息` 在摘要页内必须独占整行全宽展示，不使用双列主卡布局，避免右侧留白导致信息卡片视觉偏窄。
3. `执行模式` 与 `Sandbox 域名` 属于低频排障字段，不在摘要页 `基本身份信息` 卡片展示。
4. 摘要统计卡中的会话维度文案统一为 `会话状态`，运行状态卡不再额外展示状态胶囊标签。
5. 摘要页移除独立 `状态时间线` 卡片，避免长期空态卡片占用信息区；相关收口/接管信息仅在需要时通过其他排障视图查看。
6. 摘要页仅保留 `机器动作 / 运行状态 / 会话状态 / 最近活跃 / Sandbox 基础信息` 五块内容，其他摘要卡片与附加区块全部移除。
7. 摘要布局采用“两层结构”：上层为 `运行状态 / 会话状态 / 最近活跃` 三张状态卡，下层为 `Sandbox 基础信息 + 机器动作` 双栏主卡（窄屏自动回落单列）。
8. 连通性页不再保留顶部状态卡；`osacEndpoint` 与 `opencodeBaseUrl` 在端点值容器内用右对齐状态图标（正常/缺失）表达连通性，`鉴权令牌` 不展示。
9. 归档页移除顶部三张状态统计卡（`归档状态 / 工作区脏标记 / 待归档更新`），仅保留归档时间线、归档历史与归档元数据主体内容；`手动归档` 按钮放在 `归档时间线` 卡片头部，历史快照头部不再保留“当前快照下载/恢复”按钮。
10. 历史快照存在多条记录时，必须支持“按快照行选择性下载与恢复”；每行操作使用该行 `snapshotKey`，不允许只支持“当前快照”。
11. 历史快照表格列头需支持点击排序与拖拽改列宽；`哈希` 列默认宽度应收紧，避免长值挤压“原因/状态/操作”可读性。

禁止在详情首屏混入过多原始 JSON，原始数据应折叠到调试区。

## 8. 验收标准

1. 管理员在 5 秒内能判断平台当前是否健康
2. 管理员在 10 秒内能确定最优先处理的风险类型
3. 管理员在 15 秒内能通过筛选或搜索定位到指定 Runtime
4. 首屏不再同时出现重复导航语义和低频创建操作抢占主视觉

## 9. 2026-04-06 修复约束补充

针对运行中勘察出的首屏数据错位问题，补充以下实现约束：

1. `runtime-registry` 的活体 Sandbox 拉取必须支持完整分页遍历，不能因单页参数超过 E2B 上限而静默退化为空列表。
2. `总览` 与 `运行环境` 必须基于同一批活体 Sandbox 事实计算 `running / paused`，禁止出现总览能看到 `paused`、列表摘要却为 0 的分叉结果。
3. Runtime 行展示的 `taskTitle / taskStatus` 必须优先使用 task session 事实；当列表接口未带回 session 摘要时，允许回退到 Sandbox metadata 中已有的 `taskTitle / taskStatus`，禁止无意义显示 `-`。
4. 风险标签必须按 executor 语义判断，不能把 `codex` Runtime 一律打成 `missing_opencode_base_url` 这类仅属于 OpenCode 链路的风险。
5. 首屏“状态分组”“快捷状态按钮”“状态下拉”三处必须共享同一套筛选值域，禁止出现按钮能选 `paused`、下拉却只存在 `ready/closed` 的失配。
6. “查看更多 Sandbox” 只能扩展 Runtime 历史表格，不能改变顶部摘要、状态分组和风险聚合的计数口径；这些计数必须固定绑定 `overview` 首次返回的 live Sandbox 集合。
7. `runtime-registry` 为支撑首屏与 load more 只允许读取“可见窗口 + 探测位”的 registry 记录，禁止每次刷新都请求 `environment-registry?limit=all` 这类全量历史扫描。
8. 首屏摘要卡必须保持统一宽度与统一视觉权重，禁止再插入跨列宽卡打断摘要栅格；页面说明性信息应回收到标题区或工作区切换区，不占用 KPI 卡片位。
9. Sandbox 列表行操作必须区分主次：`查看` 与电源态动作留在明面，`重启 / 归档` 等低频动作收进“更多”菜单，禁止恢复成高密度并排按钮列。
10. `查看更多 Sandbox` 等增量加载动作必须提供强反馈：按钮 busy 态、列表头进度文案、保留旧数据的表格底部加载占位，以及原位失败提示；禁止只把按钮文案改成“加载中”后让用户等待。
11. Sandbox 工作区布局优先级固定为“列表主画布 > 状态分组侧栏”：桌面端列表区域应显著大于侧栏，侧栏仅保留紧凑筛选与风险概览；中等屏幕下必须先展示列表，再展示侧栏。
12. Sandbox 列表“操作”列按钮必须保持横向可读：禁止字内换行导致“查/看”竖排；移动端可降级为两列按钮栅格，但按钮文本仍需单行显示。
13. 桌面端 `Sandbox 列表` 主卡与 `状态分组` 侧栏卡需保持同一行等高展示，列表滚动区域应填充主卡剩余高度，禁止再用固定 `vh` 将列表卡压短。
14. Sandbox 列表表头需支持 AWS 风格交互：点击列标题切换升降序，列头可拖拽调整宽度；排序与列宽必须在当前页面状态内即时生效。
15. Sandbox 列表主区需要保持更高的默认纵向可视空间：桌面端表格滚动区应使用“弹性填充 + 最小高度”策略，禁止继续使用低值固定高度导致首屏可读行数过少。
16. “状态分组”与“风险聚合”都必须整合进 `Sandbox 列表` 主卡：前者作为唯一状态快捷入口，后者作为风险标签快捷入口；不再保留独立侧栏分组模块。
17. 状态分组各项视觉风格必须统一：`暂停中` 不允许使用独立告警色，与其他状态共享同一套默认态与激活态配色。
