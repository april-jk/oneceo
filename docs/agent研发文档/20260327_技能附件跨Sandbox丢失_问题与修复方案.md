# 技能附件跨 Sandbox 丢失问题与修复方案

更新时间：2026-03-27  
状态：已修复并完成链路复测  
适用范围：`apps/web` 附件发送流程、`apps/api` task session runtime、Altus managed sandbox 复用

## 1. 问题现象

用户在任务创建页选择 `PPT 办公` skill 后，前端会生成一个 `skill-office-ppt.md` 附件并附带到会话中。随后发起 Altus managed run 时，界面出现：

1. `read_file .attachments/...-skill-office-ppt.md` 失败
2. 错误内容为 `path ... does not exist`
3. 智能体没有按 skill brief 执行，而是转去临时安装 `python-pptx` 并自己写脚本生成 PPT

## 2. 直接原因

问题不是 skill 模板内容错误，而是同一会话在“附件上传阶段”和“Altus 执行阶段”用了两个不同的 sandbox。

实际运行轨迹中：

1. 附件上传阶段先创建了 sandbox A，并把 `skill-office-ppt.md` 写入该 sandbox 的 `.attachments/`
2. Altus managed run 启动时又创建了 sandbox B
3. `read_file` 发生在 sandbox B 中，因此找不到刚才上传到 sandbox A 的附件

## 3. 根因分析

根因是 task session runtime 与 Altus managed sandbox binding 存在两套未收口的状态来源：

### 3.1 附件上传链路

[task-creation-routes.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/routes/task-creation-routes.ts#L903) 的 `ensureTaskSessionRuntime()` 会：

1. 复用或创建 sandbox
2. 更新 `taskCreationFileMemoryStore.updateRuntimeBinding()`
3. 供附件上传路由把文件写入当前 workspace

但这条链路**不会同步写入** `task_session_sandbox_bindings`。

### 3.2 Altus managed run 链路

[altus-managed-setup-service.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/services/altus-managed-setup-service.ts#L118) 的 `ensureSandbox()` 在修复前只看：

1. `task_session_sandbox_bindings`
2. 绑定不存在时直接新建 sandbox

因此当用户“先传附件，再启动 Altus run”时：

1. 附件已经在 runtime sandbox 中
2. 但 Altus run 因为看不到 binding，又新建了第二个 sandbox
3. 最终出现附件路径存在于 A、执行发生在 B 的分叉

## 4. 用户可见后果

这个问题会带来四类直接后果：

1. skill 附件虽然被选中了，但实际内容没有被读到
2. 智能体会退回通用策略，自行摸索实现路径
3. 同一请求可能额外拉起第二个 sandbox，增加 E2B 计费与耗时
4. 工具轮次被无效消耗，最终可能以 `managed_run_tool_round_limit_exceeded` 失败

补充说明：

- `python-pptx` 的安装发生在 E2B sandbox 内，不会污染开发机本地环境
- 但它是在 skill 附件读取失败之后才触发的 fallback，不是理想执行路径

## 5. 修复目标

本次修复目标只有一个：

**同一 task session 下，附件上传与 Altus managed run 必须复用同一个 sandbox。**

不做额外兜底，不引入新的附件存储体系，不改 skill 模板协议。

## 6. 修复方案

### 6.1 收口附件上传链路

在 [task-creation-routes.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/routes/task-creation-routes.ts#L893) 中新增 `syncTaskSessionSandboxBinding()`，并在 `ensureTaskSessionRuntime()` 的以下两种场景中同步写入 `task_session_sandbox_bindings`：

1. 复用已有 sandbox 时
2. 新建 sandbox 时

这样附件上传阶段创建的 runtime sandbox 会立即成为 Altus managed 可识别的正式 binding。

### 6.2 收口 Altus managed 链路

在 [altus-managed-setup-service.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/services/altus-managed-setup-service.ts#L36) 中新增 `reuseKnownSandbox()`，并将 `ensureSandbox()` 的复用优先级调整为：

1. 优先读取 file-memory 中的 `runtime.orchestratorSessionId`
2. 若可用，则直接复用，并同步回写 `task_session_sandbox_bindings`
3. 若 runtime 不可用，再回退到既有 `task_session_sandbox_bindings`
4. 只有两者都不可用时，才真正新建 sandbox

这保证了“先上传附件再启动 run”的链路不会再次分叉。

## 8. 验证结果

已于 2026-03-27 本地完成针对性复测，步骤为：

1. 创建 draft session
2. 上传 `skill-office-ppt.md`
3. 启动 Altus managed run，并要求“只读取附件，不创建 PPT”

复测结果：

1. `task_session_sandbox_bindings` 与 `sandbox_execution_environments` 最终只出现 **1 个** sandbox
2. run status 明确显示 `已恢复会话 sandbox，开始执行`
3. `read_file .attachments/...-skill-office-ppt.md` 成功完成
4. 不再出现“附件在 A、执行在 B”的跨 sandbox 丢失
5. 复测产生的 sandbox 已关闭，测试会话已删除

## 9. 结论

本问题的本质不是 PPT skill 模板错误，而是 session runtime 与 Altus managed sandbox binding 的状态分裂。

本次修复通过把两条链路统一收口到同一个 sandbox binding，解决了 skill 附件“提示已上传，但运行时读不到”的主故障点，也避免了同一请求重复创建 sandbox 的额外成本。
