# 20260327 交付物出 Sandbox 闭环实现与验证

## 1. 问题

在 Altus managed run 中，`pptx/docx/xlsx/pdf` 这类最终文件虽然已经能在 E2B sandbox 内生成，但系统之前没有把它们提升为平台正式交付物：

- 文件只存在于 sandbox workspace
- `complete_task` 没有正式 `attachments` 协议
- run 即使生成了文件，也不保证用户能直接下载
- 前端只有 web/code artifact 预览逻辑，没有最终交付物下载卡片

这会导致“日志显示已经生成成功，但用户拿不到文件”的断层体验。

## 2. 本次正式修复

本次按设计文档的最短正确路径实现，没有做 UI 补丁，也没有做兼容性兜底。

### 2.1 后端协议升级

- 扩展 `complete_task` 工具协议，新增 `attachments`
- 在 managed prompt 中明确要求：凡是生成用户可下载文件的任务，必须在 `complete_task.attachments` 中声明最终文件
- 在 tool runtime 中校验 attachment 路径必须是 workspace 相对路径

### 2.2 服务端交付物持久化

- 新增表 `task_session_deliverable_artifacts`
- 新增 deliverable DAO
- 新增 `task-session-deliverable-service.ts`
- 在 `complete_task` 执行完成前：
  1. 读取 attachment 对应的 sandbox 文件
  2. 上传到 R2
  3. 写入 deliverable 记录
  4. 将 deliverables 写回最终 assistant message 和 `run_completed` metadata

只有以上步骤全部成功后，run 才会进入 `completed`。

### 2.3 下载接口与前端卡片

- 新增接口：
  - `GET /api/task-creation/sessions/:sessionId/deliverables`
  - `GET /api/task-creation/sessions/:sessionId/deliverables/:artifactId/download`
- 前端新增 `TaskDeliverableCard`
- `Home.tsx` 在 `run_completed` 的 managed status_update 中优先解析 `deliverables`
- 如果存在 deliverables，则展示下载型完成卡片，而不是只走原来的 web preview artifact 卡片
- 下载按钮走带鉴权 header 的 fetch，再触发浏览器下载，避免直接打开 URL 时缺少 `X-User-Id`

## 4. 验证结果

### 4.1 API 路由验证

我先重启了 API，并确认：

- `http://127.0.0.1:4000/health` 返回 `ok`
- `GET /sessions/:sessionId/deliverables` 可正常返回空数组，说明新表和新路由已生效

### 4.2 真链路验证

我使用 `Altus managed run` 跑了最小真实场景：

- 创建草稿会话
- 让 Altus 在 sandbox 内生成 `deliverable-test.txt`
- 要求它通过 `complete_task.attachments` 声明该文件
- 轮询直到 run 进入 `completed`
- 调用 deliverables 接口确认返回 `1` 个交付物
- 调用下载接口确认文件内容为 `deliverable pipeline ok`

验证结果：

- run 成功完成
- deliverable 记录成功落库
- 下载接口可直接拿到正确文件内容

### 4.3 刷新后可恢复验证

我又补做了一轮验证，检查 `messages/recent`：

- recent messages 中存在 `messageType = status_update`
- 该消息的 `metadata.eventType = run_completed`
- 同一条 metadata 中包含 `deliverables`

这说明前端即使在刷新或历史重载后，也可以根据持久化消息重新渲染下载卡片。

## 5. 测试清理

根据仓库规则，本次用于验证的 E2B sandbox 我都已在验证后手动关闭，避免持续计费。

已清理动作包括：

- 测试 sandbox 手动 `Sandbox.kill(...)`
- 测试 session 手动删除

## 6. 当前残余说明

- `pnpm --filter web check` 已通过
- `pnpm --filter api exec tsc --noEmit` 仍会被仓库内既有的旧 TS 报错拦住，但这轮新增改动对应文件没有暴露新的独立类型错误

## 7. 结论

现在这条链路已经从“文件只留在 sandbox 里”升级为：

`complete_task.attachments -> 服务端持久化 -> deliverables 记录 -> 前端下载卡片 -> 用户直接下载`

这意味着办公类技能第一次具备了真正可交付的结果闭环，而不再只是“sandbox 内部成功生成文件”。
