## 1. 文档目标

为 oneceo 建立一套统一、可执行、能直接约束后续 Redis 迁移的多用户隔离模型，明确：

1. `tenantKey`
2. `userId`
3. `sessionId`
4. `orchestratorSessionId`
5. `opencodeSessionId / executorSessionId`
6. `runId`

在 API、缓存、事件流、workspace、sandbox、connector profile、guide/runtime 装配中的职责与边界。

本方案不提供兼容性补丁口径，而是直接收敛成一套后续实现必须遵守的统一主键模型。

## 2. 当前问题

现状中已经出现三套强度不同的身份规则并存：

1. `managed run stream` 已经按 `session.userId === query.userId` 做强校验
2. `workspace cache` 仍允许 `tenantKey = X-Tenant-Id -> X-User-Id -> tenantId -> default`
3. `current-user-resolver` 在没有 `userId` 时允许把 `tenantKey` 直接当 `userId`

对应证据：

1. `apps/api/src/routes/altus-managed-routes.ts`
2. `apps/api/src/routes/task-creation-routes.ts`
3. `apps/api/src/services/current-user-resolver.ts`
4. `docs/20260223_workspace_cache.md`

这会带来四类直接风险：

1. 同一 `sessionId` 的缓存分区和权限校验分区不一致
2. `tenantKey` 被误当作用户主键后，可能把跨用户资源投影到同一个缓存或事件流命名空间
3. Redis 化后，如果沿用 `default` 或弱 header 回退，串读范围会从单机文件缓存扩大到共享内存态
4. connector / guide / runtime 这类“会话外配置 + 会话内投影”对象，容易在恢复和重绑时错绑到错误用户

## 3. 设计原则

### 3.1 身份与资源主键分离

必须区分：

1. 身份主键：`userId`
2. 归属域主键：`tenantKey`
3. 会话主键：`sessionId`
4. 运行时主键：`runId / orchestratorSessionId / executorSessionId`

禁止继续用任一字段兜底替代另一字段。

### 3.2 权限判断只认已绑定归属

所有读写权限判断只允许基于：

1. `session.userId`
2. `profile.userId`
3. `run.sessionId -> session.userId`
4. `sandbox_binding.sessionId -> session.userId`

不允许基于：

1. `X-Tenant-Id` 单独放行
2. `tenantId query` 单独放行
3. `orchestratorSessionId` 猜测归属
4. `workspace path` 反推归属

### 3.3 tenantKey 只作为命名空间，不作为授权主体

`tenantKey` 的职责收敛为：

1. 缓存分区
2. stream namespace
3. workspace/view namespace
4. 诊断和审计维度

`tenantKey` 不是用户身份，不参与授权判定，不允许在缺失 `userId` 时自动顶替 `userId`。

### 3.4 session 是业务隔离锚点

在 oneceo 中，绝大多数运行时对象最终都必须挂回某个 `task session`：

1. workspace
2. sandbox
3. OpenCode/Codex executor session
4. connector binding
5. guide runtime assembly
6. Altus managed run

因此后续 Redis key、stream key、恢复逻辑都必须先回到 `sessionId` 再定位运行时对象。

### 3.5 runtime 标识永远是 session 下游对象

以下对象都不是一级授权主键：

1. `orchestratorSessionId`
2. `opencodeSessionId`
3. `executorSessionId`
4. `runId`

它们只能作为：

1. 运行时查找键
2. 恢复键
3. stream 子通道键

最终授权必须回查：

`runtime -> sessionId -> userId`

## 4. 统一对象模型

### 4.1 TenantContext

```ts
type TenantContext = {
  tenantKey: string;
  userId: string;
  source: 'auth_context' | 'x-user-id';
};
```

规则：

1. `userId` 必填
2. `tenantKey` 必填
3. 首批阶段默认 `tenantKey = userId`
4. 若未来引入组织/团队空间，才允许 `tenantKey != userId`
5. 即使未来分离，授权仍只认 `userId + membership`

### 4.2 SessionOwnership

```ts
type SessionOwnership = {
  sessionId: string;
  tenantKey: string;
  userId: string;
};
```

规则：

1. `task_session` 创建时即写入 `userId`
2. `tenantKey` 作为显式列或可稳定推导字段持久化到 session 归属记录
3. 禁止继续保留“先创建 session，后 bindUserIfMissing”的主流程

### 4.3 RuntimeBinding

```ts
type RuntimeBinding = {
  sessionId: string;
  runId?: string;
  orchestratorSessionId?: string;
  executor: 'opencode' | 'codex' | 'altus_managed';
  executorSessionId?: string;
  generation?: number;
};
```

规则：

1. `runtime` 必须隶属于 `sessionId`
2. `executorSessionId` 是执行器内部会话键
3. `opencodeSessionId` 仅作为 `executorSessionId` 在 OpenCode 下的兼容别名
4. 所有 runtime 恢复流程必须先校验上游 `sessionId` 归属

### 4.4 Connector/Profile 归属

```ts
type ConnectorProfileOwnership = {
  profileId: string;
  userId: string;
  tenantKey: string;
};
```

规则：

1. profile 永远属于某个用户
2. session binding 只允许引用当前用户可见的 profile
3. guide/runtime materialization 只消费 session 已绑定的 profile 投影，不允许跨用户按 connectorKey 扫描

## 5. 字段职责定义

### 5.1 tenantKey

定义：

租户或命名空间标识。

用途：

1. Redis key 前缀
2. Workspace cache namespace
3. 诊断日志维度
4. 后续组织级别共享空间扩展点

禁止：

1. 作为用户身份回退值
2. 作为 session ownership 唯一判断条件
3. 作为 connector/profile 读取条件的唯一键

### 5.2 userId

定义：

当前用户的唯一身份键。

用途：

1. 授权
2. 归属
3. 资源创建者
4. session/profile/run/sandbox 归属校验

禁止：

1. 由 `tenantKey` 临时推断
2. 在服务内部缺失时用 `default` 顶替

### 5.3 sessionId

定义：

业务会话主键，也是所有运行态对象的一级挂载点。

用途：

1. 对话消息
2. workspace
3. connector session binding
4. managed run
5. sandbox binding
6. 事件回放与恢复

### 5.4 orchestratorSessionId

定义：

sandbox 编排层实例主键。

用途：

1. 访问 E2B sandbox
2. 标记 sandbox lifecycle
3. runtime 恢复时定位 sandbox generation

限制：

1. 不可直接用于授权
2. 不可绕过 `sessionId`

### 5.5 executorSessionId

定义：

执行器内部会话主键，按 executor 区分。

例子：

1. OpenCode 下对应 `opencodeSessionId`
2. Codex/AppServer 下对应线程或 turn session 标识

限制：

1. 只用于执行器恢复与事件关联
2. 不可作为缓存/stream 的顶级授权范围

## 6. 统一传递规范

### 6.1 HTTP 入口

入口必须先解析并固化 `TenantContext`：

1. 登录态存在时，从 auth context 取 `userId`
2. 当前无完整登录体系的阶段，允许 `X-User-Id`
3. 若未显式提供 `X-Tenant-Id`，则令 `tenantKey = userId`
4. 禁止回退到 `default`
5. 禁止只提供 `tenantId` 而没有 `userId`

结果：

所有业务路由都要拿到：

```ts
{ userId, tenantKey }
```

### 6.2 Service 层

service 方法签名统一为：

```ts
type RequestContext = {
  userId: string;
  tenantKey: string;
};
```

约束：

1. service 不能自行从 header/query 再解析一次身份
2. service 不能自行构造 `tenantKey = default`
3. service 只能接收上游显式传入的 context

### 6.3 DAO / 持久化层

DAO 不做身份推断，只接收已校验参数：

1. 按 `sessionId` 读取时，外层必须先完成 ownership 校验
2. 按 `profileId` 读取时，外层必须携带 `userId`
3. Redis key 写入必须显式传入 `tenantKey`

### 6.4 事件流与 SSE/WS

规则：

1. stream 订阅请求必须显式带 `userId`
2. 服务端必须回查 `run/session` 所属 `userId`
3. stream key 命名可以包含 `tenantKey`
4. 但订阅授权不能只比对 `tenantKey`

统一授权链：

`subscriber.userId -> run.sessionId -> session.userId`

### 6.5 Sandbox / OSAC / OpenCode

规则：

1. sandbox metadata 中允许保存 `sessionId / tenantKey / userId`
2. OSAC 和执行器侧请求只接受平台已校验后的 runtime 指令
3. 业务路由不能通过 sandbox 内路径或 `orchestratorSessionId` 直接判断归属
4. workspace 根目录可以继续按 `sessionId` 组织，但缓存和事件转发必须携带 `tenantKey`

## 7. 分层隔离矩阵

| 层 | 主键 | 授权依据 | 命名空间依据 | 禁止事项 |
|---|---|---|---|---|
| HTTP 入口 | `userId` | `userId` | `tenantKey` | 只靠 `tenantId` 放行 |
| Session | `sessionId` | `session.userId` | `session.tenantKey` | 创建后再懒绑定用户 |
| Workspace Cache | `sessionId` | 先验 session ownership | `tenantKey + sessionId` | `default` 分区 |
| Redis Stream | `runId/sessionId` | `session.userId` | `tenantKey + sessionId + runId` | 只按 stream key 放行 |
| Sandbox | `orchestratorSessionId` | `session.userId` | `tenantKey + sessionId` | 用 sandboxId 代替会话归属 |
| Executor Session | `executorSessionId` | `session.userId` | `tenantKey + sessionId + executor` | 用执行器会话键做一级授权 |
| Connector Profile | `profileId` | `profile.userId` | `tenantKey + userId` | 跨用户按 connectorKey 取 profile |
| Connector Binding | `sessionId + profileId` | `session.userId` | `tenantKey + sessionId` | 只按 `connectorKey` 绑定 |
| Guide Runtime | `sessionId + connectorKey` | `session.userId` | `tenantKey + sessionId` | 扫全局 guide/profile |

## 8. 对现有实现的直接收敛要求

### 8.1 current-user-resolver

当前问题：

1. 允许 `tenantKey` 直接变成 `userId`

收敛要求：

1. 删除 `source='tenant'`
2. 未提供 `userId` 时直接拒绝请求
3. `tenantKey` 缺失时默认等于 `userId`

### 8.2 task-creation-routes 的 workspace cache

当前问题：

1. `resolveTenantKey()` 允许 `default`
2. `tenantKey` 与 session ownership 没有统一校验链

收敛要求：

1. 所有 workspace/tree/file 读取先校验 `session.userId === currentUser.userId`
2. cache key 使用 `tenantKey + sessionId`
3. 不再允许 `default`

### 8.3 bindUserIfMissing

当前问题：

1. session 允许先裸创建再补绑用户
2. 在并发或恢复链路中容易出现“先被 A 读到，后被 B 绑定”的窗口

收敛要求：

1. `task_session` 创建时必须写定 `userId`
2. `bindUserIfMissing` 退出主路径，仅保留一次性迁移/修复脚本使用

### 8.4 runtime 恢复

当前问题：

1. 多条链路会直接拿 `orchestratorSessionId / opencodeSessionId` 查 runtime

收敛要求：

1. 查到 runtime 后必须回查 `sessionId`
2. 只有 `session.userId` 校验通过才允许继续恢复、回放、订阅

### 8.5 connector / guide

当前问题：

1. 仍有按 `connectorKey`、`taskSessionId` 做运行时重组的链路
2. Redis 化后如果 profile/session 快照不带归属，容易跨用户串装

收敛要求：

1. 绑定时固定 `sessionId + profileId + userId`
2. guide 重算必须基于 session 已绑定 profile 列表
3. 运行时装配不得跨 user 扫描 profile 或 secret

## 9. Redis 迁移前置约束

`#10` 到 `#12` 必须直接继承以下规则：

1. 每个 Redis key 都必须含 `tenantKey`
2. 每个 session 级 key 都必须含 `sessionId`
3. 每个 runtime/run 级 key 都只能作为 session 的子键
4. TTL 只能控制缓存寿命，不能替代 ownership 校验
5. replay/recover 读取到 Redis 数据后，必须再次校验 `session.userId`

推荐 key 层级：

```txt
tenant:{tenantKey}:session:{sessionId}:...
tenant:{tenantKey}:session:{sessionId}:run:{runId}:...
tenant:{tenantKey}:session:{sessionId}:runtime:{orchestratorSessionId}:...
tenant:{tenantKey}:user:{userId}:profile:{profileId}:...
```

禁止：

```txt
session:{sessionId}:...
run:{runId}:...
runtime:{orchestratorSessionId}:...
default:{sessionId}:...
```

## 11. 改造优先级

### P0

1. 固化 `TenantContext`
2. 移除 `tenant -> userId` 回退
3. session 创建时强制写入 `userId`
4. 所有 session 级读写先做 ownership 校验

### P1

1. connector/profile/binding 归属链打通
2. runtime 恢复和回放统一回查 `sessionId`
3. workspace cache 按统一 context 改造

### P2

1. Redis key/stream/TTL 规范落地
2. 多用户并发与恢复测试补齐

## 12. 验收标准

1. 任意需要访问 session 的接口，在缺失 `userId` 时直接拒绝
2. 同一 `tenantKey` 下不同 `userId` 的会话不能互读 cache、stream、profile、runtime
3. 同一 `userId` 的不同 `sessionId` 不能互串 workspace、sandbox、run replay
4. 使用 `orchestratorSessionId / executorSessionId / runId` 直查时，仍必须回查 `session.userId`
5. Redis 迁移后的 key 设计、恢复逻辑、测试方案都不再出现 `default tenant` 口径

## 13. 本文结论

`#9` 的结论只有三条：

1. `userId` 是授权主键，`tenantKey` 只是命名空间
2. `sessionId` 是 oneceo 运行态隔离锚点，所有 runtime 对象都必须挂回 session
3. Redis 化之前必须先消灭 `tenantKey -> userId` 与 `default tenant` 这两条弱隔离路径，否则后续 `#10` 到 `#14` 都会建立在错误边界上
