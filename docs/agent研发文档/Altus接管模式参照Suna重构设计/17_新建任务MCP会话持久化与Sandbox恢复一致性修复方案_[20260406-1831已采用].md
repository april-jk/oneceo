# 17 新建任务MCP会话持久化与Sandbox恢复一致性修复方案 [20260406-1831已采用]

日期：2026-04-06

关联事项：

- GitHub Issue `#32`

## 1. 问题陈述

现象：

1. 用户在 `new-task` 页面先配置 MCP（连接器）后，发送首条消息跳转到 `/session/:id` 页面。
2. 跳转后会话中的 MCP 状态丢失，用户看到“未挂载”或与发送前不一致。

用户预期：

1. MCP 配置应绑定在 session 上，而不是页面临时态。
2. 即使当时 sandbox 尚未启动，也要先把目标状态持久化，待 sandbox ready 后恢复生效。

## 2. 全链路断点定位

本问题不是单点故障，而是“预配置态 -> 会话态 -> runtime/sandbox 态”之间存在断链。

### 2.1 新建任务页配置阶段（无 sessionId）

当前 `ConnectorDialog` 的 attach 逻辑在无 `sessionId` 时直接返回，不做后端写入：

1. `handleAttach` 无 session 直接 `return`
2. `canAttach` 依赖 `Boolean(sessionId)`

结果：

1. 页面可出现乐观勾选状态，但 session 绑定表没有对应记录。

### 2.2 首条消息发送阶段

当前发送链路会带 `metadata.mcpReferences`，但该字段仅作为消息引用信息存在：

1. 前端发送：`Home.submitPrompt` 把 mcp token 写入 `metadata.mcpReferences`
2. 后端消费：`task-creation-routes` 仅把 `mcpReferences` 当作 metadata 展示/拼装依据

结果：

1. `mcpReferences` 不会转化为 `task_session_connector_bindings` 的 attach 目标状态。

### 2.3 attach 路由与 runtime 强耦合

当前 `/sessions/:id/connectors/:connectorKey/attach` 路由先强制 `ensureTaskSessionRuntime`，再调用 service attach：

1. runtime 能起来时，attach 成功
2. runtime 起不来时，attach 请求失败

但 `session-connector-service.attachConnector` 本身已经支持 runtime 不可用时写入 `pending_recover`（离线持久化语义）。路由层的强耦合把这条语义截断了。

### 2.4 sandbox 配置下发只认 session 绑定表

`sandbox-agent-provision-service` 下发 MCP 配置只读取 `task_session_connector_bindings` 中 `desiredState='attached'` 的记录。

结果：

1. 若前面没有成功落 binding，再怎么启动 sandbox 都不会下发该 MCP 配置。

## 3. 根因结论

根因是“新建任务阶段的 MCP 选择没有被稳定写入 session 级绑定”，而非单纯 sandbox 启动时机问题。

具体为三段缺口叠加：

1. 无 session 时无法持久化 attach 目标态
2. `mcpReferences` 未映射为 session connector binding
3. attach 路由阻断了 runtime 不可用场景下的 `pending_recover` 写入路径

## 4. 修复目标

仅保留一条主路径（不做兼容补丁分支）：

1. 新建任务阶段的 MCP 配置必须先沉淀为“可回放的 session 目标态”（优先 Redis）
2. 用户发送消息后不允许被连接器流程阻断，必须继续走 `创建 sandbox -> 启动 Altus 对话`
3. runtime/sandbox 未就绪时，绑定状态仍应落库为 `pending_recover`
4. 连接器配置统一通过 OSAC 消息队列投递，sandbox 未启动时先排队，启动后再下发
5. runtime/sandbox 就绪后自动 reconcile 到 live provider，保证 UI 与工具可用性一致

## 5. 修复方案（单路径）

### 5.1 前端连接器选择改为“写 Redis 草稿”

在 `new-task` 且无 `sessionId` 时，连接器切换不再伪装成已挂载成功，而是通过 API 写入 Redis 草稿（服务端态）：

1. 草稿字段：`connectorKey/profileId/enabledTools/sessionConfig/desiredState/updatedAt`
2. GitHub 仓库选择写入 `sessionConfig.repositories`
3. Redis key 按 `tenantKey + userId + draftId` 做隔离，设置合理 TTL（例如 24h）
4. 仅作为“待回放目标态”，不是 runtime live 状态
5. 若 `ONECEO_REDIS_ENABLED=false` 或 Redis 不可用，则该 API 直接走 DB 直写路径（通过现有 service），不引入旁路

### 5.2 后端异步/延迟入库策略

连接器选择请求返回不阻塞 DB 入库，后端执行“Redis 前置 + 入库任务”：

1. API 快速写 Redis（用户即时反馈）
2. 后端异步任务把 Redis 草稿写入 `task_session_connector_bindings`
3. 入库完成后更新 Redis 草稿状态为 `persisted`
4. 失败进入重试并记录错误原因，不吞错

### 5.3 发送主链路改为“不阻断 + 强制推进 sandbox/Altus”

在 `sendChatInput` 主链路（managed + sandbox）统一加入：

1. 首条消息到达后先创建 session（若尚未创建），并立即进入 `ensureSandbox` 与 Altus run 启动流程
2. 连接器草稿回放改为后台异步，不再作为发送前置阻塞条件
3. 若草稿回放失败，不中断当前消息流程，只记录错误并进入重试队列
4. 前端展示“连接器同步中”状态，直到 OSAC 队列投递完成

### 5.4 增加 OSAC 连接器消息队列（核心）

连接器配置不直接在业务路由里同步调用 OSAC，而是统一写入“OSAC 连接器队列”：

1. 队列消息类型：`REGISTER_MCP_PROVIDER`、`ATTACH_MCP_PROVIDER_TO_SESSION`、`DETACH_MCP_PROVIDER_FROM_SESSION`、`REMOVE_MCP_PROVIDER`
2. 队列消息载荷：`taskSessionId / connectorKey / profileId / enabledTools / sessionConfig / desiredState / orchestratorSessionId`
3. sandbox 未就绪时队列状态为 `waiting_sandbox`，不丢消息
4. sandbox ready 且 OSAC bridge ready 后，队列消费者按顺序投递消息
5. 投递失败按重试策略回退（指数退避），并更新连接器 runtime 状态为 `failed` 或 `pending_recover`
6. 队列处理执行层统一走 `session-connector-service` 与 `osac-agent-service`，不允许业务路由直连 OSAC websocket

### 5.5 后端 attach 路由改为“离线可持久化”

调整 attach 路由调用顺序：

1. 先做 ownership/profile 参数校验
2. 不再在路由层强制 `ensureTaskSessionRuntime`
3. 将 `session.runtime.orchestratorSessionId`（若有）传入 service
4. 由 `session-connector-service.attachConnector` 决定：
   - runtime 可用：即时 attach
   - runtime 不可用：写 `desiredState='attached' + runtimeStatus='pending_recover'`

### 5.6 runtime 启动后触发队列下发与 session reconcile

在通用 runtime 启动路径（不仅限 managed）触发两件事：

1. 队列消费者从 `waiting_sandbox` 切到 `pending` 并开始 OSAC 投递
2. 执行 `ensureSessionRecovered(taskSessionId, orchestratorSessionId)` 兜底 reconcile，确保 pending_recover 最终被消费

说明：

1. 已有 `session-mcp-recovery-service` 与 `task_session_mcp_recovery_jobs` 作为恢复任务队列；本方案在其上扩展为“OSAC 连接器投递队列语义”，避免重复造轮子。
2. 队列与恢复任务的权威状态仍落在 `task_session_connector_bindings`（`desired_state/runtime_status`）。

### 5.7 明确 `mcpReferences` 契约边界

`mcpReferences` 保持“用户输入引用元数据”语义，不承担绑定行为；session 绑定唯一事实源为 `task_session_connector_bindings`。

## 7. 验收标准

### 7.1 核心链路

1. 在 `new-task` 页面无 session 时配置 MCP，发送首条消息后跳转 `/session/:id`，连接器目标态保持 `attached`（可处于“同步中”）。
2. 刷新 `/session/:id` 页面后状态不丢失。
3. `task_session_connector_bindings` 中存在对应 `desiredState='attached'` 记录。
4. 发送消息不会因连接器投递失败而中断；流程继续进入 `创建 sandbox -> 启动 Altus 对话`。

### 7.2 sandbox 未启动场景

1. runtime/sandbox 未就绪时，连接器 OSAC 消息进入 `waiting_sandbox`，目标态已落库。
2. runtime/sandbox 就绪后队列自动下发，连接器状态从 `pending_recover/connecting` 最终进入 `connected`（或失败重试态）。

### 7.3 Redis 开关约束（强制）

1. `ONECEO_REDIS_ENABLED=true + REDIS_URL` 时：连接器选择优先写 Redis 草稿，再异步/延迟入库。
2. 仅配置 `REDIS_URL` 但未开启开关：必须完全不使用 Redis，直接走 DB 路径。
3. Redis 异常时：请求不成功假装成功；必须返回可观测错误或走可验证的 DB 同步路径。

### 7.4 OSAC 队列约束（强制）

1. 连接器下发消息必须通过 OSAC 队列消费者，禁止业务路由直接对 sandbox 内连接器服务发请求。
2. 队列消息必须具备幂等键（建议 `taskSessionId + connectorKey + profileId + desiredState + envVersion`）。
3. 同一 connector 的消息按会话内顺序执行，避免 attach/detach 乱序。

### 7.5 回归约束

1. 现有 session 页面 attach/detach 行为不回退。
2. GitHub 仓库选择（`sessionConfig.repositories`）可持续保留并恢复。
3. managed 与 sandbox 两条发送链路均可用。

## 8.1 追加修复（2026-04-06）

为解决 session 页面连接器展示慢与已选连接器图标不及时问题，补充以下实现：

1. 前端 `ConnectorDialog` 在 session 页面未展开时也会静默预加载连接器状态，保证输入框旁图标可立即反映已选连接器。
2. 后端 `listSessionConnectors` 增加 Redis 会话级投影缓存（`connectorProjection`），减少每次弹窗打开的全链路查询开销。
3. 连接器 attach/detach、草稿 apply、恢复任务状态变更后会失效对应会话缓存，保证缓存与会话绑定状态一致。
4. `listSessionConnectors` 的 runtime 直连探测改为默认关闭（可通过环境变量开启），避免 OSAC 请求超时拖慢 UI。
