# 20260410 Issue41 调试页远程调试启用链路收敛方案 [20260410-2306已采用]

## 1. 背景与目标

Issue #41（内容预览-调试）要求“启用远程调试”必须走稳定的专用能力调用，禁止通过对话让 Altus 在 sandbox 内执行临时命令。

目标：

1. 调试页只通过 `POST /api/task-creation/sessions/:sessionId/debug/start` 启用 n.eko 远程调试。
2. 前端默认移除“发消息触发调试”的分支，避免出现 `docker-compose` / `install.sh` 等不受控命令链路（仅保留“执行环境未启动”场景的固定提示词入口）。
3. 当启动失败时，用户仍可在调试页直接重试，不需要切换到聊天区。

## 2. 根因分析

1. 调试页新增的“启用远程调试”按钮曾接入 `onRequestEnableRemoteDebug`，由 `Home.tsx` 发送固定中文指令到对话流。
2. 这条路径会把调试启动交给 LLM 执行，产生不确定命令序列，偏离模板预置能力与后端标准服务接口。
3. 结果是调试启用稳定性下降，并且错误链路变成“聊天执行失败”，而不是可观测的 API 失败。

## 3. 方案设计（最短路径）

1. 删除 `OpencodePreviewPanel` 的 `onRequestEnableRemoteDebug` 入参。
2. 删除 `Home.tsx` 中对应回调与 `sendChatInput` 触发逻辑。
3. 调试页内“启用远程调试/重新启用远程调试”入口统一调用既有 `onStart`，由该回调触发 `startTaskCreationDebug(sessionId)`。
4. 调试错误态增加“重新启用远程调试”按钮，直接重走专用接口。
5. 前端 `startTaskCreationDebug` 请求失败时读取服务端错误信息，避免仅返回状态码。

## 4. 非目标

1. 不改 n.eko / Chromium 的 sandbox 启动脚本策略。
2. 不改 `ensureNekoDebug` 服务行为。
3. 不新增第二套调试启动接口。

## 5. 验证方案

1. 代码检索确认无 `onRequestEnableRemoteDebug`、`preview_debug_enable` 等旧入口残留。
2. `pnpm --filter web check` 通过。
3. 手动验证：在内容预览-调试页点击“启用远程调试”与“重新启用远程调试”，仅观察 `debug/start` 与 `debug` 接口请求。

## 6. 交付标准

1. 调试启用链路单一且可观测：仅 API 调用，不走聊天命令。
2. 用户可在调试页完成启用与失败重试闭环。
3. 前端报错信息可读，便于定位后端或环境异常。

## 7. 2026-04-11 补充变更（执行环境未启动态）

1. 在“执行环境未启动，无法加载调试画面”状态下新增“启动调试”按钮。
2. 点击按钮时，前端发送固定消息 `启动网站调试功能` 到会话对话流。
3. 该入口仅用于执行环境未启动场景，已存在的“启用远程调试/重新启用远程调试”按钮行为保持不变。

## 8. 2026-04-11 晚间补充（已替换）

为支持“先执行其他工具（如 `shell_execute` 启服务）再进入调试”的编排场景，调试页触发策略已调整：

1. “启用远程调试 / 重新启用远程调试 / 启动调试”按钮统一改为发送可见消息 `启动网站调试功能`。
2. 调试页不再在信息加载阶段自动调用 `debug/start` 进行隐式启动。
3. 旧结论“调试页只通过 `POST /debug/start` 启用”在交互入口层已被本节替换，当前采用行为以本节为准。
