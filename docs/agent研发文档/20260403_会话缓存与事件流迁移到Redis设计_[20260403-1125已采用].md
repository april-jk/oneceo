## 1. 文档目标

在 `#10` 已收敛 Redis key / TTL / stream 规范后，给 `#11` 定一个最小可落地的迁移方案，只覆盖当前主线真正需要的四块：

1. `workspace dir/tree/file` 读取缓存
2. `messages/recent` 热窗口
3. `messages/history` 的短期游标与热页
4. `session-events` SSE / 过程流短窗口回放

本设计只解决“读热路径和短窗口回放”问题，不把 Redis 扩成平台级全量存储，不新增与当前需求无关的缓存域。

## 1.1 本次参照依据

本次不是抽象地“参考 Suna”，而是只吸收已经被仓库文档验证过、且和 `#11` 直接相关的结论：

1. `docs/agent研发文档/Altus接管模式参照Suna重构设计/13_Suna流式执行链路与SSE事件流研究.md`
   - 结论：`Suna` 的 SSE 本质是“Redis stream 的转发层”，不是单纯的长连接外壳
2. `docs/agent研发文档/20260402_Redis_key_stream_TTL统一规范_[20260402-2250已采用].md`
   - 结论：`#11` 只该迁 `workspace cache + recent/history + session-events`
3. 当前已落代码
   - `apps/api/src/services/altus-run-redis-state-service.ts`
   - `apps/api/src/services/altus-run-event-writer.ts`
   - `apps/api/src/services/altus-managed-stream-service.ts`
   - 结论：oneceo 已经有一套最小可工作的 Redis run state / run stream 模式，`#11` 应直接复用这套写法，不再另起一套 Redis 基础设施

## 2. 当前实现现状

### 2.1 workspace

当前 `workspace` 路由分成两套缓存：

1. `workspace/tree`、`workspace/file`
   - 先读 `taskCreationCacheStore`
   - 这是 `apps/api/.runtime-cache/task-creation/task-creation-cache.json` 的本地文件缓存
2. `workspace/dir`、`workspace/tree`、`workspace/file`
   - 在 `executor=e2b/codex` 时额外写一份 `task_session_workspace_cache`
   - 当前主要作为 sandbox 关闭后的 DB fallback

问题：

1. 主缓存仍是单机本地文件，不跨进程
2. E2B 场景和 OpenCode 场景缓存策略不统一
3. 失效主要靠进程内 `taskCreationCacheStore.invalidateWorkspaceBySession()`，不天然跨实例同步

### 2.2 recent / history

当前 `messages/recent` 与 `messages/history` 主要依赖数据库：

1. `messages/recent`
   - 读 `task_session_recent_messages`
   - 若是 sandbox + opencode，会再比对 `resolveRenderableTimelineMessages()` 结果
   - recent cache 脏了时会异步 `replaceRecentMessagesSnapshot()`
2. `messages/history`
   - 直接走 `resolveRenderableTimelineMessages()`
   - 每次都从已解析历史中切页
3. 进程内有 `recentHistoryHydrationInFlight`，用于避免重复触发 recent 重建

问题：

1. `recent` 只有 DB 热层，没有 Redis 短热层
2. `history` 每次都做全量解析后再切页，没有 Redis 热页/游标辅助
3. `recentHistoryHydrationInFlight` 是进程内状态，不跨实例

### 2.3 session-events / SSE

当前 OpenCode 过程流链路：

1. `opencodeEventStreamService` 维护进程内订阅
2. `/opencode-events` SSE 路由断线重连时，优先从 `taskCreationFileMemoryStore.getMessages(sessionId)` 做回放
3. 然后继续订阅进程内 `opencodeEventStreamService.subscribe(orchestratorSessionId, ...)`

问题：

1. 过程流回放仍依赖 DB / file-memory-store，而不是 Redis stream
2. 实时分发主体仍是进程内订阅，不跨进程
3. `sessionEventSeq` 已存在，但没有真正落到 Redis `stream:session-events`

## 3. 参照 Suna 后的取舍

### 3.1 这次直接吸收什么

参照 `Suna`，当前 `#11` 只直接吸收两条：

1. “事件先写入 Redis stream，再由 SSE 路由转发”
   - 这条只用于 `session-events`
2. “Redis 负责短窗口热状态，DB 继续负责事实存储”
   - 这条用于 `workspace`、`recent/history`

换句话说，`#11` 要学的是：

1. Redis 是共享热层
2. SSE replay 优先 Redis，再回退 DB
3. 事件流和热缓存都服务于恢复与跨实例读取

### 3.2 这次明确不照搬什么

`Suna` 相关文档里提到的这些能力，本次明确不照搬：

1. 不引入 `StreamHub`
2. 不引入 consumer group / fan-out 基础设施
3. 不新增独立的 `agent_run:{id}:stream` 风格对象模型到 task session 主线
4. 不为了 `history` 建完整 Redis 历史索引
5. 不把工具输出流、reasoning chunk、delta chunk 全量搬进新的 Redis 公共流

原因只有一个：

1. 这些都超出了 `#11` 的最短路径
2. 我们当前平台要稳定的是 task session 的读热路径和短窗口 replay，不是重做一套 Suna 式运行平台

## 4. 这次必须解决什么

`#11` 只解决以下最小闭环：

1. 把 `workspace dir/tree/file` 的热缓存从本地文件 / DB fallback 统一到 Redis
2. 给 `messages/recent` 增加 Redis 热层，DB 继续作为事实存储
3. 给 `messages/history` 增加 Redis 热页与游标辅助，避免每次都只靠全量解析
4. 把 `session-events` 真实写入 Redis stream，并用于 SSE 断线短窗口回放

## 5. 这次明确不做什么

为了避免过度开发，本次不纳入：

1. 不把全量消息历史搬进 Redis
2. 不把 `conversation_messages` / `task_session_recent_messages` 的 DB 事实职责替换掉
3. 不新增第三套“平台统一事件总线”
4. 不把 connector guide、runtime-config、toolkit、用户上下文一并塞进 Redis
5. 不在 `#11` 引入复杂消费者组、dead-letter、后台清理作业

## 6. 设计原则

### 5.1 DB 仍是最终事实

1. `workspace` 的“最近一次成功读取结果”可以进入 Redis
2. `recent/history` 的事实记录仍以 DB 为准
3. `session-events` 的实时短窗口进入 Redis stream，但可展示消息记录仍由当前落库链路负责

### 5.2 Redis 只做热层和短窗口回放

1. `workspace`：加速读取与 sandbox 不可用时的短期 fallback
2. `recent`：首屏热窗口
3. `history`：短期分页辅助，不承担长期归档
4. `session-events`：断线续播与多实例共享短窗口

这条和 `Suna` 的相似点在于“Redis 先承担热路径与 replay”，不同点在于：

1. `Suna` 的 run stream 是执行链主总线
2. oneceo 在 `#11` 阶段只把它用于 session 过程流短窗口，不扩大成统一执行总线

### 5.3 不拆出新身份模型

所有 Redis key 必须继承 `#9/#10`：

1. `userId` 是授权主键
2. `tenantKey` 只是命名空间
3. `sessionId` 是会话态隔离锚点

## 7. Redis 落点

### 6.1 workspace

按 `#10` 既有 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:workspace:dir:{pathHash}
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:workspace:tree:{pathHash}
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:workspace:file:{pathHash}
```

写入规则：

1. 成功读取 live workspace 后，优先写 Redis
2. 同步保留现有 DB fallback 表 `task_session_workspace_cache`
3. 当前阶段不删除 DB fallback，等 Redis 跑稳后再评估是否删除
4. 不新增第二套 workspace 元数据投影，直接缓存当前路由最终返回 payload

读取规则：

1. 先读 Redis
2. Redis 未命中再读当前 live workspace
3. live workspace 不可用时，再退回 DB fallback

这样可以保证：

1. OpenCode / E2B 两条链路统一先走 Redis
2. sandbox 关闭或恢复中时，仍有 DB 兜底
3. 不会像 `Suna` 那样扩成“完整 workspace runtime state”

### 6.2 recent

按 `#10` 既有 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:messages:recent
```

内容：

1. 仅保存最近 50 条可渲染消息页
2. 内容结构直接对齐 `buildTimelinePage()` 输出所需字段
3. 保留 `oldestCursor / newestCursor / hasOlderHistory / sourceVersion`

写入规则：

1. `replaceRecentMessagesSnapshot()` 成功后同步刷新 Redis recent
2. `messages/recent` 路由发现 DB 与 resolved timeline 不一致并触发回写时，同步刷新 Redis

读取规则：

1. `messages/recent` 先读 Redis recent
2. Redis 未命中则读 DB recent
3. DB recent 命中后，立即回填 Redis
4. 对 sandbox + opencode 的“native history 必须优先”判断继续保留，不因 Redis 去掉

### 6.3 history

按 `#10` 既有 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cursor:history
```

本次只补一类内容：

1. `cursor:history`
   - 保存最近一次成功分页使用的 `beforeCursor / oldestCursor / newestCursor / updatedAt`

原因：

1. 当前需求只是减少重复全量解析，不是建设完整的 Redis 历史索引
2. 为每个 `beforeCursor` 建页缓存已经开始接近“迷你历史系统”，超出这次需求
3. `recent + cursor` 已足够支撑首屏恢复和继续上翻，不需要在 `#11` 再发散出新页缓存协议

读取规则：

1. `messages/history` 继续按现有 `resolveRenderableTimelineMessages()` 解析
2. 解析完成后只把最新游标写回 Redis
3. 本次不在 Redis 中缓存历史页内容

### 6.4 session-events

按 `#10` 既有 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:stream:session-events
```

写入对象：

1. `opencode_event`
2. `opencode_error`
3. `status_update`
4. 仅限当前 SSE 回放链路会消费的“会话语义事件”

明确不写入：

1. token 级 text delta
2. 纯内部控制噪音
3. 已在现有链路中过滤掉的 `message.part.updated/delta(text|reasoning)`

写入规则：

1. 事件进入 `opencodeEventStreamService` 后，完成当前 `projectForClient()` 所需投影
2. 以 `sessionEventSeq` 为主序号写入 Redis stream
3. 同时保留当前 DB / message store 落盘链路

读取规则：

1. `/opencode-events` SSE 重连时先读 Redis `session-events` stream
2. 只回放 `lastEventId/since` 之后的短窗口事件
3. Redis 无数据或游标超出窗口时，再退回当前 DB replay

这部分直接参照 `Suna` 的核心思想：

1. SSE 只是 stream 的读取层
2. 真正的回放来源应该是 Redis stream

但不照搬它的完整实现：

1. 不做 `subscribe first, then catch-up` 的统一 hub 层抽象
2. 仍在当前 `task-creation-routes.ts` SSE 路由内闭环完成

## 8. 失效与同步

### 7.1 workspace

当前依赖进程内失效逻辑的地方，改为：

1. 继续执行本地失效
2. 同步删除 Redis 的 `workspace:dir/tree/file:*`

本次不做：

1. 不实现按通配符批量扫描删除的复杂维护作业
2. 不引入独立 invalidation queue

最小方案：

1. `tree` 直接删固定 key
2. `file` 与 `dir` 继续使用现有路径参数重新计算 key 后删除
3. 不新增“已写过 key 列表”索引表或索引键
4. DB fallback 不主动删除，继续保留“最近一次成功结果”

### 7.2 recent / history

1. `replaceRecentMessagesSnapshot()` 更新后，直接覆盖 Redis recent
2. history 热页用 TTL 自然失效，不做额外主动删除
3. `recentHistoryHydrationInFlight` 仍先保留进程内实现，本次不额外改成分布式锁

原因：

1. 当前瓶颈主要是热页缺 Redis，不是 hydration 锁本身
2. 如果现在把它一起改成分布式协调，会超出 `#11` 范围

### 7.3 session-events

1. stream 只靠 `MAXLEN + TTL` 裁剪
2. 不做事件级删除
3. 回放失败继续退回当前 DB replay
