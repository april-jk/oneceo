# 20260401 OSAC二进制改为Cloudflare R2下发设计 [20260401-2220已采用]

## 1. 背景

当前 E2B sandbox 启动 OSAC 的方式，是平台后端直接读取本地 OSAC 二进制，再通过 `e2bConnector.writeFile()` 把文件写进 sandbox，随后在 sandbox 内执行启动命令。

现状问题：

1. OSAC 二进制分发强依赖 API 服务本地文件系统，不利于多实例部署与版本治理。
2. 二进制实际传输链路经过主后端，发布与回滚边界不清晰。
3. 如果后续继续扩展为更多 runtime 工件，这种“后端直接下发文件”的模式会让 API 服务承担过多制品分发职责。

本方案目标是把 OSAC 二进制分发迁移到 Cloudflare 对象存储完成，同时满足：

1. sandbox 下载来源改为 Cloudflare R2。
2. 不把长期主密钥送进 sandbox。
3. 权限最小化，且权限边界清楚。
4. 保留现有 OSAC bridge 启动语义，不改变 OSAC 在 sandbox 内的运行方式。

## 2. 范围

本方案只覆盖：

1. OSAC Linux amd64 二进制的存储、发布、下载与校验。
2. API 服务在 sandbox provision 时，如何改为向 sandbox 下发“下载指令”而不是“文件内容”。
3. Cloudflare 侧 bucket、对象路径、读写权限、临时授权策略。
4. 管理后台中 OSAC 版本管理、发布 latest 与回滚的产品和数据设计。

本方案不覆盖：

1. OpenCode 二进制分发改造。
2. Codex CLI 分发改造。
3. sandbox 内其他配置文件、skill 文件、workspace 归档链路改造。
4. 公网匿名开放下载。

## 3. 设计原则

1. OSAC 二进制必须由 Cloudflare R2 作为唯一制品源。
2. sandbox 内不允许出现长期 R2 Access Key、Secret Access Key、Cloudflare API Token。
3. 下载授权默认使用单对象、短 TTL、只读的 presigned GET URL。
4. 只有在未来明确出现“多对象批量拉取”需求时，才允许引入临时凭证模式。
5. sandbox 端必须做完整性校验，避免下载链路被替换或对象被误覆盖。
6. 不做兼容性补丁方案。本次目标是收敛到单一路径。

## 4. Cloudflare 官方能力依据

以下能力来自 Cloudflare 官方文档：

1. R2 支持 presigned URL，适合为单个对象提供临时访问，且不暴露 API 凭证。
   来源：
   [Presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)
   [Download objects](https://developers.cloudflare.com/r2/objects/download-objects/)
2. R2 支持 temporary access credentials，可限制到 bucket、prefix 或 object，且 TTL 最长 7 天。
   来源：
   [R2 Temporary Credentials API](https://developers.cloudflare.com/api/node/resources/r2/subresources/temporary_credentials/methods/create/)
   [R2 Authentication / Temporary access credentials](https://developers.cloudflare.com/r2/api/tokens/)

从上述能力可以推导出：

1. 如果只是下载单个固定二进制，presigned GET URL 的权限边界比临时密钥更小。
2. temporary credentials 虽然是临时的，但本质仍是一组可用 S3 凭证，需要注入 sandbox 环境，泄露面大于 presigned URL。

因此，本方案选型为：

1. 主方案：R2 presigned GET URL
2. 备用方案：R2 temporary credentials，仅在未来确有多对象拉取需求时启用

## 5. 主方案

### 5.1 总体架构

链路改为：

1. 构建/发布阶段把 OSAC 二进制上传到 Cloudflare R2。
2. API 在 provision OSAC bridge 前，为目标版本对象生成一个短时 presigned GET URL。
3. API 把“下载 URL + 期望 sha256 + 目标路径”作为启动参数交给 sandbox。
4. sandbox 通过 `curl` 或等价工具直接从 R2 下载 OSAC 二进制。
5. sandbox 校验 sha256，校验通过后 `chmod +x` 并启动 OSAC。

这里 API 只负责“签发临时下载地址”，不再传输二进制正文。

### 5.2 存储位置设计

新增专用 R2 bucket：

`oneceo-sandbox-artifacts`

对象路径规范：

1. OSAC 正式版
   `osac/linux/amd64/<version>/osac`
2. OSAC 调试版
   `osac/linux/amd64/<version>/osac_debug`
3. 元数据清单
   `osac/linux/amd64/<version>/manifest.json`
4. latest 指针
   `osac/linux/amd64/latest.json`

`manifest.json` 建议内容：

1. `version`
2. `platform`
3. `arch`
4. `objectKey`
5. `sha256`
6. `size`
7. `builtAt`
8. `sourceCommit`
9. `channel`

`latest.json` 建议内容：

1. `version`
2. `channel`
3. `objectKey`
4. `sha256`
5. `manifestKey`
6. `publishedAt`
7. `publishedBy`
8. `releaseId`

说明：

1. 使用独立 bucket，避免与 workspace archive、用户附件、交付物共桶。
2. 使用版本化路径，避免“覆盖同名文件”导致历史 sandbox 下载到错误工件。
3. manifest 与对象同路径存放，便于发布与回滚审计。
4. latest 不存放二进制，只存放“当前发布版本指针”。

### 5.3 权限设计

需要三类权限主体。

#### 5.3.1 发布写入主体

用途：

1. CI 或人工发布流程把新 OSAC 二进制和 manifest 上传到 R2。

权限：

1. 仅允许 `oneceo-sandbox-artifacts` bucket
2. 仅允许写入 `osac/linux/amd64/` 前缀
3. 允许读回刚上传的对象用于校验

建议权限：

1. R2 `Object Read Write`
2. 单 bucket 作用域
3. 不授予其他 bucket 权限

#### 5.3.2 API 签发主体

用途：

1. API 生成 presigned GET URL。

权限：

1. 仅允许 `oneceo-sandbox-artifacts` bucket
2. 仅需读取 OSAC 对象
3. 不需要写权限

建议权限：

1. R2 `Object Read Only`
2. 单 bucket 作用域

说明：

1. 该主体的长期凭证只留在 API 服务端。
2. 该主体不进入 sandbox。
3. 其能力仅用于签发下载 URL，不能上传、删除对象。

#### 5.3.3 sandbox 下载主体

用途：

1. 在 sandbox 内拉取 OSAC 二进制。

权限设计：

1. 不下发任何长期 Access Key
2. 不下发任何 Cloudflare API Token
3. 默认不下发任何临时 S3 凭证
4. 只下发一个 presigned GET URL

说明：

1. presigned URL 本质是一个短时 bearer token，但只对单对象、单方法、短 TTL 生效。
2. 泄露面远小于临时 S3 凭证。

### 5.4 鉴权与 TTL 设计

presigned URL 限制如下：

1. 方法：仅 `GET`
2. 对象：单个 `osac/linux/amd64/<version>/osac`
3. TTL：默认 120 秒
4. provision 重试时重新签发，禁止复用旧 URL

TTL 选择理由：

1. sandbox 下载的是单个二进制，体积较小，120 秒足够覆盖常规网络波动。
2. TTL 过长会扩大泄露窗口。
3. 若下载失败，API 重新 provision 或重试时可重新签一个新 URL。

### 5.5 完整性校验

sandbox 下载后必须执行：

1. `sha256sum <file>` 与 manifest 中记录值比对
2. ELF/amd64 检查继续保留
3. 仅校验通过才允许启动

原因：

1. presigned URL 解决“授权”问题，不替代“完整性”问题。
2. 即使对象路径写错或发布流程错误，sha256 校验也能阻断错误工件进入运行态。

### 5.6 sandbox 启动流程

启动动作调整为：

1. API 解析当前已发布 latest 指针，拿到 version/objectKey/sha256
2. API 生成该对象的 presigned GET URL
3. API 调用 `e2bConnector.runCommand()` 在 sandbox 内执行：
   1. 创建目录
   2. `curl -fL '<presigned-url>' -o '<remoteBinary>.tmp'`
   3. 校验 sha256
   4. 原子替换为 `<remoteBinary>`
   5. `chmod +x`
4. API 继续执行现有 `nohup osac ...` 启动逻辑

关键变化：

1. 仍然由 API 驱动启动时机
2. 但不再通过 API 传输文件内容
3. OSAC 文件源从“后端本地文件”切到“R2 对象”

### 5.7 latest 自动跟随策略

当前要求已经明确包含“后续从 cf 下载时自动下载最新版本”。

本方案对“最新”的定义必须是：

1. 不是 bucket 中按文件名排序得到的最新
2. 不是按上传时间自动取最新
3. 而是平台在管理端显式发布后的 `latest.json`

原因：

1. 上传完成不代表可以立即进入生产。
2. 需要允许先上传、后验证、再发布。
3. 需要允许回滚到历史稳定版本。

因此 sandbox provision 的自动下载逻辑是：

1. 查询平台“当前 published release”
2. 读取对应 `objectKey` 和 `sha256`
3. 生成 presigned URL
4. sandbox 下载该 published release

“自动下载最新”在这里应理解为：

1. 自动下载“平台已发布的最新版本”
2. 不是“R2 中最新上传的任意对象”

## 6. 管理后台设计

### 6.1 目标

管理后台需要新增一套 OSAC 版本管理能力，满足：

1. 上传新的 OSAC 二进制到 Cloudflare R2
2. 管理版本标签、说明、sha256、来源 commit
3. 明确区分“已上传”和“已发布”
4. 一键发布为 latest
5. 支持回滚到历史稳定版本
6. 允许查看当前线上 sandbox 将会下载的 OSAC 版本

### 6.2 入口与定位

建议放在管理端 sandbox 相关管理域，而不是放在用户态部署工作台。

建议入口：

1. `管理后台 / Sandbox / OSAC 版本管理`

原因：

1. 这是平台运行时工件，不是终端用户资产。
2. 需要与 sandbox 健康、OSAC endpoint、版本排障放在同一运维语境。
3. 权限应严格限定给平台管理员。

### 6.3 页面结构

页面由三块核心区域组成。

#### 6.3.1 顶部状态卡

展示当前线上状态：

1. `Current Published`
   - 当前生效版本号
   - 发布时间
   - 发布人
   - sha256 简写
2. `Channel`
   - 当前固定为 `stable`
3. `R2 Bucket`
   - 当前 bucket 名
4. `Distribution Mode`
   - `R2 presigned GET`

#### 6.3.2 OSAC 版本管理标签卡

这是本次要求中的核心交互。

建议为卡片式 tab：

1. `已发布`
2. `待发布`
3. `全部版本`
4. `上传新版本`

各标签职责：

1. `已发布`
   - 只显示当前 published release
   - 提供“回滚到历史版本”入口
2. `待发布`
   - 显示已上传但未发布的版本
   - 提供“校验通过后发布 latest”
3. `全部版本`
   - 时间倒序列出所有 revision
   - 显示状态、上传时间、发布时间、来源 commit、sha256
4. `上传新版本`
   - 上传二进制
   - 填写版本号、说明、channel、source commit
   - 生成 sha256
   - 执行上传与记录创建

#### 6.3.3 版本详情面板

选中某个 revision 后展示：

1. version
2. status
   - `uploaded`
   - `validated`
   - `published`
   - `archived`
3. objectKey
4. manifestKey
5. sha256
6. size
7. builtAt
8. sourceCommit
9. uploadedBy
10. uploadedAt
11. publishedBy
12. publishedAt
13. releaseNotes

操作按钮：

1. `校验文件`
2. `发布为 latest`
3. `回滚到此版本`
4. `归档版本`

### 6.4 页面交互原则

1. 上传不等于发布。
2. 发布 latest 必须是显式动作。
3. 回滚本质上也是一次“重新发布 latest 指针”的动作。
4. 页面默认高亮当前 published 版本，而不是最新上传版本。
5. 不允许直接删除已发布版本对象，避免破坏历史审计与回滚能力。

### 6.5 与现有后台范式对齐

管理端现有 `ConnectorGuideManagementSection` 已经有 `revision + publish + rollback` 的交互模型。

OSAC 版本管理建议复用同一语义：

1. `revision` 对应一个上传后的 OSAC release
2. `publish` 对应更新 `latest.json` 与平台 published 指针
3. `rollback` 对应把历史 revision 重新发布为 latest

这样可以避免后台出现两套互相冲突的“版本/发布”概念。

## 7. 数据模型设计

### 7.1 新增 release 表

建议新增平台级表：

`platform_runtime_artifact_releases`

建议字段：

1. `id`
2. `artifactType`
   - 当前固定 `osac`
3. `platform`
   - 当前固定 `linux`
4. `arch`
   - 当前固定 `amd64`
5. `version`
6. `channel`
   - 当前默认 `stable`
7. `status`
   - `uploaded`
   - `validated`
   - `published`
   - `archived`
8. `bucket`
9. `objectKey`
10. `manifestKey`
11. `sha256`
12. `sizeBytes`
13. `releaseNotes`
14. `sourceCommit`
15. `uploadedBy`
16. `uploadedAt`
17. `publishedBy`
18. `publishedAt`
19. `archivedAt`
20. `metadataJson`

约束：

1. `artifactType + platform + arch + version` 唯一
2. 同一 `artifactType + channel` 在任一时刻只允许一个 `published`

### 7.2 published 指针表

建议新增：

`platform_runtime_artifact_channels`

建议字段：

1. `id`
2. `artifactType`
3. `platform`
4. `arch`
5. `channel`
6. `publishedReleaseId`
7. `updatedBy`
8. `updatedAt`

作用：

1. 平台数据库中的真相源
2. 与 R2 中的 `latest.json` 同步

规则：

1. 数据库是平台真相源
2. R2 `latest.json` 是 sandbox 下载真相源的外部投影
3. 发布操作必须同时更新 DB 与 R2 latest 指针

## 8. 管理端上传与发布流程

### 8.1 上传新版本

后台流程：

1. 管理员在“上传新版本”卡中选择本地二进制文件
2. 填写：
   - version
   - release notes
   - source commit
3. 后端流式接收文件
4. 后端计算 sha256 与 size
5. 后端上传到 R2：
   - `osac/linux/amd64/<version>/osac`
   - `osac/linux/amd64/<version>/manifest.json`
6. 后端创建 release 记录，状态为 `uploaded`

权限要求：

1. 只有管理后台服务端持有 R2 写入凭证
2. 浏览器永远不直接拿到 R2 凭证

### 8.2 校验版本

上传后可执行服务端校验：

1. 读取 manifest
2. 校验 objectKey 存在
3. 校验 sha256 与数据库一致
4. 可选地做 ELF/linux-amd64 头检查

校验通过后状态转为 `validated`。

### 8.3 发布 latest

发布动作必须是显式按钮。

发布步骤：

1. 锁定目标 release
2. 更新数据库 channel 指针
3. 将目标 release 内容写入 R2 `osac/linux/amd64/latest.json`
4. 将目标 release 状态置为 `published`
5. 旧 published release 状态回退为 `validated`
6. 写审计日志

### 8.4 回滚

回滚与发布共用同一套逻辑：

1. 在历史版本中选中某个已验证 release
2. 点击“回滚到此版本”
3. 平台重新更新 channel 指针与 `latest.json`
4. 后续所有新 sandbox 自动下载该回滚版本

## 9. sandbox 自动下载最新版本的精确定义

### 9.1 解析顺序

新 sandbox 在启动 OSAC 时，应按以下顺序解析目标版本：

1. 若 provision 明确指定 releaseId 或 version，则使用指定版本
2. 否则读取平台 channel 当前 published release
3. 再由该 release 生成 presigned GET URL

默认情况下：

1. 不传 version
2. 直接走 `stable` channel 的 published release

### 9.2 为什么不能直接读 R2 目录取最新

禁止做法：

1. 列 bucket 前缀取最新上传对象
2. 按对象名排序推断最新版本

原因：

1. 最新上传未必经过验证
2. 上传时间和生产可用性不是同一回事
3. 无法稳定支持回滚

## 10. API 与配置调整设计

## 6. 备用方案

### 6.1 何时启用 temporary credentials

只有在未来满足以下条件时才考虑切换：

1. sandbox 在一次启动中必须拉取多个对象
2. 对象列表在运行时动态决定
3. 多次单对象 presigned URL 管理成本明显高于临时凭证

### 6.2 备用方案权限边界

若启用 R2 temporary credentials，则必须限制为：

1. 权限：`object-read-only`
2. bucket：`oneceo-sandbox-artifacts`
3. objects：仅允许单对象或极小前缀
4. TTL：不超过 300 秒

同时要求：

1. 临时凭证只放在单次下载命令的环境变量中
2. 下载完成后立即清理环境变量与 shell 历史
3. 不写入磁盘配置文件

但即便如此，该方案仍弱于 presigned URL，因此不作为默认方案。

### 10.1 新增配置

新增配置项建议：

1. `OSAC_R2_BUCKET`
2. `OSAC_R2_PRESIGN_TTL_SECONDS`
3. `OSAC_R2_ACCOUNT_ID`
4. `OSAC_R2_READ_ACCESS_KEY_ID`
5. `OSAC_R2_READ_SECRET_ACCESS_KEY`
6. `OSAC_R2_WRITE_ACCESS_KEY_ID`
7. `OSAC_R2_WRITE_SECRET_ACCESS_KEY`

其中：

1. `OSAC_R2_READ_ACCESS_KEY_ID`
2. `OSAC_R2_READ_SECRET_ACCESS_KEY`
3. `OSAC_R2_WRITE_ACCESS_KEY_ID`
4. `OSAC_R2_WRITE_SECRET_ACCESS_KEY`

只允许出现在 API 服务端环境变量中，禁止透传到 sandbox。

变量优先级约定：

1. 优先读取专用 `OSAC_R2_*` 配置
2. 若未配置专用 bucket/account/endpoint/credentials，则自动回退到现有通用 `R2_BUCKET_NAME`、`R2_ACCOUNT_ID`、`R2_ENDPOINT`、`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`

这样做的目的：

1. 生产环境可以先直接复用当前 Cloudflare R2 配置完成接入
2. 后续若切到独立 OSAC bucket 或拆分只读/只写凭证，只需补充 `OSAC_R2_*` 变量，不需要改代码

### 10.2 现有配置处理

现有配置中的：

1. `osacBootstrapConfig.osacBinaryPath`
2. `/osac/binaries/:name`
3. `OSAC_DOWNLOAD_BASE_URL`
4. `OSAC_BINARY_TOKEN`

在本方案采用后，处理原则如下：

1. `osacBinaryPath` 仅保留给发布脚本或本地开发辅助用途，不再参与 sandbox 生产分发
2. `/osac/binaries/:name` 从生产链路移除
3. `OSAC_DOWNLOAD_BASE_URL` 不再作为主路径
4. `OSAC_BINARY_TOKEN` 不再用于 sandbox 下载鉴权

这意味着 OSAC 文件分发将收敛到唯一入口：R2 对象 + presigned GET URL。

## 11. 发布与回滚设计

发布流程：

1. 构建 OSAC 二进制
2. 计算 sha256
3. 上传到 `osac/linux/amd64/<version>/osac`
4. 上传 `manifest.json`
5. 在管理端生成 release 记录
6. 通过“发布为 latest”把该版本切为当前线上版本

回滚流程：

1. 在管理端选择目标历史 release
2. 重新发布为 latest
3. 不覆盖现有对象
4. 不删除历史版本对象

好处：

1. 回滚只涉及配置切换，不涉及重新分发文件
2. 已发布对象天然可审计
3. 不会出现“同一路径对象被覆盖导致旧 sandbox 拉错版本”

## 12. 安全分析

### 9.1 为什么主方案比“后端直接下发文件”更合理

1. API 不再承担二进制正文传输。
2. 工件源统一到对象存储，版本管理更清晰。
3. 可以独立审计 bucket 中到底发布了哪些版本。

### 9.2 为什么主方案比“给 sandbox 临时凭证”更合理

1. presigned URL 不需要把任何 S3 Access Key/Secret/SessionToken 放进 sandbox。
2. 授权粒度天然是“单对象 + 单方法 + TTL”。
3. 即使 URL 泄露，也只影响一个对象和极短时间窗口。

### 9.3 风险与控制

风险：

1. presigned URL 被日志打印
2. sandbox 下载时网络短暂抖动
3. 错误版本对象被签发

控制措施：

1. 日志中禁止输出完整 presigned URL，只记录 bucket/key/version/ttl
2. 下载失败时允许重新签发重试，不复用旧 URL
3. 强制 sha256 校验
4. 对象 key 使用版本化路径，不允许覆盖式发布

## 13. 对现有架构的影响

影响点：

1. [`sandbox-osac-bridge-service.ts`](/Users/watson/codingProj/oneceo/apps/api/src/services/sandbox-osac-bridge-service.ts)
   当前直接 `fs.readFile(local binary)` + `e2bConnector.writeFile()` 的路径需要替换为“签发 URL + sandbox 内下载”
2. [`osac-routes.ts`](/Users/watson/codingProj/oneceo/apps/api/src/routes/osac-routes.ts)
   当前 `/binaries/:name` 生产用途可移除
3. 发布流程
   需要增加“上传 OSAC 到 R2 + 生成 manifest + 管理端发布 latest”的工件发布步骤
4. 管理后台
   需要新增 OSAC 版本管理页面与对应 API

不变点：

1. sandbox 仍通过 `e2b-connector` 执行命令
2. OSAC 仍由平台控制启动
3. OSAC websocket endpoint 与 bridge ready 逻辑不变

## 14. 验收标准

方案采用后，必须满足：

1. 生产 provision 链路中，API 不再调用 `e2bConnector.writeFile(...osac binary...)`
2. sandbox 内不存在长期 R2 Access Key、Secret、Cloudflare API Token
3. sandbox 启动日志中可看到“从 R2 下载 OSAC”而不是“后端文件写入”
4. 下载对象必须通过 sha256 校验
5. 版本回滚只需切换对象 key 或版本配置
6. `/osac/binaries/:name` 不再是生产依赖链路
7. 管理端可以上传 OSAC 二进制并生成 release
8. 管理端可以显式发布 latest 与回滚历史版本
9. 新 sandbox 默认跟随当前 published latest，而不是跟随最新上传文件

## 15. 最终建议

建议采用以下最终方案：

1. 使用 Cloudflare R2 建立独立 bucket：`oneceo-sandbox-artifacts`
2. OSAC 使用版本化对象路径：`osac/linux/amd64/<version>/osac`
3. 增加管理端 OSAC 版本管理标签卡，统一管理 revision、发布与回滚
4. API 仅持有单 bucket、只读的 R2 长期凭证，用于生成 presigned GET URL
5. 后台上传链路由服务端持有单 bucket、指定前缀的写权限
6. sandbox 只接收单对象、短 TTL 的 presigned GET URL，不接收任何长期主密钥
7. 下载后强制做 sha256 与 ELF/amd64 校验
8. 暂不采用 temporary credentials 作为主路径
9. “自动下载最新”严格定义为“自动下载后台已发布 latest 的版本”

原因：

1. 该路径满足“通过 Cloudflare 存储桶下发”
2. 该路径同时满足“后台可管理版本与发布”
3. 权限边界最小
4. 不会把主密钥送进 sandbox
5. 相比临时凭证，泄露面更小，链路也更短
6. 相比“按上传时间自动取最新”，更符合生产可控发布语义
