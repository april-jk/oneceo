# 07 前端对话页与交互状态

## 1. 当前问题

当前 managed 前端逻辑集中在：

- `useTaskCreationAgent.ts`

并同时承担：

- session 创建
- runtime 预热
- WebSocket 消息发送
- SSE 事件合并
- direct mode / managed mode 双模式分支
- interrupt / replay / restore

这导致 managed 前端状态过重，且与 direct mode 强耦合。

## 2. 目标前端结构

建议把前端拆成两套 hook：

### 2.1 managed

- `useAltusManagedConversation`
- `useAltusManagedRunStream`

### 2.2 direct

- 保持现有 `useTaskCreationAgent` 的 direct 分支

## 3. managed 前端最小流程

1. 发送输入
2. 确保 session 存在
3. 调用 `start run`
4. 保存 `activeRunId`
5. 订阅 `run stream`
6. 将 stream 事件转换为 UI 状态

## 4. 前端状态模型

managed mode 仅保留以下 UI 状态：

- `session`
- `messages`
- `activeRun`
- `runStatus`
- `isStreaming`
- `needsUserInput`

不再保留 direct 风格状态：

- `opencodeSessionId`
- `executorSessionId`
- `runtimeReady`
- `sseCursor`

这些状态不属于 managed 模式。

设置层也要遵守这个边界：

1. 当用户选择 `Altus 接管模式（managed mode）` 时，不显示执行器选择。
2. `OpenCode / ClaudeCode / Codex` 执行器选择只属于 `直通模式（sandbox mode）`。
3. 切到 managed mode 时可以保留上一次 direct mode 的 executor 记忆，但不得在 UI 上继续要求用户选择 executor。
4. managed mode 的流式消息与工具事件必须显式标记为 `Altus`，不得沿用 `Codex` 的事件文案或执行器标签。
5. managed mode 的 assistant 消息不得暴露底层模型提供商身份；前端展示名称统一为 `Altus`。

## 5. 中断与继续

managed 前端中断逻辑应改成：

1. 用户点击停止
2. 调用 `POST /runs/:runId/stop`
3. UI 标记当前 run 为 stopped
4. 下一次发送消息时创建新 run

不再使用当前围绕 `activeManagedRuns` 和 replay input 的进程内修补逻辑。

## 6. Clarification 交互

当 run 进入 `waiting_user`：

1. 对话页显示 clarification message
2. 输入框继续可用
3. 用户回复后启动新 run
4. 新 run 自动从 session 历史中读取未完成问题

## 6.1 原子消息规范

managed mode 的流式事件不能继续粗暴复用 direct mode 的 `status_update / executor_event` 展示语义，前端需要把以下事件收敛成稳定的原子消息单元：

- `run_ack`
  - 展示为一次 run 启动胶囊，不重复堆叠。
- `run_status`
  - 作为当前 run 的状态胶囊更新，不生成多条噪音消息。
- `tool_call_started -> tool_call_completed / tool_call_failed`
  - 必须以 `toolCallId` 作为同一原子卡片的稳定 key。
  - UI 上表现为一个紧凑工具卡片的状态更迭，而不是两条分离文本。
- `clarification_requested`
  - 展示为独立澄清消息，不与普通 assistant 文本混排。
- `artifact_updated`
  - 以轻量 review 胶囊展示，不能伪装成执行器输出文本。

样式要求：

- managed 原子消息默认比 direct mode 更紧凑
- 工具卡片只保留：工具名、状态、摘要
- 原子消息主形态应为紧凑胶囊/芯片，而不是大块执行卡片
- 鼠标 hover 到工具原子消息时，需要显示 hover detail，包含工具用途、目标对象、输入/输出摘要与失败原因
- hover detail 只展示高价值摘要，不直接把完整 JSON 倾倒到主层
- 详情内容折叠到点击后的 detail dialog，不在主消息流里铺开

首轮反馈补充约束：

1. `start run` 成功返回后，前端允许先按与 stream 完全相同的 `messageKey` 本地种入一条 `run_ack` 原子胶囊，用来覆盖 EventSource 尚未建立前的空档；后续真实 `run_ack` 到达时只能做同 key 合并，不能再额外堆一条。
2. 后端需要在 sandbox/运行环境准备阶段先发一次 `run_status(starting)`，待真正进入执行后再推进到 `run_status(running)`，避免首轮长时间只剩空白等待。
3. `assistant_delta` 与最终 `assistant_message` 必须共享同一稳定 `messageKey`，前端按同 key 追加 delta、再由最终消息收口，不能把每个 chunk 渲染成独立消息，也不能让 final 变成第二条重复 assistant。
4. managed `run stream` 的身份信息不能只依赖普通 fetch header，因为浏览器 `EventSource` 无法携带自定义 `X-User-Id`；前端订阅 URL 必须显式带当前认证用户 `userId`，后端再按 `session.userId === query.userId` 做强校验。
5. `POST /api/altus-managed/inputs` 不能把首轮文本消息阻塞在 sandbox 预热、OSAC 启动或 skill 下发完成之后才返回；对于无附件消息，接口必须优先创建 run 并返回 `runId`，让前端立刻建立 `run stream`，真正的 sandbox 准备与 skill 同步归入 run 协调阶段执行。

新会话首轮跳转补充约束：

1. `bindSessionId(...)` 后不能仅凭 `sessionId state` 已更新就清除 route-sync guard，必须等 URL 真正收敛到 `/session/:id` 且清掉遗留的 `?new` / `?sessionId` 参数后，才允许释放同步保护。
2. 在 route-sync guard 未释放前，location/search effect 不得因为看到旧的 `?new` 或空 path 而调用 `resetConversationState(...)`，否则会把刚种入的新 session optimistic 消息与恢复状态清空。
3. `loadHistory(initial)` 允许在新 session 绑定后立即执行，但它必须建立在“已保留 optimistic cache 且 route-sync guard 仍有效”的前提上，避免首轮跳转期间出现 reset 与 history 初始化互相打架。

## 6.2 产物预览卡与网页预览

managed mode 还需要继续对齐 `suna` 的“过程预览 + 完成卡片”链路，不能只停在原子消息。

目标分层：

1. 输入区附近的轻量工具预览
2. 对话消息流中的过程预览
3. run 完成后的产物卡片

其中第 3 层是当前 oneceo 最缺失的部分。对于网页类任务，完成卡片至少要提供：

- `Preview`
- `Code`
- `Open`

并且 `Preview` 必须建立在真实 workspace raw file URL 之上，而不是仅靠 `/workspace/file` 的 JSON 响应临时拼 `srcDoc`。

当前已落地的第一阶段实现：

- `apps/api/src/routes/task-creation-routes.ts`
  - 新增 `/workspace/raw/*`
  - Altus workspace 文件读取改为与 Codex 一样走 E2B 分支
- `apps/web/client/src/lib/task-creation-client.ts`
  - 新增 `getWorkspaceRawFileUrl(...)`
- `apps/web/client/src/components/AltusArtifactPreviewCard.tsx`
  - 新增网页类产物完成卡片
- `apps/web/client/src/pages/Home.tsx`
  - 将 `write_file` 完成事件聚合为 run 级 `managed_artifact_card`
  - 只要 managed `assistant_message` / `status_update` metadata 已经携带 `deliverables`，就立即插入最终交付卡片，不等待 `run_completed`
  - `run_completed` 仅作为网页类 artifact 卡片的兜底收口，不应阻塞正式 deliverable 卡片展示

当前进一步收口后的约束：

- 最终完成卡片只展示网页类产物，不再把 `game.js` 这类纯代码文件抬为主卡片
- 完成卡片右上角 `Open in viewer` 必须进入 oneceo 内部右侧预览面板
- 卡片内部工具条 `Open` 仍可保留为外部打开 raw 页面
- replay `Files` 视图允许继续查看代码文件，但它与“最终完成卡片”的语义必须分离

当前阶段仍未落地的点：

- 输入区附近的 floating preview
- 过程中的文件内容流式 preview
- 非 HTML 文件的 richer preview renderer

当前已落地的第二阶段实现：

- `apps/web/client/src/components/AltusRunReplayDrawer.tsx`
  - 已新增独立的 `Actions / Files` 抽屉查看器
  - 已支持 `Prev / Next / Jump to Latest`
- `apps/web/client/src/pages/Home.tsx`
  - 已把 managed 结构化事件聚合为 run 级 replay actions / files
  - 已支持从 `managed_tool` 原子消息点击后跳到对应 replay step

当前仍未落地的点：

- 输入区附近的 floating preview
- 过程中的文件内容流式 preview
- 非 HTML 文件的 richer preview renderer

更完整的代码级研究与实现边界，见：

- `docs/agent研发文档/Altus接管模式参照Suna重构设计/12_Suna预览卡片与Altus产物预览对齐设计.md`

## 6.3 Actions / Files 回放查看器

对齐 `suna` 的目标不只是产物卡片，还包括独立的运行查看器：

- `Actions`
- `Files`
- `Prev`
- `Next`
- `Jump to Latest`

这一层不应直接复用 direct mode 的预览面板，而应在 managed mode 新增独立的 replay drawer。

建议最小状态：

- `isAltusReplayOpen`
- `activeReplayRunId`
- `activeReplayView`
  - `actions | files`
- `currentReplayIndex`
- `latestReplayIndex`

建议最小组件：

- `AltusRunReplayDrawer`
- `AltusRunActionsView`
- `AltusRunFilesView`

数据来源必须是 managed 结构化事件，而不是 assistant markdown：

- `tool_call_started`
- `tool_call_completed`
- `tool_call_failed`
- `run_status`
- `run_completed`

并且聊天流中的 `managed_tool` 原子消息必须支持：

1. 点击消息
2. 打开 replay drawer
3. 跳转到对应 `toolCallId` 的 replay step

## 7. 历史恢复

页面刷新后：

1. 拉取 session messages
2. 拉取 latest run
3. 若 latest run 仍 active，则重连 run stream

这一恢复模型必须独立于 direct mode。

## 8. 设计结论

前端层面的本质变化是：

> managed mode 从“一个超大 hook 同时处理 managed/direct/runtime/SSE”重构为“基于 session 与 run 的标准对话页状态机”。

## 9. Suna 代码参照

本篇前端设计需要对照的 `suna` 源码如下：

- `referance/suna/apps/frontend/src/lib/api/agents.ts` -> `unifiedAgentStart(...)`
  - 对应 oneceo 前端的 `start run` API 调用。
- `referance/suna/apps/frontend/src/lib/streaming/use-agent-stream.ts` -> `startStreaming(...)`
  - 对应 oneceo 的 `useAltusManagedRunStream`。
- `referance/suna/apps/frontend/src/hooks/messages/useAgentStream.ts`
  - 对应 run 事件到 UI 消息状态的转换层。
- `referance/suna/apps/frontend/src/hooks/threads/use-optimistic-agent-start.ts`
  - 对应前端在启动 run 时的 optimistic state 处理。
- `referance/suna/apps/frontend/src/components/thread/chat-input/chat-input.tsx`
  - 对应输入框如何触发 run，而不是直接操作 executor session。
- `referance/suna/apps/frontend/src/stores/suna-modes-store.ts`
  - 说明前端 `mode` 是产品输入与 prompt shaping 信号，不是后端执行分支。
- `referance/suna/apps/frontend/src/components/thread/chat-input/floating-tool-preview.tsx`
  - 对应输入区附近的轻量工具预览。
- `referance/suna/apps/frontend/src/components/thread/content/ShowToolStream.tsx`
  - 对应对话流中的过程预览卡与流式工具预览。
- `referance/suna/apps/frontend/src/components/thread/tool-views/CompleteToolView.tsx`
  - 对应任务完成后的附件/产物卡片。
- `referance/suna/apps/frontend/src/components/thread/file-attachment/index.tsx`
  - 对应附件统一分发到图片、文档、HTML、presentation 等预览组件。
- `referance/suna/apps/frontend/src/components/file-renderers/html-renderer.tsx`
  - 对应 `Preview / Code / Open` 三态网页预览器。
- `referance/suna/apps/frontend/src/lib/utils/url.ts`
  - 对应 HTML 真实 iframe 预览 URL 的构造方式。

oneceo 重构 managed 前端时，应以这些入口为参照拆出 `session UI`、`run stream UI`、`mode UI` 三层，而不是继续在 `useTaskCreationAgent.ts` 内堆叠状态。
