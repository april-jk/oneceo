# OneCEO通用内部部署模板与Umami继承方案 [20260428-1901已采用]

## 1. 背景

本方案用于修复部署稳定性问题中的一个基础缺口：生成应用的形态很多，不能在宏观部署模块里只为 HTML 或某一种框架写特殊逻辑；但完全依赖 agent 临场拼 `package.json`、`railway.json`、健康检查和统计埋点，又会导致部署成功率和统计继承不稳定。

因此 OneCEO 需要一套平台内置的通用内部模板。它不是 Railway Marketplace 模板，也不是替代部署 skill 的提示词，而是在导出部署源码前由平台统一补齐的最小运行契约。

## 2. 目标

- 让静态 HTML、前端构建产物、Node 脚本、Python Web、PHP 站点这些常见形态默认具备可部署基线。
- 在部署前自动继承 OneCEO 的 Umami 监控能力，不要求 agent 在项目代码里硬编码 `websiteId`。
- 用 `oneceo.manifest.json` 和 `railway.json` 固定构建、启动、端口、健康检查的部署契约。
- 将语言/框架修复逻辑放在部署源码归一化层和 deployment skill 内，不把具体模板细节写进宏观部署触发模块。
- 降低回归成本：默认跑模板归一化、合规检查、skill 上下文测试；真实部署只作为高风险发布或专项验收使用。

## 3. 非目标

- 不把 Railway Marketplace 模板作为运行时依赖。Marketplace 适合用户手工创建项目，OneCEO 的生成应用需要动态源码、动态环境变量和会话级绑定。
- 不在部署触发器里用固定关键词决定部署行为。部署是否执行仍由对话上下文、能力工具和 deployment skill 裁决。
- 不为每次部署代码小改动强制跑全语言真实部署矩阵。真实部署有资源成本，不能作为普通单元回归。
- 不在模板里写死 Umami host、websiteId 或用户域名。具体值必须来自部署时的 session analytics binding。

## 4. 分层设计

### 4.1 宏观编排层

负责判断用户是否在请求部署、挂载 deployment skill、调用部署工具、同步部署状态。该层不能关心 HTML、PHP、FastAPI、Vite 等具体模板细节。

### 4.2 部署源码归一化层

负责在发布前识别工作区形态并补齐内部模板材料：

- `package.json`：只在 Node/静态模板需要时生成。
- `server.js`：只在静态 HTML 或前端 dist 需要 Node HTTP 包装时生成。
- `oneceo.manifest.json`：统一声明 appType、stack、build、start、healthcheck、features、runtime。
- `railway.json`：统一落地 Railway config-as-code，避免平台猜 start command。
- PHP/Python 等非 Node 形态不强行转成 Node 项目，只补它们自己的启动契约。

### 4.3 Umami 继承层

部署工具在上传源码前先创建或复用会话级 Umami website binding，然后把运行时变量写入 Railway：

- `VITE_ANALYTICS_ENABLED`
- `VITE_ANALYTICS_HOST`
- `VITE_ANALYTICS_ENDPOINT`
- `VITE_ANALYTICS_WEBSITE_ID`
- `VITE_ANALYTICS_TAG`
- `VITE_PUBLIC_DOMAIN`

内部模板只读取这些变量或被平台注入 snippet，不保存固定监控配置。

### 4.4 合规检查层

部署前必须检查：

- build command 是否存在。
- start command 是否存在。
- 健康检查路径是否与运行时匹配。
- analytics 是否能从工作区或平台注入命中。
- 声明需要数据库时，依赖是否存在。

## 5. 通用内部模板矩阵

| 形态 | 识别信号 | 内部模板动作 | 健康检查 | Umami 继承 |
| --- | --- | --- | --- | --- |
| 静态 HTML | 根目录 `index.html` 且无 `package.json` | 生成 Node 静态服务器、`package.json`、manifest、`railway.json` | `/api/system/health` | HTML 注入 + 运行时 env 替换 |
| 前端 dist | Vite/React/Vue/Svelte 等前端依赖和 HTML 入口 | 将 preview/dev start 改为 `node server.js`，生成 dist 静态服务器 | `/api/system/health` | dist server 运行时注入 |
| Node 脚本 | `server.js` / `index.js` / `app.js` 且无 `package.json` | 生成最小 `package.json`、manifest、`railway.json` | `/health` | 模板入口注入 |
| Python Web | `requirements.txt` / `pyproject.toml` / `main.py` / `app.py` | 根据 FastAPI/Flask 信号生成 start command、manifest、`railway.json` | `/health` | HTML/Jinja 模板注入 |
| PHP 站点 | `index.php` / `public/index.php` | 生成 PHP built-in server start command、manifest、`railway.json` | `/` | 仅在 PHP 文件包含 HTML 文档闭合标签时注入 |
| Java Web | `pom.xml` / `build.gradle` | 第一阶段依赖 deployment skill 修复与 manifest；后续再固化 Java 内部模板 | 由 manifest 指定 | 由模板入口或静态资源注入 |

## 6. PHP 注入边界

PHP 文件既可能是 HTML 模板，也可能是纯接口脚本。为了避免把 `<script>` 直接追加到纯 PHP 代码后面，PHP 入口只在存在 `</body>` 或 `</html>` 时注入 Umami snippet；否则报告无法注入，交给 deployment skill 或项目代码修复。

## 7. 验收条件

1. 静态 HTML、前端 dist、Node 脚本、Python Web 现有模板回归继续通过。
2. PHP 根目录 `index.php` 可被归一化为可部署基线，生成 `oneceo.manifest.json` 与 `railway.json`。
3. PHP HTML 文档可以继承 Umami snippet，且 snippet 写入 `</body>` 前。
4. 纯 PHP 接口文件不会被强行追加 Umami snippet。
5. TypeScript 编译通过。
6. 普通回归不要求真实部署；真实 Railway 部署只在高风险发布、专项验收或用户明确要求时执行。

## 8. 后续扩展

- 将 Java/Spring Boot、PHP Composer、Python ASGI/WSGI 的更完整模板下沉到同一内部模板目录。
- 将模板版本号写入 deployment baseline，便于后续对历史部署做迁移提示。
- 将真实部署矩阵改成按风险触发：低风险跑本地模板回归，高风险抽一个代表形态真实部署，重大发布再跑多形态矩阵。
