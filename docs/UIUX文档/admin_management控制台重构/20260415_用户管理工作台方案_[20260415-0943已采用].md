# 2026-04-15 用户管理工作台方案 [20260415-0943已采用]

## 1. 背景

当前管理后台已经有 `Sandbox 管理`、`对话管理`、`审计日志` 等运行治理入口，但对普通用户 `app_users` 的治理能力仍然缺失：

1. 管理员只能在 `对话管理` 中被动看到用户归属，无法主动按用户维度定位问题。
2. 用户是否活跃、最近从哪里登录、是否仍有活跃会话、最近是否创建过对话或 Sandbox，当前没有统一视图。
3. 当用户归属异常、legacy id 映射残留或需要临时禁用账号时，缺少管理态入口。

本方案只针对 `app_users` 与其关联运行数据建设 `用户管理` 功能，不纳入 `admin_users`，保持“用户态与管理态身份源分离”的既有原则。

## 2. 已确认范围

### 2.1 本次明确包含

1. `app_users`
2. `app_user_sessions`
3. `task_creation_sessions`
4. `sandbox_execution_environments`
5. `app_user_legacy_id_mappings`

### 2.2 本次明确不包含

1. `admin_users` / `admin_user_sessions`
2. 管理员代用户修改密码
3. 后台创建普通用户
4. 用户权限体系、套餐、组织、多租户
5. 连接器、技能、工件等用户配置的直接编辑

## 3. 现有事实

### 3.1 数据与鉴权

1. `app_users` 已包含：
   - `email`
   - `display_name`
   - `status`
   - `created_at`
   - `updated_at`
   - `last_login_at`
2. `app_user_sessions` 已包含：
   - `user_id`
   - `ip_address`
   - `user_agent`
   - `last_seen_at`
   - `expires_at`
   - `revoked_at`
3. 用户态登录链路已经依赖 `app_users.status === 'active'`：
   - 登录时非 `active` 用户不可登录；
   - 请求解析 session 时若用户非 `active`，当前 session 也会被视为无效。

这意味着：

1. 第一阶段无需重做用户态鉴权模型。
2. `禁用用户` 可以直接复用现有 `status` 语义。
3. 为了治理清晰，禁用用户时仍建议同步撤销该用户所有未撤销 session 记录。

### 3.2 管理后台结构

1. 管理后台侧边导航由 `apps/admin_management/web/src/App.tsx` 中的 `NAV_ITEMS` 驱动。
2. 管理后台服务侧采用 BFF 结构：
   - `apps/admin_management/server/routes/*`
   - `apps/admin_management/server/services/*`
   - `apps/admin_management/server/connectors/oneceo-api-connector.ts`
3. 重量级平台页已逐步拆成独立组件，例如：
   - `SkillManagementSection`
   - `ConnectorGuideManagementSection`
   - `OsacReleaseManagementSection`

因此用户管理也应走同样路径，而不是继续膨胀 `App.tsx`。

## 4. 目标与非目标

### 4.1 目标

1. 在管理后台新增与 `Sandbox 管理`、`对话管理` 同级的 `用户管理` 一级入口。
2. 让管理员能按用户维度查看：
   - 基础身份
   - 最近登录与活跃
   - 活跃 session
   - 最近对话
   - 最近 Sandbox
   - legacy id 映射
3. 提供最小但有效的治理动作：
   - 启用用户
   - 禁用用户
   - 强制下线全部 session
4. 提供“归属异常”视角，帮助管理员反查 legacy 或绑定异常问题。
5. 保持移动端与中窄屏可用，不新增杂乱层级。

### 4.2 非目标

1. 不把用户管理做成 CRM。
2. 不在第一阶段做用户资料任意编辑。
3. 不把 `admin_users` 混入同一页。
4. 不绕开现有用户态认证链路。
5. 不新增 Redis 依赖。

## 5. 信息架构建议

### 5.1 导航层级

建议在侧边栏 `运行管理` 分组下新增：

- `用户管理`
  - tag：`USR`
  - subtitle：`用户身份与会话`
  - signal：`用户治理`

放在 `Sandbox 管理` 与 `对话管理` 同级，但仍归属 `运行管理`，原因是该页面的主要价值是服务会话归属、运行排障与风险治理，而不是平台配置。

### 5.2 页面结构

用户管理页建议采用：

`全宽索引面板 + 统一详情抽屉`

原因：

1. 管理员会先扫列表，再点开单个用户处理问题。
2. 抽屉能保留列表上下文，不需要像对话管理那样切入重型 popup。
3. 现有后台已具备 drawer 样式基础，可以复用。

页面分为四层：

1. 顶部摘要
2. 筛选工具栏
3. 用户索引表
4. 详情抽屉

## 6. 页面方案

### 6.1 顶部摘要

首屏只保留四项：

1. `全部用户`
2. `7 天活跃`
3. `已禁用`
4. `归属异常`

说明：

1. `7 天活跃` 以 `app_user_sessions.last_seen_at` 或会话最新活跃时间聚合。
2. `归属异常` 指存在 legacy 映射残留、缺少 canonical 归属或关联记录异常的用户。

### 6.2 筛选栏

建议第一版只做以下筛选，保持短路径：

1. 关键词：
   - 邮箱
   - 显示名
   - 用户 ID
2. 状态：
   - 全部
   - 启用
   - 禁用
3. 活跃度：
   - 全部
   - 7 天活跃
   - 30 天活跃
   - 长期未活跃
4. 活跃会话：
   - 全部
   - 有活跃会话
   - 无活跃会话
5. 对话：
   - 有对话
   - 无对话
6. Sandbox：
   - 有 Sandbox
   - 无 Sandbox
7. 归属健康：
   - 全部
   - 正常
   - 存在 legacy 映射
   - 存在异常

### 6.3 列表列设计

第一版不建议做过多窄列，建议收成五列：

1. `用户`
   - 显示名
   - 邮箱
   - 用户 ID（短展示 + 复制）
2. `状态`
   - 启用 / 禁用
   - 注册时间
3. `最近活跃`
   - 最近登录
   - 最近 seen
   - 最近 IP
4. `关联概况`
   - 活跃 session 数
   - 对话数
   - Sandbox 数
   - 归属健康标签
5. `操作`
   - 查看详情

这样列表横向更稳，也符合“先扫读后深挖”的操作习惯。

### 6.4 详情抽屉

详情抽屉建议采用二级 tab：

1. `概览`
2. `登录会话`
3. `对话`
4. `Sandbox`
5. `映射`

各 Tab 建议内容如下。

#### 6.4.1 概览

1. 用户基础信息：
   - 显示名
   - 邮箱
   - 状态
   - 注册时间
   - 最近登录时间
2. 运行概览：
   - 活跃 session 数
   - 对话总数
   - Sandbox 总数
   - 最近活跃时间
3. 风险提示：
   - 是否存在 legacy 映射
   - 是否存在无对话却有 Sandbox 的异常
   - 是否存在历史空归属关联

#### 6.4.2 登录会话

展示最近会话列表：

1. IP
2. User-Agent
3. 创建时间
4. 最近 seen
5. 是否已撤销 / 是否已过期

并提供治理动作：

1. `强制下线全部 session`

#### 6.4.3 对话

展示最近对话简表：

1. 标题
2. 状态 / 阶段
3. 最近活跃
4. Executor
5. 跳转 `对话管理`

#### 6.4.4 Sandbox

展示最近 Sandbox 简表：

1. Sandbox ID
2. 状态
3. Executor
4. 最近活跃
5. 跳转 `Sandbox 管理`

#### 6.4.5 映射

展示 `app_user_legacy_id_mappings`：

1. legacy user id
2. source
3. first seen
4. last seen

该页只做可见性，不提供修改动作。

## 7. 治理动作建议

第一阶段只提供三类动作：

1. `启用用户`
2. `禁用用户`
3. `强制下线全部 session`

### 7.1 状态语义

第一阶段只使用两种状态：

1. `active`
2. `disabled`

不建议同时引入 `suspended / banned / archived / deleted` 等多个状态，避免扩散用户态语义和后端判断分支。

### 7.2 动作约束

1. `禁用用户`：
   - 更新 `app_users.status = 'disabled'`
   - 同步撤销该用户所有未撤销 session
2. `启用用户`：
   - 更新 `app_users.status = 'active'`
   - 不自动恢复旧 session
3. `强制下线全部 session`：
   - 只撤销当前用户所有活跃 session
   - 不修改用户状态

## 8. 数据与接口设计

### 8.1 API 侧新增管理态内部接口

建议在 `apps/api/src/routes/` 新增用户治理内部路由，仍使用内部 token 鉴权，不复用用户态接口。

#### 列表接口

`GET /api/internal/admin/app-users`

查询参数建议：

1. `cursor`
2. `limit`
3. `query`
4. `status`
5. `activity`
6. `hasSession`
7. `hasConversation`
8. `hasSandbox`
9. `ownershipHealth`

返回：

1. `summary`
2. `items`
3. `nextCursor`

其中单行 `item` 建议包含：

1. 用户基础信息
2. `activeSessionCount`
3. `conversationCount`
4. `sandboxCount`
5. `lastSeenAt`
6. `lastSeenIp`
7. `ownershipHealth`

#### 详情接口

`GET /api/internal/admin/app-users/:userId`

返回聚合：

1. `user`
2. `stats`
3. `recentSessions`
4. `recentConversations`
5. `recentSandboxes`
6. `legacyMappings`

#### 动作接口

1. `POST /api/internal/admin/app-users/:userId/status`
2. `POST /api/internal/admin/app-users/:userId/revoke-sessions`

### 8.2 管理后台 BFF

建议新增：

1. `apps/admin_management/server/services/user-management-service.ts`
2. `apps/admin_management/server/routes/user-management-routes.ts`

并在 `apps/admin_management/server/connectors/oneceo-api-connector.ts` 中补齐：

1. `listAppUsers()`
2. `getAppUserDetail()`
3. `updateAppUserStatus()`
4. `revokeAppUserSessions()`

管理后台前端仅调用自身 BFF：

1. `GET /api/user-management`
2. `GET /api/user-management/:userId`
3. `POST /api/user-management/:userId/status`
4. `POST /api/user-management/:userId/revoke-sessions`

## 9. 前端实施建议

### 9.1 组件边界

建议新增独立组件：

`apps/admin_management/web/src/components/UserManagementSection.tsx`

而不是继续把页面逻辑塞回 `App.tsx`。

`App.tsx` 只负责：

1. 新增 `SectionKey = 'user'`
2. 新增 `NAV_ITEMS` 项
3. 在 `renderContent()` 中挂载 `UserManagementSection`

### 9.2 视觉方向

遵循当前后台已形成的收敛风格：

1. 首屏不要大段说明文案。
2. 用紧凑摘要 + 稳定筛选栏 + 清晰索引表。
3. 抽屉内部重点突出状态、风险、最近活动和跨模块跳转。
4. 不新增花哨插画、Hero 或冗余卡片堆叠。

### 9.3 响应式

1. 桌面端：
   - 列表全宽
   - 抽屉从右侧滑入
2. 中屏：
   - 筛选栏允许折行
   - 表格保留横向滚动
3. 小屏：
   - 抽屉退化为全屏 modal
   - 列表保留最重要的三组信息：用户、状态、最近活跃

## 10. 实施顺序建议

### 第一阶段：只读治理视图

1. 导航入口
2. 列表查询
3. 详情抽屉
4. 跨模块跳转

### 第二阶段：最小治理动作

1. 启用 / 禁用
2. 强制下线全部 session
3. 审计日志记录

不建议跳过第一阶段直接做动作按钮，否则管理员在缺少上下文的情况下容易误操作。

## 11. 验证建议

1. `npm --prefix apps/api run type-check`
2. `npm --prefix apps/admin_management run type-check`
3. `npm --prefix apps/admin_management run build`
4. 用户状态切换后验证：
   - 已登录用户请求是否立即失效
   - 被禁用用户是否无法再次登录
5. 强制下线后验证：
   - 旧 session 是否全部失效
   - 用户状态是否保持不变
6. Playwright 验证：
   - 列表筛选
   - 抽屉展开
   - 状态切换确认流
   - 从用户详情跳转到对话 / Sandbox

## 12. 风险与约束

1. 用户管理只能治理 `app_users`，不能误触管理态账户。
2. 禁用用户要沿用既有 `active` 语义，不引入多套状态判断。
3. 不复用用户态 owner 接口，避免管理端误走用户态鉴权链路。
4. 不直接改动 Sandbox 生命周期，只提供可见性与跳转。
5. 不新增 Redis 依赖或缓存旁路。
