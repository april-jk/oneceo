# 20260415 Admin 连接器 Guide 动态化改造方案 [20260415-2034已采用]

更新时间：2026-04-15

## 1. 背景

当前管理后台 `Connector Guide 管理` 已经有基本的 policy / revision / publish / rollback 能力，但“哪些 connector 需要这类轻量化 guide / skills”仍然带有硬编码痕迹。

这导致两个直接问题：

1. 平台新增可用 MCP connector 后，Admin 页面不会稳定、完整地自动反映。
2. Guide 支持范围与平台真实可用 connector 目录容易脱节，出现“用户已能使用，但后台治理页没有同步”的现象。

这次改造不再按“补某一个 connector（例如 Slack）”处理，而是统一收口为：

1. Admin Connector Guide 候选集合动态化。
2. API Connector Guide 支持边界动态化。
3. Guide 是否需要管理，依据当前平台 MCP catalog 的真实状态决定，而不是依赖前端/后端各自维护的硬编码列表。

## 2. 当前问题定位

### 2.1 平台 connector catalog 已经是动态的

文件：

1. `apps/api/src/connectors/definitions/index.ts`
2. `apps/api/src/routes/connector-routes.ts`
3. `apps/api/src/services/user-connector-service.ts`

现状：

1. API 侧通过 connector definitions 构建 catalog。
2. `GET /api/connectors/catalog` 会返回当前平台 connector 列表与状态。
3. 每个 connector 已带有 `key / name / available / availabilityReason / visibleInMenu` 等字段。

这说明平台已经存在“真实连接器目录”这个真相源。

### 2.2 Admin 页面虽然接入了 catalog-summary，但候选集合仍未真正动态化

文件：`apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`

现状：

1. 页面进入时会调用 `GET /api/connector-guides/catalog-summary`。
2. “可见 Connector”卡片会显示 catalog 数据。
3. 但 `connectorOptions` 仍然保留 `BUILTIN_CANDIDATE_CONNECTOR_KEYS`，并对 catalog 做额外条件过滤。

结果：

1. 页面展示与可操作集合不是同一语义来源。
2. 新 connector 进入 catalog 后，未必能进入“新建 / 筛选 / 管理”集合。

### 2.3 API 侧 Connector Guide 支持范围仍然是固定集合

文件：`apps/api/src/services/connector-guide-service.ts`

现状：

1. `SUPPORTED_CONNECTOR_KEYS` 仍然是硬编码数组。
2. `assertSupportedConnectorKey()` 只接受固定几类 connector。
3. 即使 Admin 页面未来动态显示了新 connector，只要 API 侧不放开，创建 policy 仍会失败。

结果：

前端与后端都各自维护一份支持范围，平台新增 connector 后容易继续漂移。

## 3. 改造目标

### 3.1 总目标

把 Connector Guide 改成真正基于平台 MCP catalog 动态派生的治理能力。

### 3.2 具体目标

1. Admin 页面候选 connector 统一从 catalog-summary 派生。
2. API 创建/校验/发布 Connector Guide 时，不再依赖固定 `SUPPORTED_CONNECTOR_KEYS`。
3. 平台新增可见且可用的 MCP connector 后，Admin 页面无需额外硬编码即可进入治理范围。
4. Guide policy、revision、publish 现有数据结构保持不变，只调整“支持范围判定”和“候选派生逻辑”。

## 4. 核心原则

### 4.1 真相源唯一

Connector Guide 的治理范围以平台 connector catalog 为准，不再以前端常量或后端固定数组为准。

### 4.2 最短路径实现

不新增新表，不引入事件总线，不做自动轮询，不增加降级或兼容补丁。

### 4.3 展示集合与操作集合一致

页面上看到的“当前可治理 connector”和真正能点击新建/筛选/编辑的集合，必须来自同一份派生规则。

## 5. 动态化范围定义

### 5.1 作为 Guide 候选的 connector 来源

统一来源：`GET /api/connector-guides/catalog-summary`

候选规则建议收敛为：

1. `catalog-summary.items` 中 `visibleInMenu=true` 且 `available=true` 的 connector
2. 再并入当前数据库中已存在 policy 的 `connectorKey`

这样做的原因：

1. 用户的诉求是“依据整个平台哪些 MCP 可用，动态设置哪些 MCP 需要这些轻量化 skills”
2. `available=true` 更符合“当前已可实际使用”的治理范围
3. 同时保留已存在 policy 的 key，避免某 connector 暂时不可用时历史 policy 在后台页面消失

### 5.2 不进入本次范围的 connector

以下对象本次不自动纳入 Guide 治理：

1. `visibleInMenu=false` 的 connector
2. catalog 中不可用且数据库也不存在既有 policy 的 connector

这样可以避免把纯内部、实验中或未启用的 connector 一起带入管理页，扩大治理噪音。

## 6. 方案总览

### 6.1 Admin Web：候选集合完全改为 catalog-summary 驱动

文件：`apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`

改造点：

1. 删除 `BUILTIN_CANDIDATE_CONNECTOR_KEYS`
2. `connectorOptions` 改为基于以下数据直接派生：
   - `catalogSummary.items.filter(item => item.visibleInMenu && item.available).map(item => item.key)`
   - `policies.map(policy => policy.connectorKey)`
3. 做并集、排序后作为：
   - 新建按钮区候选
   - 筛选下拉候选
   - 详情选择上下文的合法集合
4. “可见 Connector”卡片与 `connectorOptions` 使用相同判定口径，避免展示/操作不一致

预期结果：

1. 新增可用 MCP connector 后，Admin 页面自动出现可管理项
2. 不再需要为 Slack / Figma / 下一批 connector 单独补前端常量

### 6.2 Admin Server：继续保留 catalog-summary 聚合接口，但语义更明确

文件：

1. `apps/admin_management/server/services/connector-guide-management-service.ts`
2. `apps/admin_management/server/routes/connector-guide-routes.ts`

改造点：

1. 保持 `GET /api/connector-guides/catalog-summary` 作为 Admin 唯一 catalog 入口
2. 返回结构保持不变：
   - `items`
   - `stats`
   - `updatedAt`
3. 前端不再直接写死 connector keys，只消费该聚合接口

预期结果：

1. Admin 侧只有一份 connector 来源
2. 后续 catalog 字段扩展时，不需要改前端多处入口

### 6.3 API：Connector Guide 支持边界改为动态校验

文件：`apps/api/src/services/connector-guide-service.ts`

改造点：

1. 删除固定 `SUPPORTED_CONNECTOR_KEYS`
2. 新增动态判定逻辑，例如：
   - 从 connector registry / definitions 获取 catalog
   - 判断目标 `connectorKey` 是否存在
   - 判断该 connector 当前是否 `visibleInMenu=true`
   - 对创建新 policy 时要求 `available=true`
   - 对读取既有 policy / revision / rollback 不依赖当前可用性，避免历史数据不可访问
3. `assertSupportedConnectorKey()` 改为动态检查，而不是固定数组检查

预期结果：

1. 后端支持边界与平台真实 connector 目录保持一致
2. 新增 connector 后无需再同步修改后端固定常量

### 6.4 API：Builtin guide 模板从“支持范围”中解耦

文件：`apps/api/src/services/connector-guide-service.ts`

改造点：

1. `BUILTIN_CONNECTOR_GUIDES` 保留，但它只表示“哪些 connector 提供默认种子文案”
2. 它不再承担“哪些 connector 允许创建 guide”的职责
3. 对于 catalog 中存在、但暂时没有 builtin 文案的 connector：
   - 允许创建 policy
   - revision 初始值可为空，或按通用空模板创建

预期结果：

1. “是否支持 guide”与“是否有默认文案模板”成为两个不同概念
2. 后续新增 connector 时，可以先纳入治理范围，再逐步补齐默认文案

## 7. 数据与接口影响

### 7.1 数据层

不新增表，继续复用：

1. `connector_guide_policy`
2. `connector_guide_revision`
3. `task_session_connector_guide`

### 7.2 接口层

保留现有接口：

1. `GET /api/connector-guides`
2. `GET /api/connector-guides/:policyId`
3. `POST /api/connector-guides`
4. revision 相关接口
5. `GET /api/connector-guides/catalog-summary`

本次主要改变的是这些接口背后的“支持范围判定逻辑”，不是接口面。

## 8. 验收标准

### 8.1 功能验收

1. 当某 MCP connector 在 catalog 中满足 `visibleInMenu=true` 且 `available=true` 时，Admin 页面自动出现该 connector 的管理入口
2. 新建按钮与筛选下拉同时出现该 connector
3. 创建该 connector 的 guide policy 成功
4. 发布后，会话 guide 重算链路可以正常纳入该 connector
5. 新增一个新的可用 MCP connector 后，Admin 无需新增硬编码即可接入 Guide 管理

### 8.2 回归验收

1. 已有 GitHub / Supabase / Vercel / Notion 等既有 guide 管理流程不退化
2. 历史 policy 在 connector 暂时不可用时仍可查看与维护
3. 页面展示集合与操作集合一致，不再出现“卡片里有、按钮区没有”的状态

## 9. 风险与边界

### 9.1 风险

如果某 connector 目录项短时从 `available=true` 变成 `false`，新建入口会消失，但历史 policy 仍需可见。

对应处理：

1. 新建候选只来自当前可用 catalog
2. 已存在 policy 的 connector 仍并入候选集合

### 9.2 边界

本次只做 Connector Guide 动态化，不做：

1. 自动轮询刷新
2. SSE / WebSocket 实时推送
3. Guide 文本生成自动化
4. Skills 模块重构

## 10. 最小实施清单

1. 修改 `apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`
2. 修改 `apps/api/src/services/connector-guide-service.ts`
3. 若需要，补充 Admin / API 的最小单元测试
4. 运行最小验证：
   - `pnpm --filter api type-check`
   - `npm --prefix apps/admin_management run type-check`

## 11. 结论

这次不再按 Slack 单点补洞，而是把 Connector Guide 的治理逻辑正式收口为：

1. 平台 MCP catalog 是真相源
2. Admin 页面按 catalog 动态展示
3. API 按 catalog 动态校验
4. builtin guide 文案只负责模板，不再负责支持范围

这样后续平台新增 MCP 时，Admin Connector Guide 才会真正随平台能力动态生长，而不是继续依赖硬编码追着补。
