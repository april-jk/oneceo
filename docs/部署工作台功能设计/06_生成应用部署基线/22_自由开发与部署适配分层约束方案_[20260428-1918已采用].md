# 自由开发与部署适配分层约束方案 [20260428-1918已采用]

## 1. 核心判断

OneCEO 不应在开发之初强制套固定模板。这样会限制 Altus 的实现自由，也会让简单任务被模板复杂度拖累。

OneCEO 也不应等到部署最后一刻才第一次理解项目结构并盲目注入部署材料。这样会让部署稳定性过度依赖 LLM 临场判断，出现 start command、健康检查、Umami 注入、Railway 配置不一致的问题。

推荐模型是：

```text
开发自由
  + 项目画像持续收集
  + 部署契约前置意识
  + 部署前模板适配
  + 平台合规校验兜底
```

一句话：**不约束开发表达，但约束交付契约；不让模板当起点，而让模板当部署适配层。**

## 2. 分层职责

### 2.1 开发阶段：自由生成

Altus 可以自由选择实现方式：

- 纯 HTML / CSS / JS
- Vite / React / Vue / Svelte
- Node / Express / Koa / Fastify
- Python / FastAPI / Flask / Django
- PHP 站点
- Java / Spring Boot
- 其它后续支持的 Web 形态

开发阶段不强制要求项目一开始就存在 `oneceo.manifest.json`、`railway.json` 或 OneCEO 官方模板目录。

但开发阶段必须满足“可交付意识”：

- 如果目标是网站，必须逐步形成可访问首页。
- 如果目标是后端服务，必须逐步形成 HTTP 启动入口。
- 如果进入调试流程，必须能被本地预览或调试浏览器访问。
- 如果用户没有请求部署，不主动把部署材料当主要开发目标。

### 2.2 项目画像阶段：持续识别但不阻断

平台在开发过程中持续维护 `project profile`，但 profile 不直接阻断开发。

建议 profile 字段：

```json
{
  "artifactType": "web_app | api_service | static_site | script | unknown",
  "runtimeFamily": "static | frontend_dist | node | python | php | java | unknown",
  "entrypoints": ["index.html", "server.js"],
  "buildCommand": "npm run build",
  "startCommand": "node server.js",
  "healthcheckPath": "/api/system/health",
  "hasManifest": true,
  "hasRailwayConfig": true,
  "analyticsStatus": "workspace | platform_injectable | missing | unsafe",
  "deployability": "ready | repairable | blocked | not_deployable",
  "evidence": {
    "files": [],
    "commands": [],
    "lastPreviewUrl": ""
  }
}
```

profile 的来源可以是：

- 文件变更事件
- 调试启动命令
- Playwright 预览结果
- manifest / package / requirements / composer / pom 等配置文件
- deployment skill 对项目的结构化判断

### 2.3 部署触发阶段：由 LLM 裁决意图，平台验证边界

用户表达“帮我部署”“重新部署”“发布当前项目”时，LLM 可以裁决是否调用部署工具。

但平台必须验证：

- 当前用户是否有部署权限。
- 当前会话是否存在可发布工作区。
- 当前任务是否不是明显的非部署型脚本。
- deployment skill 是否已挂载。
- 工具调用参数是否匹配当前 session 和 workspace。

LLM 的职责是“选择工具与修复策略”，不是绕过平台边界。

### 2.4 部署适配阶段：模板材料后置补齐

只有进入部署流程后，平台才执行内部模板适配：

- 已合规项目：不重写业务代码，只补缺失配置。
- 缺少部署材料的项目：按 runtime family 补最小启动契约。
- 不安全注入的项目：拒绝盲注，交给 deployment skill 修复结构。
- 非部署型项目：不部署，返回明确原因。

模板适配层只负责交付契约，不负责重新设计应用。

### 2.5 合规检查阶段：硬验证，不靠 LLM 自证

部署前必须由平台代码检查：

- build command 是否存在或可为空。
- start command 是否存在。
- port 是否使用 `$PORT` / `process.env.PORT` / 对应平台端口。
- healthcheck path 是否能与运行时匹配。
- Umami 是否已经存在、可安全注入或可运行时注入。
- 声明 database 时，依赖是否存在。
- `railway.json` 是否与 manifest 一致。

LLM 可以解释失败和提出修复，但不能用自然语言覆盖合规检查结果。

## 3. 降低 LLM 随机性的约束方案

### 3.1 结构化 project profile

不要让 LLM 每次从完整聊天上下文里重新猜项目状态。平台应维护结构化 profile，并在每次部署、调试、修复前把 profile 注入上下文。

收益：

- 降低上下文漂移。
- 提高缓存稳定性。
- 减少重复读文件和重复猜测。
- 让 LLM 的判断从“自由发挥”变成“基于证据裁决”。

### 3.2 工具入参使用枚举和 schema

部署工具不要接受自由文本作为主要参数，应使用结构化字段：

```json
{
  "action": "deploy | redeploy | status | rollback",
  "sessionId": "...",
  "workspaceRoot": "...",
  "sourceProfileId": "...",
  "expectedRuntimeFamily": "static | frontend_dist | node | python | php | java",
  "repairPolicy": "none | safe_template_adapt | skill_repair_then_retry"
}
```

LLM 只能选择 schema 中允许的动作，平台负责校验动作是否与上下文一致。

### 3.3 Reducer 校验状态迁移

部署流程状态不能由 LLM 文案决定，必须由 reducer 根据工具结果迁移：

```text
idle
  -> profiling
  -> adapting
  -> compliance_checking
  -> publishing
  -> verifying_public_access
  -> succeeded
  -> failed_repairable / failed_terminal
```

约束点：

- 没有 public URL 200 验证，不能进入 `succeeded`。
- Railway 返回 FAILED，不能被包装成“部署成功但访问异常”。
- 合规检查失败，不能进入 publish。
- 修复后必须重新跑合规检查。

### 3.4 模板适配只允许最小变更

平台内部模板只能补交付契约：

- `package.json`
- `server.js`
- `oneceo.manifest.json`
- `railway.json`
- analytics bootstrap

禁止在模板适配层重写业务逻辑、重构 UI、替换框架。

如果需要改业务代码，应生成 repair task 交给 deployment skill 明确执行，并记录原因。

### 3.5 Umami 注入有安全边界

Umami 继承必须遵守：

- websiteId、host、endpoint 来自部署时 analytics binding，不写死在模板。
- HTML / EJS / Jinja 可注入。
- PHP 只有存在 `</body>` 或 `</html>` 时注入。
- 无 HTML 文档结构时不盲注。
- 前端 dist 可在运行时 server 注入。

### 3.6 真实部署回归按风险分级

部署有资源成本，不能每次代码改动都跑完整真实矩阵。

建议：

- 低风险：跑单元测试、模板归一化测试、合规检查测试。
- 中风险：增加一次本地 preview / Playwright 检查。
- 高风险：选一个代表形态做真实部署 smoke。
- 重大发布：跑多形态真实部署矩阵。

## 4. 推荐实施顺序

### 阶段一：固化 profile 数据模型

新增或扩展 task session runtime metadata，保存项目画像。

验收：

- 静态 HTML、Vite、Node、Python、PHP 至少能产生 runtime family。
- profile 可在 context-debug 中查看。
- 部署工具能读取 profile。

### 阶段二：部署工具 schema 化

将部署动作参数收敛成枚举和结构化字段。

验收：

- “能用 Vercel 部署吗”这类能力咨询不触发部署。
- “帮我部署当前项目”触发 deploy。
- deploy/status/redeploy/rollback 都走同一 schema。

### 阶段三：部署 reducer 状态机

把部署状态迁移从自然语言结果中抽离出来。

验收：

- FAILED 不会被 final 文案说成成功。
- 404 public URL 不会进入 succeeded。
- 修复重试必须重新执行合规检查。

### 阶段四：内部模板适配扩展

继续扩展 Java、PHP Composer、Python ASGI/WSGI、Node package 等模板适配。

验收：

- 每种 runtime 有最小 manifest / railway config。
- 不安全注入会被识别为 repairable，而不是静默发布。

### 阶段五：成本感知部署回归

建立分级测试策略。

验收：

- 普通 PR 不跑真实部署矩阵。
- 部署核心链路变更至少跑模板测试和一个代表形态 smoke。
- 重大发布才跑多形态真实部署矩阵。

## 6. 未完成阶段补齐方案

### 6.1 阶段一补齐：project profile 数据模型

目标：把项目状态从“LLM 临场猜测”变成“平台持续维护的结构化事实”。

#### 数据结构

新增 `TaskSessionProjectProfile`：

```ts
type TaskSessionProjectProfile = {
  version: '1.0';
  sessionId: string;
  runtimeGeneration?: number;
  updatedAt: string;
  artifactType: 'web_app' | 'api_service' | 'static_site' | 'script' | 'unknown';
  runtimeFamily: 'static' | 'frontend_dist' | 'node' | 'python' | 'php' | 'java' | 'unknown';
  deployability: 'ready' | 'repairable' | 'blocked' | 'not_deployable' | 'unknown';
  entrypoints: Array<{ path: string; kind: 'html' | 'server' | 'template' | 'config' }>;
  commands: {
    build?: string;
    start?: string;
    preview?: string;
  };
  healthcheckPath?: string;
  analyticsStatus: 'workspace' | 'platform_injectable' | 'runtime_injectable' | 'unsafe' | 'missing' | 'unknown';
  configFiles: {
    manifest?: boolean;
    railwayJson?: boolean;
    packageJson?: boolean;
    requirementsTxt?: boolean;
    pyprojectToml?: boolean;
    composerJson?: boolean;
    pomXml?: boolean;
    gradle?: boolean;
  };
  evidence: Array<{
    source: 'file_scan' | 'manifest' | 'package_json' | 'preview' | 'compliance' | 'skill';
    message: string;
    path?: string;
  }>;
};
```

#### 生成来源

- `normalizeDeploymentSourceDirectoryForPublish` 前先做一次只读扫描，生成初始 profile。
- `ensureTemplateCompliance` 输出结果回写 profile。
- 调试成功后的 preview URL、HTTP 状态、页面标题回写 profile。
- deployment skill 修复后重新刷新 profile。

#### 存储位置

第一阶段先写入 task session metadata / runtime metadata，避免新建表扩大迁移成本。

后续如果 profile 需要历史版本和审计，再拆成独立表：

```text
task_session_project_profiles
  id
  session_id
  runtime_generation
  profile_json
  created_at
  updated_at
```

#### 接入点

- context-debug 增加 `projectProfile`。
- Altus managed prompt 的动态上下文增加压缩版 profile。
- 部署工具执行前读取 profile，并与实时扫描结果比对。

#### 验收

- 静态 HTML、Vite、Node、Python、PHP 至少能产出正确 `runtimeFamily`。
- 修改文件后 profile 会刷新。
- context-debug 能看到 profile。
- 部署工具结果 debug 中能看到 profile 摘要。

### 6.2 阶段二补齐：部署工具 schema 化

目标：让 LLM 只能在清晰动作空间里选择，而不是通过自由文本影响部署链路。

#### 统一 schema

内部统一成一个部署 action input：

```ts
type ManagedDeploymentToolInput = {
  action: 'deploy' | 'redeploy' | 'status' | 'rollback';
  sessionId: string;
  workspaceRoot: string;
  sourceProfileVersion?: string;
  expectedRuntimeFamily?: TaskSessionProjectProfile['runtimeFamily'];
  repairPolicy: 'none' | 'safe_template_adapt' | 'skill_repair_then_retry';
  reason?: string;
};
```

对外仍可保留多个 tool name，降低模型选择难度；进入 service 后统一映射成这个 schema。

#### 平台校验

执行前检查：

- tool action 与当前用户意图匹配。
- `sessionId`、`workspaceRoot` 来自平台上下文，不接受 LLM 自造路径。
- `expectedRuntimeFamily` 与 profile 不一致时不直接部署，先重新 profile。
- `repairPolicy=skill_repair_then_retry` 只允许在合规检查失败后进入。

#### 验收

- 能力咨询不触发部署工具。
- 明确部署请求触发 deploy。
- LLM 传错 action / workspaceRoot 时被平台拒绝。
- redeploy / rollback / status 都进入同一内部 schema。

### 6.3 阶段三补齐：部署 reducer 状态机

目标：部署状态不能由工具 summary 或 final 文案决定。

#### 状态定义

```ts
type DeploymentFlowState =
  | 'idle'
  | 'profiling'
  | 'adapting'
  | 'compliance_checking'
  | 'publishing'
  | 'polling_provider'
  | 'verifying_public_access'
  | 'succeeded'
  | 'failed_repairable'
  | 'failed_terminal';
```

#### 事件定义

```ts
type DeploymentFlowEvent =
  | { type: 'PROFILE_READY'; profile: TaskSessionProjectProfile }
  | { type: 'ADAPTATION_DONE' }
  | { type: 'COMPLIANCE_READY'; ok: boolean; errors: string[] }
  | { type: 'PUBLISH_STARTED'; deploymentId?: string }
  | { type: 'PROVIDER_STATUS'; status: string; url?: string }
  | { type: 'PUBLIC_ACCESS_VERIFIED'; statusCode: number; url: string }
  | { type: 'REPAIR_REQUIRED'; category: string; checks: string[] }
  | { type: 'TERMINAL_FAILURE'; reason: string };
```

#### 硬规则

- `succeeded` 只能由 `PUBLIC_ACCESS_VERIFIED(statusCode=200)` 进入。
- `FAILED` / `CRASHED` / `404 Application not found` 必须进入 `failed_repairable` 或 `failed_terminal`。
- `COMPLIANCE_READY(ok=false)` 不能进入 `publishing`。
- 修复后必须回到 `profiling -> adapting -> compliance_checking`。

#### 接入点

- `AltusManagedDeploymentToolService` 不再直接拼最终成功语义，而是发 reducer event。
- `altus-run-coordinator` 读取 reducer state 判断是否允许 `complete_task`。
- 部署卡片显示 reducer state，而不是只显示 Railway 最新状态。

#### 验收

- Railway FAILED 时 final 不能说部署完成。
- public URL 404 时不能进入 succeeded。
- 修复后未重新合规检查，不能重新发布。
- reducer 单测覆盖所有状态迁移。

### 6.4 阶段四补齐：内部模板适配扩展

目标：继续增强运行时覆盖，但仍保持“模板适配只补契约，不重写业务”。

#### Java / Spring Boot

识别：

- `pom.xml`
- `build.gradle`
- `build.gradle.kts`

适配：

- Maven：`./mvnw package -DskipTests` 或 `mvn package -DskipTests`
- Gradle：`./gradlew build -x test` 或 `gradle build -x test`
- start command 从 jar 推导：`java -jar target/*.jar` 或 `java -jar build/libs/*.jar`
- healthcheck 默认 `/actuator/health`，没有 actuator 证据时标记 repairable，不盲目发布。

#### PHP Composer

识别：

- `composer.json`
- `public/index.php`
- Laravel / Symfony 信号

适配：

- 普通 PHP：`php -S 0.0.0.0:$PORT -t public`
- Laravel：优先要求 `.env` / `APP_KEY` / `php artisan serve --host=0.0.0.0 --port=$PORT`，缺关键配置标记 repairable。
- 不把只有 `composer.json` 的库项目当作网站。

#### Python ASGI / WSGI

识别：

- `FastAPI(` / `Django` / `Flask(`
- `requirements.txt` / `pyproject.toml`

适配：

- FastAPI：`uvicorn module:app --host 0.0.0.0 --port $PORT`
- Flask：`gunicorn module:app --bind 0.0.0.0:$PORT`
- Django：需要 `manage.py` 和 settings，缺少生产入口时 repairable。

#### Node package 细分

识别：

- Express/Koa/Fastify 服务
- Next.js
- Vite frontend

适配：

- Node HTTP 服务：保留业务 start，校验 `$PORT`。
- Next.js：`next build` + `next start -p $PORT`。
- Vite frontend：继续使用 dist server。

#### 验收

- 每个 runtime 至少有一个 template normalization 单测。
- 不确定形态返回 repairable，不盲目发布。
- Umami 注入只在安全入口执行。

### 6.5 阶段五补齐：成本感知部署回归

目标：用低成本测试覆盖大部分风险，把真实部署留给必要场景。

#### 风险分级

低风险：

- 只改文档、提示词、展示文案。
- 只改模板单个 runtime 的非核心字段。

要求：

- `git diff --check`
- 相关单测

中风险：

- 修改模板适配、合规检查、Umami 注入。

要求：

- 模板归一化单测
- compliance 单测
- TypeScript 编译
- 本地 preview 或 Playwright 检查一个代表形态

高风险：

- 修改部署工具、Railway 发布、状态同步、reducer。

要求：

- 单测 + 类型检查
- 一个真实部署 smoke，优先选择当前改动影响最大的 runtime
- 不跑全矩阵，除非本次改动影响多 runtime 判断边界

重大发布：

- deployment 主链大改
- Railway 资源模型调整
- analytics binding 逻辑调整

要求：

- 多形态真实部署矩阵
- 至少覆盖 static / frontend_dist / node / python / php
- 记录部署 ID、public URL、HTTP 状态、Umami binding 状态

#### 执行产物

- 新增 `docs/智能体能力测试题库/部署链路成本分级回归SOP`。
- 测试脚本输出 `riskLevel`、`selectedCases`、`skippedRealDeployReason`。
- PR / 提交说明必须写明是否跑真实部署，以及未跑的成本理由。

## 7. 结论

OneCEO 应该避免两个极端：

- 开发之初强制模板，牺牲自由度。
- 部署前临场猜测，牺牲稳定性。

正确路径是：

```text
自由开发
  -> 平台持续形成项目画像
  -> 用户明确部署时进入模板适配
  -> 平台合规检查硬验证
  -> LLM 只负责选择工具和修复策略
```

这样既保留 Altus 的生成自由，也把部署成功率、Umami 继承、状态迁移和成本控制放回平台可验证的边界内。
