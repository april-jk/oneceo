# 26. 竞品式 PPT 子任务编排工作流方案 [20260501-1718已采用]

更新时间：2026-05-01

## 1. 背景

用户提供竞品截图，要求先复刻其 PPT 任务中“生成前半段工作流”，暂不包含 PPT 专用渲染器。当前 oneceo 不支持真正的多子 agent 并发或多 agent 协作，因此本方案不采用“主 agent 调多个子 agent”的实现，而是在 Altus managed run 内引入可观测、可恢复的子任务编排。

本轮开始前，旧有 PPT 相关 skill 需要先从项目代码移除并归档：

1. `office-ppt`
2. `magazine-web-ppt`
3. 旧 `ppt_task_router -> ppt_research_curator -> ppt_storyboard_designer -> ppt_visual_system_designer -> ppt_builder -> ppt_qa_reviewer` prompt 规则
4. 旧 `packages/shared/src/ppt-generation.ts` 类型资产

归档位置：

`docs/agent研发文档/技能平台化热加载设计/archive/20260501_ppt_skill_backup/`

## 2. 竞品工作流拆解

截图里可复刻的关键链路是：

1. 需求分析：识别主题、篇幅、核心概念歧义和信息缺口。
2. Search Agent 调用规划：明确搜索指令，不直接进入成稿。
3. 素材收集：收集文本资料、图片候选、Logo、概念图。
4. PPT 规划视觉方案：生成整体风格、页面规格、字体、字号、色彩、边距。
5. 结构规划：输出封面、目录、章节、过渡页、结束页。
6. 生成 PPT 指令：将前述计划转成可被后续渲染器消费的结构化指令。
7. 完成态说明：总结页数、风格、覆盖范围和下一步入口。

本轮明确不复刻：

1. PPT 专用渲染器。
2. 多子 agent 并行执行。
3. 直接生成 `.pptx` 文件。
4. 新增独立 MCP server。

## 3. 目标

### 3.1 产品目标

让用户发起 PPT 任务时，Altus 不再直接“写 PPT 内容”，而是先形成一套可检查的生成前工作流。用户和管理员应能看到每个阶段做了什么、为什么这么做、下一阶段拿什么输入。

### 3.2 工程目标

在现有 oneceo 架构内，用子任务编排代替多子 agent：

1. 一个 run 内维护多个 `PptWorkflowSubtask`。
2. 每个子任务有固定输入、输出、状态和证据。
3. 子任务顺序执行，必要时允许某一步失败后重试。
4. 所有阶段产物写入会话上下文和过程 artifact，供后续渲染器接入。

### 3.3 交付目标

第一阶段只交付生成前的结构化产物：

1. `PptTaskAnalysis`
2. `PptResearchPlan`
3. `PptMaterialBrief`
4. `PptVisualPlan`
5. `PptDeckOutline`
6. `PptRenderInstructionDraft`

其中 `PptRenderInstructionDraft` 只是后续渲染器的输入草稿，不负责真实渲染。

## 4. 非目标

1. 不恢复旧 `office-ppt` 或 `magazine-web-ppt` skill。
2. 不继续依赖旧 PPT skill seed。
3. 不做兼容旧 PPT prompt 的补丁方案。
4. 不新增真正的多 agent runtime。
5. 不新增数据库表，除非实现阶段发现现有 run/state 结构无法承载。
6. 不绕过现有 OSAC、Sandbox、连接器和 managed run 链路。

## 5. 子任务编排设计

### 5.1 编排入口

PPT 意图识别后通过新的平台 skill `ppt-workflow` 进入 `ppt_pre_render_workflow`。该 skill 不恢复旧 `office-ppt` / `magazine-web-ppt` 的渲染能力，只作为 managed run 内子任务编排的入口和操作规程。

建议阶段：

1. `ppt_intent_analyzer`
2. `ppt_research_planner`
3. `ppt_material_collector`
4. `ppt_visual_planner`
5. `ppt_outline_planner`
6. `ppt_render_instruction_planner`
7. `ppt_preflight_reviewer`

### 5.2 状态模型

每个子任务记录：

1. `key`
2. `title`
3. `status`: `pending | running | completed | failed | skipped`
4. `inputRefs`
5. `outputRef`
6. `evidence`
7. `startedAt`
8. `completedAt`
9. `error`

第一阶段优先复用现有 run event / message metadata 表达，不先新建表。

### 5.3 阶段契约

#### ppt_intent_analyzer

输出 `PptTaskAnalysis`：

1. 用户原始需求
2. 主题
3. 篇幅或页数推断
4. 目标受众
5. 核心概念歧义
6. 信息缺口
7. 是否需要搜索

#### ppt_research_planner

输出 `PptResearchPlan`：

1. 搜索问题列表
2. 搜索覆盖面
3. 图片素材需求
4. 不搜索的边界
5. 预期证据类型

#### ppt_material_collector

输出 `PptMaterialBrief`：

1. 文本事实摘要
2. 候选图片和 Logo 类型
3. 概念图需求
4. 来源 URL
5. 素材缺口

该阶段可调用现有 `web_search` / `web_extract`，但必须有上一步的 research plan，不允许自由扩散。

#### ppt_visual_planner

输出 `PptVisualPlan`：

1. 风格关键词
2. 页面比例
3. 字体系统
4. 字号层级
5. 色彩方案
6. 边距与栅格
7. 封面、过渡页、结束页视觉方向

#### ppt_outline_planner

输出 `PptDeckOutline`：

1. 总页数
2. 每页类型
3. 每页标题
4. 每页核心信息
5. 每页素材需求
6. 章节关系

#### ppt_render_instruction_planner

输出 `PptRenderInstructionDraft`：

1. deck metadata
2. theme tokens
3. slides[]
4. 每页 layout intent
5. 每页 content blocks
6. 每页 image slots
7. sources

#### ppt_preflight_reviewer

输出 `PptPreflightReview`：

1. 是否覆盖用户需求
2. 是否存在关键缺口
3. 是否存在重复页面结构
4. 是否可交给渲染器
5. 需要用户确认的问题

## 6. 与旧 PPT Skill 的边界

旧方案把 PPT 能力包装成直接交付型平台 skill；新方案把 PPT 生成前流程包装成 `ppt-workflow` 平台 skill，并把实际执行收敛为 managed run 内的子任务编排。

差异：

1. 旧方案：依靠直接交付型 skill brief 指挥模型生成 `.pptx` 或 HTML deck。
2. 新方案：依靠 `ppt-workflow` skill brief 固定子任务顺序，并产出结构化 artifact。
3. 旧方案：阶段目标包含最终渲染。
4. 新方案：阶段目标停在 `PptRenderInstructionDraft`，等待后续渲染器消费。
5. 旧方案：容易和子 skill、多 agent 语义混淆。
6. 新方案：明确不需要多子 agent，用一个 agent 顺序执行多个子任务。

## 7. 实现落点建议

进入实现后，优先检查并复用：

1. `apps/api/src/services/altus-managed-prompt-service.ts`
2. `apps/api/src/services/altus-run-coordinator.ts`
3. `apps/api/src/services/altus-managed-input-service.ts`
4. `apps/api/src/services/altus-managed-tool-runtime.ts`
5. `apps/api/src/agents/task-creation/`
6. `apps/web/client/src/components/` 中会话消息和过程展示相关组件

第一阶段不改 PPT 渲染器，渲染器只作为后续接口的消费者。

## 8. 验收标准

1. 新建 PPT 请求不会加载旧 `office-ppt` / `magazine-web-ppt` skill。
2. prompt 中不再出现旧 `ppt_task_router` 等 skill 阶段规则。
3. PPT 请求会形成明确的子任务阶段。
4. 每个阶段都有可检查输出。
5. 搜索必须由 `PptResearchPlan` 触发。
6. 最终输出为 `PptRenderInstructionDraft`，不伪装成已生成 PPT。
7. 若信息不足，先问关键澄清问题，不直接生成完整 deck。
