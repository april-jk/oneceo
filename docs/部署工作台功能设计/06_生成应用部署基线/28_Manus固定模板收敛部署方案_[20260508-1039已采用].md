# Manus固定模板收敛部署方案 [20260508-1039已采用]

## 1. 背景

2026-05-07 对 `referance/manus部署模板推演` 下三个样本的拆解，进一步确认了一件事：

1. Manus 面向用户看起来支持多种任务表达，甚至允许用户口头指定 Java 等语言。
2. 但它的真实交付外壳并没有随语言要求自由切换。
3. 它更像是把绝大多数“可部署网页应用”任务收敛进一套固定可部署模板，再让模型只在模板允许范围内产出内容。

当前样本：

1. [2048的网页游戏并部署](/Users/watson/codingProj/oneceo/referance/manus部署模板推演/2048的网页游戏并部署)
2. [game-2048](/Users/watson/codingProj/oneceo/referance/manus部署模板推演/game-2048)
3. [java写个2048网站](/Users/watson/codingProj/oneceo/referance/manus部署模板推演/java写个2048网站)

共同特征非常强：

1. 顶层目录统一为 `client / server / shared / package.json / vite.config.ts / pnpm-lock.yaml`
2. build/start 契约统一为：
   - `vite build`
   - `esbuild server/... --outdir=dist`
   - `node dist/index.js`
3. `client/index.html` 统一预埋 analytics runtime 占位符
4. `vite.config.ts` 统一包含 Manus runtime 与调试采集插件
5. server 层统一是固定 Node Web Shell，不是随任务自由切换语言 runtime

这说明 Manus 的真实策略不是“技术栈自由”，而是“需求表达自由 + 模板壳固定”。

## 2. 结论先行

如果 OneCEO 当前目标是：

1. 把部署成功率抬到 Manus 同级
2. 把最终对用户的成功高质量交付作为唯一核心点

那么当前阶段不应继续追求“多语言广泛兼容”，而应直接采用 Manus 同类策略：

1. 暂时放弃 Java、PHP、Python 等非主模板路线的主链承诺
2. 把网页类项目统一收敛到一套固定模板壳
3. 让 Altus 在固定模板内生成内容、页面、数据结构和少量业务代码
4. 让部署链路只服务这套固定模板，而不是服务无限制自由项目

## 3. 当前问题与 Manus 的差异

OneCEO 当前还在试图同时做两件彼此冲突的事：

1. 允许较高自由度的项目结构
2. 又要求 Manus 级稳定部署

这会导致：

1. 部署前需要识别大量 runtime family
2. Fast Lane 要维护越来越多的例外
3. deploy tool 容易进入 repair_required / status 误判 / 反复重试

而 Manus 的样本说明，它几乎没有把运行时自由暴露给最终交付主链。

真正稳定的不是“模型更强”，而是：

1. 模板固定
2. runtime 固定
3. 目录结构固定
4. build/start 固定
5. analytics 固定
6. debug/preview 固定
7. 发布产物形态固定

## 4. 本轮战略收敛

### 4.1 明确放弃项

当前阶段明确放弃主链支持：

1. Java 部署主链
2. PHP 部署主链
3. Python 部署主链
4. 任意 Node 自由结构部署

不是永久放弃，而是：

1. 暂不纳入核心稳定性交付目标
2. 不再作为当前 Fast Lane / 主部署链的优先优化对象

### 4.2 明确保留项

当前阶段只保留一套主模板路线：

1. 前端：Vite + React
2. 服务端：固定 Node Web Shell
3. 运行壳：`client + server + shared`
4. 构建契约：`vite build + esbuild server + node dist/index.js`
5. analytics 注入：模板预埋
6. healthcheck：模板预埋

### 4.3 交付目标

我们不再把“支持更多语言”作为首要目标，而是把：

1. 用户最终拿到一个稳定上线的网站
2. 页面质量高
3. 部署成功率高
4. 交付时间可预测

作为唯一核心点。

## 5. 对 Manus 的高比例模拟目标

我们不追求 1:1 抄 UI，而追求部署与模板策略层面的高比例仿真。

需要模拟的核心能力：

1. 固定模板壳
2. 固定目录结构
3. 固定 build/start/runtime 契约
4. 固定 analytics/preview/debug 注入
5. 固定最小发布面
6. 固定 deploy tool 判定逻辑

不需要模拟的内容：

1. “名义上支持很多语言”
2. 对外宣称的技术栈自由
3. 部署期 LLM 自修复万能兼容

## 6. OneCEO 需要收敛成的固定模板

### 6.0 锚点

为了让提示词、E2E、日志回放能定位“哪层约束在起作用”，本方案补充三类锚点：

1. `ONECEO_FIXED_SHELL_ANCHOR`
2. `ONECEO_WEBAPP_TODO_BLUEPRINT_ANCHOR`
3. `ONECEO_WEBAPP_MACRO_REVIEW_ANCHOR`

分别对应：

1. 固定模板壳不可漂移
2. 编码前必须先形成蓝图型 todo
3. 收尾时只做宏观 todo 对照自检

### 6.1 顶层结构

统一收敛为：

1. `client/`
2. `server/`
3. `shared/`
4. `package.json`
5. `vite.config.ts`
6. `tsconfig*.json`
7. `oneceo.manifest.json`

### 6.2 build/start 契约

统一收敛为：

1. `build`: `vite build && esbuild server/... --outdir=dist`
2. `start`: `node dist/index.js`
3. public 产物：`dist/public`

### 6.3 server 壳

统一收敛为固定 Node Web Shell：

1. 不依赖 Express / Koa / Fastify 等额外框架
2. prod 模式托管 `dist/public`
3. 固定 fallback 到 `index.html`
4. 固定 healthcheck 路由
5. 启动时只依赖 Node 标准库，降低部署期安装与启动不确定性

### 6.4 固定路径所有权

固定模板不仅要固定运行壳，还要固定代码写入区域：

1. `client/` 负责页面结构、样式、组件与前端交互
2. `server/` 负责 HTTP 入口、少量接口与健康检查
3. `shared/` 负责共享常量与简单类型；前端若引用共享文件，统一通过 `@shared/...` 导入
4. `package.json`、`oneceo.manifest.json`、`vite.config.ts` 属于契约文件，普通网站生成任务默认不允许漂移

这一步约束的是结构，不是内容表达。

### 6.5 analytics 壳

统一收敛为：

1. `client/index.html` 预埋 analytics 占位符
2. 由平台在模板内注入
3. 不再依赖 deploy 期临时猜入口

## 7. Altus 生成策略要改什么

### 7.1 平台先注入模板 scaffold

Altus 生成网页类项目时：

1. 平台先把官方固定模板 scaffold 直接 materialize 到空工作区
2. 该 scaffold 至少包含：
   - `client/index.html`
   - `client/src/*`
   - `server/index.ts`
   - `shared/`
   - `package.json`
   - `vite.config.ts`
   - `oneceo.manifest.json`
3. 再让 Altus 在这个模板内工作，而不是从零开始拼技术栈

本条不以“是否已经授权部署”为前提。只要任务属于新建网站/网页应用源码，即使用户明确说“不要部署，只完成源码”，平台也应该先铺官方固定模板壳；`deploymentAllowed=false` 只限制部署工具调用，不限制源码交付使用固定壳。

### 7.2 Altus 不再从零拼栈

Altus 收到的网页类项目任务应默认变成：

1. 基于当前已有的官方模板实现网站
2. 保持 build / start / healthcheck / analytics 契约不变
3. 只改这些区域：
   - 页面内容
   - 样式
   - 交互
   - 少量 server 路由
   - 数据模型

### 7.3 Altus 必须先写蓝图型 todo

`ONECEO_WEBAPP_TODO_BLUEPRINT_ANCHOR`

对“新建可部署网站”任务，不允许直接跳进编码，必须先形成蓝图型 todo。

todo 规则：

1. todo 条数不做硬上限，但必须与任务规模匹配
2. todo 必须覆盖完整主路径，不能遗漏主要页面、主要后端能力、验证与收尾
3. 每个实现项必须写清目标路径，例如：
   - `client/src/App.jsx`
   - `client/src/styles.css`
   - `server/index.ts`
   - `shared/...`（前端引用时使用 `@shared/...`）
4. 如果任务同时包含前端与后端，todo 必须显式覆盖两侧
5. 弱约束网站任务默认按最小完整官网骨架展开：
   - hero
   - 核心价值/服务
   - 案例/作品/证明
   - CTA/联系区
6. 首页主内容、用户验收标识、hero、核心模块与主要浏览器交互必须绑定到 `client/src/App.jsx` 或 `client/src/App.tsx`
7. `client/src/main.*` 只负责 React 挂载，不能作为主要业务内容承载文件

todo 的职责不是写很多计划，而是在编码前明确“做什么、写到哪里、做到什么程度”。

### 7.4 语言要求的处理方式

用户说“用 Java / PHP / Python 写”时，当前阶段不按字面切 runtime。

而是：

1. 解释为“按该语言风格/业务语义理解需求”
2. 最终仍交付在固定模板壳上
3. 不因为用户口头指定语言就切换掉固定 Node Web Shell

这条是战略取舍，不是兼容性补丁。

## 7.5 硬边界补充（2026-05-10）

为保证面向用户交付的高可用性，固定模板策略需要从“提示词建议”升级成“部署主链硬边界”：

1. 新建可部署网站的主链只允许走 `oneceo_official_vite_node_shell`
2. `client/`、`server/`、`shared/`、`package.json`、`vite.config.ts`、`oneceo.manifest.json` 组成唯一稳定交付车道
3. 对外不再承诺“任意 Node 自由结构网站”具备 Manus 同级部署稳定性

部署阶段补充强约束：

1. 若项目画像属于 `web_app` 或 `static_site`，但模板族不是 `oneceo_official_vite_node_shell`，部署工具必须直接返回 `template_compliance/non_official_frontend_template`
2. `package.json`、`vite.config.ts`、`oneceo.manifest.json`、`client/index.html`、健康检查壳默认视为平台契约文件，不允许在普通部署修复里漂移
3. 平台级预检失败必须与工作区代码失败分流，不能继续把沙箱 Playwright/浏览器能力异常下沉为 Altus 的源码修复任务

## 7.6 平台预检原则（2026-05-10）

固定模板主链的本地运行验收，必须视为“平台托管预检”，而不是 Altus 自由调试环节：

1. preflight 负责 build、start、healthcheck、browser smoke
2. preflight 必须复用平台预装的 Playwright/浏览器能力契约
3. 如果 preflight 失败原因为：
   - Playwright 模块缺失
   - 浏览器二进制缺失
   - 平台默认浏览器路径缺失

则统一记为 `platform_capability`，只允许汇报平台阻塞，不允许继续修改工作区代码或契约文件。

### 7.5 Altus 结束前只做宏观自检

`ONECEO_WEBAPP_MACRO_REVIEW_ANCHOR`

为了避免长尾和 token 浪费，结束前不做“逐文件重读式复盘”，而是做一次宏观 todo 对照检查：

1. todo 中承诺的主要路径是否都已落地
2. 固定模板壳契约是否仍然成立
3. 主要页面与主要后端能力是否已经覆盖
4. 是否新增了不应出现的 runtime、启动脚本或目录漂移
5. 是否已经满足结束条件

这一步强调高层一致性核对，而不是再次细读每个文件。

## 8. 部署链要改什么

### 8.1 Fast Lane 不再做 runtime family 广覆盖

当前主链只服务这一套固定模板。

也就是：

1. 不再继续扩 Java/PHP/Python 的 Fast Lane
2. 不再继续扩任意 Node 自由结构 Fast Lane
3. 先把固定模板壳做到接近 Manus 的确定性

### 8.2 预检简化

因为模板固定，preflight 可以收缩成：

1. 模板指纹匹配
2. build/start/healthcheck 完整
3. analytics 注入点存在
4. 最小发布目录可生成

### 8.3 发布面固定

固定模板的发布面也固定：

1. `dist/public`
2. 打包后的 server 入口
3. `package.json`
4. `oneceo.manifest.json`
5. 部署配置文件

### 8.4 公网 URL 稳定性规则

固定模板部署完成后，主要交付 URL 必须优先选择已经可被 TLS 正常访问的 provider URL。

规则：

1. `latestUrl` / `latestStaticUrl` 优先使用 Railway provider 域名，例如 `*.up.railway.app`
2. oneceo.space 自定义域名保留为 `publicDomain` / `publicUrl` 绑定信息
3. 自定义域名即使记录为 `active`，也不能覆盖 provider URL 作为主要交付 URL
4. 避免用户拿到证书未就绪或证书不匹配的 oneceo.space URL 后误判为部署失败

这条规则服务于“先稳定交付，再逐步推广品牌域名”。

### 8.5 Analytics 运行时注入规则

官方固定 Web Shell 不能只依赖构建期静态注入。

原因：

1. Vite 构建后的 `dist/public/index.html` 可能只保留 `ONECEO_ANALYTICS` 占位
2. Railway analytics 变量属于运行时环境，最终可用性取决于部署容器启动时的 `VITE_ANALYTICS_*`
3. 如果固定壳 server 只静态返回 HTML，会导致公网 HTML 中出现空注释，Umami 永远无法被浏览器加载

因此固定壳 `server/index.ts` 必须在响应 HTML 时执行运行时注入：

1. 读取 `VITE_ANALYTICS_ENABLED`
2. 读取 `VITE_ANALYTICS_HOST` / `VITE_ANALYTICS_ENDPOINT`
3. 读取 `VITE_ANALYTICS_WEBSITE_ID`
4. 用真实 script 替换 `<!-- ONECEO_ANALYTICS:START --><!-- ONECEO_ANALYTICS:END -->`
5. 保持静态资源仍按普通文件流返回

## 12. 2026-05-09 E2E 追加验证与修复结论

本轮把验收从“部署成功”继续推进到“公网浏览器真实可运行 + Umami 统计可回写”。

新增验收维度：

1. 公网 URL 返回 `HTTP 200`
2. CSR bundle 中能找到用户验收 marker
3. HTML 中发布了 OneCEO analytics bootstrap
4. Playwright 真实浏览器访问公网 URL
5. 浏览器侧 `analytics.oneceo.ai/api/send` 返回 `200`
6. `/deployment?refresh=1` 最终从 `bound` 刷新为 `tracking`
7. 浏览器运行时 `pageErrors=[]`

已修复的问题：

1. `/deployment` 与 `/deployment/analytics` 不再直接复用 cached `bound` 响应；`refresh=1` 或 cached analytics 为 `bound` 时会绕过读缓存。
2. Umami E2E 浏览器访问改用真实 Chrome UA；Headless UA 即使 `/api/send=200`，也可能被统计侧过滤。
3. 固定壳 Vite 配置统一使用 React 自动 JSX runtime，不再同时开启 `esbuild.jsxInject` 与默认显式 `import React`，避免模板自身制造重复声明。
4. 部署源码归一化只在文件实际使用 `React.*` 命名空间时补齐 `import * as React from 'react';`；普通 JSX 文件不再因为出现 JSX 标签就被额外注入 React 导入。
5. 固定壳 Vite 配置补充 `@shared -> root/shared` alias，前端若要引用共享常量或类型，统一走 `@shared/...`，不再依赖脆弱的相对路径猜测。

## 13. 2026-05-09 部署前本地运行验收门

本轮新增部署前置门禁，用来避免“模板结构检查通过，但应用自身 build/start/browser 失败后仍继续推 Railway”的黑盒失败。

执行原则：

1. 门禁只对当前主线承诺的 `node/js/html` 快车道栈启用，包括 `oneceo_fixed_vite_node_shell`、`static_node_http_api_dbless`、`frontend_dist_http_api_dbless`、`node_script_http_api_dbless` 以及 Vite/Node/Static/Frontend 相关栈。
2. Java/PHP/Python 等非本轮目标栈暂时跳过本地运行验收，不改变其既有部署路径，避免用固定模板优化误伤长尾语言。
3. 本地运行验收完全读取 `oneceo.manifest.json` / `railway.json` 归一化后的 build/start/healthcheck 契约，不写死用户页面内容。
4. 验收顺序为依赖安装、build、按 start 命令注入 `PORT` 启动、healthcheck、Playwright 打开根页面做浏览器 smoke。
5. 失败时停止 Railway 发布，并把 install/build/server/browser 日志写入 `deployment_preflight_not_ready` 修复结果，交给 Altus 先修复再重新调用部署工具。

当前门禁边界：

1. 第一层只验证“能构建、能启动、健康检查可达、浏览器打开不是白屏且没有明显运行时错误”。
2. 暂不做复杂语义验收，例如自动判断 2048 全部规则、预约表单完整业务流或后台 API 细节。
3. 后续可以在同一门禁后追加任务感知 Playwright 检查，但必须基于用户需求摘要生成有限测试项，避免泛化能力被硬编码测试拖垮。
