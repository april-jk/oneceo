## 2. 目标

本轮只做两件事：

1. 在开始工作前先评估“这次是否真的需要 Todo”，让简单任务可以直接执行；
2. 把开发类任务的澄清问题细化成更明确的关键分歧项，而不是继续停留在泛化提问。

## 3. 非目标

本轮明确不做：

1. 不引入新的 Plan Mode、多轮采访引擎或独立需求采集页面；
2. 不照搬 ClaudeCode 的多问题、多预览、多注释 UI；
3. 不新增 Todo 数据表、Todo 状态机或第二套会话存储；
4. 不改写已有 Office adopted contract；
5. 不为了“防漏”引入强侵入式执行拦截，避免把现有稳定路径打坏。

## 4. ClaudeCode 参照结论

### 4.1 Todo 不是所有任务都必须写

ClaudeCode 在 [TodoWriteTool/prompt.ts](/Users/watson/codingProj/oneceo/referance/claudecode_src/tools/TodoWriteTool/prompt.ts) 里把边界写得非常清楚：

必须使用 Todo 的典型场景：

1. 复杂多步骤任务；
2. 非平凡任务；
3. 用户明确要求 Todo；
4. 用户一次给出多个任务；
5. 接收到新指令后需要先捕获工作项；
6. 正式开始工作前要先把一个任务标记成 `in_progress`。

明确不该使用 Todo 的场景：

1. 只有一个直接、简单的任务；
2. 任务非常 trivial；
3. 少于 3 个 trivial step 即可完成；
4. 纯对话、纯解释、纯信息回答。

结论：

1. ClaudeCode 的核心不是“能写 Todo”，而是“明确定义何时不该写 Todo”；
2. 这正是 oneceo 当前还缺的部分。

### 4.2 澄清不是泛问，而是结构化采集关键分歧

ClaudeCode 在 [AskUserQuestionTool/prompt.ts](/Users/watson/codingProj/oneceo/referance/claudecode_src/tools/AskUserQuestionTool/prompt.ts) 和 [AskUserQuestionTool.tsx](/Users/watson/codingProj/oneceo/referance/claudecode_src/tools/AskUserQuestionTool/AskUserQuestionTool.tsx) 里的做法有两个关键点：

1. 提问走正式工具，不走随意 plain text；
2. 问题围绕“方向分歧”来设计，而不是“你还有什么补充吗”这种泛问题。

它允许：

1. 明确选项；
2. 推荐项；
3. 用户补充自定义输入；
4. 在真正需要决策时再问。

结论：

1. ClaudeCode 借鉴价值不在于把 UI 做复杂，而在于把“该问什么”结构化；
2. oneceo 当前 `ask_user` 已经具备单问题 + options 的最小能力，足够先承接这一轮优化；
3. 本轮不需要复制 ClaudeCode 的多问题和 preview，只需要把问题本身问对。

## 5. oneceo 当前缺口

### 5.1 Todo 使用边界还不够清楚

当前 [altus-managed-prompt-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-managed-prompt-service.ts) 已经明确：

1. `simple` 任务直接执行；
2. `complex` 任务先写 Todo。

但缺少 ClaudeCode 那种更清晰的“反向边界”：

1. 单命令任务不该写 Todo；
2. 单点小改动不该写 Todo；
3. 纯解释不该写 Todo；
4. 如果开始时判断为简单任务，但检查后发现实际变成多步骤任务，应在扩展点补写 Todo。

### 5.2 澄清问题还没有细化到开发分歧层

当前 [task-intent-shape-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/task-intent-shape-service.ts) 的澄清更偏“宽泛业务系统 vs 边界型软件请求”：

1. `business_system + detail 命中不足` 时问一条通用问题；
2. `boundary_only_software_request` 时问一条交付物类型问题。

这能挡住“完全宽泛”的请求，但还不够覆盖开发中的关键分歧，例如：

1. 语言/框架未指定；
2. 交付物类型不明确；
3. 范围边界不明确；
4. 是否需要后端/数据库/登录/部署不明确。

### 5.3 现有 ask_user 能力够用，但问题生成策略不够好

当前 managed 路径已经有：

1. `ask_user`
2. `clarification_request`
3. 可选 `options`

因此本轮不需要新做 UI，只需要把“生成什么问题、何时附带 options”收敛好。

## 6. 设计原则

本轮遵守以下原则：

1. 最小化修改，优先复用现有 `task-intent-shape-service` 和 `ask_user/clarification_request`；
2. Clarification 继续保持硬门禁；
3. Todo 改成“显式评估后的单一前置判定”，而不是对所有任务一刀切；
4. 问题只问一个最高优先级分歧，不做多轮盘问；
5. 只有拿得到 session / workspace 上下文的层才允许根据仓库现状决定是否追问技术栈；
6. 如果请求已足够明确，就直接执行，不为了“显得谨慎”而多问；
7. phase 1 不引入运行中途的 Todo 补写硬门禁，所有强制分流都在进入 sandbox / 模型循环前完成。

## 7. 方案设计

### 7.1 新增一个最小前置判定：`todoRequired`

在现有 `taskIntentProfile` 基础上，新增一个最小判定字段：

1. `todoRequired: boolean`
2. `todoReason: 'multi_step' | 'multi_target' | 'debug_chain' | 'integration_chain' | 'explicit_user_request' | 'none'`

它的职责只有一个：

1. 在开始执行前判断“当前请求是否需要 Todo”。

本轮要明确一个约束：

1. `todoRequired` 是进入执行前关于 Todo 的唯一判定源；
2. prompt 中原有的 `simple / normal / complex` 只保留为模型的描述性工作语言，不再作为“是否必须先写 Todo”的独立裁决源；
3. 一旦 `taskIntentProfile.todoRequired` 已经给出结论，模型不得再用泛化复杂度判断去推翻它。

为避免把 text-only 分类器做成“伪上下文判定器”，本轮采用两段式收敛：

1. `task-intent-shape-service.ts` 只负责 text-only 基础信号；
2. 最终的 `todoRequired / todoReason / clarificationType / clarificationQuestion / clarificationOptions` 由有 session 与 workspace 上下文的 setup 层收敛。

因此本轮不新增独立服务，但最终判定不直接落在 text-only 分类器里，而是优先放在：

1. [task-intent-shape-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/task-intent-shape-service.ts)
   - 提供 text-only 基础信号与候选澄清类型
2. [altus-managed-setup-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-managed-setup-service.ts)
   - 结合 session 历史、workspaceRoot、现有仓库技术栈线索，给出最终 `taskIntentProfile`
3. [altus-managed-prompt-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-managed-prompt-service.ts)
   - 只消费最终 profile，不再自己衍生第二套 Todo 裁决

### 7.2 Todo 必须与不必须的边界

#### 7.2.1 必须先写 Todo 的情况

以下情况命中任意一类，即 `todoRequired=true`：

1. 任务至少包含 3 个可区分的动作；
2. 用户一次提出多个子任务；
3. 需要“检查/分析 -> 修改 -> 验证”的串联链路；
4. 需要修改多个文件、多个模块或多个子系统；
5. 涉及部署、迁移、联调、运行环境、连接器集成；
6. 用户明确要求写 Todo；
7. 在启动前结合 session 历史、workspace 线索与当前请求，已经能够判断会跨多个点处理。

#### 7.2.2 不强制 Todo 的情况

以下情况默认 `todoRequired=false`：

1. 纯问答、纯解释、纯知识回答；
2. 单命令即可完成的操作；
3. 单文件单点小改动；
4. 单处注释、单处文案、单个小样式修改；
5. 明显可以在少于 3 个 trivial step 完成的请求。

#### 7.2.3 本轮不做运行时补写硬门禁

为了保持最小改动并避免引入新的运行态拦截复杂度，本轮明确：

1. `todoRequired` 只作为启动前的单一前置分流；
2. 如果启动前判定为 `todoRequired=false`，则允许直接进入执行；
3. phase 1 不新增“执行到一半发现任务扩张后，runtime 强制拦截补写 Todo”的控制器逻辑；
4. 如果模型在执行中主动发现范围扩大，仍然可以自发补写 `todowrite`，但这不是本轮闭环成立所依赖的硬性机制。

这样做的原因是：

1. 用户当前要求是“开始前评估是否需要 Todo”，不是“引入新的运行中拦截器”；
2. 当前链路里最容易引入不可控 bug 的部分正是执行中途拦截；
3. 先把启动前的边界判准，比半途补救更稳定。

### 7.3 细化澄清问题的分歧类型

本轮不扩成多问题采访，只增加“澄清类型”：

1. `clarificationType: 'artifact_type' | 'tech_stack' | 'scope_boundary' | 'integration_target' | 'acceptance_requirement' | 'none'`

每次只问一个最高优先级分歧。

优先级顺序如下：

1. 交付物类型不清楚；
2. 技术栈不清楚；
3. 范围边界不清楚；
4. 集成对象不清楚；
5. 验收要求不清楚。

原因：

1. 交付物类型和技术栈会直接决定后续所有实现路径；
2. 范围和集成决定工作量与边界；
3. 验收要求一般放在后一级，因为很多场景可以先按仓库默认标准推进。

### 7.3.1 澄清的最终判定层

这里要额外明确：

1. `task-intent-shape-service.ts` 只能基于文本判断“可能缺什么”；
2. 凡是依赖仓库现状、现有技术栈、session 历史上下文才能判断的问题，必须在 [altus-managed-setup-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-managed-setup-service.ts) 的 `buildTaskIntentProfile(...)` 阶段完成；
3. 因此“仓库已经天然约束技术栈就不追问”这一条，不应由 text-only classifier 直接负责。

### 7.4 开发类任务的最小澄清模板

针对软件开发请求，本轮新增以下最小模板。

#### 7.4.1 交付物类型不清楚时

优先问：

1. 这次要交付的是网页应用、后端 API、本地脚本，还是完整业务系统？

适用场景：

1. “帮我做一个管理系统”
2. “做个工具给我用”
3. “开发一个应用”

#### 7.4.2 编程语言或框架不清楚时

仅在以下前提下询问：

1. 用户明确要新建项目或新做功能；
2. 仓库现有代码不能自然约束技术栈；
3. 不同语言/框架会显著改变实现结果。

优先问：

1. 这次希望使用哪种开发语言或框架？如果没有指定，我将按仓库现有技术栈继续。

典型场景：

1. “帮我写一个爬虫”
2. “开发一个后台”
3. “做个小工具”

#### 7.4.3 范围边界不清楚时

优先问：

1. 这次只需要前端页面，还是需要包含后端、数据库和登录权限？

典型场景：

1. “帮我做一个后台系统页面”
2. “做一个 CRM”

#### 7.4.4 集成对象不清楚时

优先问：

1. 这次需要接入现有系统吗？如果需要，请说明目标系统或接口边界。

典型场景：

1. “接一个企业内部系统”
2. “和现在的平台打通”

#### 7.4.5 验收要求不清楚时

优先问：

1. 这次只需要源码，还是还需要本地可运行、测试通过，或可以直接部署？

典型场景：

1. “帮我搭一个项目”
2. “开发一套系统”

### 7.5 问题生成规则

为了避免把用户问烦，本轮问题生成遵守以下约束：

1. 每轮最多只问一个问题；
2. 问题必须是当前最高分歧点；
3. 能被仓库现状或已有上下文自然约束的，不再问；
4. 能使用现有 adopted default 的，不再问；
5. 问题优先具体到用户可以直接回答，而不是泛问“还有什么要求”；
6. 当存在 2 到 4 个明显候选方向时，使用 `options`；
7. 若没有合理选项，就只发自由回答问题。

### 7.5.1 单问题澄清后的再分流闭环

为了避免“第一问答完后流程断开”，本轮把澄清闭环定义为：

1. `user_input` 与 `user_response` 都要重新构建最终 `taskIntentProfile`；
2. 每一轮都只选择当前最高优先级的一个阻塞分歧来问；
3. 用户回答后，系统重新计算：
   - 如果已经没有阻塞分歧，则进入 `direct_answer / direct_execute / todo_first_then_execute`
   - 如果仍然存在新的最高优先级阻塞分歧，则继续进入下一轮单问题澄清
4. 已经被用户明确回答过的字段，不重复追问；
5. 只有当前回答没有覆盖该阻塞点时，才允许继续停留在 `waiting_user`。

因此本轮不是“只允许问一次”，而是“每轮只问一个最高优先级问题，并在每轮答复后重新分流”。

### 7.6 与现有硬门禁的关系

Clarification 继续作为硬门禁，Todo 不升级为新的硬门禁。

原因：

1. 澄清失败会直接导致实现方向错误，因此必须硬拦；
2. Todo 的本质是执行组织机制，不是方向判定；
3. 当前 complex task -> `todowrite` 的正向链路已经可用；
4. 本轮目标是减少 Todo 误用，不是把执行链再加一道高风险拦截。

因此本轮收敛为：

1. 只要最终 `taskIntentProfile.needsClarification=true`，就继续由 coordinator 在 pre-sandbox 阶段硬拦；
2. 这个硬门禁适用于 `user_input` 和 `user_response`，直到阻塞分歧被真正消除；
3. `todoRequired=true` 时，通过最终 profile + prompt contract 明确要求先写 Todo；
4. `todoRequired=false` 时，通过最终 profile + prompt contract 明确禁止为了简单任务预先滥写 Todo；
5. phase 1 不新增运行中的 Todo 补写硬门禁。

### 7.7 对 ClaudeCode 的借鉴边界

本轮借鉴的是规则，不是整套实现。

保留：

1. Todo 的正反边界；
2. AskUser 的结构化问题思路；
3. 复杂任务先组织、简单任务直接做。

不照搬：

1. 多问题问卷；
2. preview UI；
3. plan mode；
4. todo reminder 注入机制；
5. 更重的任务系统。

原因：

1. oneceo 当前 managed UI 和工具面还没有承接这些重能力；
2. 直接照搬会扩大改动面，引入不可控 bug；
3. 当前需求只要求把判定边界和问题质量收准。

### 8.1 详细实现步骤

#### 步骤 1：扩展 `AltusManagedTaskIntentProfile` 类型

文件：

## 9. 验证闭环

本轮方案的验证应覆盖以下场景：

### 9.1 简单任务不写 Todo

例如：

1. “给这个函数补一行注释”
2. “把这个按钮文案改成提交”
3. “帮我执行一次 npm install 看结果”

预期：

1. 不出现 `todowrite`
2. 直接执行或直接回答
3. 如果前端已经展示 Todo 状态徽标，浅色主题下 `completed` 徽标必须保持足够对比度，不能再出现浅底浅字导致“已完成”难以辨认

### 9.2 复杂任务仍然先写 Todo

例如：

1. “帮我重构登录模块并补测试”
2. “实现一个带数据库和接口的后台系统”
3. “排查这个会话卡住的问题并修复”

预期：

1. 先出现 `todowrite`
2. 再进入执行

### 9.3 宽泛开发任务优先问关键问题

例如：

1. “帮我做一个企业管理系统”
2. “开发一个内部工具”
3. “做一个后台”

预期：

1. 先进入 `clarification_request`
2. 问题内容具体，不是泛问
3. 不先写 Todo
4. 不先执行

### 9.4 技术栈未定时问语言/框架

例如：

1. “帮我写一个爬虫工具”
2. “开发一个小型管理后台”

预期：

1. 如果仓库不能自然约束技术栈，则先问语言/框架；
2. 如果仓库现状已明显约束技术栈，则直接按仓库继续，不重复提问。

### 9.5 首轮澄清后再次分流

例如：

1. 用户先说“帮我做一个企业管理系统”
2. 系统先问交付物类型
3. 用户回答“做一个内部管理后台”
4. 系统发现仍缺少范围边界

预期：

1. 第二轮仍然只问一个最高优先级问题；
2. 不直接执行；
3. 不重复已经问过并已回答的字段；
4. 直到阻塞分歧消失后，才进入 direct_execute 或 todo_first。

### 9.6 Todo 判定权唯一

例如：

1. 请求文本较长，模型主观上可能会觉得“复杂”
2. 但最终 `taskIntentProfile.todoRequired=false`

预期：

1. 不因为模型自判复杂度就先写 `todowrite`
2. 以最终 `taskIntentProfile` 为准
3. prompt 中的 `simple / normal / complex` 只作为描述性工作语言，不形成第二套裁决源

## 10. 剩余风险与控制

### 10.1 workspace 探测开销风险

风险：

1. 如果在 setup 层做整仓扫描，会拖慢首轮响应。

控制：

1. 只允许根目录轻量探测；
2. 只读少量固定文件；
3. 不做递归目录遍历；
4. 解析失败直接降级，不阻塞。

### 10.2 技术栈误判风险

风险：

1. 仓库可能同时存在多套技术栈文件；
2. `package.json` 可能只是工具脚本，不代表真实项目框架。

控制：

1. 只有当根目录线索足够单一时，才视为“仓库已天然约束技术栈”；
2. 一旦信号冲突，就回退为允许追问；
3. 宁可多问一次，也不要因为误判技术栈而直接走错实现路径。

### 10.3 多轮澄清重复追问风险

风险：

1. 如果“用户答复是否覆盖上一问”判断不准，可能出现连续追问同一件事。

控制：

1. phase 1 只按关键词覆盖做保守判断；
2. `pendingClarificationType` 作为上一问目标字段的真相源，不通过 question 文案反推；
3. 无法确认覆盖时允许继续问，但必须切换成更具体的问题；
4. 不允许原样重复上一条 `clarificationQuestion`。

### 10.4 prompt 漂移风险

风险：

1. 即使 profile 已经给出 `todoRequired=false`，旧 prompt 文案仍可能诱导模型先写 Todo。

控制：

1. 必须同步清理 prompt 中所有独立的 Todo 裁决语句；
2. 用测试锁住“`todoRequired=false` 不先写 Todo”。

### 10.5 回归现有 adopted contract 的风险

风险：

1. Office、部署类、纯问答类现有 adopted contract 可能被新的澄清或 Todo 判定误伤。

控制：

1. Office adopted contract 优先级保持不变；
2. 部署相关 profile 字段不重构；
3. 补充回归测试覆盖：
   - PPT/DOCX/XLSX 直接开工
   - 部署请求仍走部署工具
   - 纯问答不强行澄清或 Todo

### 10.6 phase 1 不处理运行中途扩张的风险

风险：

1. 某些启动时看似简单、执行后才发现复杂的任务，phase 1 不会做 runtime 强拦截补 Todo。

控制：

1. 这是有意保留的边界，不视为逻辑缺口；
2. 先把启动前判断收准；
3. 如果后续真实回归里发现这类场景占比高，再单独设计 phase 2 的运行中补写机制。

### 10.7 澄清态生命周期闪动风险

风险：

1. 如果 `user_response` 仍需继续澄清，但 run entry 先把 session 切到 `executing`，前端会出现短暂错误状态。

控制：

1. run entry 的“是否进入 executing”条件必须和最终 clarification gate 保持一致；
2. 只要 profile 仍然 `needsClarification=true`，无论 `user_input` 还是 `user_response`，都维持 `waiting_user/clarifying`。

### 10.8 旧澄清污染新问题风险

风险：

1. 会话存在 `pendingClarificationType` 时，前端后续输入可能仍以 `user_response` 进入 managed run；
2. 如果后端无条件复用旧 pending clarification，就会把“你是谁开发的”“查查半导体行业年报”这类新问题继续追问成“使用哪种开发语言或框架”。

控制：

1. `pendingClarificationType` 只在当前输入像是在回答上一轮澄清时继续生效；
2. 当前输入明显是新的能力问答、身份问答、检索/研究/报告类任务时，必须按新 turn 重新判定 profile；
3. 新 turn 判定后如果不再需要澄清，run entry 继续清理 pending clarification，避免旧问题污染后续轮次。

## 11. 结论

本方案是对当前 adopted“首轮澄清优先与 Todo 前置”方案的最小增量优化，核心收口如下：

1. Todo 不再被理解为所有任务的默认前置，而是先判断、再决定；
2. 简单任务直接执行；
3. 复杂任务继续先写 Todo；
4. 澄清问题从“泛化确认”升级为“围绕交付物、技术栈、范围和验收的单问题结构化澄清”；
5. repo-aware 的技术栈追问只在 setup 层做，不把 text-only classifier 扩成伪上下文引擎；
6. 整体仍复用当前 oneceo 的 managed 工具和 coordinator 主链，不引入新系统。

如果进入代码实现阶段，建议优先按最小路径落地：

1. 先把 `task-intent-shape-service.ts` 收成 text-only 基础信号层；
2. 再在 `altus-managed-setup-service.ts` 完成最终 profile 收敛；
3. 然后更新 `altus-managed-prompt-service.ts` 的单一判定约束；
4. 最后把 `clarification_request` 的 gate 扩到“澄清未消除前持续生效”，并透传 options。
