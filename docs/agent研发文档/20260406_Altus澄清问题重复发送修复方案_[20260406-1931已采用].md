# 20260406 Altus 澄清问题重复发送修复方案 [20260406-1931已采用]

## 1. 问题描述

在 Altus managed 模式中，当模型进入“需要补充信息（clarification）”分支时，聊天区会出现同一语义文本重复展示：

1. 先出现一段 Altus 普通消息（来自 assistant 流式文本）。
2. 随后出现“需要补充信息”卡片（clarification_request），内容与上一步高度重复。

用户侧感知为“同一条补充信息被重复发送”。

## 2. 根因分析（全链路）

### 2.1 事件链路

- 模型流式输出阶段先发送 `assistant_delta`。
- 当本轮最终被判定为澄清问题时，后端再发送 `clarification_requested`。
- 前端因此同时持有：
  - `agent_message`（assistant 流式聚合结果）
  - `clarification_request`（澄清卡片）

### 2.2 身份键不一致导致回放难以合并

- 落库的 `clarification_request` 使用 `messageKey = managed:<runId>:clarification`。
- 实时流 `clarification_requested` 若未显式携带 `messageKey`，前端会退化生成 `managed:<runId>:clarification_requested`。
- 两者 key 不同，实时/回放合并时无法稳定视为同一消息。

## 3. 修复目标

1. 同一轮澄清问题在 UI 中仅保留一条有效表达，不出现重复文案。
2. 实时流与历史回放对同一澄清消息使用一致 messageKey。
3. 不引入兼容补丁路径，不增加降级分支，仅修正主链路行为。

## 4. 修复方案

### 4.1 后端：统一澄清事件 messageKey

文件：`apps/api/src/services/altus-run-coordinator.ts`

- 在 `requestClarification(...)` 中定义统一 key：
  - `managed:<runId>:clarification`
- `persistTimelineMessage` 与 `appendRunEvent('clarification_requested', payload)` 同时使用该 key。

### 4.2 前端：澄清事件 key 对齐

文件：`apps/web/client/src/hooks/useTaskCreationAgent.ts`

- `resolveManagedStreamMessageKey(...)` 中对 `clarification_requested` 特判：
  - 优先使用 payload/envelope messageKey。
  - 否则回退到 `managed:<runId>:clarification`（与落库对齐）。

### 4.3 前端：同轮澄清去重

文件：`apps/web/client/src/hooks/useTaskCreationAgent.ts`

- 在 `mergeRealtimeMessage(...)` 中增加澄清去重逻辑：
  - 当 incoming 为 `clarification_request` 时，查找同 run 的 managed assistant 文本消息。
  - 若 assistant 文本与 clarification question 归一化后等价，则删除 assistant 文本，仅保留 clarification 卡片。

## 5. 验证点

1. 触发 `ask_user` 或纯文本澄清分支时，聊天区只出现一条澄清信息。
2. 刷新页面后历史回放中仍只保留一条澄清信息。
3. 现有 managed assistant 流式拼接与工具事件顺序测试继续通过。

## 6. 影响范围

- `apps/api` Altus run coordinator（澄清事件 payload）。
- `apps/web` managed 消息 key 与实时合并逻辑。
- 对 sandbox 直通模式、非澄清消息无行为变更。

## 7. 状态

- 2026-04-06 已修复并完成测试验证，标记为已解决。

## 8. 回归补充（2026-04-07，Issue #36）

### 8.1 回归现象

在部分会话里，assistant 文本与 clarification 卡片语义一致但存在中英文边界空格差异，例如：

1. `Supabase连接器`
2. `Supabase 连接器`

由于两条消息并未被视为“同一文本”，UI 仍会出现一前一后两条重复提示。

### 8.2 回归根因

`apps/web/client/src/hooks/useTaskCreationAgent.ts` 中的去重比较依赖严格相等。旧归一化只会压缩空白，不会消除中英文边界空格差异，导致这类同义文本无法命中去重。

### 8.3 回归修复口径

1. 保持主链路不变，仍只在 `clarification_request` 到达时移除同 run 的重复 assistant 文本。
2. 增强比较归一化：在比较层增加“空白无关”的语义键，允许 `Supabase连接器` 与 `Supabase 连接器` 命中去重。
3. 增加回归测试，固定该场景，避免后续重引入。

## 9. 对话呈现策略补充（2026-04-07）

当 `clarification_request` 的问题文本可判定为“直接来自上一条 assistant 文本”（仅空格/中英文边界差异）时：

1. 不再重复渲染“需要补充信息 + 全量问题正文”消息块。
2. 在消息流末尾仅展示高对比提醒条，语义为“等待用户回复后继续执行”。
3. 若不满足重复来源判定，继续按原路径显示完整澄清问题，避免误隐藏有效信息。

## 10. 侧边栏状态样式同步（2026-04-07）

当会话状态为 `waiting_user`（待补充）时：

1. 侧边栏任务条目的状态文案“待补充”使用与澄清提醒条一致的 warning 色（`--function-warning`）。
2. 条目左侧图标切换为与提醒条一致的虚线圆提示图标。
3. 当用户回复并使会话状态回到 `in_progress/completed` 后，图标与文案颜色自动恢复默认样式。
