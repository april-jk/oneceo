# 20260331 Altus Sandbox恢复与MCP持久化恢复设计 [20260331-0115已采用]

> 2026-04-21 补充实现记录：

## 1. 问题背景

当前 Altus 模式下，session 级 MCP attach 已经切到：

1. 平台侧持久化 `task_session_connector_bindings`
2. 运行时通过 OSAC 在 sandbox 内注册 provider
3. run 创建前从 live MCP provider 生成 snapshot

现状存在三个结构性缺口：

1. 当 sandbox 已停止、被关闭、或因恢复切换到新 sandbox 时，平台侧只有“上一次 runtime 结果”，没有“下一次必须恢复成什么状态”的明确恢复控制面。
2. 用户在 sandbox 不在线时仍然需要调整对话的 connector/MCP 附加状态，但当前 attach/detach 更偏向“在线立即执行”，离线操作语义不完整。
3. API/服务重启后，缺少统一的 MCP backlog recovery 机制，无法把“未完成恢复的 session MCP 目标状态”重新纳入恢复队列。

这会导致：

1. sandbox stop/close 后，MCP 实际丢失，但平台状态与用户认知不一致。
2. 用户在 settings / 对话页调整 connector 状态时，平台无法稳定表达“已记录，待 sandbox 恢复后生效”。
3. run 恢复到新 sandbox 后，MCP 恢复依赖偶发的运行时链路，缺少统一 reconcile。

## 2. 目标

本方案只解决 Altus mode 下 session 级 MCP 的恢复问题，目标是：

1. 平台侧持久化 session MCP 的目标状态，而不是只记住上一次 live runtime 状态。
2. 当 sandbox 已停止或关闭时，用户仍可调整 session 的 connector attach/detach、profile、enabled tools、session config。
3. 当 sandbox 被恢复或替换后，平台能自动把 session MCP 恢复到持久化目标状态。
4. 当 API 重启后，系统能自动恢复尚未完成的 MCP backlog。
5. run 启动前拿到的是“reconcile 之后”的 MCP snapshot，而不是陈旧 snapshot。

## 3. 非目标

本次不做：

1. 新的 connector 定义平台化改造。
2. Direct/OpenCode 模式的历史 `/mcp` 配置链路兼容扩展。
3. 多 sandbox 并发共享同一 session MCP live state。

## 5. 核心设计

### 5.1 核心原则

1. 平台侧以 binding 为真相源，OSAC live state 只是运行时投影。
2. session MCP 恢复采用“reconcile”而不是“补丁式热修”。
3. sandbox stop/close 不清空用户目标状态，只清空 live runtime 事实。
4. 任何 run 启动前，必须先完成一次 session MCP reconcile。

### 5.2 目标状态与运行时状态拆分

对每个 `task_session_connector_binding`，拆成两层状态：

1. `desired`：
   - 是否 attached
   - 使用哪个 profile
   - enabled tools
   - session config
2. `runtime`：
   - 当前 live provider 是否已挂载
   - 当前挂载在哪个 sandbox
   - 当前 live tools 是什么
   - 当前是否待恢复/恢复中/恢复失败

新的状态语义：

1. `desiredState`
   - 继续作为用户目标状态，只允许 `attached | detached`
2. `runtimeStatus`
   - 扩展为：
   - `detached`
   - `pending_recover`
   - `recovering`
   - `connected`
   - `failed`
   - `needs_auth`

规则：

1. sandbox 不在线且 `desiredState='attached'` 时，binding 必须进入 `pending_recover`。
2. 进入恢复执行时，binding 进入 `recovering`。
3. OSAC live attach 成功后才进入 `connected`。
4. 用户 detach 时，平台立即更新 `desiredState='detached'`，即使 sandbox 离线也立即生效。

### 5.3 新增恢复任务表

新增表：`task_session_mcp_recovery_jobs`

字段建议：

1. `id`
2. `taskSessionId`
3. `orchestratorSessionId`
4. `recoveryKey`
   - 形式：`session:<taskSessionId>:sandbox:<orchestratorSessionId>:generation:<n>`
5. `jobType`
   - `session_reconcile`
6. `status`
   - `pending`
   - `running`
   - `completed`
   - `failed`
   - `cancelled`
7. `attemptCount`
8. `lastError`
9. `payloadJson`
   - 保存本次恢复的 binding snapshot
10. `nextRetryAt`
11. `createdAt`
12. `updatedAt`

唯一约束：

1. 同一 `taskSessionId + orchestratorSessionId + jobType + status in (pending,running)` 只允许一条活跃 job。

作用：

1. 支持 sandbox 恢复后的 MCP reconcile 入队。
2. 支持 API 重启后的 backlog 扫描。
3. 支持幂等恢复与失败重试。

### 5.4 新增 provider 持久化快照

新增表：`task_session_mcp_provider_snapshots`

字段建议：

1. `id`
2. `taskSessionId`
3. `connectorKey`
4. `profileId`
5. `runtimeProviderId`
6. `providerLabel`
7. `runtimeTransport`
8. `runtimeEnvVersion`
9. `toolsJson`
10. `bindingConfigJson`
11. `lastRecoveredAt`
12. `createdAt`
13. `updatedAt`

作用：

1. 平台侧持久化“最近一次成功恢复的 provider 事实”。
2. sandbox 离线时，前端仍可显示最近成功 tool catalog，而不是完全无信息。
3. run 启动前如果 live provider 尚未 attach，但需要展示历史 MCP 能力，可以基于该 snapshot 提示“待恢复”。

## 6. 恢复机制设计

### 6.1 sandbox stop/close 时

触发点：

1. sandbox 被显式关闭
2. sandbox 失联
3. 运行时被替换到新 sandbox

平台动作：

1. 扫描该 `orchestratorSessionId` 关联的 `task_session_connector_bindings`
2. 对所有 `desiredState='attached'` 的 binding：
   - 清空 `runtimeProviderId`
   - 清空 `runtimeAttachedToolsJson`
   - `runtimeStatus='pending_recover'`
   - `runtimeLastStoppedAt=now`
   - `lastError='sandbox_unavailable_pending_recover'`
3. 对 `desiredState='detached'` 的 binding：
   - `runtimeStatus='detached'`

这里不做 OSAC 调用，因为 sandbox 已不可用。

### 6.2 sandbox 恢复或新 sandbox 建立时

触发点：

1. [altus-managed-setup-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-managed-setup-service.ts) 中 `ensureSandbox()` 成功返回 sandbox
2. 显式“启动/恢复任务执行环境”成功
3. 旧 sandbox 失效后切换到新 sandbox

平台动作：

1. 生成 `session_reconcile` job
2. `payloadJson` 内写入当前 binding snapshot
3. 后台执行 `reconcileSessionMcpBindings(taskSessionId, orchestratorSessionId)`

### 6.3 reconcile 算法

输入：

1. `taskSessionId`
2. `orchestratorSessionId`
3. 当前 binding 列表
4. OSAC live provider 列表

执行顺序：

1. 先确保 sandbox runtime metadata 与 OSAC bridge ready
2. 拉取 live provider 列表
3. 对每个 binding 做期望态对比

规则：

1. `desiredState='detached'`
   - 若 live provider 存在，则执行 detach/remove
   - 最终写回 `runtimeStatus='detached'`
2. `desiredState='attached'` 但 profile 不可用或未授权
   - 不做 attach
   - 写回 `runtimeStatus='needs_auth'`
3. `desiredState='attached'` 且 profile 可用
   - register provider
   - attach provider to session
   - list live tools
   - 更新 binding 的 `runtimeProviderId/runtimeStatus/runtimeAttachedToolsJson`
   - 写 provider snapshot

幂等要求：

1. 如果 live provider 已存在且 config hash 相同，不重复 register，只做 attach state 校准。
2. 如果 live provider 已存在但 env/profile/config 变化，按覆盖 register 执行。

### 6.4 API 重启后的 backlog recovery

现有 [index.ts](/Users/watson/codingProj/oneceo/apps/api/src/index.ts) 已有 OSAC persistent recovery 启动点，但它只关注 OSAC 连接，不关注 session MCP desired state。

新增服务：`session-mcp-recovery-service`

启动时执行：

1. 扫描 `task_session_mcp_recovery_jobs` 中 `pending/running/failed(nextRetryAt<=now)` 的 job
2. 扫描 `task_session_connector_bindings` 中：
   - `desiredState='attached'`
   - `runtimeStatus in ('pending_recover','recovering')`
3. 对每个 session：
   - 若 sandbox 当前 ready，则入队/恢复 reconcile job
   - 若 sandbox 当前不存在，则保持 `pending_recover`，等待下次 sandbox 被恢复

这样 API 重启后不会丢掉“用户已经要求恢复的 MCP”。

## 7. 用户离线调整能力

当 sandbox 已关闭时，用户在对话页调整 connector，应遵循：

1. attach：
   - 立即持久化 binding desired state
   - 不返回“失败”
   - 前端显示 `待恢复`
2. detach：
   - 立即持久化为 detached
   - 若 sandbox 离线，不需要等待运行时
3. 切换 profile / enabled tools / repositories：
   - 立即改 binding
   - 若当前无 sandbox，则 `runtimeStatus='pending_recover'`
   - 下一次 sandbox ready 后按最新配置恢复，不用恢复旧配置

这要求前端 connector 选择器新增平台态展示：

1. `已附加`
2. `待恢复`
3. `恢复中`
4. `需重新授权`
5. `恢复失败`

## 8. run 启动前的要求

run 创建前，不能只依赖历史 `runtimeAttachedToolsJson`。

新的顺序：

1. `ensureSandbox()`
2. `ensureSessionMcpRecovered()`
3. `captureConnectorSnapshot()`
4. `captureMcpToolSnapshot()`
5. 创建 run

否则会出现：

1. 平台认为 binding 已 attached
2. 但新 sandbox 里 live MCP 尚未恢复
3. 模型启动时拿到空工具集

## 10. 失败与重试规则

只保留一条主路径：

1. recovery job 失败后进入 `failed`
2. 若错误是可重试运行时错误：
   - `nextRetryAt = now + retryBackoff`
3. 若错误是 profile/auth/config 错误：
   - binding 进入 `needs_auth` 或 `failed`
   - 不自动无限重试

backoff：

1. 第 1 次：30s
2. 第 2 次：2m
3. 第 3 次：5m
4. 第 4 次及以后：15m

## 14. 20260409 Issue #43 续聊文件未恢复修复记录

### 14.1 复盘结论

1. `AltusManagedSetupService.ensureSandbox()` 之前绕开了 `sandbox-agent-provision-service` 的完整恢复门禁，只做了 `getSandboxInfo` 级别复用判断。
2. 当 sandbox 已暂停/不可执行但元信息仍可读时，会误判可复用，导致 managed run 启动后工具命令连续失败。
3. `Altus` 写文件链路（`managed write_file`、`managed shell_execute`、附件写入）缺少 `markSandboxDirty`，可能让归档任务误判“无增量”，从而跳过最新工作区归档。

### 14.2 本次修复（已落代码）

1. `altus-managed-setup-service.ensureSandbox()` 改为统一走 `sandboxAgentProvisionService.provisionWithLock(executor=altus)`。
2. 继续保留会话绑定回写、runtime metadata 补齐、`ensureSessionRecovered`，但不再使用旁路 sandbox 复用实现。
3. `altus-managed-tool-runtime` 在 `shell_execute` / `write_file` / `mcp tool call` 成功后统一标记 `markSandboxDirty`。
4. `altus-managed-input-service` 的附件写入完成后改为 `markSandboxDirty`，确保上传附件也进入归档增量。
5. `osac-agent-service.callSessionMcpTool` 增加活跃触达与成功后 dirty 标记，补齐 MCP 写入场景的归档信号。

### 14.3 目标效果

1. 续聊时若旧 sandbox 实际不可执行，会自动走 provision 恢复链路，不再直接复用坏会话。
2. 只要 sandbox 内产生文件写入，归档任务都会拿到 pending/diff 信号，保证后续恢复能看到最新工作区文件。

## 15. 20260409 Issue #45 部署后会话列表空白修复记录

### 15.1 复盘结论

1. WebSocket 首条消息存在鉴权解析时序窗口：`resolveClientAuthContext` 异步执行时，`handleUserMessage` 可能先落库，导致 `createTask(..., userId)` 仍拿到 `undefined`。
2. `handleUserMessage` 与 `resumeTask` 路径把 `createTask` 的 `userId` 参数固定传 `undefined`，使 `task_creation_sessions.user_id` 可持续写空。
3. 直通模式 `handleOpencodeInput` 在补建 DB session 时只写 `{id,status}`，未写 `userId`，并且没有对历史空归属会话做 `bindUserIfMissing` 回填。

### 15.2 本次修复（已落代码）

1. `websocket-service` 新增鉴权等待门禁：在处理业务消息前等待当前连接的 auth resolve promise 完成，避免首条消息抢跑。
2. `handleUserMessage` 与 `resumeTask` 路径统一透传 `resolvedUserId` 到 `createTask/resumeTask`。
3. `task-creation-service.createTask` 在“会话已存在”场景增加 `bindUserIfMissing`，对历史空归属会话执行增量回填。
4. `handleOpencodeInput` 在 DB 建会话与兜底 ensure 会话时写入 `userId`，并在会话已存在且用户已识别时执行 `bindUserIfMissing`。
5. `readCookieFromHeader` 增加 URI 解码容错，避免异常 cookie 打断 auth resolve。

### 15.3 目标效果

1. 新创建与续聊会话不再写出空 `user_id`。
2. 直通模式会话同样保证 `task_creation_sessions.user_id` 正确归属。
3. 已有历史空归属会话在用户继续操作该会话时可被自动回填，后续在会话列表可见。

### 15.4 鉴权链路补充审计与硬化（20260409）

1. WebSocket 入口新增“消息级鉴权门禁”：`user_input/user_response/auto_plan/opencode_input` 四类写操作消息在处理前必须存在 `resolvedUserId`，否则直接返回登录态错误并终止本次处理。
2. `GET /api/altus-managed/runs/:runId/stream` 移除 `query.userId` 旁路兼容，改为强制 `currentUserResolver.require(req)`；仅当当前鉴权用户与 `session.userId` 一致时允许订阅。
3. 审计结论：`connector-routes` 与 `task-creation-routes` 的写接口均已以 `currentUserResolver.require(req)` 为主路径，`resolve(req)` 仅用于 catch 分支的缓存兜底读取，不参与写入授权决策。

### 15.5 Issue #45 二次回归修复（20260409）

#### 15.5.1 回归现象

1. 部署重启或页面刷新后，用户端会话列表可能整体空白。
2. 管理端仍可看到这些 session，且部分 session 的 `task_creation_sessions.user_id` 为空。

#### 15.5.2 根因结论

1. `POST /api/task-creation/sessions` 在“DB 会话已存在”分支仅复用会话，没有执行 `bindUserIfMissing`，导致历史空归属会话无法在用户入口被回填。
2. `GET /api/task-creation/sessions` 严格按 `currentUser.userId` 过滤；当历史会话归属为空时，用户列表会被过滤为 0 条。

#### 15.5.3 本次修复（已落代码）

1. `POST /api/task-creation/sessions` 新增“已存在会话归属回填”：
   - 若会话已归属其他用户，直接返回 403；
   - 若会话归属为空，执行 `bindUserIfMissing(sessionId, currentUser.userId)`。
2. `GET /api/task-creation/sessions` 新增“受限自动回填”：
   - 当当前用户会话列表为空时，先检查是否存在“已归属到其他用户”的会话；
   - 仅在不存在其他用户归属数据时，回填最近空归属会话到当前用户，再重新执行用户态列表查询。
3. `requireOwnedTaskSession`、`AltusManagedSetupService.ensureSessionOwnership`、`sessionConnectorService.assertSessionOwnership`、`sessionConnectorDraftService.applyDraftToSession` 在遇到空归属会话时统一先执行 `bindUserIfMissing`，避免 orphan session 在详情页/managed/connector 链路持续报 403。
4. `taskCreationSessionDAO.createSession` 增加缺失 `userId` 的告警日志（`TASK_SESSION_CREATE_MISSING_USER_ID`），用于持续监测是否仍有新空归属写入路径。
5. `TaskCreationService.createTask/resumeTask` 新增 `userId` 必填校验，阻断绕过鉴权调用导致的空归属写入。

#### 15.5.4 目标效果

1. 历史空归属会话可在用户端列表请求链路中被修复并重新可见。
2. 会话列表继续以 `userId` 作为唯一过滤条件，不放宽跨用户读取边界。
3. 详情页、managed run、connector 入口访问到 orphan session 时可就地回填归属，不再因“缺失归属用户”阻断恢复流程。

### 15.6 Issue #45 三次加固（20260409）

#### 15.6.1 新增复盘结论

1. 仍有一批历史 session 的 `task_creation_sessions.user_id` 不是空值，而是旧匿名标识（legacy local id），这类数据不会被“只回填空值”逻辑修复。
2. 归属校验存在少量“字符串未规范化比较”（如前后空格差异）路径，可能导致本应同一用户却被误判为无权限。
3. 列表回填链路缺少“legacy id 定向迁移”能力，刷新后可能持续空列表。

#### 15.6.2 本次修复（已落代码）

1. `taskCreationSessionDAO` 新增 legacy 迁移能力：
   - `rebindSessionsFromLegacyUserId(userId, legacyUserId, limit)`：仅允许 non-canonical legacy id（非 app user uuid）定向迁移到当前登录用户；
   - `adoptSessionFromLegacyUserId(sessionId, userId, legacyUserId)`：详情访问链路可按同规则就地认领。
2. `GET /api/task-creation/sessions` 在用户会话为空时新增优先级：
   - 先尝试 legacy 定向迁移；
   - 再进入原有 orphan（空归属）回填逻辑。
3. `POST /api/task-creation/sessions` 在“会话已存在且 owner 不同”时：
   - 若命中 legacy hint，执行定向认领；
   - 否则维持 403，继续守住跨用户边界。
4. 统一 owner 比较规范化：
   - `requireOwnedTaskSession`、`AltusManagedSetupService.ensureSessionOwnership`、`sessionConnectorService.assertSessionOwnership`、`sessionConnectorDraftService.applyDraftToSession` 改为规范化用户 ID 比较，避免空格等脏数据误判。
5. Web 端 `buildClientIdentityHeaders` 透传 `X-Legacy-User-Id`（来源：`localStorage.oneceo_client_user_id`），用于历史会话定向迁移，不参与新登录态鉴权。

#### 15.6.3 目标效果

1. 历史“legacy user_id”会话可在用户端列表请求时被定向迁移并恢复可见。
2. ownership 判定对历史脏字符串更稳健，不再因格式差异误伤合法用户。
3. 用户态读写依然以登录态 `app_users.id` 为准，不回退到匿名 `X-User-Id` 身份模型。

## 16. 20260409 managed 完成任务消息吞并修复记录

### 16.1 问题现象

1. 在 `web_search -> complete_task` 这类无附件任务中，前端最终只显示一句简短“已查询并汇总...”，缺少模型在同轮已生成的详细正文。
2. 用户体感为“完成任务工具吞了消息”，任务完成后答复信息量明显下降。

### 16.2 根因结论

1. `altus-run-coordinator` 在 `complete_task` 分支固定使用 `complete_task.summary` 作为最终落库消息。
2. 同轮 assistant 在触发 `complete_task` 之前已生成的更完整正文未被优先保留，导致最终消息可能被短 summary 覆盖。
3. 提示词中原有“concise summary”约束进一步放大了该问题，模型更倾向产出一句话 summary。

### 16.3 本次修复（已落代码）

1. `apps/api/src/services/altus-run-coordinator.ts`
   - 新增 `resolveFinalAssistantContent`：
     - 当同轮 assistant 正文与 `complete_task` summary 同时存在时，优先保留信息更完整的一侧，避免短 summary 覆盖详细正文。
   - `complete_task` 完成分支改为先构建 `completionMessage`，再经 `resolveFinalAssistantContent` 计算最终落库与流式回传内容。
2. `apps/api/src/services/altus-managed-prompt-service.ts`
   - 将 completion 规则从“concise summary”改为“summary 必须是可直接展示给用户的完整最终答复（必要时分点）”，避免一句话占位式完成文本。
3. `apps/api/tests/altus-run-coordinator.test.ts`
   - 新增回归用例：`execute preserves richer assistant text when complete_task summary is concise`，确保详细正文不会被简短 summary 吞并。

### 16.4 验证结果

1. `pnpm -C apps/api exec tsx --test tests/altus-run-coordinator.test.ts` 通过（14/14）。
2. `pnpm -C apps/api exec tsx --test tests/altus-managed-prompt-service.test.ts` 通过（7/7）。
3. `pnpm --filter api type-check` 通过。

### 16.5 20260424 补充修复：完成消息 Markdown 列表格式保护

1. 问题现象：部分 `complete_task` 最终答复会把多条 `• item` 放在同一段内，前端 Markdown 渲染只能按普通段落展示，导致“核心功能”“验证”等列表格式丢失。
2. 根因结论：
   - `resolveFinalAssistantContent` 为避免短 summary 吞并详细正文，会优先保留同轮更长的 assistant 文本；
   - 这条路径此前没有对 assistant 原文做 Markdown 规范化，因此模型原文中的非标准 bullet glyph 会直接落库。
3. 本次修复：
   - 在 `altus-run-coordinator` 增加 `normalizeManagedCompletionMarkdown`，将 `• item • item` 和行首 `• item` 转换为标准 Markdown `- item` 列表；
   - `buildCompletionMessage` 与 `resolveFinalAssistantContent` 都走同一规范化边界，确保 summary 路径和 assistant 原文优先路径一致；
   - `complete_task` 的验证区块改为 `验证:\n\n- ...`，让 Markdown 列表与标题之间保持稳定空行；
   - 补充提示词约束，要求模型在 `complete_task.summary` 中使用分行 Markdown 列表，不再把多个 `• item` 拼在一行。
4. 验证要求：覆盖 bullet glyph 转 Markdown、详细 assistant 原文优先但格式被规范化、原有完成消息验证列表仍正确显示。
