## 1. 问题定义

上一轮用户态多语言整改把“平台界面文案”和“运行时内容”混成了同一类文本，导致语言切换边界被画错。

当前错误不在于“还有文案没翻译”，而在于：

1. 一部分本应被视为会话内容、任务内容、交付内容、项目内容的数据，被当成了平台静态文案
2. 这些内容在渲染时通过 `t(...)` 或映射函数被二次改写
3. 用户切换语言后，页面中的 AI/用户/智能体/经理/员工相关内容会跟着变化

这会直接破坏对话系统最基础的语义一致性：

1. 用户发出去的话不应被语言设置重写
2. AI 在会话中生成的文本不应被界面语言回译
3. 任务、交付、反馈、项目说明这类内容，一旦形成，就应按原文展示

## 2. 对用户意图的理解

我对这次需求的理解如下，这里作为后续修复的硬边界：

1. `设置 -> 设置 -> 语言` 只控制平台壳层语言，不控制会话内容本身
2. 对话页面、CEO View、AgentProject 以及类似页面中，凡是“像内容一样存在”的文本，都必须保持生成时/录入时的原文
3. 这里的“原文”包括：
   - 用户输入
   - AI 回复
   - 智能体消息
   - 经理/员工之间的任务沟通
   - 项目描述、任务描述、交付标题、交付正文、评价反馈
   - 运行时日志、执行回放、代码、文件内容、错误详情
4. 切换语言只能改变这些内容外围的界面文案，例如按钮、标题、字段名、空态、提示语、工具栏、弹窗说明
5. 即使某些页面当前还是 mock/demo 数据，只要这些数据承担的是“会话内容/任务内容/交付内容”的角色，也不能在渲染时跟随语言切换

还需要补一条，避免后续把修复范围做过头：

6. “创建时生成一条新内容”和“展示一条已存在内容”不是一回事
7. 对于创建时即时生成的新输入文本，例如快捷动作建议、部署指令模板、附件默认提示语，可以按用户当前界面语言生成
8. 但这些文本一旦作为消息、任务、备注、描述被真正写入会话或页面状态，就必须按生成后的原文展示，不能在后续语言切换时再次改写
9. 平台自动生成并注入消息流的系统文案也适用同一规则
10. 例如欢迎语、中断确认、运行状态回退文案、失败兜底文案，如果它们最终进入消息历史，就应被视为“单次生成内容”，而不是可被界面语言反复改写的 UI 壳层

换句话说，语言设置影响的是“平台怎么说”，不影响“内容本身说了什么”。

## 3. 当前根因

根因已经可以明确分成两类：

### 3.1 错误的国际化原则外扩

上一轮方案中把“所有用户可见文本”都纳入 locale 管理，但没有把“平台静态 UI 文案”和“运行时内容文本”拆开。

这个原则对按钮、标题、提示语是对的，但对会话、任务、交付、项目内容是错的。

### 3.2 代码层把内容当成了界面文案

当前已确认的错误实现包括：

1. `TaskDetail.tsx`
   - `translateTaskDetailMockText(...)` 会把经理名、任务名、消息正文、交付标题、交付正文、评价反馈在渲染时做语言替换
2. `ProjectDetail.tsx`
   - `translateProjectDetailMockText(...)` 会把经理名称、描述、任务标题、任务描述、员工角色等内容型字段做语言替换
3. `ManagerNode.tsx`
   - `translateManagerNodeMockText(...)` 会把角色、经理类型等内容字段做语言替换
4. `ManagerView.tsx`
   - `translateManagerViewMockText(...)` 会把项目描述、经理类型、经理描述、员工当前任务等内容字段做语言替换
5. `Home.tsx`
   - `localizeCapsuleLabel(...)` 基于原始消息文本做模式匹配并改写展示标签
   - 这意味着状态胶囊是否翻译，依赖的是“原始消息写了什么字”，而不是独立的系统状态码
6. `AgentProject.tsx`
   - 用 `t(...)` 直接生成模拟对话消息、建议原因、审批确认消息
   - 这类内容虽然是 mock，但它们在页面中的角色本质上仍是“对话内容”
7. `Sidebar.tsx`
   - `sidebar.sample*` 当前被用来生成示例项目、示例经理、示例任务名称
   - 这些名称虽然是示例数据，但在侧边栏里承担的是“内容对象名称”，不应随着界面语言切换而变化
8. `useTaskCreationAgent.ts`
   - 这里存在一批默认写入消息流的系统文本，例如欢迎语、中断确认、`managed run 已创建/已完成/已失败`、`交付文件已生成`、`请求失败，请稍后重试`
   - 它们不是普通按钮或标题，而是消息流里的系统生成内容，不能继续按“界面壳层文案”思路处理

## 4. 修复目标

本轮修复目标不是继续扩大多语言覆盖，而是收回错误边界，建立一条明确规则：

1. 平台 UI 文案可以国际化
2. 运行时内容不做显示时翻译
3. 内容类文本一律按原始数据渲染
4. locale 文件中不再承载对话正文、任务正文、交付正文、评价正文这类内容

## 5. 内容边界模型

### 5.1 可以进入 i18n 的内容

只允许以下文本进入 locale：

1. 导航、页签、按钮、弹窗标题、副标题
2. 表单字段名、placeholder、空态、loading、toast、tooltip、aria-label
3. 平台固定说明文案
4. 与业务对象无关的通用状态文案
   - 例如“发送”“保存”“查看详情”“暂无数据”
5. 基于结构化状态码渲染的 UI 文案
   - 例如 `pending / running / completed` 这类内部枚举对应的展示文本
6. 创建时用于帮助用户发起新操作的模板文本
   - 例如快捷动作建议、部署动作模板、附件默认提示语
   - 前提是它们只在“创建动作发生当下”生成一次，而不是在展示历史内容时反复翻译
7. 平台在消息发送或状态变化当下生成、并直接写入消息流的系统文本
   - 例如欢迎语、中断确认、运行状态回退文案
   - 它们允许在生成当下使用当前界面语言，但生成后必须作为消息原文固定下来

### 5.2 不允许进入 i18n 的内容

以下文本必须按原文展示，不能在渲染时调用 `t(...)` 改写：

1. 用户消息
2. AI 回复
3. 智能体消息
4. 项目名称、项目描述（若来源于用户或 AI）
5. 经理名称、经理说明（若来源于用户或 AI）
6. 员工角色、员工当前任务（若来源于任务系统或 AI）
7. 任务标题、任务描述
8. 交付标题、交付正文、评价反馈
9. 执行日志、调试输出、报错详情、代码块、文件内容
10. 用于模拟上述场景的 mock 内容
11. 侧边栏中的示例项目名、示例经理名、示例任务名
12. 已经写入消息流的系统生成消息正文

### 5.3 一个关键判断标准

判断某段文本能不能国际化，不看它现在是不是硬编码，而看它在页面里扮演什么角色：

1. 如果它是“平台在解释界面”，可以国际化
2. 如果它是“内容本身”，不能国际化

## 6. 修复策略

本轮按最短路径修复，不新增新的兼容层，不做显示期补丁。

### 6.1 删除显示期内容翻译

直接删除以下模式：

1. `translateTaskDetailMockText(...)`
2. `translateProjectDetailMockText(...)`
3. `translateManagerNodeMockText(...)`
4. `translateManagerViewMockText(...)`
5. `Home.tsx` 中基于原始消息文本的 `localizeCapsuleLabel(...)`

修复后原则：

1. 内容字段直接展示原值
2. UI 外壳字段继续走 `t(...)`

### 6.2 对 Home / 对话时间线做边界收口

`Home.tsx` 里的胶囊标签、状态展示必须按以下规则处理：

1. 如果展示文本来自原始消息内容，则原样展示
2. 不再通过字符串匹配把原始消息改写成另一种语言
3. 只有未来明确引入独立状态码字段时，才能基于状态码做本地化展示

本轮不新增状态码协议，只撤回当前错误的文本映射。

### 6.3 对 mock 页面做内容与 UI 分离

以下页面虽然当前数据是 mock，但它们展示的是“内容”，不是“界面壳层”：

1. `TaskDetail.tsx`
2. `ProjectDetail.tsx`
3. `ManagerNode.tsx`
4. `ManagerView.tsx`
5. `AgentProject.tsx`
6. `CEOView.tsx`（纳入复扫，保证未来继续沿正确边界实现）

处理原则：

1. mock 内容保留为固定原文数据
2. 页面标题、按钮、标签、字段名继续国际化
3. 不允许再用 locale key 去承载消息正文、任务正文、交付正文

### 6.4 对 Sidebar 示例数据做同样收口

`Sidebar.tsx` 中的示例项目、示例经理、示例任务当前仍通过 `sidebar.sample*` 词条生成。

这里需要统一按“内容对象”处理：

1. 这些名称是列表里的对象名，不是界面壳层标签
2. 即使它们是 demo 数据，也不应该随着语言切换来回变
3. 因此本轮要把 `sidebar.sample*` 从“界面国际化词条”降回固定示例数据，或直接按后续真实数据形态处理

### 6.5 对消息流系统默认文案做单独收口

`useTaskCreationAgent.ts` 中存在一些不是由 AI 直接产出、而是平台在前端消息链路里兜底生成的文本，例如：

1. 欢迎语
2. 中断确认
3. `managed run 已创建 / 运行中 / 已完成 / 已失败`
4. `交付文件已生成`
5. `请求失败，请稍后重试`

这些文本不能简单归入普通 UI 文案，原因是：

1. 它们会进入消息流
2. 一旦进入消息流，就会被用户当作历史内容感知
3. 如果继续用显示期翻译，会重复出现“切换语言后历史内容被改写”的问题

本轮对这类文本的处理原则是：

1. 不做显示期翻译
2. 如需支持多语言，只允许在“生成该条消息时”按当前语言生成一次
3. 生成后按消息原文固定，不在渲染阶段再次 `t(...)`

### 6.6 locale 词条同步收缩

本轮需要同时清理 locale 中不该存在的内容型词条，例如：

1. `taskDetail.mock.*`
2. `projectDetail.mock.*`
3. `managerNode.mock.*`
4. `managerView.mock.*`
5. `agentProject` 下承担对话正文作用的词条
6. `sidebar.sample*`
7. 仅用于历史消息正文的系统消息模板词条（如果后续发现已有错误接入）

保留原则：

1. 页面壳层文案保留
2. 内容正文类词条删除
3. 对象名称类示例词条删除

## 8. 验收标准

修复完成后必须满足以下结果：

1. 切换中英文后，平台按钮、标题、标签、提示语会变化
2. 切换中英文后，已展示的对话消息、任务说明、交付正文、反馈内容不变化
3. 同一份内容在不同界面语言下展示的正文保持一致
4. mock 内容页不再通过 locale 动态切换正文内容
5. locale 文件中不再存放会话正文、任务正文、交付正文、评价正文这类内容型长文本

## 10. 非目标

本轮不做以下事情：

1. 不做历史消息迁移
2. 不做 AI 自动翻译能力
3. 不做“根据界面语言强制指定模型输出语言”的策略改造
4. 不新增新的消息协议或状态协议
5. 不把所有硬编码字符串一刀切都迁回 locale
6. 不把创建时提示模板也错误地归类成历史内容展示

## 11. 明确保留的非问题项

为了避免过度设计，本轮明确以下能力可以保留现状：

1. 输入框 placeholder、按钮、弹窗、说明文案继续国际化
2. `buildTaskSessionDeploymentPrompt(...)` 这类“创建时生成一条新消息”的模板函数可以继续按当前界面语言生成文本
3. `HomePage` 的快捷动作建议可以继续按当前界面语言展示，因为它们属于发起入口，不属于历史内容
4. `DeliverableViewer`、`TaskDocumentsDialog` 中的标题、标签、状态徽标可以继续国际化，但正文内容、反馈内容必须保持原文
5. `Projects.tsx` 中的示例项目描述当前属于示例内容，而不是界面壳层文案；本轮只复扫其边界，不把它错误纳入“必须国际化”的整改项
6. `useTaskCreationAgent.ts` 里进入消息流的系统兜底文本，不属于普通页面壳层文案；它们要么保持固定原文，要么在生成时按当前语言生成一次，但都不能在展示历史时再次翻译

## 12. 结论

这次问题本质上不是“国际化做得不够”，而是“把内容系统误当成了界面系统”。

因此修复方向不能继续补词条，而必须把边界退回到正确位置：

1. 平台壳层语言可切换
2. 内容层原文不可被界面语言改写

只有这样，oneceo 的多语言能力才不会破坏 AI 对话、任务协作和交付链路的真实性。
