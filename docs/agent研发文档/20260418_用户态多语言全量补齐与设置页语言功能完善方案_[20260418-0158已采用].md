# 20260418 用户态多语言全量补齐与设置页语言功能完善方案 [20260418-0158已采用]

更新时间：2026-04-18 02:02

## 1. 背景

当前 `apps/web/client` 已经接入：

1. `i18next`
2. `react-i18next`
3. `LanguageDetector`
4. `locales/zh.json`
5. `locales/en.json`

但现状并不是“平台已支持多语言”，而是“框架已接入，覆盖很不完整”。

实测盘点结果表明：

1. `设置 -> 设置` 中虽然有语言切换入口，但只会影响极少数已接入 `t()` 的区域
2. 用户态页面、弹窗、Toast、按钮、占位文案、状态文案、ARIA 标签、空态提示中仍有大量硬编码中文/英文
3. 目前不同页面的国际化接入方式不一致，有的页面用 `useTranslation()`，有的完全没接
4. 如果只修“设置 - 设置”页面，会出现“语言切换成功，但大部分页面无变化”的假实现

因此本次不能按点状修补处理，必须作为一次用户态前端全量 i18n 收敛工作来做。

## 2. 当前问题盘点

### 2.1 设置页问题

当前 `SettingsDialog.tsx` 已接入 `useTranslation()`，但问题仍然存在：

1. 语言选项本身已存在，但没有建立“整个平台用户态已经全量受控”的前提
2. 局部文案在切换语言后会变化，但大量下游页面不会变化
3. 用户对“语言已切换”的感知与实际展示不一致

### 2.2 用户态平台范围内的硬编码问题

已通过仓库扫描确认，用户态 `apps/web/client/src` 中仍有大量硬编码文案，主要集中在：

1. `pages/`
   - `Home.tsx`
   - `HomePage.tsx`
   - `Login.tsx`
   - `Register.tsx`
   - `AgentProject.tsx`
   - `CEOView.tsx`
   - `TaskDetail.tsx`
   - `ProjectDetail.tsx`
   - 其他用户端工作台页面
2. `components/`
   - `Sidebar.tsx`
   - `SettingsDialog.tsx`
   - `ConnectorCenterPanel.tsx`
   - `OpencodePreviewPanel.tsx`
   - `TaskRuntimeDrawer.tsx`
   - 其他用户端弹窗、抽屉、工具面板
3. 运行时反馈
   - `toast.success/error/info`
   - placeholder
   - empty state
   - loading text
   - action labels
   - aria-label

### 2.3 遗漏风险

如果直接人工边改边看，最容易遗漏：

1. toast 文案
2. 拼接字符串
3. 模板字符串中的中文
4. 动态按钮文案
5. 仅在错误分支/空态分支中出现的文本
6. 组件内部说明文案
7. 图标按钮的 `aria-label`

## 3. 目标

本轮目标只有两类：

1. 让 `设置 -> 设置 -> 语言` 成为真实可用的全局语言切换入口
2. 对整个平台用户态范围做一次完整国际化收敛，避免明显遗漏

注意：

1. 本轮只覆盖用户态 `apps/web/client`
2. 不包含 `apps/admin_management`
3. 不包含 API 返回的原始后端错误文案改造
4. 不包含测试说明文档、注释、开发者日志等非用户可见文本

## 4. 设计原则

### 4.1 统一来源

所有用户可见文本必须统一来自：

1. `apps/web/client/src/locales/zh.json`
2. `apps/web/client/src/locales/en.json`

禁止继续在组件里直接硬编码中文/英文作为最终展示文本。

### 4.2 结构优先

不能只把现有字符串机械搬进 locale 文件，而要先建立可维护的 key 结构。

建议按页面/组件/领域分区：

1. `common`
2. `sidebar`
3. `settings`
4. `account`
5. `auth`
6. `home`
7. `connectors`
8. `preview`
9. `runtime`
10. `projectDetail`
11. `taskDetail`
12. `agentProject`
13. `ceoView`

### 4.3 动态文案必须支持插值

对下列场景不能继续字符串拼接：

1. `验证码已发送到 ${email}`
2. `引用项加载失败：${error}`
3. `执行环境已接入（${id}）`
4. `skills: ${count}`

统一改为 `t(key, { ...params })`。

### 4.4 不做兼容性补丁写法

不允许：

1. `t('xxx') || '中文默认值'`
2. `condition ? '中文' : t('xxx')`
3. 在组件里保留大量未迁移硬编码，寄希望于后续再补

必须按模块把用户可见文本一次收干净。

## 5. 整改范围

### 5.1 第一层：基础设施

文件：

1. `apps/web/client/src/i18n.ts`
2. `apps/web/client/src/locales/zh.json`
3. `apps/web/client/src/locales/en.json`

整改目标：

1. 确认当前语言切换基于 `i18nextLng` 持久化可用
2. 保持 `localStorage -> navigator` 的检测顺序
3. 明确默认语言策略
4. 补齐新的 namespace 结构与键

### 5.2 第二层：设置页与认证页

优先处理：

1. `SettingsDialog.tsx`
2. `Login.tsx`
3. `Register.tsx`

原因：

1. 这是语言切换和身份入口
2. 用户最先看到
3. 改完后最容易验证切换是否真实生效

### 5.3 第三层：用户主工作区

重点页面：

1. `Home.tsx`
2. `Sidebar.tsx`
3. `TaskCreationChat.tsx`
4. `TaskRuntimeDrawer.tsx`

这里要覆盖：

1. 输入提示
2. 执行状态
3. 空态
4. 错误提示
5. 按钮文案
6. 发布/预览/调试相关文案

### 5.4 第四层：连接器与预览面板

重点组件：

1. `ConnectorCenterPanel.tsx`
2. `OpencodePreviewPanel.tsx`

这是用户态里文案最密集、也最容易遗漏的区域之一，必须专门清理。

### 5.5 第五层：其余用户态页面

包括但不限于：

1. `HomePage.tsx`
2. `AgentProject.tsx`
3. `CEOView.tsx`
4. `TaskDetail.tsx`
5. `ProjectDetail.tsx`
6. `ManagerNode.tsx`

注意：

这些页面不少仍带模拟数据和原型文本，但只要属于用户态展示面，就必须纳入本次整改。

## 6. 遗漏控制方案

### 6.1 扫描法

整改过程中必须反复使用仓库扫描：

1. 扫中文硬编码
2. 扫英文长文本硬编码
3. 扫 `toast.*(...)`
4. 扫 `placeholder=`
5. 扫 `aria-label=`

### 6.2 分模块清单法

每改完一组模块，就记录：

1. 已整改文件
2. 仍剩余文件
3. 是否还有扫描残留

### 6.3 验证法

至少要验证：

1. 中文环境
2. 英文环境
3. 语言切换后无需刷新即可更新的页面
4. 刷新后语言保持

## 8. 验收标准

1. `设置 -> 设置 -> 语言` 切换后，用户态主要页面文本能同步变化
2. 刷新页面后语言保持
3. 用户态主页面、设置、登录、注册、连接器、预览、运行反馈等区域不再存在明显硬编码中文/英文遗漏
4. toast、placeholder、aria-label、空态、按钮文案都已进入 i18n 管理
5. 仓库复扫后，仅允许保留：
   - 注释
   - 测试数据
   - 非用户态内容
   - 明确属于业务数据而非界面文案的文本

## 9. 风险与边界

### 9.1 风险

1. `Home.tsx`、`ConnectorCenterPanel.tsx`、`OpencodePreviewPanel.tsx` 体量较大，改动面会比较宽
2. 部分文案混在 mock data 或说明性结构里，迁移时容易把“业务示例”与“界面文案”混在一起
3. 如果词条命名无约束，后续会继续膨胀成难维护结构

### 9.2 边界

1. 后端直接返回的中文错误信息，本轮只做“前端包装层可控部分”的国际化
2. 管理后台不在这轮范围
3. 测试、注释、文档中的语言不在本轮强制整改范围

## 10. 本轮预期产出

代码文件：

1. `apps/web/client/src/i18n.ts`
2. `apps/web/client/src/locales/zh.json`
3. `apps/web/client/src/locales/en.json`
4. 用户态各页面与组件中涉及硬编码文案的文件

验证产出：

1. 类型检查
2. 关键用户路径手动验证
3. 多语言遗漏复扫结果

## 11. 当前结论

这不是“给设置页补一个语言选择器”的任务，而是：

> 以设置页语言入口为开关，完成 oneceo 用户态前端的全量国际化收敛。

只有按这个范围执行，才能保证“设置 - 设置”的语言功能是真实可用，而不是局部演示状态。
