# 20260426 E2B 生命周期约束下的 Sandbox 工作区防丢失更改指引 [20260427-0006已采用]

## 1. 文档目的

本指引用于修复 OneCEO 当前 Sandbox 工作区在恢复、切换、调试、executor 变更时可能丢失文件的问题。

本次不从“调试页面访问失败”入手做补丁，而是从 E2B Sandbox 生命周期限制出发，重新明确 OneCEO 应承担的工作区持久化边界，并给出代码修改指引。

## 2. E2B 能力边界

依据 `docs/e2b文档索引.html` 对应的 E2B 官方文档，当前应按以下边界理解 E2B：

1. Sandbox filesystem 是单个 sandbox 的隔离文件系统，不是平台级永久文件存储。
2. Running sandbox 有连续运行上限，不能假设一个 sandbox 会长期存在。
3. `pause/resume` 可以保留同一个 sandbox 的 filesystem、memory、process state，但这属于同 sandbox 生命周期能力，不等于 OneCEO 的业务归档。
4. `kill` 是终态，sandbox 被释放后不能恢复其中数据。
5. snapshot 可以生成运行态检查点，但会临时暂停 sandbox 并断开连接，更适合作为 E2B 层检查点，不适合作为 OneCEO 唯一业务真相源。
6. Volumes 是独立于 sandbox 生命周期的持久化方向，但当前 E2B 文档标注为 private beta，不能作为 OneCEO 主链强依赖。
7. 文件读写、上传、下载 API 只保证当前 sandbox 内的文件操作，不自动保证新 sandbox 能继承旧 sandbox 文件。

因此 OneCEO 的长期原则是：

> E2B 是运行容器，R2 + manifest + DB binding 才是 OneCEO 工作区真相源。

## 3. OneCEO 当前使用现状

当前 OneCEO 同一个 task session 可能被多个链路访问或切换 sandbox：

1. Altus managed run 创建、复用、恢复 sandbox。
2. OpenCode / Codex / Altus executor 可能因执行器不同进入不同模板或不同 runtime。
3. 调试链路启动 n.eko / browser / app server。
4. 附件上传、skills、MCP、连接器恢复依赖 session 级 workspace。
5. 后台 archive job 会在 idle/timeout 前窗口尝试归档 dirty workspace。
6. `taskCreationFileMemoryStore.runtime` 与 `task_session_sandbox_bindings` 都会记录 sandbox 运行时信息。
7. R2 archive 当前用于 workspace 冷存储，但 restore miss 在部分场景下不会阻断新 sandbox 使用。

这导致当前风险不是单点 bug，而是生命周期协议不完整。

## 4. 已确认的问题形态

典型失败链路如下：

1. sandbox A 里已经生成用户文件，例如网页源码、附件、session memory。
2. sandbox A 被标记 dirty，但还没有完成 R2 强归档。
3. 后续因为 executor、template、debug、binding 或 runtime 信息变化，新建了 sandbox B。
4. sandbox B 执行 `workspace_restore`，但 R2 没有可用归档。
5. restore 返回 false，provision 链路继续执行。
6. sandbox B 被写成当前 runtime/binding。
7. 调试页面连接到 sandbox B，但里面没有用户页面文件或服务，最终出现 `127.0.0.1:8000 refused` 等现象。

这里的真实故障是：

> 工作区来源还没完成交接，新 sandbox 已经成为当前 canonical sandbox。

## 5. 当前代码风险点

### 5.1 executor 不一致时没有迁移来源

位置：

- `apps/api/src/services/sandbox-agent-provision-service.ts`
- `resolveReusableSandbox(...)`

当前逻辑中，如果 file-memory 里的 executor 与本次 executor 不一致，会直接返回不可复用，且不返回旧 sandbox 作为迁移来源。

风险：

1. 旧 sandbox 仍然可能有最新文件。
2. 新 sandbox 会被创建。
3. 如果旧 sandbox 未归档，新 sandbox 无法恢复文件。

补充约束：

当前 `provisionWithLock(...)` 的锁粒度是 `taskSessionId:executor`。这会导致同一个 task session 在 executor 切换时仍可能并发进入两条 provision 链路。工作区生命周期锁必须提升为 session 级，至少覆盖 handoff、archive、restore、binding update 四个步骤。

### 5.2 只有 template migration 会强归档

位置：

- `apps/api/src/services/sandbox-agent-provision-service.ts`
- `archive_before_template_migration`

当前只在 template mismatch 时触发迁移前归档。

风险：

1. executor 切换不会强归档。
2. binding 切换不会强归档。
3. debug 恢复不会强归档。
4. runtime 指针被新 sandbox 覆盖前没有强交接。

### 5.3 restore miss 默认太宽松

位置：

- `apps/api/src/services/sandbox-archive-service.ts`
- `restoreWorkspaceIfArchived(...)`

当前找不到 R2 restore key 时直接返回 `false`。

风险：

1. 对全新 session，restore miss 是正常的。
2. 但对已有 dirty workspace 的 session，restore miss 应该是故障。
3. 当前调用方无法稳定区分“无历史文件”和“应该恢复但缺失归档”。

### 5.4 archive job 是最佳努力，不是生命周期屏障

位置：

- `apps/api/src/services/sandbox-archive-job.ts`

当前 archive job 根据 idle/timeout 时间窗口归档。

风险：

1. 用户刚生成文件后立即启动调试或切换 executor，后台 job 可能还没来得及归档。
2. 不能把 idle job 当作 sandbox rebind 前的数据安全屏障。

### 5.5 close 前归档失败不能静默继续

位置：

- `apps/api/src/services/sandbox-environment-service.ts`
- `closeEnvironment(...)`

当前 close 链路会在关闭前尝试 `archiveSandboxWorkspace(..., { forceUpload: true })`，但归档失败后只是记录 metadata 和日志，后续仍可能继续关闭 sandbox。

风险：

1. 对全新、无用户文件、无 dirty 的 sandbox，关闭失败归档可以降级。
2. 但对已有 dirty workspace 或已有历史文件预期的 sandbox，归档失败后继续关闭会违反“文件不能丢失”的主目标。
3. close 链路必须接入同一套 workspace handoff/fail-closed 规则。

### 5.6 runtime/binding 状态源仍可能分裂

涉及：

- `taskCreationFileMemoryStore.runtime`
- `task_session_sandbox_bindings`
- `sandbox_execution_environments.metadata`

风险：

1. 附件、skills、Altus managed、debug 可能读到不同的 sandbox 指针。
2. 旧文档已经修过附件跨 sandbox 问题，但当前 executor/debug/rebind 场景仍需要统一生命周期协议。

### 5.7 archive 存储不可用时必须显式降级为阻断

位置：

- `apps/api/src/services/sandbox-archive-service.ts`
- `isArchiveEnabled()`
- `isArchiveStorageConfigured()`

当前 archive/restore 在开关未启用或 R2 未配置时会返回失败或 false。

风险：

1. 如果 session 没有历史 workspace，允许继续创建空 sandbox。
2. 如果 session 已经存在 dirty workspace 或历史归档预期，archive 存储不可用必须阻断生命周期切换。
3. 不能在 R2 不可用时继续 rebind 到新 sandbox。

## 6. 目标状态

本次修改后应达到：

1. 同一个 task session 的用户 workspace 文件不会因为 sandbox 新建、切换、恢复、调试而静默丢失。
2. 任何新 sandbox 成为 canonical binding 前，必须完成旧 workspace 的归档、恢复和校验。
3. restore miss 在有历史 workspace 预期时必须阻断，而不是继续使用空 workspace。
4. 后台 idle archive 只作为成本优化和兜底，不作为强一致保障。
5. E2B pause/resume、snapshot、volume 都不替代 OneCEO 自己的 R2 manifest 归档。

## 7. 非目标

本次不做：

1. 不把 E2B Volume 接入主链。
2. 不把 snapshot 作为唯一恢复方式。
3. 不重构整个 Altus runner。
4. 不改变 OSAC 主通信边界。
5. 不解决 n.eko UI 本身的体验问题。
6. 不把 debug URL 选择作为主修复方向。

## 8. 核心设计原则

### 8.1 工作区来源层级

OneCEO 工作区来源需要拆成“长期真相源”和“运行态抢救来源”两层，避免把 live sandbox 误当成永久存储：

1. R2 archive + manifest：长期真相源。
2. 当前 canonical sandbox：运行态投影，可能包含尚未归档的最新 delta。
3. dirty old sandbox：抢救来源，只用于补齐 R2 归档，不作为长期真相源。
4. E2B pause/snapshot：E2B 层辅助能力，不能替代 OneCEO 归档。

### 8.2 canonical binding 后置

任何新 sandbox 不得在以下条件满足前写成当前 canonical binding：

1. 已识别旧 workspace source。
2. 如旧 workspace dirty，已完成强归档。
3. 新 sandbox 已完成 restore。
4. restore 后 manifest 校验通过。
5. 必要 workspace layout 和 state root 已确认。

例外：

1. 对 `restoreRequired=false` 的全新 session，不要求 restore，但必须完成 workspace layout 校验后才能写 binding。
2. 对复用中的当前 canonical sandbox，不要求 restore，但必须通过 workspace readiness 检查。

### 8.3 restore fail-closed

restore 结果需要区分三类：

1. `not_required`：全新 session，无历史 workspace 预期。
2. `restored`：已从 R2 或指定 snapshot key 恢复。
3. `missing_required_archive`：存在历史 workspace 预期，但 R2 缺失且没有可抢救 source。

只有前两类允许继续 provision。

### 8.4 旧 sandbox 优先作为救援来源

当 R2 archive 缺失时，如果发现同 task session 下仍有 ready/dirty 旧 sandbox，必须先从旧 sandbox backfill archive，再恢复到新 sandbox。

### 8.5 session 级生命周期锁

同一个 task session 的以下操作必须串行：

1. provision。
2. archive。
3. restore。
4. close。
5. debug readiness 修复。
6. runtime/binding update。

锁 key 应以 `taskSessionId` 为主，而不是 `taskSessionId:executor`。executor 是切换原因，不应成为绕开生命周期锁的维度。

## 9. 建议状态模型

为工作区生命周期引入显式状态，不再只靠 `archiveDirty` 和 `pendingArchiveUpdate`：

1. `active_clean`：当前 sandbox 与 R2 archive 一致。
2. `active_dirty`：当前 sandbox 有未归档变更。
3. `archiving`：正在上传 R2 archive。
4. `archived`：R2 archive 已完成并有 manifest。
5. `handoff_required`：将发生 sandbox 切换，必须交接。
6. `restoring`：新 sandbox 正在恢复。
7. `restored_verified`：恢复并校验通过。
8. `handoff_blocked`：缺少必需 archive 或 source，不允许切换。

这些状态可以先落在 `sandbox_execution_environments.metadata`，后续再根据复杂度决定是否独立表化。

## 10. 修改指引

### 10.1 调整生命周期锁粒度

位置：

- `apps/api/src/services/sandbox-agent-provision-service.ts`
- `provisionWithLock(...)`

修改方向：

1. 将涉及 `taskSessionId` 的 provision 锁从 `taskSessionId:executor` 收敛为 `taskSessionId`。
2. 如果担心同一 session 下不同 executor 的只读探测被阻塞，可以后续再细化读写锁，但第一阶段不要引入。
3. 该锁必须覆盖 source discovery、handoff archive、new sandbox restore、binding update。

验收点：

1. 同一 session 同时触发 Altus/debug/opencode provision 时，只允许一个生命周期切换链路生效。
2. 后到的 provision 必须复用前一个链路完成后的 canonical sandbox 或重新从最新状态计算。

### 10.2 扩展 reusable resolution 返回值

位置：

- `apps/api/src/services/sandbox-agent-provision-service.ts`

将 `resolveReusableSandbox(...)` 的结果从当前：

```ts
{
  reusable,
  templateMismatchSandboxId
}
```

扩展为：

```ts
{
  reusable,
  handoffSourceSandboxId,
  handoffReason,
  restoreRequired
}
```

其中：

1. executor mismatch 时，`handoffSourceSandboxId` 应指向旧 sandbox。
2. template mismatch 时，仍指向旧 sandbox。
3. runtime/binding 指针不一致时，也应选出最可信 source。
4. 没有历史 workspace 的全新 session，`restoreRequired=false`。
5. archive 存储未启用但 `restoreRequired=true` 时，应返回可阻断的 handoff 状态，而不是继续创建新 sandbox。

### 10.3 新增生命周期 handoff barrier

位置：

- `apps/api/src/services/sandbox-agent-provision-service.ts`
- `apps/api/src/services/sandbox-environment-service.ts`

在 `open_environment` 前、dirty sandbox `closeEnvironment(...)` 前增加统一步骤：

```text
workspace_handoff_prepare
```

职责：

1. 根据 `handoffSourceSandboxId` 判断是否需要迁移。
2. 如果 source dirty 或没有最新 archive，执行 `archiveSandboxWorkspace(source, reason, { forceUpload: true })`。
3. 记录 `preferredRestoreSnapshotKey`。
4. 如果 source 不可读但历史 workspace 必须存在，进入 `handoff_blocked`。
5. 如果 archive 存储不可用且历史 workspace 必须存在，进入 `handoff_blocked`。

该步骤应覆盖：

1. template mismatch。
2. executor mismatch。
3. canonical binding 切换。
4. debug/provision 触发的新 sandbox。
5. close 前 dirty workspace 保护。

### 10.4 修改 restore API 的输入与返回结构

位置：

- `apps/api/src/services/sandbox-archive-service.ts`

将 `restoreWorkspaceIfArchived(...)` 从 `Promise<boolean>` 改为结构化结果：

```ts
type RestoreWorkspaceOptions = {
  snapshotKey?: string;
  taskSessionId?: string;
  restoreRequired?: boolean;
  expectedSourceSandboxId?: string;
  reason?: string;
};

type RestoreWorkspaceResult =
  | { status: 'not_required' }
  | { status: 'restored'; archiveKey: string; manifest?: ArchiveManifest }
  | { status: 'missing_required_archive'; reason: string };
```

规则：

1. `restoreRequired=false` 且没有任何 archive candidate 时，返回 `not_required`。
2. `restoreRequired=true` 且没有 archive candidate 时，返回 `missing_required_archive`。
3. `snapshotKey` 存在时必须优先使用该 key；如果该 key 缺失，不能静默回退到空 workspace。
4. `expectedSourceSandboxId` 用于校验 manifest 来源，避免恢复错 session 或错 sandbox 的归档。

### 10.5 增加 manifest 校验

归档时 manifest 至少写入：

1. `taskSessionId`
2. `sourceSandboxId`
3. `workspaceRoot`
4. `stateRoot`
5. `executor`
6. `template`
7. `generation`
8. `fileCount`
9. `totalSizeBytes`
10. `archiveSha256`
11. `workspaceTreeHash`
12. `archiveReason`
13. `createdAt`
14. `archiveStorageStatus`
15. `dirtySequence`

说明：

1. 当前代码里的 `sha256` 是 tar archive 的 hash，只能证明 R2 对象未被篡改，不能单独证明恢复后的文件树完整。
2. 如果第一阶段不实现完整 `workspaceTreeHash`，至少需要写入并校验 `fileCount`、`totalSizeBytes`、关键 sentinel 文件列表。
3. 对网站交付类任务，sentinel 文件至少包括 `index.html` 或 manifest 中记录的入口文件。

恢复后至少校验：

1. workspace root 存在。
2. state root 存在。
3. manifest 中 `taskSessionId` 与当前 session 一致。
4. manifest 中 `sourceSandboxId` 与 handoff source 一致，或者明确允许从 session 最新 archive 恢复。
5. 文件数量不低于 manifest 记录。
6. 关键 sentinel 文件存在。
7. 如果有 `workspaceTreeHash`，校验 hash 一致。

### 10.6 canonical binding 更新后置

位置：

- `sandbox-agent-provision-service.ts`
- 任何写 `taskCreationFileMemoryStore.updateRuntimeBinding(...)` 的路径
- 任何写 `task_session_sandbox_bindings` 的路径

规则：

1. 新 sandbox 创建成功不等于可绑定。
2. `restoreRequired=true` 时，必须 `workspace_restore` 成功且校验通过后才允许写 binding。
3. `restoreRequired=false` 的全新 session，必须 workspace layout 校验通过后才允许写 binding。
4. 复用当前 canonical sandbox 时，必须 workspace readiness 检查通过后才允许继续沿用 binding。
5. 如果 restore 失败，不能覆盖旧 binding。
6. 旧 binding 应保留，状态标记为 `handoff_blocked` 或 `restore_failed`。
7. `altus-managed-setup-service.ts` 中 provision 返回后的 `upsertSandboxBinding(...)` 和 `updateRuntimeBinding(...)` 也必须依赖 provision 返回的 workspace 状态，不能无条件写入。

### 10.7 close 前归档失败阻断

位置：

- `apps/api/src/services/sandbox-environment-service.ts`

规则：

1. close 前如果 sandbox 是 dirty 或存在历史 workspace 预期，归档失败必须阻断 close。
2. 对无 taskSessionId、无 dirty、无归档预期的临时 sandbox，可以保留当前降级行为。
3. close 失败应返回明确错误，例如 `workspace_archive_required_before_close_failed`。
4. 管理端手动强制关闭如需绕过，必须显式记录为 destructive override，不作为普通用户链路默认行为。

### 10.8 Altus managed run 完成后立即归档

位置：

- Altus managed run completion 链路
- `altus-managed-tool-runtime.ts` 的 dirty 标记链路

规则：

1. run 过程中可以 debounce dirty archive。
2. run 结束时，只要 `archiveDirty=true`，必须触发轻量强归档。
3. 归档失败不应伪装成功，应在 run event 或 debug log 中明确暴露。

### 10.9 debug 启动前做 workspace readiness 检查

位置：

- `sandbox-debug-service.ts`

调试不是迁移来源，但调试前需要检查：

1. 当前 sandbox 是否是 canonical binding。
2. workspace 是否存在 manifest 或最小文件结构。
3. 如果当前 sandbox 是新建且 restore 未完成，应先触发 restore 或阻断 debug。
4. debug 不应该因为 URL fallback 掩盖 workspace 丢失。

### 10.10 保留旧 sandbox 到交接完成

规则：

1. 新 sandbox `restored_verified` 前，不 kill 旧 sandbox。
2. 新 sandbox 成功成为 canonical 后，旧 sandbox 标记为 `superseded_archived`。
3. 旧 sandbox 可由后台清理，但清理前必须确认已有 R2 archive。

## 11. 恢复来源选择策略

恢复来源选择顺序：

1. 当前 `task_session_sandbox_bindings` 指向的 sandbox。
2. `taskCreationFileMemoryStore.runtime.orchestratorSessionId`。
3. `sandbox_execution_environments` 中同 `taskSessionId` 且 `archiveDirty=true` 的 ready sandbox。
4. 同 `taskSessionId` 的最近 active sandbox。
5. R2 最新 archive manifest。

说明：

1. 前 4 项是 live sandbox source，用于抢救和补齐 archive。
2. 第 5 项是冷存储 source，用于没有 live sandbox 可用时恢复。
3. live source 一旦被选中，目标不是长期依赖它，而是先强归档成 R2 archive，再从 archive 恢复或继续复用。

如果 1、2 指向不同 sandbox：

1. 优先选择 dirty 且 lastActive 更新的 sandbox 作为 source。
2. 将另一个 sandbox 记录为 conflict candidate。
3. 不允许在未归档 source 的情况下直接覆盖 canonical binding。

如果没有 live source，但存在 R2 session archive：

1. 允许从 `sessions/<taskSessionId>/workspace.tar.gz` 恢复。
2. 必须校验 `sessions/<taskSessionId>/metadata.json`。
3. 如果 metadata 缺失但 archive 存在，第一阶段可以允许恢复，但必须标记 `manifest_missing_recovered_from_archive`，后续补写 manifest。

## 12. 验收条件

### 12.1 executor 切换不丢文件

步骤：

1. Altus managed run 生成 `index.html`、`style.css`、`script.js`。
2. 确认 sandbox dirty。
3. 触发另一个 executor 或模板切换。
4. 新 sandbox 创建后检查 workspace。

预期：

1. 新 sandbox 有完整文件。
2. R2 有最新 archive 和 manifest。
3. binding 指向新 sandbox。
4. 旧 sandbox 不会在归档前被释放。

### 12.2 restore 缺失时阻断

步骤：

1. 构造有历史 dirty workspace 的 session。
2. 删除或模拟缺失 R2 archive。
3. 触发新 sandbox provision。

预期：

1. provision 进入 `handoff_blocked`。
2. 不覆盖旧 binding。
3. 前端/事件显示明确恢复失败原因。
4. 不出现空 workspace 被当成成功环境。

### 12.3 旧 sandbox 可抢救时自动 backfill

步骤：

1. session 有 ready dirty 旧 sandbox。
2. R2 archive 缺失。
3. 触发新 sandbox provision。

预期：

1. 系统从旧 sandbox 强归档到 R2。
2. 新 sandbox 从该 archive 恢复。
3. manifest 校验通过后再切换 binding。

### 12.4 debug 不掩盖 workspace 丢失

步骤：

1. 使用有交付物的 session 打开调试。
2. 强制当前 runtime 指向一个未恢复的新 sandbox。

预期：

1. debug 启动前检测 workspace readiness。
2. 若可恢复，则先恢复再打开 debug。
3. 若不可恢复，则明确报 `workspace_restore_missing_source`。
4. 不再只表现为浏览器里的 `ERR_CONNECTION_REFUSED`。

### 12.5 idle archive 不再是唯一保障

步骤：

1. 文件写入后立即触发 sandbox 切换，不等待 idle job。

预期：

1. 切换前仍会强归档。
2. 新 sandbox 恢复成功。
3. idle job 只作为后续补充，不影响主链正确性。

### 12.6 close 不会丢 dirty workspace

步骤：

1. 构造一个已有 `taskSessionId` 且 `archiveDirty=true` 的 sandbox。
2. 模拟 R2 不可用或 archive 失败。
3. 触发普通 close。

预期：

1. close 被阻断。
2. sandbox 不进入不可恢复的 kill/closed 终态。
3. metadata 记录 `workspace_archive_required_before_close_failed` 或等价错误。
4. 管理端如需强制关闭，必须走显式 destructive override。

## 13. 测试建议

### 13.1 单元测试

覆盖：

1. `resolveReusableSandbox` executor mismatch 返回 handoff source。
2. template mismatch 返回 handoff source。
3. dirty source archive 成功后生成 restore key。
4. restoreRequired=true 但 archive missing 时失败。
5. restoreRequired=false 且无历史时允许继续。
6. session 级锁阻止同 session 不同 executor 并发 handoff。
7. close dirty sandbox 时 archive 失败会阻断关闭。

### 13.2 集成测试

覆盖：

1. Altus run 写文件 -> re-provision -> 文件仍在。
2. 附件上传 -> Altus run -> debug -> 文件仍在。
3. file-memory 与 sandbox binding 不一致时自动选择正确 source。
4. R2 archive manifest 缺失时阻断。

### 13.3 浏览器链路测试

覆盖：

1. 创建网页交付任务。
2. 打开 session history。
3. 启动调试。
4. 调试浏览器内能访问实际页面。
5. 切换/恢复后再次打开调试仍能访问页面。

## 14. 实施顺序

建议分五步实现：

1. 先改 source discovery 和 handoff result，不改变 archive 逻辑。
2. 再加生命周期 handoff barrier，覆盖 provision 和 close。
3. 再把 restore 返回值结构化并 fail-closed。
4. 再加 manifest 校验和 binding 后置。
5. 最后补 Altus completion archive 与 debug readiness check。

每一步都需要单独验证，避免一次性大改导致无法定位回归。
