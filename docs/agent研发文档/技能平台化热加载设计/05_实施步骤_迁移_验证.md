# 05 实施步骤、迁移与验证

## 1. 实施顺序

按最短路径分六步。

### 第 1 步：数据库与 API

新增：

1. `platform_skills`
2. `platform_skill_revisions`
3. DAO、service、route
4. skill 种子数据迁移

产出结果：

1. 主平台 API 可以列出技能
2. 管理后台代理层有稳定数据源

### 第 2 步：管理后台技能管理页

改造：

1. `apps/admin_management/server`
2. `apps/admin_management/web`
3. 技能列表、编辑、revision 预览、sandbox 验证页面

产出结果：

1. 管理员可以在后台动态新增 skill
2. 管理员可以发布 revision、归档/启用 skill
3. 后台可对已发布 revision 做 session 级 sandbox 验证

### 第 3 步：前端 skill picker API 化

改造：

1. `AttachmentPickerButton.tsx`
2. `task-attachments.ts`
3. `Home.tsx`
4. `TaskCreationChat.tsx`
5. `useTaskCreationAgent.ts`

产出结果：

1. 前端不再依赖 `SKILL_ATTACHMENT_TEMPLATES`
2. 发送链路只传 skill 引用

### 第 4 步：sandbox skill sync

新增：

1. `sandbox-skill-sync-service.ts`
2. skill 渲染与目录管理
3. runtime metadata signature 记录

产出结果：

1. sandbox 能拿到当前消息对应的真实 skill
2. skill 变更时能够热更新

### 第 5 步：接入 managed/direct 主链路

改造：

1. `altus-managed-input-service.ts`
2. direct mode prompt dispatch 主链路
3. `osac-agent-service.ts`

产出结果：

1. managed 与 direct 行为一致
2. skill 不再依赖 prompt inline

### 第 6 步：删除旧实现

移除：

1. `apps/web/client/src/lib/skill-attachment-templates.ts`
2. `inline-skill:*`
3. `appendAttachmentsToPrompt()` 中的 skill 注入逻辑
4. skill 伪文件打标逻辑

这一步必须做，不保留双轨。

## 2. 迁移原则

迁移期间遵守以下原则：

1. 先把内置 skill 写入数据库作为 seed
2. 再切前端读取源
3. 最后删除静态文件实现

不允许出现：

1. 前端一部分读静态模板，一部分读数据库
2. managed 走数据库，direct 还走 inline

## 3. 验证项

### 3.1 后端验证

1. skill CRUD 接口可用
2. revision 发布后旧 revision 仍可查询
3. sandbox sync diff 正确
4. skill signature 未变化时不会重启 runtime
5. 管理后台验证接口只能访问已发布 revision

### 3.2 管理后台验证

1. 技能列表可按 `query / status / category` 过滤
2. 编辑页保存后立即出现新的 published revision
3. 归档 skill 后不再出现在业务前端 picker
4. sandbox 验证页能看到同步结果和失败原因

### 3.3 前端验证

1. picker 能展示后台新增 skill
2. 选择 skill 后消息 metadata 只包含 skill 引用
3. 发送 skill-only 消息时不再生成伪文件

### 3.4 端到端验证

至少覆盖以下场景：

1. 后台新增一个新 skill，用户端无需发版即可看到
2. 选择 skill 后启动 run，sandbox 中存在对应 `SKILL.md`
3. 同一 session 下一条消息换 skill，sandbox 中 skill 集合正确更新
4. sandbox 恢复后再次运行，仍能恢复对应 revision 的 skill
5. 管理员发布 skill 新 revision，不影响已经发送过的旧消息

## 4. 需要新增的测试

建议最少补四类测试：

1. `platform-skill-service` 单测
2. `sandbox-skill-sync-service` 单测
3. `apps/admin_management` 技能管理代理层接口测试
4. 一个真实 E2B smoke test

smoke test 要验证的不是“文件写进去了”，而是：

1. OpenCode 能发现该 skill
2. 当前 run 使用的是本次消息绑定的 revision
3. 管理后台触发的验证链路与正式运行链路使用的是同一套 sync service

## 5. 结论

这次改造的核心不是把 `skill-attachment-templates.ts` 搬到后端，而是把 oneceo 的 skill 从“前端静态 prompt 文案”升级成“平台注册、后台发布、sandbox 原生加载的运行时能力”。

只有这样，后续新增 skill 才能真正做到：

1. 后台动态添加
2. 用户端自动可见
3. sandbox 内真实可用
4. 不再依赖前端硬编码文件
