# 2026-04-05 admin_management 控制台整站重构方案 [20260405-2329已采用]

## 1. 背景与目标

本次需求明确指向 `apps/admin_management` 整站 UI 重构，不是单页美化。重构范围同时覆盖：

- 一级导航结构
- 页面级信息架构
- 主工作区与详情区的交互组织
- 组件层级与前端文件组织
- 统一视觉语言

当前实现事实：

- 管理后台当前共有 8 个一级模块：`KVM 管理`、`对话管理`、`智能体管理`、`技能管理`、`连接器 Guide`、`OSAC 版本`、`Sandbox 管理`、`审计日志`
- 主体编排仍然集中在 `apps/admin_management/web/src/App.tsx`
- 样式主入口集中在 `apps/admin_management/web/src/styles.css`
- `SkillManagementSection`、`ConnectorGuideManagementSection`、`OsacReleaseManagementSection` 已有独立业务组件，但整体页面骨架和视觉系统仍未统一
- 登录页已有本地未提交视觉调整，本轮实现需要在此基础上统一，不应直接覆盖

本次重构目标不是补丁式修样式，而是把管理后台收敛成一套可持续演进的“平台治理控制台”。

## 2. 本轮范围

本轮只改前端 Web，不改后端接口语义，不新增业务能力，不做新旧视觉双轨并存。

覆盖页面：

1. `KVM 管理`
2. `对话管理`
3. `智能体管理`
4. `技能管理`
5. `连接器 Guide`
6. `OSAC 版本`
7. `Sandbox 管理`
8. `审计日志`

## 3. 问题归纳

### 3.1 全局层面

- 一级导航为单层平铺，模块间缺少治理域分组，用户进入后只能按名称猜测入口
- 顶部头部信息稳定性不够，页面上下文、服务状态、刷新动作、管理员信息虽然都存在，但没有形成固定的层级模板
- 当前页面大量复用相似的“hero + 卡片 + 表格”结构，复杂页与简单页视觉差异不足
- `App.tsx` 内部承载了过多页面渲染、状态和布局细节，后续继续改 UI 的边际成本过高

### 3.2 复杂页面层面

- `对话管理` 目前是“左侧会话列表 + 右侧超长详情流”，状态流转、消息、LLM、Sandbox、OSAC 全部纵向堆叠，排查成本高
- `Sandbox 管理` 已经具备比较多功能，但总览、运行实例、模板治理、详情 inspector、低频调试动作仍然混在同一感知层级
- `KVM 管理` 先展示宿主机，再展示 KPI，再展示图表，再展示 VM 表格，阅读顺序和操作顺序并不完全一致

### 3.3 治理类页面层面

- `技能管理`、`连接器 Guide`、`OSAC 版本` 都属于“治理工作台”，但当前视觉和交互组织还没有统一成同一种 master-detail 工作模式
- `智能体管理` 和 `审计日志` 信息量相对轻，但仍沿用偏重的版式，导致简单页面不够利落

## 4. 设计方向

本轮采用统一的视觉方向：`Editorial Ops Console`。

核心特征：

- 不是通用 CRM 卡片后台，而是带“值班台 / 治理台”气质的控制台
- 主界面采用浅底纸面感内容区，配深色导航轨道和高对比信号色
- 标题、分区、状态、元信息之间建立明确层级，强化“先看信号，再进工作区，再看细节”
- 大量使用稳态边界、标签带、分区标题和 inspector 结构，而不是继续靠同质化卡片堆页面

视觉关键词：

- 深墨侧栏
- 冷白工作台
- 青绿主动作
- 钴蓝信息强调
- 琥珀告警
- 红色危险动作
- 等宽元信息 + 更收敛的无衬线正文

## 5. 一级信息架构重排

一级导航不新增业务页面，但调整为“分组导航”：

### 5.1 运行治理

- `KVM 管理`
- `对话管理`
- `Sandbox 管理`
- `审计日志`

这组页面服务于运行态观测、排障、回溯。

### 5.2 平台配置

- `智能体管理`
- `技能管理`
- `连接器 Guide`
- `OSAC 版本`

这组页面服务于能力发布、策略治理和工件发布。

### 5.3 导航交互规则

- 左侧导航改为“分组标题 + 导航块”而不是纯按钮长列表
- 当前激活项保留明显激活条，但要额外展示所在分组
- 侧栏底部固定管理员信息与退出动作，减少顶部头部负担

## 6. 统一页面骨架

所有一级页面统一为四层骨架：

1. `Shell 层`
   - 左侧分组导航
   - 顶部全局状态条
2. `Page Header 层`
   - 页面归属
   - 标题与一句话说明
   - 服务状态
   - 刷新动作
   - 页面级辅助动作
3. `Summary Strip 层`
   - 只放摘要指标、当前值守重点或关键状态卡
4. `Workspace 层`
   - 根据页面类型切换为 master-detail、双栏排障、或 inspector 模式

规则：

- 摘要卡不承载复杂表单
- 筛选、列表、时间线、详情 inspector 各自占独立层级
- 复杂页面优先“横向分区”，避免所有内容继续纵向拉长

## 7. 页面级重构方案

### 7.1 KVM 管理

目标：先看资源风险，再进入实例操作。

改为：

1. 顶部摘要条
   - 宿主机数
   - 运行 VM
   - 异常 VM
   - 编排器状态
2. 主工作区双栏
   - 左侧：宿主机舰队视图
   - 右侧：风险提示与容量热点
3. 次级区域
   - VM 列表
   - 控制中心

关键调整：

- 宿主机卡片重构为“标题区 / 容量区 / 心跳区 / 趋势区”
- `KvmControlCenter` 不再像独立模块悬浮在页面尾部，而是被纳入统一操作面板语义
- VM 表格的操作区与状态区要明显分离

### 7.2 对话管理

目标：把“会话排查”从长页面改成工作台。

改为三栏排障布局：

1. 左栏：会话索引列
2. 中栏：会话主工作区
   - 摘要
   - 状态流转
   - 时间线 / 消息 / LLM 调用切换
3. 右栏：运行绑定 inspector
   - OpenCode
   - KVM
   - Sandbox
   - OSAC

关键调整：

- 右栏从“附属信息堆栈”改为“当前会话运行上下文”
- 消息、时间线、LLM 不再全部同时展开，而是进入稳定 tab 分区
- 与 Sandbox、任务会话的跳转按钮统一收敛成 inspector 内的关联入口
- 下载会话详情放在页头动作，不再掺入正文主流

### 7.3 Sandbox 管理

目标：让 Sandbox 页面真正成为运行时控制台，而不是大杂烩。

保留 `overview / runtime / templates` 三个工作区，但重排为：

1. 顶部信号带
   - 总环境
   - 运行中
   - 待归档
   - 风险项
2. 工作区切换带
3. 当前工作区主体
   - `overview`：总览与高风险入口
   - `runtime`：风险聚合 + 运行实例注册表 + sticky inspector 入口
   - `templates`：模板列表与构建治理
4. 详情层
   - Runtime inspector 使用全高详情面板
   - 手工创建 Runtime 保持抽屉

关键调整：

- 低频调试工具必须完全放入 detail inspector 或高级调试页，不占用主工作区
- Runtime 列表和风险聚合要形成“先筛选风险，再选中实例”的路径
- 模板治理和运行实例治理不再共享同一视觉语义
- `paused` 状态单独展示，便于区分“暂停但不计费”的 Sandbox
- Runtime inspector 详情页签收敛为 `摘要 / 连通性 / 归档 / 高级调试` 四个主页签，不再保留 `指标` 页签入口

### 7.4 技能管理

目标：收敛成标准治理工作台。

布局：

1. 顶部治理摘要
2. 筛选条
3. 左侧 skill 列表
4. 右侧编辑与 revision 工作区

关键调整：

- 现有业务逻辑保留，但视觉上统一为“治理台”而不是普通表单页
- revision、resources、validation 统一使用工作区标签卡
- 文件夹导入、创建 skill 等动作放在固定工具栏区域

### 7.5 连接器 Guide

目标：与技能管理形成同类治理体验，但突出 policy / revision / publish 流。

布局：

1. Guide 策略摘要
2. 过滤与创建动作
3. 左侧 policy 列表
4. 右侧 revision 编辑器与校验结果

关键调整：

- policy 与 revision 的关系要一眼可见
- 校验结果区不能只作为普通结果框，而要成为独立状态面板

### 7.6 OSAC 版本

目标：强化“上传不等于发布”的治理心智。

布局：

1. 顶部当前发布摘要
2. 发布规则提示
3. 左侧版本列表
4. 右侧详情 / 发布 / 回滚 / 上传工作区

关键调整：

- `published / pending / all / upload` 不再只是简单切换按钮，而是作为明确的工作模式标签
- 当前已发布版本要在详情区内持续可见

### 7.7 智能体管理

目标：做成轻量但可信的能力总览页。

布局：

1. 服务状态摘要
2. 能力分布
3. 任务创建状态补充

关键调整：

- 该页不需要过重的多层卡片，应更短、更清晰
- 能力卡、服务状态卡、阶段图表三类信息必须有视觉差异

### 7.8 审计日志

目标：让成功 / 失败 / 风险操作在首屏快速分层。

布局：

1. 顶部摘要
2. 可扩展的筛选条
3. 时间序日志流

关键调整：

- 日志项采用时间轴化列表，而不是普通卡片堆叠
- 失败动作、危险动作、连续重试记录要有更强烈的边界提示

## 9. 视觉系统约束

### 9.1 字体

- 正文继续使用当前无衬线方向，但收紧字重层级
- 元信息、ID、时间、命令、标签继续使用等宽字体
- 禁止回退到通用模板化视觉

### 9.2 颜色

- 背景：冷白纸面
- 侧栏：深墨蓝灰
- 主动作：青绿
- 信息强调：钴蓝
- 告警：琥珀
- 危险：红

### 9.3 交互

- hover 与 active 反馈保持轻量，不做大位移动效
- 复杂详情采用 tab、inspector、drawer，禁止继续无限纵向堆叠
- 表格只在自身区域横向滚动，不让整个页面横滚
- 桌面端侧边栏保持 `品牌区 / 导航区 / 身份区` 三段式，其中导航区必须独立纵向滚动；鼠标停留在侧边栏任意位置时，滚轮优先驱动导航区，不允许把主页面滚动链带走
- 窄屏端（侧边栏回落到文档流后）不再劫持滚轮，恢复页面自然滚动

## 10. 实施策略

遵循最短路径实现，不做兼容性补丁方案：

1. 先完成壳层与视觉 token 收敛
2. 再拆 `App.tsx` 中的五个核心页面
3. 最后把 `技能管理`、`连接器 Guide`、`OSAC 版本` 接入统一骨架

实施时必须遵守：

- 不改接口契约
- 不引入新的大型 UI 框架
- 不保留新旧两套 UI 并行
- 不为了“兼容老结构”继续扩大 `App.tsx`

## 11. 验收标准

- 8 个一级模块全部纳入统一壳层与视觉系统
- 导航分组、页面头部、摘要区、工作区、详情区层级稳定
- `对话管理` 与 `Sandbox 管理` 的阅读和操作路径明显缩短
- `技能管理`、`连接器 Guide`、`OSAC 版本` 呈现为同类治理工作台
- `App.tsx` 不再承担超大段页面 JSX
- 中等宽度下不出现主布局崩坏

## 12. 采用结论

## 13. Sandbox 状态补充

根据后续使用反馈，`Sandbox 管理` 页面补充一条状态展示规则：

- `暂停中` 必须作为独立状态卡展示
- `暂停中` 不应并入 `运行中` 或只通过筛选器间接查看
- 顶部摘要区和总览区都要能直接看到 `paused` 数量
