# 2026-04-20 管理后台部署管理工作台二期方案 [20260420-0010已采用]

## 1. 背景

`20260419_管理后台部署管理工作台方案_[20260419-2340已采用].md` 已经把后台部署管理的一期目标定义为：

1. 新增一级 `部署管理`
2. 支持按部署 / 按对话 / 按用户查看
3. 第一阶段只读

但在你最新审核意见里，目标已经发生实质变化：

1. `用户视图` 不应该围绕“用户详情”展开，而应该直接只展示“有部署记录的用户列表”。
2. `对话视图` 不应该展示所有对话，而应该只展示“有过部署记录的对话”。
3. `部署索引` 应该覆盖所有“有过部署记录的会话”。
4. 三个视图都必须以**部署**为重心，而不是把部署当作用户或对话的附属字段。
5. 还需要继续下钻到 `Railway`，提供真正可执行的 Railway 资源视图和批量管理能力，包括删除服务、变更服务等管理动作。

因此，一期的“只读部署工作台”已经不足以承接当前需求。本方案定义二期目标：

**把部署管理从“部署结果索引页”升级为“以部署为中心的治理工作台 + Railway 资源管理工作台”。**

## 2. 目标

### 2.1 本轮明确包含

1. 重构 `部署管理` 的三大视图，使其全部改为“只展示有部署记录的对象”：
   - 部署索引：所有有过部署记录的会话
   - 对话视图：所有有过部署记录的对话
   - 用户视图：所有有过部署记录的用户
2. 三个视图的主信息密度改为**部署优先**：
   - 部署状态
   - Railway 项目 / 环境 / 服务
   - 最近部署时间
   - 最近 URL
   - 成功 / 失败 / 处理中统计
3. 在 `部署管理` 内新增第四个一级子视图：`Railway 视图`
4. Railway 视图支持真正的管理操作：
   - 批量删除服务
   - 批量变更服务运行配置
   - 批量变更服务变量
   - 批量查看 / 筛选 Railway 资源状态
5. 补齐后台内部 API 与 BFF，使管理后台可以直接拉取 Railway 资源事实，而不是只依赖 task session 快照。

### 2.2 本轮明确不包含

1. 不做新的部署供应商抽象层
2. 不支持跨供应商统一管理
3. 不做“任意 GraphQL 输入框”式的 Railway 万能控制台
4. 不引入新的独立权限系统；沿用当前 admin 管理态
5. 不在本轮把后台部署管理扩成“完整 CI/CD 平台”

## 3. 核心问题重定义

二期需求不是“继续把部署信息展示得更完整”，而是要解决下面四类真实管理问题：

1. **谁在持续部署**
   - 哪些用户、哪些会话、哪些对话最近有部署动作
2. **哪些部署有风险**
   - 最近失败、无 URL、反复 pending、Railway 服务异常
3. **Railway 资源是否失控**
   - 服务数量失控、僵尸服务、错误环境、域名挂错、服务配置漂移
4. **管理员是否能批量纠偏**
   - 删除错误服务
   - 批量变更服务运行配置
   - 批量变更服务变量

所以二期的信息架构必须从“会话索引上的部署列”升级成“部署治理中心”。

## 4. 现状事实

### 4.1 现有部署数据真值源

当前项目里部署事实并不只有 task session panel：

1. `apps/api/src/services/task-session-deployment-runtime-service.ts`
   - 提供 task session deployment panel 真值聚合
2. `apps/api/src/services/railway-deployment-service.ts`
   - 提供 Railway deployment panel 与 deploy / redeploy / rollback 能力
3. `apps/api/src/services/platform-deployment-account-service.ts`
   - 已经具备 Railway project / environment / service / domain / variable 级别的管理能力基础
4. `apps/api/src/services/railway-graphql-client.ts`
   - 已有 Railway GraphQL 通道

这说明：

1. 一期只读部署页是建立在真实后端能力上的
2. 二期增加 `Railway 视图` 是有落地基础的，不是概念设计

### 4.2 当前后台实现的不足

当前后台的 `部署管理` 实现虽然已经新增：

1. 部署索引
2. 对话视图
3. 用户视图
4. 用户详情里的部署页签
5. 对话详情里的部署摘要

但仍有四个问题：

1. 三个视图的聚焦点还不够纯粹，仍带有用户页 / 对话页的继承感
2. `用户视图` 仍偏“用户入口”，而不是“部署用户清单”
3. `对话视图` 与 `部署索引` 的边界不够清晰
4. 还没有真正对接 Railway 资源侧的列表与管理动作

## 5. 核心决策

### 5.1 三个现有视图全部改成“部署中心视图”

二期不再把三视图理解为：

1. 用户页里看部署
2. 对话页里看部署
3. 会话页里看部署

而统一改成：

1. **部署索引**
   - 主体是“所有有部署记录的会话”
2. **对话视图**
   - 主体是“所有有部署记录的对话”
3. **用户视图**
   - 主体是“所有有部署记录的用户”

三者只是聚合维度不同，但视觉和信息重心都必须围绕部署。

### 5.2 新增 `Railway 视图`，与三视图并列

在 `部署管理` 内新增四个 tab：

1. `部署索引`
2. `对话视图`
3. `用户视图`
4. `Railway 视图`

其中：

1. 前三个视图基于 task session deployment 聚合
2. 第四个视图基于 Railway project / environment / service / domain / deployment 事实

这样可以避免把 Railway 资源管理动作塞进会话详情弹窗，导致职责混乱。

### 5.3 Railway 动作不再回避，但必须分级

你已经明确要求“可以批量管理 Railway 的部署，包括删除服务、变更服务等”，因此本轮不再维持“一期只读”的限制。

但动作必须分级：

#### A 类：低风险批量动作

1. 批量打标签 / 归类
2. 批量刷新状态
3. 批量同步 deployment panel
4. 批量变更显示字段或命名

#### B 类：中风险批量动作

1. 批量修改服务名
2. 批量变更服务域名 / targetPort
3. 批量修改服务变量（受白名单限制）

#### C 类：高风险破坏动作

1. 批量删除服务
2. 批量解绑域名
3. 批量移除环境关键变量

设计上必须把 C 类动作与普通列表操作强隔离，要求：

1. 明确预检结果
2. 明确影响数量
3. 明确二次确认
4. 必须写入后台审计日志

## 6. 页面信息架构

## 6.1 一级导航

`部署管理` 继续保留为 `运行管理` 分组下一级模块，不新增新的顶层导航。

## 6.2 二级视图结构

部署管理页内统一改为四个子视图：

1. `部署索引`
2. `对话视图`
3. `用户视图`
4. `Railway 视图`

整体骨架：

1. 顶部摘要条
2. 二级 tab
3. 筛选工具栏
4. 主列表区
5. 右侧或弹层详情区
6. Railway 批量动作工具条（仅 Railway 视图出现）

## 7. 四个视图的详细定义

### 7.1 视图一：部署索引

#### 目标

展示所有**有过部署记录的会话**，作为最宽口径的部署索引。

#### 数据范围

只包含满足以下任一条件的 task session：

1. 有 deploymentId
2. 有 latestStatus
3. 有 latestUrl / latestStaticUrl
4. 有历史 deployments[]
5. Railway 资源侧已存在映射服务

#### 列表列

1. 会话
   - title
   - taskSessionId
2. 当前部署状态
   - success / failed / pending / ready
3. Railway 资源
   - project
   - environment
   - service
4. 最近发布
   - latest deploymentId
   - latest deploy time
5. 最近 URL
6. 归属
   - 用户
   - 对话状态
7. 操作
   - 打开部署详情
   - 打开 Railway 资源

#### 设计原则

这里的主语是“部署中的会话”，不是“会话里附带部署字段”。

### 7.2 视图二：对话视图

#### 目标

只展示**有过部署记录的对话**，用于从对话维度排查部署行为。

#### 数据范围

仅包含存在部署记录的对话，不显示纯对话但从未部署的会话。

#### 列表列

1. 对话标题
2. 最近部署状态
3. 最近 Railway 服务
4. 最近 URL
5. 发布次数
6. 最近失败时间 / 原因
7. 操作

#### 重心要求

这里虽然叫“对话视图”，但第一视觉层必须仍然是部署结果：

1. 部署状态优先于会话状态
2. Railway 服务优先于消息数
3. 最近 URL 优先于对话更新时间

### 7.3 视图三：用户视图

#### 目标

只展示**有过部署记录的用户列表**，用于回答“哪些用户正在部署、哪些用户部署失败集中”。

#### 数据范围

不显示全部用户，只显示至少存在一条部署记录的用户。

#### 列表列

1. 用户
   - displayName / email / userId
2. 部署数量
3. 成功数量
4. 失败数量
5. 处理中数量
6. 最近部署状态
7. 最近 Railway 服务
8. 最近 URL
9. 操作
   - 查看该用户的部署清单
   - 打开用户详情

#### 关键修改

这一视图不再是“用户管理详情的镜像页”，而是“部署用户榜单”。

也就是说：

1. 首屏是部署用户列表
2. 每行是部署统计，不是用户基础资料
3. 用户信息只是归属标签，不是页面主语

### 7.4 视图四：Railway 视图

#### 目标

把后台部署治理真正延伸到 Railway 资源侧，让管理员可以直接看和管：

1. 项目
2. 环境
3. 服务
4. 域名
5. 最近部署

#### 列表对象

首期 Railway 视图以 `service` 为主对象。

每行一个 Railway service，附带：

1. project
2. environment
3. serviceId
4. serviceName
5. 当前域名
6. 最近部署状态
7. 最近 deploymentId
8. 关联用户
9. 关联会话数
10. 风险标记

#### 风险标记示例

1. 孤儿服务
   - Railway 上存在，但后台没有会话映射
2. 会话缺失
   - 有服务，但 task session 已不存在
3. 域名异常
   - domain / targetPort 不匹配
4. 部署失败堆积
5. 重复服务

## 8. Railway 管理动作设计

### 8.1 本轮建议支持的动作

为了让“删除服务、变更服务等”有边界，本轮把 Railway 动作明确收敛为以下几类：

#### 1. 批量删除服务

适用：

1. 孤儿服务
2. 测试残留服务
3. 明确确认不再使用的错误服务

交互要求：

1. 仅在 Railway 视图可见
2. 必须先勾选多行
3. 弹出影响确认弹窗
4. 展示将删除的：
   - project
   - environment
   - serviceName
   - 关联用户 / 会话
5. 必须二次输入确认词
6. 成功后写审计日志

#### 2. 批量变更服务运行配置

适用：

1. 构建方式错误
2. build / start command 漂移
3. root directory / healthcheck 配置不一致
4. 需要统一 image 来源

交互要求：

1. 允许批量修改受控字段：
   - builder
   - buildCommand
   - startCommand
   - rootDirectory
   - healthcheckPath
   - sourceImage
2. 首期不开放服务重命名
3. 写入前必须明确展示影响范围

#### 3. 批量变更服务域名 / targetPort

适用：

1. domain 指向错误
2. targetPort 与模板配置不一致

交互要求：

1. 先做预检
2. 仅允许管理员编辑受控字段
3. 写入审计日志

#### 4. 批量变更服务变量

本轮只允许“白名单变量”：

1. 公网域名相关
2. 平台标记相关
3. OneCEO 管理标记变量

本轮不开放：

1. 任意 secret 覆盖
2. 任意 DATABASE_URL 手工改写
3. 任意内部平台关键变量删除

### 8.2 本轮不建议直接开放的动作

以下动作不建议在本轮直接开放到后台 UI：

1. 批量 rollback deployment
2. 批量 redeploy
3. 环境级删除
4. 项目级删除
5. 任意 GraphQL mutation

原因：

1. 风险面过大
2. 当前需求重点是资源治理，而不是把后台做成 Railway 全功能控制台

## 9. 数据层与接口设计

## 9.1 继续保留 task session 部署聚合层

原有接口继续存在并扩展，而不是推倒重做：

1. `GET /api/internal/admin/deployments/overview`
2. `GET /api/internal/admin/deployments`
3. `GET /api/internal/admin/deployments/conversations`
4. `GET /api/internal/admin/deployments/users`
5. `GET /api/internal/admin/deployments/task-sessions/:taskSessionId`

但查询逻辑要调整为：

1. 只返回“有部署记录”的对象
2. 三视图的默认排序全部改成部署相关排序

## 9.2 新增 Railway 管理态接口

建议新增一组内部 admin Railway 路由：

1. `GET /api/internal/admin/railway/services`
2. `GET /api/internal/admin/railway/services/:serviceId`
3. `POST /api/internal/admin/railway/services/batch-rename`
4. `POST /api/internal/admin/railway/services/batch-domain-update`
5. `POST /api/internal/admin/railway/services/batch-variable-update`
6. `POST /api/internal/admin/railway/services/batch-delete`

对应 admin_management BFF 再转发：

1. `/api/deployment-management/railway/services`
2. `/api/deployment-management/railway/services/:serviceId`
3. `/api/deployment-management/railway/services/batch-*`

## 9.3 服务实现建议

建议新增一个专用服务，而不是把 Railway 动作继续塞进 deployment runtime service：

1. `apps/api/src/services/admin-railway-management-service.ts`

职责：

1. 拉取 Railway service 列表
2. 关联 user / task session / deployment panel
3. 生成风险标签
4. 执行受控批量动作
5. 写审计记录

原因：

1. `task-session-deployment-runtime-service.ts` 的职责是“会话部署状态闭环”
2. Railway 管理动作属于“后台治理动作”，职责不同，应该拆开

## 10. UI 交互要求

### 10.1 三个部署聚合视图

三视图统一要求：

1. 第一列不是用户 / 对话基础资料，而是部署核心标识
2. 状态色块以部署状态为准
3. Railway project / service 要进入主信息区，不再埋到详情里
4. URL 要尽量前置显示

### 10.2 Railway 视图

Railway 视图需要新增：

1. 勾选列
2. 批量动作栏
3. 风险筛选
4. 预检结果侧栏 / 弹窗
5. 操作结果回执

### 10.3 高风险动作确认

批量删除服务必须满足：

1. 必须显示受影响服务数
2. 必须显示受影响用户数 / 会话数
3. 必须显示是否存在线上 URL
4. 必须二次确认
5. 必须记录 operator、time、payload、result

## 11. 与现有页面的联动调整

### 11.1 用户管理

保留“用户详情 -> 部署页签”，但其角色变更为：

1. 从用户页跳转到部署管理中的该用户部署清单
2. 不再把用户页内部署页签当作主展示中心

### 11.2 对话管理

保留“对话详情 -> 部署摘要”，但其角色变更为：

1. 只展示简明 deployment summary
2. 默认把管理员引导到 `部署管理 -> 对话视图 / 部署索引`
3. 不在对话弹窗里继续扩张 Railway 管理动作

### 11.3 部署管理

部署管理成为部署中心的唯一主入口：

1. 所有部署治理
2. 所有 Railway 资源治理
3. 所有批量动作

## 12. 风险与约束

### 12.1 风险

1. Railway 批量删除是破坏性操作，必须确保关联分析正确
2. Railway 视图的数据量可能显著高于 task session 聚合视图，必须考虑分页
3. Railway 资源与 task session 的关联可能存在历史脏数据，需要允许“孤儿资源”存在

### 12.2 约束

1. 不能绕开现有 Railway GraphQL 通道
2. 不能把危险动作直接暴露为无确认按钮
3. 不能把三视图重新做回用户页 / 对话页的变体
4. 不能用“显示全部用户 / 全部对话”稀释部署中心视图

## 13. 实施顺序建议

按风险与收益，建议拆成两阶段实现：

### 阶段 A：部署中心重构

1. 重构三视图的数据口径与列设计
2. 只显示有部署记录的对象
3. 三视图全部改为部署优先
4. 调整用户页 / 对话页跳转行为

### 阶段 B：Railway 管理视图

1. 新增 Railway service 列表
2. 新增 Railway 详情
3. 新增批量 rename / domain update / variable update / delete
4. 补齐审计链路

原因：

1. 阶段 A 能先把当前视图方向纠正
2. 阶段 B 再进入危险动作与 Railway 资源治理，便于验证边界

## 14. 本方案的采用条件

如果你确认本方案，后续代码实现将按以下边界执行：

1. 三个既有视图全部改成“只看有部署记录对象”
2. 页面重心全部前移到部署状态与 Railway 资源
3. 新增 `Railway 视图`
4. Railway 批量管理首批支持：
   - 批量删除服务
   - 批量变更服务运行配置
   - 批量白名单变量变更

在你明确采用前，不进入代码实现。
