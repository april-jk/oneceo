# 20260420 Altus 测试集执行 SOP [20260420-1457已采用]

## 1. 目标

提供一份可直接照着执行的操作手册，用于：

1. 初始化一次 Altus 能力评测 run
2. 逐题执行测试题
3. 基于证据完成人工判分
4. 汇总结果并输出给修复团队

## 2. 适用范围

适用于以下场景：

1. 日常 smoke 回归
2. 某一轮修复后的专题复测
3. 不同模型 / prompt / 路由版本的横向对比

不适用于：

1. 完全无人值守的自动评测
2. 不保留原始证据的主观打分

## 3. 依赖与前置条件

执行前必须确认：

1. API 服务已启动，默认地址为 `http://localhost:4000`
2. WebSocket 入口可用，默认地址为 `ws://localhost:4000/ws/task-creation`
3. 测试账号凭据已配置：
   - 优先设置 `ONECEO_E2E_USER_EMAIL` / `ONECEO_E2E_USER_PASSWORD`
   - 或创建本地未跟踪文件 `apps/web/e2e/playwright-test-account.json`
4. 当前测试使用的题库种子已确定：
   - `docs/智能体能力测试题库/题库种子/altus_eval_seed_v1.json`
5. 本次评测目标已经明确：
   - 是 smoke
   - 还是某一组专项 case

## 4. 跑前检查清单

正式执行前，逐项确认：

1. 当前 API 是否是要验证的那一版代码
2. 当前 Git 分支和 commit 是否已记录
3. 是否存在已知的环境阻塞：
   - E2B 并发上限
   - 登录失效
   - 测试账号异常
   - 本地数据库状态异常
4. 本轮是否需要单独写测试方案文档到 `docs/单元测试文档/`
5. 本轮使用的 case 范围是否已经固定

建议先执行：

```bash
curl http://localhost:4000/health
```

## 5. 标准执行流程

### 5.1 初始化 run

#### 方式 A：快速 smoke

```bash
pnpm --filter api altus-eval:init -- --smoke
```

#### 方式 B：完整初始化

```bash
pnpm --filter api altus-eval:init -- \
  --suite ../../../docs/智能体能力测试题库/题库种子/altus_eval_seed_v1.json \
  --executor manual \
  --provider runtime \
  --model current-altus \
  --temperature 0 \
  --base-url http://localhost:4000 \
  --mode managed \
  --auth-profile playwright-test-account
```

初始化完成后，记录输出的 `run_dir`。

### 5.2 逐题执行

单题执行命令：

```bash
pnpm --filter api exec tsx scripts/altus-eval/run-case.ts -- \
  --run-dir '/绝对路径/到/run目录' \
  --case-id ALTUS-CLARIFY-001 \
  --api-base http://localhost:4000 \
  --ws-url ws://localhost:4000/ws/task-creation \
  --timeout 180000
```

专项复测时，按固定 case 列表逐题执行。

### 5.3 查看证据

每道题执行后，重点查看：

1. `artifacts/<case_id>.json`
2. `sessionDetail`
3. `fullMessages`
4. `latestRun`
5. `deployment`
6. `workspaceTree`

优先观察以下信号：

1. 是否错误改写标题
2. 是否错误进入营销 fallback
3. 是否进入 `waiting_user`
4. 是否错误触发部署链路
5. 是否把脚本任务改写为网页应用
6. 是否把“不要部署”等边界约束丢失

### 5.4 人工判分

当前流程为“自动采集证据 + 人工判分”。

需要把判分结果写回 `case_results.jsonl`，每题至少补齐：

1. `status`
2. `hard_fail`
3. `hard_fail_reasons`
4. `dimension_scores`
5. `total_score`
6. `verdict`
7. `evidence_refs`
8. `notes`

### 5.5 汇总

全部题目判分完成后执行：

```bash
pnpm --filter api altus-eval:finalize -- --run-dir '/绝对路径/到/run目录'
```

最终以以下文件作为本轮结果出口：

1. `summary.md`
2. `run_manifest.json`
3. `case_results.jsonl`

## 6. 判分建议顺序

建议按固定顺序判分，避免只看总分：

1. 先看是否触发硬失败
2. 再看 `status`
3. 再看能力维度分
4. 最后写 `notes`

推荐判分时先回答 4 个问题：

1. 任务有没有被识别对
2. 该澄清时有没有先澄清
3. 执行链路有没有被错误改写
4. 是否存在“声称完成但无证据”

## 7. 单题判分模板

可以按下面结构填写每题备注：

```text
结论：
- pass / failed_soft / failed_hard / blocked

核心证据：
- session title:
- planning message:
- execution handoff:
- deployment status:

判断：
- 是否命中预期行为：
- 是否触发禁止行为：
- 是否满足硬失败规则：

备注：
- 环境干扰：
- 仍需补验证的点：
```

## 8. 结果汇报模板

建议对修复团队的汇报结构固定为：

### 8.1 概览

1. 本轮 run 路径
2. 测试时间
3. 当前服务地址
4. 分支 / commit
5. 总分与通过情况

### 8.2 已确认修复

按 case 列出已经稳定观察到的正向变化，不写“可能修好”。

### 8.3 未修复问题

按优先级列出：

1. 问题名称
2. 对应 case
3. 直接证据
4. 为什么说明修复未真正生效

### 8.4 环境阻塞

明确区分：

1. 环境问题导致无法继续深入验证
2. 但关键缺陷是否已经在进入环境前暴露

## 9. 常见阻塞与处理方式

### 9.1 E2B 并发已满

现象：

1. 进入执行阶段后报 concurrent sandbox limit

处理：

1. 标记为 `blocked` 或在备注中写清环境阻塞
2. 如果错误在 sandbox 调度前已出现，仍然可以对前置路由做负面结论

### 9.2 登录失败

现象：

1. `auth login failed`

处理：

1. 检查 `ONECEO_E2E_USER_EMAIL` / `ONECEO_E2E_USER_PASSWORD` 或本地未跟踪 `playwright-test-account.json`
2. 确认测试账号仍然有效

### 9.3 API 不是目标版本

现象：

1. 修复团队声称已修，但当前结果完全不像新版本

处理：

1. 先记录当前服务 commit
2. 明确“当前运行实例未观察到修复”
3. 不把“代码库里可能已修”当作“运行实例已修”

## 10. 推荐执行策略

### 10.1 日常回归

只跑 smoke 集，目标是快速发现明显退化。

### 10.2 修复后复测

只跑与本轮修复直接相关的 case，目标是确认修复是否真正进入当前链路。

### 10.3 版本验收

按能力域全量执行，目标是输出稳定的阶段性质量结论。

## 11. 当前已知限制

本 SOP 对应的是当前第一版评测工具链，限制如下：

1. 仍需人工判分
2. 还没有自动化 dashboard
3. 还没有自动批量执行 case 的总控脚本
4. 环境依赖较强，尤其受 sandbox 资源状态影响
