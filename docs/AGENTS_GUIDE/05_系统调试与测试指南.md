# 系统调试与测试指南

> 本文档用于统一 oneceo 的“设计后开发验证”和“直接功能测试”两类调试流程。目标不是补一套额外流程，而是把现有协作规则落成可执行检查表，确保功能可用、符合已采用文档、不过度设计。

## 最高原则：以结果为导向

测试的目标不是为了完成一组形式化动作，而是为了证明“功能已经按需求实现并真实生效”。

执行测试时必须遵守以下原则：

1. 一切测试为确认功能结果服务，避免盲目堆叠单元测试。
2. 没拿到明确输入值、明确输出值、明确副作用证据之前，不能认定功能通过。
3. `HTTP 200`、脚本打印 `success`、函数没有抛错，都不能单独作为通过依据。
4. 需要缓存、消息流、状态落盘时，必须下沉到 Redis、数据库、事件流等实际存储层核验。
5. 如果功能是后端整改，必须验证整改后的完整行为，而不是只验证某个局部函数能运行。

## 适用场景

本文档只解决两类核心场景：

1. 用户要求 AI 先设计文档，再按文档开发，并在开发后测试，确认实现符合项目需求且未偏离设计。
2. 用户直接要求 AI 对某个功能或链路做测试，不要求先做新的设计方案。

## 总原则

1. 测试前先确认“依据”是什么，禁止脱离依据做功能判断。
2. 测试要覆盖主路径、身份边界、状态持久化、失败路径，不只看接口 `200`。
3. 需要验证缓存、消息流、运行态时，必须下沉到存储层或事件层，不只看页面现象。
4. 发现设计与实现不一致时，先指出“哪份已采用文档”和“哪个实现行为”冲突，再修复。
5. 没有被用户要求的扩展能力，不进入测试目标，不借测试顺手放大需求。

## 测试前必须先写测试文档

无论是“设计后开发验收”还是“直接测试某功能”，开始执行测试前都必须先形成测试文档。测试文档至少要包含四部分：

1. 测试单元清单
2. 每个测试单元的预期输入与预期输出
3. 边界条件与失败条件
4. 每个测试单元对应的验证方式

这里的“测试单元”必须精确到最小可验证模块，不能只写“测试聊天功能”这种大项，必须细到：

1. 某个具体接口
2. 某个具体函数
3. 某个具体页面动作
4. 某个具体 Redis key 或 stream
5. 某个具体数据库写入或更新行为

没有这份测试文档，不进入实际测试。

## 测试脚本与测试文档存放规则

1. 测试脚本的存放位置保持现状不变，禁止为了补测试而重新迁移测试脚本目录。
2. 新增或更新的测试文档统一存放到 `docs/单元测试文档/`。
3. 测试文档命名应直接体现测试主题，便于后续按功能检索。
4. 测试文档负责描述测试单元、预期、边界和核验方式；实际测试代码仍放在当前项目既有测试目录中。

## 测试标准流程

### 第一步：导出详细测试单元

先完整列出本次需要验证的最小测试单元，粒度必须足够小。

示例：

1. `POST /api/task-creation/sessions`
2. `GET /api/task-creation/sessions/:sessionId/messages/recent`
3. `taskSessionRedisCacheService.setRecentMessagesPage()`
4. `current-user-resolver.require()`
5. `session-events` replay 写入 Redis 的某个 stream

### 第二步：编写预期文档

对每个测试单元写清楚：

1. 预期输入是什么
2. 预期输出是什么
3. 预期副作用是什么
4. 边界条件是什么
5. 失败条件是什么

必须尽可能把边界条件列全，而不是只写 happy path。

该文档必须落在 `docs/单元测试文档/` 下。

### 第三步：编写脚本测试

测试必须通过脚本逐个触发，不允许只靠人工口述判断。

脚本测试要求：

1. 对导出的所有测试单元逐个执行
2. 输入值明确
3. 返回值明确
4. 失败时能定位是哪个测试单元不符合预期
5. 能复现并重复执行

### 第四步：核验真实结果

脚本执行完成后，必须继续核验真实结果，而不是停在脚本返回值。

例如：

1. Web 测试：接口返回 `200` 不算通过，必须取得返回内容，并确认内容符合预期。
2. Redis 测试：脚本返回 `success` 不算通过，必须检查 Redis 中对应键值或 stream 已按预期写入。
3. 数据库测试：必须直接查询数据库，确认数据已成功插入、更新或删除。
4. 后端测试：必须确认整改功能在真实请求链路下行为完整，而不是只验证内部函数调用成功。

## 测试依据优先级

执行测试前，按以下优先级确定验收标准：

1. 当前主题下最新的 `[yyyymmdd-hhmm已采用]` 设计文档
2. 根 `AGENTS.md` 与 `docs/AGENTS_GUIDE/*.md`
3. 现有接口契约、数据库结构、缓存键空间规范
4. 已存在且可信的回归测试
5. 用户在当前会话中新增明确要求

如果上述内容冲突：

1. 已采用文档优先于历史实现
2. 当前用户的明确新要求优先于旧文档，但要同步更新文档
3. 不允许用“兼容旧逻辑”替代修正主链逻辑

## 场景一：先设计文档，再开发，再测试

### 阶段 1：设计验收前

此阶段不进入代码实现。先完成以下检查：

1. 找到本次功能对应的系统文档或新增文档。
2. 确认文档状态是否为 `[尚未采用]`。
3. 把范围拆成可验证条目：
   - 页面与交互
   - 接口输入输出
   - 身份与权限边界
   - 状态存储与缓存
   - 失败场景与恢复
4. 对每个条目写出“测试可观察信号”：
   - 返回值
   - 数据库记录
   - Redis 键
   - SSE/WebSocket 事件
   - 页面状态变化

### 阶段 2：用户确认文档后开始开发

进入代码实现前，先把测试计划和实现边界对齐：

1. 列出本次会修改的组件和文件。
2. 先生成测试文档，导出最小测试单元清单。
3. 为每个测试单元补充预期输入、预期输出、边界条件和验证方式。
4. 列出对应的测试层级：
   - 函数级脚本测试
   - 路由/接口级测试
   - 存储层验证
   - 浏览器或真实链路验证
5. 写清楚“本次不做什么”，防止测试扩大成新的需求。

### 阶段 3：开发完成后的验收测试

必须按下列顺序执行：

1. 文档对照
   - 对照已采用文档逐条列出功能点
   - 标记“已实现 / 未实现 / 行为不一致”
2. 代码级验证
   - 最小导入验证
   - 相关类型检查或最小测试
3. 逐个执行测试文档中的脚本测试
   - 不允许跳过已导出的测试单元
   - 对每个单元记录明确输入和明确输出
4. 接口级验证
   - 对每个新增或修改接口逐个触发
   - 校验成功路径、鉴权失败、越权失败、状态错误
5. 存储层验证
   - DB：检查事实数据是否正确落盘
   - Redis：检查缓存/stream/状态键是否正确写入、读取、失效
6. 用户态验证
   - 如果是页面或消息流功能，必须验证前端真实可见行为
7. 文档回写
   - 更新文档中的“实现状态 / 偏差 / 最终采用结果”

### 阶段 4：判定是否符合需求

只有同时满足以下条件，才算“符合设计并可用”：

1. 行为与已采用文档一致
2. 主路径可用
3. 核心失败路径有预期结果
4. 身份边界不串用户、不串管理员
5. 状态存储与缓存行为可被证据证明

如果不满足，禁止用“基本可用”结案。

## 场景二：用户直接要求测试某个功能

这种情况不默认补新方案文档，但仍要先建立测试依据。

### 执行步骤

1. 找到相关已采用文档；如果没有，就以现有实现契约和用户当前要求为准。
2. 先编写测试文档，并导出最小测试单元清单：
   - 页面动作
   - 路由
   - service 函数
   - DB 表
   - Redis 键或 stream
   - 外部依赖
3. 为每个测试单元写预期输入、预期输出和边界条件。
4. 明确测试深度：
   - 只做接口测试
   - 做真实链路测试
   - 做存储层核验
5. 编写脚本并逐项触发
6. 检查 DB / Redis / 事件流等实际结果
7. 输出结果时区分：
   - 行为正确
   - 行为错误
   - 未实现
   - 无法验证

### 必须避免的误区

1. 只看前端页面，不看接口和存储
2. 只看接口返回成功，不看副作用
3. 看到旧逻辑能跑就默认符合需求
4. 在测试过程中偷偷扩展实现范围
5. 没有预期输入和预期输出就直接开始写测试代码

## 组件级自动测试方案

以下方案用于指导“应该先补哪一层测试、如何证明链路正确”。

### 1. 文档与需求层

目标：确认开发目标没有偏移。

建议动作：

1. 为每个已采用文档提取验收项清单
2. 对每项验收项建立映射：
   - 对应页面/接口
   - 对应存储
   - 对应测试文件
3. 在提交前核对“实现覆盖率”，确认没有遗漏主功能点

### 2. Web 用户端

目标：确认用户可见行为真实可用。

最少覆盖：

1. 页面路由守卫
2. 登录/注册/退出
3. 新建任务与会话恢复
4. 消息发送、处理中状态、消息回放
5. 会话列表、历史消息、附件、交付物

自动化方式：

1. 组件测试：状态恢复、缓存合并、消息列表渲染
2. 浏览器测试：真实点击、发送、刷新、重连
3. 网络核验：检查 SSE/WebSocket/HTTP 请求是否按预期发生

### 3. API 路由层

目标：确认接口行为符合设计且身份边界正确。

最少覆盖：

1. 成功路径
2. 未登录
3. 越权访问
4. 非法输入
5. 状态冲突
6. 幂等或重复触发

自动化方式：

1. 先导出每个路由的最小测试单元
2. 最小 Express app 路由测试
3. stub 依赖 service / DAO
4. 对 SSE 路由增加 replay、重连、断连清理验证
5. 每个路由测试都要拿到明确请求和明确响应体，不允许只断言状态码

### 4. Service 层

目标：确认核心业务规则和状态机正确。

最少覆盖：

1. 身份绑定
2. 会话归属
3. 运行态切换
4. 缓存写入与失效
5. 错误分支

自动化方式：

1. 单元测试
2. 假实现端口或 fake adapter
3. 必要时对时间、游标、序列号做确定性断言

### 5. DB 层

目标：确认事实数据正确。

最少覆盖：

1. 主记录是否落盘
2. 顺序字段是否正确
3. 归属字段是否正确
4. 更新是否覆盖到正确行
5. 删除/归档/恢复是否一致

自动化方式：

1. DAO 级测试
2. 真实 DB 最小集成测试
3. 必要时直接 SQL 查询验证

强制要求：

1. 如果涉及数据库落盘，必须通过脚本触发相关功能代码
2. 触发后必须直接连接数据库查询
3. 必须证明实际行数据已按预期插入、更新或删除
4. 不允许只凭 service 返回值判定通过

### 6. Redis 层

目标：确认热缓存、stream、运行态协调键真实可用。

最少覆盖：

1. 开关关闭时不启用
2. 开关打开后能真实写入
3. key 命名符合规范
4. TTL 生效
5. stream replay 顺序正确
6. 失效逻辑能删掉旧键

自动化方式：

1. fake Redis 单测：验证 key builder、service 逻辑
2. live Redis 集成测试：验证真实写入、真实读取、真实失效
3. 路由触发后直接检查 Redis 中的键和值

强制要求：

1. 如果涉及 Redis，必须在脚本触发后检查对应 key 或 stream
2. 必须拿到实际键名、实际值、实际 TTL 或实际 stream entry
3. 不允许只凭日志或 `success` 返回值判定通过

### 7. Sandbox / OSAC / OpenCode

目标：确认运行时链路不是“接口成功但系统没工作”。

最少覆盖：

1. sandbox 创建/恢复/关闭
2. OSAC 转发是否经过统一链路
3. OpenCode session 是否正确绑定
4. 事件桥接是否落盘且可回放

自动化方式：

1. service 级 stub 测试
2. 路由级桥接测试
3. 真实链路复现时对比：
   - taskSessionId
   - orchestratorSessionId
   - opencodeSessionId

## Redis 与存储核验标准

凡是涉及缓存、流、运行态的功能，测试时必须同时回答下面四个问题：

1. 哪个接口或服务会写入 Redis？
2. 写入哪个 key 或 stream？
3. 该数据何时读取、何时失效？
4. 如果 Redis 没命中，系统按什么事实来源回退？

建议输出格式：

1. 接口列表
2. 触发步骤
3. 预期 Redis key
4. 实际 Redis key/value
5. 是否符合设计

## 全链路测试

当脚本级和存储级测试都已通过后，需要由用户决定是否继续做全链路测试。

### 执行方式

1. 先向用户确认是否进入全链路测试
2. 经用户确认后，再使用 Playwright 或等效工具做真实业务操作
3. 遇到需要登录、二次验证、特定点击路径等无法自动完成的步骤，主动请求用户协助

### 目标

全链路测试用于确认“从触发到生效”的完整业务过程，而不是代替前面的脚本级验证。

也就是说，全链路测试只能建立在下面条件之上：

1. 输入输出已明确
2. 接口响应已明确
3. DB/Redis/事件流等底层状态已核验

如果底层状态还没有验证清楚，不进入全链路测试。

## 推荐执行模板

### 模板 A：设计后开发验收

1. 找到最新已采用文档
2. 提取验收项
3. 映射到接口、页面、存储
4. 开发完成后逐项测试
5. 记录偏差并修复
6. 回写文档与工作汇报

### 模板 B：直接测试功能

1. 定位目标功能
2. 先写测试文档并导出最小测试单元
3. 为每个单元补预期输入、预期输出、边界条件
4. 编写脚本并逐个触发
5. 检查 DB / Redis / 事件流
6. 需要时再请求用户一起做全链路测试
7. 汇总结论和问题点

## 输出要求

测试结论必须区分以下四类：

1. 已按设计实现且验证通过
2. 已实现但与设计不一致
3. 设计要求存在，但实现缺失
4. 当前无法验证，需补充环境或证据

禁止只输出“已测试通过”而没有证据链。
