# 部署工具模板修复循环终止方案 [20260418-1558已采用]

## 1. 问题背景

在真实会话里，Altus 先生成了一个可本地运行的外贸网站项目，目录形态为：

- `public/index.html`
- `public/css/*`
- `public/js/*`
- `server.js`
- `package.json`
- `oneceo.manifest.json`

随后用户要求“帮我部署当前项目”，managed deploy run 出现以下异常链路：

1. `deploy_application` 返回 `status=retryable_repair_required`
2. summary 固定为“当前项目缺少稳定发布所需的部署基线，Altus 需要先自动修复后再继续发布”
3. Altus 回到工作区反复改写 `public/index.html`
4. 再次调用 `deploy_application` 后仍得到同一结果
5. 最终 run 以 `managed_run_tool_round_limit_exceeded` 失败

这说明问题不在 Railway 真正发布阶段，而是在“模板合规检查 -> 自修复 -> 再检查”这一段闭环里。

## 2. 根因结论

根因已经定位为同一条部署基线事实在两个服务中的入口集合不一致：

### 2.1 注入服务识别了 `public/index.html`

`deployment-template-bootstrap-service.ts`

- 会按候选顺序查找 HTML 入口
- 其中包含 `public/index.html`
- 找到后会把 OneCEO analytics bootstrap 注入到该文件

因此对于这类项目，平台实际上已经完成了模板注入。

### 2.2 合规检查没有识别 `public/index.html`

`template-compliance-service.ts`

- `detectAnalyticsEntry()` 用于判断项目是否已经具备 analytics 注入入口
- 它检查了 `client/index.html`、`index.html`、`templates/index.html` 等路径
- 但遗漏了 `public/index.html`

结果是：

1. 注入已经写进 `public/index.html`
2. 合规检查却看不到这个注入结果
3. `analyticsEntryDetected=false`
4. baseline 一直停留在 `needs_attention`
5. deploy tool 一直回 `template_compliance`
6. Altus 永远无法通过这次修复

这不是 agent 不会修，而是平台判定条件自相矛盾。

## 3. 修复目标

本次修复只做一个最短闭环目标：

**让部署模板注入与模板合规检查共享同一组 HTML 入口候选，并保证 `public/index.html` 项目在注入后能立即被判定为 deploy-ready。**

不在本次范围内追加：

- 新的模板策略
- 额外兜底 prompt
- 新的发布 provider 逻辑
- UI 层兼容补丁

## 4. 修复方案

### 4.1 收敛 HTML 入口候选集合

在 `template-compliance-service.ts` 中，把 `public/index.html` 加入 `detectAnalyticsEntry()` 的候选列表。

要求：

1. 注入服务与合规服务对 HTML 入口的识别顺序保持一致
2. 至少覆盖以下路径：
   - `client/index.html`
   - `index.html`
   - `public/index.html`
   - `templates/index.html`
   - `app/templates/index.html`

### 4.2 保持 deploy tool 行为不变

`altus-managed-deployment-tool-service.ts` 不新增兼容分支。

原因：

- deploy tool 当前按 baseline `ready / needs_attention / unavailable` 决策本身是对的
- 错的是 baseline 生成阶段的合规事实不一致
- 修正检测后，deploy tool 会自然停止返回 `retryable_repair_required`

### 4.3 不引入 prompt 级补丁

`altus-managed-prompt-service.ts` 本次不加“多次失败后停止改 HTML”的提示。

原因：

- 当前失败不是模型理解错，而是平台给出的修复目标永远不可满足
- 如果先补 prompt，只会掩盖平台检测不一致
- 正确路径是先让平台检查结果可被真正修复

## 5. 验收标准

修复完成后必须满足：

1. 对包含 `public/index.html + package.json + server.js + oneceo.manifest.json` 的项目执行：
   - `ensureDeploymentTemplateBootstrap()`
   - `ensureTemplateCompliance()`
2. `analyticsEntryDetected=true`
3. `compliance.ok=true`
4. baseline `status=ready`
5. `deploy_application` 不再因为 `missing_analytics_entry` 返回 `retryable_repair_required`

## 6. 回归范围

至少覆盖三类：

1. `index.html` 根静态项目
2. `client/index.html` 前端项目
3. `public/index.html` 静态目录项目

其中第 3 类是本次真实故障样本，必须新增回归测试。

## 7. 风险说明

本次改动风险窄，主要风险只有一项：

- `detectAnalyticsEntry()` 入口列表扩大后，可能让原本未纳入检测的 `public/index.html` 项目从 `needs_attention` 转为 `ready`

这是预期变化，不是回归，因为该文件本来就是平台真实注入目标。

## 8. 结论

这次故障的本质不是 Railway 不稳定，也不是 Altus 不会修模板，而是：

**平台把注入写进了 `public/index.html`，却在合规检测时不承认 `public/index.html`。**

只要把注入入口与检测入口统一，这条会话里的 deploy 自修复死循环就会自然消失。
