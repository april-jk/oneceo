> 问题来源：用户反馈会话 `1aa95058-0c2d-4731-94ac-e1b044b2fc78` 在开发中途开始出现所有工具命令连续失败，表现为“像 sandbox 关闭了一样”。

## 1. 结论

这次问题不是“sandbox 自然过期”或“归档链路正常回收”导致的。

根因是：

1. 开发中的 managed run 已经绑定并正在使用某个 sandbox。
2. 非 sandbox 维护模块的业务读路径又触发了 runtime ensure / rebound。
3. rebound 过程中，旧 sandbox 被当作重复环境主动关闭。
4. 运行中的 managed run 仍然持有旧 sandbox id，后续所有工具调用开始稳定失败。

所以本次修复主题不应定义为“deployment 过早触发”，而应定义为：

**收回 sandbox 切换控制权，禁止业务模块触发 runtime rebound。**

## 2. 设计边界回顾

根据当前 oneceo 架构与既有文档，sandbox 生命周期的职责边界应当是：

1. sandbox 的创建、复用、切换、关闭、归档、恢复，只能由 sandbox 维护链路负责。
2. 业务模块可以读取当前 sandbox/runtime 状态，但不能自行决定切换 sandbox。
3. deployment 是交付末段能力，只能消费已有 runtime/sandbox 状态，不能反向驱动 sandbox 重建。
4. 预览、artifact、deployment、debug 等业务读路径不应通过只读请求改写会话 runtime binding。
5. deployment 即使在交付末段，也只能读取或消费当前 sandbox/runtime 结果，不能成为 sandbox 切换的触发者。
6. sandbox 切换的唯一合法目的，是 sandbox 维护模块在确认当前环境不可继续使用时，为保证始终有可用 sandbox 且尽量保住工作区状态而执行受控切换。

6. 运行中的 managed run 继续对旧 sandbox 执行工具

## 5. 根因归类

### 5.1 不是 deployment 本身坏了

deployment 只是触发面之一。

真正的根因是：

**sandbox 生命周期控制权泄漏到了业务读路径。**

### 5.2 具体违规点

1. deployment / preview 这类业务模块越权触发了 runtime ensure
2. runtime ensure 进一步触发了 sandbox rebound
3. rebound 又会主动关闭旧 sandbox
4. 活跃 run 对 sandbox 的绑定没有被保护，导致执行上下文和 session binding 分叉

### 5.3 为什么这是系统性问题

如果不把它定义成“控制权泄漏”，而只定义成“deployment 太早”，后续同类问题仍可能从这些模块重新出现：

1. artifact 预览
2. HTML 预览恢复
3. debug 面板
4. replay drawer
5. 任何其他会调用 `ensureTaskSessionRuntime()` 的业务读路径

## 6. 修复目标

本次修复只做一件事：

**收回 sandbox 切换控制权，确保只有 sandbox 维护模块可以触发 sandbox rebinding。**

具体目标：

1. 开发中的 managed run 不再被业务读路径切换 sandbox
2. deployment / preview / replay / debug 读路径不再能引发 runtime rebound
3. sandbox 切换只能由明确的 sandbox 维护链路触发
4. 活跃 run 的执行 sandbox 与会话 binding 在运行期保持一致，不再被外部读接口改写

## 7. 最小修复方案

本方案不做兼容补丁，不引入新框架，只按最短路径恢复模块边界。

### 7.1 后端：把 `ensureTaskSessionRuntime()` 从业务读路径中移出

处理原则：

1. `deployment`
2. `deployment/template`
3. 其他纯读 preview/debug/deployment 读接口

不得再直接调用会导致 provision / rebinding 的 `ensureTaskSessionRuntime()`。

最小改法：

1. 新增一个纯读 runtime 解析函数，例如“读取当前 session binding + 当前 environment + 当前状态”
2. 该函数只读取，不 provision，不 rebound，不 updateRuntimeBinding，不 reconcile duplicate environments
3. `/deployment`、`/deployment/template`、相关只读接口全部改用纯读函数

这一步的核心不是换名字，而是：

**彻底切断业务读路径对 sandbox 维护动作的调用权。**

### 7.2 后端：把 `/runtime/start` 明确定义为显式维护控制面

为了避免把唯一合法维护入口也一起误伤，当前代码基线下要明确：

1. `/runtime/start` 继续保留
2. 它是现有公共 HTTP 面里唯一允许进入 `ensureTaskSessionRuntime()` 的显式维护入口
3. 但 preview / artifact / deployment / replay / debug 的普通业务流程不得再隐式调用它

active managed run 存在时，`/runtime/start` 的行为要写死：

1. 不允许触发 provision / rebound
2. 不允许改写 runtime binding
3. 只能返回“当前存在 active run，已阻止 runtime 切换”的明确结果

无 active managed run 时，`/runtime/start` 仍然可以继续承担 sandbox 维护职责。

这样 `/runtime/start` 的角色就闭环了：

**它不是业务读路径，但它也不能再作为业务 UI 的隐式恢复捷径。**

### 7.3 后端：给 `ensureTaskSessionRuntime()` 增加控制面保护

即使未来还有调用遗漏，`ensureTaskSessionRuntime()` 本身也必须有硬边界：

1. 当 session 存在 active managed run 时，业务调用不能触发 sandbox rebound
2. 在该状态下，它至多允许：
   - 读取当前 binding
   - resolve 当前 environment status
   - touch 当前 sandbox
3. 不允许：
   - `provisionWithLock`
   - `updateRuntimeBinding`
   - `reconcileTaskSessionDuplicateEnvironments`

如果当前 sandbox 已坏，应直接返回“当前 runtime 不可用”，由 sandbox 维护链路或 run 失败流程处理，而不是由业务读接口偷偷切换。

当前代码最小收口原则：

1. 不新增新的切换框架
2. 继续复用现有 `ensureTaskSessionRuntime()` 作为底层维护实现
3. 但允许调用它的上层入口，只保留：
   - `/runtime/start`
   - sandbox 维护模块内部调用
4. 其他业务模块不再直接或间接进入这条链路

### 7.4 前端：开发态禁止自动触发 deployment 读取

虽然根因不应只落在前端，但前端也应恢复正确时机约束。

最小要求：

1. 在开发进行中，不自动拉 `/deployment`
2. 在开发进行中，不自动拉 `/deployment/template`
3. 只有满足以下任一条件时才允许进入 deployment 读取：
   - run 已完成
   - 用户显式打开 deployment tab
   - 已存在 deployment record，且只是刷新该 record
   - 用户明确触发 deploy/redeploy/rollback 流程

这一步不是主修复，但它能避免开发阶段继续制造无意义的 deployment 读请求。

### 7.5 前端：所有会间接触发 `runtime/start` 的恢复动作在 active run 期间必须停掉

不能只收口 deployment 自动读取，因为当前 preview 恢复链路也会走到 `startTaskCreationRuntime(sessionId)`。

因此首批还要一起收口：

1. HTML 预览恢复按钮
2. artifact preview 的 reload/recover 动作
3. preview panel 内部的 runtime 恢复动作
4. 其他会隐式调用 `startTaskCreationRuntime(sessionId)` 的 UI 路径

当 active managed run 存在时，这些路径必须统一改为：

1. 不自动调用 `/runtime/start`
2. 不以“恢复预览”名义触发 runtime rebound
3. 只展示当前状态，例如：
   - 当前开发仍在进行，预览恢复已暂停
   - 请等待当前 run 完成，或显式停止后再恢复 runtime

这样才能把我们前面讨论过的触发面一起封住，而不是只挡住 deployment。

### 7.6 sandbox 切换条件回收至 sandbox 维护模块

为了避免后续又从别的业务路径重新漏出控制权，本次还需要把“什么情况下允许切 sandbox”写成明确规则：

1. 只有 sandbox 维护模块可以判定是否需要切换 sandbox。
2. 合法切换前提只能是：
   - 当前 sandbox 已确认不可继续执行
   - 或 sandbox 维护链路明确要求进行恢复/替换
3. 合法切换目标只能是：
   - 保证 session 始终有可用 sandbox
   - 在切换前后尽量保住工作区与必要运行态
4. 以下都不是合法切换理由：
   - deployment 信息读取
   - preview 读取
   - artifact 展示
   - replay 查看
   - debug 面板普通刷新

当前代码基线下，唯一允许触发切换的执行面也要写死为：

1. sandbox 维护模块内部
2. `/runtime/start` 这类显式维护入口

并且这两类入口在执行切换时，都必须沿用现有 sandbox 维护链路，不允许各自再私有实现一套切换逻辑。

这样可以把我们前面讨论的核心约束写死：

**deployment 不只是“开发中不该触发”，而是从职责上就不拥有触发 sandbox 切换的权力。**

### 7.7 明确本期边界：不做运行中热切换，只做控制权收口

为了避免修复目标膨胀，本方案首批明确不做“active managed run 过程中无缝热切换到新 sandbox”。

本期只收口两件事：

1. 防止业务路径误触发 sandbox 切换
2. 把合法切换入口收回 sandbox 维护控制面

如果 active run 期间当前 sandbox 真实不可用，本期规则是：

1. 当前 run 进入明确失败或待恢复状态
2. 业务读路径不负责切换
3. 由显式维护入口或 sandbox 维护模块在 run 结束后恢复新的可用 sandbox

这样既符合“sandbox 切换是独立模块职责”，也避免这一轮修复引入新的运行中 handoff 复杂设计。

## 8. 明确不做的事

为了避免把问题修复杂，本次明确不做：

1. 不做“工具失败后自动换 sandbox”  
   这是把同一 run 扩展成跨 sandbox 执行，会放大状态不一致。

2. 不做“每次工具执行前重新读取 session binding”  
   这会让 run 的执行目标变成动态的，破坏 run 级一致性。

3. 不做“给 deployment 加兜底重试并静默换 runtime”  
   这是继续放大业务模块越权。

4. 不做“把 sandbox rebound 散落到多个业务模块的本地判断里”  
   这会继续削弱 sandbox 模块的唯一控制权。

## 9. 逻辑闭环验证

修复后，以下链路必须成立：

1. 开发中的 managed run 正在使用 sandbox A
2. 前端打开 artifact preview / preview panel / replay drawer / deployment tab
3. 后端只读取 sandbox A 的当前状态
4. 不会创建 sandbox B
5. 不会触发 duplicate reconcile
6. sandbox A 不会被业务读路径关闭
7. run 继续在 sandbox A 上执行直至完成或由 sandbox 维护链路显式接管

如果 sandbox A 此时真实不可用：

1. 读接口返回“当前 runtime 不可用”
2. 不由业务读路径擅自切到 sandbox B
3. sandbox 切换仍然只允许走 sandbox 维护模块
4. 若显式调用 `/runtime/start`，在 active run 期间收到阻止结果，而不是发生静默 rebound

## 12. 最终判断

本问题不是单点空指针，也不是部署逻辑单独异常。

它暴露的是 oneceo 当前一条更基础的架构违规：

**sandbox 切换控制权被业务模块绕开 sandbox 维护模块直接触发。**

因此本次修复必须以“恢复模块边界”为目标，而不是继续围绕 deployment 行为做局部补丁。只有这样，才能保证：

1. 新对话不再在开发中途被莫名切 sandbox
2. deployment 不再越权驱动 runtime rebound
3. sandbox 的切换、归档、恢复重新回到单一维护控制面
