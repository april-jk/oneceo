# 运行时注入、环境变量与统计采集设计 [尚未采用]

## 1. 目标

OneCEO 需要像 Manus 一样，让“生成出来的应用”天然具备平台能力，但实现方式必须是 OneCEO 自己可控的。

本文件解决三件事：

1. 平台能力怎么注入到应用
2. 环境变量怎么组织
3. 统计和用户识别怎么采集

## 2. 注入总原则

平台能力不直接散落在业务代码里，而是分四层注入：

1. 模板预留
2. 部署前补齐
3. 运行时下发
4. 浏览器自动采集

换句话说，业务应用只依赖 OneCEO runtime contract，不直接依赖平台内部实现。

## 3. 注入链路

建议链路如下：

1. agent 生成项目时输出 `oneceo.manifest.json`
2. 平台在部署前读取 manifest
3. 平台按 manifest 注入 Railway 环境变量
4. 服务端启动时通过 `@oneceo/app-runtime` 读取环境变量并暴露运行时信息
5. 浏览器启动后调用 `/api/__oneceo/runtime`
6. 浏览器自动初始化统计采集、visitor id、可选 user identify

## 4. 建议的运行时组件

## 4.1 `@oneceo/app-runtime`

建议新增内部 workspace package：`@oneceo/app-runtime`

职责：

- 读取并校验运行时环境变量
- 暴露 `/api/__oneceo/runtime`
- 提供浏览器端 `initRuntime()`、`identifyUser()`、`track()` 能力
- 统一 visitor/session/user 上下文
- 统一健康检查元数据

第一阶段不要求发布到外部 npm，只需要在 monorepo 内部形成稳定 workspace package。

## 4.2 `vite-plugin-oneceo-runtime`

如模板继续使用 Vite，可增加一个轻量 Vite 插件：

- 开发态注入 OneCEO debug collector
- 帮助插入 `data-oneceo-app` 之类的 HTML 标识
- 校验必要环境变量是否存在

注意：

- 这不是为了复制 `vite-plugin-manus-runtime`
- 而是为了把 OneCEO 自己的运行时契约收口

## 5. 建议的环境变量分层

## 5.1 公共可暴露变量

Vite 模板下建议使用：

| 变量 | 用途 |
| --- | --- |
| `VITE_ONECEO_APP_ID` | 平台应用标识 |
| `VITE_ONECEO_RUNTIME_ENDPOINT` | 浏览器获取运行时信息的入口 |
| `VITE_ONECEO_ANALYTICS_ENDPOINT` | 浏览器统计上报地址 |
| `VITE_ONECEO_ANALYTICS_SITE_ID` | 当前站点统计标识 |
| `VITE_ONECEO_AUTH_ENABLED` | 前端是否显示用户态入口 |
| `VITE_ONECEO_ENVIRONMENT` | `development/staging/production` |

## 5.2 仅服务端变量

| 变量 | 用途 |
| --- | --- |
| `ONECEO_PROJECT_ID` | 对应平台项目 |
| `ONECEO_DEPLOYMENT_ID` | 当前部署版本 |
| `ONECEO_ENVIRONMENT_ID` | 平台环境标识 |
| `ONECEO_ANALYTICS_WRITE_KEY` | 统计写入凭据 |
| `ONECEO_SIGNING_SECRET` | visitor/session 签名 |
| `DATABASE_URL` | Railway Postgres |
| `ONECEO_AUTH_MODE` | `optional/required/disabled` |
| `ONECEO_BASE_URL` | 当前对外访问基准地址 |

## 5.3 原则

- 浏览器能看到的变量只放非敏感信息。
- 所有敏感写入密钥都只在服务端使用。
- 统计采集必须允许浏览器走同源入口，避免每个项目再处理跨域。

## 6. 统计采集设计

## 6.1 必采事件

第一阶段默认采集以下事件：

- `page_view`
- `route_change`
- `session_start`
- `identify_user`
- `cta_click`
- `form_submit`
- `signup_success`
- `login_success`
- `api_error`
- `client_error`
- `business_event`（供生成应用按业务自定义）

## 6.2 默认采集字段

每条事件至少包含：

- `siteId`
- `deploymentId`
- `visitorId`
- `sessionId`
- `userId`（如果存在）
- `eventName`
- `path`
- `referrer`
- `userAgent`
- `country/region`（服务端补全）
- `device/browser/os`
- `occurredAt`

## 6.3 采集原则

- 页面浏览和路由切换应自动采集，不依赖业务开发者手写。
- 用户识别只在 OneCEO 身份已知时触发。
- 统计上报必须异步、非阻塞，绝不影响页面主流程。
- 上报失败只能影响统计，不得影响业务功能。

## 7. visitor / session / user 三层身份

## 7.1 visitor

- 任何访问者都会被分配 first-party `visitorId`
- 默认写入同源 cookie 或 local storage
- 用于站点层唯一访客统计

## 7.2 session

- 每次进入站点或超过超时时间后生成 `sessionId`
- 用于访问次数、停留时长、跳出率统计

## 7.3 user

- 只有应用明确启用了 OneCEO 用户态身份时才进行 `identifyUser`
- 用户统计不能拿匿名 `visitorId` 冒充真实用户

这和仓库现有“用户态与管理态分离、能力绑定真实 `app_users.id`”的要求一致。

## 8. 调试采集

参考 Manus 的 `debug-collector.js`，OneCEO 也应保留开发态调试采集，但需要收口为 OneCEO 自己的实现。

建议默认采集：

- console error / warning
- failed network requests
- client uncaught error
- 关键 UI 事件

原则：

- 只在开发态或显式 debug 模式开启
- 必须做敏感字段脱敏
- 产物可进入 OneCEO 调试页或任务工作台

## 9. 不应做的事

- 不要把统计 SDK 直接硬编码在每个项目里
- 不要让业务代码直接持有统计写入密钥
- 不要把用户统计建立在匿名访客 ID 之上
- 不要把调试采集和生产统计混为一条链路

## 10. 与参考项目的对应关系

| 参考项目做法 | OneCEO 是否保留 | 说明 |
| --- | --- | --- |
| `client/index.html` 注入 Umami | 保留思路 | 改成 OneCEO 自己的统计入口 |
| `vite.config.ts` 注入 debug collector | 保留思路 | 改成 OneCEO debug collector |
| `server/_core/env.ts` 读平台 env | 保留 | 但变量命名和能力归属改为 OneCEO |
| `localStorage` 存 `manus-runtime-user-info` | 不直接照搬 | OneCEO 统一走 runtime endpoint 与 app user identity |

## 11. 当前建议的审查点

- 是否同意统计采集由平台注入，而不是项目自由接入。
- 是否同意 visitor/session/user 三层身份模型。
- 是否同意开发态保留 debug collector，但与生产统计分链。
