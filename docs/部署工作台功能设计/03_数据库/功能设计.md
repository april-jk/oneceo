# 数据库功能设计

## 1. 功能定位

“数据库”不是占位页，而是部署工作台中的数据库控制台。

它的目标是提供一个可视化、可直接修改数据的管理入口，让用户可以在部署工作台内完成：

- 浏览数据库表
- 查看表结构
- 查看和修改表数据
- 刷新与分页浏览
- 进入数据库设置和结构管理
- 查看并复制数据库连接信息
- 后续扩展到 schema、权限、迁移和备份

## 2. 交互模型

数据库页建议分成左右两栏：

### 左侧

- 表列表
- 每个表的来源或标签
- 底部 `设置` 入口

### 右侧

- 当前表标题
- 工具栏
- 数据表格
- 分页区

这套结构对应的是“数据库控制台”心智，而不是只读状态页。

## 3. 页面结构

建议结构：

- 左侧表导航
- 右侧数据浏览与编辑区
- 底部分页区
- 左下数据库设置入口

## 4. 数据范围

当前文档定义中，数据库页不再只是“是否接入数据库”的说明页，而是要覆盖两类能力：

- 数据浏览与直接修改
- 数据库设置与结构管理
- Railway 数据库实例创建与连接信息展示

不建议只做一个空白壳子再延后。

## 5. 数据库来源约束

数据库实例来源明确约束为：

- 由平台在 Railway 中直接创建 PostgreSQL 服务
- 连接信息直接从 Railway 返回的数据库变量中获取

不采用的方案：

- 不在 OneCEO 内部自建独立 PostgreSQL 编排体系
- 不让用户自行输入一套外部数据库来完成这条主流程

当前约束下，数据库控制台默认围绕 Railway Postgres 展开设计。

## 6. 计划设计方式

### 第一阶段

- 在 Railway 中创建 PostgreSQL 数据库
- 表列表可切换
- 表格数据可查看
- 支持刷新、分页、列视图
- 支持新增、编辑、删除行
- 左下 `设置` 中展示连接信息，并为每一项提供复制按钮

### 第二阶段

- 支持表结构查看与字段定义
- 支持索引、约束、关系查看
- 支持数据库设置与连接信息管理

### 第三阶段

- 支持迁移、备份、恢复、权限、审计
- 支持 SQL 查询或高级编辑能力

## 7. 审核点

- 数据库是否应该放在部署工作台里。
- 数据库页是否要直接承接“可视化管理 + 直接修改数据”。
- 左侧表导航 + 右侧表格管理是否符合你的产品预期。
- Railway Postgres 是否作为数据库能力的唯一第一阶段来源。
- 左下 `设置` 中直接展示连接信息并允许复制，是否符合你的安全与产品预期。
