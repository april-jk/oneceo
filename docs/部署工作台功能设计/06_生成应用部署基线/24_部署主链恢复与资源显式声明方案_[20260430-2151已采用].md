# 部署主链恢复与资源显式声明方案 [20260430-2151已采用]

## 1. 背景

`23_Altus数据库与存储桶工具化接入方案_[20260430-1326已采用].md` 已经把 Railway Postgres / Bucket 接成了 Altus managed tools，也已经验证了资源创建、接入、部署和回收主链。

但上一阶段有一个边界收敛得不够严：

1. 模板基线会根据 `package.json` 依赖自动推断 `database=railway_postgres`
2. 部署工具会根据 `baseline.features.database / objectStorage` 直接做资源 gate

这会把“资源能力接入”反向污染“部署主链”：

- 某些本来只是带了 `pg` 依赖的项目，会被误认为必须先接平台数据库
- 部署主链从“只看可部署性”变成“被资源推断拦截”
- 这违背了部署主链必须保持泛化稳定的原则

本方案的目标不是推翻 23，而是把 23 中会误伤主链的部分收回来，然后把数据库/存储桶正式收敛为“Altus 显式声明后才进入约束”的旁路能力。

## 2. 目标

本次方案只解决两个问题：

1. 恢复部署主链保守稳定，不再因为依赖猜测被数据库/存储桶误拦截
2. 保留数据库/存储桶 managed tools，但改成显式声明资源需求，再由部署链在显式声明下做一致性校验

## 3. 非目标

本次不做以下事情：

- 不修改 Railway 发布执行器主逻辑
- 不修改数据库/存储桶真实创建、注入、回收实现
- 不新增新的资源类型
- 不把数据库/存储桶自动写入业务代码

平台仍只负责资源生命周期；如何在 Node / Python / PHP / Java 项目里接入这些资源，仍由 Altus 根据技术栈自行完成。

## 4. 核心设计

### 4.1 恢复部署主链保守态

部署主链只做两类判断：

1. 工作区是否满足部署基线
2. 当前会话是否已经显式声明需要某类平台资源

部署主链不再根据以下信号自动推断资源需求：

- `package.json` 是否包含 `pg`
- `package.json` 是否包含 `drizzle-orm`
- 未来其他语言包或 SDK 是否看起来像数据库 / 对象存储依赖

也就是说：

- `pg` 依赖不再自动触发数据库 gate
- `@aws-sdk/*` 之类依赖不再自动触发存储桶 gate
- 普通 HTML / 静态站 / Node / Python / PHP / Java 项目，不会再因为“像是可能用数据库”而被误拦

### 4.2 资源需求只认显式声明

数据库和存储桶能力改成“显式声明”模型。

显式声明来源只允许两类：

1. **工具声明**
   - Altus 调用了 `ensure_project_database`
   - Altus 调用了 `ensure_project_storage_bucket`
2. **manifest 强声明**
   - `oneceo.manifest.json` 明确写了：
     - `features.database = "railway_postgres"`
     - `features.objectStorage = true`

除这两类外，平台不再自行猜测当前项目是否需要平台资源。

补充约束：

- OneCEO 用户项目的托管数据库固定为 **Railway Postgres**
- OneCEO 用户项目的托管对象存储固定为 **Railway Bucket**
- Altus 不需要、也不应在当前主链里向用户追问数据库引擎类型
- Altus 不需要、也不应在当前主链里向用户追问对象存储类型
- 只要已经明确“需要数据库”，就直接按 Postgres 进入资源创建与接入
- 只要已经明确“需要对象存储”，就直接按 Railway Bucket 进入资源创建与接入

### 4.3 会话级资源声明状态

在 `task_creation_sessions.metadata_json` 中增加会话级资源声明：

```json
{
  "resourceDeclarations": {
    "database": {
      "requested": true,
      "provisioned": true,
      "source": "tool",
      "toolName": "ensure_project_database",
      "reason": "需要用户与业务数据持久化",
      "updatedAt": "2026-04-30T21:51:00.000Z"
    },
    "storage": {
      "requested": true,
      "provisioned": true,
      "source": "tool",
      "toolName": "ensure_project_storage_bucket",
      "reason": "需要文件上传",
      "updatedAt": "2026-04-30T21:51:00.000Z"
    }
  }
}
```

说明：

- 这是**当前会话对部署资源的显式意图**
- 不是跨用户全局配置
- 不是平台对代码依赖的猜测
- `get_*_status` / `inspect_*` 不会写入声明
- 只有 `ensure_*` 成功后才写入声明

### 4.4 部署阶段的资源一致性校验

部署时按以下顺序判断：

1. 先做现有模板基线检查
2. 再读取会话资源声明 + manifest 强声明
3. 只对被显式声明的资源做 ready 校验

规则如下：

- **未声明数据库 / 存储桶**
  - 不做对应资源 gate
  - 直接按普通部署主链继续

- **声明了数据库**
  - 必须确认当前项目已有 ready 的 Railway Postgres
  - 不满足则返回 `database_resource_missing`

- **声明了存储桶**
  - 必须确认当前项目已有 ready 的 Railway Bucket
  - 不满足则返回 `object_storage_resource_missing`

这样平台只在“Altus 已明确说要用”时才约束，不会反向绑架主部署链。

## 5. 代码改动范围

### 5.1 `template-compliance-service.ts`

目标：

- 取消数据库依赖自动推断进入 manifest fallback

具体调整：

- `buildDefaultManifest()` 默认：
  - `features.database = false`
  - `features.objectStorage = false`
- 保留 `databaseDependencyDetected` 作为**合规诊断信息**
- 保留显式 manifest 中 `features.database / objectStorage` 的读取与校验

结论：

- 依赖扫描仍可用于“manifest 与代码不一致”的提示
- 但不再用于“平台自动宣布这个项目需要数据库”

### 5.2 `altus-managed-resource-tool-service.ts`

目标：

- `ensure_*` 成功后写入资源声明
- `get_*_status` / `inspect_*` 只读不声明

具体调整：

- `ensure_project_database`
  - 创建或修复资源成功后，写入会话级数据库声明
- `ensure_project_storage_bucket`
  - 创建或修复资源成功后，写入会话级存储声明

### 5.3 `altus-managed-deployment-tool-service.ts`

目标：

- 取消基于依赖推断的自动资源 gate
- 只对显式声明资源做 gate

具体调整：

1. 删除当前“只看 `baseline.features.database / objectStorage` 就强制检查资源”的逻辑
2. 增加：
   - 读取会话资源声明
   - 结合 manifest 强声明
   - 仅在显式声明时校验资源 ready

### 5.4 Prompt / Tool 描述

需要同步更新 managed prompt / tool description：

- 明确 `ensure_project_database` 与 `ensure_project_storage_bucket` 会为当前会话记录资源使用声明
- 明确 Altus 不应为了“可能会用到”而提前调用资源工具
- 只有当需求或设计已经明确需要数据库 / 对象存储时，才调用对应工具

## 6. 风险分析

### 6.1 本方案解决的风险

1. 普通项目被数据库依赖误伤
2. 部署主链被资源判断污染
3. 平台代码通过硬编码依赖特征来替 Altus 做错误裁决

### 6.2 本方案保留的风险

1. Altus 可能显式创建了资源，但业务代码没有真正使用
2. manifest 强声明可能和最终代码不一致

这两类风险本次不通过平台猜测解决，而是通过后续验收约束解决：

- Altus 若调用了资源工具，应自行完成接入与验证
- manifest 若显式要求资源，部署时仍必须兑现

## 7. 验收条件

### 7.1 主链回归

以下项目不得因为资源推断被拦截：

1. 纯 HTML 项目
2. 普通静态站
3. 普通 Node Web 项目
4. 仅依赖中带 `pg`，但未显式声明数据库的项目

### 7.2 显式声明资源

以下链路必须成立：

1. Altus 调 `ensure_project_database`
2. 平台创建或复用 Railway Postgres
3. 会话 metadata 写入数据库声明
4. 后续部署时数据库 gate 生效

存储桶同理。

### 7.3 Manifest 强声明

若 `oneceo.manifest.json` 显式声明：

- `database = railway_postgres`
- 或 `objectStorage = true`

则部署时必须做对应 ready 校验，资源缺失时返回修复结果，而不是带病上线。

## 8. 实施顺序

1. 先修改文档与索引
2. 回收 `template-compliance-service.ts` 的自动数据库推断进入 fallback manifest
3. 增加会话级资源声明服务
4. 修改资源工具在 `ensure_*` 成功后写入声明
5. 修改部署工具只对显式声明资源做 gate
6. 回归测试：
   - template baseline
   - managed deployment tool
   - 最小主链回归

## 9. 结论

数据库和存储桶应该是 **Altus 主动声明、平台按声明供给** 的能力，而不是平台通过依赖猜测自动强加的约束。

本方案的收口原则只有一句：

**部署主链保持保守泛化；资源能力只在显式声明后进入部署约束。**
