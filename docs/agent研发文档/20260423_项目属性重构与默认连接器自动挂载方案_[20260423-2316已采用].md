# 20260423 项目属性重构与默认连接器自动挂载方案 [20260423-2316已采用]

更新时间：2026-04-23

## 1. 背景

当前用户态项目能力已经具备“创建普通项目 / 编辑项目 / 会话归属项目 / 项目级记忆注入”的最小闭环，但项目模型仍然偏历史阶段：

1. 项目弹窗字段仍是 `项目名称 + 项目描述 + Altus Project Memory（context/guidelines/operatingRules/executionManual）`
2. 前端弹窗位于 [Sidebar.tsx](/Users/watson/codingProj/oneceo/apps/web/client/src/components/Sidebar.tsx)，结构仍是通用表单，不符合当前产品形态
3. 后端项目真相源位于 `app_user_projects`，但项目级语义仍围绕 `description + altusProjectMemory`
4. 连接器系统已经独立演进为 `connector profile -> session connector binding -> runtime materialization`
5. 项目与连接器之间目前没有正式关联，因此“项目内会话默认使用哪些连接器”尚未闭环

用户现在要求把项目重新定义为：

1. `项目名称`
2. `项目指令`
3. `默认连接器`

并且：

1. 项目内新建会话时，默认连接器需要自动选择
2. 后端存储、项目记忆、会话创建默认行为都要随之重构
3. 先形成完整改造计划，再进入代码实现

## 2. 目标

本次目标不是“美化弹窗”，而是重构项目模型，使项目成为：

1. 一个轻量但正式的项目级操作上下文
2. 一个项目级默认连接器模板
3. 一个在新建会话时可自动继承的默认配置源

交付目标分四层：

1. 前端项目新建/编辑弹窗字段与交互重设计
2. 项目数据模型从 `description + altusProjectMemory` 收敛到 `instruction + defaultConnectorProfiles`
3. 新建会话时自动将项目默认连接器写入 connector draft / session binding
4. Altus 运行时继续能读取项目级上下文，但来源改为新的 `项目指令`

## 3. 非目标

本次明确不做：

1. 不做完整项目管理系统重构
2. 不做项目成员、项目权限、项目分享
3. 不做“一个项目绑定多个不同场景模板”
4. 不做项目级连接器运行态常驻
5. 不做旧字段长期兼容 UI
6. 不做前端补丁式“同时保留旧记忆字段和新指令字段”双写双读长期共存

## 5. 核心决策

### 5.1 项目属性改为三项

项目编辑/创建只保留：

1. `项目名称`
2. `项目指令`
3. `默认连接器`

对应语义：

1. `项目名称`：项目标签与会话归属展示名
2. `项目指令`：项目级共享操作上下文，替代旧 `altusProjectMemory`
3. `默认连接器`：项目下新会话默认启用的 connector profiles

### 5.2 “默认连接器”一期按多 profile 选择落地

虽然文案是“默认连接器”，但从系统事实看，session connector binding 本身天然支持多个 connector/profile 绑定。

因此本方案一期直接按“可选择 0~N 个默认 connector profiles”落地，而不是强行限制只能选 1 个。

理由：

1. 用户例子里已经表现出“项目 + GitHub + 数据库/部署场景”这种多连接器组合诉求
2. 当前 connector draft / session binding 已经是多 entry 结构
3. 若前端强行做单选，后续很快又要返工到多选

用户态文案仍保持“默认连接器”，但数据模型按“默认连接器集合”设计。

### 5.3 项目指令替代旧 Altus Project Memory

不再保留：

1. `context`
2. `guidelines`
3. `operatingRules`
4. `executionManual`

统一收敛为：

1. `projectInstruction: string`

Altus prompt 中项目级上下文改为单段块，而不是四段旧字段拼接。

### 5.4 存储仍优先复用 `metadata_json`

本次不新增项目表物理列，继续使用 `app_user_projects.metadata_json` 承载新增属性。

新的 `metadata_json` 结构建议：

```json
{
  "pinned": true,
  "projectInstruction": "数据库使用 Railway Postgres，推送到 GitHub 后自动部署。",
  "defaultConnectorProfiles": [
    {
      "connectorKey": "github",
      "profileId": "uuid-1"
    },
    {
      "connectorKey": "railway",
      "profileId": "uuid-2"
    }
  ]
}
```

## 6. 数据模型改造方案

### 6.1 项目 summary 返回结构调整

当前前端 `TaskCreationProjectSummary` 需要调整为：

```ts
type TaskCreationProjectDefaultConnector = {
  connectorKey: ConnectorKey;
  profileId: string;
  profileName?: string | null;
  displayName?: string | null;
};

type TaskCreationProjectSummary = {
  id: string;
  name: string;
  status?: string;
  pinned?: boolean;
  projectInstruction?: string;
  defaultConnectors?: TaskCreationProjectDefaultConnector[];
  createdAt?: string | null;
  updatedAt?: string | null;
};
```

移除：

1. `description`
2. `altusProjectMemory`

展示约束补充：

1. 当前项目树 / 项目页里原本展示 `description` 的位置，统一改为展示 `projectInstruction` 的首段摘要
2. 摘要只作为前端展示派生值，不新增独立存储字段
3. 若 `projectInstruction` 为空，则不显示副标题，也不再回退旧 `description`

### 6.2 DAO 改造

需要重构 [app-user-project.dao.ts](/Users/watson/codingProj/oneceo/apps/api/src/db/dao/app-user-project.dao.ts)：

新增/替换：

1. `normalizeProjectInstruction(value)`
2. `readProjectInstruction(metadataJson)`
3. `normalizeDefaultConnectorProfiles(value)`
4. `readDefaultConnectorProfiles(metadataJson)`

删除：

1. `AltusProjectMemory` 类型
2. `readAltusProjectMemory`
3. `normalizeAltusProjectMemory`

长度建议：

1. `name`: 80
2. `projectInstruction`: 8000
3. `defaultConnectorProfiles`: 最多 20 项

### 6.3 默认连接器 profile 校验

`defaultConnectorProfiles` 不能盲信前端。

创建/编辑项目时后端必须校验：

1. `profileId` 归属当前用户
2. `profileId` 对应 profile 存在
3. `profile.connectorKey === connectorKey`
4. profile 未被删除
5. 对于需要授权的连接器，若 profile 已失效，允许保存但返回 `authStatus` 给前端展示“需重新授权”
6. 返回给前端的 `profileName / displayName / authStatus` 必须由服务端基于 `userConnectorService.getProfileMaterial(...)` 重新解析，不能信任前端提交的显示文案

一期不做保存时强制 `authorized`，否则会阻塞用户先建项目再补授权的流程。

## 9. 默认连接器自动选择方案

### 9.1 触发时机

项目默认连接器自动带入的唯一正式触发点：

1. 用户在某项目上下文创建“新会话”
2. 会话尚未生成 sessionId
3. 前端需要先把项目默认连接器写入 connector draft
4. 首条消息成功创建 session 后，沿用现有 `applyPendingConnectorDraftAsync` 自动应用到该 session

这意味着：

1. 不直接在项目 API 中操作 session connector binding
2. 不直接在项目编辑后批量改已有 session 连接器
3. 只影响“后续新建会话”

### 9.2 前端自动带入流程

在 `new-task?projectId=...` 场景下：

1. 读取项目详情
2. 若项目存在 `defaultConnectors`
3. 自动把这些连接器 profile 写入当前 draft state
4. 同步调用 `saveSessionConnectorDraft(draftId, entries)`
5. 用户发送首条消息后，现有 `applyPendingConnectorDraftAsync` 继续把 draft 应用到新 session

为保证该流程和当前 draft 生命周期自洽，前端本地 draft state 需要补充元信息：

1. `source: "manual" | "project_default"`
2. `sourceProjectId?: string`
3. `userTouched: boolean`

用途：

1. 区分“项目自动注入”与“用户手动选择”
2. 支撑未发送首条消息前的切项目替换规则
3. 与现有“首条消息成功后清空 draft”行为兼容，不影响 session 创建后的清理

### 9.3 冲突规则

新建会话页若用户手动改过连接器选择，项目默认连接器不应重复覆盖。

规则建议：

1. 仅在“进入 new-task 且当前 draft 为空”时自动注入项目默认连接器
2. 若当前 draft 已存在 entry，只有当 `source === "project_default"` 且 `userTouched === false` 时，才允许被新的项目默认连接器替换
3. 若当前 draft 已存在 entry，且 `source === "manual"` 或 `userTouched === true`，则视为用户已手动选择，不再自动覆盖
4. 若切换项目后仍处于未发送状态：
   - 若当前 draft 来自旧项目默认连接器且用户未手动改动，则清空旧项目自动注入 entry，再注入新项目默认连接器
   - 若用户已手动编辑过，则保留现有选择，不做自动替换

一期建议采用最短路径：

1. 不做复杂冲突 UI
2. 但必须补齐上述 draft 来源标记，否则“切项目替换”与“手动选择保护”无法落地

### 9.4 自动选择的“相关连接器”定义

这里的“自动选择相关连接器”本质上不是推理新连接器，而是：

1. 自动带入该项目已配置好的默认 connector profiles

一期不做：

1. 根据项目指令 NLP 猜测要不要选 GitHub / Railway / Notion
2. 后端自动推荐连接器

否则语义会失控。

### 9.5 未授权 profile 的自动挂载语义

保存项目时允许 `authStatus !== authorized` 的 profile 留在 `defaultConnectors`，但自动挂载到 session 时不能静默表现成“已经成功附着”。

约束：

1. 若 profile 已删除、归属不匹配或 `connectorKey` 不匹配，则跳过并写 warn 日志
2. 若 profile 存在但 `authStatus !== authorized`，则 session binding 应按现有连接器 attach 语义落成 `needs_auth`，而不是继续排队 recover
3. 也就是说，“可保存”不等于“自动挂载后直接可用”，前端需要能看到该连接器处于待授权状态

## 13. 迁移方案

### 13.1 数据迁移

新增一次 migration / backfill：

1. 扫描 `app_user_projects.metadata_json`
2. 把旧 `altusProjectMemory` 合并为 `projectInstruction`
3. 若无 `defaultConnectorProfiles`，补空数组
4. 保留 `pinned`
5. 删除旧 `altusProjectMemory`

### 13.2 运行期容错

为了避免迁移前短暂读旧数据崩溃：

1. 后端读取项目时，若无 `projectInstruction` 但有旧 `altusProjectMemory`，可临时在服务端做一次只读 fallback
2. fallback 只用于迁移窗口期
3. 迁移完成后移除该 fallback

这不是兼容方案，而是迁移窗口保护。

发布步骤固定为：

1. 后端先进入 tolerant read 状态
2. 再执行 migration / backfill
3. 再切前端 UI 与 API 调用
4. 稳定后删除 fallback

## 16. 风险

### 风险 1：旧项目记忆丢失

若直接删 `altusProjectMemory` 而不迁移，项目级上下文会被清空。

约束：

1. 发布顺序必须是“后端 tolerant read -> migration -> 前端切新字段 -> 移除 fallback”

### 风险 2：项目默认连接器误覆盖用户手动选择

若项目默认连接器每次进入 new-task 都强制覆盖，会破坏用户操作。

约束：

1. 只有在 `draft` 为空，或当前 `draft` 明确来自“未手动修改的项目默认连接器”时，才允许自动注入 / 替换

### 风险 3：项目引用失效 profile

若项目绑定的 profile 被删除或失效，编辑页和自动挂载会异常。

约束：

1. 列表返回时带 profile 有效性
2. 已删除或归属不匹配的 profile 才跳过并写 warn 日志
3. `needs_auth` profile 不跳过，而是落成 session 的待授权状态，避免用户误以为该连接器已正常可用

## 17. 本轮建议结论

建议按以下范围实施：

1. 项目模型收敛为 `name + projectInstruction + defaultConnectors`
2. 默认连接器按“多 profile 集合”落地
3. 项目默认连接器只影响“后续新建会话”
4. 自动挂载复用现有 connector draft -> apply 流程
5. 旧 `altusProjectMemory` 通过 migration 合并进 `projectInstruction`

这是最短路径，且不会破坏现有连接器主链。
