# PPT 技能附件上传 400 问题与低风险修复方案

更新时间：2026-03-27  
状态：已修复并完成最小链路复测  
适用范围：`apps/web` 技能附件上传、`apps/api` task session runtime provision、E2B sandbox/OpenCode 预检

## 1. 问题现象

用户在任务创建页点击 `PPT 办公` 技能后，前端会先生成一个本地 markdown 附件，再通过附件上传接口提交到当前 task session。

实际表现为：

1. 前端提示 `request failed: 400`
2. 后端日志记录 `上传附件失败`
3. 该错误只要触发附件上传就会出现，不限于 `PPT 办公`，`Word 文档`、`Excel 表格` 等 skill brief 附件同样会受影响

## 2. 复现链路

完整链路如下：

1. 前端在 [AttachmentPickerButton.tsx](/D:/oneceo-task-creation-agent-fresh/apps/web/client/src/components/AttachmentPickerButton.tsx) 将 skill 模板包装为 `skill-*.md` 文件
2. 发送消息前，前端先调用附件上传接口
3. 后端在 [task-creation-routes.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/routes/task-creation-routes.ts) 的附件上传路由里执行 `ensureTaskSessionRuntime(sessionId)`
4. runtime provision 进入 [sandbox-agent-provision-service.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/services/sandbox-agent-provision-service.ts) 并执行 `sandbox_verify`
5. `sandbox_verify` 内部对 LLM 网关做连通性校验失败，后端最终将错误包装为 `400`

## 3. 根因分析

根因不是 `PPT 办公` skill 模板内容错误，而是 Sandbox 直连链路错误复用了平台主链路的 LLM 协议配置。

当前配置冲突如下：

1. 平台主链路使用 `OPENAI_BASE_URL=https://llmapi.oneceo.ai/v1`
2. 同时设置 `LLM_PROXY_UPSTREAM_API_TYPE=anthropic`
3. Sandbox 预检脚本会读取 `LLM_PROXY_UPSTREAM_API_TYPE` 决定调用 `/messages` 还是 `/chat/completions`
4. 但当前 Sandbox/OpenCode 实际仍按 OpenAI-compatible 方式工作

这会导致：

1. Sandbox 预检把网关请求误打到 `/v1/messages`
2. 该请求与当前 Sandbox 直连的网关口径不匹配
3. `sandbox_verify` 返回 `exit status 15`
4. 附件上传路由捕获异常后向前端返回 `400`

后端日志中的关键错误为：

```text
上传附件失败: Error: [PROVISION:sandbox_verify] exit status 15
```

## 4. 修复目标

本次修复遵循“低风险、最短路径、只修根因”的原则：

1. 不关闭 `sandbox_verify`
2. 不修改主平台 `llm-proxy` 的协议行为
3. 不引入兼容性兜底或降级逻辑
4. 仅为 Sandbox 直连链路增加独立配置，切断与主平台协议配置的错误耦合

## 5. 低风险修复方案

### 5.1 代码改动

在 [sandbox-agent-provision-service.ts](/D:/oneceo-task-creation-agent-fresh/apps/api/src/services/sandbox-agent-provision-service.ts) 的 `buildSandboxEnv()` 中增加 Sandbox 专用环境变量覆盖：

- `SANDBOX_OPENAI_API_KEY`
- `SANDBOX_OPENAI_BASE_URL`
- `SANDBOX_OPENAI_MODEL`
- `SANDBOX_OPENAI_API_TYPE`

修复后的行为：

1. 如果存在 `SANDBOX_OPENAI_*`，Sandbox 在下发环境变量时优先使用这套配置
2. 同步覆盖 `OPENAI_*`、`CODEX_*`、`OPENCODE_*`
3. 仅在 Sandbox 内部将 `LLM_PROXY_UPSTREAM_API_TYPE` 强制设为 `openai`
4. `opencode.json` 与 `sandbox_verify` 使用同一套直连口径

### 5.2 环境配置改动

在 [apps/.env](/D:/oneceo-task-creation-agent-fresh/apps/.env) 中新增 Sandbox 独立配置：

1. `SANDBOX_OPENAI_API_KEY`
2. `SANDBOX_OPENAI_BASE_URL`
3. `SANDBOX_OPENAI_MODEL`
4. `SANDBOX_OPENAI_API_TYPE=openai`

这组配置仅用于 Sandbox/E2B 直连，不影响平台主链路现有的 `OPENAI_BASE_URL`、`LLM_PROXY_UPSTREAM_API_TYPE`、`OPENCODE_MODEL`。

## 6. 风险评估

本方案属于低风险修复，原因如下：

1. 修改范围仅限 Sandbox provision 阶段
2. 不改变前端 skill 附件逻辑
3. 不改变平台主链路的大模型供应商与协议
4. 不跳过预检，只是让预检读取正确配置

已知影响范围：

1. 新建或恢复 Sandbox 时会优先读取 `SANDBOX_OPENAI_*`
2. Sandbox 内 OpenCode 的默认模型从主链路配置解耦
3. 如果后续要切换 Sandbox 直连网关，只需改 `SANDBOX_OPENAI_*`，不需要再动平台主链路

## 10. 结论

本问题的直接根因是“Sandbox 直连链路错误复用了平台主链路的协议配置”，而不是 skill 模板本身错误。

本次修复通过增加 `SANDBOX_OPENAI_*` 独立配置，将 Sandbox 直连链路与平台主链路解耦，属于最短路径、低风险、可验证、可回退的修复方案。
