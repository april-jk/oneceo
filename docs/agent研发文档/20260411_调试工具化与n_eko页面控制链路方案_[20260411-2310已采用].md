# 20260411 调试工具化与 n.eko 页面控制链路方案 [20260411-2310已采用]

## 1. 背景

当前“启动网站调试功能”主要通过自然语言触发，缺少独立的工具语义：

1. 模型可能把“调试”理解为普通命令执行，无法稳定走统一调试链路。
2. 无法表达“先启动服务，再让 n.eko 浏览器打开目标页面”的可组合工具流程。
3. 调试动作在事件流里缺少稳定工具名，不利于观测与复盘。

你提出的目标是：参照 Suna 的工具化思路，把调试能力做成可被模型准确识别、可重复调用、可与其他工具协同的专用工具。

## 2. 参照 Suna 的实现依据

本方案直接参考 `referance/suna/backend/core/tools/browser_tool.py` 的三点设计思想：

1. 能力以独立工具注册（不是提示词临时约定）。
2. 工具职责清晰、参数结构化、可多次调用。
3. 工具可与其他工具串联（例如先操作环境，再做浏览器动作）。

本方案不照搬 Suna 的 Stagehand 浏览器栈，只吸收“工具化与编排”模式；实际执行仍使用 oneceo 现有 E2B + OSAC + n.eko 链路。

## 3. 目标与非目标

### 3.1 目标

1. 新增 Altus managed 专用工具 `debug_open_page`，让模型通过工具调用而不是自由文本命令触发调试链路。
2. 支持“非一次性调用”：同一 run 内可多次调用，并与 `shell_execute` 等工具组合。
3. 工具执行统一复用现有 `ensureNekoDebug`，并通过 Chromium CDP 打开指定页面。
4. 在 run 事件流中稳定记录 `tool_call_started/completed` 的工具名 `debug_open_page`，便于排障。

### 3.2 非目标

1. 不新增第二套调试服务端口或新 sandbox 调试架构。
2. 不改 `kvm-orchestrator` 主链路（继续停用）。
3. 不引入 Suna Stagehand/browser API 依赖。

## 4. 方案设计（最短路径）

### 4.1 新增工具定义

在 `apps/api/src/services/altus-managed-shared.ts` 的 `buildManagedToolDefinitions()` 增加：

1. 工具名：`debug_open_page`
2. 参数：
   - `url`（string，必填）：要在 sandbox 内 Chromium 打开的 URL（支持 `http`/`https`，可含路径、查询参数与锚点）。
     - 示例1：`http://127.0.0.1:3000`
     - 示例2：`http://127.0.0.1:3000/folder1/`
     - 示例3：`http://127.0.0.1:3000/folder1/index.html`
     - 示例4：`http://127.0.0.1:3000/app?tab=debug`
     - 示例5：`http://127.0.0.1:3000/app?tab=debug#section-2`
     - 示例6：`https://example.com/docs/getting-started`
   - `ensureDebug`（boolean，选填，默认 `true`）：调用前是否确保 n.eko 调试已就绪。
3. 描述中明确关键短语：`启动网站调试功能`、`打开调试页面`、`在 n.eko 中打开页面`。

### 4.2 工具运行时执行逻辑

在 `apps/api/src/services/altus-managed-tool-runtime.ts` 的 `execute()` 中新增 `debug_open_page` 分支：

1. 参数校验：`url` 必须为非空字符串，且必须是 `http://` 或 `https://`。
   - 保留并透传完整 path/query/hash（例如 `/folder1/`、`?tab=debug`、`#section-2`），不做路径截断与重写。
   - 若用户仅提供主机或缺协议（如 `127.0.0.1:3000/folder1/`），返回明确错误，提示补全为 `http://127.0.0.1:3000/folder1/`。
2. 当 `ensureDebug=true` 时：
   - 调用 `ensureNekoDebug(this.input.sandboxId)`，复用既有调试启动链路。
3. 用 `e2bConnector.runCommand` 通过 Chromium CDP 打开页面：
   - 优先调用 `PUT http://127.0.0.1:${cdpPort}/json/new?{encodedUrl}`。
   - 若失败，回退一次 `GET` 方式（兼容不同 Chromium 行为）。
4. 返回结构化结果（`type: result`）：
   - `targetUrl`
   - `debugUrl`（n.eko 访问地址）
   - `ready`
   - `status`
   - `sandboxId`
   - `cdpPort`
5. 该工具执行后调用 `markWorkspaceDirty('managed_debug_open_page')`，与现有运行时脏标记机制保持一致。

### 4.3 提示词与识别规则

在 `apps/api/src/services/altus-managed-prompt-service.ts` 的 `# Tool usage rules` 增加明确规则：

1. 当用户要求“启动网站调试功能 / 打开调试页面 / 在调试窗口打开某网站”时，优先调用 `debug_open_page`。
2. 若目标站点未运行，先用 `shell_execute` 启动服务，再调用 `debug_open_page`。
3. 禁止通过临时 `docker-compose/install.sh` 文本命令替代该工具链路。

这保证“文本意图 -> 专用工具”映射稳定，不依赖偶然 prompt 理解。

### 4.4 与前端触发入口的关系

前端保留现有“执行环境未启动”按钮发送固定文本 `启动网站调试功能` 的行为，不新增前端协议。

后端通过新工具定义 + 提示词规则完成稳定识别并落到调试工具链路。

## 5. 典型编排流程（非一次性）

用户意图：启动本地站点并在调试画面打开。

1. `shell_execute`：`pnpm dev --host 0.0.0.0 --port 3000`（或项目实际启动命令）。
2. `debug_open_page`：`url=http://127.0.0.1:3000`。
3. 若页面路由切换，再次调用 `debug_open_page`：`url=http://127.0.0.1:3000/admin`。

以上过程中 Altus 可继续调用 `read_file/search_code/shell_execute` 等工具，不会因调试工具调用而终止流程。

## 7. 验证方案

1. 单测：
   - `debug_open_page` 参数校验（空 URL / 非 http(s) URL）。
   - `ensureDebug=true` 时调用 `ensureNekoDebug`。
   - CDP 打开成功时返回结构化结果。
2. 类型检查：
   - `pnpm --filter api type-check`
3. 最小链路联调：
   - 发送“启动网站调试功能”；
   - 观察 run 事件中出现 `tool_call_started/debug_open_page`；
   - 调试页可打开目标 URL。

## 8. 风险与约束

1. Chromium CDP `/json/new` 在不同版本可能存在方法差异（PUT/GET），因此在工具内部一次性兼容两种请求方式。
2. 若 sandbox 内目标服务未启动，`debug_open_page` 只负责打开页面，不负责猜测业务启动命令；应由 Altus 先调用 `shell_execute` 启动服务。

## 9. 评审结论

1. 工具名采用：`debug_open_page`。
2. URL 协议约束采用：仅 `http/https`（调试场景允许 `http`，不开放 file/data 等协议）。
3. 本方案已确认进入实现，文档状态更新为 `[20260411-2310已采用]`。
