# 08 数据模型、存储与迁移

## 1. 设计原则

managed mode 的存储改造遵循以下原则：

1. `task_session` 保留，作为会话容器
2. managed mode 新增 `run` 层
3. managed mode 不再以 `file-memory-store` 作为权威状态
4. direct mode 现有存储链路不动
5. 前端如果需要预生成 `sessionId`，必须生成合法 UUID，不能使用任意字符串占位

## 2. 建议数据对象

### 2.1 复用对象

- `task_creation_sessions`
- `task_creation_messages`

### 2.2 新增对象

- `task_session_runs`
- `task_session_run_events`
- `task_session_sandbox_bindings`
- `task_session_connector_snapshots`

## 3. 表意说明

### 3.1 `task_session_runs`

字段建议：

- `id`
- `session_id`
- `mode` 固定为 `managed`
- `status`
- `started_at`
- `completed_at`
- `stop_reason`
- `sandbox_binding_id`
- `connector_snapshot_id`
- `model`
- `metadata_json`

### 3.2 `task_session_run_events`

字段建议：

- `id`
- `run_id`
- `session_id`
- `event_type`
- `payload_json`
- `sequence`
- `created_at`

### 3.3 `task_session_sandbox_bindings`

字段建议：

- `id`
- `session_id`
- `sandbox_id`
- `workspace_root`
- `status`
- `last_active_at`

## 4. file-memory-store 处理原则

本次明确口径：

- `file-memory-store` 退出 managed mode 主链路
- direct mode 可继续使用当前实现

不采用：

- 在 managed mode 内继续 DB/file 双写
- 用 file-memory-store 作为 managed 的热缓存权威源

## 5. 历史迁移原则

由于本次只重构 managed mode，因此历史迁移只需要满足：

1. 老 session 仍可查看历史消息
2. 新的 managed run 只读已有会话消息
3. 不要求将旧的 `intent/planning/execution_plan` 中间消息转换为新 run event

换句话说：

- 旧历史保留
- 新 managed run 使用新结构
- 不做复杂历史补录

## 6. 数据边界

direct mode 的以下数据继续保持原样：

- executor runtime binding
- opencode/codex session id
- direct mode 事件回流表述

managed mode 的新表不反向侵入 direct mode。

## 7. 设计结论

数据层的关键动作只有两个：

1. 让 `session` 成为稳定的对话容器
2. 为 managed mode 新增独立 `run + run_event` 层

这足以支撑后续对话智能体重构，无需在 managed 模式内保留旧状态存储方案。

## 8. Suna 代码参照

本篇数据建模应直接对照 `suna` 的持久化入口：

- `referance/suna/backend/core/threads/repo.py` -> `create_thread_with_message_and_run(...)`
  - 说明 thread、首条 message、首个 run 可以在同一事务语义下初始化，但仍是独立对象。
- `referance/suna/backend/core/threads/repo.py` -> `create_message_full(...)`
  - 说明消息有独立存储边界，不依赖执行态缓存。
- `referance/suna/backend/core/agents/repo.py` -> `create_agent_run_with_id(...)`
  - 说明 run 拥有独立表意和生命周期。
- `referance/suna/backend/core/agents/repo.py` -> `get_agent_run_with_thread(...)`
  - 说明 run 与 thread 的关联查询是基础能力。
- `referance/suna/backend/core/agents/repo.py` -> `update_agent_run_status(...)`
  - 说明 run 状态落库必须与 message 层分离。

oneceo 的表结构命名可以不同，但结构关系必须对齐为：

- `session/thread-like container`
- `message history`
- `run`
- `run event`

不得再让 managed mode 继续依赖 `file-memory-store` 承担权威执行态。
