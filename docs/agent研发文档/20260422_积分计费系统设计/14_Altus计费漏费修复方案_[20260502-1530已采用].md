# 14_Altus 计费漏费修复方案 [尚未采用]

## 更新时间

2026-05-02

## 关联背景

1. Altus managed run 多轮 tool call 循环中，LLM 调用先执行、计费后扣减（后付费模式）
2. 当某轮扣费时余额不足，`deductCredits` CAS 失败返回 `success: false`，不写入 `credit_transactions` 也不写入 `token_usage_logs`
3. 结果：LLM token 已在上游消费（平台已产生成本），但管理端查不到任何计费记录——漏费
4. 同时，余额检查仅在 run 启动时执行一次，循环中间无预检，导致余额耗尽后仍会白调 LLM

## 1. 问题定位

### 1.1 漏费路径

```
runModelLoop for each round:
  1. callModelWithRetry()  →  LLM 流式返回完整响应（token 已在上游消费）
  2. chargeForModelCall()  →  deductCredits() + logTokenUsage()
```

`chargeForModelCall`（altus-run-coordinator.ts:431-593）的执行逻辑：

- `deductCredits` 成功（`success: true`）→ 写入 `credit_transactions` + `logTokenUsage` 写入 `token_usage_logs`
- `deductCredits` 失败（余额不足，`success: false`）→ 抛出 `insufficient_credits`，**不写 `token_usage_logs`**
- 重试也失败 → 仅 console.error，**不写任何表**

### 1.2 止损缺失

余额检查仅在 run 启动时执行（altus-run-coordinator.ts:2722），`runModelLoop` 的 for 循环内无余额预检。多轮场景下前面几轮把余额花完，后续轮次白调 LLM。

## 2. 修复方案

### 2.1 止血：扣费失败时仍记录 token_usage_logs

**改动位置**：`altus-run-coordinator.ts` 的 `chargeForModelCall` 方法

**改动内容**：

1. 将 `logTokenUsage` 调用从 `if (result.success)` 分支内移出，改为**无论扣费成功与否都写入**
2. 扣费失败时，`logTokenUsage` 的 `metadataJson` 中追加 `billed: false` 标记，便于管理端区分
3. 重试路径同理：重试也失败时，仍然写入 `logTokenUsage`（标记 `billed: false` + `retryFailed: true`）

**改动前逻辑**（简化）：

```typescript
if (result.success) {
  console.log(`[Billing] 扣费成功`);
  await billingService.logTokenUsage({ ... });  // 只在成功时记录
} else {
  throw new Error(`insufficient_credits: ...`);
}
```

**改动后逻辑**（简化）：

```typescript
// 无论扣费成功与否，都记录 token 使用日志
const isBilled = result.success;
if (!isBilled) {
  console.error('[Billing] 扣费失败（余额不足），仍记录 token 使用日志');
}
await billingService.logTokenUsage({
  ...,
  metadataJson: {
    ...metadataJson,
    billed: isBilled,  // 标记是否成功扣费
    ...(isBilled ? {} : { unbilledReason: 'insufficient_credits' }),
  },
});

if (!isBilled) {
  throw new Error(`insufficient_credits: ...`);
}
```

重试路径同理：重试也失败时写入 `logTokenUsage`，标记 `billed: false, retryFailed: true`。

### 2.2 止损：每轮循环前做余额预检

**改动位置**：`altus-run-coordinator.ts` 的 `runModelLoop` 方法，for 循环开头

**改动内容**：

在 for 循环体开头（round 检查之后、LLM 调用之前）加入余额预检：

```typescript
for (let round = 0; round < maxToolRounds; round += 1) {
  if (signal.aborted) {
    throw new Error('managed_run_aborted');
  }

  // 新增：每轮循环前余额预检
  const userId = state.input.userId;
  if (userId) {
    const hasEnough = await billingService.hasEnoughCredits(userId, 0);
    if (!hasEnough) {
      const credits = await billingService.getUserCredits(userId);
      await this.eventWriter.appendRunEvent(
        state.input.runId,
        state.input.sessionId,
        userId,
        'run_status',
        {
          status: 'failed',
          content: `积分不足，无法继续运行。当前余额: ${credits?.balance || 0} 积分`,
        }
      );
      throw new Error(`insufficient_credits: 积分不足，无法继续运行`);
    }
  }

  // ... 原有逻辑
}
```

## 3. 不涉及变更

- `billing-service.ts` 的 `deductCredits` 方法不变——CAS 机制正确，余额不足时不应写入 `credit_transactions`
- `token_usage_logs` 表结构不变——`billed` 标记放在 `metadataJson` JSON 字段内，无需加列
- 不引入预扣费模式——改动面过大且 token 估算不精确

## 4. 影响范围

- `apps/api/src/services/altus-run-coordinator.ts`：`chargeForModelCall` 方法 + `runModelLoop` 方法
- 管理端 `token_usage_logs` 查询：新增 `billed: false` 记录后，管理端可按此标记筛选漏费记录
- 用户端无影响——用户端只看 `credit_transactions`（扣费成功才有记录），不受影响

## 5. 验证方式

1. 模拟余额不足场景：给测试用户设极低余额，触发 managed run，确认：
   - `token_usage_logs` 中有 `billed: false` 的记录
   - `credit_transactions` 中没有对应的扣费记录（余额不足不应凭空扣费）
   - 管理端 usage-logs 页面能看到该笔消费
2. 模拟多轮循环余额耗尽场景：确认第二轮开始前预检生效，不会白调 LLM
3. 正常余额场景回归：确认扣费成功时行为不变，`billed` 为 `true` 或不出现
