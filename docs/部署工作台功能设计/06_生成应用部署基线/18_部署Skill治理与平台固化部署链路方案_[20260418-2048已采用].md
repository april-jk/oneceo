# 部署 Skill 治理与平台固化部署链路方案 [20260418-2048已采用]

更新时间：2026-04-18

## 1. 背景

当前 OneCEO 已经分别具备以下能力：

1. 部署工具链：
   - `deploy_application`
   - `redeploy_application`
   - `rollback_application_deployment`
   - `get_application_deployment_status`
2. 平台侧模板合规修复、Railway 发布、Umami 注入、部署状态后台同步
3. Altus managed run 自动挂载 deployment skill 的第一版实现思路
4. 管理后台对平台 skill 的 revision、资源、导入、发布治理能力

但当前链路仍然存在一个结构性问题：

1. 平台已经把“部署”做成了一个主链能力
2. 运行时差异又开始通过 prompt / seed / 局部判断持续堆积
3. 未来如果要支持新的语言、框架、设计模式，仍然容易回到改硬编码的路径

用户希望的目标很明确：

1. 部署主链本身必须稳定，不因不同语言项目而反复改平台硬编码
2. 部署所依赖的“运行时识别、修复顺序、语言指导、模板补齐规则”要抽到 skill 治理层
3. 管理端 `skills 管理` 必须能统一治理这套 deployment skill
4. 后续要适配 Python / Java / PHP / HTML / JavaScript / Node.js 等项目时，应优先通过修改 deployment skill revision 完成，而不是再改业务代码

## 2. 结果导向结论

本次方案的核心结论只有一条：

**部署链路分成“平台固化层”和“Skill 治理层”两层。**

其中：

1. 平台固化层负责：
   - Railway 资源操作
   - Umami 站点注入与统计契约
   - 仓库导出与发布
   - 部署状态后台同步
   - 资源绑定、鉴权、持久化、审计
2. Skill 治理层负责：
   - 项目形态识别
   - 不同语言 / 脚本 / 框架的部署指导
   - 发布前修复顺序
   - 语言相关的基线补齐规则
   - 发布后验证顺序

这样做以后：

1. 平台仍然掌握“怎么真正发到 Railway、怎么注入 Umami、怎么拿状态”的唯一执行权
2. 技能层只负责“Altus 在发之前和发的时候应该如何判断与修复”
3. 新语言支持优先通过 Skills 管理后台发布新 revision 完成
4. 平台代码只在新增真正的底层能力时才需要改动

## 3. 现有问题归纳

基于当前已采用方案与近几轮问题，可以把症结归纳成四类：

### 3.1 平台固定能力与运行时指导边界不清

当前有些内容其实应该永远固化在平台：

1. Railway project / service / environment / repo token 的绑定与修复
2. Umami website 创建、最终域名回写、注入契约
3. 部署状态后台同步与部署面板读模型

但另一些内容本来就应该抽成可变知识：

1. 某个 Python 项目该看 `requirements.txt` 还是 `pyproject.toml`
2. 某个 Java 项目优先识别 Maven 还是 Gradle
3. 某个静态 HTML/JS 项目应该补哪些入口和健康检查

这两类内容如果都继续堆在平台代码里，系统会越来越不稳定。

### 3.2 deployment skill 第一版仍偏“自动挂载”，还不够“后台治理”

第一版方案解决了“部署时自动附加 skill”的问题，但还没有彻底解决：

1. skill 的治理入口是否完全落在管理端
2. deployment skill 是否有明确的平台角色元数据
3. 是否能在后台清楚看见“哪些部署动作会自动加载它”
4. 是否能通过 revision 发布替换语言指导，而不影响平台底层执行器

### 3.3 新语言 / 新设计模式的扩展仍然容易回落到硬编码

如果没有明确规定“哪些问题必须通过 skill 解决”，未来非常容易出现：

1. 为某个语言在 `AltusManagedInputService` 里再加一段判断
2. 为某个框架在 deploy service 里再塞一段修复逻辑
3. 为某个模板在 prompt 里追加一段说明

这样会再次把部署主链拖回不可治理状态。

### 3.4 管理后台没有把 deployment skill 当成“系统治理资产”来展示

用户希望能在管理端一并治理 deployment skill，这意味着后台不只是“能编辑一个普通 skill”，还要清楚表达：

1. 这是系统级 deployment skill
2. 它会在部署链路中自动加载
3. 它是平台固化部署链路的指导层，而不是普通用户附件
4. 它的修改会影响哪些部署动作

## 4. 两层模型

### 4.1 平台固化层

这一层继续由代码固化，不能交给 skill 自由改写。

职责边界如下：

1. Railway 部署执行
   - 创建 / 绑定 project、service、environment、repo、token
   - 调用 Railway API
   - 追踪 deployment source 与 deployment runtime
2. Umami 注入执行
   - 创建 / 查找 website
   - 回写最终域名
   - 生成平台统计脚本注入所需配置
   - 维护平台级统计契约
3. 部署状态同步
   - 后台 job 拉取 Railway 状态
   - 持久化 deployment status
   - 更新部署工作台卡片
4. 合规检查底层能力
   - manifest
   - build/start command
   - health check
   - analytics injection presence
   - 资源绑定检查
5. 安全边界
   - 用户隔离
   - 凭证隔离
   - project ownership
   - 平台日志与审计

这一层的原则是：

**skill 可以指导 Altus 怎样准备项目，但不能决定平台怎样越过这条固化链路去部署。**

### 4.2 Skill 治理层

这一层由管理后台治理，以 revision 为最小变更单位。

职责边界如下：

1. 项目形态识别
   - HTML / static JS
   - Node.js
   - Python
   - Java
   - PHP
   - 后续新增语言 / 框架
2. 入口探测顺序
   - 哪些文件优先看
   - 哪些构建工具优先识别
   - 哪些启动入口优先认定
3. 基线补齐指导
   - 缺 manifest 怎么处理
   - 缺健康检查怎么处理
   - 缺运行入口怎么处理
   - 哪些文件可以改、优先改什么
4. 发布前修复顺序
   - 模板合规问题怎么修
   - 部署配置问题怎么修
   - 哪些问题必须回到平台资源修复
5. 发布后验证顺序
   - 怎么判断这次成功的是线上部署，而不是本地预览
   - 什么时候继续调用状态工具
   - 什么时候结束 run，什么时候继续修

这一层的原则是：

**skill 负责指导，平台负责执行。**

## 5. deployment skill 的治理模型

### 5.1 唯一系统角色

平台必须有一个明确的系统级 deployment skill 角色：

1. `systemRole = deployment_orchestrator`
2. `category = deployment`
3. `adminManaged = true`
4. `autoActivation = deployment`

其中：

1. `slug` 可以继续是 `deployment-orchestrator`
2. 但自动加载不应该再只依赖硬编码 slug
3. 自动加载应优先基于系统角色元数据判断

原因很简单：

1. 后续 skill 的正文和资源会迭代
2. 甚至 slug 也可能调整
3. 但“部署编排”这个平台角色不能丢

### 5.2 revision 作为唯一配置面

未来这套 deployment skill 的修改应统一走：

1. 管理后台打开 skill
2. 新建或编辑 draft revision
3. 修改正文和资源
4. 预览
5. 发布 revision

发布后由平台自动把新的 published revision 用到部署场景。

### 5.3 资源拆分原则

deployment skill 的正文应保持短而稳定，重点写规则，不要把所有语言细节堆进主 entry。

推荐资源结构：

1. `references/runtime-classifier.md`
2. `references/deploy-repair-loop.md`
3. `references/railway-contract.md`
4. `references/umami-contract.md`
5. `references/static-html-js.md`
6. `references/nodejs.md`
7. `references/python.md`
8. `references/java.md`
9. `references/php.md`
10. 后续新增：
   - `references/go.md`
   - `references/rust.md`
   - `references/nextjs.md`
   - `references/fastapi.md`
   - `references/springboot.md`

规则：

1. 主 body 只写工作流原则
2. 各语言细节都下沉到 references
3. Altus 按需读取，而不是一次性全部塞入上下文

### 5.4 管理端治理字段必须改成受控选择

`skills 管理` 中以下治理字段不允许继续使用自由输入框：

1. `systemRole`
2. `autoActivation.triggers`
3. `autoActivation.toolNames`

原因：

1. 这三个字段都直接参与系统行为，不属于普通内容编辑
2. 一旦手填拼错，运行时不会报编译错误，只会表现为自动挂载失效或行为偏移
3. deployment skill 的目标本来就是“后台治理替代硬编码”，因此后台配置必须同样可治理、可枚举、可审计

落地规则：

1. 选项源由 API 统一下发，不能在前端自行维护硬编码副本
2. `toolNames` 必须直接从平台 `buildManagedToolDefinitions()` 推导，确保和 Altus 当前真实可用的平台内建工具保持一致
3. 当前受控工具集合只覆盖平台内建 managed tools；动态 MCP 工具不进入该治理枚举，避免把运行时连接器波动混入平台级 skill 治理
4. 管理端只允许通过下拉 / 多选勾选配置，不再允许直接输入原始字符串

## 6. 自动加载规则

### 6.1 触发来源

deployment skill 应在以下场景自动加载：

1. 用户显式点击部署相关功能
   - deploy
   - redeploy
   - rollback
   - status
2. 用户在会话里表达明确部署意图
   - 部署
   - 发布
   - 上线
   - 重新部署
   - 回滚部署
   - 查询部署状态

### 6.2 自动加载方式

自动加载应继续走现有 skill 解析链，不额外开新通道，但要同时支持“文本意图触发”和“工具触发”两条治理入口：

1. 文本意图触发：
   - 先识别这次输入是 deployment action
   - 从平台 skill catalog 中解析当前 `systemRole=deployment_orchestrator` 的 published revision
   - 若用户没有显式重复选择，则自动把它加入本次 managed skill selections
2. 工具触发：
   - 管理端可在 skill governance 中配置 `autoActivation.toolNames`
   - 当 Altus 运行时真正调用到对应 tool 时，平台在 tool runtime 内自动补挂对应 skill
   - 自动补挂后，该 skill 需要立即同步进 sandbox，并在后续模型轮次中作为 active skill 生效
3. 两条入口共用同一套治理元数据，不允许一条走 metadata、一条再写硬编码
4. 后续仍由 `managedSkillCatalog` 与 `managedSkillContext` 注入 prompt

### 6.3 不该发生的事

自动加载不允许变成：

1. 直接在 system prompt 里硬编码大段 deployment 说明
2. 在多个 service 中分别维护不同版本的部署指导
3. 每支持一种语言就新增一段 deploy if/else prompt

## 7. 管理端治理要求

管理端 `skills 管理` 必须把 deployment skill 当成“系统治理资产”呈现，而不是普通 skill。

至少要新增或明确展示以下信息：

1. 基础标识
   - slug
   - name
   - category
   - status
2. 治理属性
   - `systemRole`
   - `adminManaged`
   - `autoActivation`
   - `required`
   - `autoActivation.triggers`
   - `autoActivation.toolNames`
3. 发布状态
   - published revision
   - last updated by
   - last published at
4. 资源概览
   - runtime references 数量
   - templates 数量
   - 关键平台契约资源
5. 影响范围
   - deploy
   - redeploy
   - rollback
   - status
   - 关联 tools 列表（例如 `deploy_application`、`redeploy_application`）

同时要支持：

1. 仅对 draft revision 编辑
2. 发布前校验
3. revision 切换与回滚
4. 查看当前 auto-loaded 的 published revision

## 8. Altus 执行约束

deployment skill 接入后，Altus 在部署场景必须遵守以下约束：

1. 必须优先调用 managed deployment tools，而不是把部署解释成纯咨询
2. 当 deploy tool 返回 `retryable_repair_required` 时：
   - `template_compliance / deployment_configuration / workspace_missing`
     - 可以依据 skill 指导回到 workspace 修复
   - `resource_binding`
     - 不得继续盲改模板
     - 必须优先继续平台资源修复链
3. 本地调试成功不能视为线上部署成功
4. 必须以 deployment status 与最终 URL 为准完成验收
5. 任何关于 Umami / Railway 的底层 token、project id、service id 处理都不能由 skill 自行发明或绕过平台契约

## 9. 多语言扩展规则

未来新增语言时，按以下顺序处理：

### 9.1 优先只改 skill

如果底层部署平台能力不变，只是多了一种项目形态识别与指导，优先通过 deployment skill revision 解决。

典型场景：

1. 新增 Python Poetry 项目识别
2. 新增 Java Gradle 项目入口指导
3. 新增 PHP Laravel 项目发布前检查
4. 新增静态站点多入口识别

### 9.2 只有底层能力缺失时才改平台代码

只有在以下情况才允许进入平台代码修改：

1. 需要新增新的底层部署 provider 能力
2. 需要新增平台通用合规检查能力
3. 需要新增 Railway / Umami / deployment state 的真实执行能力
4. 需要新增 skill 元数据治理能力

### 9.3 禁止把语言规则重新打散到业务代码

以下做法应视为偏离方案：

1. 在 Altus input service 里为某语言单独写死一套部署 prompt
2. 在部署 service 里为某语言加入零散字符串判断
3. 在 UI 层手工区分语言并拼接部署策略

## 10. 分阶段实施建议

### Phase A：治理元数据收束

目标：

1. 给 deployment skill 增加系统角色和自动加载元数据
2. 让自动加载逻辑从“写死 slug”升级为“按系统角色解析”

### Phase B：后台治理显性化

目标：

1. 管理端 skills 管理显式展示 deployment skill 的治理属性
2. 能清楚看到当前发布中的 deployment revision
3. 能在后台直接修改语言指导资源并发布

### Phase C：语言资源化

目标：

1. 把现有语言 / 脚本场景的部署指导拆进 references
2. 建立新增语言只改 skill revision 的主路径

### Phase D：回归验收

目标：

1. 验证不同项目形态下部署链路是否都走同一平台固化层
2. 验证修改 deployment skill revision 后无需改代码即可影响新部署 run
3. 验证部署面板状态仍然由后台同步，不依赖前台请求触发

## 11. 验收标准

方案实施后，必须满足以下条件：

1. 管理后台能明确治理 deployment skill 的 revision 与资源
2. deploy / redeploy / rollback / status 场景会自动加载 deployment skill
3. Altus 在部署时能根据 skill 指导区分 HTML / JavaScript / Node.js / Python / Java / PHP 等项目形态
4. Umami 注入、Railway 部署、部署状态同步仍然完全由平台固化层执行
5. 新增语言指导时，优先只需要修改 deployment skill revision，而不需要修改业务硬编码
6. deployment skill 的变更不会绕过平台鉴权、资源隔离和状态持久化

## 12. 非目标

本次方案不做以下事情：

1. 不把 Railway / Umami 执行逻辑交给 skill
2. 不把 deployment skill 变成普通用户可随意替换的执行器
3. 不引入第二套独立 deployment runtime
4. 不通过 prompt 拼接替代后台治理

## 13. 结论

OneCEO 后续的部署稳定性，不应继续依赖“更多硬编码 + 更多 prompt 说明”。

正确方向是：

1. 平台把部署、统计、状态同步、资源绑定这些真正的执行能力继续固化
2. 管理后台把 deployment skill 当成系统资产治理
3. Altus 在部署场景自动加载这套受治理的 skill
4. 以后语言扩展和设计模式演进，优先通过发布新的 skill revision 完成

这样部署主链才能既稳定，又可演进。
