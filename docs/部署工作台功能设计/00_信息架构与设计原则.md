# 部署工作台信息架构与设计原则

## 1. 目标

部署工作台的目标不是展示 Railway 或 GitHub 供应链细节，而是让用户以 OneCEO 平台视角完成：

- 发布应用
- 查看当前线上状态
- 理解版本变化
- 进入扩展能力区

## 2. 信息架构

工作台分三层：

1. 一级：内容预览中的“部署”
2. 二级：发布、仪表盘、数据库、存储桶、设置
3. 三级：设置下的通用、域名、通知、支付、SEO、密钥、GitHub

补充说明：

- “仪表盘”本身保留一个页内视图切换，不单独升级为全局三级导航。
- 这个切换位于仪表盘右上角，用于在“部署数据”和“站点数据”之间切换。

这样设计的原因：

- 一级只承载“部署”这个能力入口，避免与文件、更改、调试并列时过重。
- 二级承载“可感知的功能模块”，和 Manus 的工作台心智接近。
- 三级只放在“设置”内部，避免顶层导航过深过宽。
- 仪表盘的数据视图切换保持页内完成，避免把导航层级继续做深。

## 3. 设计原则

### 3.1 平台优先

- 用户看到的是 OneCEO 的部署能力。
- 底层供应链不作为主叙事对象。
- 即使设置里保留 GitHub，也只作为平台托管链路视角，不暴露底层复杂度。

### 3.2 逐步展开

- 默认先看到“发布与访问”。
- 运维类信息放进“仪表盘”。
- 仪表盘内同时容纳“部署数据”和“站点数据”，但通过右上角切换分流，不混排在一个长页面里。
- 尚未开通的能力也保留正式入口，但必须明确为“待接入”，不能伪装成可用。
- 当前阶段“存储桶”属于保留入口，不进入开发。
- 当前阶段“设置”保留前端 UI，但其内部子条目不进入详细设计，等待后续统一规划。

### 3.3 从只读到可配置

当前阶段先形成工作台骨架：

- 第一阶段：只读状态卡 + 结构占位
- 第二阶段：补 API + 保存能力
- 第三阶段：补自动化、告警、审计和策略

## 4. 当前建议的后端支撑顺序

建议优先级：

1. 域名
2. 数据库
3. 密钥
4. 通知
5. SEO
6. 支付

原因：

- 域名与密钥最直接影响发布闭环。
- 数据库与对象存储都是业务能力扩展基础。
- 数据库现在已经明确不是占位页，而是未来要直接承接可视化管理与数据修改的核心能力，因此优先级前移。
- 存储桶当前按用户要求保留入口但暂停开发，因此不进入当前开发优先级排序。
- 设置内部子条目当前不进入设计，因此上面的优先级只保留为未来参考，不作为本轮文档与实现目标。
- 通知、SEO、支付更适合在前两者稳定后补齐。

## 5. 审核重点

- 这个层级是否符合你预期的产品结构。
- 仪表盘用“右上角切换按钮”承载双数据视图是否符合你的产品预期。
- 哪些二级功能应当现在就可操作，哪些只保留入口。
- GitHub 是否继续保留在“设置”下，还是进一步平台化隐藏。
- 设置子条目当前是否确认只保留 UI、不继续做功能设计。
