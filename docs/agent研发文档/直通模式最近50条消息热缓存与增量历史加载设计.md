# 直通模式最近50条消息热缓存与增量历史加载设计

## 1. 背景

当前 task session 对话区的历史消息展示，仍然强依赖于：

- 连接到远程 sandbox 内的 OpenCode
- 从 OpenCode 原生历史接口实时拉取完整历史

这会带来两个直接体验问题：

1. 用户点击会话后，首屏消息展示会被远端 sandbox / OpenCode 启动状态卡住。
2. 当用户已经向上翻阅历史后，如果连接重建、页面刷新、运行态重连，前端容易回退到“重新加载最近一屏”的状态，用户丢失已查看进度。

本设计的目标不是替代 OpenCode 原生历史，而是增加一个“热缓存 + 增量历史”的双层加载模型，让用户首屏立即可见，同时保留完整历史能力。

## 2. 目标

### 2.1 必须满足

- 每个 task session 在数据库中持久化最近 50 条可展示消息。
- 用户点击进入会话后，页面优先直接显示这 50 条最近消息，不等待远程 sandbox。
- 用户继续向上滚动时，在最近 50 条已经显示完之后，再按需加载更早的远程历史。
- 如果连接中断后恢复，或页面刷新，用户已经向上展开的历史浏览进度不能被重置。
- 多次 sandbox 重建 / runtime generation 切换的边界仍然要保留。
- `conversation_messages` 与 recent cache 都必须按“逻辑消息”去重，数据库中不能保留同一逻辑消息的重复行。
- OpenCode 流式文本写入数据库时，只保留最终整段消息；delta / checkpoint 不进入正式消息存储。

### 2.2 非目标

- 不把 OpenCode 全量历史永久搬回平台数据库。
- 不在本次方案中改动 OpenCode 原生消息语义。
- 不把“最近 50 条热缓存”扩展成长期归档系统。

## 3. 设计原则

### 3.1 双层历史模型

- 热层：平台数据库只保存最近 50 条“可直接渲染”的消息。
- 冷层：更老的完整历史仍然来自 OpenCode 原生历史 / 平台现有 fallback。

### 3.2 首屏不阻塞

- 会话页首屏只依赖热层。
- 远程历史获取只发生在用户继续上滑时。
- `GET /messages/recent` 必须严格快速返回数据库 recent cache，不能同步等待 OpenCode native history、sandbox provision、runtime 恢复。
- 如果 recent cache 缺失、含旧噪音、或缺少可渲染 assistant 回复，只允许后台异步触发 native history 回填；首屏请求本身不能被这条链路阻塞。
- 对 `conversation_messages` 的噪音清理也不能放在 `/messages/recent`、`/messages/history`、`getMessages()` 这类热读路径中同步执行；清理必须后台异步化。

### 3.3 已加载内容不能被重置

- 一旦用户已经展开过更老的历史，后续重连、刷新、runtime 恢复都只能增量合并，不能再把消息列表整体替换成“最近 50 条”。

### 3.4 generation-aware

- 热缓存消息、远程增量历史、流式新消息都必须保留 `runtimeGeneration`。
- generation 边界消息也属于可渲染消息，必须参与缓存与分页。

### 3.5 消息身份稳定

- 每一条可渲染消息都必须具备稳定的 `messageKey`。
- `messageKey` 在 recent cache、older history、SSE replay、实时流之间必须保持一致。
- 前端不再依赖 `content`、`createdAt`、数组下标去推测“是不是同一条消息”。
- `messageKey` 首先服务于后端存储层 upsert，其次才用于前端跨来源合并。

### 3.6 存储层优先于展示层

- 前端不承担“把脏数据库重新洗干净”的职责。
- 去重必须在后端写入数据库时完成，前端只做身份一致性合并。
- 如果数据库中出现重复消息，视为存储层缺陷，而不是展示层的正常输入。
- `opencode_event` 的空文本消息也视为存储层缺陷，后端写入时必须直接拒绝；不能依赖前端去隐藏。

### 3.7 浏览位置以消息锚点恢复

- 浏览位置恢复不再只依赖 `scrollTop`。
- 前端需要记录当前视窗第一条可见消息的 `messageKey`，以及该消息相对滚动容器顶部的偏移量。
- 刷新、重连、历史 prepend 后，优先按消息锚点恢复；只有锚点不存在时才退回 `scrollTop`。

### 3.8 本地视图缓存必须可失效

- `sessionStorage` 中的历史视图缓存只是加速层，不能被视为权威数据源。
- 每次热缓存结构调整、消息身份规则变化、噪音清洗规则变化时，都必须提升缓存 `version`。
- 读取缓存时，如果发现旧噪音模式，必须直接丢弃缓存，而不是尝试和服务端 recent 结果继续 merge。
- 旧噪音模式至少包括：
  - `opencode_event` 内容为空
  - `opencode_event` 内容以 `[Message] ` 开头
  - 空的 `status_update`
- 服务端 recent/history 结果也必须执行同样的噪音过滤，避免旧脏数据在页面刷新后重新回灌。
- 对 `fetch` 被主动取消或超时触发的 `AbortError`，前端只能视为“本次请求作废”，不能立即降级成错误提示或 fallback 到另一条历史链路，否则会造成页面刷新时的闪烁和重复请求。

## 4. 当前问题拆解

### 4.1 首屏展示依赖远程 OpenCode

当前 `/api/task-creation/sessions/:id/messages` 会优先尝试：

- OpenCode native history
- 平台 fallback 历史

这会让“点击对话框 -> 页面出现最近消息”的速度受限于：

- sandbox 是否还存活
- OpenCode server 是否可达
- 归档恢复是否已完成

### 4.2 历史上滑与重连耦合

当前前端消息数组没有区分：

- 首屏热缓存消息
- 用户主动向上加载出来的更老历史
- 底部实时流式新消息

因此一旦发生：

- runtime 重连
- SSE 重建
- 页面刷新

前端容易重新执行一次“历史初始化”，覆盖用户已展开的上方历史。

## 5. 总体方案

引入三层消息来源：

1. `recent-cache`
   - 数据库存最近 50 条消息
   - 用于首屏即时显示
2. `history-backfill`
   - 用户上滑时按页拉取更老历史
   - 优先从 OpenCode native history 分页获取
   - 不可用时回退到平台持久化历史
3. `live-tail`
   - WebSocket / SSE 持续追加底部新消息

前端最终展示的消息列表由三段拼接组成：

- `olderHistoryMessages`
- `recentCachedMessages`
- `liveMessages`

其中：

- `recentCachedMessages` 只负责首屏启动
- 一旦更老历史被展开，就写入本地 view cache
- 后续重连只能做增量 merge，不允许 reset 整体列表
- 但如果本地 view cache 被识别为旧版本或脏缓存，必须直接作废，再以 recent/history 结果重建

## 6. 数据模型设计

## 6.1 新增数据库热缓存表

建议新增表：`task_session_recent_messages`

字段建议：

- `id`
- `session_id`
- `message_id`
- `message_key`
- `role`
- `message_type`
- `content`
- `metadata_json`
- `timeline_cursor`
- `runtime_generation`
- `created_at`
- `updated_at`

约束建议：

- `session_id + message_id` 唯一
- `session_id + message_key` 唯一
- `timeline_cursor` 建索引
- `session_id, timeline_cursor desc` 建联合索引

说明：

- `timeline_cursor` 是 recent 50 滚动窗口的唯一排序依据。
- recent cache 不能依赖 `created_at` 做窗口裁剪，必须依赖稳定单调递增的 `timeline_cursor`。

### 6.1.1 conversation_messages 也需要逻辑消息唯一键

现有 `conversation_messages` 也需要补齐逻辑消息字段：

- `message_key`
- `runtime_generation`
- `timeline_cursor`
- `updated_at`

约束建议：

- `session_id + message_key` 唯一
- `session_id, timeline_cursor desc` 建联合索引

含义：

- `conversation_messages` 是干净主消息表
- `task_session_recent_messages` 是最近 50 条干净窗口
- 两张表都不允许保留同一逻辑消息的多个版本

### 6.1.2 timeline_cursor 的定义

`timeline_cursor` 必须满足：

- 在同一个 `session_id` 内单调递增
- 只在“逻辑消息首次落库”时分配
- 后续同一 `messageKey` 的 upsert 更新不能改变其 `timeline_cursor`

原因：

- 如果重复到达的旧消息在 upsert 时刷新 `timeline_cursor`，它会被错误抬升为“最新消息”
- recent 50 的真实语义是“最近进入时间线的 50 条逻辑消息”，而不是“最近被更新的 50 行”

推荐实现：

- 在平台侧为每个 `session_id` 维护一个持久化单调序号
- 新逻辑消息首次插入时获取下一个 `timeline_cursor`
- 已存在的逻辑消息只更新 `content` / `metadata` / `updated_at`

### 6.1.3 为什么不能只靠内存队列

不能只在应用内维护 FIFO 队列，原因是：

- 同一会话会经历多次 sandbox 重启
- 存在 WAL 重放与补写
- 存在同一逻辑消息的重复到达
- API 进程自身也可能重启

因此：

- FIFO 语义必须固化到数据库字段 `timeline_cursor`
- 内存队列只能作为临时缓冲，不能作为 recent 50 的最终顺序依据

### 6.2 为什么不直接复用现有全量消息表

可以复用现有消息来源生成热缓存，但不建议直接把“最近 50 条窗口语义”塞进现有全量表：

- 全量表承担的是持久消息记录
- 热缓存承担的是“首屏展示窗口”
- 两者生命周期与读写模式不同

用独立热缓存表更容易：

- 做窗口裁剪
- 控制查询成本
- 保证首屏接口稳定

## 7. 后端写入策略

### 7.1 写入时机

所有会进入用户消息区的可渲染消息，在落主消息记录后，同时进入 recent cache：

- `user_input`
- `user_response`
- `opencode_user_input`
- `opencode_event` 中实际可展示的文本
- `status_update`
- `error`
- generation 边界消息

### 7.1.1 messageKey 生成规则

后端必须统一生成并透传 `messageKey`。

优先级：

1. 显式 `metadata.messageKey`
2. generation 边界消息：`boundary:<runtimeGeneration>:<timelineCursor>`
3. OpenCode 流式文本消息：`stream:<runtimeGeneration>:<opencodeSessionId>:<partId>`
4. 具有 `sessionEventSeq` 的运行时 / 持久化消息：`runtime:<runtimeGeneration>:<sessionEventSeq>:<type>`
5. 无法识别逻辑事件键时，才退回数据库行主键：`db:<id>`

约束：

- 同一条消息从不同来源重复进入前端时，`messageKey` 必须完全相同。
- `messageKey` 只用于身份标识，不承诺对用户可读。

### 7.1.2 存储写入必须是 upsert，不是 insert-only

所有正式消息写入都必须改成：

1. 先生成 `messageKey`
2. 向 `conversation_messages` 按 `(session_id, message_key)` 执行 upsert
3. 再向 `task_session_recent_messages` 按 `(session_id, message_key)` 执行 upsert
4. 最后裁剪 recent cache 到最近 50 条

结果要求：

- 如果同一逻辑消息被平台再次收到，只能更新已有行，不能新增第二行
- recent 50 必须来自干净主消息，而不是一边插入一边依赖展示层修补
- upsert 命中已有逻辑消息时，必须保留首次分配的 `timeline_cursor`

### 7.1.2.1 timeline_cursor 分配规则

写入流程要拆成两种情况：

1. 新逻辑消息
   - 根据 `(session_id, message_key)` 未命中
   - 分配新的单调递增 `timeline_cursor`
   - 插入 `conversation_messages`
2. 已存在逻辑消息
   - 根据 `(session_id, message_key)` 命中
   - 只更新内容、元数据、`updated_at`
   - 不修改 `timeline_cursor`

这样 recent 50 的淘汰顺序才能稳定。

### 7.1.3 OpenCode 流式消息的持久化规则

OpenCode SSE 文本消息分为两类：

1. `stream delta / checkpoint`
   - 只用于实时显示、断线恢复辅助或内存/WAL
   - 不进入 `conversation_messages`
   - 不进入 `task_session_recent_messages`
2. `final aggregate`
   - 代表该逻辑消息的最终完整文本
   - 只在收到最终文本后进入数据库
   - 按 `messageKey` upsert 到主消息表和 recent cache

约束：

- 数据库中不保留 delta 片段
- 数据库中不保留同一条流式消息的多个 checkpoint 完整快照
- 数据库只保留该流式消息最终版本

### 7.2 窗口裁剪

每次 upsert 后按 `session_id + timeline_cursor desc` 保留最近 50 条：

- 主消息 upsert 成功
- 删除该 session 更老的第 51 条之后消息

要求：

- 裁剪逻辑在同一事务内完成
- 保证 recent cache 始终是“最新 50 条可渲染消息”
- 窗口语义是严格 FIFO：
  - first come：逻辑消息首次落库时拿到固定 `timeline_cursor`
  - first out：`timeline_cursor` 最小的消息优先被 recent cache 淘汰

### 7.2.1 recent 50 的滚动窗口语义

recent cache 不是“最后插入的 50 行”，而是：

- 对同一 `session_id`
- 按 `timeline_cursor` 排序后的
- 最新 50 条逻辑消息

因此即使出现：

- 同一逻辑消息重复到达
- WAL 重放
- 内容修正型 upsert

只要 `timeline_cursor` 不变，recent 50 就不会被旧消息错误扰动。

### 7.2.2 前后端展示排序也必须以 timeline_cursor 为第一依据

`timeline_cursor` 不只用于数据库窗口裁剪，也必须作为 recent/history 响应、Redis 热缓存页面和前端合并渲染的第一排序依据。

要求：

- 后端 `messages/recent` 与 `messages/history` 返回的每条消息必须透传 `timelineCursor` 或 `metadata.timelineCursor`。
- 后端分页游标计算必须优先使用 `timeline_cursor`，只有旧数据缺失该字段时才退回 `sessionEventSeq`、`timestamp` 或 `createdAt`。
- 前端合并本地乐观消息、recent cache、history backfill、SSE/realtime 消息时，也必须优先按 `timelineCursor` 进行稳定排序。
- 当某些旧消息没有 `timelineCursor` 时，前端只能在“双方都有可比较游标”的消息之间重排，避免把无法判断顺序的旧消息强行移动到错误位置。

原因：

- `createdAt` / `timestamp` 可能在并发写入、批量 flush、Redis 回放或页面刷新时相同或倒置。
- `sessionEventSeq` 有历史兼容语义，可能来自时间戳推导，不能替代数据库事实游标。
- 用户可见消息顺序必须和 `conversation_messages.timeline_cursor` 保持一致，避免发送消息、Altus 状态、智能体最终回复在刷新后出现不同排列。

### 7.3 generation 边界

如果最近 50 条中包含 generation 切换边界，该边界消息必须保留。

不做“跨边界强行保留额外消息”的复杂规则，首版按时间窗口截取即可，但边界消息本身要进入 recent cache。

## 8. 后端读取接口设计

## 8.1 新增首屏接口

新增接口：

- `GET /api/task-creation/sessions/:sessionId/messages/recent`

返回：

- 最近 50 条热缓存消息
- `oldestCursor`
- `newestCursor`
- `hasOlderHistory`
- `source = "recent-cache"`
- 每条消息显式包含 `messageKey`

说明：

- 该接口不依赖远程 sandbox / OpenCode。
- 如果 session 没有 recent cache，再退回当前已有的消息恢复逻辑，并把结果回填 recent cache。

## 8.2 新增历史回填接口

新增接口：

- `GET /api/task-creation/sessions/:sessionId/messages/history?before=<cursor>&limit=<n>`

行为：

- `before` 表示“从当前最老已显示消息之前继续往上取”
- 返回更老一页历史消息
- 返回：
  - `messages`
  - `nextBeforeCursor`
  - `hasMore`
  - `source = "opencode-native" | "persisted-fallback"`
  - 每条消息显式包含 `messageKey`

### 8.3 分页原则

- 默认每次拉 50 条
- 只允许按“更老方向”分页
- 排序仍以 `sessionEventSeq` 优先、`createdAt` 次之
- 返回结果必须已经完成：
  - `runtimeGeneration` 补全
  - generation 边界注入

## 9. 前端加载策略

## 9.1 首屏进入

会话页打开后，顺序调整为：

1. 请求 `/messages/recent`
2. 立即渲染最近 50 条
3. 建立 WebSocket / SSE
4. 不主动拉取更老 OpenCode 历史

这样用户打开会话时，总能立即看到近况，而不是等待远端恢复。

补充约束：

- 前端读取 `/messages/recent` 时必须设置短超时，避免页面长期卡在“智能体正在处理...”。
- 如果 `/messages/recent` 超时、失败、或返回空消息页，允许回退到 `/messages/history` 获取可渲染消息，但不能无限等待 recent。
- 返回给前端的消息 `metadata` 必须瘦身，只保留续聊、流合并、终态判断所需字段；不能把 OpenCode 原始 event/rawPayload 整包透传到 recent/history 响应。
- OpenCode 内部路径 `.opencode/`、`.git/`、`node_modules/` 相关的 `session.diff`、`file.*`、内部日志/数据库变更，不进入 recent/history。
- 即便是保留的 OpenCode 事件，写入主消息表与 recent cache 时也只能保存瘦身后的 metadata：
  - 会话身份字段
  - 时序字段
  - part/tool 摘要
  - 必要状态字段
  - 不能保存完整 `event` 原文或大尺寸 `rawPayload`

## 9.1.1 前端消息结构

前端 `AgentMessage` 增加：

- `messageKey`

统一要求：

- React 渲染 `key` 使用 `messageKey`
- recent/history/live merge 去重使用 `messageKey`
- sessionStorage 历史缓存保留 `messageKey`
- 浏览位置锚点使用 `messageKey`

## 9.2 上滑加载

当用户滚动到消息列表顶部，并且：

- `hasOlderHistory = true`
- 当前没有正在拉 older history

则调用 `/messages/history?before=<oldestCursor>`

返回消息追加到列表顶部：

- 不替换已有数组
- 不清空底部流式消息
- 只按 `messageKey` 去重

## 9.3 消息列表分层状态

前端状态拆分为：

- `recentCachedMessages`
- `olderHistoryMessages`
- `liveMessages`
- `oldestLoadedCursor`
- `hasOlderHistory`
- `historyLoading`

最终渲染：

- `mergedMessages = olderHistoryMessages + recentCachedMessages + liveMessages`

这样重连时只更新 `liveMessages` 和 session runtime，不会冲掉已加载的 older history。

## 10. 重连与刷新后的进度保持

## 10.1 连接重建

当 WebSocket / SSE 重连成功时：

- 不重新执行“全量历史初始化”
- 只继续监听新消息
- `olderHistoryMessages`、`recentCachedMessages`、`oldestLoadedCursor` 保持不变

## 10.2 刷新页面后的恢复

新增前端本地 view cache，按 `sessionId` 存储：

- 已加载的消息切片
- `oldestLoadedCursor`
- `hasOlderHistory`
- 当前 scroll anchor
- anchor 相对偏移
- `version`

建议存储位置：

- `sessionStorage` 优先

缓存约束：

- 本地 view cache 必须带版本号。
- 当消息结构、去重规则、滚动锚点语义发生变化时，提升版本号并强制旧缓存失效。
- 读取缓存时，如果 `version` 不匹配，必须直接丢弃，不能继续把旧缓存渲染到会话页。

建议上限：

- 最多缓存 300 条已加载消息
- 超过后裁剪最老部分

目的：

- 页面刷新后，先从本地 view cache 恢复用户刚才展开过的历史范围
- 再与 `/messages/recent` 返回的最新热缓存做 merge

### 10.2.1 recent 失败时的首屏回退

如果 `/messages/recent` 失败：

1. 先检查当前版本的本地 view cache 是否存在
2. 如果存在，允许先渲染该缓存，避免首屏空白
3. 随后立即回退请求 `/messages/history?limit=<pageSize>` 作为干净首屏来源
4. 回退成功后，用 `messageKey` 合并结果并更新本地 view cache
5. 如果本地 view cache 也不存在，则直接以 `/messages/history` 结果作为首屏

约束：

- `recent` 失败不能让会话页出现空白消息区。
- `recent` 失败时不能继续复用旧版本缓存。
- `history` 回退结果仍然要遵守 `messageKey` 合并与 generation 边界规则。

## 10.3 Scroll Anchor 恢复

记录：

- `anchorMessageKey`
- `anchorOffsetTop`
- `scrollTop`（兜底）

恢复时：

- 先渲染本地 view cache
- 定位到 `anchorMessageKey`
- 按偏移量恢复滚动位置
- 如果锚点消息不存在，再退回 `scrollTop`

这样即使刷新后，用户仍停留在他刚才查看的历史位置附近。

## 11. 合并规则

## 11.1 去重键

消息去重键统一为：

- `messageKey`

说明：

- `messageKey` 的主职责是保证存储层 upsert 和跨来源身份一致
- 前端仍使用 `messageKey` 合并 recent/history/live，但不再承担“修复脏重复数据”的职责

## 11.2 recent cache 与 older history 合并

- 如果 older history 中已经包含 recent cache 的一部分，不重复插入
- 以 `messageKey` 作为唯一判重基础

## 11.3 recent cache 与 live tail 合并

- recent cache 只代表首屏历史快照
- live tail 到达后，如果命中相同 `messageKey`，则做增量更新
- 不得在重连时重新把 recent cache 整体覆盖 live tail

## 12. 失败兜底

### 12.1 sandbox 不可用

- `/messages/recent` 仍可返回数据库热缓存
- 用户至少能立即看到最近 50 条消息
- 用户继续上滑时：
  - 如果远程历史不可拉取，返回明确 `hasMoreUnknown` / `historyUnavailable`
  - 前端提示“更早历史暂时不可用”，但不影响当前已显示消息

### 12.1.1 recent cache 表结构未迁移或字段缺失

- 如果 `task_session_recent_messages` 缺表、缺列、索引未建好，后端不能直接让 `/messages/recent` 500。
- 后端应自动回退到 `conversation_messages` 主消息表读取最近窗口。
- 如果 recent cache 读取失败但主消息表可用，前端不应感知到底层差异。

### 12.2 OpenCode 历史读取失败

- older history 接口退回平台持久化历史
- 不阻塞热缓存首屏

### 12.3 本地 view cache 丢失

- 最差情况下回到“首屏只显示最近 50 条”
- 不影响主链路

### 12.4 同一条消息被多次刷新叠加显示

现象：

- 同一消息可能同时从 recent cache、older history、SSE replay、实时流进入前端
- 如果前端只按内容或时间戳猜测重复，会出现重复叠加显示

解决：

- 后端稳定生成 `messageKey`
- 数据库写入按 `(session_id, message_key)` upsert，先保证主存储干净
- recent cache 按 `(session_id, message_key)` upsert，保证窗口干净
- recent window 从历史全量消息重建时，也必须先按 `message_key` 去重；否则旧脏数据会在重建阶段再次触发 recent 表唯一键冲突。
- 前端所有合并逻辑只认 `messageKey`
- React 渲染 key 也使用 `messageKey`

## 13. 对现有系统的影响

### 13.1 后端

- 新增 recent cache 表
- 为 `conversation_messages` 增加逻辑消息唯一键
- 新增 recent cache 写入 / trim 逻辑
- 新增 `/messages/recent`
- 新增 `/messages/history`
- 调整现有消息持久化链路，写主消息时按 `messageKey` upsert，再同步写 recent cache
- 调整 OpenCode 流式持久化链路，只持久化 final aggregate，不持久化 checkpoint 快照

### 13.2 前端

- `useTaskCreationAgent` 要拆分“首屏最近消息”和“上滑历史”
- 增加 scroll anchor 管理
- 增加 sessionStorage 级的 view cache
- 重连后只做 tail merge，不重置历史数组

## 14. 验收标准

- 点击会话后，在 sandbox 未完全就绪时，页面仍能在 300ms 内显示最近消息。
- `conversation_messages` 中同一 `(session_id, message_key)` 只能存在一行。
- `task_session_recent_messages` 中同一 `(session_id, message_key)` 只能存在一行。
- OpenCode SSE 文本在数据库中只保留 final aggregate，不保留 delta / checkpoint 行。
- 同一 `(session_id)` 下，`timeline_cursor` 必须单调递增且不可被旧消息 upsert 刷新。
- recent 50 必须严格等于按 `timeline_cursor` 排序后的最新 50 条逻辑消息。
- 最近 50 条全部显示后，继续上滑才会触发远程历史获取。
- 远程历史获取过程中，底部实时消息仍能正常追加。
- 同一会话中，多次 sandbox generation 切换的边界仍然可见。
- 用户上滑展开 older history 后：
  - WebSocket/SSE 重连不会把消息列表重置到最近 50 条
  - 页面刷新后可以恢复到之前查看的历史附近位置
- 同一消息在 recent/history/replay/live 多次进入时不会重复显示
- sandbox 不可用时，最近 50 条仍能稳定显示。

## 15. 实施顺序建议

### Phase A

- 为 `conversation_messages` 增加 `message_key` / `runtime_generation` / `timeline_cursor`
- 新增 recent cache 表
- 把主消息写入改成存储层 upsert
- 为 `session_id` 维度补齐稳定的 `timeline_cursor` 分配逻辑
- 写入链路同步维护最近 50 条干净窗口
- 新增 `/messages/recent`

### Phase B

- 调整 OpenCode 流式持久化，只保留 final aggregate
- 前端首屏改为优先 recent cache
- 流式 tail 与首屏消息分层管理

### Phase C

- 新增 `/messages/history`
- 前端实现上滑增量历史加载

### Phase D

- 增加 sessionStorage view cache
- 做刷新后 scroll anchor 恢复

## 16. 本文档结论

建议采用：

- 平台数据库维护最近 50 条热缓存
- OpenCode 原生历史继续承担冷历史来源
- 前端使用“recent + older + live”三段式消息模型
- 用本地 view cache 保持用户的历史查看进度

这样可以显著降低用户对 sandbox 启停的感知，同时不牺牲完整历史能力。

- 新建 managed 会话时，用户输入在草稿会话创建请求返回前先进入本地消息列表；草稿会话创建完成后，再用同一个 `messageKey` 绑定真实 `sessionId` 并写入历史视图缓存，避免页面先切到聊天态但消息区短时间空白。

- 本轮不改变 recent/history 后端窗口语义，也不新增缓存来源。
