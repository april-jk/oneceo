# 20260410 Issue45 会话归属收口与列表稳定性修复方案 [20260410-0034已采用]

## 1. 背景

Issue #45 当前表现为：

1. 用户端会话列表在刷新或重部署后可能整体空白。
2. 管理端仍可看到对应 session。
3. `task_creation_sessions.user_id` 存在 `empty/legacy` 混合历史数据。

已完成事实核验见：

1. [20260410_#45_会话列表空白根因定位测试方案_[20260410-0034已采用].md](/Users/watson/codingProj/oneceo/docs/单元测试文档/20260410_#45_会话列表空白根因定位测试方案_[20260410-0034已采用].md)

## 2. 已确认根因（必须同时修）

1. **源头写入未完全收口**
   - 仍存在非 canonical owner（legacy 或空 owner）写入路径，导致后续用户态过滤不可见。
2. **列表回填策略在多用户库被阻断**
   - `GET /sessions` 当前在存在 foreign owned sessions 时，直接阻断 orphan 回填。
3. **legacy 迁移依赖浏览器残留标识**
   - `X-Legacy-User-Id` 来源于 `localStorage.oneceo_client_user_id`；当前仅读取，不保证持续写入。

## 3. 修复目标

1. 新写入 session 必须绑定真实 `app_users.id`（canonical UUID）。
2. legacy 会话迁移必须改为服务端持久映射，不再依赖浏览器临时状态。
3. 列表恢复逻辑改为“可证明归属的定向迁移”，移除会导致长期空白的全局阻断。
4. 保持用户隔离边界：用户态仍只允许读取自己的 session。

## 4. 非目标

1. 不放宽跨用户可见性。
2. 不保留“匿名 owner 长期可用”的兼容路径。
3. 不在本轮重做整套会话模型或引入新执行链路。

## 5. 方案设计（最短路径，非补丁）

### 5.1 会话创建写入收口

1. 生产主链路（HTTP/WebSocket/managed/direct）禁止 `createSession` 写入空 owner。
2. 生产主链路禁止写入 non-canonical owner（legacy 文本）。
3. DAO 层将 `createSession` 区分为：
   - 业务入口：`createSessionForUser(userId: canonicalUuid, ...)`
   - 调试入口：仅测试/脚本可用，且必须显式声明，禁止默认进入生产环境。
4. `_tmp` 脚本全部补齐显式 `userId`，并加“非测试库拒绝写入”保护。

### 5.2 服务端持久化 legacy 映射

新增表：`app_user_legacy_id_mappings`

字段：

1. `id`
2. `app_user_id`（UUID, FK `app_users.id`）
3. `legacy_user_id`（TEXT, unique）
4. `source`（`request_header` / `manual_backfill`）
5. `first_seen_at`
6. `last_seen_at`
7. `created_at`
8. `updated_at`

规则：

1. 任何已登录请求若携带合法 legacy id（`X-Legacy-User-Id`），执行 upsert 映射。
2. 后续迁移与认领仅依赖该映射表，不再直接依赖浏览器本地值。

### 5.3 列表恢复逻辑重构

`GET /api/task-creation/sessions` 调整为：

1. 先按 `currentUser.userId` 查询 owned sessions。
2. 若为空：
   - 优先执行 `rebindSessionsFromMappedLegacyIds(currentUser.userId)`。
   - 不再使用“全局 foreign owner 存在即阻断”的 orphan 回填门禁。
3. orphan（空 owner）仅允许在**显式会话访问链路**按 session 粒度认领（如 `POST /sessions` 指定 sessionId、`requireOwnedTaskSession`），禁止全局批量盲认领。

说明：

1. 这样可以避免跨用户误认领。
2. 同时避免“库里有其他用户数据 -> 我自己的历史永远恢复不了”的死锁。

### 5.4 现有脏数据迁移

一次性迁移步骤：

1. 按 `app_user_legacy_id_mappings` 将 `task_creation_sessions.user_id = legacy_user_id` 批量更新为 `app_user_id`。
2. 迁移后对 `legacy_user_id` 行做审计抽样，确认列表可见性恢复。
3. 对无法映射的 orphan 数据保持未认领状态，不做跨用户猜测绑定。

### 5.5 可观测性与告警

1. 保留并升级 `TASK_SESSION_CREATE_MISSING_USER_ID` 告警为阻断错误（生产链路）。
2. 新增告警：`TASK_SESSION_CREATE_NON_CANONICAL_OWNER_BLOCKED`。
3. 增加巡检 SQL（日报）：
   - 新增 `empty/legacy` 数量
   - 当日新写入坏 owner 数量必须为 0

## 7. 验收标准

1. 新建/续聊/直通链路不再产生空 owner 与 legacy owner。
2. legacy 历史会话在存在映射后可稳定迁移，不依赖 localStorage。
3. 刷新、重部署后，用户端会话列表仍可见（同一登录用户）。
4. 用户态列表仍只返回自身会话，不泄漏跨用户数据。
5. 当日坏 owner 新增量为 0。

## 8. 测试计划

1. 单测：
   - `task-creation-business-routes.test.ts` 增加“mapped legacy 优先迁移、orphan 不做全局盲回填”。
2. 集成测试：
   - 双用户 + 混合 foreign 数据 + legacy 数据 + orphan 数据场景。
3. 数据库核验：
   - 迁移前后统计 `empty/legacy/uuid`。
4. 回归验证：
   - 刷新页面、重启 API 后列表可见性保持一致。

## 9. 实施顺序

1. 先落 DB 映射模型与 DAO。
2. 再改列表恢复逻辑（迁移优先、去除全局阻断）。
3. 收口创建链路与 `_tmp` 脚本写入。
4. 最后执行历史数据迁移与回归测试。
