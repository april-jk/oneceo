# 02 技能模型、版本与后台管理

## 1. 技能模型

为了避免“管理员刚改了 skill，老会话语义就被悄悄改掉”，skill 必须版本化。

建议新增两张表。

### 1.1 `platform_skills`

表示 skill 的逻辑实体。

建议字段：

1. `id`
2. `slug`
3. `name`
4. `description`
5. `category`
6. `status`
7. `published_revision_id`
8. `created_at`
9. `updated_at`

约束：

1. `slug` 全局唯一
2. `status` 只允许 `active / archived`
3. 用户侧只能看到 `active + published_revision_id 非空` 的 skill

### 1.2 `platform_skill_revisions`

表示 skill 的不可变快照。

建议字段：

1. `id`
2. `skill_id`
3. `revision_number`
4. `slug_snapshot`
5. `name_snapshot`
6. `description_snapshot`
7. `body_markdown`
8. `published_at`
9. `created_by`
10. `created_at`

说明：

1. `body_markdown` 保存 skill 主体内容
2. 发送消息时绑定的是 `revision_id`，不是动态指向最新正文

### 1.3 `user_platform_skill_bindings`

用户不是直接消费“所有平台 skill”，而是先把平台 skill 引用进自己的可用 skill 集。

建议字段：

1. `id`
2. `user_id`
3. `platform_skill_id`
4. `enabled`
5. `created_at`
6. `updated_at`

约束：

1. `user_id + platform_skill_id` 唯一
2. 绑定的是 `platform_skill_id`，不是固定 revision
3. 用户引用平台模板后，始终跟随该 skill 当前 `published_revision_id`

### 1.4 `user_custom_skills`

用户自定义 skill 走独立表，不复用平台表。

建议字段：

1. `id`
2. `user_id`
3. `slug`
4. `name`
5. `description`
6. `category`
7. `body_markdown`
8. `status`
9. `created_at`
10. `updated_at`

约束：

1. `user_id + slug` 唯一
2. `status` 只允许 `active / archived`
3. 本次不做用户自定义 skill 的 revision 历史

## 2. 为什么必须做 revision

如果只存一张当前表，会出现两个严重问题：

1. 用户昨天选中的 skill，今天后台改完后，重放/续跑结果会变
2. sandbox 恢复时无法还原“消息当时对应的 skill 内容”

revision 化后，消息、run、sandbox 恢复都能使用同一个快照。

用户态 skill 则分两类：

1. 平台模板引用：自动跟随管理员发布的最新 published revision
2. 用户自定义 skill：由用户自己维护正文

## 3. 后台管理能力

管理后台需要具备以下最小闭环：

1. 列表查看 skill
2. 新建 skill
3. 编辑 skill 并发布新 revision
4. 启用/归档 skill
5. 预览某个 revision 的 `SKILL.md` 渲染结果
6. 选择一个运行中的 session，对已发布 revision 做 sandbox 同步验证

本次不做复杂工作流审批，直接采用“保存即发布新 revision”的模式。

业务前端用户设置页需要具备以下闭环：

1. 查看平台公开模板目录
2. 把某个平台模板加入“我的可用 skills”
3. 从“我的可用 skills”里停用某个平台模板
4. 新建用户自定义 skill
5. 编辑用户自定义 skill
6. 归档/启用用户自定义 skill

## 4. API 设计

### 4.1 主平台 API

放在 `apps/api`，因为它是 skill 的真实来源和 sandbox 运行时消费方。

建议新增：

1. `GET /api/task-creation/skills`
   返回当前用户已配置可用的 skill 列表
2. `GET /api/task-creation/settings/skills`
   返回用户 settings 页所需的完整数据
3. `POST /api/task-creation/settings/skills/platform/:skillId/enable`
4. `POST /api/task-creation/settings/skills/platform/:skillId/disable`
5. `POST /api/task-creation/settings/skills/custom`
6. `PUT /api/task-creation/settings/skills/custom/:customSkillId`
7. `POST /api/task-creation/settings/skills/custom/:customSkillId/archive`
8. `POST /api/task-creation/settings/skills/custom/:customSkillId/activate`
2. `GET /api/internal/skills`
3. `GET /api/internal/skills/:skillId`
4. `POST /api/internal/skills`
5. `PUT /api/internal/skills/:skillId`
6. `POST /api/internal/skills/:skillId/archive`
7. `POST /api/internal/skills/:skillId/activate`
8. `GET /api/internal/skills/:skillId/revisions`
9. `GET /api/internal/skills/:skillId/revisions/:revisionId/rendered`
10. `POST /api/internal/skills/:skillId/revisions/:revisionId/validate`

其中：

1. `task-creation/skills` 面向业务前端 attachment picker
2. `task-creation/settings/skills` 面向业务前端设置页
3. `internal/skills` 面向管理后台

### 4.2 管理后台入口

`apps/admin_management` 不自己保存 skill 数据，只做管理入口。

建议方式：

1. `admin_management` 新增 skill 管理 section
2. 通过自身 server 代理到 `apps/api` 的内部 skill 接口
3. 内部接口走固定 internal token，不复用用户态接口
4. `admin_management` 只负责页面和代理，不直接访问主库

这样可以保持：

1. skill 的来源只有一处
2. 管理后台不重复实现数据库访问层

## 5. 种子数据

现有内置 skill 需要在首轮迁移时写入数据库，至少包含：

1. `requirements-breakdown`
2. `implementation-plan`
3. `test-checklist`
4. `office-ppt`
5. `office-docx`
6. `office-xlsx`

迁移后：

1. 前端不再从静态 TS 常量读取这些 skill
2. skill 正文修改只走后台发布
3. 用户首次进入 skill 设置页时，系统可以按当前平台公开模板自动初始化默认引用，避免升级后 attachment picker 为空
