# 04 消息事件流与状态模型

## 1. 设计目标

managed mode 的消息与事件体系需要解决当前三类问题：

1. 历史消息和实时消息来源不统一
2. WebSocket / SSE / file-memory-store 三套状态互相覆盖
3. 页面刷新后无法自然恢复到某个 run 的真实状态

因此新设计必须做到：

- `消息表` 是历史权威源
- `run_event` 是执行轨迹权威源
- `stream` 只负责实时投递

## 2. 标准事件模型

建议 run stream 事件统一为以下类型：

- `run_ack`
- `run_status`
- `assistant_delta`
- `assistant_message`
- `tool_call_started`
- `tool_call_progress`
- `tool_call_completed`
- `tool_call_failed`
- `clarification_requested`
- `artifact_updated`
- `run_completed`
- `run_failed`
- `run_stopped`

## 3. 标准消息模型

会话消息统一为：

- `user`
- `assistant`
- `tool`
- `system`

说明：

- `assistant_delta` 不直接落为最终消息
- assistant 完整产出结束后，再写入一条 `assistant`
- tool 调用过程写入 `run_event`
- 若需要在对话里展示工具结果摘要，则写入 `tool`

## 4. 单一流式通道

managed mode 必须收敛为单一权威流式通道。

设计要求：

1. 前端 managed 模式只订阅 `run stream`
2. 不再同时依赖 WebSocket managed 消息 + SSE executor 消息合并
3. refresh 后通过：
   - 拉取 `session messages`
   - 拉取 `latest run`
   - 如 run 仍 active，则继续订阅该 run stream

## 5. 状态转换规则

### 5.1 用户发消息

- 写入 `user` message
- 创建 `run`
- 推送 `run_ack`

### 5.2 模型开始生成

- `run.status = running`
- 推送 `run_status`

### 5.3 工具调用

- 推送 `tool_call_started`
- 若有 stdout/stderr/进度，推送 `tool_call_progress`
- 成功则推送 `tool_call_completed`
- 失败则推送 `tool_call_failed`

### 5.4 需要用户补充

- `run.status = waiting_user`
- session 状态同步变为 `waiting_user`
- 写入一条 `system` 或 `assistant` clarification message

### 5.5 完成

- 写入 assistant 最终消息
- `run.status = completed`
- session 状态回到 `idle` 或 `completed`

## 6. 前端恢复规则

刷新页面时按以下顺序恢复：

1. 读 session 基本信息
2. 读 session messages
3. 读 latest managed run
4. 若 run 为 active 状态，立即恢复 stream

这意味着前端不需要继续维护当前复杂的：

- SSE cursor
- WS queue
- message merge policy

用于 managed mode 的大部分逻辑。

## 7. 与 direct mode 的隔离

本设计只对 managed mode 生效。

因此：

- direct mode 继续保留现有 `WebSocket + SSE + executor session`
- managed mode 改为 `run stream`

两者不得再共享同一套消息实时协议。

## 8. 设计结论

managed mode 的状态恢复和实时显示，必须以：

`session messages + latest run + run stream`

为唯一模型，不再依赖 `file-memory-store + WebSocket managed push + direct-style SSE merge` 的历史方案。

## 8.1 当前落地进展（2026-03-25）

本篇事件模型已开始进入代码落地，当前已完成的第一步是：

- `apps/api/src/services/altus-run-coordinator.ts`
  - 对 `llm-proxy` 的 managed 模型请求已从阻塞式完整返回改为 `stream: true`
  - coordinator 已能消费上游 `SSE chunk`
  - 已能合并流式 `tool_call` 参数并发出 `tool_call_progress`

当前已落地、可直接在前端消费的事件仍以以下几类为主：

- `run_ack`
- `run_status`
- `tool_call_progress`
- `tool_call_started`
- `tool_call_completed`
- `tool_call_failed`
- `assistant_message`
- `clarification_requested`
- `run_completed`
- `run_failed`
- `run_stopped`

这轮落地的重点是先消除“工具结果回填后下一轮模型调用必须整轮阻塞等待”的结构性问题。  
`assistant_delta` 的完整前后端流式闭环可以在此基础上继续扩展，但不再影响本轮 `upstream_timeout` 根因修复。

## 9. Suna 代码参照

本篇关于“消息是历史源、run_event 是轨迹源、stream 只做实时投递”的设计，需要对照以下 `suna` 代码：

- `referance/suna/backend/core/threads/repo.py` -> `create_message_full(...)`、`get_thread_messages(...)`
  - 说明会话消息属于 thread/message 存储层。
- `referance/suna/backend/core/agents/repo.py` -> `update_agent_run_status(...)`
  - 说明 run 状态独立落库，不混入 message 模型。
- `referance/suna/backend/core/agents/runner/executor.py` -> `execute_agent_run(...)`
  - 说明执行过程中会持续写入 run stream 与 run 状态。
- `referance/suna/backend/core/agents/api.py` -> `stream_agent_run(...)`
  - 说明前端订阅的是 `run` 事件流，而不是 WebSocket 会话态。
- `referance/suna/apps/frontend/src/lib/api/agents.ts` -> `unifiedAgentStart(...)`
  - 说明前端先拿到 `runId` 再进入流式订阅。
- `referance/suna/apps/frontend/src/lib/streaming/use-agent-stream.ts` -> `startStreaming(...)`
  - 说明 run stream 是前端的单一实时入口。
- `referance/suna/apps/frontend/src/hooks/messages/useAgentStream.ts`
  - 说明对 UI 的增量状态处理围绕 run stream，而不是多通道 merge。
