# 27. PPT 渲染器接入方案 [20260502-1237已采用]

更新时间：2026-05-02

## 1. 背景

`26_竞品式PPT子任务编排工作流方案_[20260501-1718已采用].md` 已把 PPT 任务第一阶段收敛为 `ppt-workflow` 平台 skill：先完成需求分析、检索规划、素材简报、视觉方案、结构规划和 `PptRenderInstructionDraft`，不直接生成 `.pptx`。

下一阶段需要引入 PPT 渲染器，但不能回退到旧 `office-ppt` / `magazine-web-ppt` 的“prompt 直接交付文件”模式。渲染器必须消费 `PptRenderInstructionDraft`，并作为 oneceo 现有 Altus managed + Sandbox 链路中的受控执行能力。

## 2. 目标

1. 让 PPT 任务在完成 `PptRenderInstructionDraft` 后，可以进入真实 `.pptx` 渲染。
2. 渲染器只消费结构化指令，不重新解释用户原始需求。
3. 渲染过程在 Sandbox 内完成，输出文件进入现有附件和交付物链路。
4. 渲染失败时返回可修复的结构化错误，由 `ppt-workflow` 回到对应子任务修正指令。
5. 第一版优先保证文件可打开、结构正确、内容完整、样式一致，不追求复杂动画、母版模板和高级 Office 特性。

## 3. 非目标

1. 不恢复旧 PPT skill seed。
2. 不新增多子 agent runtime。
3. 不让 API 服务直接生成二进制 PPTX。
4. 不新增独立 MCP server 作为第一版入口。
5. 不支持任意用户上传 PPT 模板的深度复刻。
6. 不做 HTML deck、PDF deck、Keynote 或 Google Slides 输出。

## 4. 总体设计

引入一个受控工具：`render_pptx_from_instructions`。

调用条件：

1. 当前 active skill 包含 `ppt-workflow`。
2. 当前 run 已形成 `PptRenderInstructionDraft`。
3. 用户明确要求最终生成 PPT / PPTX，或在预检后确认进入渲染。

执行位置：

1. Altus managed runtime 暴露工具定义。
2. 工具运行时校验输入和 active skill。
3. Sandbox 内写入渲染输入 JSON。
4. Sandbox 内执行平台下发的 PPT 渲染脚本。
5. 输出 `.pptx`、`render-report.json` 和可选封面/页面预览。
6. `complete_task.attachments` 引用最终 `.pptx`。

核心边界：

`ppt-workflow` 负责“应该渲染什么”，`pptx-renderer` 负责“按指令生成文件”。

## 5. 数据契约

### 5.1 输入：PptRenderInstructionDraft

第一版继续沿用 26 号方案中的草稿结构，但在进入渲染前升级为 `PptRenderInstruction`：

```json
{
  "deck": {
    "title": "",
    "audience": "",
    "purpose": "",
    "slideCount": 0,
    "fileName": "deck.pptx"
  },
  "theme": {
    "canvas": "16:9",
    "fontSystem": {},
    "typeScale": {},
    "colorTokens": {},
    "gridAndSpacing": {},
    "aestheticPreset": "ink-classic",
    "rhythmPlan": [
      { "index": 1, "visualRole": "hero-dark", "layoutFamily": "hero-cover" }
    ],
    "qualityRules": []
  },
  "slides": [
    {
      "index": 1,
      "pageType": "cover",
      "title": "",
      "coreMessage": "",
      "layoutIntent": "",
      "visualRole": "hero-dark",
      "layoutFamily": "hero-cover",
      "kicker": "",
      "chrome": { "left": "", "right": "" },
      "contentBlocks": [],
      "imageSlots": [],
      "speakerNotes": "",
      "sourceRefs": []
    }
  ],
  "sources": [],
  "openQuestions": []
}
```

渲染前硬校验：

1. `deck.title` 非空。
2. `deck.slideCount` 与 `slides.length` 一致。
3. 每页 `index` 连续。
4. 每页至少有 `pageType`、`title` 或 `coreMessage`。
5. `theme.colorTokens` 至少包含背景、主色、文本色。
6. `openQuestions` 为空；如果不为空，不进入渲染。

### 5.2 输出：PptRenderResult

```json
{
  "status": "completed",
  "pptxPath": "deliverables/example.pptx",
  "reportPath": "deliverables/example.render-report.json",
  "slideCount": 8,
  "warnings": [],
  "repairHints": []
}
```

失败时：

```json
{
  "status": "failed",
  "stage": "validate | render | verify",
  "errors": [],
  "repairHints": []
}
```

## 6. 渲染器第一版能力

### 6.0 美术层参考

本阶段参考 `op7418/guizang-ppt-skill` 的审美方法，但不采用其 HTML deck 输出路线。可迁移的是“电子杂志 × 电子墨水”的设计约束：

1. 一份 deck 只能选一套主题色预设，避免任意 hex 拼色。
2. 标题、关键 quote 和大数字使用衬线字体；正文使用非衬线字体；元数据、页码、来源和章节标签使用等宽字体。
3. 每页先规划 `visualRole`：`hero-dark`、`hero-light`、`light`、`dark`，禁止整份 deck 连续白底正文。
4. 页面从固定布局家族中选择：封面、章节幕封、数据大字报、左文右图、图片网格、Pipeline、问题页、大引用、Before/After、图文混排。
5. 图片是第一公民：图片框使用标准比例，顶部和左右不裁切，只允许裁底部；图片不加厚边框或强阴影。
6. 渲染前后都要做 P0 级审美自检：字体分工、主题节奏、图片比例、标题换行、chrome/kicker 不重复。

落地方式：这些规则进入 `ppt-workflow` 的 `PptVisualPlan`、`PptRenderInstructionDraft.theme`、`slides[].visualRole`、`slides[].layoutFamily` 和渲染器默认推断逻辑。渲染器仍输出 `.pptx`，不生成 HTML、WebGL 或网页翻页 deck。

### 6.0.1 版式去模板化修正

2026-05-02 根据真实输出复盘，单靠主题预设会导致“同一模板换色”。后续渲染器必须满足：

1. `layoutFamily` 不能只是提示词，必须实质改变页面结构。
2. 标题、`coreMessage`、`contentBlocks` 之间不得重复同一句话；重复内容由渲染器跳过并记录 warning。
3. `imageSlots` 优先使用同页未重复图片；同一 deck 内避免连续复用同一 URL。
4. 正文页需要承载多层信息：观点、解释、例子、证据或来源，不能只放一行短句。
5. `big-number`、`pipeline`、`before-after`、`image-grid`、`quote-image`、`lead-image-side-text` 至少具有肉眼可辨的不同结构。

### 6.1 页面类型

第一版只支持稳定页面类型：

1. `cover`
2. `agenda`
3. `section-divider`
4. `content`
5. `comparison`
6. `timeline`
7. `quote`
8. `closing`

未知 `pageType` 直接失败，并要求 `ppt_outline_planner` 修正，不做静默降级。

### 6.2 内容块

支持内容块：

1. `heading`
2. `paragraph`
3. `bullets`
4. `metric`
5. `table`
6. `quote`
7. `image`
8. `source-note`

第一版不支持：

1. 动画。
2. 视频。
3. 复杂图表。
4. SmartArt 等 Office 专有高级对象。

### 6.3 素材处理

素材规则：

1. 只使用已经存在于 Sandbox 工作区的图片，或由素材收集阶段明确给出 URL 并下载到工作区的图片。
2. 如果 image slot 缺图，渲染器不自行搜索。
3. 缺图但页面可表达时，返回 warning，并使用主题色占位块。
4. Logo、品牌图、人物图等敏感素材不能凭空生成。

## 7. 实现落点

### 7.1 API 服务

新增服务建议：

1. `apps/api/src/services/ppt-render-tool-service.ts`
2. `apps/api/src/services/ppt-render-instruction-validator.ts`

改动服务：

1. `apps/api/src/services/altus-managed-tool-runtime.ts`
   - 增加 `render_pptx_from_instructions` 执行分支。
2. `apps/api/src/services/altus-managed-shared.ts`
   - 增加工具定义。
3. `apps/api/src/services/altus-managed-prompt-service.ts`
   - 仅当 `ppt-workflow` active 时提示渲染工具边界。
4. `apps/api/src/services/platform-skill-seeds.ts`
   - 更新 `ppt-workflow` 文案：预检通过后可以调用渲染器。

### 7.2 Sandbox

第一版渲染脚本应放在受控平台资源中，下发到 Sandbox 后执行：

1. 输入：`ppt-workflow/render-instructions.json`
2. 输出：`deliverables/<safe-name>.pptx`
3. 报告：`deliverables/<safe-name>.render-report.json`

脚本职责：

1. 读取 JSON。
2. 校验 layout 和内容。
3. 生成 PPTX。
4. 写 render report。
5. 返回 stdout JSON，供工具 runtime 解析。

### 7.3 前端

第一版无需新建完整 PPT 编辑器，只接入现有附件显示：

1. 任务完成消息展示 `.pptx` 附件。
2. 渲染失败时展示结构化错误摘要。
3. 后续再考虑 PPT 预览、页缩略图和修复按钮。

## 8. 工作流变化

采用后，PPT 链路变为：

1. `ppt_intent_analyzer`
2. `ppt_research_planner`
3. `ppt_material_collector`
4. `ppt_visual_planner`
5. `ppt_outline_planner`
6. `ppt_render_instruction_planner`
7. `ppt_preflight_reviewer`
8. `render_pptx_from_instructions`
9. `ppt_render_result_reviewer`
10. `complete_task` 附带 `.pptx`

渲染器失败时，只允许回到产生问题的上游阶段：

1. schema 错误：回到 `ppt_render_instruction_planner`
2. 页面结构错误：回到 `ppt_outline_planner`
3. 样式 token 错误：回到 `ppt_visual_planner`
4. 素材缺失：回到 `ppt_material_collector`

## 9. 验收标准

1. 用户明确要求 PPTX 时，最终附件包含 `.pptx`。
2. 生成的 `.pptx` 能被 PowerPoint / Keynote / LibreOffice 打开。
3. 页数与 `PptRenderInstruction.slideCount` 一致。
4. 每页标题、核心信息和主要内容块不丢失。
5. 缺失图片不会导致空白页；必须有 warning 或占位。
6. 渲染器不自行搜索、不自行改写主题、不自行补新页面。
7. 失败时返回结构化 `repairHints`，而不是只给异常堆栈。
8. `complete_task.attachments` 中必须包含生成文件路径。

## 10. 测试计划

1. `ppt-render-instruction-validator` 校验成功。
2. `slideCount` 不一致时报错。
3. 未知 `pageType` 报错。
4. `openQuestions` 非空时禁止渲染。
5. `render_pptx_from_instructions` 只允许在 `ppt-workflow` active 时调用。

### 10.2 集成测试

1. mock Sandbox 执行成功，返回 `.pptx` 和 report。
2. mock Sandbox 执行失败，runtime 返回结构化错误。
3. Altus run 完成时附件包含 `.pptx`。

### 10.3 真实 smoke

使用一个 5 页职业规划 PPT 请求验证：

1. 先形成 `PptRenderInstruction`。
2. 调用渲染器。
3. 输出 `career-plan.pptx`。
4. 下载后能打开，页数为 5。
