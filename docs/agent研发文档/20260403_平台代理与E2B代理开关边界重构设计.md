# 20260403 平台代理与 E2B 代理开关边界重构设计

## 1. 问题背景

当前 `apps/api` 内同时存在两个代理开关：

1. `ONECEO_PROXY_ENABLED`
2. `E2B_PROXY_ENABLED`

现状实现把两者混在同一条优先级链路里使用：

1. `apps/api/src/config/env.ts` 通过 `E2B_PROXY_ENABLED ?? ONECEO_PROXY_ENABLED` 决定是否初始化全局 `undici` 代理
2. `apps/api/src/index.ts` 通过同样的优先级决定是否补充全局 `NO_PROXY`
3. `apps/api/src/connectors/e2b-connector.ts` 也通过同样的优先级决定是否再次设置全局 dispatcher

这导致两个问题：

1. 名义上属于 E2B 专项的开关，实际上会影响 GitHub、Tavily、LLM Proxy 等非 E2B 外呼
2. 用户关闭 `ONECEO_PROXY_ENABLED` 后，只要 `E2B_PROXY_ENABLED=true`，API 主进程仍会继续走平台代理，配置语义与运行行为不一致

## 2. 目标

本次重构只解决一个问题：

1. 明确全局 HTTP 代理与 E2B 专项代理的作用边界

必须满足：

1. `ONECEO_PROXY_ENABLED` 只控制 API 主进程的全局出站代理
2. `E2B_PROXY_ENABLED` 不允许再参与 API 主进程的全局代理初始化
3. 关闭 `ONECEO_PROXY_ENABLED` 后，GitHub、Tavily、LLM Proxy、普通 `fetch` 外呼都不再走平台代理
4. `sandbox-archive-job` 这类通过 E2B connector 发起的请求，在 API 主进程内也必须服从全局代理开关，而不是再被 `E2B_PROXY_ENABLED` 反向打开

## 3. 关键事实与约束

经检查当前 `e2b` SDK 类型定义：

1. `SandboxOpts`
2. `SandboxConnectOpts`
3. `ConnectionOpts`

只提供：

1. `apiKey`
2. `domain`
3. `apiUrl`
4. `headers`
5. `requestTimeoutMs`

未暴露独立 `fetch` / `dispatcher` / `http client` 注入能力。

因此，在当前 SDK 能力边界下，E2B 请求无法在 API 主进程内稳定做到“只对 E2B 单独挂代理而不污染全局 `fetch`”。

结论：

1. 在 API 主进程里，代理初始化必须收敛为全局唯一入口
2. `E2B_PROXY_ENABLED` 不能再参与 `apps/api/src/config/env.ts` 和 `apps/api/src/index.ts` 的全局代理决策
3. `apps/api/src/connectors/e2b-connector.ts` 只能作为“未经过全局环境初始化时的独立 connector 兜底入口”，不能再作为 API 主进程行为来源

## 4. 设计方案

### 4.1 全局代理入口

新增统一代理配置模块，负责：

1. 读取 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`
2. 解析 `ONECEO_PROXY_ENABLED`
3. 解析 `E2B_PROXY_ENABLED`
4. 统一布尔开关口径

规则：

1. `ONECEO_PROXY_ENABLED` 只用于全局 `undici` dispatcher
2. `E2B_PROXY_ENABLED` 只用于 E2B connector 本地判断
3. 两者不再互相回退，不再互相覆盖

### 4.2 `env.ts`

`apps/api/src/config/env.ts` 改造为：

1. 全局代理是否启用，只读取 `ONECEO_PROXY_ENABLED`
2. 代理 URL 仍读取 `HTTP_PROXY` / `HTTPS_PROXY`
3. 日志前缀改成全局语义，不再继续打印 `E2B_PROXY`

### 4.3 `index.ts`

`apps/api/src/index.ts` 改造为：

1. 只有在 `ONECEO_PROXY_ENABLED=true` 时才追加 E2B 域名到 `NO_PROXY`
2. 不再读取 `E2B_PROXY_ENABLED`

### 4.4 `e2b-connector.ts`

`apps/api/src/connectors/e2b-connector.ts` 改造为：

1. 只读取 `E2B_PROXY_ENABLED`
2. 不再回退读取 `ONECEO_PROXY_ENABLED`
3. 仅当全局 dispatcher 尚未初始化时，才允许用 `E2B_PROXY_ENABLED` 做独立 connector 启动兜底

这意味着：

1. 在 API 主进程正常启动路径中，E2B 请求最终服从全局代理入口
2. 在少量独立脚本 / 独立测试只直接 import `e2b-connector` 的场景中，`E2B_PROXY_ENABLED` 仍然可单独生效

## 5. 配置语义

重构后配置语义固定如下：

### 5.1 `ONECEO_PROXY_ENABLED`

作用：

1. API 主进程全局 HTTP 出站代理总开关

影响范围：

1. GitHub 连接器外呼
2. Tavily 外呼
3. LLM Proxy 上游外呼
4. KVM orchestrator HTTP 外呼
5. OSAC bridge readiness HTTP 外呼
6. API 主进程中所有依赖全局 `fetch` / `undici` dispatcher 的请求

### 5.2 `E2B_PROXY_ENABLED`

作用：

1. E2B connector 独立运行场景的专项代理开关

影响范围：

1. 仅在未经过全局环境初始化、直接加载 `e2b-connector` 的场景中生效

不再允许解释为：

1. API 主进程级全局代理开关
2. 覆盖 `ONECEO_PROXY_ENABLED`
3. 反向打开整个 API 的代理转发

## 6. 验收标准

1. 当 `ONECEO_PROXY_ENABLED=false` 且 `HTTP_PROXY/HTTPS_PROXY` 仍有值时，API 主进程不再打印“已启用代理转发”
2. 当 `ONECEO_PROXY_ENABLED=false` 时，GitHub/Tavily/LLM Proxy 等外呼不再访问本地代理端口
3. 当 `ONECEO_PROXY_ENABLED=false` 且 `E2B_PROXY_ENABLED=true` 时，API 主进程内的 `sandbox-archive-job` 不再因为 E2B 开关而访问本地代理端口
4. 当独立脚本未加载 `config/env.ts`、只直接 import `e2b-connector` 时，`E2B_PROXY_ENABLED=true` 仍可保留现有专项行为
5. `.env.example` 中两个开关的说明与实际代码行为一致

## 7. 2026-04-04 Supabase MCP 传输补充

结合真实链路验证结果，Supabase MCP 传输策略补充如下：

1. Supabase provider 的远端传输从 `remote_sse` 调整为 `streamable_http`。
2. 代理变量注入策略保持不变，仍由 `ONECEO_PROXY_ENABLED + HTTP(S)_PROXY + NO_PROXY` 控制。
3. attach 排障优先级统一为：先看 `ATTACH_MCP_PROVIDER_TO_SESSION` 回包状态与 `errorMessage`，再看 live provider 检查结果。
4. 若回包为 `failed_to_attach/attach_failed`，应直接判定 attach 失败，不再以“运行时未保留 provider”作为一线错误语义。
