# 28 Word / Excel 生成 Skill 产品化质量门方案 [20260502-1500已采用]

## 1. 背景

`Word 文档` 与 `Excel 表格` 已在 2026-03-28 完成首版多阶段协同升级：

- `office-docx` 已具备 `docx_task_router -> docx_qa_reviewer` 的 6 阶段协议。
- `office-xlsx` 已具备 `xlsx_task_router -> xlsx_qa_reviewer` 的 6 阶段协议。
- Altus managed prompt 已要求生成 `document_manifest.json` / `workbook_manifest.json`。
- 真实 smoke 已证明 `.docx` / `.xlsx` 可以生成、落库、下载。

但当前状态仍然主要依赖 prompt 纪律，平台没有对最终文件和 manifest 做强校验。因此它们处于“技术首版可用”，还没达到“产品平均可交付”的稳定状态。

本轮目标是补齐产品级质量门，而不是重写 Office skill 或替换生成引擎。

## 1.1 2026-05-06 边界修正

基于真实用户回放复盘，确认旧方案还有两个系统性问题：

- 平台允许 `write_file` 直接写 `.docx/.xlsx/.pdf/.pptx`，导致模型可能先把文本伪装成二进制交付物。
- `document_manifest.json / workbook_manifest.json` 被设计成模型显式生成文件，导致内部质量证据泄漏到用户动作流。

因此补充以下边界修正：

- `write_file` 只允许写 UTF-8 文本文件，最终二进制交付物必须走真实生成链路。
- Office 质量门默认基于真实文件结构验证，不再把 manifest 当成模型必须显式生成的用户可见产物。
- manifest 若未来仍存在，也只能作为内部可选证据，不能再成为用户流程的一环。

## 2. 当前问题

### 2.1 质量门停留在 prompt 约束

当前 prompt 要求：

- DOCX 写 `document_manifest.json`。
- XLSX 写 `workbook_manifest.json`。
- 完成前执行 QA gate。

但平台侧没有读取这些 manifest，也没有把 manifest 缺失、字段缺失、文件结构异常转成可观测的失败或重试依据。

### 2.2 文件质量缺少结构化验证

DOCX 当前缺少平台侧验证：

- 文件是否能被解包和读取。
- 是否存在有效标题层级。
- 是否有明显占位符、空章节或模板残留。
- 文档结构是否与 `contentArchetype` 基本匹配。
- 使用外部资料时是否保留来源 URL。

XLSX 当前缺少平台侧验证：

- workbook 是否能被读取。
- sheet 数量和 sheet 名是否符合 workbook plan。
- 是否存在公式。
- 派生值是否被大量硬编码。
- 是否包含来源或说明 sheet。
- 是否存在空表、无表头、无数据区等伪完成情况。

### 2.3 回归样例不足

既有真实 smoke 覆盖：

- Word：1 条业务计划书。
- Excel：1 条学习计划。

这只能证明路径曾经成功，不能证明不同 archetype 在日常产品使用中稳定。

## 3. 目标

本轮完成后，`office-docx` / `office-xlsx` 应达到以下状态：

1. 用户选择 Word / Excel skill 后，仍然保持当前单入口体验。
2. 生成完成后，平台能验证最终文件存在、可读取、结构合理。
3. Office 质量证据改为平台基于真实文件结构直接提取；`document_manifest.json` / `workbook_manifest.json` 不再作为模型显式交付步骤。
4. 常见 Word / Excel 任务有固定回归样例和可复跑脚本。
5. E2B smoke 每次启动 sandbox 都有关闭行为，避免测试成本泄漏。

## 4. 非目标

本轮不做：

- 不替换 `python-docx` / `openpyxl` 路线。
- 不新增 Office mode 产品入口。
- 不改前端 Skill 菜单形态。
- 不新增模板市场。
- 不重做 PPT 工作流。
- 不把质量门设计成复杂多服务链路。

## 5. 实现范围

### 5.1 增加 Office 产物质量验证器

新增 API 内部服务，建议命名：

- `apps/api/src/services/office-artifact-quality-service.ts`

职责：

- 对 DOCX / XLSX 附件做最小文件级验证。
- 以真实文件结构为主做验证；不要求模型额外生成 sidecar manifest。
- 生成结构化 `OfficeArtifactQualityReport`。
- 不直接修改用户文件。

### 5.2 DOCX 验证规则

输入：

- 最终 `.docx` 文件路径。
- 可选内部 manifest 证据。

验证项：

1. 文件存在且扩展名为 `.docx`。
2. 文件大小大于最小阈值，避免空壳文件。
3. `word/document.xml` 可读取。
4. 正文中存在非空段落。
5. 标题或章节数量达到最小要求。
6. 不包含明显占位符，如 `TODO`、`TBD`、`示例文本`、`lorem ipsum`、`待补充`。
7. 若 manifest 声明 `sourcePreservationRequired=true`，正文或 manifest 中必须出现 URL。
8. 若 manifest 声明 `sectionCount`，实际检测到的章节数不能明显少于声明值。

输出：

- `passed`
- `warnings[]`
- `errors[]`
- `metrics.paragraphCount`
- `metrics.headingLikeParagraphCount`
- `metrics.urlCount`
- `manifestStatus`

### 5.3 XLSX 验证规则

输入：

- 最终 `.xlsx` 文件路径。
- 可选内部 manifest 证据。

验证项：

1. 文件存在且扩展名为 `.xlsx`。
2. 文件大小大于最小阈值，避免空壳文件。
3. workbook 可读取。
4. 至少存在 1 个 worksheet。
5. 每个非说明类 worksheet 至少有表头或有效数据区。
6. 若 manifest 声明 `requiresFormulas=true`，必须存在公式单元格。
7. 若 manifest 声明 `requiresSourceSheet=true`，必须存在来源、Sources、参考、说明等 sheet 或 URL。
8. 避免把结构性任务交付成单 sheet 扁平表：当 manifest 声明 sheet 数大于 1 时，实际 sheet 数不能少于声明值。

输出：

- `passed`
- `warnings[]`
- `errors[]`
- `metrics.sheetCount`
- `metrics.formulaCellCount`
- `metrics.urlCount`
- `metrics.nonEmptyCellCount`
- `manifestStatus`

### 5.4 将质量报告接入完成链路

最短路径：

1. 在 `complete_task` 附件持久化之后，对 `.docx` / `.xlsx` 附件执行质量验证。
2. 质量报告先写入日志或 timeline metadata。
3. 若出现硬错误，阻止进入“正常可交付”状态，并把错误返回给 run，让 agent 修复后重新完成。

2026-05-05 稳定性修正：

- 交付持久化链路不再把 `document_manifest.json` / `workbook_manifest.json` 缺失视为阻断型错误，避免模型偶发漏写 manifest 时导致真实可用的 Office 文件无法交付。
- manifest 不再要求在 prompt 中显式生成；即使未来存在，也只作为内部可选证据读取，平台默认回到“基于真实文件结构”的质量验证。
- XLSX 质量验证必须识别 `inlineStr`、仅公式单元格等常见 OpenXML 写法，不能只统计 `<v>`，否则会把真实有内容的工作簿误判为空表。
- `complete_task.attachments` 从“仅 prompt 约束”升级为“运行时硬规则”：下载型交付若缺少附件声明，或把附件数组错误写成字符串/非法结构，平台必须直接阻断完成，避免出现“run 已完成但正式交付物为空”的假完成。
- 这类阻断不能停留在“最终报错给用户”。工具层必须返回可修复的错误语义，让 Altus 明确知道应如何重试：
  - `complete_task_attachments_invalid`：把字符串化附件改成真实 JSON 数组，再次调用 `complete_task`。
  - `complete_task_downloadable_requires_attachments`：先确认最终 `pdf/docx/xlsx/pptx/zip` 文件已生成，再把工作区相对路径写入 `complete_task.attachments` 后重试。
  - `complete_task_attachment_path_invalid`：附件必须指向工作区内真实文件，不能传空路径或工作区根目录。
- 因此，下载型交付的产品目标是“优先促成完成交付”，而不是把格式错误直接暴露成用户态失败；只要属于可修复工具错误，就应回到 Altus 修复回路里完成二次提交。
- DOCX / XLSX 质量门要对 archetype 做最小感知：`meeting_memo`、`external_statement`、`input_form` 这类天然紧凑型交付不能继续套用统一的高阈值，否则会误杀真实可用文件。
硬错误示例：

- 文件不存在。
- 文件无法读取。
- DOCX 无有效正文。
- XLSX 无 worksheet 或 workbook 无法读取。

警告示例：

- 来源 URL 缺失。
- 章节数量偏少。
- 公式数量偏少。
- workbook 只有单 sheet，但任务仍可能是简单表格。

## 6. 关键数据结构

### 6.1 OfficeArtifactQualityReport

```ts
type OfficeArtifactKind = 'docx' | 'xlsx';

interface OfficeArtifactQualityReport {
  kind: OfficeArtifactKind;
  artifactPath: string;
  manifestPath?: string;
  passed: boolean;
  errors: string[];
  warnings: string[];
  metrics: Record<string, number | string | boolean>;
  manifestStatus: 'found' | 'missing' | 'invalid' | 'not_required';
}
```

### 6.2 Manifest 最小字段

DOCX：

```json
{
  "artifactType": "docx",
  "fileName": "final.docx",
  "contentArchetype": "business_plan",
  "stylePack": "formal_executive",
  "sectionCount": 6,
  "sourcePreservationRequired": true
}
```

XLSX：

```json
{
  "artifactType": "xlsx",
  "fileName": "final.xlsx",
  "contentArchetype": "budget_tracker",
  "sheetCount": 4,
  "requiresFormulas": true,
  "requiresSourceSheet": false
}
```

## 8. 风险与处理

### 8.1 质量门过严导致简单任务失败

处理：

- 将不可读取、空文件、manifest 缺失列为硬错误。
- 将章节偏少、公式偏少、来源不足列为 warning。
- 只有明确与 manifest 声明冲突时才升级为硬错误。

### 8.2 读取 DOCX / XLSX 需要依赖

处理：

- 优先使用已有 Node 依赖或轻量解析方式。
- DOCX 可先用 zip 读取 `word/document.xml` 做结构检查。
- XLSX 可使用现有 xlsx 解析库；若没有现成依赖，再评估新增最小依赖。

### 8.3 模型不稳定生成 manifest

处理：

- prompt 明确 manifest 与最终文件同目录。
- 平台质量门将 manifest 缺失转成可观测错误。
- 后续如仍不稳定，再在 tool runtime 层增加自动 manifest 搜索和关联。
