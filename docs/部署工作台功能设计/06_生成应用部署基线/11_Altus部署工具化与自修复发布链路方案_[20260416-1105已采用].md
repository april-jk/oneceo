# Altus 部署工具化与自修复发布链路方案 [20260416-1105已采用]

## 1. 背景

当前 OneCEO 已经具备可工作的部署主链：

- Sandbox 工作区导出到 GitHub 托管仓库
- Railway 项目、环境、服务与域名编排
- Umami website 绑定与变量注入
- 模板 bootstrap 与合规检查

现阶段缺的不是“能不能部署”，而是两件事：

1. 部署还主要停留在平台按钮和 direct capability 层，没有进入 Altus managed tool runtime。
2. 部署前的模板不适配、脚本缺失、统计入口缺失等问题，虽然已经能被检查出来，但还没有形成“Altus 自动修复后再继续发布”的闭环。

用户目标是参照 Suna 的工具封装方式，把部署收敛成 Altus 可以直接调用的 tools，并且支持通过发送消息触发，例如：

- “帮我部署这个项目”
- “重新发布一下”
- “看一下当前部署状态”

同时，用户界面保持极简，只显示端到端的发布进度和结果；失败原因、Railway 构建细节、模板不合规细节进入内部 debug 通道，不直接暴露给普通用户。

## 2. 目标

本方案落地后，Altus managed 模式的发布链路应满足：

1. 部署是标准 tool call，而不是 managed mode 外部特殊分支。
2. 用户通过自然语言发消息即可触发部署、重部署、回滚、状态查询。
3. 平台持续提供固定模板注入与部署基线，不依赖 agent 临场自由发挥。
4. 出现模板不适配、脚本缺失、健康检查缺失、统计入口缺失等“可修复问题”时，Altus 应优先自动修复并重试部署。
5. 普通用户界面只看到简单状态，不看到供应商报错、内部 token、构建日志细节。
6. 所有细节仍然保留内部 debug 模式，便于排障、回放和平台治理。

## 3. 范围与非目标

### 3.1 本次范围

- Altus managed tool schema 增加部署相关工具
- Altus prompt 增加部署与自修复行为约束
- managed tool runtime 接入部署执行器
- 复用现有 Railway + GitHub + Umami + template compliance 主链
- 前端 managed 对话区补齐部署工具的极简状态呈现
- 前端部署工作台增加内部 debug 数据承载，但默认不向用户展开

### 3.2 非目标

- 不替换现有 Railway 供应商
- 不移除 direct mode deployment capability
- 不让用户直接看到 Railway/Umami/GitHub 的原始错误回包
- 不把部署修复做成无上限循环
- 不在本阶段引入第二套模板体系

## 4. 参照 Suna 的收敛原则

参照 Suna，本方案不再把“部署”视为 UI 侧额外按钮逻辑，而是视为 runner 可调用的标准工具能力。其核心原则是：

1. 工具定义统一进入 tool registry
2. 模型通过 tool call 触发部署，而不是走隐藏的前端捷径
3. 执行结果通过 run event 流返回
4. 失败不是直接终止，而是先判断是否属于可修复问题
5. 可修复问题回到 agent 的读文件、改文件、跑命令能力中处理，再重试部署

对 OneCEO 来说，Suna 参照的不是其具体云厂商，而是这一套：

- `tool definition`
- `tool executor`
- `prompt contract`
- `run event projection`
- `UI 只消费统一事件流`

## 5. 总体方案

## 5.1 工具层收敛

Altus managed mode 新增四个部署工具：

1. `deploy_application`
2. `redeploy_application`
3. `rollback_application_deployment`
4. `get_application_deployment_status`

其中：

- `deploy_application` 是主入口，负责模板基线检查、必要注入、发布、健康校验、统计绑定。
- `redeploy_application` 用于代码更新后的再次发布。
- `rollback_application_deployment` 用于恢复到上一个可用版本。
- `get_application_deployment_status` 用于查询最新部署状态和访问地址。

这四个工具进入：

- `apps/api/src/services/altus-managed-shared.ts`
- `apps/api/src/services/altus-managed-tool-runtime.ts`

不再只存在于：

- `direct-mode-capability-registry.ts`
- `direct-mode-deployment-capability-service.ts`

## 5.2 执行层复用，而不是重写

managed deploy tool 不新造一套部署逻辑，而是封装现有服务：

- `deployment-template-bootstrap-service.ts`
- `template-compliance-service.ts`
- `task-creation-deployment-source-service.ts`
- `platform-deployment-account-service.ts`
- `task-session-deployment-analytics-service.ts`
- `railway-deployment-service.ts`
- `direct-mode-deployment-capability-service.ts`

推荐实现方式：

新增：

- `apps/api/src/services/altus-managed-deployment-tool-service.ts`

该服务负责把 managed tool 的入参、执行状态、自修复判定、debug 元数据收敛起来；底层优先复用现有 direct deploy 服务和基线服务，不重复实现发布逻辑。

同时，平台部署动作本身需要再下沉一层公共 runtime，避免“路由一套、direct capability 一套、按钮触发再拼一套”：

- `apps/api/src/services/task-session-deployment-runtime-service.ts`

该 runtime 负责统一封装：

1. 会话环境解析
2. 部署面板状态构建
3. analytics 绑定准备
4. 工作区发布到 GitHub
5. Railway deploy / redeploy / rollback
6. 公网健康检查等待

这样无论入口来自：

- Altus managed tools
- direct mode deployment capability
- 平台 deployment REST routes

最终都会落到同一条执行链，避免后续修一处漏一处。

当前已完成的收敛状态：

- `altus-managed-deployment-tool-service.ts` 已直接调用 `task-session-deployment-runtime-service.ts`
- 不再通过 `direct-mode-deployment-capability-service.ts` 做二次转发
- `AltusManagedToolRuntime` 已把 `userId / sessionId / sandboxId / workspaceRoot` 一并传入 deployment runtime

因此当前 managed tools、direct capability、REST routes 已经共享同一套部署执行语义和错误映射。

## 5.3 生成期与部署期都走固定模板基线

平台继续提供固定注入模板/组件，最小基线仍然是：

- `package.json`
- `oneceo.manifest.json`
- build/start scripts
- healthcheck 路由
- analytics bootstrap
- Railway Postgres 契约

其中平台已有的强制注入与检查继续保留：

- `ensureDeploymentTemplateBootstrap`
- `ensureTemplateCompliance`
- Umami runtime env 注入

本方案新增的是“Altus 自修复回路”，不是替换这些平台基线。

## 6. 工具契约设计

## 6.1 `deploy_application`

建议参数：

```json
{
  "mode": "publish",
  "userVisibleIntent": "deploy"
}
```

说明：

- 对用户不暴露复杂参数
- task session、workspace、sandbox、userId 由 managed run 上下文自动注入
- tool 自己判断当前是首次部署还是覆盖发布

建议返回结构：

```json
{
  "phase": "completed",
  "status": "success",
  "url": "https://xxx.oneceo.app",
  "deploymentId": "dep_xxx",
  "summary": "发布成功，站点已可访问",
  "debugToken": "internal-only",
  "repair": null
}
```

若命中可修复问题，则不直接报 fatal error，而是返回：

```json
{
  "phase": "repair_required",
  "status": "retryable",
  "summary": "当前项目缺少部署基线，需先修复后再继续发布",
  "repair": {
    "category": "template_compliance",
    "checks": [
      "missing_build_script",
      "missing_healthcheck_route",
      "missing_analytics_entry"
    ],
    "suggestedActions": [
      "检查 package.json 的 build/start 脚本",
      "补齐 /api/system/health 路由",
      "确保 HTML 入口可注入 OneCEO analytics bootstrap"
    ]
  }
}
```

这个结构只提供给 Altus 自己使用；前端主界面不直接渲染原始 `checks`。

## 6.2 `redeploy_application`

行为：

- 使用当前 session 对应 environment/service 的最新版本重新发布
- 若 workspace 已变更，可先同步源码再触发重新部署
- 若发现新的模板不合规，也进入同一套 repair 回路

## 6.3 `rollback_application_deployment`

行为：

- 选择上一个可回滚版本
- 返回新的部署状态与访问地址
- 若平台供应商不允许回滚，写入 debug 元数据并返回受控失败结果

## 6.4 `get_application_deployment_status`

行为：

- 返回当前部署状态、访问地址、最近一次成功时间、绑定域名、统计状态
- 结果用于 Altus 在聊天里回答“已经发布完成”“正在发布”“还在修复中”

## 7. Altus 自修复闭环

## 7.1 自修复边界

仅对以下“代码或模板层问题”进入自动修复：

1. 缺少或错误的 `build` / `start` 脚本
2. 缺少 `oneceo.manifest.json`
3. 缺少健康检查路由
4. HTML 入口无法被 analytics bootstrap 注入
5. Railway Postgres 契约声明缺失但代码中已明显依赖数据库

## 7.1A 新增硬边界（2026-05-10）

为了确保对用户交付的确定性，本方案补充以下硬边界：

1. `web_app` / `static_site` 进入部署主链时，若项目画像模板族不是 `oneceo_official_vite_node_shell`，不再放行自由修复，直接返回 `template_compliance`
2. `package.json`、`vite.config.ts`、`oneceo.manifest.json`、`client/index.html`、固定健康检查壳视为平台契约文件；普通部署修复不允许擅自漂移这些文件
3. `repairPolicy=safe_template_adapt` 对应的是“在固定壳内修内容与局部实现”，不是“自由切换 runtime 或重写部署契约”

## 7.1B 平台能力失败分流（2026-05-10）

本方案新增一类不可继续下沉给 Altus 代码修复的错误：

- `platform_capability`

触发条件包括但不限于：

1. sandbox 缺少 Playwright 模块
2. sandbox 缺少 Playwright 浏览器二进制
3. 平台约定的浏览器路径或运行能力不可用

命中后要求：

1. 不再指导 Altus 修改工作区源码、`package.json`、`manifest` 或固定模板契约
2. 只允许汇报平台阻塞、等待平台能力恢复或由运维修复
3. 部署工具返回 `retryable_repair_required`，但修复责任归平台能力层，不归工作区代码层
6. 统计变量引用错误但属于模板层可修正问题

以下问题不进入自动代码修复，而是记为平台/权限类错误：

1. GitHub App 未授权
2. Railway Admin Token/Project Token 无效
3. Umami 平台不可用
4. 域名或网络层异常
5. 用户仓库/环境不存在且平台无权限创建

## 7.1C 风险确认后的部署意图继承（2026-05-10）

部署主链补充一条会话意图规则：

1. 上一条用户消息已经是显式部署请求，例如“帮我部署当前项目”
2. 平台随后因为 `deploy.production` 或 `deploy.preview` 进入风险确认提问
3. 用户当前轮只回复“确认”“确认继续”“继续”这类确认语句

此时 runtime 必须把这条回复解释为“确认上一条显式部署意图”，而不是把当前轮重新降级成普通闲聊或 advisory turn。

实现约束：

1. “历史部署请求不能被模糊当前轮误继承”这条总规则继续保留
2. 唯一例外是：存在待回答的部署风险确认问题，且当前轮是明确确认回复
3. 命中该例外时，要恢复上一条显式部署意图对应的 `deploymentAllowed / deployRequested / capabilityKind`
4. 不能只放开 `deploymentAllowed`，否则 deployment skill 自动挂载和 tool runtime 仍会因为 `deployRequested=false` 而走偏

这样可以避免“用户已经确认继续，但 Altus 仍回答当前会话部署权限未开放”的假阻塞。

## 7.2 自修复执行方式

推荐回路：

1. 用户发消息要求“部署”
2. 模型调用 `deploy_application`
3. 工具先做 bootstrap + compliance + deploy readiness
4. 若返回 `repair_required`
5. prompt 明确要求 Altus：
   - 不把底层报错直接展示给用户
   - 使用 `read_file` / `search_code` / `write_file` / `shell_execute` 修复工作区
   - 修复后自行再次调用 `deploy_application`
6. 最多允许 2 到 3 轮 repair-retry
7. 超过上限后，run 进入受控失败，并把详情沉淀到 debug 通道

这样修复动作仍然留在 Altus 的标准工具回路里，而不是写死在 deploy tool 内部做黑盒改代码。

## 7.3 Prompt 约束

`altus-managed-prompt-service.ts` 需要新增以下硬约束：

1. 用户要求发布、部署、上线时，优先调用部署工具，不要只返回文字说明。
2. 如果部署工具返回 `repair_required`，必须优先修复并重试，而不是立刻向用户报告失败。
3. 普通用户回复只给出阶段性结论，例如“正在修复发布配置”“正在发布”“发布完成”。
4. 不向普通用户暴露 Railway/GitHub/Umami 的原始错误。
5. 真正完成时，再调用 `complete_task` 结束 run。

## 8. 平台固定注入模板/组件

## 8.1 平台模板职责

平台提供一套稳定的发布基线，而不是让 agent 每次临场拼：

1. analytics bootstrap 注入片段
2. 默认 manifest 生成
3. 默认 healthcheck 约定
4. 默认 build/start 契约
5. Railway 环境变量映射
6. Umami website 绑定变量

## 8.2 模板的使用时机

### 生成阶段

- agent 生成网站时优先在模板内填充业务代码

### 部署阶段

- 平台再次执行 bootstrap 与 compliance
- 任何遗漏都由平台基线兜底检查出来

### 修复阶段

- Altus 按平台契约修复
- 不允许引入与平台模板冲突的自定义发布方式

## 8.3 推荐补强点

现有 `ensureDeploymentTemplateBootstrap` 主要注入 HTML analytics 片段，本方案建议后续再补一个更明确的模板物料层：

- `apps/api/src/services/deployment-template-materializer-service.ts`

职责不是生成整个应用，而是提供：

1. 标准 health route 代码片段
2. 标准 manifest 模板
3. 标准环境变量声明模板
4. 标准 analytics helper 代码片段

这样 Altus 在 repair 阶段可以明确套用平台物料，而不是自由生成近似代码。

## 9. 前端交互方案

## 9.1 用户主界面只保留极简状态

聊天区与部署卡片只展示：

1. `正在准备发布`
2. `正在修复发布配置`
3. `正在同步代码`
4. `正在创建部署`
5. `正在等待站点可访问`
6. `发布完成`
7. `发布暂未完成`

以及必要结果：

- 访问地址
- 当前部署状态
- 是否已接入站点统计

## 9.2 不直接显示的内容

以下内容默认不向普通用户显示：

- Railway 构建日志全文
- GitHub App 权限细节
- Umami API 原始报错
- compliance 原始错误数组
- 内部 token / deployment debug payload

## 9.3 内部 debug 模式

debug 信息仍然要保留，但只进入：

1. run event metadata
2. 部署工作台内部 debug 区
3. 管理态或开发态调试入口

建议新增 debug 载荷结构：

```json
{
  "debug": {
    "deploymentPhase": "template_check",
    "retryCount": 1,
    "templateChecks": ["missing_healthcheck_route"],
    "providerErrors": [],
    "lastDeploymentId": "dep_xxx"
  }
}
```

前端普通用户态不消费 `debug` 字段。

## 10. 后端实施落点

## 10.1 API 服务

新增或修改：

- `apps/api/src/services/altus-managed-shared.ts`
  - 注册部署工具 schema
- `apps/api/src/services/altus-managed-tool-runtime.ts`
  - 执行部署工具
- `apps/api/src/services/altus-managed-deployment-tool-service.ts`
  - 部署工具执行封装、自修复判定、debug 元数据整合
- `apps/api/src/services/altus-managed-prompt-service.ts`
  - 增加部署与修复约束
- `apps/api/src/services/altus-run-coordinator.ts`
  - 细化部署工具事件写入与 tool result 回传

## 10.2 复用现有部署服务

继续复用：

- `direct-mode-deployment-capability-service.ts`
- `platform-deployment-account-service.ts`
- `task-creation-deployment-source-service.ts`
- `deployment-template-bootstrap-service.ts`
- `template-compliance-service.ts`
- `task-session-deployment-analytics-service.ts`
- `railway-deployment-service.ts`

原则：

- 发布主链只保留一份
- managed tool 是新的接入层，不是新的部署实现

## 10.3 推荐数据结构

`altus-managed-deployment-tool-service.ts` 应区分三类结果：

1. `success`
2. `retryable_repair_required`
3. `fatal_platform_error`

这样 runner 和 prompt 才能稳定分流。

补充约束：

- Railway `FAILED / CRASHED / REMOVED` 等终态失败，或部署面板明确返回公网访问验证失败、`404 Application not found`，不得包装为 `success`。
- `get_application_deployment_status` 不是只要查询成功就代表部署成功；它必须把终态失败映射为 `retryable_repair_required`，并携带 `repair.category=deployment_failed`。
- `complete_task` 的部署完成守卫必须拒绝 failed 类 deploymentStatus，避免 Altus 在公网不可用时向用户声明“部署完成”。

## 11. 前端实施落点

建议修改：

- `apps/web/client/src/pages/Home.tsx`
  - 增加部署工具名称、摘要、预览文案
  - 对部署工具使用极简状态文案
- `apps/web/client/src/hooks/useTaskCreationAgent.ts`
  - 把部署事件归并为用户可理解的阶段
- 部署工作台相关组件
  - 承接内部 debug 数据，但默认折叠或仅开发态可见

当前已落地为双视图投影模型：

- 后端 run event 在写入 `tool_call_completed / tool_call_failed` 时直接生成：
  - `userView.summary`
  - `userView.preview`
  - `userView.detail`
  - `internalView.detail`
- 前端主会话与工具回放默认只读取 `userView`
- `internalView` 只在 replay 抽屉中按需切换，不在普通消息流直接展示
- 这样部署展示的稳定性不再依赖前端二次解析 `outputPreview/debug` 原始结构

建议新增部署工具展示名：

- `deploy_application` -> `发布应用`
- `redeploy_application` -> `重新发布`
- `rollback_application_deployment` -> `回滚部署`
- `get_application_deployment_status` -> `查询部署状态`

## 12. 与现有 direct capability 的关系

当前 direct mode 已有：

- `deploy_session_website`
- `redeploy_session_website`
- `rollback_session_deployment`
- `get_session_deployment_status`

本方案不移除它们。

关系定义如下：

1. direct mode 继续保留快速拦截能力
2. managed mode 新增标准 deploy tools
3. 两者底层尽量复用同一套部署服务
4. 后续若要统一，只统一服务层，不强制统一入口层

## 13. 验收口径

满足以下条件才算落地完成：

1. 用户在 Altus managed 对话里发送“帮我部署这个项目”，会触发真实 tool call
2. 首次部署时会自动完成项目资源准备、源码同步、Railway 发布、Umami 绑定
3. 如果缺少模板基线，Altus 会先修复，再自动重试部署
4. 用户主界面只看到简单阶段与最终结果，且默认只消费后端投影好的 `userView`
5. debug 数据只保留在内部通道，通过 `internalView` 承接，不在主消息流直出 provider 原始错误
6. 代码更新后，再发送“重新部署”可以成功发布新版本
7. `get_application_deployment_status` 能返回最新地址与当前状态

## 14. 实施顺序

1. 先补部署工具 schema 与执行封装
2. 再补 prompt 约束与 repair-retry 回路
3. 再补前端极简状态展示
4. 最后补 debug 元数据与工作台内部调试承载
