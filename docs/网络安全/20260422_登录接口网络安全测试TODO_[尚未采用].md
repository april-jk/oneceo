## 3. 当前实现事实基线

以下是当前代码中已经确认的事实，用于限定后续测试 TODO：

1. 登录入口为 `POST /api/auth/login`，服务端在 [auth-routes.ts](/Users/watson/codingProj/oneceo/apps/api/src/routes/auth-routes.ts) 中直接调用 `appAuthService.login(...)`。
2. 登录失败统一返回 `400` 与通用文案“邮箱或密码错误”，当前已具备基础的账户存在性信息收敛。
3. 密码校验当前使用 `scrypt + salt + timingSafeEqual`，位于 [auth-password.ts](/Users/watson/codingProj/oneceo/apps/api/src/utils/auth-password.ts)。
4. 会话 token 由 `randomBytes(32)` 生成，服务端落库时只保存 `sha256` 哈希，不直接保存明文 token。
5. 正式用户态 cookie 当前为 `app_session_v2_id` / `app_session_v2_state`，同时兼容旧的 `app_session_id` / `app_session_state` 读取与清理。
6. cookie `Secure` 属性由浏览器可见的 `Origin/Referer` 协议决定，目标是避免 HTTP 页面被错误写成 `Secure` 而无法回传。
7. 认证接口已显式返回 `Cache-Control: private, no-store, max-age=0`、`Pragma: no-cache`、`Expires: 0`、`Vary: Origin, Cookie`。
8. CORS 当前通过 `FRONTEND_URL` 白名单控制，并开启 `credentials: true`。
9. 当前代码中未看到登录接口级别的显式 `rate limit / lockout / captcha / 风控分级 / 异常登录告警`。
10. 当前代码中未看到登录接口级别的 CSRF token 校验。
11. 当前代码中存在非生产环境用的 `X-Oneceo-Auth-Debug-*` 调试头，需要单独验证不会形成敏感信息泄露面。

## 4. 安全目标

登录接口的安全测试需要覆盖以下目标：

1. 避免未授权用户登录成他人账户。
2. 避免通过 cookie 污染、重复 cookie、旧 cookie 兼容逻辑造成会话混淆与越权。
3. 避免登录接口被撞库、爆破、枚举、重放、自动化滥用。
4. 避免跨站请求、错误 CORS 配置、缓存复用、调试头等浏览器边界问题导致认证绕过或信息泄露。
5. 避免日志、错误信息、审计字段不足，导致上线后无法追踪安全事件。

## 5. 登录接口网络安全测试 TODO

以下 TODO 按测试主题分组，后续执行时默认先做 `P0`，再做 `P1/P2`。

### 5.1 P0 越权与身份边界

- [ ] 验证不存在“只靠篡改 cookie 名称/顺序/重复值”即可登录为其他用户的路径。
- [ ] 验证同时携带 `app_session_v2_id` 与旧 `app_session_id` 时，不会解析到错误用户。
- [ ] 验证重复 session cookie 时，中间件的解析顺序不会让旧 token 抢占新 token。
- [ ] 验证无效旧 token + 有效新 token 混发时，最终身份只会落到有效 token 对应用户。
- [ ] 验证旧 `Secure app_session_id` 残留场景下，不会阻断当前正式登录态建立。
- [ ] 验证 `/api/auth/session`、`/api/auth/me` 在匿名态下不会错误回显任意用户信息。
- [ ] 验证用户状态不是 `active` 时，登录不能成功建立会话。
- [ ] 验证已注销/已吊销 session token 无法通过重放重新进入已登录态。
- [ ] 验证 `POST /api/auth/logout` 只会撤销当前 token，不会误伤其他用户会话。
- [ ] 验证 `POST /api/auth/legacy-client-id` 不能借助登录态把他人的 legacy 会话错误回绑到当前用户。

### 5.2 P0 抗滥用与暴力破解

- [ ] 验证单 IP 对 `/api/auth/login` 的高频失败请求是否会被限制、延迟或告警。
- [ ] 验证单邮箱在短时间内反复失败登录是否会触发节流、冷却或锁定策略。
- [ ] 验证密码喷洒场景：同一密码撞多个邮箱时，系统是否有速率限制与告警能力。
- [ ] 验证撞库场景：同一 IP/UA/网段批量尝试不同账户时，系统是否能识别与阻断。
- [ ] 验证缺少显式限流时的真实系统承压边界，确认登录接口是否会被低成本滥用打满。
- [ ] 验证注册验证码发送接口 `/api/auth/register/send-code` 是否也需要与登录攻击一起纳入同一风控域。
- [ ] 验证不存在通过并发请求竞争，重复建立大量有效 session 的异常路径。
- [ ] 验证异常登录失败是否具备安全日志，可支持后续封禁或审计。

### 5.3 P0 账户枚举与侧信道

- [ ] 验证“邮箱不存在”和“密码错误”在状态码、错误文案、响应体结构上完全一致。
- [ ] 验证“账号被禁用/非 active”与普通密码错误的外部响应是否仍然一致。
- [ ] 验证响应时间上不存在明显可感知的账户存在性差异。
- [ ] 验证响应头不会因为账户存在性不同而泄露额外调试线索。
- [ ] 验证非生产环境调试头不会直接暴露用户 id、session token、邮箱明文等敏感值。

### 5.4 P0 Session 与 Cookie 安全

- [ ] 验证正式登录 cookie 必须保持 `HttpOnly + SameSite + Path + Expires/Max-Age + Priority` 一致策略。
- [ ] 验证在 HTTPS 页面下，正式登录 cookie 会正确写入 `Secure`。
- [ ] 验证在 HTTP 页面下，不会因为代理头误判把 cookie 写成 `Secure`。
- [ ] 验证登出会同步清理 `app_session_v2_id` / `app_session_v2_state` 与 legacy cookie 名称。
- [ ] 验证匿名态访问 `/session`、`/me` 时，辅助状态 cookie 会被正确清除，不保留伪登录态。
- [ ] 验证 session token 不会出现在响应体、日志、调试头或可读 JS cookie 中。
- [ ] 验证服务端数据库只保存 token hash，不保存明文 token。
- [ ] 验证旧 cookie 兼容读取不会被利用成长期绕过通道，尤其是 path/domain 冲突场景。
- [ ] 验证浏览器端 `document.cookie` 只能读取辅助状态 cookie，不能读取正式鉴权 cookie。
- [ ] 验证登录前预置任意 `app_session_v2_state=authenticated` 不能伪造真实登录态。

### 5.5 P0 跨站、CORS 与浏览器边界

- [ ] 验证来自非白名单 `Origin` 的跨站 `fetch(..., credentials:true)` 登录请求不会被允许。
- [ ] 验证 `Origin: null`、伪造 `Origin`、缺失 `Origin` 的边界请求行为符合预期。
- [ ] 验证浏览器普通 `<form>` 跨站提交是否会触发不期望的登录或登出副作用。
- [ ] 验证登录、登出、会话探测接口的 `no-store`、`Vary: Cookie, Origin` 在真实浏览器与代理链路下有效。
- [ ] 验证不会因为缓存命中导致 A 用户浏览器复用到 B 用户的匿名/登录态快照。
- [ ] 验证跨站页面无法通过响应差异稳定探测当前浏览器是否已登录。
- [ ] 验证 CORS 配置不会因为 `FRONTEND_URL` 多值配置错误而意外放大可信源范围。

### 5.6 P1 输入验证与协议健壮性

- [ ] 验证邮箱字段的大小写、首尾空格、Unicode 近形字符不会导致多账户绕过或识别歧义。
- [ ] 验证 password/email 缺失、超长、空字符串、错误类型、异常 JSON body 时接口行为稳定。
- [ ] 验证超大 body、畸形 JSON、错误 content-type 不会触发异常栈泄露或进程级拒绝服务。
- [ ] 验证登录接口不会把用户输入原样写入结构化日志，避免日志污染。
- [ ] 验证 `x-forwarded-for` 等可伪造头部只用于审计字段时，不会影响鉴权结果本身。

### 5.7 P1 Session 生命周期与并发

- [ ] 验证多设备并发登录策略是否明确：允许多 session 还是新登录踢旧登录。
- [ ] 验证 session 过期后，旧 cookie 会被及时识别为失效，不会长时间保留伪活跃态。
- [ ] 验证登出后刷新页面不会因为本地辅助状态 cookie 或缓存快照误判为已登录。
- [ ] 验证 session `touch` 续期行为不会被攻击者拿来无限保活被盗 cookie。
- [ ] 验证密码修改、用户封禁、权限状态变更后，旧 session 是否需要统一失效。

### 5.8 P1 注册与相邻接口联动风险

- [ ] 验证 `/register/send-code` 的冷却逻辑不能被并发、大小写邮箱或空白字符绕过。
- [ ] 验证验证码错误、过期、已消费状态不会通过差异化错误泄露账户状态。
- [ ] 验证注册成功后自动登录不会绕过正常登录应有的安全控制。
- [ ] 验证注册、登录、legacy 绑定的组合链路不存在跨用户会话串联。

### 5.9 P1 审计、监控与告警

- [ ] 验证失败登录、异常频率、跨 IP 尝试是否有统一审计字段：`request_id / ip / user_agent / email(脱敏) / outcome`。
- [ ] 验证登录成功与失败是否可以区分记录，且不会把敏感字段写入日志。
- [ ] 验证异常登录峰值、爆破、撞库、账户枚举是否已有或需要新增告警指标。
- [ ] 验证安全事件日志在生产模式下不会被调试日志淹没。

### 5.10 P2 依赖、配置与部署安全

- [ ] 验证 `FRONTEND_URL`、cookie 策略、反向代理头、HTTPS 终止位置在各环境下配置一致。
- [ ] 验证 `NODE_ENV=production` 时调试头与调试日志行为符合安全预期。
- [ ] 验证密码哈希参数、session TTL、验证码 TTL、验证码冷却时间是否满足上线要求。
- [ ] 验证依赖包未引入已知高危认证/密码学漏洞，必要时补依赖漏洞扫描。
- [ ] 验证灰度/开发环境不会因为宽松配置被误用于真实生产流量。

## 8. 当前初步风险判断

基于现有代码静态阅读，本模块最需要优先实测的不是“密码存储是否过弱”，而是以下三类：

1. 登录接口缺少显式抗滥用控制，存在被爆破、撞库、枚举的现实风险。
2. 旧 cookie 兼容读取与新 cookie 轮换并存，必须重点验证不会引入会话混淆或越权。
3. 登录/登出尚未看到显式 CSRF 令牌校验，需要结合 `SameSite`、CORS 和真实浏览器行为确认是否存在跨站副作用面。
