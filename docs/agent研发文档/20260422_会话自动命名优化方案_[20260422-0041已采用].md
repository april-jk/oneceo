# 20260422 会话自动命名优化方案 [20260422-0041已采用]

## 1. 背景

当前任务会话标题已经具备“首次明确输入锁定”的基础能力，但用户侧识别体验仍然较差，典型现象包括：

1. 大量会话仍停留在 `新建任务会话`。
2. 一部分列表会退化成 `任务会话 2cf306` 这类 ID 型标题。
3. 一部分标题直接截取用户原始输入，包含寒暄、语气词、过程词，识别效率不高。
4. 不同读取路径（创建态、列表态、详情态、前端 fallback）对标题的兜底口径不一致。

本轮需要把“会话标题锁定”进一步收口为“可识别、稳定、统一口径的自动命名”。

## 2. 目标

1. 用户侧主标题不再出现 `任务会话 {id后缀}`。
2. 占位标题统一为状态型标题，而不是 ID 型标题。
3. 自动命名不再直接使用用户原话截断，而是生成更短、更可识别的任务标题。
4. 自动命名以后端为单一真相源，前端不再维护另一套独立命名规则。
5. 已手动重命名标题仍保持最高优先级。

## 3. 非目标

1. 不引入 LLM 生成标题。
2. 不回溯重算所有历史标题。
3. 不改动侧边栏整体布局结构。
4. 不改变用户手动重命名入口。

## 4. 现状问题归纳

### 4.1 合理之处

1. 已有 `titleLocked / titleSource / titleResolvedAt`，标题生命周期基础模型可复用。
2. 已有弱意图过滤，可避免 `你好 / 在吗 / ok` 直接锁定标题。
3. 手动重命名会锁定标题，不会再被自动逻辑覆盖。

### 4.2 不合理之处

1. 当前“自动命名”本质是“用户原话截断”，不是“任务标题提炼”。
2. `新建任务会话`、`任务会话 2cf306`、前端本地 fallback 同时存在，用户看到的是多套命名体系。
3. 前后端各维护一套相似但不完全一致的规则，易出现刷新前后标题不一致。
4. 列表页 DB hydrate 仍可能退化到 `任务会话 {id后缀}`，这对用户识别任务几乎无帮助。

## 5. 设计原则

1. **统一真相源**：标题内容由后端统一决定，前端只消费。
2. **任务可识别**：标题优先表达“对象 + 动作/问题”，而不是原话口语。
3. **稳定优先**：同一会话标题一旦进入更高质量来源，后续只允许升级，不允许被低质量来源覆盖。
4. **占位可解释**：占位标题表达当前状态，不使用随机后缀冒充名称。

## 6. 标题来源优先级

统一采用以下优先级：

1. `manual`
2. `task_description`
3. `clarification_summary`
4. `first_explicit_user_input`
5. `placeholder`

规则：

1. 高优先级来源可以覆盖低优先级来源。
2. 相同优先级来源只在当前标题为空或完全等于占位标题时覆盖。
3. `manual` 一旦写入，后续任何自动来源都不能再覆盖。

## 7. 占位标题策略

统一替换为以下状态型占位标题：

1. 默认新会话：`待识别任务`
2. 当前状态为 `waiting_user`：`待补充需求`
3. 若后续确有项目上下文，可扩展为 `{项目名} · 待识别任务`，但本轮先不引入项目名前缀拼接。

禁止：

1. 用户侧主标题显示 `任务会话 {id后缀}`
2. 用户侧主标题显示裸 `sessionId`

说明：

1. 会话 ID 仍可作为调试副信息、tooltip 或管理后台字段存在。
2. 但不能再承担“标题兜底”的职责。

## 8. 自动命名策略

### 8.1 输入来源

本轮自动命名仅依赖以下确定性输入：

1. 用户首次明确输入
2. task description title
3. 澄清态待确认问题的摘要（若后续已有稳定字段）

### 8.2 标题提炼目标

1. 长度优先控制在 10 到 24 个中文字符内，最大不超过 32 个中文字符等价长度。
2. 输出尽量保留“对象 + 动作/问题”。
3. 去掉礼貌词、寒暄词、过程词、弱语气词。

### 8.3 提炼规则

对 `first_explicit_user_input`：

1. 先做标准化：
   - 合并空白
   - 去掉首尾标点
   - 去掉前缀礼貌词：`你好`、`请`、`请帮我`、`帮我`、`麻烦你`、`我想`、`我需要`、`继续`、`再` 等
2. 删除低信息过程短语：
   - `做一次`
   - `帮我看下`
   - `帮我处理一下`
   - `看看`
   - `排查一下`
3. 若包含明确动作词，优先截取“动作词及其后面的对象短语”。
4. 若包含问题词（如 `报错`、`失败`、`为什么`、`怎么`），优先保留问题对象。
5. 若句子过长，按语义分隔符（逗号、顿号、句号、换行）只取首个高信息片段。
6. 最终结果若仍不足以形成可识别标题，则退回占位标题，不强行生成。

### 8.4 输出示例

1. `你好，做一次v7冷启动排查`
   - 输出：`v7 冷启动排查`
2. `帮我开发2048小游戏，使用html实现`
   - 输出：`HTML 2048 小游戏`
3. `请分析这个报错的根因`
   - 输出：`报错根因分析`
4. `继续刚才的 railway 发布失败排查`
   - 输出：`Railway 发布失败排查`

## 9. 数据模型调整

### 9.1 titleSource 扩展

现有：

- `placeholder`
- `first_explicit_user_input`
- `manual`

新增：

- `task_description`
- `clarification_summary`

### 9.2 titleState 新增

新增字段：

- `titleState?: 'provisional' | 'resolved' | 'manual'`

含义：

1. `provisional`：来自首次明确输入，后续允许被更高质量来源升级。
2. `resolved`：来自更稳定结构化来源，不再被同级自动来源覆盖。
3. `manual`：用户手动命名，最高优先级。

## 10. 后端行为调整

### 10.1 新建会话

新建 session 时统一写入：

1. `title = '待识别任务'`
2. `titleLocked = false`
3. `titleSource = 'placeholder'`
4. `titleState = 'provisional'`

### 10.2 标题解析入口

保留现有 `/sessions/:sessionId/title/resolve`，但其职责改为：

1. 输入用户消息。
2. 后端生成“提炼后的短标题”。
3. 写入 `titleSource = first_explicit_user_input`
4. 写入 `titleState = provisional`
5. 仅当当前标题仍处于 `placeholder / provisional` 时生效。

### 10.3 DB hydrate / 列表摘要

`buildSessionSummaryFromDbSessions`、`buildFileSessionFromDb`、`buildLightweightFileSessionFromDb` 不再使用 `任务会话 {id后缀}` 作为兜底。

统一改为：

1. 先使用 session 上已存标题。
2. 若标题为空，再看 `taskDescription.title`。
3. 若仍为空，则使用 `待识别任务` 或 `待补充需求`。

### 10.4 标题升级

当 task description 中出现更稳定 title 时：

1. 若当前 `titleSource` 为 `placeholder` 或 `first_explicit_user_input`
2. 且当前不是 `manual`
3. 则允许升级为 `task_description`
4. 同时写入 `titleState = resolved`

## 11. 前端行为调整

1. 前端继续在发送消息后触发 `resolveTaskCreationSessionTitle`，但不再自行维护另一套“是否需要命名”的判定规则，只负责把非空用户输入交给后端解析。
2. Sidebar fallback 从 `任务会话 {{suffix}}` 改为 `待识别任务`。
3. 前端收到服务端返回标题后直接展示，不再拼接 ID 型主标题。
4. 当会话状态为 `waiting_user` 且标题仍是 placeholder 时，前端可显示 `待补充需求`，但优先以后端返回标题为准。

## 13. 验收标准

1. 用户侧不再出现 `任务会话 {id后缀}` 作为主标题。
2. 新会话默认显示 `待识别任务`。
3. 澄清态未命名会话显示 `待补充需求`。
4. 首次明确任务输入能被提炼为更短、更可识别的标题，而不是原话硬截断。
5. task description 可覆盖 provisional 标题，形成更稳定标题。
6. 手动标题仍保持最高优先级。
