# 2026-04-15 用户管理工作台方案 [20260415-0943已采用]

## 1. 背景

当前管理后台已经有 `Sandbox 管理`、`对话管理`、`审计日志` 等运行治理入口，但对普通用户 `app_users` 的治理能力仍然缺失：

1. 管理员只能在 `对话管理` 中被动看到用户归属，无法主动按用户维度定位问题。
2. 用户是否活跃、最近从哪里登录、是否仍有活跃会话、最近是否创建过对话或 Sandbox，当前没有统一视图。
3. 当用户归属异常、legacy id 映射残留或需要临时禁用账号时，缺少管理态入口。

本方案只针对 `app_users` 与其关联运行数据建设 `用户管理` 功能，不纳入 `admin_users`，保持“用户态与管理态身份源分离”的既有原则。

## 2. 已确认范围

### 2.1 本次明确包含

1. `app_users`
2. `app_user_sessions`
3. `task_creation_sessions`
4. `sandbox_execution_environments`
5. `app_user_legacy_id_mappings`

### 2.2 本次明确不包含

1. `admin_users` / `admin_user_sessions`
2. 管理员代用户修改密码
3. 后台创建普通用户
4. 用户权限体系、套餐、组织、多租户
5. 连接器、技能、工件等用户配置的直接编辑

## 3. 现有事实

### 3.1 数据与鉴权

1. `app_users` 已包含：
   - `email`
   - `display_name`
   - `status`
   - `created_at`
   - `updated_at`
   - `last_login_at`
2. `app_user_sessions` 已包含：
   - `user_id`
   - `ip_address`
   - `user_agent`
   - `last_seen_at`
   - `expires_at`
   - `revoked_at`
3. 用户态登录链路已经依赖 `app_users.status === 'active'`：
   - 登录时非 `active` 用户不可登录；
   - 请求解析 session 时若用户非 `active`，当前 session 也会被视为无效。

这意味着：

1. 第一阶段无需重做用户态鉴权模型。
2. `禁用用户` 可以直接复用现有 `status` 语义。
3. 为了治理清晰，禁用用户时仍建议同步撤销该用户所有未撤销 session 记录。

### 3.2 管理后台结构

1. 管理后台侧边导航由 `apps/admin_management/web/src/App.tsx` 中的 `NAV_ITEMS` 驱动。
2. 管理后台服务侧采用 BFF 结构：
   - `apps/admin_management/server/routes/*`
   - `apps/admin_management/server/services/*`
   - `apps/admin_management/server/connectors/oneceo-api-connector.ts`
3. 重量级平台页已逐步拆成独立组件，例如：
   - `SkillManagementSection`
   - `ConnectorGuideManagementSection`
   - `OsacReleaseManagementSection`

因此用户管理也应走同样路径，而不是继续膨胀 `App.tsx`。

## 4. 目标与非目标

### 4.1 目标

1. 在管理后台新增与 `Sandbox 管理`、`对话管理` 同级的 `用户管理` 一级入口。
2. 让管理员能按用户维度查看：
   - 基础身份
   - 最近登录与活跃
   - 活跃 session
   - 最近对话
   - 最近 Sandbox
3. 提供最小但有效的治理动作：
   - 启用用户
   - 禁用用户
4. 不再把旧账号迁移痕迹作为单独功能入口暴露给管理员。
5. 保持移动端与中窄屏可用，不新增杂乱层级。

### 4.2 非目标

1. 不把用户管理做成 CRM。
2. 不在第一阶段做用户资料任意编辑。
3. 不把 `admin_users` 混入同一页。
4. 不绕开现有用户态认证链路。
5. 不新增 Redis 依赖。

## 5. 信息架构建议

### 5.1 导航层级

建议在侧边栏 `运行管理` 分组下新增：

- `用户管理`
  - tag：`USR`
  - subtitle：`用户身份与会话`
  - signal：`用户治理`

放在 `Sandbox 管理` 与 `对话管理` 同级，但仍归属 `运行管理`，原因是该页面的主要价值是服务会话归属、运行排障与风险治理，而不是平台配置。

### 5.2 页面结构

用户管理页建议采用：

`全宽索引面板 + 居中详情窗 + 关联对象就地叠层查看`

原因：

1. 管理员会先扫列表，再点开单个用户处理问题。
2. 用户索引作为主工作区保持不动，详情窗关闭后可以立即回到原筛选与原选中项。
3. 在用户详情里查看“相关对话 / Sandbox”时，优先继续在当前页面之上叠层打开详情，而不是直接切走主栏目。
4. 即使管理员临时切到 `对话管理` 或 `Sandbox 管理`，再次回到 `用户管理` 时，也要恢复之前的筛选、排序、选中用户和已打开详情。
5. 若管理员是从用户详情的 `对话` 或 `Sandbox` 分页跳到对应一级模块，页头仅保留来源路径提示；返回原用户详情统一通过关闭当前弹窗完成，不额外叠加单独“返回用户详情”按钮。

页面分为四层：

1. 顶部摘要
2. 筛选工具栏
3. 用户索引表
4. 详情窗口

补充交互约束：

1. `对话` 与 `Sandbox` 列表都以标题作为默认入口，点击标题后在当前页上的二级浮窗打开详情，不再额外堆叠“查看对话 / 查看 Sandbox”按钮。
2. 二级浮窗里的“在对话管理中查看”与“在 Sandbox 管理中查看”进入对应一级模块后，用户管理的筛选、排序、选中用户和当前详情分页必须继续保留。
3. 返回动作统一通过关闭当前层完成，不在顶栏或详情页里重复叠加“返回用户详情”一类按钮。

## 6. 页面方案

### 6.1 顶部摘要

首屏只保留四项：

1. `全部用户`
2. `7 天活跃`
3. `已禁用`

说明：

1. `7 天活跃` 以 `app_user_sessions.last_seen_at` 或会话最新活跃时间聚合。

### 6.2 筛选栏

建议第一版只做以下筛选，保持短路径：

1. 关键词：
   - 邮箱
   - 显示名
   - 用户 ID
2. 状态：
   - 全部
   - 启用
   - 禁用
3. 活跃度：
   - 全部
   - 7 天活跃
   - 30 天活跃
   - 长期未活跃
4. 登录状态：
   - 全部
   - 已登录
   - 未登录
5. 对话：
   - 有对话
   - 无对话

筛选栏不再单独保留 `Sandbox` 下拉项，原因是：

1. 用户列表卡片本身已经直接显示 Sandbox 数与最近 Sandbox 时间；
2. `Sandbox` 作为筛选项与 `对话 / 登录状态` 并列时，优先级偏低，容易拉长第一行；
3. 更符合后台操作习惯的做法，是把 `Sandbox` 维度放到“排序”里，而不是继续占一个独立筛选位。

### 6.2.1 排序

用户列表增加与 `Sandbox 管理` 一致的排序交互，采用“点击字段切换升降序”的方式，默认按 `上次登录` 降序。

第一版提供以下排序字段：

1. 用户
2. 状态
3. 上次登录
4. 登录状态
5. 对话
6. Sandbox

### 6.3 列表列设计

用户索引区采用 AWS 控制台常见的 `顶部筛选 + 紧凑表格索引 + 行点击看详情` 结构，而不是卡片式列表。

第一版不建议做过多窄列，建议收成以下表格列：

1. `用户`
   - 显示名
   - 邮箱
   - 用户 ID（短展示 + 复制）
2. `状态`
   - 启用 / 禁用
   - 最近登录
3. `上次登录`
   - 上次登录时间
   - 最近 IP
4. `登录状态`
   - 当前已登录 / 当前未登录
   - 辅助说明补充“当前没有在线登录 / 从未登录过”
   - 判定口径以“最近仍有访问心跳的未撤销会话”为准，不再把 30 天内未过期但长期无访问的 cookie 直接算成已登录
5. `对话`
   - 对话数
   - 最近对话时间
6. `Sandbox`
   - Sandbox 数
   - 最近 Sandbox 时间
7. `操作`
   - 查看详情

这样更符合后台扫描式操作习惯：先横向扫表，再点行打开详情。

排序按钮直接放入表头，文案、方向指示和使用方式与 `Sandbox 管理` 保持一致。

用户索引表进一步约束为高密度行式布局：

1. 第一列只保留用户名、邮箱与截断后的用户 ID，不再重复堆叠状态标签。
2. `状态`、`登录状态`、`对话`、`Sandbox` 统一采用“主值 + 轻量说明”的双层排布。
3. `操作` 列收敛为单个图标入口，列表行本身仍然可以直接点击打开详情。

首屏摘要与筛选区继续压缩：

1. 摘要卡改为更扁的统计条，提示信息收进卡片头部，不再占用额外高度。
2. 页面内局部刷新按钮移除，统一使用顶栏刷新，避免重复操作入口。
3. 筛选区采用更紧凑的单行工具栏，尽量让索引表在首屏更早出现。

用户管理页面的文案统一采用更贴近管理员日常理解的说法：

1. `最近活跃` 统一改为 `上次登录`
2. `登录会话` 在详情列表中统一改为 `登录记录`
3. 不再把旧账号迁移信息作为用户管理工作台的一部分展示
4. 列表与筛选中不再单独展示笼统的“关联情况”字段

### 6.4 详情窗口

详情采用居中浮动的二级详情窗。窗口内部继续使用二级 tab：

1. 保持 AWS 控制台常见的“索引表上打开独立详情窗”的阅读路径；
2. 避免详情层继续挤压用户列表的横向表格结构；
3. 更适合承载 `概览 / 对话 / Sandbox` 这类跨分组信息。
4. 当管理员从用户详情继续查看“相关对话 / 相关 Sandbox”时，默认在当前详情之上叠层打开对应详情窗，关闭后返回原用户详情，而不是重新进入列表检索。

详情窗口建议采用二级 tab：

1. `概览`
2. `对话`
3. `Sandbox`

不再保留“旧账号关联”页签或迁移信息入口。

各 Tab 建议内容如下。

#### 6.4.1 概览

概览页采用 `左侧账号摘要 + 右侧登录记录` 的双栏结构，避免把账号信息和登录历史继续纵向堆叠。

1. 左侧账号摘要：
   - 显示名
   - 邮箱
   - 状态
   - 当前登录状态
   - 上次登录时间
   - 最近访问时间
   - 顶部统计条展示 `当前登录 / 上次登录 / 最近访问`
   - 下方关键信息卡只保留 `用户 ID / 最近来源 IP / 账号状态 / 登录状态`
2. 右侧登录记录：
   - 最近会话列表
   - IP
   - 访问设备标识（User-Agent）
   - 创建时间
   - 最近访问
   - 是否已撤销 / 是否已过期
   - 表头补充最近记录数量，方便管理员判断当前看到的是最新几条

#### 6.4.2 对话

展示最近对话简表：

1. 标题即入口
2. 状态 / 阶段
3. 最近更新
4. 处理方式
5. 点击标题默认打开 `对话详情`
6. 如需完整工作台，再显式进入 `对话管理`

#### 6.4.3 Sandbox

展示最近 Sandbox 简表：

1. 标题即入口
2. 状态
3. 处理方式
4. 最近更新
5. 点击标题默认打开 `Sandbox 详情`
6. 如需完整工作台，再显式进入 `Sandbox 管理`

## 7. 治理动作建议

第一阶段只提供两类动作：

1. `启用用户`
2. `禁用用户`

### 7.1 状态语义

第一阶段只使用两种状态：

1. `active`
2. `disabled`

不建议同时引入 `suspended / banned / archived / deleted` 等多个状态，避免扩散用户态语义和后端判断分支。

### 7.2 动作约束

1. `禁用用户`：
   - 更新 `app_users.status = 'disabled'`
   - 同步撤销该用户所有未撤销 session
2. `启用用户`：
   - 更新 `app_users.status = 'active'`
   - 不自动恢复旧 session

## 8. 数据与接口设计

### 8.1 API 侧新增管理态内部接口

建议在 `apps/api/src/routes/` 新增用户治理内部路由，仍使用内部 token 鉴权，不复用用户态接口。

#### 列表接口

`GET /api/internal/admin/app-users`

查询参数建议：

1. `cursor`
2. `limit`
3. `query`
4. `status`
5. `activity`
6. `hasSession`
7. `hasConversation`
8. `hasSandbox`

返回：

1. `summary`
2. `items`
3. `nextCursor`

其中单行 `item` 建议包含：

1. 用户基础信息
2. `activeSessionCount`
3. `conversationCount`
4. `sandboxCount`
5. `lastSeenAt`
6. `lastSeenIp`

#### 详情接口

`GET /api/internal/admin/app-users/:userId`

返回聚合：

1. `user`
2. `stats`
3. `recentSessions`
4. `recentConversations`
5. `recentSandboxes`
6. `legacyMappings`

#### 动作接口

1. `POST /api/internal/admin/app-users/:userId/status`

### 8.2 管理后台 BFF

建议新增：

1. `apps/admin_management/server/services/user-management-service.ts`
2. `apps/admin_management/server/routes/user-management-routes.ts`

并在 `apps/admin_management/server/connectors/oneceo-api-connector.ts` 中补齐：

1. `listAppUsers()`
2. `getAppUserDetail()`
3. `updateAppUserStatus()`

管理后台前端仅调用自身 BFF：

1. `GET /api/user-management`
2. `GET /api/user-management/:userId`
3. `POST /api/user-management/:userId/status`

## 9. 前端实施建议

### 9.1 组件边界

建议新增独立组件：

`apps/admin_management/web/src/components/UserManagementSection.tsx`

而不是继续把页面逻辑塞回 `App.tsx`。

`App.tsx` 只负责：

1. 新增 `SectionKey = 'user'`
2. 新增 `NAV_ITEMS` 项
3. 在 `renderContent()` 中挂载 `UserManagementSection`

### 9.2 视觉方向

遵循当前后台已形成的收敛风格：

1. 首屏不要大段说明文案。
2. 用紧凑摘要 + 稳定筛选栏 + 清晰索引表。
3. 详情窗内部重点突出状态、风险、最近活动和跨模块入口。
4. 不新增花哨插画、Hero 或冗余卡片堆叠。
5. 跨模块入口要给出清楚来源提示，例如“来自 用户管理 / 某个用户”；回到上一层统一使用关闭当前弹窗，不重复堆叠单独返回按钮。

### 9.3 响应式

1. 桌面端：
   - 列表全宽
   - 抽屉从右侧滑入
2. 中屏：
   - 筛选栏允许折行
   - 表格保留横向滚动
3. 小屏：
   - 抽屉退化为全屏 modal
   - 列表保留最重要的三组信息：用户、状态、上次登录

## 10. 实施顺序建议

### 第一阶段：只读治理视图

1. 导航入口
2. 列表查询
3. 详情窗口
4. 关联对象就地叠层查看
5. 来源路径提示与关闭返回

### 第二阶段：最小治理动作

1. 启用 / 禁用
2. 审计日志记录

不建议跳过第一阶段直接做动作按钮，否则管理员在缺少上下文的情况下容易误操作。

## 11. 验证建议

1. `npm --prefix apps/api run type-check`
2. `npm --prefix apps/admin_management run type-check`
3. `npm --prefix apps/admin_management run build`
4. 用户状态切换后验证：
   - 已登录用户请求是否立即失效
   - 被禁用用户是否无法再次登录
5. Playwright 验证：
   - 列表筛选
   - 详情窗口展开
   - 状态切换确认流
   - 从用户详情打开对话详情并关闭返回
   - 从用户详情打开 Sandbox 详情并关闭返回

## 12. 风险与约束

1. 用户管理只能治理 `app_users`，不能误触管理态账户。
2. 禁用用户要沿用既有 `active` 语义，不引入多套状态判断。
3. 不复用用户态 owner 接口，避免管理端误走用户态鉴权链路。
4. 不直接改动 Sandbox 生命周期，只提供可见性与跳转。
5. 不新增 Redis 依赖或缓存旁路。
