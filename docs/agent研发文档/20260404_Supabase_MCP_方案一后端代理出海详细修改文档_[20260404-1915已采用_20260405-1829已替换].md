## 1. 问题定义与现状证据

现象：

1. Supabase 连接器 attach 阶段反复失败
2. 运行时回复 `status: failed_to_attach`
3. 错误信息为 `context deadline exceeded`
4. API 最终对外常表现为“运行时未保留已挂载的 MCP provider”

证据（日志）：

1. `apps/api/data/connector-debug.log` 中多次出现 Supabase attach 返回 `failed_to_attach`
2. 同一批日志中 attach 阶段持续约 20s 后失败，失败模式稳定

关键链路代码：

1. `apps/api/src/services/session-connector-service.ts`
2. `apps/api/src/services/session-mcp-recovery-service.ts`
3. `apps/api/src/services/osac-agent-service.ts`
4. `apps/api/src/connectors/definitions/supabase.ts`

## 2. 根因分析（方案一视角）

根因链路：

1. Supabase provider 历史使用 `remote_sse` 传输，已根据真实测试切换为 `streamable_http`
2. attach 时由 runtime 侧发起到 `https://mcp.supabase.com/mcp` 的远端建链
3. 网络链路不可达、延迟过高或代理策略不稳定时，runtime 返回 `failed_to_attach + context deadline exceeded`

当前二次放大问题：

1. `session-connector-service` 对 `failed_to_attach` 没有专门状态映射
2. attach 回复后仍进入 “等待 provider 出现在 live 列表” 逻辑
3. 最终被“运行时未保留已挂载的 MCP provider”覆盖掉原始错误语义

结论：

1. 第一故障点是网络建链（非 UI 问题）
2. 第二故障点是错误语义丢失（可通过 API 代码修复）

## 3. 目标与验收标准

目标：

1. 让 Supabase streamable_http attach 能通过代理稳定建立连接
2. 让失败信息可观测且可定位，不再被泛化错误掩盖
3. 保持现有 OSAC / 恢复链路不被绕过

验收标准：

1. Supabase attach 成功时，日志中出现 `status: connected`
2. Supabase attach 失败时，`lastError` 保留 runtime 原始 `errorMessage`
3. 接口返回不再优先落到泛化错误“运行时未保留已挂载 provider”
4. `session-mcp-recovery` 在失败后可继续按现有机制重试

## 4. 修改方案（文件级别）

## 4.1 代理配置生效与边界确认

修改文件：

1. `apps/api/.env`（部署环境）
2. `env.windows`（本地模板）

修改内容：

1. 明确设置 `ONECEO_PROXY_ENABLED=true`
2. 设置 `HTTP_PROXY`、`HTTPS_PROXY`
3. 设置 `NO_PROXY`，确保内网与平台链路不误走代理
4. 若使用小写环境变量，也需与大写保持一致

建议 `NO_PROXY` 至少包含：

1. `127.0.0.1`
2. `localhost`
3. `.e2b.app`
4. 业务内网域名与数据库/redis 内网域

注意：

1. 该步骤是方案一的前提，不做则后续代码优化无法根治网络建链失败

## 4.2 Supabase attach 错误语义保真

修改文件：

1. `apps/api/src/services/session-connector-service.ts`

修改点 A：补充状态映射

1. 在 `mapRuntimeStatus` 中增加 `failed_to_attach -> failed`
2. 对 `attach_failed` 等同义状态做统一映射（如 runtime 存在该值）

修改点 B：attach 回复后立即判失败

1. 在处理 `ATTACH_MCP_PROVIDER_TO_SESSION` 回包时读取 `status`
2. 若 `status` 非 `connected`，直接按失败分支处理
3. 优先使用 payload 的 `errorMessage` 作为 `lastError`
4. 失败时写入 runtime 事件 `provider_attach_failed`

修改点 C：避免泛化错误覆盖

1. 仅在 attach 回包为 `connected` 且后续 live probe 确实丢失时，才保留“运行时未保留 provider”错误
2. attach 回包已经明确失败时，不再进入该泛化分支

预期收益：

1. 用户与排障日志能看到真实根因（网络 deadline）
2. 失败语义与恢复任务状态一致

## 4.3 Supabase 代理环境注入增强

修改文件：

1. `apps/api/src/services/session-connector-service.ts`

说明：

## 4.4 attach 超时重试参数固化

说明：

## 9. 真实测试结果记录（2026-04-04）

测试环境与脚本：

1. 测试脚本：`test/supabase_proxy_demo/mcp_real_probe.py`
2. 目标端点：`https://mcp.supabase.com/mcp`
3. 认证方式：Supabase token（文档内仅保留脱敏信息）

### 9.1 传输协议验证

测试 1：`transport=sse`

1. 结果：失败
2. 现象：HTTP 405 Method Not Allowed
3. 结论：该端点不接受 sse 方式

测试 2：`transport=streamable_http`

1. 结果：成功
2. 现象：`initialize` 成功、`list_tools` 成功
3. 服务端信息：`name=supabase`、`version=0.7.0`
4. 工具数量：`tools_count=29`

结论：Supabase MCP 在当前链路下应使用 `streamable_http`，不是 `sse`。

### 9.2 具体命令透传验证

测试命令：`call_tool(list_projects, {})`

1. 结果：成功
2. 现象：`isError=false`
3. 返回：包含项目列表数据（id/ref/region/status/database/created_at 等字段）

结论：命令可从客户端真实传达至 Supabase MCP 并返回有效业务数据。

### 9.3 代理链路验证

测试配置：

1. `ONECEO_PROXY_ENABLED=true`
2. `HTTP_PROXY/HTTPS_PROXY` 已配置
3. `NO_PROXY=localhost,127.0.0.1,.e2b.app`

测试命令：同 9.2（`list_projects`）

1. 结果：成功
2. 现象：`initialize/list_tools/call_tool` 全部成功
3. 返回：与直连场景一致，命令结果正常

结论：通过代理也可以稳定传达具体 MCP 命令。

## 10. 方案可行性评价

综合评价：方案一可行，且可作为短路径落地方案。

### 10.1 可行性结论

1. 技术可行：已通过真实链路验证“可连接、可列工具、可发命令、可拿到业务结果”。
2. 代理可行：已验证在代理环境下命令仍可达并成功返回。
3. 改造可控：主要改动集中在状态映射、错误语义保真和环境配置，不需要重构主架构。

### 10.2 收益评估

1. 能直接缓解 `failed_to_attach/context deadline exceeded` 在受限网络下的高频失败问题。
2. 能把“泛化错误”改为“真实错误”，显著降低排障成本。
3. 与现有 OSAC 恢复链路兼容，风险较低。

### 10.3 风险与边界

1. 若代理本身不支持长连接，仍可能出现 attach 不稳定。
2. 若 NO_PROXY 配置不当，可能误伤平台内部链路。
3. 方案一本质是网络与可观测性修复，不解决 remote 模式的全部架构性不确定性。

### 10.4 建议

1. 先按方案一上线（最短路径、见效快）。
2. 线上继续观察 attach 成功率、失败类型分布和恢复耗时。
3. 若仍有长期稳定性问题，再进入方案二（下沉为沙箱本地 provider）评审。
