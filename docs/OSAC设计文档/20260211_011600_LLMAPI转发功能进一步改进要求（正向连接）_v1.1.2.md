# OSAC LLM API 转发功能进一步改进要求（正向连接）v1.1.2

> 目标：修正当前“反向上游”方案导致的 sandbox 无法访问内网问题。采用 **编排服务正向连接 OSAC** 的方式建立 LLM 代理通道，所有 LLM 请求由 OSAC 通过已建立的 WebSocket 通道转发到编排服务，再由编排服务转发到真实上游模型服务。

## 1. 背景与问题（结论）
1) sandbox 内禁止访问内网服务（192.168.x.x），因此 OSAC 内部代理 **不能直接访问** 编排服务的 `/api/llm-proxy`。
2) 当前方案采用 OSAC 从 sandbox 直接访问编排服务，导致上游不可达。
3) 需要改为：**编排服务主动连接 OSAC**，并在该连接上建立 LLM 代理通道。

## 2. 新方案核心设计
### 2.1 通路方向
1) 编排服务主动连接 OSAC 的 WebSocket（已有控制通道）。
2) 在该连接上新增 **LLM 代理通道**（JSON 消息流）。
3) OSAC 本地代理接收 `127.0.0.1:18111` 的 OpenAI 请求后，通过 WS 转发给编排服务。
4) 编排服务调用 `/api/llm-proxy`（本地服务）访问真实上游模型，得到响应后通过 WS 逐块回传给 OSAC。
5) OSAC 将响应按原样返回给 opencode。

### 2.2 责任边界
- OSAC：负责本地代理监听 + 将请求转换为 WS 消息 + 透传响应。
- 编排服务：负责 WS LLM 通道的收发 + 对接 `/api/llm-proxy`。
- 上游模型：仍由编排服务统一对接，OSAC 不直接访问内网模型。

## 3. OSAC 需要新增/调整的功能
### 3.1 LLM 代理通道协议（WS 消息）
OSAC 与编排服务之间新增消息类型（JSON）：

**请求消息：**
```json
{
  "type": "LLM_PROXY_REQUEST",
  "payload": {
    "requestId": "uuid",
    "method": "GET|POST",
    "path": "/v1/models|/v1/chat/completions|/v1/completions|/v1/embeddings",
    "headers": { "Content-Type": "...", "Authorization": "...", "Accept": "..." },
    "body": "<string or base64>",
    "isStream": true
  }
}
```

**响应消息（非流式）：**
```json
{
  "type": "LLM_PROXY_RESPONSE",
  "payload": {
    "requestId": "uuid",
    "status": 200,
    "headers": { "Content-Type": "application/json" },
    "body": "<string or base64>"
  }
}
```

**流式分片：**
```json
{
  "type": "LLM_PROXY_CHUNK",
  "payload": {
    "requestId": "uuid",
    "chunk": "<raw bytes or base64>",
    "isFinal": false
  }
}
```

**流式结束：**
```json
{
  "type": "LLM_PROXY_END",
  "payload": {
    "requestId": "uuid",
    "status": 200,
    "headers": { "Content-Type": "text/event-stream" }
  }
}
```

**错误：**
```json
{
  "type": "LLM_PROXY_ERROR",
  "payload": {
    "requestId": "uuid",
    "status": 503,
    "error": {
      "message": "Upstream unavailable",
      "type": "upstream_unavailable",
      "code": "upstream_unavailable"
    }
  }
}
```

> 编排服务与 OSAC 需对 `requestId` 做路由与匹配。

### 3.2 OSAC 本地代理
- 监听地址：`127.0.0.1:<OSAC_LLM_PROXY_PORT>`（默认 18111）
- 接收 OpenAI 兼容请求后，将请求组装为 `LLM_PROXY_REQUEST` 并通过 WS 发送。
- 对于 `stream=true`：持续转发 `LLM_PROXY_CHUNK`，最后 `LLM_PROXY_END`。
- 不允许 OSAC 直接访问内网目标。

### 3.3 OSAC 环境变量
```bash
OSAC_LLM_PROXY_PORT=18111
OSAC_LLM_PROXY_ENABLE=true
# 不再依赖 OSAC_LLM_UPSTREAM_BASE_URL 访问内网
```

## 4. 编排服务侧改动要求
### 4.1 新增“LLM 代理桥接模块”
要求：独立模块，最小耦合，不影响现有 OSAC 控制与业务服务。

**职责：**
1) 监听 OSAC WS 消息流中的 `LLM_PROXY_*` 事件。
2) 将 `LLM_PROXY_REQUEST` 转发到 `POST/GET /api/llm-proxy`（已有模块）。
3) 将响应按 `LLM_PROXY_RESPONSE/CHUNK/END` 回传。

### 4.2 SSE 透传
对于 `stream=true`：
- 编排服务必须按 SSE 原样分片回传（不缓冲到结束）。

### 4.3 错误映射
编排服务转发失败时，返回 OpenAI 风格错误：
```json
{
  "error": {
    "message": "Upstream timeout",
    "type": "upstream_timeout",
    "code": "upstream_timeout"
  }
}
```

## 5. 验收标准
1) OSAC 内 `curl http://127.0.0.1:18111/v1/models` 返回模型列表。
2) OSAC 内 `opencode run "Hello"` 正常返回。
3) SSE `stream=true` 能逐条透传。
4) sandbox 内不需要访问任何内网 IP。

## 6. 兼容与扩展
- 新增接口（如 `/v1/images/generations`）可通过 WS 协议扩展 `path` 实现，无需改动核心逻辑。
- OSAC 与编排服务解耦，保持 `client -> connector -> service -> route` 分层。
