# 07 前端对话页与交互状态

## 1. 当前问题

当前 managed 前端逻辑集中在：

- `useTaskCreationAgent.ts`

并同时承担：

- session 创建
- runtime 预热
- WebSocket 消息发送
- SSE 事件合并
- direct mode / managed mode 双模式分支
- interrupt / replay / restore

这导致 managed 前端状态过重，且与 direct mode 强耦合。

## 2. 目标前端结构

建议把前端拆成两套 hook：

### 2.1 managed

- `useAltusManagedConversation`
- `useAltusManagedRunStream`

### 2.2 direct

- 保持现有 `useTaskCreationAgent` 的 direct 分支

## 3. managed 前端最小流程

1. 发送输入
2. 确保 session 存在
3. 调用 `start run`
4. 保存 `activeRunId`
5. 订阅 `run stream`
6. 将 stream 事件转换为 UI 状态

## 4. 前端状态模型

managed mode 仅保留以下 UI 状态：

- `session`
- `messages`
- `activeRun`
- `runStatus`
- `isStreaming`
- `needsUserInput`

不再保留 direct 风格状态：

- `opencodeSessionId`
- `executorSessionId`
- `runtimeReady`
- `sseCursor`

这些状态不属于 managed 模式。

设置层也要遵守这个边界：

1. 当用户选择 `Altus 接管模式（managed mode）` 时，不显示执行器选择。
2. `OpenCode / ClaudeCode / Codex` 执行器选择只属于 `直通模式（sandbox mode）`。
3. 切到 managed mode 时可以保留上一次 direct mode 的 executor 记忆，但不得在 UI 上继续要求用户选择 executor。
4. managed mode 的流式消息与工具事件必须显式标记为 `Altus`，不得沿用 `Codex` 的事件文案或执行器标签。
5. managed mode 的 assistant 消息不得暴露底层模型提供商身份；前端展示名称统一为 `Altus`。

## 5. 中断与继续

managed 前端中断逻辑应改成：

1. 用户点击停止
2. 调用 `POST /runs/:runId/stop`
3. UI 标记当前 run 为 stopped
4. 下一次发送消息时创建新 run

不再使用当前围绕 `activeManagedRuns` 和 replay input 的进程内修补逻辑。

## 6. Clarification 交互

当 run 进入 `waiting_user`：

1. 对话页显示 clarification message
2. 输入框继续可用
3. 用户回复后启动新 run
4. 新 run 自动从 session 历史中读取未完成问题

## 6.1 原子消息规范

managed mode 的流式事件不能继续粗暴复用 direct mode 的 `status_update / executor_event` 展示语义，前端需要把以下事件收敛成稳定的原子消息单元：

- `run_ack`
  - 展示为一次 run 启动胶囊，不重复堆叠。
- `run_status`
  - 作为当前 run 的状态胶囊更新，不生成多条噪音消息。
- `tool_call_started -> tool_call_completed / tool_call_failed`
  - 必须以 `toolCallId` 作为同一原子卡片的稳定 key。
  - UI 上表现为一个紧凑工具卡片的状态更迭，而不是两条分离文本。
- `clarification_requested`
  - 展示为独立澄清消息，不与普通 assistant 文本混排。
- `artifact_updated`
  - 以轻量 review 胶囊展示，不能伪装成执行器输出文本。

样式要求：

- managed 原子消息默认比 direct mode 更紧凑
- 工具卡片只保留：工具名、状态、摘要
- 详情内容折叠到点击后的 detail dialog，不在主消息流里铺开

## 7. 历史恢复

页面刷新后：

1. 拉取 session messages
2. 拉取 latest run
3. 若 latest run 仍 active，则重连 run stream

这一恢复模型必须独立于 direct mode。

## 8. 设计结论

前端层面的本质变化是：

> managed mode 从“一个超大 hook 同时处理 managed/direct/runtime/SSE”重构为“基于 session 与 run 的标准对话页状态机”。

## 9. Suna 代码参照

本篇前端设计需要对照的 `suna` 源码如下：

- `referance/suna/apps/frontend/src/lib/api/agents.ts` -> `unifiedAgentStart(...)`
  - 对应 oneceo 前端的 `start run` API 调用。
- `referance/suna/apps/frontend/src/lib/streaming/use-agent-stream.ts` -> `startStreaming(...)`
  - 对应 oneceo 的 `useAltusManagedRunStream`。
- `referance/suna/apps/frontend/src/hooks/messages/useAgentStream.ts`
  - 对应 run 事件到 UI 消息状态的转换层。
- `referance/suna/apps/frontend/src/hooks/threads/use-optimistic-agent-start.ts`
  - 对应前端在启动 run 时的 optimistic state 处理。
- `referance/suna/apps/frontend/src/components/thread/chat-input/chat-input.tsx`
  - 对应输入框如何触发 run，而不是直接操作 executor session。
- `referance/suna/apps/frontend/src/stores/suna-modes-store.ts`
  - 说明前端 `mode` 是产品输入与 prompt shaping 信号，不是后端执行分支。

oneceo 重构 managed 前端时，应以这些入口为参照拆出 `session UI`、`run stream UI`、`mode UI` 三层，而不是继续在 `useTaskCreationAgent.ts` 内堆叠状态。
