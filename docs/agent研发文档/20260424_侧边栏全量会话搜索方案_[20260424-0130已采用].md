# 20260424_侧边栏全量会话搜索方案_[20260424-0130已采用]

## 1. 背景

当前侧边栏只有“最近会话列表”，没有真正的全量搜索能力：

- 前端 [Sidebar.tsx](/Users/watson/codingProj/oneceo/apps/web/client/src/components/Sidebar.tsx) 里只有一个 `/search` 导航占位
- 后端 [task-creation-routes.ts](/Users/watson/codingProj/oneceo/apps/api/src/routes/task-creation-routes.ts:4148) 只提供最近会话列表 `GET /api/task-creation/sessions`
- 会话正文实际存储在 [conversation_messages](/Users/watson/codingProj/oneceo/apps/api/src/db/schema.ts:180) 表，但没有用户可用的检索接口

因此“侧边栏搜索”不能只对当前已加载的侧边栏列表做前端过滤，必须对该用户的全部会话和全部对话内容做真实搜索。

## 2. 目标

实现搜索页功能，支持对当前用户全部会话进行检索，覆盖：

1. 会话标题
2. 会话内全部消息正文
3. 搜索结果点击后直接进入对应会话

要求：

- 搜索范围是“当前用户的全部会话”，不是最近列表子集
- 搜索结果支持命中消息片段摘要
- 搜索动作和结果展示在独立 `/search` 页面完成
- 搜索结果按标题命中优先和最近活跃时间排序
- 不影响现有侧边栏最近会话列表、项目树、收藏、右键菜单逻辑

## 3. 非目标

- 本轮不做向量检索
- 本轮不做跨用户搜索
- 本轮不做附件内容检索
- 本轮不做 workspace 文件内容检索
- 本轮不做高亮富文本渲染，只返回纯文本摘要
- 本轮不实现全文搜索基础设施重构（如 PostgreSQL `tsvector` 长期索引体系）

## 4. 用户体验

## 4.1 入口

侧边栏继续保留“搜索”导航入口，但点击后进入独立 `/search` 页面。

交互：

- 进入页面后自动聚焦搜索框
- 默认页只保留一个上下左右居中的搜索框，不展示介绍文案、统计卡片、结果概览
- 输入关键词后进行防抖搜索
- 当进入有效搜索态并出现结果区时，搜索框通过轻量 transform 位移动画上移，为结果列表腾出空间，避免整页重排导致的卡顿
- 清空输入后恢复搜索页默认空态
- `Esc` 清空当前输入
- 支持通过 URL query `?q=` 保留当前搜索词

## 4.2 搜索结果结构

每条结果展示：

- 会话标题
- 命中来源：
  - `标题命中`
  - `消息命中`
- 一段命中的消息摘要
- 最近更新时间
- 按项目分组聚合，但分组样式保持极简列表化，不使用厚卡片和统计模块

点击结果后跳到 `/session/:id?view=history`

## 4.3 空态

分三种：

1. 未输入关键词：
   - 显示搜索提示空态
2. 输入中但还没发起请求：
   - 显示轻量 loading
3. 已搜索但无结果：
   - 显示“未找到相关对话”

## 5. 搜索语义

## 5.1 查询输入

输入参数：

- `q`: 用户输入关键词，前后 trim

规则：

- 长度 `< 2` 不发请求
- 长度上限 `100`
- 连续空白折叠成单空格

## 5.2 命中范围

一期命中范围：

1. file memory 中的手动会话标题
2. `task_descriptions.title`
3. `conversation_messages.content`

只搜索当前用户拥有的 session。

补充说明：

- `task_creation_sessions` 表本身没有独立 title 字段，不能按不存在的列设计标题搜索
- 当前用户可见标题来源实际包括：
  - file memory 里的手动重命名标题
  - 最新任务描述标题
  - 首条用户输入自动派生标题
- 其中“首条用户输入自动派生标题”天然会被消息正文搜索覆盖
- 因此一期标题搜索实现收敛为：
  - 手动标题搜索
  - task description 标题搜索
  - message 正文搜索

这里需要额外约束：

- 不直接搜索所有内部过程消息
- 默认只搜索用户可感知的消息内容：
  - `role in ('user', 'agent')`
  - 排除纯过程态、纯结构化中间结果、空内容消息

原因：

- 当前 `conversation_messages` 同时承载用户消息、智能体回复、以及 layer 过程结果
- 如果把内部过程消息一起搜进去，会把搜索结果污染成大量不可读的系统文本或 JSON 摘要
- 用户要的是“全部对话可搜”，不是“所有内部事件可搜”

## 5.3 排序规则

排序优先级：

1. 标题命中优先于消息命中
2. 同类型命中下，最近有命中的会话优先
3. `task_creation_sessions.updated_at` 更新更近者优先

这里取消“命中次数更多者优先”。

原因：

- 对 `ILIKE` 结果再做命中次数统计不是最短路径
- 在长消息和多消息聚合场景下，计数规则不稳定，也会增加 SQL 复杂度
- 一期保持“标题优先 + 最近命中优先”更简单且可解释

## 6. 后端方案

## 6.1 新增接口

新增：

- `GET /api/task-creation/sessions/search?q=...&limit=...`

响应结构：

```json
{
  "success": true,
  "data": [
    {
      "sessionId": "uuid",
      "title": "Railway 部署修复",
      "updatedAt": "2026-04-24T01:23:45.000Z",
      "matchType": "title" | "message",
      "snippet": "…数据库使用 railway 的 postgres，配置了自动部署…",
      "projectId": "uuid|null",
      "projectName": "项目名称|null",
      "isFavorite": false,
      "status": "in_progress"
    }
  ]
}
```

限制：

- 默认 `limit = 20`
- 最大 `limit = 50`

## 6.2 查询实现

在 DAO 新增用户维度搜索方法，基于：

- `task_creation_sessions`
- `conversation_messages`

实现方式：

1. 先过滤 `task_creation_sessions.user_id = currentUser.userId`
2. 复用现有 user 归属收口逻辑，保证 legacy user id / 未回填归属 session 不会在搜索里漏掉
3. 标题命中走 `ILIKE`
4. 消息命中走 `conversation_messages.content ILIKE`
5. 以 `session_id` 聚合，取每个 session 的一条最佳可展示命中

摘要生成：

- 从最佳命中消息里截取关键词前后各约 30~50 个字符
- 无法定位时截取前 80 个字符

这里需要避免直接复用现有 `buildSessionSummaryFromDbSessions(...)`。

原因：

- 现有列表构建逻辑会对每个 session 再拉一次全量消息和任务描述，属于 N+1
- 搜索接口如果沿用这条链路，会在 20 条结果时就引入大量额外查询
- 搜索 route 应该返回专门的轻量结果结构，不走最近列表 summary 组装链路

## 6.3 最短路径实现约束

一期不引入新表，不做搜索索引迁移。

原因：

- 当前会话搜索先验证产品价值
- 用户量和会话量在当前阶段可接受 `ILIKE + limit` 的短路径实现
- 避免在未验证交互前就引入 `tsvector`、GIN、复杂 ranking

补充约束：

- 一期必须对消息侧搜索加硬性 `limit`
- route 层默认只返回前 20 条，不支持 `all`
- DAO 内部先缩小到用户拥有的 session，再做标题/消息检索，避免全表扫描放大

但需要明确约束：

- DAO 和 route 要单独封装，后续可无缝替换成全文索引实现

## 10. 风险与取舍

## 10.1 性能风险

`ILIKE` 搜索在数据量大时会变慢。

当前取舍：

- 一期接受
- DAO 单独封装，后续可升级成全文索引

## 10.2 结果准确性

只搜标题和消息正文，不搜附件和结构化元数据。

当前取舍：

- 先满足“全部对话可搜”
- 后续若需要再扩展附件与交付物内容搜索

## 10.3 归属一致性风险

当前最近会话列表接口在 route 层包含 legacy user id 回填、无归属修补、memory 合并等收口逻辑。

如果搜索接口只写一个“按 `user_id` 直接查 DB”的简版实现，会出现：

- 列表里能看到的会话，搜索不到
- 搜索结果和最近列表不一致

因此一期要求：

- 搜索接口与最近列表保持同样的用户归属语义
- 至少复用同一套 owner 归属收口前置逻辑

## 11. 实施顺序

1. 后端 DAO 增加标题/正文搜索原语
2. route 增加 `/sessions/search` 并复用现有 owner 收口逻辑
3. client 增加搜索 API
4. Sidebar 增加搜索输入、折叠态展开聚焦、搜索结果面板
5. 补测试与文案

## 12. 结论

本方案采用最短路径实现搜索页全量对话搜索：

- 不做前端假搜索
- 继续使用独立 `/search` 页面
- 不做过度设计
- 直接打通“搜索页输入 -> 后端检索全部会话 -> 页面聚合展示 -> 点击结果进入会话”

如果这版方案确认采用，再进入代码实现。
