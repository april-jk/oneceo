# Altus 中止完成语义与立即续发修复方案 [20260607-1436已采用]

## 1. 背景

用户发送跟进消息后，如果 Altus managed run 还处于 `queued`、`starting` 或准备 Sandbox 的阶段，用户可能因为输入错误立即点击中止并重新发送。

当前界面在中止请求返回后立即恢复输入，但后端旧 run 仍可能保留活动状态。用户紧接着发送的新消息会被活动 run 检查拒绝，并显示：

> 当前会话已有运行中的 Altus managed run

本方案只修复中止完成语义与立即续发竞态，不扩展为消息排队、自动重试或多 run 并发方案。

## 2. 当前链路与根因

### 2.1 当前停止链路

1. 前端 `interruptCurrentRun()` 调用 `POST /api/altus-managed/runs/:runId/stop`。
2. 后端 `stopRun()` 写入 Redis stop request。
3. 后端调用当前进程内 `AbortController.abort()`。
4. `stopRun()` 未等待 coordinator 完成终止，直接返回当前数据库 run。
5. 前端收到成功响应后，直接把本地状态改为 `stopped`，关闭事件流并恢复输入。
6. coordinator 在后续异步流程中捕获 abort，刷新 Sandbox memory，然后调用 `markStopped()`。
7. `markStopped()` 最终才把数据库 run 状态更新为 `stopped`。

因此 stop API 返回成功与数据库活动 run 消失之间存在时间窗口。

### 2.2 新消息被拒绝的位置

正常前端发送使用 `/api/altus-managed/inputs`，首先进入 `AltusManagedInputService.submit()`。

该服务在调用 `AltusManagedRunEntryService.startRun()` 前，会独立调用 `taskSessionRunDAO.findActiveRun()`。旧 run 尚未写入终态时，请求会在这里直接失败。

因此，仅修改 `startRun()` 内部的活动 run 检查无法覆盖真实发送链路。

### 2.3 当前未提交修改的问题

当前工作区修改通过 Redis stop request 判断旧 run 是否正在终止，并在 `startRun()` 中最多轮询两秒。

该方案不采用，原因如下：

1. 正常 `/inputs` 链路会在外层活动 run 检查处提前失败。
2. Redis 未显式启用时，stop request 不会保存，修复完全失效。
3. 固定轮询把旧 run 的终止延迟转移给下一次发送，仍可能超时失败。
4. 同一活动 run 约束分散在 input service 和 run entry service，竞态判断重复。
5. 新增测试复制了简化算法，没有调用真实服务，无法验证生产链路。

## 3. 修复目标

1. stop API 返回成功时，目标 run 必须已经写入数据库终态。
2. 前端恢复输入时，后端必须已经允许同会话创建下一条 run。
3. Redis 开启或关闭时行为一致。
4. 活动 run 检查只在 run 创建边界执行一次。
5. 中止前置准备阶段、模型运行阶段和工具执行阶段均遵循同一完成语义。
6. 不允许同时存在两个活动 managed run。

## 4. 设计原则

### 4.1 stop 成功代表终止完成

`POST /runs/:runId/stop` 不再表示“已发出 abort 信号”，而表示：

1. 已接受中止请求；
2. run 已持久化为 `stopped`；
3. 活动 run 查询不再返回该 run；
4. `run_stopped` 事件和时间线状态已写入；
5. 前端可以安全发送下一条消息。

### 4.2 数据库是活动 run 的事实来源

中止正确性不能依赖 Redis。Redis stop request 仍可作为跨实例中止信号，但不能承担“是否允许创建新 run”的唯一判断依据。

### 4.3 不在新消息入口等待旧 run

新消息入口不增加固定延时、轮询、自动重试或排队逻辑。中止请求本身负责完成终态收口。

## 5. 后端修改

### 5.1 为进程内 run 保存执行 Promise

`AltusManagedRunEntryService` 在启动 coordinator 时，除保存 `AbortController` 外，同时保存该 run 的执行 Promise。

执行 Promise 的 `finally` 继续负责删除 controller、停止 heartbeat，并删除 Promise 引用。

### 5.2 stopRun 等待终止执行完成

当目标 run 存在进程内 controller 时：

1. 写入 stop request；
2. 调用 `controller.abort()`；
3. 等待对应 coordinator Promise 完成；
4. 重新读取数据库 run；
5. 仅当状态为 `stopped` 或其他终态时返回。

如果 coordinator Promise 结束后状态仍非终态，stop API 明确失败，不能返回伪成功。

当目标 run 不在当前进程内时，沿用现有 lifecycle 终止路径直接调用 `markStopped()`，完成终态写入后返回。

### 5.3 提前写入数据库终态

coordinator 捕获 abort 后，应先执行 `lifecycleService.markStopped()`，再执行非关键的 Sandbox skill memory 与 Altus memory 刷新。

中止的用户可见完成不应被 Sandbox memory 刷新耗时阻塞。memory 刷新失败只记录警告，不允许把已经中止的 run 改成失败或继续保持活动状态。

### 5.4 收口活动 run 检查

删除 `AltusManagedInputService.submit()` 中提前执行的 `findActiveRun()`。

活动 run 检查保留在 `AltusManagedRunEntryService.startRun()` 的 run 创建边界，并保持“存在真实活动 run 就拒绝”的现有业务规则。

删除当前候选修改中的 Redis stop request 读取与固定两秒轮询。

## 6. 前端修改

`interruptCurrentRun()` 必须读取 stop API 返回的 run：

1. 只有返回状态为 `stopped`、`completed` 或 `failed` 时，才结束 processing、关闭 stream 并恢复输入。
2. 如果响应仍是活动状态，视为中止失败，不得在本地伪造 `stopped`。
3. 中止成功后使用服务端返回的终态更新 `managedRunStatus`。
4. 清理当前 run 的 recovery state，避免刷新页面后重新恢复已经停止的 run。

前端不等待 `run_stopped` SSE 才开放输入，因为 stop API 本身已经承担终态完成承诺；SSE 继续用于时间线同步。

## 7. 并发与边界条件

### 7.1 run 尚未开始实际执行

controller 已注册、coordinator 正在余额检查或准备 Sandbox 时，中止信号必须最终进入统一 abort 分支并写入 `stopped`。

### 7.2 run 正在模型或工具执行

底层可取消操作收到 abort 后进入统一终止分支。stop API 等待该分支完成后返回。

### 7.3 run 已自然完成

stop 请求读取到终态时直接返回现有终态，不重复写入停止事件。

### 7.4 重复点击中止

多个 stop 请求应得到同一个终态结果，不重复写入 `run_stopped` 时间线消息。

### 7.5 Redis 未启用

完整链路依赖进程内 controller、执行 Promise 与数据库终态，必须正常通过。

### 7.6 Redis 已启用

stop request 继续用于运行时协作，但不能改变 stop API 的终态返回契约。

## 8. 测试方案

### 8.1 API 服务测试

在真实服务实例上覆盖：

1. `startRun()` 创建 queued run。
2. `stopRun()` 触发 abort，并等待 `markStopped()` 完成。
3. stop 返回时数据库状态已经是 `stopped`。
4. stop 返回后立即调用下一次 `submit()`，新 run 创建成功。
5. 未中止的真实活动 run 仍会拒绝第二次 submit。
6. Redis 未启用时上述行为保持一致。
7. coordinator memory 刷新延迟或失败不阻塞数据库终态。

删除只复制算法、不调用生产服务的 `altus-managed-stop-start-race.test.ts`，将回归场景放入现有 managed input/run service 测试体系。

### 8.2 Web 测试

覆盖：

1. stop API 返回活动状态时，前端不解锁输入。
2. stop API 返回 `stopped` 时，前端结束 processing 并允许立即发送。
3. stop API 失败时保留当前运行态并显示错误。

### 8.3 静态验证

- `pnpm --filter api type-check`
- `pnpm --filter web check`
- 相关 API `node:test`
- 相关 Web `vitest`

## 9. 不采用的方案

1. 不在 start/submit 中增加固定时长轮询。
2. 不让新消息自动等待、排队或重试。
3. 不依赖 Redis stop key 决定是否允许新 run。
4. 不允许前端仅凭 stop HTTP 200 本地伪造终态。
5. 不通过放宽活动 run 检查来允许两个 run 并发。

## 10. 验收标准

1. 用户在 Altus 尚未开始实际执行时点击中止，中止完成后可立即发送修改后的消息。
2. 新消息不再出现“当前会话已有运行中的 Altus managed run”。
3. stop API 响应中的 run 已是数据库终态。
4. 同一会话始终最多只有一个活动 managed run。
5. Redis 开启和关闭两种配置均通过回归测试。
6. 页面刷新后不会恢复已停止的旧 run。
