## 三、技术要点说明

### 1. 千分比整数存库

缓存比例在数据库中以整数（千分比）存储，避免浮点精度问题：
- `cache_hit_multiplier`：缓存命中时按原价的多少千分比计费。例如 OpenAI 默认 500 表示 50%。
- `cache_creation_multiplier`：缓存创建时按原价的多少千分比计费。例如 Anthropic 默认 1250 表示 125%。

业务代码中统一通过 `multiplier / 1000` 转换为实际比例参与计算。

### 2. 向后兼容

- 数据库迁移时自动为 openai / anthropic 插入默认行，数值与原硬编码逻辑完全一致（OpenAI hit 500、Anthropic hit 100 / creation 1250）。
- 若数据库中无对应 provider 的配置，`getCacheMultipliers()` 会回退到上述默认值，确保旧数据或异常场景下计费不中断。

### 3. 实时生效

- 配置修改通过 `POST /api/internal/billing/cache-config` 写入数据库。
- PricingService 每次计算积分时实时查询最新配置，无需重启 API 服务。
- 管理后台修改后，下一次 LLM 调用立即按新比例计费。

### 4. 异步化改造

- `calculateCredits()` 和 `getModelPricingWithCache()` 等核心方法由同步改为异步，以支持数据库读取。
- 用户端 `/api/billing/pricing` 等路由同步适配 async/await。

## 五、待后续完善的事项

1. **管理后台 UI 体验优化**
   - 当前缓存比例修改直接生效，建议增加「当前值 vs 修改值」对比预览和确认二次弹窗，避免误操作。

2. **配置变更审计**
   - 当前仅更新数据库行，未记录「谁在什么时间把哪个 provider 的比例改成了多少」。
   - 后续建议增加操作日志表或接入现有 admin audit 机制。

3. **未知 provider 兜底策略**
   - 若未来新增第三方模型提供商且 `cache_pricing_config` 中无对应配置，当前回退到 openai 默认值。
   - 建议后续在管理后台提供「新增 provider 缓存配置」入口，或 fallback 行为可配置。

4. **缓存比例对统计看板的影响**
   - 当前 `BillingStatsDashboard.tsx` 中的缓存效果概览仍使用前端简化估算。
   - 若管理员修改了缓存比例，统计看板的「缓存节省积分」展示可能与实际计费不一致，需后续精确化。

5. **并发修改竞态**
   - 管理后台同时修改同一 provider 的配置时，后提交者覆盖前者，无版本控制或乐观锁。
   - 后续建议增加 `updated_at` 校验或数据库行级锁。
