# MCP 高风险工具调用统一确认标准 [20260504-1256已采用]

## 1. 标准目标

所有 MCP provider 只要暴露可改变外部系统状态、用户数据、权限、资源生命周期或发送对外消息的工具调用，都必须进入统一高风险确认流程。该标准不只适用于 Google Super，也适用于后续 GitHub、Slack、Notion、Vercel、自定义 MCP、自定义 API 生成 MCP tools 等所有 MCP 调用入口。

确认流程的目标：

1. 用户在真正执行前能看到可复核的操作对象、动作类型、关键参数与影响。
2. 确认只覆盖本次明确 tool call，不成为后续同类操作的默认授权。
3. sandbox、模型、OSAC 不持有长期确认权限，也不能绕过 API broker 直接执行高风险操作。
4. 审计记录能追溯 user、session、run、connector/provider、tool、目标对象、参数 hash、确认状态与执行结果。
5. 只要任一层运行结果表达的是 `confirmation_required`，当前 run 都必须立即切换为 `waiting_user`，不能继续产出成功总结。
6. approve 后的恢复执行必须是“恢复原始待确认动作”，而不是“允许模型重新规划一个看起来类似的新动作”。

## 2. 高风险定义

满足任一条件的 MCP tool call 必须判定为高风险：

1. 对外发送消息：send、reply、forward、publish、post、notify、invite。
2. 修改数据：create、update、write、append、insert、batch update、clear、label、complete。
3. 删除或归档：delete、remove、archive、cancel。
4. 资源移动或复制：move、copy、upload、import、export 到外部位置。
5. 权限变更：share、permission、grant、revoke、add member、remove member、role mutation。
6. 部署或生产资源变更：deploy、redeploy、rollback、promote、scale、restart、stop。
7. 支付、账单、密钥、凭证、webhook、环境变量等安全敏感变更。
8. 任何 connector guide、tool schema、tool name、arguments 中出现明确写入或权限语义，且无法证明是只读操作。

低风险示例：

1. list/search/get/read/describe 类只读操作。
2. schema 查询、tool 搜索、连接状态读取。
3. 只读取当前用户已授权可见数据且不改变任何外部状态的操作。

## 3. 统一确认 UI 要求

高风险 MCP 调用第一次触发时，后端不得直接转发给真实 MCP provider。API broker 必须返回 `confirmation_required` 结果，由前端在会话运行区显示统一确认 UI。

确认 UI 必须包含：

1. 标题：明确显示为某类高风险 MCP 操作确认，例如“确认 Google Workspace 操作”或“确认 MCP 高风险操作”。
2. 工具来源：connector/provider key、tool name。
3. 动作类型：例如 `send_email`、`share_drive_item`、`update_sheet_values`、`delete_issue`。
4. 目标对象：必须尽量是真实可复核对象，例如 email recipient、file id、event id、repo、issue number、deployment id、channel id、project id。
5. 关键参数摘要：展示必要参数，正文、token、secret、authorization、html/content 大字段必须脱敏。
6. 影响说明：说明执行后会改变什么外部状态。
7. 操作按钮：`确认执行` 与 `拒绝`。

禁止行为：

1. 禁止用普通聊天文本“我确认了”“可以执行”替代确认按钮。
2. 禁止只显示“将执行某 MCP 操作”这类不可复核文案。
3. 禁止在目标对象缺失时生成可确认 UI。
4. 禁止把确认 token 暴露为长期凭证或保存到 sandbox。

## 4. 后端确认协议

### 4.1 逻辑等价形态

`confirmation_required` 的标准语义只有一种，但传输层允许存在多种等价包装形式。平台实现必须统一识别至少以下几类：

1. 顶层对象：

```json
{
  "type": "confirmation_required",
  "connectorKey": "connector_key",
  "toolName": "provider__TOOL_NAME",
  "confirmationId": "confirmation-id",
  "summary": {}
}
```

2. provider envelope + `structuredContent`：

```json
{
  "providerId": "provider_id",
  "toolName": "provider__TOOL_NAME",
  "result": {
    "structuredContent": {
      "type": "confirmation_required",
      "connectorKey": "connector_key",
      "toolName": "provider__TOOL_NAME",
      "confirmationId": "confirmation-id",
      "summary": {}
    }
  }
}
```

3. provider envelope + `content[].text` 承载结构化 JSON：

```json
{
  "providerId": "provider_id",
  "toolName": "provider__TOOL_NAME",
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"type\":\"confirmation_required\",\"connectorKey\":\"connector_key\",\"toolName\":\"provider__TOOL_NAME\",\"confirmationId\":\"confirmation-id\",\"summary\":{}}"
      }
    ]
  }
}
```

4. 其他仅改变包装层、但语义上等价于 `confirmation_required` 的 managed runtime / MCP 返回体

只要识别到上述任一形态：

1. 当前 run 必须立即停止同轮剩余工具规划
2. 当前 run 必须转入 `waiting_user`
3. 不得继续生成“已成功发送”“已写入外部系统”等最终成功文本

高风险 tool call 的未确认返回格式统一为：

```json
{
  "type": "confirmation_required",
  "connectorKey": "connector_key",
  "toolName": "provider__TOOL_NAME",
  "confirmationId": "confirmation-id",
  "summary": {
    "connectorKey": "connector_key",
    "toolName": "provider__TOOL_NAME",
    "action": "write_action",
    "target": "target-object",
    "impact": "human readable impact",
    "parameterSummary": {
      "key": "value"
    }
  }
}
```

确认记录必须至少绑定：

1. `appUserId`
2. `taskSessionId`
3. `agentRunId`
4. `connectorKey` 或 `providerId`
5. `toolName`
6. `argumentsHash`
7. `confirmationTokenHash`
8. `summaryJson`
9. `status`
10. `expiresAt`
11. `approvedAt`
12. `consumedAt`

其中 `agentRunId` 要求进一步收紧为：

1. 必须绑定 originating run
2. 不允许长期落成 `null`
3. 如果运行态上下文不足以绑定 originating run，必须显式报错并终止创建 pending confirmation

确认 token 规则：

1. 只能由后端 approve 接口生成。
2. 默认有效期不超过 10 分钟；具体连接器可更短。
3. 只匹配同一 user、session、run、connector/provider、tool、arguments hash。
4. 成功执行一次后必须立即消费并失效。
5. 参数变化、run 变化、session 变化、用户变化、过期、已消费都必须拒绝执行。

## 5. 目标对象提取标准

每个高风险 MCP 调用必须提取可复核目标对象。目标对象可以来自 tool name、arguments、嵌套 `arguments` / `parameters` / `input`、schema 语义字段或 connector adapter 的结构化摘要。

通用目标字段包括但不限于：

1. 消息与邮件：`to`、`recipient`、`recipient_email`、`email_address`、`channel_id`、`thread_id`、`message_id`。
2. 文件与文档：`file_id`、`fileId`、`folder_id`、`document_id`、`doc_id`、`url`、`name`、`title`。
3. 表格：`spreadsheet_id`、`spreadsheetId`、`sheet_id`、`range`、`cell_range`。
4. 日历：`calendar_id`、`event_id`、`attendee_email`、`summary`。
5. 权限：`permission_id`、`user_email`、`group_email`、`role`、`domain`。
6. 项目与部署：`project_id`、`deployment_id`、`environment_id`、`service_id`。
7. 代码与协作：`repo`、`owner`、`issue_number`、`pull_number`、`branch`。

如果目标对象缺失：

1. 后端必须拒绝真实执行。
2. 返回或抛出可诊断错误，要求 agent 补齐目标。
3. 不允许生成确认按钮让用户确认不可复核操作。

## 6. MCP Broker 执行顺序

API broker 对 MCP `tools/call` 的统一顺序：

1. 校验 session ownership 与 connector/profile 归属。
2. 根据 connector/provider/tool/arguments 分类风险。
3. 低风险：直接进入现有 broker 执行链路。
4. 高风险且无 confirmation token：构建 summary，创建 pending confirmation，返回 `confirmation_required`。
5. 高风险且带 confirmation token：校验 token 绑定、有效期、参数 hash。
6. 校验通过：转发真实 MCP provider。
7. 执行完成或失败：写审计事件，消费 token。
8. 校验失败：拒绝执行，不得降级直连。

补充约束：

1. 高风险确认的“待确认返回”必须在真实 provider 写操作之前发生
2. 识别到 `confirmation_required` 后，managed run 不得继续同轮 search/get schema/重构参数
3. approve 后首轮 replay 失败时，run 必须显式结束为恢复失败，不得退回普通模型规划
4. 首轮 replay 失败后，不得再出现同轮 `SEARCH_TOOLS -> GET_TOOL_SCHEMAS -> MULTI_EXECUTE_TOOL` 作为兜底

## 7. 前端标准

前端必须把 `confirmation_required` 识别为一等运行态 UI，而不是普通 tool 输出文本。

前端确认按钮行为：

1. `确认执行` 调用后端 approve 接口。
2. approve 返回一次性 confirmation token。
3. 前端通过当前会话运行链路把 token 交回 agent/runtime，要求重试同一个 tool call。
4. managed 模式下，前端应优先提交结构化 confirmation metadata；后端必须基于 metadata 恢复原始待确认 tool call。
5. 对于 approve，优先采用后端隐式恢复重放：后端在下一次 managed run 首轮前隐藏执行原始 tool call，并仅把工具结果续接给模型；不得向用户时间线额外插入“恢复提示”痕迹。
6. `拒绝` 调用后端 reject 接口，并告知 agent 不得重试该 tool call。
7. 一旦某次 tool call 返回 `confirmation_required`，managed run 必须立即停止后续同轮工具尝试并切换到 `waiting_user`，不得在未确认状态下继续搜索、改参或重复触发同一写操作确认。
8. 用户点击 `确认执行` 后，前端必须立即给出“已确认，正在继续执行”的运行反馈，并继续展示后续工具执行与结果回流，交互体验应与 Codex 类似。
9. 前端必须按 `confirmationId` 对确认卡片做历史去重与已处理隐藏；刷新页面或回放历史时，不得再次暴露已批准/已拒绝的旧确认按钮。
10. 后端对“已批准但尚未消费”的同一 `confirmationId` 应允许安全重发一次性 token，用于前端刷新、重复渲染或确认后续提交失败时的恢复；`consumed` 状态仍不得再次批准。
11. 前端显示“已成功发送邮件”“已成功创建文档”等写操作成功状态时，必须以后端真实 provider 成功结果为依据，不能把模型的自述文本当作执行成功证据。

前端不能：

1. 让用户通过聊天文本绕过按钮。
2. 在没有 `confirmationId` 时显示确认按钮。
3. 在没有明确目标对象时显示确认按钮。
4. 在确认后把 token 缓存在 localStorage、sessionStorage 或可被 sandbox 读取的位置。
5. 不能把“确认后继续执行”完全依赖为一段普通提示词；必须有结构化 confirmation metadata 驱动的后端恢复协议，优先采用隐式重放原始 tool call。
6. 不能把 provider envelope 中未被识别的 `confirmation_required` 当成普通工具输出文本继续展示。

## 8. 测试要求

每个新增 MCP connector 或新增高风险工具族时，必须补充：

1. 低风险 read/search/get/list 不触发确认。
2. 高风险 create/update/delete/share/send 等触发 `confirmation_required`。
3. 嵌套参数能提取目标对象。
4. 目标对象缺失时拒绝执行。
5. approve 后同一参数 hash 可执行一次。
6. token 复用、过期、参数变化、user/session/run 不匹配均拒绝。
7. 前端展示目标、影响、确认/拒绝按钮。
8. `confirmation_required` 位于顶层对象、provider envelope、`structuredContent` 与 `content[].text` 时都能被统一识别。
9. 原始 run 在未批准前不会继续写出高风险成功总结。
10. approve 后首轮 replay 失败时，run 会显式失败，而不是继续普通规划。
11. confirmation 记录会绑定 originating `agentRunId`，审计链能追溯到创建 run 与消费 run。
