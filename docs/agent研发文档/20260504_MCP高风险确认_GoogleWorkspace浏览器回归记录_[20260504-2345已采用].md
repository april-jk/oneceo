## 2. 回归目标

本次浏览器回归重点验证以下三段链路：

1. `google_super` 连接器在真实会话中的恢复与可用性状态
2. 高风险写操作是否稳定出现统一确认卡片
3. 用户点击 `确认执行` 后，后端是否直恢复原始待确认 tool call，而不是重新让模型规划一次

## 4. 测试过程

### 4.1 首轮 Google Docs 创建

测试请求：

1. 请使用 Google Workspace 创建一个 Google Docs 文档
2. 标题为 `oneceo browser confirmation smoke test`

观察结果：

1. 首轮没有进入高风险确认卡片

3. 后续复测时确认该会话的 `Google Workspace` 连接器已 attach，但工具运行态并不稳定

结论：

1. 首轮失败不能直接归因为确认链路
2. 更早的前置问题是连接器运行态尚未完全恢复

### 4.2 `pending_recover` 前置阻塞

继续在真实会话中发起 Google Workspace 相关请求后，页面出现以下语义：

1. `Google Workspace MCP 工具当前不可用，连接状态为 pending_recover`
2. `Google Workspace MCP 当前处于恢复等待状态，无法执行测试`

同时，会话内可看到：

1. `google_super__COMPOSIO_SEARCH_TOOLS`
2. `load_connector_guide`

但没有进入稳定的确认卡片链路。

结论：

1. `google_super` 在部分新会话或首轮真实调用时，确实存在 `pending_recover` 窗口
2. 在该窗口内，系统先暴露的是“连接器恢复等待中”，而不是“高风险待确认”
3. 因此，`pending_recover` 是确认闭环之前的前置阻塞条件

### 4.3 连接恢复后的只读能力验证

4. 因此，这条新建任务样本只能用于证明“连接器挂载前置失败”，不能直接用于证明“确认后恢复逻辑失败”

4. 当前问题不是单点异常，而是“连接器附着、运行态恢复、确认闭环”三段同时存在缺口

### 4.8 同一高风险确认重复显示两个 UI

后续人工测试中，又观察到一条更细的前端表现问题：

1. 在邮件发送的高风险写操作里，页面先出现一张“确认高风险 MCP 操作”卡片
2. 用户点击 `确认执行` 后，页面出现“正在发送邮件，请稍候...”
3. 但随后同一个发送邮件流程中，又再次出现一张内容几乎相同的确认卡片
4. 最终邮件仍显示发送成功

从现象上看，这更像是“同一个确认对象被重复渲染成两个 UI”，而不是“后端未拦截导致又生成了一次新的真实审批”。判断依据如下：

1. 最终链路是单次确认后直接成功，而不是再次停在第二次审批上
2. 如果后端真的再次创建了新的待确认记录，主链通常会再次停在 `waiting_user`，而不是已经成功发送邮件
3. 当前前端代码中，`GoogleWorkspaceConfirmationPanel` 至少会在多个分支里按 `confirmationId` 渲染：
   - 消息渲染分支
   - managed tool item 渲染分支
   - 另一处工具事件渲染分支
4. 这些分支共享同一套 `hiddenGoogleConfirmationIds` 过滤，但在“点击确认前”无法阻止同一个 `confirmationId` 同时落入多个渲染入口

因此，这条问题当前更应归类为：

1. 前端确认卡片重复渲染
2. 不宜直接归因为“后端没有成功拦截”
3. 但它会严重影响用户对“是否真的又拦截了一次”的判断，属于高优先级体验问题

补充代码核对结论：

1. 在 `apps/api/src/services/composio-connector-service.ts` 中，`google_super` 的高风险识别发生在真正 `callComposioMcp(..., 'tools/call', ...)` 之前
2. 若 `verifyAndConsumeConfirmation(...)` 未通过，后端会直接返回 `confirmation_required`
3. 只有确认已消费通过后，代码才会继续执行真实的 `tools/call`

因此，按当前代码主路径判断：

1. 正常情况下不存在“先把邮件发出去，再补一个确认卡片”的顺序
2. 若页面表现为“确认卡片还在，但同时已经出现成功发送”，更应优先怀疑：
   - 同一确认的前端重复渲染
   - 历史消息与当前恢复消息的时序展示混乱
   - 旧确认卡片未及时隐藏
3. 这并不能完全排除边界 bug，但至少不能直接下结论为“后端主链没有拦截”

### 4.9 `/approve` 与成功发送的时间序核对

针对“是否在点击确认前就已经成功发送邮件”的怀疑，本次又做了日志与网络层核对，得到以下证据：

1. 浏览器网络日志中，当前会话 `67f737a1-cc16-496d-addb-edc06e18337d` 出现真实请求：
   - `POST /api/task-creation/sessions/67f737a1-cc16-496d-addb-edc06e18337d/mcp-confirmations/9267ad7c-9d05-4857-81be-7641bbee9fc4/approve`
2. 后端日志中，上述 `/approve` 的时间是：
   - `2026-05-05T03:30:30.562Z`
3. 同一会话在 `/approve` 之后，后端才继续出现后一波 Google 工具调用：
   - `03:30:45.310Z` `google_super__COMPOSIO_SEARCH_TOOLS`
   - `03:30:57.152Z` `google_super__COMPOSIO_GET_TOOL_SCHEMAS`
   - `03:31:06.704Z` `google_super__COMPOSIO_MULTI_EXECUTE_TOOL`
   - `03:31:17.750Z` `google_super__COMPOSIO_SEARCH_TOOLS`
   - `03:31:24.115Z` `google_super__COMPOSIO_GET_TOOL_SCHEMAS`
   - `03:31:31.300Z` `google_super__COMPOSIO_MULTI_EXECUTE_TOOL`
4. 页面里“已成功发送邮件”出现在这波 `/approve` 之后的恢复轨迹中，而不是出现在 `/approve` 之前的独立发送结果中

基于这组时间序证据，本次核对结论应更新为：

1. 浏览器网络层与后端运行日志显示：当前这次 `/approve` 之后，确实发生了一轮新的恢复执行
2. 但会话持久化记录同时暴露出一条更严重的反证：
   - 在 `/approve` 之前，已经存在一条 `runId = 62678c3c-6df4-44f2-b455-af855908c549` 的 agent 最终消息
   - 内容为“已使用 Google Workspace 成功发送邮件”
   - 时间为 `2026-05-05T03:30:10.172Z`
3. 与之对应的 `mcp_tool_confirmation_approved` 记录时间是：
   - `2026-05-05T03:30:30.808Z`
4. 这说明至少在持久化消息层面，**确实存在“成功发送结论早于批准记录”的异常时序**
5. 因而本轮核对后的更准确结论不应再写成“当前证据不支持确认前成功发送”，而应改为：
   - 网络与后端工具调用日志支持“批准后有一轮恢复执行”
   - 但消息时间线又显示“批准前已经出现成功发送结论”
   - 当前系统存在严重的时序不一致，不能再简单归因为纯前端重复渲染

换句话说，当前问题至少包含两层：

1. 前端存在确认 UI 重复展示
2. 更关键的是，会话消息层已经出现“成功发送文本早于批准记录”的异常，这会让用户合理怀疑拦截并未真正生效

### 4.10 同一 tool call id 的重复确认展示

继续核对页面侧栏 `Actions` 后，又拿到一条更强的 UI 级证据：

1. 页面中出现两条“等待确认 Google Workspace 高风险操作”
2. 这两条记录对应的 tool call 名称完全一致：
   - `mcp__google_super_composio_multi_execute_tool__f196890a737c`
3. 同一会话的网络层只抓到一条真实 `approve`：
   - `confirmationId = 9267ad7c-9d05-4857-81be-7641bbee9fc4`

这意味着：

1. 当前至少可以确认“两个确认 UI”并不是源自两个不同的 tool call id
2. 它们更像是同一条 `multi_execute_tool` 调用在不同视图入口被重复展示
3. 但结合上一节新增发现，不能再仅凭“单次 `/approve` + 后续成功发送”就断定问题只有前端重复渲染
4. 当前更稳妥的判断应是：
   - 同一确认对象重复渲染大概率存在
   - 同时消息时间线也存在“批准前先写出成功发送结论”的异常
   - 两类问题可能同时成立

说明：

1. 由于页面未直接暴露两张卡片的 `confirmationId` 文本，本轮还不能用 UI 文本直接证明“两张卡的 confirmationId 完全相同”
2. 但“同一 tool call id + 单次 approve + 消息层提前出现成功发送”三项合并后，也已经足以说明当前链路不能简单视为“只有展示问题”

### 4.11 数据库级回放核对：原始 run 在未批准前继续走到成功总结

继续直接核对本地数据库中的 `conversation_messages`、`task_session_run_events` 与 `task_session_mcp_tool_confirmations` 后，本次又得到一组比浏览器层更强的证据。

会话：

1. `67f737a1-cc16-496d-addb-edc06e18337d`

关键 run：

1. 原始待确认 run：`62678c3c-6df4-44f2-b455-af855908c549`
2. `/approve` 后恢复 run：`e0e65b79-0d3a-4597-b0e7-53bd992fbefd`
3. 待确认记录：`9267ad7c-9d05-4857-81be-7641bbee9fc4`

数据库中可确认以下顺序：

1. 在原始 run `62678...` 里，`google_super__COMPOSIO_MULTI_EXECUTE_TOOL` 先后出现两次不同 `toolCallId` 的 `tool_call_completed`
2. 这两次 `outputPreview` 都不是“邮件已发送”的 provider 回执，而是同一个 `confirmation_required`
3. 两次都指向同一个 `confirmationId = 9267ad7c-9d05-4857-81be-7641bbee9fc4`
4. 但原始 run 没有停在 `waiting_user`
5. 相反，它在第二次 `confirmation_required` 之后继续产出 `assistant_delta`
6. 从 `03:30:04Z` 开始逐字流出：
   - `已成功发送邮件！`
   - `收件人: 3065025109@qq.com`
   - `主题: 测试`
   - `内容: 当前时间：2026-05-05T03:29:34.273Z`
7. 随后该 run 自己又调用了 `complete_task`
8. `03:30:10Z` 持久化出最终 `assistant_message`
9. 而用户的 `/approve` 对应 `user_response` 是 `03:30:30Z`

因此，本轮调查可以明确确认：

1. “批准前成功发送文本”不是单纯的 UI 排序错觉
2. 原始待确认 run 的确在未批准前继续走完了“成功总结”这条路径
3. 且在这条路径里，没有查到 Gmail provider 返回的 `messageId` / `threadId` 作为真实发信回执
4. 当前“已成功发送邮件”更像是模型在读取到 `confirmation_required` 后继续自行总结，而不是基于真实发送结果收口

### 4.12 数据库级回放核对：`/approve` 后首轮 replay 已失败但 run 仍继续重规划

对恢复 run `e0e65b79...` 的数据库事件继续核对后，又确认了另一条关键链路：

1. `/approve` 后新 run 首轮确实先发起了 synthetic replay：
   - `toolCallId = confirmed:9267ad7c-9d05-4857-81be-7641bbee9fc4`
2. 该首轮 replay 没有成功执行发信，而是立刻失败为：
   - `connector_guide_blocked:google_super`
3. 失败后 run 没有立即终止，也没有把“replay 首轮失败”暴露为恢复失败
4. 相反，系统继续进入常规模型规划：
   - `load_connector_guide`
   - `google_super__COMPOSIO_SEARCH_TOOLS`
   - `google_super__COMPOSIO_GET_TOOL_SCHEMAS`
   - `google_super__COMPOSIO_MULTI_EXECUTE_TOOL`
5. 这条重规划链后续再次暴露：
   - `google_super_confirmation_target_missing`
6. 即使在出现上述失败后，恢复 run 最终仍再次产出：
   - `已使用 Google Workspace 成功发送邮件`

因此，本轮数据库证据进一步确认：

1. `/approve` 后并不是“首轮 replay 成功直恢复”
2. 当前实现实际上允许“replay 失败后继续普通规划”
3. 这正是此前浏览器层看到 `SEARCH_TOOLS -> GET_TOOL_SCHEMAS -> MULTI_EXECUTE_TOOL` 的直接后端证据
4. 最终再次出现“成功发送邮件”文本，同样不能直接等价为真实 Gmail 发信成功

### 4.13 数据库级补充判断：重复确认并非只有前端重复渲染

本轮数据库核对也修正了此前一个更保守的判断。

此前仅从 UI 观察时，更倾向于把“双确认”理解为：

1. 同一确认对象被多个前端入口重复展示

但数据库里的原始 run `62678...` 证明：

1. 同一业务参数下，模型在未批准前至少重新发起了两次新的 `google_super__COMPOSIO_MULTI_EXECUTE_TOOL`
2. 两次调用各自拥有不同的 `toolCallId`
3. 但因为 pending confirmation 复用逻辑存在，它们又都拿到了同一个 `confirmationId = 9267...`

这意味着：

1. 前端重复渲染问题仍然可能存在
2. 但这次样本里的“两个确认 UI”已经不能只归因为前端
3. 后端实际上也发生了“同一待确认业务参数被模型再次发起工具调用、并复用原 confirmationId”的事实

### 4.14 数据库级补充判断：confirmation 与原始 run 的绑定缺失

本次直接查询 `task_session_mcp_tool_confirmations` 还发现：

1. `confirmationId = 9267ad7c-9d05-4857-81be-7641bbee9fc4`
2. 其 `agent_run_id = null`

这会带来两个直接后果：

1. confirmation 审计事件无法稳定回挂到原始 run
2. 后续排查“这条 confirmation 究竟由哪一轮 run 触发、又由哪一轮 run 消费”时，证据链天然不完整

因此，本轮数据库核对后，还应把“confirmation 与 originating run 绑定缺失”视为当前问题的一部分。

### 4.15 自动化回归对证：provider envelope 包裹的 `confirmation_required` 未被截停

在补充最小后端自动化回归时，新增了如下测试：

1. `execute stops the turn when google workspace confirmation is wrapped in provider envelope`

该测试模拟真实链路中的关键包装形式：

1. 模型先发起 `google_super__COMPOSIO_MULTI_EXECUTE_TOOL`
2. runtime 返回的不是顶层 `{"type":"confirmation_required"}`
3. 而是 provider envelope：
   - 顶层包含 `providerId` / `toolName`
   - `confirmation_required` 位于 `result.structuredContent`
   - 同时 `result.content[].text` 也承载了同一份结构化确认 JSON

该测试的预期应为：

1. 首轮工具调用返回待确认后，run 立即进入 `waiting_user`
2. 不再继续第二轮模型调用
3. 不再继续调用 `complete_task`

但当前实际失败表现是：

1. `fetchCount = 2`
2. 即协调器在拿到 provider envelope 后仍继续进入了下一轮模型调用

这条自动化失败用例与前述数据库证据完全一致，进一步确认：

1. 当前问题不是“浏览器排序错了”
2. 也不是“前端把成功文本摆早了”
3. 而是后端 managed 协调器确实没有稳定识别外层包装中的 `confirmation_required`

### 4.16 自动化回归对证：approve 后 replay 首轮失败仍继续普通规划

本轮还新增了如下测试：

1. `execute does not continue normal planning when approved mcp replay fails on the first attempt`

该测试模拟真实恢复路径：

1. 当前 run 由 `/approve` 触发，带有 `confirmedMcpToolReplay`
2. 首轮 synthetic replay 直接执行原始 `google_super__COMPOSIO_MULTI_EXECUTE_TOOL`
3. 该 replay 首轮失败为：
   - `connector_guide_blocked:google_super`

按本次修订后的目标语义，预期应为：

1. run 立即暴露恢复失败
2. 不再继续普通模型规划
3. 不再继续 `load_connector_guide`
4. 不再继续 `SEARCH_TOOLS / GET_TOOL_SCHEMAS / MULTI_EXECUTE_TOOL`

但当前实际失败表现是：

1. `executeMock` 被调用了 `193` 次，而不是预期的 `1` 次
2. 说明 run 在 replay 首轮失败后继续进入了长循环式普通规划

这条自动化失败用例与前述数据库证据也完全一致，进一步确认：

1. `/approve` 后当前实现并不保证“首轮 replay 失败即恢复失败”
2. 当前实现允许 replay 失败后继续退化回普通 managed run
3. 这正是浏览器层出现重复搜索工具、重复 schema、再次触发写操作的重要后端原因

## 5. 关键判断

基于本次回归，可以确认以下判断：

1. `Composio` 本身没有查到通用的“发邮件前人工审批”机制
2. 当前发信受阻的主因来自 `oneceo` 自己的连接器恢复与高风险确认闭环
3. 读 Gmail 能成功，说明 `google_super` 与 Composio 连接本身可用
4. 发邮件发不过，不是因为 Gmail OAuth 没连上，而是因为：
   - 部分场景先被 `pending_recover` 挡住
   - 部分场景虽然进入确认，但 approve 后恢复仍会退化
   - 部分全新会话根本没有挂载 `google_super`，会直接提示“当前会话未连接 Google Workspace”
5. 浏览器观察、数据库回放与自动化回归三层证据已经互相对齐：
   - provider envelope 中的 `confirmation_required` 未被稳定识别
   - replay 首轮失败后会继续普通规划
   - 两者共同放大了“批准前成功文本”“重复确认”“target_missing”这些表象

## 6. 现阶段问题清单

截至本记录形成时，真实浏览器回归确认的剩余问题如下：

1. `google_super` 在首轮真实调用时仍可能先落入 `pending_recover`
2. `pending_recover` 场景与“高风险待确认”虽然已经能区分，但前者仍会让用户误以为确认链路失效
3. Gmail 发送场景进入确认后，run 仍可能落成 `managed_model_plain_text_without_tool_call`
4. 用户点击 `确认执行` 后，恢复 run 仍可能再次出现 `SEARCH_TOOLS -> GET_TOOL_SCHEMAS -> MULTI_EXECUTE_TOOL`
5. 上述退化继续叠加时，仍可能重新暴露 `google_super_confirmation_target_missing`
6. 新建任务对 `google_super` 的继承或自动附着不稳定，导致同一用户在不同会话中同时出现“已连接”和“未连接”两种状态
7. 同一个 `confirmationId` 在前端可能被多个渲染分支同时展示，造成“两个确认 UI”并存的错觉
8. 原始待确认 run 在拿到 `confirmation_required` 后没有稳定停在 `waiting_user`，而是可能继续产出成功总结
9. `/approve` 后首轮 synthetic replay 即使失败，也可能继续退化为普通规划 run
10. `task_session_mcp_tool_confirmations.agent_run_id` 为空，导致 confirmation 与原始 run 的证据链断裂
11. 当前自动化回归已能稳定复现：
   - provider envelope 包裹的 `confirmation_required` 未被截停
   - replay 首轮失败后仍继续普通规划

## 7. 阶段性结论

本次回归后的最准确结论是：

1. `Google Workspace` 连接与只读能力可用
2. 高风险确认链可以被触发
3. 前端点击确认后已经不再依赖“补发继续执行消息”这条旧路径
4. 但“批准后后端必定直恢复原始待确认 tool call”仍未达到完全稳定
5. 新建任务对 `google_super` 的会话继承也还不稳定
6. 同一确认在前端仍存在重复渲染问题，会制造“是不是又拦截了一次”的误判
7. 更关键的是，原始待确认 run 与批准后的恢复 run 都可能在没有真实发信回执的前提下写出“已成功发送邮件”总结
8. 当前链路不能认定为已经完成最终闭环验收

## 8. 证据分层

为避免后续再次把不同层级的问题混为一谈，本记录将当前证据明确拆为三层：

### 8.1 浏览器观察证据

1. `pending_recover` 会先于确认链路暴露
2. 高风险确认卡片可见
3. 确认后仍能看到 `SEARCH_TOOLS -> GET_TOOL_SCHEMAS -> MULTI_EXECUTE_TOOL`
4. UI 中存在重复确认展示

### 8.2 数据库回放证据

1. 原始待确认 run 在未批准前继续写出成功总结
2. `/approve` 后首轮 replay 先失败，再继续普通规划
3. confirmation 与 originating run 的绑定存在缺失

### 8.3 自动化回归证据

1. provider envelope 包裹的 `confirmation_required` 当前无法稳定截停 run
2. replay 首轮失败后，run 当前不会立即失败，而会继续普通规划

### 8.4 现阶段证据总合

截至目前，这三层证据已经足以支持以下结论：

1. 当前问题不是单一前端展示 bug
2. 也不是单一 `target_missing` 字段提取 bug
3. 当前主问题是高风险确认语义识别与批准后恢复语义都还没有完全落到实现上

## 9. 建议后续排障重点

后续如果进入代码修复阶段，应优先围绕以下方向继续定位：

1. `approved replay` 上下文解析失败时，是否存在静默降级为普通 managed run 的路径
2. `pending_recover` 到 `connected` 的恢复时机、提示语义与重试触发条件
3. Gmail 发送参数在确认摘要、目标提取、恢复放行时的结构是否始终一致
4. `waiting_user` 场景是否仍被错误包装成 `managed_model_plain_text_without_tool_call`
5. 新建任务创建时，`google_super` 是否按预期继承已启用连接器与会话附着状态
6. 前端多个确认渲染入口是否应在进入视图派生前，先按 `confirmationId` 做全局去重
7. MCP 工具结果里的 `confirmation_required` 是否被外层 provider envelope 包裹后，未被 managed 协调器识别并及时截停
8. `/approve` 后 synthetic replay 的首轮失败，是否被允许继续落回普通模型规划而不是直接暴露恢复失败
9. confirmation 落库时 `agent_run_id` 为什么会是空值，以及这是否导致 run 级审计与恢复核对失真
