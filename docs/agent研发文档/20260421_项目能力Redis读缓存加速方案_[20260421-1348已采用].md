# 20260421 项目能力 Redis 读缓存加速方案 [20260421-1348已采用]

## 1. 背景

当前用户态“普通项目”能力已经完成后端持久化，但读取路径仍然基本直打数据库：

1. 侧边栏初始化时会读取普通项目列表；
2. 普通项目详情页会读取项目信息与项目内 session；
3. 会话移动到项目、项目编辑、项目删除后，前端刷新时仍会重新走 DB 查询；
4. 项目相关读取量上来后，会把压力集中在：
   - [task-creation-routes.ts](/Users/watson/codingProj/oneceo/apps/api/src/routes/task-creation-routes.ts)
   - [app-user-project.dao.ts](/Users/watson/codingProj/oneceo/apps/api/src/db/dao/app-user-project.dao.ts)
   - [task-creation-session.dao.ts](/Users/watson/codingProj/oneceo/apps/api/src/db/dao/task-creation-session.dao.ts)

用户要求为“项目相关功能”补 Redis 加速，但必须避免把 Redis 变成新的真相源。

## 2. 目标

本轮只做“项目读缓存”，目标是：

1. 普通项目列表读取优先命中 Redis；
2. 普通项目详情读取优先命中 Redis；
3. 普通项目内 session 列表读取优先命中 Redis；
4. 所有写路径仍然先写 DB，再失效 Redis；
5. Redis 未显式启用时，功能完全保持现状；
6. 不引入异步投影、消息总线、双写源或额外依赖。

## 3. 非目标

本轮明确不做：

1. 不把项目写操作改成 Redis 前置；
2. 不把 session 总列表整体搬进 Redis；
3. 不做 Redis outbox / projection worker；
4. 不做前端 localStorage 项目缓存；
5. 不绕过现有 owner 校验与 DB 真相源。

## 4. 总体原则

### 4.1 真相源

1. `app_user_projects` 仍是项目真相源；
2. `task_creation_sessions.metadata_json.projectId/projectName` 仍是 session 项目归属真相源；
3. Redis 只缓存“读接口结果”，不缓存未落库状态。

### 4.2 Redis 开关约束

严格复用现有 [redis-client-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/redis-client-service.ts)：

1. 仅当 `ONECEO_REDIS_ENABLED=true` 且 `REDIS_URL` 有效时启用；
2. 只配置 `REDIS_URL` 但未显式开启，等同于不启用；
3. Redis 异常时必须自动回退 DB；
4. 业务代码不得直接 new Redis 客户端。

### 4.3 写路径原则

所有写操作仍走：

1. DB 写入成功；
2. file memory 同步（已有逻辑继续保留）；
3. Redis 缓存失效；
4. 下次读请求再回填 Redis。

不做“先写 Redis 再异步落库”的方案。

### 5.2 普通项目详情页

当前普通项目详情页在前端通过“项目列表 + 全量 session 列表”拼装，查询面偏大。

对应前端位置：

本轮建议和普通项目详情页统一，直接复用 `projects/:projectId/sessions`。

## 6. Redis Key 设计

保持简单、按用户隔离：

1. 项目列表
   - `oneceo:task-projects:user:${userId}:list:v1`
2. 单项目详情
   - `oneceo:task-projects:user:${userId}:detail:${projectId}:v1`
3. 单项目 session 列表
   - `oneceo:task-projects:user:${userId}:sessions:${projectId}:v1`

说明：

1. 全部带 `userId`，避免跨用户串读；
2. 全部带 `v1`，后续结构变化时可直接升版本；
3. 暂不设计集合索引 key，直接按精确 key 删除即可。

## 7. 缓存内容与 TTL

### 7.1 缓存内容

Redis value 直接存 JSON 序列化后的接口响应 `data`，不做额外投影层：

1. 项目列表缓存的是 `TaskCreationProjectSummary[]`
2. 项目详情缓存的是单个 `TaskCreationProjectSummary`
3. 项目 session 列表缓存的是 `TaskCreationSessionSummary[]`

### 7.2 TTL

本轮建议统一先用短 TTL：

1. `300s`（5 分钟）

原因：

1. 项目读数据量不算极端高，5 分钟足够起到热缓存作用；
2. 即使失效链路漏删，也不会长时间保留脏数据；
3. 保持最短路径，不需要引入复杂过期分层。

## 8. 读写逻辑

### 8.1 读路径

所有读接口遵循同一模式：

1. 先判定 Redis 是否启用；
2. 启用时先查 Redis；
3. 命中则直接返回；
4. miss 时查 DB；
5. DB 查到后写回 Redis；
6. 返回 DB 结果。

### 8.2 写路径

以下接口成功后，都必须删缓存：

1. `POST /api/task-creation/projects`
2. `PUT /api/task-creation/projects/:projectId`
3. `DELETE /api/task-creation/projects/:projectId`
4. `POST /api/task-creation/sessions/:sessionId/project`

删除策略采用“精确 key 失效”，不做 patch 更新：

1. 创建项目：
   - 删除用户项目列表 key
2. 编辑项目：
   - 删除用户项目列表 key
   - 删除该项目详情 key
3. 删除项目：
   - 删除用户项目列表 key
   - 删除该项目详情 key
   - 删除该项目 session 列表 key
4. session 移动项目：
   - 删除用户项目列表 key（保持简单，哪怕当前列表还不含计数）
   - 删除原项目 session 列表 key（如果有原项目）
   - 删除新项目 session 列表 key（如果有新项目）

说明：

1. 这里故意选择“删缓存而不是更新缓存”，逻辑更短、更稳；
2. 写操作本来就需要命中 DB，因此不追求写路径零查询。

## 10. 推荐实现顺序

按最短路径建议：

1. 新增 `task-creation-project-redis-cache-service.ts`
2. 给 `GET /projects` 接读缓存
3. 新增 `GET /projects/:projectId`
4. 新增 `GET /projects/:projectId/sessions`
5. 普通项目详情页改走新接口
6. 项目创建/编辑/删除/归属写操作接缓存失效
7. 侧边栏普通项目展开态切到项目 session 接口

## 11. 验证要求

至少覆盖：

### 11.1 Redis 关闭

1. `ONECEO_REDIS_ENABLED=false` 时功能完全正确；
2. 只配置 `REDIS_URL` 但不开开关时，仍完全不使用 Redis。

### 11.2 Redis 开启

1. 首次读 miss，回退 DB 成功；
2. 二次读命中 Redis；
3. 创建项目后，项目列表缓存失效；
4. 编辑项目后，项目列表与项目详情缓存失效；
5. 删除项目后，项目列表 / 项目详情 / 项目 session 缓存失效；
6. session 移动项目后，原项目与新项目 session 列表缓存失效；
7. Redis 故障时接口仍回退 DB 正常返回。

### 11.3 前端主链

1. 侧边栏项目列表仍正常；
2. 普通项目详情页仍正常；
3. 普通项目展开态会命中 `GET /projects/:projectId/sessions`；
4. session 移动到项目后，项目详情页刷新能看到正确结果；
5. 删除项目后，session 仍能在无项目链路找回。

## 12. 本轮建议结论

建议采用“DB 真相源 + Redis 读缓存 + 写后删缓存”的最短路径：

1. 改动面可控；
2. 不会把 Redis 引入为第二真相源；
3. 与当前仓库 Redis 使用规则一致；
4. 后续若要继续扩展项目计数、项目统计、项目详情聚合，也可以在同一缓存服务里继续收口。

不建议本轮直接上：

1. Redis 前置写；
2. outbox projection；
3. 项目全域读模型重构；
4. 前端本地缓存与 Redis 混合缓存。
