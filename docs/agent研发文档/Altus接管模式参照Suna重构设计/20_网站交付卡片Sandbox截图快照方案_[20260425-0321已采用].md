# 20 网站交付卡片 Sandbox 截图快照方案 [20260425-0321已采用]

## 1. 背景

当前网页类交付卡片仍然以 `workspace/raw/*` HTML 预览为主。这个路径对简单静态页面可用，但对复杂网站不稳定：

1. 多文件 React/Vite/Next 类项目需要自己的 dev/build server 才能正确解析 CSS、JS chunk、路由和静态资源。
2. `workspace/raw/index.html` 只代表单个文件可读，不代表整个网站运行环境可用。
3. sandbox 关闭或恢复后，前端再尝试重载 raw HTML，容易出现 CSS 缺失、JS 缺失或路由失效。
4. 用户在对话流里真正需要的是“完成结果长什么样”的稳定视觉反馈，不需要在完成卡片里继续交互。

因此，网页类完成卡片不应继续把 raw HTML iframe 当作主预览能力。

## 2. 设计判断

本方案采用与 Manus 类似的完成态预览策略：

> 网站在 sandbox 内真实运行，系统确认页面可渲染后截图；对话区完成卡片展示持久化截图。用户需要交互时，进入调试页面或执行部署。

这比本地迁移预览更合理，原因是：

1. 网站真实运行依赖服务进程，不依赖平台猜测 HTML 资源关系。
2. 截图在任务完成后脱离 sandbox 生命周期，历史对话不会因为 sandbox 关闭而失效。
3. 完成卡片职责回归“视觉摘要”，不再承担浏览器交互职责。
4. 调试和部署仍是交互入口，职责清晰，不在聊天卡片里混合复杂运行态。

## 3. 目标

1. 网页类任务完成后，对话区展示稳定的网站截图卡片。
2. 截图必须来自 sandbox 内真实运行的网站，而不是 raw HTML 拼接结果。
3. 截图必须持久化，sandbox 关闭后仍可显示。
4. 用户需要交互时，继续使用：
   - `调试` 页面
   - `部署` 后的线上地址
   - 卡片工具条中的源码/打开入口
5. 保留 raw HTML 预览作为简单文件 fallback，不再作为复杂网站主路径。

## 4. 非目标

1. 不在完成卡片里提供交互式网页浏览器。
2. 不把 sandbox 端口转发 URL 作为长期交付物。
3. 不继续扩展 raw HTML 资源恢复逻辑来兼容复杂站点。
4. 不引入新的前端运行容器或本地静态迁移引擎。
5. 不改变部署成功的判定逻辑；本地预览截图不等于线上发布成功。

## 5. 总体方案

网页类完成态新增一条系统侧截图收口链路：

1. Altus 在 sandbox 内生成网站项目。
2. 运行完成前，系统识别该 run 属于网页类交付。
3. 系统在 sandbox 内启动或复用项目服务。
4. 系统等待服务端口就绪。
5. 系统使用浏览器打开 sandbox 内真实 URL。
6. 页面渲染稳定后截取固定视口截图。
7. 截图上传到持久化对象存储。
8. 截图引用写入 run event / final message metadata。
9. 前端 `AltusArtifactPreviewCard` 优先展示截图。
10. 如果截图不存在，复杂网站卡片展示占位与调试/部署入口；只有简单 HTML 文件才允许降级到 raw HTML 预览。

完成卡片的主展示从：

```text
iframe -> workspace/raw/index.html
```

调整为：

```text
img -> persisted website preview screenshot
```

### 5.1 网页类截图触发条件

截图链路由系统判定，不依赖模型额外说明。满足以下任一条件即可进入截图候选：

1. 意图识别结果为 `artifactKind === "web_app"` 或 `mode === "deployable_web_app"`。
2. run 的 `deliverables` 或 `managedArtifacts` 中存在 `html/htm`，且同一 workspace 存在 `package.json` 或 `oneceo.manifest.json`。
3. workspace 中存在 `oneceo.manifest.json`，且 manifest 类型指向 `web` / `node` / `static` 可运行网站。
4. 本轮 run 中出现过 `debug_open_page` 成功事件，且目标 URL 指向当前 sandbox 内的本地服务。
5. 本轮 run 中出现过 `debug_open_page` 成功事件，但没有 manifest / package 启动命令时，允许使用本轮 HTML 交付物或 workspace 根目录常见 `index.html` 作为截图入口。

判定顺序：

1. 优先使用 task intent / managed setup 的结构化意图。
2. 其次使用 manifest。
3. 再使用完成态 web artifact。
4. 最后使用成功的 `debug_open_page` 事件。

如果只能发现单个孤立 `index.html`，且没有 manifest / package script / debug URL，则视为简单 HTML 文件，不进入复杂网站截图链路。

## 6. 运行与截图链路

### 6.1 服务启动来源

按最短路径复用现有产物约定，避免新增复杂项目识别系统：

1. 优先读取 `oneceo.manifest.json` 中的启动命令、端口和 healthcheck。
2. 其次读取 `package.json` 的标准脚本：
   - `start`
   - `dev`
   - `preview`
3. 如果任务过程中已经调用过 `debug_open_page`，可优先复用其 `targetUrl` 对应端口。
4. 如果调试阶段已经成功打开页面，但项目是单文件 HTML、没有 `package.json` / manifest 启动命令，则使用 sandbox 内部 `file://` URL 对 HTML 文件截图。
5. 如果没有可识别入口，则不强行猜测复杂命令，截图状态记为 `capture_unavailable`。

这里的原则是：优先使用项目已经声明的运行方式；只有在调试工具已经证明 HTML 页面可打开时，才把该 HTML 文件作为完成态截图入口，避免“调试可用但完成卡片误报无启动命令”。

### 6.1.1 服务启动约束

网站服务通常是长驻进程，截图服务必须按后台任务处理：

1. 启动命令必须以后台方式执行，不能阻塞 `complete_task` 主流程。
2. 启动日志写入固定临时文件，例如 `/tmp/oneceo-preview-<runId>.log`。
3. 每个 run 最多启动一次预览服务；如果端口已可访问，直接复用。
4. 默认端口优先级：
   - manifest 显式端口
   - `PORT` 环境变量
   - package script 中显式 `--port`
   - 常见端口 `3000 / 5173 / 4173 / 8080`
5. 端口等待必须有硬超时，建议首版：
   - 服务启动命令执行超时：20 秒
   - 端口探测总超时：45 秒
   - 页面截图总超时：30 秒
6. 超时后记录 `capture_failed`，不能继续无限等待，也不能把长驻服务输出当作普通命令结果写入对话区。
7. 若截图服务自己启动了新进程，截图完成后可以保留该进程供调试页复用；但不得把该进程作为完成卡片展示的长期依赖。

### 6.2 端口访问

系统使用两类 URL，各司其职：

1. sandbox 内部 URL：
   - `http://127.0.0.1:<port>`
   - 用于 Playwright 截图，避免依赖外部网络抖动。
2. 端口转发 URL：
   - 通过 `e2bConnector.getSandboxHost(sandboxId, port)` 获取。
   - 仅作为调试页或临时打开入口，不写成长期交付地址。

### 6.3 截图动作

截图由系统侧执行，不要求模型额外调用工具：

1. 进入 `complete_task` 收口阶段后，如果 run 属于网页类交付，则触发 `captureWebsitePreviewSnapshot`。
2. 在 sandbox 内用预置 Playwright / Chromium 打开本地服务 URL。
3. 使用固定视口，例如 `1280x720` 或 `1365x768`。
4. 等待 `domcontentloaded`、关键资源加载和短暂稳定窗口。
5. 截图保存为 PNG。
6. 上传 R2，返回 `storageKey / width / height / capturedAt / sourceUrl / port`。

截图失败不应把已完成的网站任务整体判定失败，但必须在 metadata 里记录失败原因，方便后续排查。

### 6.4 截图结果状态

`previewSnapshot.status` 使用明确枚举：

1. `captured`：截图成功，前端必须优先展示截图。
2. `capture_unavailable`：没有可识别启动入口，或该产物只是简单 HTML 文件。
3. `capture_failed`：已识别为复杂网站，但启动、端口探测、页面渲染或截图失败。
4. `storage_failed`：截图已生成，但持久化存储失败。

失败语义：

1. `capture_unavailable` 可进入 fallback。
2. `capture_failed` 对复杂网站不进入 raw iframe fallback，前端展示占位和调试/部署入口。
3. `storage_failed` 也不进入 raw iframe fallback，避免用户看到一个后续仍可能失效的临时预览。
4. 在 R2、Playwright、sandbox 正常配置下，复杂网站出现 `capture_failed/storage_failed` 视为功能回归，应进入日志排查，而不是视为正常降级。

## 7. 持久化模型

为减少改动，第一阶段不新增数据库表。

截图信息写入已有结构化消息 metadata：

```json
{
  "previewSnapshot": {
    "kind": "website_screenshot",
    "storageKey": "sessions/<sessionId>/previews/<runId>/website.png",
    "mimeType": "image/png",
    "width": 1280,
    "height": 720,
    "capturedAt": "2026-04-25T03:14:00.000Z",
    "source": {
      "sandboxId": "sandbox-id",
      "port": 3000,
      "url": "http://127.0.0.1:3000"
    },
    "status": "captured"
  }
}
```

写入位置：

1. `deliverables_ready` run event metadata。
2. 最终 assistant message / `managed_artifact_card` metadata。

前端不直接暴露 `storageKey`，而是通过后端 session 鉴权接口读取图片。

后续如果需要做多截图、多设备、多历史版本，再升级为独立表；第一阶段不做。

### 7.1 权威读取源

第一阶段不新增表的前提下，必须指定 metadata 权威读取顺序，避免后端接口多处猜测：

1. 最终 `assistant_message` metadata 中的 `previewSnapshot`。
2. `deliverables_ready` run event metadata 中的 `previewSnapshot`。
3. 同 run 最新 `tool_call_completed(complete_task)` event 的 `previewSnapshot`。

写入时三处可冗余保存同一份快照信息；读取时按上述顺序取第一份 `storageKey` 合法且状态为 `captured` 的记录。

如果三处都没有合法记录，图片读取接口返回 404，不触发 sandbox 恢复，也不尝试重新截图。重新截图必须通过后续显式修复动作完成，避免用户刷新历史会话时又唤醒 sandbox。

### 7.2 metadata 最小字段

`previewSnapshot` 必须至少包含：

1. `kind`
2. `status`
3. `storageKey`
4. `mimeType`
5. `width`
6. `height`
7. `capturedAt`
8. `source.sandboxId`
9. `source.port`

失败状态必须包含：

1. `status`
2. `reasonCode`
3. `message`
4. `source` 中可获得的上下文

## 8. 前端展示策略

`AltusArtifactPreviewCard` 展示优先级调整为：

1. `previewSnapshot.status === "captured"`：
   - 显示持久化截图。
   - 卡片内不滚动，不接管鼠标交互。
   - 保留“发布 / 源码 / 打开”工具条。
2. 已部署公网 URL：
   - 可作为打开入口和部署态信息，不作为默认卡片 iframe。
3. raw HTML 预览：
   - 仅用于 `capture_unavailable` 且判定为简单 HTML 文件的场景。
   - 对复杂 `web_app`，截图失败后不再自动回流到 raw iframe。
   - 继续沿用现有重载逻辑，但不再投入复杂资源恢复。
4. 截图失败：
   - 卡片展示简洁占位和“进入调试 / 查看源码 / 发布”入口。

视觉上对齐 Manus：

1. 顶部显示应用名称、发布状态、时间信息。
2. 中间显示截图。
3. 右上角突出“发布”按钮。
4. 底部只放轻量提示，不放可滚动网页。

## 9. 后端改动点

### 9.1 新增服务

建议新增：

```text
apps/api/src/services/task-session-website-preview-snapshot-service.ts
```

职责：

1. 判定 run 是否需要网站截图。
2. 解析启动命令和端口。
3. 启动或复用 sandbox 内服务。
4. 等待端口可访问。
5. 执行 Playwright 截图。
6. 上传截图到 R2。
7. 返回结构化 `previewSnapshot`。

该服务必须是可测试的纯编排层：命令解析、端口探测、截图执行、R2 上传分别拆成小函数，避免把所有分支塞进 `AltusRunCoordinator`。

### 9.2 接入点

接入 `AltusRunCoordinator` 的完成收口阶段：

1. `complete_task` 参数解析完成。
2. 交付物持久化完成。
3. run 标记 `completed` 之前。
4. 若为网页类交付，调用截图服务。
5. 将结果写入 `deliverables_ready` 与最终完成消息 metadata。

### 9.3 图片读取接口

新增鉴权接口：

```text
GET /api/task-creation/sessions/:sessionId/preview-snapshots/:runId/website.png
```

要求：

1. 复用 task session 权限校验。
2. 只允许读取当前 session/run metadata 中登记过的 `storageKey`。
3. 设置 `Content-Type: image/png`。
4. 设置合理缓存头，避免同一历史卡片重复拉取。
5. 不在该接口内启动或恢复 sandbox。
6. 不接受前端传入任意 `storageKey`。

## 11. 与现有方案的关系

### 11.1 与 Issue39 raw 预览修复的关系

当前 Issue39 修复仍保留，但定位调整：

1. 简单 HTML 文件预览兜底。
2. 源码文件查看辅助能力。
3. runtime 恢复后的临时预览。

它不再承担复杂网站完成卡片的主展示职责。

### 11.2 与部署链路的关系

截图只证明 sandbox 内页面能渲染，不证明线上部署成功。

部署链路仍以 Railway/平台部署状态、healthcheck、公网 URL 为准。提示词和工具约束中已有“不要把 debug_open_page 当作部署成功”的规则，本方案继续遵守。

### 11.3 与调试链路的关系

用户需要交互时进入 `调试` 页。调试页继续复用现有 n.eko / remote browser 能力，不把这套交互能力复制进完成卡片。

## 12. 实施顺序

1. 文档审核通过后，将本文件状态更新为 `[yyyymmdd-hhmm已采用]`，并同步 README 索引。
2. 先补截图触发条件与 metadata 类型测试，不接入实际截图。
3. 新增后端截图服务，但先只支持 `oneceo.manifest.json` 和标准 `package.json` 脚本。
4. 新增 preview snapshot 图片读取接口，按 metadata 权威顺序读取，不唤醒 sandbox。
5. 在 `AltusRunCoordinator` 完成收口阶段接入截图服务。
6. 前端 `AltusArtifactPreviewCard` 优先显示截图。
7. 补单元测试覆盖 metadata、URL 构造、卡片优先级、复杂 web_app 不回流 raw iframe。
8. 补至少一个 Playwright/Vitest 回归：复杂站点完成卡片显示 PNG 截图而不是 raw iframe。
9. 保留当前 raw 预览测试，确认简单 HTML fallback 未被破坏。

## 13. 验收标准

1. 复杂 Vite/React 网站完成后，对话区卡片显示截图，不再依赖 `workspace/raw/index.html` iframe。
2. sandbox 关闭后刷新页面，完成卡片截图仍可显示。
3. 截图存在时，卡片内不可滚动、不可交互。
4. 点击“发布”仍进入部署链路。
5. 点击“源码”仍可查看项目文件。
6. 进入“调试”页仍可交互访问 sandbox 内页面。
7. 截图失败时，任务完成信息不丢失，卡片显示可理解占位和替代入口。
8. 部署成功判定不受截图成功影响。
9. 复杂 web_app 截图失败时，不自动展示 raw HTML iframe。
10. 简单单文件 HTML 在没有截图入口时，仍可走现有 raw HTML fallback。
11. 图片读取接口不会因为历史卡片刷新而启动 sandbox。

## 14. 风险与约束

1. 启动命令识别不完整：
   - 第一阶段只支持明确 manifest / package scripts。
   - 不做任意命令猜测，避免误启动和长时间挂起。
2. 截图时机过早：
   - 需要等待端口、DOM 和短稳定窗口。
   - 后续可增加 selector 或截图质量检查，但第一阶段不做复杂视觉判定。
3. 截图资源占用：
   - 每个网页 run 只截图一次。
   - 默认桌面视口，不做多设备截图。
4. 结果不交互：
   - 这是刻意设计。交互归调试页或部署页。
5. R2 配置缺失：
   - 截图状态记录为失败，完成卡片降级；不阻塞已有交付物下载或源码查看。
6. metadata 冗余写入：
   - 第一阶段为了避免新增表，会把 `previewSnapshot` 写入多个完成态事件。
   - 读取顺序必须固定，避免前端或接口随机选取不一致版本。
7. 复杂站点截图失败后的用户体验：
   - 不回退 raw iframe 会让用户看到占位而不是半坏页面。
   - 这是刻意选择，目的是避免把错误伪装成可用预览。

## 15. 需要用户确认的口径

1. 完成卡片默认只显示截图，不提供交互式 iframe。
2. 用户需要交互时，通过调试页或部署后的线上地址进入。
3. raw HTML 预览只作为简单 HTML fallback，不再作为复杂 web_app 的失败回退。
4. 第一阶段只做桌面截图，不做移动端截图。
