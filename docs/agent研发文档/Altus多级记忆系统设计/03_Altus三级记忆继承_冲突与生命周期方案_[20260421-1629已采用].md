# 03 Altus三级记忆继承、冲突与生命周期方案 [20260421-1629已采用]

更新时间：2026-04-21

---

## 1. 目标

本文件只回答三件事：

1. 三层记忆运行时如何继承
2. 冲突时谁优先
3. 生命周期里哪些动作允许，哪些动作禁止

---

## 2. 运行时继承规则

## 2.1 只做运行时组装，不做持久化复制

运行时组装：

```ts
type ResolvedAltusMemoryContext = {
  userMemory: AppUserPersonalization;
  projectMemory: AltusProjectMemory | null;
  sessionMemory: AltusSessionMemory;
}
```

原则：

1. 用户级是长期偏好
2. 项目级是公共约束
3. session 级是当前会话事实

不做：

1. 把用户级复制到项目
2. 把项目级复制到 session
3. 把项目级全文塞进 session memory

## 2.2 读取顺序

每次 run 启动时：

1. 读取用户级记忆
2. 根据 `projectId` 读取项目级记忆
3. 读取 session 级记忆
4. 组装 prompt context

补充要求：

1. 如果 session 创建时就指定项目，`projectId` 必须在 `POST /sessions` 完成持久化
2. 首轮 `initialMessage` 和首轮 run 都必须读取到这个已落盘的 `projectId`
3. 不允许出现“首轮消息先写入，再异步补绑项目”的链路
4. 用户级 / 项目级读取允许先查 Redis，未命中或 Redis 异常时直接回退 DB
5. session 级读取同样遵循“先 Redis，后 DB”，并且只在 run 启动阶段做一次装载

## 2.3 运行快照原则

首版采用“run 启动时快照”规则：

1. 用户级记忆在 run 启动时读取一次
2. 项目级记忆在 run 启动时读取一次
3. session 级记忆在 run 启动时读取一次

如果 run 执行过程中用户修改了：

1. 个性化信息
2. 项目级记忆

这些变更都只从**下一轮** run 开始生效。

原因：

1. 避免当前 run 中 prompt context 变化
2. 避免同一轮输出前后逻辑漂移
3. 与 session 文件回写版本控制保持一致

## 3. 冲突优先级

## 3.1 回答风格冲突

例如：

1. 用户级要求“温和、简短”
2. 项目级要求“正式、完整”
3. session 级要求“这轮先只给结论”

优先级：

`session 当前指令 > 用户级风格偏好 > 项目级风格提示`

## 3.2 项目规范冲突

例如：

1. 用户级偏好“尽量自由发挥”
2. 项目级要求“必须按项目规范执行”

优先级：

`session 当前任务约束 > 项目级规范 > 用户级偏好`

## 3.3 当前会话事实冲突

例如：

1. 项目级说“默认输出 markdown”
2. session 级已经确认“这轮输出 json”

优先级：

`session 级已确认事实 > 项目级默认约束 > 用户级长期偏好`

## 3.4 固化结论

首版把优先级写死成三条：

1. 本轮执行事实和明确要求，始终以 session 级为准
2. 项目规范类约束，高于用户个人偏好
3. 用户级主要控制称呼、解释深度、语气和默认表达方式

## 4. session 与项目的关系

## 4.1 基础约束

1. 一个 session 同时只能属于一个项目
2. session 默认无项目归属
3. session 是否继承项目记忆，只看当前 `projectId`

## 4.2 首版允许的动作

1. 新建 session 时直接选择项目
2. 尚未进入有效运行的无项目 session 加入某个项目
3. 尚未进入有效运行的已归属项目 session 移出项目

## 4.3 首版不允许的动作

首版**不支持**以下路径：

1. 已在项目 A 下产生有效会话内容后，再直接迁移到项目 B
2. 已在项目 A 下产生有效会话内容后，先移出项目，再重新加入项目 B

原因：

1. session memory 中可能已经沉淀项目 A 的约束和决定
2. 直接迁移会把 A 的运行态事实带到 B
3. 这是首版最容易产生脏状态的路径

如果用户确实需要换项目：

1. 创建新的目标项目 session

## 4.4 项目归属锁定窗口

首版把项目归属变更窗口写死为：

1. 只有“未进入有效运行”的 session，才允许加入项目或移出项目
2. 一旦 session 已进入有效运行，项目归属冻结

“进入有效运行”的首版判定规则：

1. `altusSessionMemory.version > 0`
2. 或者该 session 已在当前项目归属下完成过一次有效 Altus run 写入

冻结后的直接效果：

1. 不允许 A -> B
2. 不允许 A -> 无项目
3. 不允许 无项目 -> B，如果该 session 已经带有其他项目历史运行态事实

## 4.5 项目删除规则

首版采用最小限制：

1. 只要项目下还有关联 session，就不允许删除项目

原因：

1. 不做隐式批量解绑
2. 不做历史 session 批量改写
3. 保证项目删除不会制造 session 悬挂态

后续如果需要支持强制删除，可以再单独设计。

## 4.6 项目改名规则

首版要求项目改名后同步刷新 session 展示缓存：

1. 批量更新该项目下 session 的 `projectName`
2. 同步更新 file-memory / session summary 里的展示字段
3. 运行时继承仍然只认 `projectId`，不认旧 `projectName`

原因：

1. 当前侧边栏和会话摘要直接展示 `projectName`
2. 如果只改项目表，不同步 session，会出现 UI 漂移
3. 这个同步属于显示一致性，不影响项目记忆真相源

## 5. session 级记忆写入生命周期

## 5.1 写入责任

统一由：

`task-session-altus-memory-service`

负责。

Altus 其他服务只负责提交候选增量，不直接写 JSON 到 DB。

补充要求：

1. session 级 Altus memory 的服务边界应尽量贴近 `task-session-skill-state-service`
2. 不额外拆出第二个冲突协调器或独立回写编排器
3. 所有 DB / Redis / sandbox 文件的收口都由这一个 service 负责
4. 运行中不重复读取 DB；当前 run 所需状态由内存快照和 sandbox 文件承接

## 5.2 触发点

### A. run 开始时

写入：

1. 新目标候选
2. 新约束候选
3. 当前追问上下文

读取：

1. 先从 Redis 读取 session 级记忆
2. Redis 未命中时回退 DB
3. 成功装载后 materialize 到 sandbox 文件
4. 当前 run 后续直接使用运行态内存快照，不重复打 DB

### B. waiting_user 时

写入：

1. `summary.latestOutcome`
2. 最新 `openQuestions`
3. flush sandbox 文件记忆

### C. completed 时

写入：

1. 完成摘要
2. 新 decisions
3. 清理已关闭 openQuestions
4. 工作笔记整理
5. flush sandbox 文件记忆

### D. failed 时

写入：

1. 失败摘要
2. 必要时新的待确认项
3. flush sandbox 文件记忆

### E. archive / restore 时

1. archive 前：从 sandbox 文件回写 DB
2. restore 后：用 DB / archive 文件重建 sandbox 文件

补充说明：

1. 这里的回写流程应直接对齐 skills memory 的 `saveSandboxFileMemoryToDb` 模式
2. 即：读 sandbox 文件 -> normalize -> 写 DB -> 刷新 Redis
3. 不单独新增 Altus 专属的复杂回写状态机

## 5.3 首版明确不做

1. 每个 token 高频写库
2. 跨 session 自动总结
3. 用户级 / 项目级自动写入 session
4. 比 skills memory 更复杂的额外并发协议
5. run 中为了读取最新 session memory 反复查询 DB

---

## 6. 降级规则

1. 没有用户级记忆时，用空 personalization
2. session 没有项目归属时，`projectMemory = null`
3. session 级记忆不存在时，返回空 session memory
4. 发现项目不存在但 session 仍残留 `projectId` 时，不注入项目记忆，并把该 session 视为数据异常，后端应返回显式错误供修复
5. 发现 `projectId` 有效但 `projectName` 旧值漂移时，以项目表最新名称覆盖 session 展示缓存
6. 用户级 / 项目级 Redis 不可用时，直接回退 DB，不阻塞运行

第四条不会成为正常主链逻辑，因为首版禁止删除仍有关联 session 的项目，但需要作为兜底保护。

## 7. 与 skills memory 对齐原则

这次 Altus session memory 设计，首版明确只对齐到 skills memory 的复杂度，不超过它：

1. 同样是 DB metadata 真相源
2. 同样是 Redis 可选缓存
3. 同样是 sandbox 文件运行态副本
4. 同样是在 run 生命周期和 archive / restore 这些受控时机 flush
5. 同样由单一 service 负责 DB / cache / file 三者收口

因此首版不做：

1. 双写协调器
2. 文件回写 compare-and-set
3. 额外的冲突状态机

如果未来 task session 允许一个 session 同时存在多个活跃 sandbox，再重新升级这部分设计。
