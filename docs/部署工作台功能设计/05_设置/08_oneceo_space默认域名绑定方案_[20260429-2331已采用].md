# 设置 / oneceo.space 默认域名绑定方案 [20260429-2331已采用]

## 1. 背景

当前用户部署成功后，平台仍会在多个用户可见位置暴露 Railway 默认域名，例如 `*.up.railway.app`：

- Altus 最终回复
- 发布与访问卡片
- 打开网站按钮
- Umami website domain
- 部署面板 API 返回的 `latestUrl` / `latestStaticUrl` / `domains`

这会让用户感知到供应商细节，也会让 OneCEO 的部署产物不像平台自己的交付物。现在 `oneceo.space` 已购买并托管在 Cloudflare，本方案目标是把用户部署后的默认访问入口统一替换为 `oneceo.space` 下的 OneCEO 托管域名。

## 2. 目标

1. 用户侧只暴露 `https://<project-slug>.oneceo.space`。
2. Railway 默认域名只作为内部 provider URL，用于健康检查、调试和管理后台诊断。
3. 域名创建、DNS 写入、证书等待、状态同步全自动完成，不要求用户手动进入 Cloudflare 或 Railway。
4. 域名稳定绑定到 OneCEO 用户项目，不随 session、重新部署、回滚而变化。
5. Umami 统计、发布卡片、Altus 回复都使用同一个 canonical public URL。

## 3. 非目标

1. 第一阶段不做 Cloudflare Worker / 反向代理网关。
2. 第一阶段不开放用户自定义根域名绑定。
3. 第一阶段不隐藏 DNS 查询中的 CNAME 指向；产品 UI 和公开访问 URL 不暴露 Railway 即可。
4. 第一阶段不为每次部署生成新域名。

## 4. 关键结论

第一阶段采用：

```text
用户浏览器
  -> https://<project-slug>.oneceo.space
  -> Cloudflare DNS only CNAME/TXT
  -> Railway custom domain
  -> Railway service
```

不采用：

```text
用户浏览器 -> Cloudflare Worker -> Railway provider URL
```

原因：

- 现有部署链路已经以 Railway service / environment / domain 为核心，直接绑定 Railway custom domain 改动最短。
- Railway custom domain 会自动管理访问入口和证书，Cloudflare 只负责 DNS。
- Worker 代理会额外引入缓存、上传大小、WebSocket、header、健康检查、日志和计费变量，不适合作为默认第一阶段。

## 5. 官方能力依据

Railway 自定义域名能力：

- `customDomainCreate(input)` 可为指定 `projectId` / `environmentId` / `serviceId` 绑定自定义域名。
- 返回 `domain`、`cnameTarget`、`status.dnsRecords`。
- 后续通过 `domains(projectId, serviceId, environmentId)` 查询 `serviceDomains` 与 `customDomains`。

本仓库已有 Railway API 文档记录：

- `docs/使用railway做部署服务的文档/railway-api-docs/railway_project_management_and_monitoring_guide.md`

Cloudflare DNS 能力：

- Cloudflare 托管 `oneceo.space` zone。
- 后端使用 Cloudflare DNS API 创建、更新、查询 DNS records。
- API Token 只授予 `oneceo.space` 的 Zone Read 与 DNS Edit。

## 6. 域名模型

### 6.1 域名归属

域名绑定单位是 OneCEO 用户项目：

```text
OneCEO user
  -> Railway Project
OneCEO user project
  -> Railway Environment
  -> Railway Service
  -> <project-slug>.oneceo.space
```

这与当前已经确定的部署资源模型一致：

- 一个 OneCEO 用户对应一个 Railway Project。
- 一个 OneCEO 用户项目对应一个 Railway Environment。
- 一个 OneCEO 用户项目对应一个默认 OneCEO 公网域名。

### 6.2 slug 生成

默认域名格式：

```text
<safe-project-name>-<short-project-id>.oneceo.space
```

示例：

```text
game-2048-a53b7.oneceo.space
user-admin-3f290.oneceo.space
```

生成规则：

1. 优先取用户项目名称。
2. 转小写。
3. 只保留 `a-z`、`0-9`、`-`。
4. 连续 `-` 合并。
5. 前后 `-` 去除。
6. 最长 48 字符。
7. 追加用户项目 ID 的短 hash，避免同名冲突。
8. 若项目名为空，使用 `app-<short-project-id>`。

禁止：

- 使用 sessionId 作为主域名。
- 使用随机后缀导致每次部署域名变化。
- 使用用户输入的完整域名作为默认域名。

## 7. 数据模型

第一阶段不新增独立表，先扩展现有 platform deployment account config。原因是默认域名与当前用户项目部署资源一一对应，生命周期跟随当前 `projectKey`。

建议新增字段：

```ts
type DeploymentConfig = {
  serviceDomain?: string; // Railway provider service domain，仅内部使用

  publicDomain?: string; // <project-slug>.oneceo.space
  publicUrl?: string; // https://<project-slug>.oneceo.space
  publicDomainProvider?: 'cloudflare_railway_custom_domain';

  railwayCustomDomainId?: string;
  railwayCnameTarget?: string;

  cloudflareZoneId?: string;
  cloudflareDnsRecords?: Array<{
    id?: string;
    type: string;
    name: string;
    value: string;
    proxied?: boolean;
    status?: 'created' | 'updated' | 'unchanged' | 'error';
    error?: string;
  }>;

  domainStatus?:
    | 'unconfigured'
    | 'creating_custom_domain'
    | 'pending_dns'
    | 'pending_certificate'
    | 'active'
    | 'failed'
    | 'repair_required';

  domainStatusMessage?: string;
  domainLastCheckedAt?: string;
  domainActivatedAt?: string;
};
```

后续如果需要支持用户自定义域名、多域名、域名审计，再独立 `deployment_domains` 表。

## 8. 后端模块拆分

### 8.1 `cloudflare-dns-service.ts`

职责：

- 校验 Cloudflare 配置是否完整。
- 根据 Railway 返回的 DNS records 做 upsert。
- 查询 DNS record 当前状态。
- 删除 OneCEO 托管的 DNS records。

环境变量：

```text
CLOUDFLARE_API_TOKEN=
CLOUDFLARE_ZONE_ID=
ONECEO_DEPLOYMENT_PUBLIC_DOMAIN=oneceo.space
ONECEO_DEPLOYMENT_PUBLIC_DOMAIN_PROXY=false
```

`ONECEO_DEPLOYMENT_PUBLIC_DOMAIN_PROXY=false` 表示 Cloudflare DNS only。第一阶段固定使用 DNS only。

### 8.2 `deployment-domain-service.ts`

职责：

- 生成默认 public domain。
- 创建或复用 Railway custom domain。
- 读取 Railway `status.dnsRecords`。
- 调用 Cloudflare DNS upsert。
- 轮询 Railway custom domain 状态。
- 输出用户态 public URL 与内部 provider URL。

### 8.3 `platform-deployment-account-service.ts`

接入点：

1. `provisionForUser()`
2. `recycleProjectService()`
3. 修复 service / environment 的分支

在 Railway service 创建、service domain 创建后，调用：

```ts
ensureProjectPublicDomain({
  userId,
  projectKey,
  railwayProjectId,
  railwayEnvironmentId,
  railwayServiceId,
  targetPort,
});
```

### 8.4 `railway-deployment-service.ts`

职责调整：

- 返回用户态 public URL 时优先使用 `publicUrl`。
- Railway provider URL 不再进入用户态 `latestUrl` / `latestStaticUrl` / `domains`。
- 管理后台或 debug API 可读取 `providerUrl`。

### 8.5 `task-session-deployment-runtime-service.ts`

职责调整：

- 公网验证拆成两层：
  1. provider reachability：验证 Railway service 已运行。
  2. public domain reachability：验证 `oneceo.space` 可访问。
- provider 通过、public domain 未生效时，不把部署标记为失败，进入 `domain_pending_dns` 或 `domain_pending_certificate`。
- Umami binding 使用 public domain。

## 9. 创建与绑定流程

### 9.1 新部署流程

```text
1. ensureUserProject(userId)
2. ensureProjectEnvironment(userProject.projectId, projectKey)
3. createService(...)
4. configureServiceInstance(...)
5. ensureServiceDomain(...)
   - 生成 Railway provider URL
   - 仅内部保存
6. ensureProjectPublicDomain(...)
   6.1 生成 <project-slug>.oneceo.space
   6.2 查询 Railway customDomains
   6.3 不存在则 customDomainCreate
   6.4 读取 status.dnsRecords 与 verificationDnsHost / verificationToken
   6.5 Cloudflare DNS upsert CNAME 与 Railway ownership TXT
   6.6 保存 domainStatus
7. 创建 project token
8. 部署源码
9. 等待 Railway deployment success
10. provider URL 健康检查
11. public URL 健康检查
12. Umami website domain 绑定 public domain
13. 用户侧展示 public URL
```

### 9.2 重新部署

重新部署不重新生成域名。

流程：

1. 读取已有 `publicDomain`。
2. 若 `domainStatus=active`，直接复用。
3. 若 custom domain 或 DNS 缺失，补齐。
4. 不删除旧域名。
5. 不生成新域名。

### 9.3 回滚

回滚只切换 Railway deployment，不改域名。

## 10. DNS 写入策略

Cloudflare 写入以 Railway 返回的域名验证要求为准，不手写固定记录。

规则：

1. `recordType=CNAME`：
   - `name` 使用 Railway 返回的 `fqdn`。
   - `content/value` 使用 Railway 返回的 `requiredValue`。
   - `proxied=false`。
2. Railway ownership `TXT`：
   - `name` 使用 Railway 返回的 `verificationDnsHost`，若未带根域名则补齐 `.oneceo.space`。
   - `content/value` 使用 Railway 返回的 `verificationToken`。
   - `proxied` 不适用。
3. 若同名同类型记录已存在：
   - 内容一致：保持不变。
   - 内容不同且由 OneCEO 管理：更新。
   - 内容不同且不是 OneCEO 管理：标记 `repair_required`，不覆盖。

识别 OneCEO 管理记录的方式：

- `comment` 包含 `managed-by=oneceo deploymentProjectKey=<projectKey>`。
- 或 metadata/tag 支持时写入等价元数据。

## 11. 状态机

```text
unconfigured
  -> creating_custom_domain
  -> pending_dns
  -> pending_certificate
  -> active
```

异常路径：

```text
creating_custom_domain -> failed
pending_dns -> failed | repair_required
pending_certificate -> failed
active -> repair_required
```

状态含义：

- `unconfigured`：尚未创建 OneCEO 域名。
- `creating_custom_domain`：正在向 Railway 创建 custom domain。
- `pending_dns`：Railway 已返回 DNS 要求，Cloudflare 正在写入或等待传播。
- `pending_certificate`：DNS 已可解析，等待 Railway 证书签发。
- `active`：`https://<project-slug>.oneceo.space` 可访问。
- `failed`：自动配置失败，可重试。
- `repair_required`：发现记录冲突、Railway custom domain 丢失、Cloudflare 权限不足等需要修复的状态。

## 12. 用户态展示规则

### 12.1 API 返回

用户态 API 新增或明确使用：

```ts
publicUrl?: string;
publicDomain?: string;
domainStatus?: string;
domainStatusMessage?: string;
```

用户态 API 不返回 Railway URL 到：

- `latestUrl`
- `latestStaticUrl`
- `domains`
- 当前 deployment item 的 `url` / `staticUrl`

如果必须兼容旧字段：

- `latestStaticUrl = publicUrl`
- `domains = [publicUrl]`
- Railway provider URL 只出现在 `providerDebug` 或管理后台专用接口。

### 12.2 发布与访问页面

展示：

- `https://<project-slug>.oneceo.space`
- 域名状态
- 打开网站按钮

不展示：

- `*.up.railway.app`
- Railway project / service / environment 细节

### 12.3 Altus 回复

Altus 回复中的部署地址必须来自 `publicUrl`。

当 public domain 未生效：

```text
网站已部署完成，OneCEO 域名正在配置中。配置完成后将通过 https://xxx.oneceo.space 访问。
```

禁止使用 Railway URL 兜底展示。

## 13. Umami 绑定规则

Umami website 的 domain 必须使用 `publicDomain`：

```text
domain = <project-slug>.oneceo.space
```

注入配置：

```js
window.__ONECEO_ANALYTICS__ = {
  publicDomain: "<project-slug>.oneceo.space",
  ...
}
```

环境变量：

```text
VITE_PUBLIC_DOMAIN=<project-slug>.oneceo.space
```

部署前生成 Umami runtime config 时，域名选择顺序必须是：

1. 本次部署面板已经解析出的 public URL。
2. `account.publicUrl` / `account.publicDomain`。
3. 已保存的 analytics domain。
4. Railway service domain 仅作为最后兜底，不能在 oneceo.space 已存在时优先使用。

如果已有 Umami website 的 `websiteName` 或 `domain` 仍包含 `railway.app`，下一次 live refresh 必须重新按 oneceo.space 更新绑定，避免管理面板继续显示供应商域名。

验收时以 public URL 访问页面，再确认 Umami 数据增长。

## 14. 老部署迁移

老部署不立即批量重绑，避免造成额外 Railway/Cloudflare 调用和潜在域名冲突。

迁移触发点：

1. 用户打开发布与访问页面并触发后台同步。
2. 用户点击刷新结果。
3. 用户重新部署。
4. 后台 deployment sync backlog 扫描到缺失 public domain。

迁移流程：

1. 读取现有 Railway service / environment。
2. 补建 `publicDomain`。
3. 写 Cloudflare DNS。
4. public URL active 后替换用户态展示。
5. 保留 Railway service domain 作为内部 provider URL。

## 15. 失败与恢复

### 15.1 Cloudflare 配置缺失

表现：

- `CLOUDFLARE_API_TOKEN` 或 `CLOUDFLARE_ZONE_ID` 缺失。

处理：

- 不阻断 Railway 部署。
- `domainStatus=failed`。
- 用户态显示“默认域名配置失败，请稍后重试”。
- 不展示 Railway URL。

### 15.2 DNS 记录冲突

表现：

- 同名同类型记录已存在，但内容不是 Railway 要求值。

处理：

- 如果记录不是 OneCEO 管理，不覆盖。
- `domainStatus=repair_required`。
- 管理后台展示冲突记录。

### 15.3 Railway custom domain 丢失

处理：

- 自动重建 custom domain。
- 重新写入 Cloudflare DNS。

### 15.4 证书长时间未签发

处理：

- 后台继续同步。
- 用户态显示“域名证书配置中”。
- 不将主部署标记为失败。

## 16. 安全边界

1. Cloudflare token 只保存在 API 进程环境变量，禁止进入 sandbox。
2. Sandbox 环境变量过滤规则继续拦截 `CF_*`、`CLOUDFLARE_*`。
3. Altus / OpenCode / agent 工具不直接拿 Cloudflare token。
4. 所有 DNS 修改由后端服务完成。
5. 只有 OneCEO 托管域名进入用户态上下文。

## 17. 验收条件

### 17.1 新部署

- 新部署完成后，用户看到的唯一访问入口是 `https://xxx.oneceo.space`。
- 发布与访问页面不出现 `.railway.app`。
- Altus 最终回复不出现 `.railway.app`。
- `GET /api/task-creation/sessions/:sessionId/deployment` 用户态响应不出现 `.railway.app`。
- `https://xxx.oneceo.space` 返回应用页面。
- Umami website domain 是 `xxx.oneceo.space`。
- 通过 `xxx.oneceo.space` 访问页面后，Umami 统计增长。

### 17.2 重新部署

- 域名不变化。
- 重新部署后 `xxx.oneceo.space` 指向新版本。
- Umami websiteId 不变化。

### 17.3 老部署迁移

- 老部署刷新后自动补建 `xxx.oneceo.space`。
- 迁移完成后用户侧不再显示 Railway URL。
- Railway URL 仍可在管理后台调试信息中查看。

### 17.4 失败场景

- Cloudflare token 缺失时，部署主链不崩溃。
- DNS 冲突时不覆盖非 OneCEO 管理记录。
- 证书未完成时不将部署误判为失败。

## 18. 实施阶段

### 阶段 1：文档与配置

- 确认本方案。
- 在生产环境补齐 Cloudflare env。
- 明确 `oneceo.space` zone ID。

### 阶段 2：后端域名服务

- 新增 `cloudflare-dns-service.ts`。
- 新增 `deployment-domain-service.ts`。
- 扩展 deployment config 字段。
- 添加单元测试覆盖 DNS upsert、状态机、冲突处理。

### 阶段 3：部署链路接入

- `platform-deployment-account-service.ts` 创建服务后自动绑定 public domain。
- `task-session-deployment-runtime-service.ts` 拆分 provider/public reachability。
- `railway-deployment-service.ts` 输出 public URL。

### 阶段 4：用户态展示收敛

- 发布与访问页面只显示 public URL。
- Altus 回复只使用 public URL。
- 用户态 API 过滤 provider URL。

### 阶段 5：Umami 对齐

- Umami domain 改为 public domain。
- 注入配置写入 public domain。
- 真实访问后验证统计增长。

### 阶段 6：迁移与回归

- 老部署懒迁移。
- 跑真实部署 e2e。
- 验证 HTML / Vite / Node / Python / PHP / Java 中至少核心子集不会因为域名接入破坏部署。
