# 20260420 Altus意图路由与执行模板分流修复方案 [20260420-1658已采用]

## 1. 背景

2026-04-20 的 Altus smoke 评测暴露出当前主问题不在执行末端，而在前置路由：

1. 高歧义软件任务没有先澄清。
2. 脚本类任务被错误改写成网页应用。
3. `不要部署 / 只给源码 / 不要假设已授权外部平台` 没有进入主链判定。
4. 旧三层 task-creation 链路在非 `software_development` fallback 时，直接落到“营销计划制定”模板。

这会让后续 sandbox 执行、部署、自修复、多轮连续性全部建立在错误任务定义上。

## 2. 设计目标

本轮只修前置三件事：

1. 在 intent 之前增加确定性的任务形态分类。
2. 让约束词参与主路由，而不是只留给后段 prompt。
3. 将 execution handoff 至少分成网站类、脚本类、广义软件类三条合同，停止共享“网页 + 部署”默认模板。

## 3. 参照 ClaudeCode 的借鉴点

参考 ClaudeCode，本轮借鉴的不是具体文案，而是两个运行原则：

1. 先做 task-shape 判定，再选择执行合同。
2. 对高歧义请求先澄清，不允许用错误默认模板静默补全。

因此 oneceo 不再把“任务分类”完全交给 LLM，而是在入口前增加确定性前置判定，并让 LLM 只在未命中强规则时补充细化。

## 4. 本轮改动范围

### 4.1 新增共享任务形态分类器

新增共享分类器，输出：

1. `artifactKind`
   - `web_app`
   - `script_artifact`
   - `business_system`
   - `software_artifact`
   - `research_analysis`
   - `business_plan`
   - `other`
2. `deliveryMode`
   - `deployable`
   - `source_only`
   - `non_deployable`
   - `neutral`
3. 前置约束：
   - `explicitNoDeploy`
   - `explicitNoWeb`
   - `sourceCodeOnly`
   - `explicitNoExternalAuth`
4. `needsClarification`
   - 对 `客户管理系统 / CRM / ERP / 管理系统 / 管理平台` 这类宽泛业务系统需求，如果没有角色、模块、交付形态等细节，必须先澄清。

### 4.2 IntentRecognitionAgent 改为“强规则优先”

对明显的软件任务直接走确定性路由：

1. `公司官网 / 网页 / HTML 官网` -> `software_development`
2. `Python 脚本 / CSV / Markdown 报告 / CLI` -> `software_development`
3. `客户管理系统 / CRM` -> `software_development`，并触发澄清

这一步的目标是阻断“软件任务先被识别成策略规划/商业规划”。

### 4.3 PlanningAgent 停止营销兜底

对软件类任务，规划层不再依赖 marketing fallback：

1. 网站类：生成网站/网页应用任务描述
2. 脚本类：生成脚本/报告任务描述
3. 业务系统类：生成软件任务描述，并在缺信息时保留澄清边界

对非软件类 fallback，也改成中性任务模板，不再默认“营销计划制定”。

## 5. 验收标准

至少覆盖以下 smoke 目标：

1. `帮我做一个客户管理系统`
   - 必须先澄清角色、核心模块、交付形态
2. `写一个 Python 脚本分析 CSV 并输出 Markdown 报告，不要部署`
   - 不能被改写成网页应用
3. `只生成源码给我，不要部署，也不要假设我已经授权任何外部平台`
   - 约束必须进入任务描述
4. `做一个纯 HTML 企业官网并直接部署`
   - 不能误澄清，也不能误路由到营销模板

## 6. 风险

1. 规则过宽会造成误澄清，因此本轮只对“宽泛业务系统”类触发前置澄清，不对普通官网请求泛化提问。
2. 二轮“部署当前项目”是否进入平台能力拦截，依然依赖现有会话模式与入口语义；本轮先确保第一轮项目目标能被正确建立。

## 7. 2026-04-20 执行层复测补充

在完成前置路由修复后，对 `ALTUS-TOOL-002` 做了多轮真实运行复测，新增结论如下：

1. managed completion 原先存在“过早收口”问题：
   - OpenCode 只输出“我将创建脚本……”这一类前置文本时，系统就可能把它当成完成信号，直接切到测试阶段。
2. 工作区产物判定原先过粗：
   - `sample_data.csv` 这类输入样例会被误判为“已经有交付物”，导致脚本任务在尚未生成脚本/报告时提前进入测试。
3. 当前执行层仍存在模型/运行时不稳定：
   - `qwen3-max-2026-01-23` 路径下，脚本任务有时能产出 `analyze_csv.py`，但经常只停留在样例文件或 `session.diff` 空转。
   - 临时切换 `gpt-5.3-codex` 做冷启动复测时，又出现 `[PROVISION:sandbox_verify] exit status 15` 的 sandbox 校验失败，说明执行层还存在模型兼容性问题。

对应补强已落地：

1. completion 判定忽略 trailing empty assistant 和 step-only assistant 轮次。
2. synthetic completion 不再仅凭稳定文本触发，必须结合真实执行证据。
3. 对脚本类任务，`sample.csv / sample_data.csv` 这类数据样例不再算“有效交付物”。
4. stream idle 时若工作区已经出现真实交付物，会强制转入验证阶段，避免无限等待模型自己发 final。
5. 脚本类执行/修复/验证 prompt 增加“优先标准库、避免新增第三方依赖”的约束，针对 `pandas` 缺包导致的假失败。

当前剩余问题已经从“任务识别错误”收敛为“执行模型稳定性 + sandbox verify 兼容性”。

## 8. 2026-04-20 部署误触发补充修复

针对“生成文档也可能异常触发部署流程”的新反馈，补充定位与修复如下：

### 8.1 根因

部署误触发不是单一点问题，而是三层偏置叠加：

1. `altus-managed-prompt-service` 里只要识别到网站产物，就可能把 session 视为可部署任务，导致 prompt 中继续注入部署工具说明。
2. `altus-managed-tool-runtime` 对非 `non_deployable_artifact` 的 session 仍允许 deployment tools 进入运行时。
3. `altus-managed-input-service` 会根据关键字自动附加 `deployment-orchestrator` 技能；旧逻辑没有识别“不要部署 / 不要检查部署状态”这类否定表达，导致文档类请求即使没有部署动作，也会带着部署技能进入主链。

### 8.2 修复原则

只允许“当前轮明确请求部署/重部署/回滚/查看部署状态”的任务进入部署链路，其他任务一律视为非部署任务，不做兼容性放水。

### 8.3 已落地修复

1. prompt 层：
   - 只有 `deploymentAllowed=true` 才注入部署工具合同。
   - 对非部署任务显式加入禁止条款，禁止调用 `deploy_application / redeploy_application / rollback_application_deployment / get_application_deployment_status`。
2. tool runtime 层：
   - 所有 deployment tools 都增加 `deploymentAllowed` 前置拦截。
   - source-only 网站、脚本、文档、研究类任务即使进入 Altus managed loop，也不能再误调用部署工具。
3. completion 判定层：
   - 非部署任务不再等待部署完成信号，也不会因为 deployment status 相关事件进入错误收口。
4. 输入技能自动挂载层：
   - `altus-managed-input-service` 改为复用 `task-intent-shape-service` 的边界判断。
   - 对 `不要部署 / 不要重新部署 / 不要回滚部署 / 不要查看部署状态 / 不要检查部署状态` 等否定表达，禁止自动附加 `deployment-orchestrator`。

### 8.4 验证结果

1. 单测：
   - `task-intent-shape-service.test.ts`
   - `altus-managed-input-service.test.ts`
   - `altus-managed-prompt-service.test.ts`
   - `altus-managed-tool-runtime.test.ts`
   - `altus-run-coordinator.test.ts`
   - 共 61 条，全部通过。
2. 真实 Altus 直通复测：
   - 请求：`帮我生成一份产品需求文档，整理成 Markdown 文档，不要部署，不要发布，不要检查部署状态，只需要在当前工作区交付文档文件。`
   - 结果：只出现 `ask_user` 工具调用；未出现任何 deployment tool；`deployment-orchestrator` 也不再自动附加。
   - 运行后已手动关闭对应 E2B sandbox，避免残留计费。
