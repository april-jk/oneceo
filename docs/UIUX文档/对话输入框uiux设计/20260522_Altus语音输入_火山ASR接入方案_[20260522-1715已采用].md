# 20260522 Altus语音输入 火山ASR接入方案 [20260522-1715已采用]

## 背景

当前 `oneceo` 在对话输入框右下角已经有麦克风按钮占位，但没有真正实现语音输入能力。  
这次目标不是做完整的“语音秘书系统”，而是给 Altus / task-creation 主输入框补齐一条最短、稳定、可直接上线迭代的语音转文字链路。

用户明确要求：

1. 使用字节跳动 / 火山引擎语音识别 API。
2. 参照 `AgentLine` 项目里已经实现过的语音转文字逻辑。
3. 在 `oneceo` 中实现“通过语音输入直接安排任务”。

## 设计原则

1. 不把 `AgentLine` 整套 Voice Secretary 搬进来。
2. 只复用已经验证过的“录音 + 火山 ASR”实现方式。
3. 不新造第二套任务编排入口。
4. 语音输入的最终结果必须回到 `oneceo` 现有发送链路。
5. 配置方式遵循 `oneceo` 现有规则，优先走 `.env` / `process.env`，不引入 `AgentLine` 的 server settings 页面依赖。

## 最终采用方案

### 1. 识别提供方策略

本轮采用“双提供方 + 明确互斥”的方案：

- 默认：浏览器原生语音识别
- 可选：火山引擎语音识别
- 切换入口：设置页

原则：

- 浏览器模式和火山模式不能同时工作，避免重复识别、重复回填和调试歧义
- 默认优先浏览器模式，直接解决 Chrome / Edge 一类浏览器可用但后端链路偶发失败时的可用性问题
- 只有用户明确切换到火山模式时，才启用录音上传和服务端转写

### 2. 浏览器模式

浏览器模式直接使用原生 `SpeechRecognition / webkitSpeechRecognition`：

- 点击麦克风后调用浏览器原生语音识别
- 停止录音后取浏览器返回的最终文本
- 将文本回填到输入框
- 不自动发送，用户可自行修改后再点发送

原因：

- 这是最短路径，Chrome / Edge 场景下不依赖第三方接口即可完成识别
- 规避“后端识别服务暂时不可用”时影响基础输入能力
- 符合用户对“先识别、再人工确认是否发送”的交互要求

### 3. 火山模式

火山模式沿用 `AgentLine` 已验证的录音上传思路：

- 浏览器点击麦克风后请求麦克风权限
- 使用 `AudioContext + ScriptProcessorNode` 采集音频
- 前端直接转为 `16k / mono / wav`
- 停止录音后将 blob 上传给 `oneceo` API

### 4. 后端转写方式

火山模式使用 task-creation 域内接口：

- `POST /api/task-creation/voice/transcribe`

职责：

- 接收前端上传的 `audio` 文件
- 使用火山引擎 ASR 转写
- 返回最终文本与置信度

### 5. 火山引擎接入方式

后端直接参照 `AgentLine/packages/server/src/voice-secretary/volcengine-speech.ts`：

- 支持 HTTP flash endpoint
- 支持 WebSocket `bigmodel_nostream`
- 先保留 `AgentLine` 中已经验证过的鉴权与协议处理方式

### 6. oneceo 里的发送行为

语音转写成功后：

- 将识别文本回填到当前输入框
- 若输入框已有内容，则与已有内容按换行拼接
- 不自动发送
- 用户手动编辑确认后，再走现有发送逻辑

也就是说：

- 语音输入只是“文本输入来源”发生变化
- Altus / task creation 主流程本身不改语义
- “发送动作”仍然只由用户点击发送按钮触发

## 环境变量方案

`oneceo` 本次采用专用环境变量：

- `ONECEO_VOLCENGINE_ASR_APP_ID`
- `ONECEO_VOLCENGINE_ASR_ACCESS_TOKEN`
- `ONECEO_VOLCENGINE_ASR_SECRET_KEY`
- `ONECEO_VOLCENGINE_ASR_ENDPOINT`

原因：

- 与 `oneceo` 现有 `.env` 体系保持一致
- 不把 `AgentLine` 的后台设置系统移植进来
- 本地 / staging / product 可以按 `oneceo` 现有环境分层加载

## 风险与边界

1. 浏览器模式依赖当前浏览器是否支持原生语音识别；Safari 等环境不一定可用
2. 火山模式依赖麦克风权限、录音能力和后端 ASR 配置同时正常
3. 两种模式都必须遵守“识别后只回填，不自动发送”的交互，避免误识别直接进入任务链路

## 验证方式

1. 本地登录后进入 `/new-task`
2. 在设置页确认当前语音识别方式，默认应为“浏览器原生语音识别”
3. 点击输入框右下角麦克风
4. 说一句完整任务，例如“帮我做一个产品发布页”
5. 再点一次麦克风结束录音
6. 观察是否：
   - 浏览器模式下可直接拿到识别文本并回填输入框
   - 火山模式下成功调用后端转写并回填输入框
   - 两种模式都不会自动发送
   - 用户手动点击发送后，任务链路再正常启动

## 采用结论

采用该方案进入实现。核心原则是：

> 默认提供浏览器原生语音识别，保留可切换的火山 ASR 路径；无论哪种模式，oneceo 都只负责“语音转文字并回填输入框”，发送动作必须由用户手动确认。
