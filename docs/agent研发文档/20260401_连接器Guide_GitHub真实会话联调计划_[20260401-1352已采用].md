## 1. 目标

本联调只验证 GitHub connector guide 的真实会话闭环，不扩展到 Supabase / Vercel。

本次必须验证的事实只有四条：

1. 真实会话 attach GitHub connector 后，`task_session_connector_guides` 会生成 GitHub guide 生效记录
2. Altus 启动 managed run 时，system prompt 会注入：
   - `# Connector MCP Instructions`
   - `# Relevant Connector Guides`
3. 注入内容来自 GitHub connector guide published revision，而不是现有 skills 模块
4. 整个过程在日志和数据库里都有证据，能形成可复查链路

## 2. 不验证的范围

本次不做：

1. runtime preflight / blocking rules 执行拦截
2. Supabase / Vercel guide 联调
3. guide 文本效果优劣评估
4. skill 模块回归测试的全量覆盖

## 3. 前置条件

联调前必须满足：

1. `apps/api` 已重启并加载当前代码
2. `apps/admin_management` 已启动，可打开“连接器 Guide”页面
3. GitHub connector 当前可在真实会话里完成 attach
4. 数据库连接当前稳定，不出现连续 `ECONNRESET`

若第 4 条不满足，本轮联调暂停，先排数据库稳定性。

## 4. 证据源

联调只接受以下证据：

1. 浏览器真实操作结果
2. API 本地日志
3. 数据库查询结果
4. 管理后台页面显示
5. session detail / recent / run 相关接口结果

单一证据不能作为闭环结论。

## 5. 联调对象

固定使用一个新的真实 task session。

固定验证 connector：

1. `github`

固定验证 guide：

1. `connector_guide_policies.connector_key = 'github'`

## 6. 联调步骤

## 6.1 步骤一：确认 GitHub guide 已发布

操作：

1. 打开 admin_management 的“连接器 Guide”
2. 找到 `github` policy
3. 确认存在 published revision

需要记录：

1. policy id
2. published revision id
3. published revision version number
4. `serverInstructionsMarkdown` 前 1 段摘要
5. `guideReminderMarkdown` 前 1 段摘要

判定：

1. 若不存在 `github` policy，联调失败
2. 若存在 policy 但无 published revision，先停止联调，补发布

## 6.2 步骤二：创建新的真实 task session

操作：

1. 在 oneceo 前端创建一个新的 task session
2. 记录 `taskSessionId`

需要记录：

1. `taskSessionId`
2. 会话标题
3. 创建时间

判定：

1. 新会话创建成功，且 session 详情接口可读

## 6.3 步骤三：在该会话 attach GitHub connector

操作：

1. 打开该 session 的 connectors 设置
2. 选择 GitHub connector
3. 完成 attach

需要记录：

1. 使用的 `profileId`
2. attach 后前端显示的 GitHub 状态
3. attach 后 `/api/task-creation/sessions/:id/connectors` 返回内容中 GitHub 这一项

判定：

1. GitHub connector 的 `attached = true`
2. `desiredState = attached`
3. profile 与 connectorKey 对应正确

## 6.4 步骤四：检查 session guide 落库

操作：

1. 查询 `task_session_connector_guides`
2. 过滤 `task_session_id = 当前 taskSessionId`

需要记录：

1. 是否存在 `connector_key = github`
2. 对应 `policy_id`
3. 对应 `revision_id`
4. `trigger_mode`
5. `resolved_at`

判定：

1. 必须存在且仅存在一条 `github` guide 生效记录
2. `policy_id` 必须等于步骤一的 GitHub policy
3. `revision_id` 必须等于步骤一的 published revision

## 6.5 步骤五：触发一次真实 managed run

操作：

1. 在当前 session 发送一条明确会触发 Altus 的消息
2. 消息建议使用：
   - “请读取当前 GitHub 连接器可访问的仓库范围，并告诉我你准备如何使用它”

需要记录：

1. `runId`
2. run 创建时间
3. 该 run 使用的 connector 快照 / session context

判定：

1. run 成功启动
2. 没有因为 connector guide 注入导致 run 启动失败

## 6.6 步骤六：检查 system prompt 注入

操作：

1. 从 run 侧日志、持久化消息、调试输出或可用接口中，拿到本次实际使用的 composite system prompt 证据

优先级：

1. 若现有日志已输出 system prompt，直接取日志
2. 若无直接日志，则在不破坏主流程的前提下增加临时调试日志后重试

需要记录：

1. 是否出现 `# Connector MCP Instructions`
2. 是否出现 `# Relevant Connector Guides`
3. 是否出现 `## github`
4. 是否包含步骤一 published revision 中的关键文本片段

判定：

1. 两个 section 都必须出现
2. section 内必须能定位到 GitHub guide 文本
3. 文本来源必须和 published revision 一致

## 6.7 步骤七：检查日志顺序

操作：

1. 查看 `apps/api` 日志
2. 关注 session connector attach、guide 重算、run 启动三段日志

需要记录：

1. attach 行为的时间点
2. guide 重算的时间点
3. run 启动的时间点

判定：

1. attach 发生后，再发生 guide 生效，再发生 run prompt 构建
2. 不允许 run 先于 guide 生效

## 7. 需要补充的调试日志

若现有日志不足以证明第 6.6 和 6.7 步，可在联调前补以下临时日志：

1. `connectorGuideService.recomputeSessionGuides(taskSessionId)`：
   - 打印 `taskSessionId`
   - 打印命中的 connector keys
   - 打印生成的 `policyId/revisionId`

2. `connectorGuideService.buildPromptSections(taskSessionId)`：
   - 打印 `taskSessionId`
   - 打印命中的 session guides 数量
   - 打印是否生成 `instructionsSection/reminderSection`

3. `altus-run-coordinator.ts` 在构建 `compositeSystemPrompt` 前：
   - 打印 `runId`
   - 打印 guide section 是否非空

这些日志只用于联调，联调完成后要确认是否保留。

## 8. 结果输出格式

联调完成后输出必须包含：

1. 会话信息
   - `taskSessionId`
   - `runId`

2. guide 落库结果
   - `policyId`
   - `revisionId`
   - `resolvedAt`

3. prompt 注入结果
   - 是否命中 `Connector MCP Instructions`
   - 是否命中 `Relevant Connector Guides`
   - 匹配到的 GitHub 文本片段

4. 日志结论
   - attach -> guide resolve -> run build 顺序是否成立

5. 最终结论
   - 成功
   - 失败
   - 失败卡点

## 9. 成功标准

只有同时满足以下四条，才算本轮联调成功：

1. GitHub connector 在真实 session 内 attach 成功
2. `task_session_connector_guides` 存在 `github` 生效记录，且 `policyId/revisionId` 指向当前 published revision
3. 日志中出现 `CONNECTOR_GUIDE_PROMPT_SECTIONS_READY`，且 `instructionConnectorKeys/reminderConnectorKeys` 包含 `github`
4. 日志中出现 `ALTUS_RUN_PROMPT_READY`，且 `hasConnectorGuideInstructions=true`、`hasConnectorGuideReminders=true`

## 10. 失败处理原则

如果失败，只允许归类到以下之一：

1. attach 未成功
2. session guide 未落库
3. prompt 未注入
4. 数据库 / 环境不稳定导致证据缺失

禁止在联调中引入临时兼容逻辑或绕过真实会话链路。
