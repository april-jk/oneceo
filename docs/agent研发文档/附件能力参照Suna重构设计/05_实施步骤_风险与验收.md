## 2. 明确不采用的方案

### 2.1 不继续沿用 `.attachments`

原因：

- 与 `suna` 不一致
- 用户和 Agent 心智差
- 会持续制造隐藏目录语义

### 2.2 不继续沿用“前端先上传、再拼 prompt”

原因：

- 输入协议分裂
- 失败处理复杂
- Agent 看到的是自然语言说明而不是标准附件协议

### 2.3 不做兼容性双主链路长期并存

原因：

- 这会让后续消息处理、UI 展示、Prompt assembly 永远存在双套规则
- 与仓库对“不要补丁式方案”的要求冲突

## 3. 主要风险

### 3.1 风险：Hook 改造范围较大

原因：

- `useTaskCreationAgent.ts` 目前承担了较多职责

控制方式：

- 将附件输入提交逻辑集中到一个新的 client API 和 dispatch service
- 不把附件处理散落在多个组件里

### 3.2 风险：Prompt 注入过长

原因：

- 文本类附件可能很大

控制方式：

- 单文件解析内容截断
- 只注入可读摘要，不注入全量原文

### 3.3 风险：文件名冲突与引用不一致

原因：

- 用户可能多次上传同名文件

控制方式：

- 以服务端最终写入路径为准
- canonical 引用块永远写实际路径

### 3.4 风险：发送失败后前端状态不一致

原因：

- 附件上传与消息持久化属于一组复合动作

控制方式：

- 由统一输入接口返回结果
- 前端只根据接口结果统一切换状态

### 3.5 风险：首条消息无 session 时出现双入口竞争

原因：

- 当前前端先 `createTaskCreationSession(...)` 再 `startTaskCreationManagedRun(...)`
- 如果新增附件输入接口但不收敛入口，会同时存在两套 run 启动主链路

控制方式：

- 统一由 `POST /api/altus-managed/inputs` 作为 managed 用户输入唯一入口

### 3.6 风险：附件解析结果只存在请求期内存，导致恢复时丢失

原因：

- prompt assembly 在 run 重试、刷新、再次执行时需要稳定来源

控制方式：

- 把截断后的 `attachmentContext` 持久化进 `user_input.metadata`
- prompt service 只从消息存储读取，不依赖请求期对象

## 4. 验收场景

### 4.1 本地文件

1. 添加 `md / pdf / png / ts` 等允许类型文件。
2. 发送后消息卡片显示附件。
3. Sandbox 中能在当前 session 的 `${workspaceRoot}/uploads` 看到实际文件。

### 4.2 重名文件

1. 连续上传两次同名文件。
2. 第二次不覆盖第一次。
3. 消息中显示实际重命名后的路径。

### 4.3 远程链接导入

1. 通过网站 / Google Drive / OneDrive 导入公开文件。
2. 导入后与本地文件走同一套发送链路。

### 4.4 粘贴图片

1. 从剪贴板粘贴图片到输入框。
2. 图片作为待发送附件出现。
3. 发送后消息正确展示附件。

### 4.5 文本类附件上下文

1. 上传 Markdown/代码文件。
2. Agent 在第一轮执行中能够理解文件内容，而不是只看到路径。

### 4.6 失败场景

1. 文件超限。
2. 格式不支持。
3. 上传过程中断。
4. 前端能明确展示失败，不出现“消息已发出但附件丢失”的假成功。

## 5. 最终验收定义

满足以下条件才算本次附件能力设计落地完成：

1. 用户输入附件已成为统一消息协议的一部分。
2. 文件统一落到当前 session 的 `${workspaceRoot}/uploads`。
3. managed run 能消费文本类附件内容。
4. 前端存在清晰可见的附件状态机。
5. 远程导入、本地选择、拖拽、粘贴至少四类输入方式能够统一工作。
6. 不再依赖“自然语言附件列表拼 prompt”的旧方案。
