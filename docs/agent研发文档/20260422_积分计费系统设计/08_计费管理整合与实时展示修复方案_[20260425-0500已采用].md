# 08 计费管理整合与实时展示修复方案 [20260425-0500已采用]

## 1. 背景

本方案来源于 2026-04-25 管理后台与用户前端测试反馈，目标是在不改变积分计费主链路前提下，解决管理端功能重叠、计费数据下钻不足、定价配置不可编辑、缓存命中展示异常，以及用户端积分变化不实时的问题。

本方案已于 2026-04-25 05:00 根据用户确认采用，后续代码实现以本方案为准。

## 0. 用户确认结论

1. 计费管理中完全移除「用户积分」主 Tab，用户积分详情统一整合到用户管理详情。
2. 用户端消费记录按 session 聚合展示。
3. qwen3 / 通义千问缓存计费规则以官方接口文档为准：显式缓存创建按输入 token 125%，显式缓存命中按 10%，隐式缓存命中按 20%；OpenAI-compatible 优先读取 `usage.prompt_tokens_details.cached_tokens` 与 `usage.prompt_tokens_details.cache_creation_input_tokens`，DashScope 兼容读取 `usage.cached_tokens`。
4. 定价更新立即对新会话生效，同时支持设置生效时间。

## 2. 问题归类

### 2.1 管理员界面

1. 「用户积分」与「使用明细」功能重叠，需要将使用明细下钻整合到用户积分详情中。
2. 用户积分详情中的「积分历史」与「使用明细」概念重叠，需要拆成：
   - 使用明细：会话/对话消费、token、积分消耗。
   - 获取历史：充值、活动、后台调整或其他获得积分的记录。
3. 用户积分栏缺少索引、搜索、筛选能力。
4. 对话管理、用户管理需要和计费管理深度绑定：
   - 会话详情展示积分与 token 消耗。
   - 用户详情整合用户积分详情。
   - 整合后可减少计费管理模块内重复的用户积分入口。
5. 定价配置需要管理员可随时更改。
6. 新建定价时 provider 只有 openai、anthropic，不符合实际模型使用情况，需要从项目当前使用模型中读取候选。
7. 缓存比例计费配置需要整合到定价配置。
8. qwen3 后台未显示缓存命中，需要查明并修复。
9. 平台统计 UI 不符合管理后台使用习惯，需要优化信息架构。

### 2.2 用户前端

1. 消耗积分后余额不会实时更新，需要刷新浏览器。
2. 会话界面没有实时展示本会话积分消耗与剩余积分。
3. 用户消费记录不应直接暴露模型名，应按 session / 对话展示消费。

## 4. 设计原则

1. 管理后台以「用户」和「会话」作为计费下钻主入口，计费管理只保留平台级配置与统计。
2. 用户前端只展示用户能理解的消费对象：session、对话、时间、积分，不直接暴露模型名。
3. 定价配置与缓存比例配置合并管理，避免同一模型的价格信息分散。
4. qwen3 缓存命中修复必须基于实际上游响应字段，不做盲目兼容或兜底逻辑。
5. 平台统计优先满足管理员对成本、异常、高消耗对象的快速判断，不堆叠重复指标。

## 5. 管理端整合方案

### 5.1 计费管理页面重组

计费管理保留以下 Tab：

1. **平台统计**
2. **定价配置**
3. **计费审计**（可选，保留明细查询但不作为用户积分主入口）

原「用户积分」不再作为独立主工作台，完全移除该主 Tab。用户积分详情统一进入用户管理详情中的「积分」Tab。

### 5.2 用户管理详情整合用户积分详情

在用户详情中新增「积分」Tab：

1. 余额概览：当前余额、累计获取、累计消耗、最近消费时间。
2. 使用明细：按 session / 对话聚合展示积分消耗、token 消耗、时间。
3. 获取历史：充值、活动赠送、后台调整等入账记录。
4. 管理操作：后台加减积分、备注、操作人、操作原因。

#### 5.2.1 用户详情积分入口与调整操作修正

根据 2026-04-25 后续反馈，用户管理详情中的积分能力必须满足：

1. 从计费管理、使用明细或其他模块点击真实存在的用户进入用户管理时，如果来源是计费场景，应直接打开用户详情的「积分」Tab，而不是落到「概览」Tab。
2. 用户详情弹窗不能仅因为当前用户列表筛选结果中没有该用户就关闭详情；跨模块传入的真实用户 ID 应优先通过详情接口加载。
3. 「积分」Tab 内必须提供调整用户积分入口，管理员可以输入正整数积分与调整原因。
4. 调整成功后必须刷新用户计费详情与用户列表摘要，避免余额展示滞后。
5. 当前接口语义为人工增加积分；如后续需要扣减积分，需单独补充负向调整的权限、原因与审计规则。

「使用明细」与「获取历史」必须分离：

- `token_usage_logs` 主要服务于使用明细。
- `credit_transactions` 中正向入账记录服务于获取历史。
- 后台调整需要明确记录 transaction type 与备注。

#### 5.2.2 用户详情积分栏账本式布局修正

根据 2026-04-25 后续界面反馈，用户详情「积分」Tab 需要从多卡片堆叠调整为单块账本式布局：

1. 顶部突出当前余额，累计获得、累计消费、最后充值作为次级指标横向排列。
2. 人工调整区压缩为紧凑表单行，不再复用用户列表筛选网格样式。
3. 使用明细与获取历史改为行列表，金额、tokens、调用次数和时间按列对齐，便于管理员纵向扫读。
4. 支出金额使用负向视觉，入账金额使用正向视觉；session 标题仍可跳转对话详情。
5. 时间默认使用紧凑相对时间，完整时间通过 hover title 保留。

### 5.3 对话管理详情整合会话计费信息

在会话详情中新增「计费」区块：

1. 本会话总积分消耗。
2. 输入 token、输出 token、缓存命中 token、缓存创建 token。
3. 按消息/调用聚合的消费列表。
4. 关联用户余额变化入口：点击跳转到该用户详情的「积分」Tab。

### 5.4 用户积分索引能力

如果保留计费管理中的用户积分索引，需要支持：

1. 按邮箱、display name、user id 搜索。
2. 按余额区间筛选。
3. 按最近消费时间排序。
4. 按余额不足、近期高消耗筛选。

## 6. 定价配置与缓存比例整合

### 6.1 定价配置可编辑

管理员可以对定价配置执行：

1. 新建模型定价。
2. 停用旧定价。
3. 创建新版本定价。

为避免历史账单被改写，不直接修改已生效历史记录。更新价格时采用「停用旧配置 + 创建新配置」方式，历史 usage 继续保留当时消耗结果。

### 6.2 新建定价的模型候选来源

新建定价时不再固定 provider 下拉为 openai、anthropic，而是从项目当前可用模型配置中读取候选：

1. 已配置的模型列表。
2. 最近实际调用过但缺少定价的模型。
3. 已有定价但停用的模型。

候选项展示字段：

- provider
- model
- 当前是否已有有效定价
- 最近调用时间

### 6.3 缓存比例配置整合

将缓存命中比例与缓存创建比例合并到模型定价表单中展示：

1. OpenAI 类模型：缓存命中折扣字段。
2. Anthropic 类模型：缓存命中折扣与缓存创建倍率字段。
3. qwen / 通义千问：显式缓存创建 125%，显式缓存命中 10%，隐式缓存命中 20%；字段解析优先使用 `usage.prompt_tokens_details.cached_tokens` / `cache_creation_input_tokens`，兼容 DashScope 的 `usage.cached_tokens`。
4. 其他 provider：必须基于该 provider 的实际计费规则配置，不默认复用 OpenAI 或 Anthropic。

当前 `07_缓存计费比例管理端可调方案_[尚未采用].md` 可并入本方案，避免缓存配置成为独立入口。

#### 6.3.1 定价配置对话框交互修正

1. 管理端表单使用百分比输入缓存比例，例如 `20` 表示按标准输入单价的 20% 计费；后端仍按千分比整数存储，由前端提交时自动转换。
2. 新建与更新模式必须区分：新建显示「新建定价配置 / 创建定价」，更新显示「更新定价配置（创建新版本）/ 保存新版本」。
3. 更新已有定价时模型名称与 provider 只读，避免管理员误以为在更新 A 模型时实际创建 B 模型定价。
4. 表单按「模型范围 / 基础定价 / 缓存计费 / 生效控制」分组，缓存计费区域必须提示“缓存比例按 provider 生效，将影响该 provider 下所有模型”。
5. qwen 系列模型在管理端统一显示为 `Qwen / 通义千问`，避免 OpenAI-compatible 调用方式与实际供应商计费规则混淆。

#### 6.3.2 定价配置列表与详情操作修正

根据 2026-04-25 反馈，定价配置页继续收敛为列表优先的信息架构：

1. 定价配置 Tab 不再展示 `sub-panel user-management-summary-strip` 计费规则摘要栏，避免在配置页顶部堆叠重复说明卡。
2. 定价配置列表的操作列只保留「详情」，禁止在列表行内直接展示「更新」「停用/删除」等破坏性或高影响操作。
3. 点击「详情」打开定价详情弹窗，弹窗内展示模型、provider、状态、生效时间、输入/输出单价、缓存命中与缓存创建比例。
4. 「更新定价」入口移动到详情弹窗内，仍沿用“创建新版本”语义，不直接改写历史账单。
5. 原「停用」操作在管理端文案统一改为「删除」，入口移动到详情弹窗内；删除后该规则不再参与新请求计费，历史账单不回写。
6. 已删除的定价规则不再显示在定价配置列表中；列表计数只统计生效中的规则。历史删除记录仅作为后端审计/历史数据保留，不作为管理员日常配置列表内容。

## 7. qwen3 缓存命中异常调查结论与修复方向

### 7.1 已确认链路

1. LLM 响应 usage 由 `llm-proxy-connector.ts` 转为 OpenAI 风格 usage。
2. `altus-run-coordinator.ts` 从 usage 中读取 `prompt_tokens_details.cached_tokens`。
3. `billingService.logTokenUsage()` 写入 `token_usage_logs.cached_prompt_tokens`。
4. 管理后台使用明细与平台统计读取该字段展示缓存命中。

### 7.2 最可能原因

qwen3 / 通义千问官方 OpenAI-compatible 返回的缓存命中字段为 `usage.prompt_tokens_details.cached_tokens`，显式缓存创建字段为 `usage.prompt_tokens_details.cache_creation_input_tokens` 或嵌套的 `usage.prompt_tokens_details.cache_creation.cache_creation_input_tokens`；DashScope 部分兼容场景可能返回 `usage.cached_tokens`。当前链路未完整归一化这些字段，导致 `cached_prompt_tokens` 落库为 0。

### 7.3 修复路径

1. 为 qwen/openai-compatible 路径定义明确的 usage parser，读取 `prompt_tokens_details.cached_tokens`、`prompt_tokens_details.cache_creation_input_tokens`、`prompt_tokens_details.cache_creation.cache_creation_input_tokens` 与 DashScope 兼容字段 `cached_tokens`。
2. 在本地测试环境捕获一次 qwen3 原始 usage 响应，用于验证官方字段与实际返回一致。
3. 增加 qwen3 缓存命中解析单元测试。
4. 验证 `token_usage_logs.cached_prompt_tokens`、管理端使用明细、平台统计同时显示正确值。

## 8. 平台统计 UI 优化方案

### 8.1 新信息架构

平台统计按管理动作分为四层：

1. 核心 KPI：积分消耗、Token 使用、活跃会话、预估金额。
2. 趋势分析：按今日小时或近 7/30 天日期聚合展示积分消费与充值趋势。
3. 排行分析：高消耗用户、高消耗会话、高消耗模型。
4. 余额结构：用饼图展示用户余额分布，便于快速识别低余额与高余额用户占比。

### 8.2 UI 调整

1. 保留今日、近 7 天、近 30 天快捷筛选。
2. 增加刷新按钮与数据更新时间。
3. Top 用户从匿名编号改为邮箱/昵称展示。
4. 模型排行改为横向条形图，避免长模型名挤压。
5. 余额分布保持饼图展示，用于表达各余额区间用户占比。
6. 移除独立的“缓存效果概览”卡片，避免平台统计页信息焦点偏离积分消耗/充值管理。
7. 增加“积分消费/充值趋势”折线图：`today` 按小时聚合，`week` / `month` 按日期聚合。
8. 增加骨架屏、空状态、错误重试入口。

### 8.3 图表视觉优化要求

1. 四类图表统一采用管理后台审计风格：克制色彩、细网格、轻量坐标轴、清晰 hover 状态。
2. 消费排行与模型使用保持横向条形图，但降低默认图表噪音：隐藏多余轴线、统一条形圆角与条宽、长标签截断。
3. 余额分布饼图使用环形图与底部图例，并在标题区补充总人数，避免管理员只看到区间而无法判断样本规模。
4. 积分消费/充值趋势使用消费红与充值绿区分，叠加轻量面积层次，但不使用高饱和大面积渐变。
5. Tooltip 统一为自定义样式，展示指标名称、数值和必要上下文，数值使用等宽数字提升核对效率。
6. 空状态统一成专用图表空态，不复用列表空态，避免图表区域在无数据时显得破碎。

### 8.4 非卡片式紧凑布局要求

1. 平台统计不再以多张独立卡片作为主结构，避免图表被割裂成松散卡片网格。
2. KPI 区使用统一指标带，四项指标在同一容器内用 1px 分隔线区分，保持紧凑审计台观感。
3. 图表区使用单一分析面板，内部以轻量分隔线划分 2×2 图表分区，不为每个图表单独创建卡片外壳。
4. 图表高度压缩到适合管理后台快速扫描的密度，优先保证比较、趋势和占比判断效率。
5. 响应式下指标带从 4 列降为 2 列再降为单列，图表面板从 2 列降为单列，并继续保留分隔线结构。

## 9. 用户前端实时展示方案

### 9.1 余额实时更新

每次会话完成一次计费落库后，用户端需要刷新当前用户 credits 状态。

最短路径：

1. 会话消息完成后调用已有 `/api/billing/credits` 刷新余额。
2. 更新 `useAuth()` 或当前全局用户状态中的 credits。
3. `CreditBadge`、设置页余额、会话积分条共用同一份状态。

### 9.2 会话界面积分动态展示

会话页展示：

1. 当前 session 已消耗积分。
2. 当前用户剩余积分。
3. 最近一次调用消耗积分。

用户前端不展示 token、模型、provider 或模型拆分明细；这些技术与成本审计信息只保留在管理后台。

会话结束或流式响应完成后调用 `/api/billing/session/:sessionId/usage` 刷新会话消耗。

### 9.3 消费记录按 session / 对话展示

用户消费记录按 session 聚合展示，不展示模型名，改为：

1. 会话标题。
2. 对话时间。
3. 消耗积分。
4. 会话入口：点击会话标题跳转到对应会话，优先打开历史视图。

模型、provider、token 细节只保留在管理后台计费审计中。

## 10. API 调整清单

### 10.1 管理端

1. 用户详情增加计费摘要接口或复用现有用户计费接口。
2. 会话详情增加 session usage 聚合接口。
3. 定价配置接口增加模型候选读取接口。
4. stats 接口增加更新时间、低余额用户数、可识别用户展示字段。

### 10.2 用户端

1. `/api/billing/credits` 保持作为余额刷新来源。
2. `/api/billing/session/:sessionId/usage` 返回用户可见的 session 聚合积分消耗，不返回 token、模型或 provider 明细。
3. `/api/billing/transactions` 返回用户可见的 session 聚合消费记录，不返回模型名、provider 或 token。

1. 修复 qwen3 usage/cache 解析，并补测试。
2. 改造用户端实时余额与 session 消耗展示。

4. 管理端用户详情整合积分详情。
5. 管理端会话详情整合计费区块。

7. 定价配置加入可编辑、模型候选、缓存比例配置。
8. 平台统计 UI 优化。

## 12. 验证标准

1. qwen3 实际产生缓存命中时，`token_usage_logs.cached_prompt_tokens > 0`。
2. 管理后台使用明细与平台统计能显示 qwen3 缓存命中。
3. 用户完成一次会话后，无需刷新浏览器即可看到余额变化。
4. 会话界面显示本 session 消耗与剩余积分。
5. 用户消费记录不出现模型名、provider 或 token，点击会话名可以进入对应会话。
6. 用户管理详情可以查看积分余额、使用明细、获取历史。
7. 会话管理详情可以查看该 session 的积分与 token 消耗。
8. 管理员可以创建新版本定价，并在同一表单管理缓存比例。
9. 新建定价时能看到当前项目实际使用模型候选。
10. 平台统计首屏能清晰展示核心成本、排行与缓存效果。
