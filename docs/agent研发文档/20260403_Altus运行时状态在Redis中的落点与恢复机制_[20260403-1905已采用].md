## 1. 文档目标

在 `#10` 已定义 Redis key / TTL / stream 规范，`#11` 已把 session 热缓存与 `session-events` 接入 Redis 后，给 `#12` 定一个最小可落地的 Altus runtime 方案，只覆盖当前主线真正需要的运行态对象：

1. managed run 状态快照
2. managed run 事件流
3. sandbox 绑定与恢复辅助状态
4. connector runtime 恢复辅助状态
5. stop / heartbeat / active-runs / recovery 的协同规则

本设计不重做通用调度平台，不新增独立 run center，不把 connector/profile/guide 的事实存储迁进 Redis。

## 3. 参照与取舍

### 3.1 直接吸收什么

参照 `Suna`，本次只直接吸收两条：

1. run 的短生命周期状态要有 Redis 热快照，供 SSE 与恢复链路共享
2. Redis 恢复对象只存最小运行态，不承担事实历史

### 3.2 明确不照搬什么

本次明确不照搬 `Suna` 的这些部分：

1. 不引入新的统一 coordinator storage
2. 不引入 background task manager / worker ownership 框架重构
3. 不引入完整 startup cleanup / dead-letter / queue 平台
4. 不把所有 tool runtime 细节展开为独立 Redis 模型

原因只有一个：

1. `#12` 的最短路径是让 Altus run 能恢复、能停止、能检测活跃状态
2. 不是把 Altus 重写成一套 Suna 风格通用运行平台

以及两个与 run 恢复直接相关的最小引用：

1. sandbox 恢复引用

## 5. 设计原则

### 5.1 DB 继续做事实来源

以下对象继续以 DB 为准：

1. `task_session_runs`
2. `task_session_run_events`
3. `sandbox binding`
4. `connector snapshot`
5. `mcp tool snapshot`

Redis 只做：

1. 当前 run 的热状态
2. 当前 run 的短窗口事件流
3. 运行时恢复辅助对象

这条在 `#12` 中必须进一步收紧为：

1. 所有会影响业务事实的状态迁移，必须先成功落 DB
2. Redis 只能写“已成功落 DB 后的派生热状态”
3. 不允许出现“Redis 先变更，DB 后补写”的主流程

原因：

1. run 是否存在、run status 是否终态、sandbox binding 是否有效，这些都必须以 DB 为准
2. Redis 的 TTL、trim、网络失败都意味着它天然不适合承担事实唯一来源
3. 若把 Redis 放在 DB 之前，会直接制造 `latest run`、后台恢复、stream replay 三条链路之间的状态不一致

### 5.2 所有恢复都必须回到 `sessionId`

继承 `#9` 约束：

1. `userId` 是授权主键
2. `tenantKey` 只是命名空间
3. `runId`、`sandboxId`、`providerId` 都不是授权主键

所以恢复链路必须固定为：

`runId -> sessionId -> userId`

不允许：

1. 只凭 `sandboxId` 重连
2. 只凭 `providerId` 恢复 connector runtime
3. 只凭 `active-runs` 集合做恢复，不回查 session ownership

### 5.3 Redis 恢复对象只存最小必要字段

恢复对象只保存：

1. 重新建立运行态所需的最小引用
2. 恢复顺序所需的版本与时间戳
3. 并发控制所需的 owner / heartbeat

不保存：

1. 大消息历史
2. 完整 tool output
3. connector/profile 全量配置
4. 可从 DB snapshot 稳定拿到的大对象

### 5.4 Redis recovery 是 DB facts 的派生快照，不是第二真相

`run:recovery` 的定位必须非常明确：

1. 它不是新的 runtime 主记录
2. 它不是 DB 的镜像副本
3. 它只是“为了恢复更快而保留的最小派生快照”

因此必须遵守：

1. `run:recovery` 中任何字段都必须能从 DB + 当前 runtime 引用重新构建
2. 如果 `run:recovery` 丢失，系统仍必须能靠 DB 自愈
3. 如果 `run:recovery` 和 DB 冲突，永远以 DB 为准并重建 Redis

## 5.5 状态统一原则

本次方案必须避免三类典型失配：

1. DB 是 `completed`，Redis 还是 `running`
2. DB sandbox binding 已切换，Redis recovery 还指向旧 sandbox
3. DB run event sequence 已推进，Redis run stream 缺段或 sequence 回退

统一规则：

1. 状态主键统一以 `runId + sessionId` 锚定
2. sequence 只允许由 DB `task_session_run_events` 生成
3. Redis 只消费 DB 已确认的 sequence
4. 任一恢复入口发现 DB/Redis 冲突时，必须先按 DB 修正 Redis，而不是相反

## 6. 持久化顺序

### 6.1 run 创建

正确顺序必须是：

1. `taskSessionRunDAO.createRun(...)`
2. DB 成功后再 `registerRun(...)`
3. DB 成功后再写 `run:recovery`

禁止顺序：

1. 先写 Redis `run:state`
2. 再尝试落 DB run 记录

原因：

1. 如果 DB 创建失败，但 Redis 已经出现活跃 run，后续 `active-runs` 扫描会拿到幽灵 run
2. `runs/latest` 这类仍以 DB 为准的接口会和 Redis 状态直接分叉

### 6.2 run event 追加

正确顺序必须是：

1. `taskSessionRunDAO.appendRunEvent(...)` 在 DB 事务里生成 `sequence`
2. 以这个 DB `sequence` 为准写 `run:stream`
3. 同步刷新 `run:state.sequence`
4. 同步刷新 `run:recovery.stream.latestSequence`

禁止：

1. Redis 自己生成 sequence
2. Redis sequence 与 DB sequence 独立递增

原因：

1. 一旦 sequence 双源生成，SSE replay 和 DB fallback 将无法稳定拼接
2. `afterSequence` 这种恢复游标必须只有一个事实来源

### 6.3 run 生命周期迁移

正确顺序必须是：

1. 先 `updateRunStatus(...)` 落 DB
2. DB 成功后再 `syncRunStatus(...)`
3. 若状态迁移影响 recovery，再同步更新或清理 `run:recovery`
4. 最后发布对应 run event

特殊点：

1. `completed / failed / stopped` 的 DB 终态必须先成立，才允许清理 Redis `owner/heartbeat/recovery`
2. 否则会出现 Redis 已清理，但 DB 仍是活跃态，导致恢复入口误判

### 6.4 sandbox binding 与 connector snapshot

正确顺序必须是：

1. 先 `upsertSandboxBinding(...)` / `createConnectorSnapshot(...)` / `createMcpToolSnapshot(...)`
2. DB 成功后再刷新 `run:recovery.sandbox` / `run:recovery.connectorRuntime`

禁止：

1. Redis 里先指向新的 sandbox/provider
2. DB binding/snapshot 还没成功落库

原因：

1. 恢复时 Redis 会被拿来做快速定位，如果它提前指向未落库对象，会导致后续恢复链路无法自洽

### 6.5 terminal 清理

正确顺序必须是：

1. DB 终态落成功
2. Redis `run:state` 同步成终态
3. 再删除 `owner`
4. 再删除 `heartbeat`
5. 再删除 `stop`
6. 再删除 `run:recovery`
7. `run:stream` 与 `run:state` 保留到 TTL 到期

如果 Redis 清理失败：

1. 不回滚 DB 终态
2. 依赖下一次恢复扫描和 TTL 兜底清理

## 7. 失配修正规则

### 7.1 Redis 缺失但 DB 存在

处理原则：

1. 不判失败
2. 直接从 DB facts 重建 `run:state` / `run:recovery`
3. `run:stream` 允许为空，stream 订阅时走 DB fallback

### 7.2 Redis 存在但 DB 不存在

处理原则：

1. 视为脏热状态
2. 直接删除 Redis 相关键
3. 不允许继续尝试恢复执行

### 7.3 DB 与 Redis 状态冲突

处理原则：

1. 若 DB 已终态，Redis 必须立即收敛到终态并清理活跃键
2. 若 DB 仍活跃而 Redis 是终态，按 DB 重建 Redis
3. 若 sequence 冲突，始终以 DB 最新 sequence 为准修正 Redis

### 7.4 sandbox / connector 引用冲突

处理原则：

1. 以 DB binding / snapshot 为准
2. Redis recovery 中的旧引用直接覆盖
3. 不做“双写兼容”或多版本兜底

## 8. Redis 落点

### 6.1 run 状态快照

沿用 `#10` 的 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:state
```

当前 `run:state` 需要稳定包含：

```ts
type RunStateSnapshot = {
  tenantKey: string;
  userId: string;
  sessionId: string;
  runId: string;
  model: string | null;
  status: 'queued' | 'running' | 'waiting_user' | 'completed' | 'failed' | 'stopped';
  sequence: number;
  startedAt: string | null;
  completedAt: string | null;
  stopReason: string | null;
  updatedAt: string;
};
```

本次不再把 sandbox / connector 细节塞进 `run:state`，避免状态快照膨胀。

### 6.2 run 恢复对象

沿用 `#10` 的 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:recovery
```

这是 `#12` 本次真正新增需要启用的对象。

建议内容：

```ts
type RunRecoverySnapshot = {
  tenantKey: string;
  userId: string;
  sessionId: string;
  runId: string;
  model: string | null;
  status: 'queued' | 'running' | 'waiting_user';
  sequence: number;
  sandbox: {
    sandboxId: string | null;
    workspaceRoot: string | null;
    reused: boolean;
    updatedAt: string | null;
  };
  connectorRuntime: {
    providerIds: string[];
    updatedAt: string | null;
  };
  stream: {
    latestSequence: number;
    latestEventType: string | null;
  };
  updatedAt: string;
};
```

规则：

1. 只在 `queued / running / waiting_user` 三个可恢复状态下保留
2. `completed / failed / stopped` 后删除或等待 TTL 自然清空
3. sandbox 和 connector runtime 只存“恢复引用”，不存事实配置
4. connector runtime 只保存“当前活跃 providerId 列表”，不再额外保存 `bindingVersion/envVersion` 这类可由 DB binding 直接重算的字段

### 6.3 active runs

沿用 key：

```txt
oneceo:v1:tenant:{tenantKey}:ops:runs:active
```

规则：

1. 只保存活跃 `runId`
2. 不作为恢复唯一依据
3. 启动时扫描它时，必须回查 `run:state` / `run:recovery` 与 DB run 记录

### 6.4 owner / heartbeat / stop

沿用 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:owner
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:heartbeat
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:stop
```

规则：

1. `owner` 只用于当前 worker 占有标记
2. `heartbeat` 只用于存活检测
3. `stop` 是跨进程 stop 信号，不依赖进程内 `AbortController`
4. `owner + heartbeat` 过期且 run 仍是活跃状态时，允许进入“待恢复”判断

### 6.5 run stream

沿用 key：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:stream
```

职责不变：

1. SSE 回放热层
2. run 恢复时的最近窗口检查

本次只补一条约束：

1. `run:recovery.stream.latestSequence` 必须和 `run:stream` 的最新 sequence 保持同源更新

## 9. 恢复机制

### 7.1 启动恢复

触发时机：

1. 新 run 启动前
2. 新的 stream 订阅到来
3. 用户再次进入 session 并请求 latest run

恢复流程：

1. 读取 `active-runs`
2. 对每个 `runId` 回查 `run:state`
3. 若 `status` 不在 `queued/running/waiting_user`，直接从 active set 移除
4. 若 `heartbeat` 仍有效，只保留，不抢占
5. 若 `heartbeat` 失效，读取 `run:recovery`
6. 若 recovery 缺失，则回查 DB run + sandbox binding，必要时补写 recovery
7. 若仍无法构成完整恢复引用，则标记 run 为 failed 或 stale，并从 active set 移除

### 7.2 sandbox 恢复

本次不新建 Redis sandbox 索引，只在 `run:recovery.sandbox` 保留：

1. `sandboxId`
2. `workspaceRoot`
3. `reused`
4. `updatedAt`

真正恢复时仍通过现有链路：

1. `AltusManagedSetupService.ensureSandbox(...)`
2. `taskSessionRunDAO.getSandboxBindingBySession(...)`
3. `sessionMcpRecoveryService.ensureSessionRecovered(...)`

也就是说：

1. Redis 只告诉系统“应该尝试恢复哪个 sandbox”
2. 真正的 sandbox 可用性仍通过 E2B / DB binding 校验

### 7.3 connector runtime 恢复

本次不把 connector runtime 事实状态迁进 Redis。

Redis 只保留：

1. 当前 run 启动时关联的 binding version
2. 当前活跃 providerId 列表
3. 当前 envVersion 列表

真正恢复仍通过：

1. `taskSessionConnectorBindingDAO.listByTaskSessionId(...)`
2. `sessionMcpRecoveryService`
3. `captureMcpToolSnapshot(...)`

### 7.4 stream 回放恢复

恢复时优先顺序：

1. `run:stream`
2. `task_session_run_events`

恢复目标：

1. 让 `/runs/:runId/stream` 订阅后立即看到最近窗口
2. 若 Redis 已裁剪，再回退 DB

## 10. 清理策略

### 8.1 终态清理

在 `completed / failed / stopped` 时：

1. 从 `active-runs` 移除
2. 删除 `owner`
3. 删除 `heartbeat`
4. 删除 `stop`
5. 删除 `run:recovery`
6. 保留 `run:state` 与 `run:stream` 直到 TTL 到期

### 8.2 僵尸 run 清理

判定条件：

1. `run:state.status` 仍为活跃态
2. `heartbeat` 已过期
3. `owner` 不存在

处理顺序：

1. 先尝试恢复
2. 恢复失败再转 failed/stale
3. 最后移出 active set

本次不引入独立后台守护进程，也不额外挂到 API 启动期。

最小入口只放在：

1. 新 run 启动前
2. stream 订阅前的轻量自检
3. `latest run` 查询前的轻量自检

## 12. 测试要求

### 10.1 run 状态

1. `startRun()` 后 Redis 中出现 `state/owner/heartbeat/active-runs/recovery`
2. `markRunning()` 后 recovery 中 sandbox 信息被刷新
3. `waiting_user` 状态下 recovery 保留
4. `completed/failed/stopped` 后 recovery 被清理
5. DB 成功、Redis 失败时，下一次恢复扫描能按 DB 重建 Redis
6. Redis 存在、DB 缺失时，恢复扫描会清掉脏热状态

### 10.2 stop / heartbeat

1. stop 请求能跨进程写入 `run:stop`
2. heartbeat 过期时能判定为待恢复
3. 活跃态 run 但无 heartbeat 时，不会继续假装健康
4. terminal DB 状态落成功后，才允许清理 `owner/heartbeat/recovery`

### 10.3 stream / replay

1. run stream 仍优先 Redis replay
2. run recovery 中的最新 sequence 与 run stream 最新 sequence 保持一致
3. Redis 裁剪后继续回退 DB
4. Redis sequence 与 DB sequence 不一致时，按 DB sequence 修正 Redis

### 10.4 live Redis 验证

本次至少要补 route 或 service 级 live Redis 验证，直接检查：

1. `run:recovery`
2. `active-runs`
3. `heartbeat`
4. `stop`
5. `run:stream`

## 13. 验收结论

`#12` 完成的标准是：

1. Altus run 的恢复最小状态已经进入 Redis，而不是只剩 `state/stream`
2. 恢复逻辑明确区分 Redis 热状态与 DB 事实记录
