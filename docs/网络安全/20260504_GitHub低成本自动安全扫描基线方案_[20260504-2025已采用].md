# GitHub低成本自动安全扫描基线方案 [20260504-2025已采用]

更新时间：2026-05-04 21:05

## 背景

当前仓库为私有仓库场景下，`GitHub Pro` 无法直接获得完整的 GitHub Advanced Security / 私有仓库 CodeQL 能力，因此先采用“低成本、可持续、可自动执行”的基线方案，优先覆盖最常见且收益最高的安全风险。

本方案目标不是一次性完成全部安全治理，而是先把以下能力接入仓库默认开发流程：

1. 自动发现依赖漏洞
2. 自动发现疑似密钥泄漏
3. 自动推动依赖版本升级
4. 在 PR 阶段尽早阻断高风险问题进入主分支

## 采用范围

- 仓库根目录 `pnpm` 工作区
- `apps/web`
- `apps/admin_management`
- `billing_model/sub2api/backend`
- `billing_model/sub2api` 及其 `deploy` 目录内 Dockerfile
- `.github/workflows`

## 方案结论

采用以下低成本基线：

1. 使用 `Dependabot` 负责依赖与 GitHub Actions 版本更新
2. 使用 GitHub Actions 定时和 PR 触发安全工作流
3. 工作流当前接入以下检查：
   - `gitleaks`：检查疑似密钥、Token、私钥等泄漏
   - `pnpm audit` / `npm audit`：检查 Node 依赖漏洞
   - `govulncheck`：检查 Go 依赖与调用链漏洞
   - `trivy config`：检查 GitHub Actions、Dockerfile、部署目录中的高危配置问题
   - `Semgrep`：检查 `apps/api` 中常见 Web 安全代码问题与敏感逻辑风险

## 为什么不采用更重方案

- 不直接上 GitHub CodeQL：
  - 私有仓库下 `GitHub Pro` 能力不足，成本不匹配当前目标
- 不一次性引入大而全的多扫描器矩阵：
  - 噪音高、维护成本高、容易让团队对告警失去信任
- 不先做“补丁式兜底”：
  - 先把自动扫描接入 PR 和定时任务，形成持续发现机制，比零散人工检查更稳定

## 文件设计

### 1. `.github/dependabot.yml`

用途：

- 每周自动检查以下生态的版本更新：
  - 根目录 `npm/pnpm`
  - `apps/admin_management` 的 `npm`
  - `apps/web` 的 `pnpm`
  - `billing_model/sub2api/backend` 的 `gomod`
  - `billing_model/sub2api*` 下 Docker 镜像
  - GitHub Actions 依赖

设计原则：

- 分目录配置，避免 monorepo 子系统相互干扰
- 限制同时打开的 PR 数量，防止安全/依赖更新淹没日常开发
- 统一在每周一凌晨分时段执行，降低集中波动

### 2. `.github/workflows/security-baseline.yml`

触发方式：

- `pull_request`
- 推送到 `task-creation-agent`
- 每周定时
- 手动触发

设计原则：

- 先覆盖收益最高的秘密泄漏和依赖漏洞
- 再补充部署与 CI 配置误配扫描，但只扫描高风险目录，避免全仓库大面积误报
- 所有失败直接让工作流失败，避免高风险结果被忽略
- 不依赖 GitHub 付费代码扫描能力

当前扫描目录：

- `.github/workflows`
- `billing_model/sub2api`
- `apps/api/src`

## 仓库设置要求

代码提交后，还需要在 GitHub 仓库网页里确认以下设置已开启：

1. `Settings -> Security & analysis`
2. 开启：
   - `Dependency graph`
   - `Dependabot alerts`
   - `Dependabot security updates`

说明：

- `dependabot.yml` 负责版本更新策略
- `Dependabot alerts/security updates` 负责 GitHub 原生漏洞告警与修复建议
- 两者配合后，才是完整的低成本依赖安全基线

## 告警处理约束

出现告警后，处理顺序固定如下：

1. 先判断是否为真实可利用风险
2. 再判断是否存在官方升级路径
3. 优先升级依赖或删除风险依赖
4. 不采用“临时忽略但不留痕”的处理方式
5. 需要忽略时，必须在相关文档或 PR 中记录原因和时间范围

## 当前已补充的安全回归测试方向

- OAuth state 不匹配与过期拦截
- 登录态 Cookie 的 `HttpOnly` / `Secure` / `SameSite` 基线
- CORS 白名单允许与拒绝行为
- 登录限流与密码喷洒拦截

## 后续增强路线

在本基线稳定后，再按优先级逐步增强：

1. 增加面向 `apps/api` 的 SAST 规则扫描
2. 将高危告警与受保护分支合并策略绑定
3. 对鉴权、OAuth、Session、Sandbox、Connector 相关目录做专项安全测试
4. 视告警质量决定是否扩大 `trivy config` 扫描范围

## 验证标准

本次变更完成后，满足以下条件即视为基线接入成功：

1. `.github/dependabot.yml` 存在且语法正确
2. `.github/workflows/security-baseline.yml` 存在且语法正确
3. PR 页面可看到 `Security Baseline` 工作流
4. 仓库 `Security` / `Insights` 中可看到依赖图与 Dependabot 行为

## 风险与边界

- 当前方案不等于完整安全审计
- 当前方案对业务逻辑漏洞、鉴权设计缺陷、越权、SSRF、沙箱逃逸等高层风险覆盖有限
- `npm audit` / `pnpm audit` 可能出现噪音，需要结合真实调用场景判断
- 如后续告警数量过大，需要再做规则收敛，而不是直接关闭扫描
