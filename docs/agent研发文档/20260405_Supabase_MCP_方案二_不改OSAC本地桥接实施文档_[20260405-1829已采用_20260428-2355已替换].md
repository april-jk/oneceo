1. 不引入“长期双主链路”兼容策略。

4. 变更必须覆盖全链路可验证：profile 保存 -> attach -> list tools -> call tool。

## 1. 背景与问题

当前现象：

1. API 侧对 Supabase attach 已使用 streamable_http。
2. 运行时回包反复出现 failed_to_attach。
3. 错误信息明确为 unsupported mcp transport: streamable_http。

已确认事实：

1. 当前 OSAC 交付能力只稳定覆盖 local_stdio、remote_sse。
2. 不改 OSAC 前提下，streamable_http 无法被 runtime 原生接受。
3. GitHub 连接器在当前仓库中已通过 local_stdio 包装方式稳定运行，可作为可复用范式。

结论：

1. 在 不改 OSAC 前提下，必须把 Supabase 的 streamable_http 能力下沉到 Sandbox 内本地桥接进程。
2. OSAC 继续只接 local_stdio provider。

## 2. 目标

本方案目标：

1. 保持 OSAC 完全不改动。
2. Supabase 连接器从 runtime 视角统一为 local_stdio。
3. 本地桥接进程负责对接上游 Supabase streamable_http。
4. attach 进入 connected，且可稳定执行至少一个真实 Supabase MCP tool。

验收标准：

1. Supabase attach 回包 status=connected。
2. provider transport 在运行日志中为 local_stdio。
3. list_tools 成功且非空。
4. call_tool(list_projects) 成功返回业务数据。
5. token 更新后无需重建会话即可恢复可用。

## 3. 非目标

本次不做：

1. 不扩展 OSAC transport 枚举。
2. 不新增 Supabase OAuth。
3. 不改 GitHub/Vercel/Figma 现有逻辑。
4. 不重构连接器中心 UI 结构。

## 4. 方案总览

主链路调整前：

1. API -> OSAC -> streamable_http -> Supabase MCP

主链路调整后：

1. API -> OSAC -> local_stdio(bridge) -> streamable_http -> Supabase MCP

关键点：

1. API 对 OSAC 发送 REGISTER/ATTACH 的 transport 固定为 local_stdio。
2. bridge 进程通过 stdio 暴露 MCP server 能力。
3. bridge 内部作为 MCP client 调用 Supabase streamable_http。
4. bridge 负责请求转发、会话初始化、错误透传、超时控制与重连。

## 5. 代码改造清单（文件级）

## 5.1 新增 Supabase 本地 bridge

新增文件：

1. apps/api/src/connectors/bridges/supabase-stdio-bridge.ts

职责：

1. 从 stdin 读取 JSON-RPC 消息。
2. 处理 initialize、tools/list、tools/call 等 MCP 基础方法。
3. 通过 HTTP 向 Supabase MCP 端点发送 streamable_http 请求。
4. 将上游响应转换回标准 MCP stdio 输出。
5. 对上游错误做结构化透传（保留 message/type/code）。

必须支持的环境变量：

1. SUPABASE_MCP_URL（默认 https://mcp.supabase.com/mcp）
2. SUPABASE_ACCESS_TOKEN（必填）
3. SUPABASE_PROJECT_URL（可选，对应 x-supabase-url）
4. HTTP_PROXY / HTTPS_PROXY / NO_PROXY（可选）
5. SUPABASE_BRIDGE_TIMEOUT_MS（默认 30000）

实现要求：

1. 仅一层桥接，不引入额外状态存储。
2. 所有敏感信息打印前必须脱敏。
3. 上游不可达时返回可诊断错误，不返回泛化文案。

## 5.2 在连接器注册层将 Supabase 物化为 local

修改文件：

修改内容：

1. 为 Supabase 新增 buildSupabaseStdioBridgeCommand。

3. command 指向 node 执行 supabase-stdio-bridge。
4. env 注入 token、可选 project url、代理变量。

约束：

1. 不保留 Supabase remote 路径作为主流程。
2. 不新增按环境自动切回 remote 的逻辑。

## 5.3 会话 attach 层去除 Supabase streamable_http 分支

说明：

## 8. 风险与应对

风险 1：bridge 进程异常退出

1. 现象：provider 短时间内 disconnected。
2. 应对：attach 时拉起新进程，失败语义透传并进入恢复链路。

风险 2：上游 streamable_http 抖动

1. 现象：tools/call 偶发超时。
2. 应对：bridge 内超时与一次重试，超限后返回明确错误码。

风险 3：代理环境配置不一致

1. 现象：sandbox 与本地行为不一致。
2. 应对：统一通过 env 注入路径，增加 bridge 启动时配置摘要日志（脱敏）。

## 14. 追加修复记录（2026-04-05）

问题现象：

1. Supabase attach 回包 `failed_to_attach`。
2. 错误为 `HTTP 400 {"message":"Mcp-Session-Id header is required for non-initialization requests"}`。

根因：

1. bridge 以无状态方式转发每个 JSON-RPC 请求。
2. 未从初始化响应头提取并复用 `Mcp-Session-Id`。
3. 在 `initialize` 与后续请求并发到达时，后续请求可能先于会话头建立发送。

修复内容：

1. `supabase-stdio-bridge` 新增 `mcpSessionId` 内存态。
2. 从上游响应头提取并更新 `Mcp-Session-Id`。
3. 非 `initialize` 请求自动携带 `Mcp-Session-Id`。
4. stdin 请求处理改为串行队列，保证先初始化再发后续请求。

涉及文件：

1. `apps/api/src/connectors/bridges/supabase-stdio-bridge.ts`
2. `apps/api/tests/supabase-stdio-bridge.test.ts`

验证命令：

1. `pnpm --filter api exec tsx --test tests/supabase-stdio-bridge.test.ts tests/connector-registry.test.ts tests/session-connector-service.test.ts`

验证结果：

1. 本地单测通过。
2. 修复后 bridge 在上游失败场景不再因为会话头缺失导致 400 问题持续复现。
