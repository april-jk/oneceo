# 20260411 Notion MCP 接入后 Admin 连接器 Guide 登录拉取与手动刷新改造设计 [20260411-1519已采用]

更新时间：2026-04-11

## 1. 背景与问题

当前已在 API 侧接入 Notion Connector（MCP），但管理后台 Connector Guide 页面没有实时反映新增连接器与策略变更，表现为：

1. 页面默认新建选项不包含 Notion。
2. 连接器变化后页面不会自动刷新，必须手动点击“刷新列表”。
3. 管理端对“支持哪些 connector guide”存在前后端写死，扩展新 connector 时需要多处手改。

## 2. 现状证据（代码定位）

### 2.1 API 侧 Connector Guide 支持范围被写死

1. `apps/api/src/services/connector-guide-service.ts`
2. `SUPPORTED_CONNECTOR_KEYS = ['github', 'supabase', 'vercel']`
3. `assertSupportedConnectorKey` 报错文案明确仅支持这三个 connector。

这会导致 Notion 即便已经是可用 MCP connector，也无法进入 Connector Guide 主链路。

### 2.2 Admin 前端新建选项被写死

1. `apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`
2. `connectorOptions = ['github', 'supabase', 'vercel']`
3. 页面文案同样固定为 GitHub/Supabase/Vercel。

这会导致后台管理员无法直接为 Notion 新建 guide policy。

### 2.3 Admin 页面缺实时刷新机制

1. 同文件仅保留手动按钮“刷新列表”。
2. 无 `setInterval`、无 SSE、无 WebSocket 订阅。

因此 API 侧发生变更后，前端不会自动感知。

## 3. 改造目标

1. Notion 纳入 Connector Guide 正式支持范围。
2. 管理员登录后台时，Admin 页面获取“最新 MCP 类型与数量”快照。
3. 允许仅通过手动刷新获取后续变更，不要求自动轮询实时更新。
4. 不触碰现有 skills 模块与其数据结构。
5. 不改 OSAC 主执行链路，只改 Connector Guide 治理链路。

## 4. 非目标

1. 不引入新的 skills 注入机制。
2. 不重构 Connector Guide 数据表。
3. 不改用户端 connector 交互流程。
4. 本期不实现 attach session 数量类治理指标（延续现有边界）。

## 5. 方案总览

采用“后端扩展支持 + 登录时强制拉取最新 + 手动刷新”的最短闭环方案。

1. API 侧把 Notion 纳入 Connector Guide 支持集合。
2. Admin 前端不再写死 connectorOptions，改为从后端返回的 policy 列表派生，并补充内置候选集合。
3. 管理员登录完成后，立即拉取 MCP 目录并计算类型数量；后续由手动“刷新列表”触发再次拉取。

该方案不依赖新增基础设施（SSE/消息总线），改动范围最小且可验证。

## 6. 详细改造设计

### 6.1 API：扩展 Connector Guide 支持集合到 Notion

文件：`apps/api/src/services/connector-guide-service.ts`

改动点：

1. `SUPPORTED_CONNECTOR_KEYS` 增加 `notion`。
2. `BUILTIN_CONNECTOR_GUIDES` 增加 `notion` 默认三段文案：
   - `serverInstructionsMarkdown`
   - `guideReminderMarkdown`
   - `blockingRulesMarkdown`
3. `assertSupportedConnectorKey` 报错文案同步更新为包含 Notion。
4. `ensureBuiltinPolicies` 自动补齐 Notion policy/revision/publish。

预期结果：

1. Notion 可创建/校验/发布 connector guide。
2. 现有 `recomputeSessionGuides` 可把 attached 的 notion binding 纳入会话 guide 计算。

### 6.2 Admin Web：连接器选项改为动态，不再硬编码三项

文件：`apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`

改动点：

1. 移除固定 `connectorOptions = ['github', 'supabase', 'vercel']`。
2. 新增 `builtinCandidateConnectorKeys`（至少含 `github/supabase/vercel/notion`），并与当前 `policies.map(policy.connectorKey)` 取并集作为页面候选。
3. 页面副标题文案改为“管理已接入 connector 的隐式 guide 文本”。
4. 筛选下拉、新建按钮均使用动态候选集合。

预期结果：

1. Admin 可直接看到 notion 候选项并创建 policy。
2. 后续新增 connector 不必每次改三处 UI 常量。

### 6.3 Admin：登录时获取最新 MCP 类型与数量（无自动轮询）

文件：

1. `apps/admin_management/server/connectors/oneceo-api-connector.ts`
2. `apps/admin_management/server/services/connector-guide-management-service.ts`
3. `apps/admin_management/server/routes/connector-guide-routes.ts`
4. `apps/admin_management/web/src/api.ts`
5. `apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`

改动点：

1. Admin server 新增透传方法/路由，获取 `GET /api/connectors/catalog` 的最新目录。
2. 前端登录后进入管理页时，先请求 catalog，再计算并展示：
   - MCP 类型列表（connector keys）
   - MCP 类型数量（catalog length）
3. Connector Guide 页面初次进入时执行 `loadPolicies()`，并与 catalog 一起构造候选集合。
4. 保留“刷新列表”按钮；点击后同时刷新 policy 列表与 catalog 计数。
5. 不引入 `setInterval`、不引入 SSE/WebSocket。

预期结果：

1. 管理员每次登录都能看到当前时刻的最新 MCP 类型与数量。
2. 后续变化通过手动刷新可立即同步。

### 6.4 扩展接口预留（新增 MCP 的统一接入位）

目标：后续新增 MCP 时，不再改动多处硬编码，只追加定义与映射。

文件：

1. `apps/admin_management/server/connectors/oneceo-api-connector.ts`
2. `apps/admin_management/server/services/connector-guide-management-service.ts`
3. `apps/admin_management/server/routes/connector-guide-routes.ts`
4. `apps/admin_management/web/src/api.ts`
5. `apps/admin_management/web/src/components/ConnectorGuideManagementSection.tsx`

接口预留：

1. `GET /api/connector-guides/catalog-summary`
2. 返回结构固定为：
   - `items`: 最新 connector catalog（每项至少包含 `key/name/available/availabilityReason/visibleInMenu`）
   - `stats`: 统计信息（`total/available/unavailable`）
   - `updatedAt`: 生成时间

使用约束：

1. 前端仅消费 `catalog-summary`，不再写死 connector keys。
2. 新增 MCP 时只需要：
   - 在 API connector definition 层新增该 connector
   - 在 Connector Guide 支持集合补充该 key
   - 如需默认文案，在 `BUILTIN_CONNECTOR_GUIDES` 增加对应三段文本
3. Admin 页面不需要再为新 MCP 增加独立按钮代码；候选项由 catalog 自动派生。

预期收益：

1. 新增 MCP 的改动面稳定在“定义 + guide 支持”两处。
2. Admin 展示层与 connector 扩展解耦，降低后续维护成本。

## 7. 数据与接口影响

### 7.1 数据层

1. 不新增表。
2. 继续使用 `connector_guide_policy / connector_guide_revision / task_session_connector_guide` 既有链路。

### 7.2 接口层

1. 复用既有接口：
   - `GET /api/connector-guides`
   - `GET /api/connector-guides/:policyId`
   - 其他 revision 相关接口不变。
2. 新增 Admin 侧聚合路由（示例）：
   - `GET /api/connector-guides/catalog-summary`
3. Admin 侧聚合路由内部透传 API：
   - `GET /api/connectors/catalog`
4. 为后续扩展预留统一入口约束：
   - Admin 前端统一从 `GET /api/connector-guides/catalog-summary` 获取 catalog 与统计信息

## 8. 回归与验收

### 8.1 功能验收

1. API 启动后，Notion 可通过 connector guide 创建与发布。
2. Admin 页面出现 Notion 候选项。
3. 管理员重新登录后，页面显示最新 MCP 类型与数量。
4. 点击“刷新列表”后，MCP 类型、数量与 policy 列表同步为最新。
5. 新增一个 MCP definition 后，Admin 无需新增页面硬编码即可显示该类型。

### 8.2 回归范围

1. GitHub/Supabase/Vercel 既有流程不退化。
2. 校验逻辑仍然只做 connector-domain 文本校验，不触碰 skills 模块。
3. 发布/回滚后会话重算链路正常。

## 9. 实施清单（按顺序）

1. 修改 API `connector-guide-service.ts` 支持 Notion。
2. 修改 Admin `ConnectorGuideManagementSection.tsx` 动态 connector 候选。
3. 新增 Admin catalog-summary 透传接口，并在登录后与手动刷新时拉取最新类型与数量。
4. 统一前端候选项来源为 catalog-summary，移除 MCP 类型硬编码依赖。
5. 跑类型检查与最小回归：
   - `npm --prefix apps/api run type-check`
   - `npm --prefix apps/admin_management run type-check`

## 10. 风险与约束

1. 若 Notion 在连接器目录可用但 OAuth/remote URL 未配置，仍会由现有 connector 定义返回不可用状态；该行为保持不变。
2. 由于不做自动轮询，登录后的新变化需要手动刷新才能看到；该行为符合本次要求。
3. 本方案不覆盖“秒级事件推送”；如后续需要可升级为 SSE，但不在本次范围。

## 11. 结论

本方案通过最小改动实现两件事：

1. 让 Notion 正式进入 Connector Guide 治理链路。
2. 让 Admin 页面在登录时拿到最新 MCP 类型与数量，并保留手动刷新获取后续变化。

在不新增复杂基础设施的前提下，能够满足“登录时最新 + 手动刷新即可”的当前诉求。
