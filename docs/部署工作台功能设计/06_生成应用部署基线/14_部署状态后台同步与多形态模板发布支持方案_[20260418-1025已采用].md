# 部署状态后台同步与多形态模板发布支持方案 [20260418-1025已采用]

## 1. 目标

本轮只解决两个问题：

1. 部署面板状态必须由后台任务持续同步，不能再依赖 `GET /deployment` 这类读请求临时向 Railway 拉数据。
2. 生成应用部署基线必须稳定支持多种项目形态，至少覆盖：
   - 纯 HTML / CSS / JS 静态站点
   - 纯 Node.js / JavaScript 服务脚本
   - 标准 Node.js 包项目
   - Python Web / Script 项目

本方案不引入新的部署供应商，不引入补丁式兼容分支，也不做“请求读不到再偷偷实时修正”的回退。

## 2. 现状问题

### 2.1 部署状态仍然绑定在读请求

当前 `buildTaskSessionDeploymentResponse()` 会在读请求阶段直接调用 Railway：

- `GET /api/task-creation/sessions/:id/deployment`
- Altus `get_application_deployment_status`
- 部署动作内的后续读面板逻辑

这会带来三个问题：

1. 面板是否刷新，取决于用户有没有再次打开页面。
2. 同一个会话的状态推进被读请求和执行请求混在一起，状态写入时机不稳定。
3. Railway 网络抖动时，面板读取会直接退化成空白或误判，而不是继续展示后台已知状态。

### 2.2 当前模板基线偏向 `package.json + HTML`

当前主链对以下情况支持较弱：

1. 只有 `index.html` 的纯静态项目
2. 没有 `package.json` 但有 `server.js` / `index.js` / `app.js` 的 Node.js 脚本项目
3. 有 `requirements.txt` / `pyproject.toml` 的 Python 项目
4. 使用 Python 模板目录而不是根目录 `index.html` 的页面项目

这会让 agent 明明生成了“可运行项目”，但部署前检查却把它当成“不可发布工作区”。

## 3. 外部契约依据

本方案依赖 Railway 官方文档中的以下契约：

1. Railway 使用 Railpack 自动识别并构建多语言项目，官方支持语言包括 Node、Python、HTML/Staticfile、Shell scripts 等。
2. 当自动检测不到合适的 start command 时，需要明确提供 start command。
3. Railway 支持 `railway.toml` / `railway.json` 作为 config-as-code，且代码内配置会覆盖 Dashboard 中的构建/启动配置。

依据：

- [Railpack | Railway Docs](https://docs.railway.com/reference/railpack)
- [No Start Command Could be Found | Railway Docs](https://docs.railway.com/deployments/troubleshooting/no-start-command-could-be-found)
- [Config as Code | Railway Docs](https://docs.railway.com/reference/config-as-code)
- [Build and Start Commands | Railway Docs](https://docs.railway.com/reference/build-and-start-commands)

## 4. 修复原则

1. 读请求只读“已持久化的部署快照”，不承担同步职责。
2. 后台同步必须是单一主链：部署动作写入初始状态，后台任务推进并回写状态。
3. 模板基线优先做“最小可部署归一化”，而不是为每种框架写一套独立分支。
4. 对多形态项目的支持依赖明确产物契约，而不是猜测 Railway 面板设置。
5. 不允许因为支持新形态而破坏已跑通的 HTML / Vite / Node 主链。

## 5. 方案概述

### 5.1 部署面板状态后台同步

新增后台同步任务，统一负责：

1. 轮询 Railway 部署状态
2. 检查公网地址可达性
3. 完成 Umami final binding
4. 把最新部署面板快照写入 sandbox metadata

持久化模型新增两层：

1. `metadata.deploymentState`
   - 负责表达状态机
   - 如 `bindingState/provisioningPhase/providerErrorCode`
2. `metadata.deploymentPanel`
   - 负责表达“给前端直接展示的快照”
   - 包括 `latestStatus/latestUrl/domains/deployments/logs/analytics`

### 5.2 读写职责切分

#### 写侧

`executeTaskSessionDeploymentAction()` 只负责：

1. 资源准备
2. 工作区发布
3. 触发 deploy / redeploy / rollback
4. 写入“后台同步开始”的状态
5. 把会话加入后台同步队列

#### 读侧

`buildTaskSessionDeploymentResponse()` 只负责：

1. 读取 `metadata.deploymentPanel`
2. 若无快照，则读取 `deploymentState`
3. 返回“后台同步中 / 等待同步 / 已同步结果”

禁止在读侧直接调用 Railway GraphQL。

### 5.3 后台同步推进规则

后台任务按以下顺序推进：

1. 读取会话环境、用户归属、session account
2. 向 Railway 拉取 deployment panel
3. 若 deployment 进入 active / completed 且 URL 可访问：
   - 执行 Umami final binding
   - 刷新 analytics 面板
4. 回写 `deploymentPanel`
5. 根据最新结果收敛 `deploymentState`

后台任务的输入来源：

1. 部署动作显式 enqueue
2. API 启动时恢复 backlog
3. 定时扫描 `bindingState=provisioning` 或缺少 `deploymentPanel` 的活跃环境

## 6. 多形态模板发布支持

### 6.1 纯静态 HTML / JS

保留当前静态基线做法，但补齐 config-as-code：

1. 若根目录存在 `index.html` 且无标准运行项目
2. 自动补：
   - `package.json`
   - `server.js`
   - `oneceo.manifest.json`
   - `railway.json`

其中 `railway.json` 明确声明：

1. build command
2. start command 为 `node server.js`
3. healthcheck path

### 6.2 纯 Node.js / JavaScript 脚本

新增 Node script baseline：

触发条件：

1. 没有 `package.json`
2. 但存在 `server.js` / `index.js` / `app.js`

自动补：

1. `package.json`
2. `oneceo.manifest.json`
3. `railway.json`

默认 start command：

- `node server.js`
- `node index.js`
- `node app.js`

按入口优先级选择。

### 6.3 标准 Node.js 包项目

继续以 `package.json` 为主，但新增 `railway.json` 自动补齐逻辑：

1. 读取 manifest 推导 build/start/healthcheck
2. 若项目未显式声明 `railway.toml/json`
3. 自动生成 `railway.json`

这样 Railway 的构建/启动配置不会再完全依赖 Dashboard。

### 6.4 Python 项目

新增 Python baseline：

触发条件：

1. 存在 `requirements.txt` 或 `pyproject.toml`
2. 或存在 `main.py` / `app.py` / `server.py`

支持三类最小入口：

1. FastAPI / ASGI
   - 识别 `FastAPI(` 与 `app =`
   - 默认 start command:
     - `uvicorn <module>:app --host 0.0.0.0 --port $PORT`
2. Flask / WSGI
   - 识别 `Flask(` 与 `app =`
   - 默认 start command:
     - `gunicorn <module>:app --bind 0.0.0.0:$PORT`
3. 通用 Python 脚本
   - 默认 start command:
     - `python main.py`
     - `python app.py`
     - `python server.py`

自动补：

1. `oneceo.manifest.json`
2. `railway.json`

其中 `railway.json` 显式设置 start command 和 healthcheck path，避免 Railway 自动探测失败。

### 6.5 HTML 模板入口扩展

Analytics bootstrap 注入不再只看：

1. `index.html`
2. `client/index.html`
3. `public/index.html`

新增候选：

1. `templates/index.html`
2. `app/templates/index.html`
3. 归一化后根目录主 HTML 入口

不做全量模板注入器，只收敛“主入口模板”。

## 8. 验收标准

### 8.1 后台同步

必须满足：

1. 部署触发后，即使前端不再轮询，后台也能把状态推进到最终快照
2. `GET /deployment` 不再直接调用 Railway
3. API 重启后，后台同步任务能恢复处于 `provisioning` 的会话
4. 部署面板最终能读到：
   - deployment status
   - public URL
   - analytics status
   - provider error

### 8.2 多形态模板

必须满足：

1. 纯静态 HTML/JS 工作区可自动归一化后部署
2. 无 `package.json` 的 Node.js 脚本项目可部署
3. 标准 Node.js 包项目继续可部署
4. FastAPI / Flask / 通用 Python 项目可生成 deploy baseline
5. 模板检查结果必须明确反映：
   - 识别到的 runtime/framework
   - start command 是否可推导
   - healthcheck 是否可推导

## 9. 不做的事

本轮明确不做：

1. 为所有 Python 框架写完整项目级适配器
2. 为 monorepo 多服务部署做自动拆分
3. 对已部署历史会话做全量离线回填迁移
4. 支持 Dockerfile 自定义高级场景

## 10. 实施顺序

1. 先把状态快照和后台同步任务落地
2. 再把 `GET /deployment` 改成只读快照
3. 再扩展模板归一化与 manifest / railway.json 生成
4. 最后补测试和真实回归
