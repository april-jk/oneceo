# 05 脱敏与保留策略 [尚未采用]

## 更新时间

2026-05-04
n## 1. 敏感信息脱敏规则

### 1.1 Headers 脱敏

以下 header 字段的值在入库前替换为 `***REDACTED***`：

```typescript
const SENSITIVE_HEADERS = new Set([
  'authorization',
  'cookie',
  'x-api-key',
  'x-auth-token',
  'x-session-token',
  'proxy-authorization',
]);
```

其余 headers（如 `content-type`、`accept`、`x-request-id`）正常保留。

### 1.2 Body 脱敏

#### 请求 Body 脱敏

递归遍历 body JSON，以下 key（不区分大小写）的值替换为 `***REDACTED***`：

```typescript
const SENSITIVE_BODY_KEYS = new Set([
  'password',
  'passwordhash',
  'password_hash',
  'token',
  'access_token',
  'refresh_token',
  'api_key',
  'apikey',
  'secret',
  'secret_key',
  'private_key',
  'credential',
  'authorization',
]);
```

**深度限制**：递归深度最多 5 层，防止超大嵌套 JSON 导致性能问题。

**大小限制**：body 超过 100KB 时，仅提取前 100KB 内的敏感字段，其余丢弃。

#### 响应 Body 脱敏

与请求 Body 相同规则。额外处理：
- 如果响应包含 `token`、`sessionId` 等字段，同样脱敏
- 如果响应是二进制流（如文件下载），不记录 body，仅记录 `content-type` 和文件大小

### 1.3 Query String 脱敏

以下 query 参数的值替换为 `***REDACTED***`：

```typescript
const SENSITIVE_QUERY_KEYS = new Set([
  'token',
  'api_key',
  'apikey',
  'secret',
  'password',
]);
```

### 1.4 IP 与 User-Agent 处理

- `ipAddress`：保留原始 IP（IPv4/IPv6），用于安全审计
- `userAgent`：完整保留，用于设备/浏览器识别

### 1.5 脱敏实现位置

在 middleware 中完成脱敏，**脱敏后的数据才进入 service 和 DAO 层**。

```typescript
// middleware 层
const sanitizedHeaders = sanitizeHeaders(req.headers);
const bodySummary = extractBodySummary(sanitizeBody(req.body));
```

## 2. 数据保留策略

### 2.1 HTTP 请求日志（api_request_logs）

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `ONECEO_API_REQUEST_LOG_RETENTION_DAYS` | 30 | 保留天数 |
| `ONECEO_API_REQUEST_LOG_CLEANUP_INTERVAL_MS` | 3600000（1小时） | 清理任务执行间隔 |
| `ONECEO_API_REQUEST_LOG_CLEANUP_ENABLED` | true | 是否启用清理 |

清理逻辑：删除 `created_at < now() - retention_days` 的记录。

### 2.2 Session API Traces（session_api_traces）

现有策略：
- `ONECEO_API_TRACE_RETENTION_DAYS` = 30（默认）
- `ONECEO_API_TRACE_CLEANUP_INTERVAL_MS` = 3600000

保持不变，与 HTTP 请求日志保留策略对齐。

### 2.3 保留策略对比

| 数据类型 | 保留时长 | 清理频率 | 备注 |
|---|---|---|---|
| `api_request_logs` | 30 天 | 每小时 | 新表，跟随 HTTP 请求日志 |
| `session_api_traces` | 30 天 | 每小时 | 现有表，策略不变 |
| `conversation_messages` | 长期 | 不清理 | 业务数据，永久保留 |
| `task_creation_sessions` | 长期 | 不清理 | 业务数据，永久保留 |

## 3. 性能考量

### 3.1 写入性能

- 请求日志写入为**异步操作**，在 `res.end` 回调中触发
- 不阻塞 HTTP 响应返回
- 使用批量写入（可选）：每 100 条或 5 秒批量 flush 一次

### 3.2 查询性能

- `api_request_logs` 已建立以下索引：
  - `app_user_id + created_at`（用户时间范围查询）
  - `path`（路径筛选）
  - `response_status`（状态码筛选）
  - `task_session_id`（会话关联查询）
- 预计单用户 30 天内请求量 < 10 万条，索引查询性能充足

### 3.3 存储估算

假设日活 1000 用户，每用户日均 50 次 API 请求：
- 日写入量：50,000 条
- 单条大小（脱敏后）：~2KB
- 日增量：~100MB
- 30 天总量：~3GB

可接受范围内，无需分表。
