# 20260524 Altus 预览服务托管与调试启动闭环方案 [20260524-1743已采用]

## 1. 问题结论

本次 `104b9bd6-7d7e-4ec3-8afb-abefd2b008b2` 的预览失败不是 sandbox 启动失败，也不是网页一定没有生成成功，而是预览服务生命周期归属错误：

> OneCEO 固定 Web Shell 的生产启动命令 `node dist/index.js` 是长驻服务，但 `shell_execute` 没有把它识别为需要平台托管的预览服务，于是它被当前台一次性命令执行。服务正常启动后不会退出，E2B 命令最终超时，Altus 把 timeout 误判为启动失败，随后反复尝试 `&`、`nohup`、换端口、调 curl，最后 `debug_open_page` 打开不稳定或错误目标而失败。

因此，大量 `[deadline_exceeded]` 是同一因果链上的症状：长驻服务被当前台命令等待，而不是多个独立问题。

## 2. 证据链

用户提供的 Actions 记录显示：

1. 固定 Web Shell 文件已存在：`package.json`、`oneceo.manifest.json`、`vite.config.ts`、`client/index.html`、`client/src/main.jsx`、`server/index.ts`。
2. `npm run build` 首次失败后，`npm install` 与第二次 `npm run build` 已完成。
3. 进入视觉检测阶段后，连续尝试：
   - `PORT=8090 node dist/index.js &`
   - `PORT=8090 node dist/index.js`
   - `PORT=8090 node dist/index.js 2>&1`
   - `fuser -k 8090/tcp ... PORT=8091 node dist/index.js`
   - `PORT=8080 node dist/index.js > /tmp/ceo-server.log 2>&1 & disown ...`
4. 之后 `debug_open_page` 两次失败，并触发 `debug_open_page_repeat_blocked`。

代码侧对应事实：

1. 固定 Web Shell 的标准启动命令是 `node dist/index.js`，定义在 `apps/api/src/services/oneceo-official-web-shell-materialization-service.ts`。
2. 固定 Web Shell 默认监听 `process.env.PORT || 8080`，并提供 `/api/system/health` 和 `/health`。
3. `apps/api/src/services/altus-managed-tool-runtime.ts` 已有 `background_service` 托管启动能力，但 `isPersistentLocalServerCommand` 只识别 `python -m http.server`、`npm run dev`、`pnpm dev`、`vite dev` 等开发命令，没有识别 `node dist/index.js`、`PORT=8080 node dist/index.js`、固定壳 `npm start`。
4. `debug_open_page` 在打开前会 curl 目标 URL；如果前一步服务没有被平台稳定托管，后续打开会天然不稳定。
5. `AltusRunCoordinator` 的 `debug_open_page_repeat_blocked` 是正确保护：同一 URL 同一失败原因重复出现后停止继续重复消耗。但它只能止损，不能修复预览服务启动事实源。

## 3. 第一性原则

网页预览是一个服务生命周期问题，不是一个 shell 文本技巧问题。

正确边界应当是：

1. 模型负责生成代码、运行构建、请求打开页面。
2. 平台负责识别网站启动契约、启动长驻服务、等待健康检查、提供稳定 URL。
3. 调试浏览器只打开平台确认 ready 的 URL。
4. timeout 只能作为诊断信号，不能作为“服务启动失败”的唯一依据。

所以最短正确修复不是：

1. 增大 `timeoutMs`。
2. 在提示词里要求模型加 `&` 或 `nohup`。
3. 让模型自行 `fuser`、换端口、`disown`。
4. 把 `debug_open_page_repeat_blocked` 放宽，让它继续重复打开。

最短正确修复是：让平台把固定 Web Shell 的生产启动命令纳入 `background_service` 托管，并让后续视觉检测只消费托管结果。

## 4. 目标流程

网站生成后的完整闭环固定为：

```text
写入/修改代码
  -> npm install / npm run build 等一次性命令前台执行
  -> 解析预览服务契约
  -> 平台托管启动长驻服务
  -> 健康检查确认 ready
  -> 返回 service.url / healthUrl / port / pid / logPath / status
  -> debug_open_page 打开 service.url
  -> browser_interact / Playwright 做视觉检测并留截图证据
  -> complete_task
```

其中“解析预览服务契约”必须优先使用结构化事实：

1. `oneceo.manifest.json` 的 `start.command`、`start.port`、`healthcheck`。
2. `package.json` 的 `scripts.start/dev/preview`。
3. 固定 Web Shell 的内置约定：
   - `command`: `node dist/index.js`
   - `port`: `PORT` 环境变量优先，否则 `8080`
   - `healthPath`: `/api/system/health`

## 5. 最小修复方案

### 5.1 扩展长驻服务识别

修改 `apps/api/src/services/altus-managed-tool-runtime.ts`。

`isPersistentLocalServerCommand` 必须识别以下固定壳服务启动形态：

1. `node dist/index.js`
2. `PORT=<port> node dist/index.js`
3. `npm start` / `pnpm start` / `yarn start` / `bun start`，但仅在当前 workspace 的 `package.json` 或 `oneceo.manifest.json` 表明它会启动固定 Web Shell 时成立

原则：

1. 不把所有 `node *.js` 都判定成长驻服务。
2. 不靠命令字符串猜测复杂框架。
3. 固定壳之外的项目仍由 manifest/package 的显式启动契约决定。

### 5.2 让托管启动使用健康检查路径

`startControlledBackgroundService` 当前只探测根路径 `/`。固定 Web Shell 已声明 `/api/system/health`，首版应让启动结果包含并优先探测：

1. `healthUrl=http://127.0.0.1:<port>/api/system/health`
2. `url=http://127.0.0.1:<port>/`

ready 判定优先使用 health URL，根路径作为页面打开入口。这样可以区分“服务进程已就绪”和“页面渲染是否健康”。

### 5.3 明确前台阻断语义

如果模型显式传 `runMode=foreground` 执行固定壳长驻命令，工具应快速失败并给出可恢复错误：

```text
shell_execute_persistent_local_server_foreground_blocked
```

这不是失败服务，而是阻止错误执行方式。模型下一步应保持 `runMode=auto` 或使用 `background_service`。

### 5.4 将 `debug_open_page` 绑定到 ready URL

当 `shell_execute` 返回 `runMode=background_service` 且 `service.status=ready` 时，返回给模型的 `nextSuggestedTool` 仍为 `debug_open_page`，并要求使用 `service.url`。

后续可把最近一次 ready preview service 写入 run 内部状态，使 `debug_open_page` 对同端口目标做一致性校验。首版不强制新增状态表，先保证工具返回结构和提示流能稳定闭环。

### 5.5 对齐交付快照启动解析

`apps/api/src/services/task-session-website-preview-snapshot-service.ts` 也会解析 manifest/package 并启动预览服务。它的端口与启动命令判断需要和 `AltusManagedToolRuntime` 对齐：

1. 固定 Web Shell 默认端口为 `8080`，不是泛化默认 `3000`。
2. manifest 有 healthcheck 时，使用同一健康检查语义。
3. 不再在完成态截图里重新猜一套不同启动规则，避免 Actions 视觉检测和交付卡片截图得出相互矛盾的结论。

首版可以抽出一个轻量 helper，例如 `altus-preview-service-contract.ts`，只负责从 manifest/package/命令解析：

```ts
{
  command: string;
  port: number;
  url: string;
  healthPath?: string;
  healthUrl?: string;
  source: 'manifest' | 'package_script' | 'oneceo_fixed_shell' | 'command';
  persistent: boolean;
}
```

如果为了控制 diff，也可以先在两个服务内保持局部实现一致，但测试必须锁住相同输入输出。后续再抽 helper。

## 6. 泛化能力

这个能力泛化到后续网站预览时，不依赖“某次模型是否聪明”，而依赖平台的四个稳定约束：

1. **契约解析**：启动命令、端口、健康检查来自 manifest/package/固定模板，不来自模型临场猜测。
2. **生命周期托管**：长驻服务必须通过 `background_service` 启动，写 pid/log，有限时间健康检查。
3. **调试入口唯一**：`debug_open_page` 使用托管服务返回的 ready URL，而不是模型自行猜端口。
4. **失败分层**：
   - 构建失败：停在 build 日志。
   - 启动失败：看 service log。
   - 健康检查失败：看 health URL 和端口探测。
   - 页面视觉失败：看 `debug_open_page` / Playwright 截图诊断。

这样后续即使是 Vite、Next、静态 HTML、固定 Web Shell，都走同一类协议：先声明/解析服务契约，再托管启动，再打开浏览器。

## 7. 自检矩阵

| 场景 | 修复前行为 | 修复后行为 | 判定 |
| --- | --- | --- | --- |
| `PORT=8080 node dist/index.js` | 前台执行，命令不退出，最后 `deadline_exceeded` | 自动进入 `background_service`，返回 ready URL | 通过 |
| `node dist/index.js` 固定壳 | 可能 timeout 或被模型改写成 ad-hoc 后台命令 | 默认端口 `8080`，健康检查 `/api/system/health` | 通过 |
| `runMode=foreground` + 固定壳启动 | 等待到 timeout | 快速失败，提示使用平台托管 | 通过 |
| 构建失败 | 可能继续尝试启动 | 停在构建错误，不能进入预览服务 | 通过 |
| 服务启动后 root 页面有问题但 health ok | 可能混淆为启动失败 | 启动 ready，视觉检测再报告页面问题 | 通过 |
| `debug_open_page` 同 URL 失败两次 | 继续重复打开或浪费轮次 | 保持 repeat block，要求先修服务/文件 | 通过 |
| 完成态截图服务 | 可能把固定壳端口猜成 3000 | 与托管启动一致使用 8080/manifest 端口 | 通过 |

## 9. 风险与边界

1. 本方案不解决用户项目自身运行时报错；它只保证平台能稳定启动并打开正确的预览服务。
2. 如果项目没有 manifest/package，也不是固定壳，平台不应强猜启动命令。
3. 如果端口被已有服务占用，托管启动应返回 `already_running` 或结构化占用信息，不能静默换端口。
4. 不能删除 `debug_open_page_repeat_blocked`，它是防止重复无效打开的保护。
5. 不应把修复做成提示词提醒；提示词可以补充，但平台必须在工具层强制正确生命周期。
