# 2026-04-19 管理后台部署管理工作台方案 [20260419-2340已采用]

## 1. 背景

当前 oneceo 的部署能力已经不是空壳：

1. 用户态部署工作台已经能展示真实 `deployment panel`、部署历史、日志、URL 与模板基线。
2. 部署主链真实状态已经沉淀在现有任务会话与 deployment runtime 服务里，而不是只存在前端临时状态中。
3. 管理后台已经有：
   - `用户管理`
   - `对话管理`
   - `Sandbox 管理`
   这些运行治理入口，但还没有一个专门承接“部署结果巡检、归因和追踪”的一级工作台。

这会带来三个直接问题：

1. 管理员想排查“某个用户最近为什么部署失败”时，只能先找用户，再点对话，再在对话里人工判断部署状态，路径过长。
2. 管理员想看“最近哪些对话触发了 deploy / redeploy / rollback”时，没有统一索引页。
3. 当前部署相关事实已经存在，但后台没有把它收敛成“按部署 / 按对话 / 按用户”可切换的治理视图。

因此，本轮不是重做用户态部署工作台，而是在 `admin_management` 中补一个**部署管理显示工作台**，让部署问题可以从管理视角被统一观察、定位和追溯。

## 2. 目标

### 2.1 本轮明确包含

1. 在管理后台新增与 `用户管理`、`对话管理` 同级的 `部署管理` 一级入口。
2. 部署管理页支持三种只读治理视角：
   - 按部署记录
   - 按对话会话
   - 按用户
3. 让管理员可以从：
   - `用户管理`
   - `对话管理`
   - 后续可扩的 `Sandbox 管理`
   快速跳到部署详情，而不是重新搜索。
4. 统一展示真实部署事实：
   - 当前状态
   - 最近 URL
   - deploymentId
   - 历史 deployments
   - logs
   - 归属用户 / 对话 / Sandbox
5. 保持 URL 深链和来源路径，刷新页面后尽量回到同一工作上下文。

### 2.2 本轮明确不包含

1. 不在后台新增直接 `deploy / redeploy / rollback` 按钮。
2. 不新增第二套部署 runtime。
3. 不改用户态部署工作台的业务语义。
4. 不把部署面板的真实来源改成 Redis-only 或前端拼装。
5. 不做部署供应商切换、权限体系、多租户配额治理。

说明：

本轮关键词是“**显示与治理观察**”，不是“后台直接代替用户执行部署动作”。这样路径最短，也符合当前需求描述。

## 3. 现有事实

### 3.1 管理后台当前结构

1. `apps/admin_management/web/src/App.tsx` 里当前已有一级模块：
   - `Sandbox 管理`
   - `对话管理`
   - `用户管理`
   - `审计日志`
   - `KVM 管理`
   - `智能体管理`
   - `技能管理`
   - `连接器 Guide`
   - `OSAC 版本`
2. 当前 `NAV_ITEMS` 里还没有 `部署管理`。
3. `用户管理` 已经具备：
   - URL 深链状态
   - 详情抽屉
   - 打开对话详情
   - 打开 Sandbox 详情
4. `对话管理` 已经具备：
   - 会话索引列表
   - 对话详情弹窗
   - `AdminDetailOrigin` 来源路径链路

这意味着后台已经有“**一级页 + 来源跳转 + 详情弹层 + URL 状态恢复**”的成熟模式，新部署页应直接复用这套结构，而不是另起炉灶。

### 3.2 部署真实数据当前所在位置

当前部署真相源已经存在于现有主链服务里：

1. `apps/api/src/services/task-session-deployment-runtime-service.ts`
2. `apps/api/src/services/railway-deployment-service.ts`
3. `apps/api/src/services/direct-mode-deployment-capability-service.ts`
4. 用户态 `TaskCreationDeploymentInfo`

当前已存在的关键真实字段包括：

1. `deploymentId`
2. `latestStatus`
3. `latestUrl` / `latestStaticUrl`
4. `domains`
5. `deployments`
6. `logs`
7. `missing`

因此后台部署页不应重新定义部署状态，也不应引入“后台专属 deployment 表意”。应直接基于现有 deployment panel 与 task session 归属关系做管理视图聚合。

### 3.3 管理后台当前缺口

当前 `apps/admin_management/server` 与 `apps/admin_management/web/src/api.ts` 中还没有现成的部署管理 BFF 路由和类型。

也就是说：

1. 后台有用户页、对话页、Sandbox 页
2. 前台有 deployment panel
3. 但后台还没有“内部管理态部署聚合接口”

所以本轮设计必须补齐一条最小闭环：

`apps/api internal admin route -> apps/admin_management BFF -> admin_management web`

## 4. 核心决策

### 4.1 新增独立一级模块，而不是把部署信息继续塞进旧页面

本轮采用：

**在 `运行管理` 分组下新增 `部署管理` 一级页。**

原因：

1. 用户管理和对话管理各自已经很重，再继续塞部署索引会让页面职责发散。
2. 部署问题天然是横跨用户、对话、Sandbox、provider 的运行治理问题，适合独立工作台。
3. 独立一级页后，`用户管理` 与 `对话管理` 可以作为“来源入口”，而不是被迫承载完整部署索引。

### 4.2 部署管理页采用三视角，而不是三套页面

本轮采用单页三视角切换：

1. `部署记录`
2. `对话部署`
3. `用户部署`

而不是新增三个一级模块或三个互不相关的二级页面。

原因：

1. 用户明确希望“可以基于用户管理、基于对话管理”等维度查看。
2. 这三类视角共享同一批底层部署事实，只是聚合维度不同。
3. 单页三视角更符合管理后台现有“工作台”风格，也便于共享筛选和详情弹层模式。

### 4.3 第一阶段只读，不做动作型后台

本轮部署管理页只做：

1. 查询
2. 聚合
3. 展示
4. 跳转
5. 问题归因

不做：

1. 后台触发发布
2. 后台回滚
3. 后台重发

原因：

1. 用户当前要求是“增加部署管理显示”。
2. 后台动作会引入额外权限边界、确认交互和责任归属，不适合作为第一阶段顺手带上。
3. 只读方案可以最快补齐治理视图，又不影响现有用户态动作语义。

## 5. 页面信息架构

### 5.1 导航位置

建议在 `运行管理` 分组下新增：

- `部署管理`
  - tag：`DEP`
  - subtitle：`部署状态与归因`
  - signal：`发布结果`

推荐放在：

`Sandbox 管理` 与 `对话管理` 之间，原因是它在运行治理里比 `审计日志` 更高频，同时与会话和 Sandbox 强关联。

### 5.2 页面骨架

延续当前 admin_management 的统一骨架：

1. 页面摘要条
2. 视角切换条
3. 筛选工具栏
4. 索引表
5. 居中详情弹层

不额外引入复杂左右分栏，原因是：

1. 部署记录本身天然适合索引表扫描。
2. 详情日志和历史部署更适合进入弹层或二级 tab。
3. 当前后台已经在 `用户管理`、`对话管理` 上证明“索引 + 浮层详情”更稳。

## 6. 三种视角设计

### 6.1 视角一：部署记录

目标：回答“最近发生了哪些部署、结果如何、属于谁、属于哪个会话”。

建议列表列：

1. `部署`
   - deploymentId
   - provider / service / environment
2. `状态`
   - latestStatus
   - 当前是否有 public URL
3. `对话`
   - session title
   - taskSessionId
4. `用户`
   - displayName / email
5. `最近访问地址`
   - latestUrl / latestStaticUrl
6. `更新时间`
7. `操作`
   - 查看详情

说明：

1. 这是默认视角。
2. 该视角按“每个 task session 当前 deployment panel”展开，不在第一阶段额外做 provider 原生 deployment 全量镜像页。
3. 如果一个会话有多次部署，索引行展示当前面板摘要，历史部署进入详情看。

### 6.2 视角二：对话部署

目标：回答“哪些对话触发过部署，它们当前部署处于什么状态”。

建议列表列：

1. `对话`
   - title
   - taskSessionId
2. `用户`
3. `会话状态`
4. `部署状态`
5. `最近部署`
   - deploymentId
   - 最近发布时间
6. `公网地址`
7. `操作`

说明：

1. 该视角偏“从对话排障进入部署”。
2. 它和当前 `对话管理` 不重复，重点不是消息和 runtime，而是 deployment 结果。
3. 点进详情后应能继续跳去完整对话详情。

### 6.3 视角三：用户部署

目标：回答“某个用户最近部署是否异常、成功率如何、主要失败集中在哪些会话”。

建议列表列：

1. `用户`
2. `最近部署状态`
3. `部署次数`
4. `成功次数`
5. `失败次数`
6. `最近部署时间`
7. `最近部署会话`
8. `操作`

说明：

1. 这是“基于用户管理”观察部署的主入口。
2. 第一阶段聚合维度以“最近 30 天 / 当前筛选结果”即可，不做复杂时序图。
3. 点开详情后展示该用户最近部署过的会话与状态列表。

## 7. 详情弹层设计

详情弹层建议统一使用二级 tab：

1. `概览`
2. `历史部署`
3. `日志`
4. `关联对象`
5. `原始状态`

### 7.1 概览

展示：

1. 当前部署状态
2. 当前 URL / 域名
3. 当前 deploymentId
4. provider / project / service / environment
5. 最近更新时间
6. bindingState / canDeploy / missing 摘要

### 7.2 历史部署

展示：

1. 当前 session 对应的 `deployments[]`
2. 每条 deployment 的：
   - id
   - status
   - createdAt / updatedAt
   - url

### 7.3 日志

展示：

1. 当前 session 对应的 deployment logs
2. 默认只展示近期日志
3. 不做实时 tail，保持静态刷新模型

### 7.4 关联对象

展示可跳转关系：

1. 用户
2. 对话
3. Sandbox

动作：

1. 在用户管理中查看
2. 在对话管理中查看
3. 在 Sandbox 管理中查看

### 7.5 原始状态

展示：

1. deployment panel 原始 JSON
2. deploymentState / metadata 摘要

用途：

1. 让管理员定位“UI 层解释错误”还是“底层状态本身异常”
2. 避免为了排障又回到数据库或日志系统里找原始结构

## 8. 与现有页面的联动

### 8.1 用户管理

当前 `用户管理` 已有 `概览 / 对话 / Sandbox` 三个详情 tab。

本轮建议新增：

1. `部署` tab
2. 展示该用户最近部署过的会话摘要
3. 每条记录默认入口为“打开部署详情”

同时保留页面跳转动作：

1. `在部署管理中查看`

跳转规则：

1. 自动切到 `部署管理`
2. 视角切到 `用户部署`
3. 自动带上 `userId`
4. 保留来源路径，例如：
   - `用户管理 / 张三 / 部署 / deployment_xxx`

### 8.2 对话管理

当前 `对话管理` 已有会话详情弹窗和来源链路。

本轮建议在对话详情中新增一个轻量部署区块，放在现有运行绑定/基础信息附近，显示：

1. 当前 deployment 状态
2. 最近 URL
3. deploymentId
4. 查看完整部署详情

跳转规则：

1. 可在当前页上方弹出部署详情浮层
2. 也可进入 `部署管理` 并自动切到 `对话部署`

### 8.3 Sandbox 管理

第一阶段不要求在 Sandbox 管理中新增完整部署 tab，但建议在 runtime detail 或关联信息区补一个“关联部署”跳转入口。

原因：

1. 部署与 Sandbox 有链路关联，但当前用户要求重点是基于用户、基于对话。
2. Sandbox 作为次级入口保留即可，不需要本轮抢主轴。

## 9. 筛选与深链

### 9.1 通用筛选项

部署管理页建议统一提供：

1. 关键词
   - taskSessionId
   - deploymentId
   - 用户邮箱
   - 对话标题
2. 状态
   - 全部
   - success / failed / pending / building / unknown
3. 最近更新时间
4. 是否存在公网 URL

### 9.2 视角专属筛选

`对话部署` 增加：

1. 会话状态
2. executor

`用户部署` 增加：

1. 用户状态
2. 最近登录活跃度

### 9.3 URL 深链

延续当前后台 query string 模型，新增：

1. `section=deployment`
2. `dep_view=records|conversations|users`
3. `dep_q`
4. `dep_status`
5. `dep_has_url`
6. `dep_session`
7. `dep_user`
8. `dep_detail`
9. `dep_tab`

要求：

1. 刷新后可恢复当前视角、筛选与已打开详情。
2. 从用户管理、对话管理跳过来时，来源路径继续保留。

## 10. 数据接口与服务设计

### 10.1 设计原则

后台部署页必须复用现有 deployment truth source，不重新定义部署状态。

采用链路：

1. `apps/api` 增加 internal admin deployment routes
2. `apps/admin_management/server` 增加 deployment management BFF
3. `apps/admin_management/web` 增加 deployment page API/types/component

### 10.2 建议新增 API

#### apps/api internal

建议新增：

1. `GET /api/internal/admin/deployments/overview`
2. `GET /api/internal/admin/deployments`
3. `GET /api/internal/admin/deployments/conversations`
4. `GET /api/internal/admin/deployments/users`
5. `GET /api/internal/admin/deployments/task-sessions/:taskSessionId`

说明：

1. 第 1 个接口返回摘要卡统计。
2. 第 2~4 个接口分别承接三种索引视角。
3. 第 5 个接口返回单个会话的 deployment detail，供详情弹层复用。

#### apps/admin_management BFF

建议新增：

1. `apps/admin_management/server/routes/deployment-management-routes.ts`
2. `apps/admin_management/server/services/deployment-management-service.ts`
3. `apps/admin_management/server/connectors/oneceo-api-connector.ts` 对应 deployment types / methods

### 10.3 详情聚合口径

单条部署详情建议至少包含：

1. `taskSession`
2. `user`
3. `sandboxBinding`
4. `deploymentPanel`
5. `latestDeployment`
6. `deployments[]`
7. `logs[]`
8. `templateBaselineSummary`（如已有真实可用快照则带出）

注意：

1. 这里复用现有 task session deployment response 的真实字段。
2. 不允许后台自己再拼一套“简化版 deployment status 机读枚举”覆盖原值。

## 11. 前端落点建议

建议新增或修改的文件：

1. `apps/admin_management/web/src/App.tsx`
2. `apps/admin_management/web/src/api.ts`
3. `apps/admin_management/web/src/types.ts`
4. `apps/admin_management/web/src/components/DeploymentManagementSection.tsx`
5. `apps/admin_management/web/src/components/adminViewState.ts`
6. `apps/admin_management/web/src/components/UserManagementSection.tsx`
7. `apps/admin_management/web/src/styles.css`

约束：

1. `部署管理` 也应走 `React.lazy`，不要继续膨胀入口包。
2. 页面状态默认值放进 `adminViewState.ts`，与 `用户管理 / 技能管理 / OSAC 版本` 现有做法一致。
3. 不要把部署管理实现重新塞回 `App.tsx` 的大段 JSX 中。

## 12. 风险与约束

### 12.1 风险

1. 单个 deployment detail 若直接全量透出 logs，弹层体积可能过大。
2. 用户聚合视角如果实时统计跨度过大，列表查询可能变重。
3. 对话、用户、部署三页都能打开部署详情时，来源路径和弹层层级要避免打架。

### 12.2 收敛策略

1. 第一阶段日志只取近期窗口，不做无限滚动。
2. 用户聚合先按当前筛选窗口和有限时间范围聚合。
3. 统一复用当前 `AdminDetailOrigin` 语义，不发明第二套来源链。

## 13. 验收标准

方案落地后应满足：

1. 管理后台新增 `部署管理` 一级入口。
2. 管理员可在一个页面里切换：
   - 部署记录
   - 对话部署
   - 用户部署
3. `用户管理` 可以进入某用户相关部署详情。
4. `对话管理` 可以进入某会话相关部署详情。
5. 部署详情展示真实字段：
   - status
   - deploymentId
   - url
   - deployments
   - logs
6. 后台不引入新的部署真相源，只复用现有 deployment panel 与 runtime 服务。
7. 页面刷新后能恢复当前部署视角、筛选与详情状态。
8. 第一阶段不出现后台直接 deploy / redeploy / rollback 按钮。

## 14. 待你审核的关键决策

这份方案默认了以下三点，请你重点审核：

1. `部署管理` 是否接受作为新的一级模块，而不是继续挂在 `对话管理` 或 `用户管理` 下面。
2. 第一阶段是否接受“只读治理页”，不在后台直接提供部署动作。
3. `用户管理` 是否接受新增 `部署` tab，`对话管理` 是否接受新增部署摘要区和跳转入口。
