# 20260419 多语言网站部署判定与误部署拦截 Playwright 测试方案 [20260419-1816已采用]

## 1. 测试目标

从第一性原理出发，本轮测试只验证两件事：

1. 用户要求生成“网站类程序”时，平台最终产出的代码是可部署的，并且部署后可以访问，从而完成交付。
2. 用户要求生成“非网站类程序 / 纯脚本”时，平台不会错误地把这类产物识别为网站并发起部署。

也就是说，本轮测试不关注语言本身，而关注：

- 产物是否具备“可对外访问的网页应用”属性
- 平台是否做出了正确的“应该部署 / 不应该部署”判定

## 2. 范围与原则

### 2.1 覆盖范围

覆盖以下技术形态：

1. HTML
2. JavaScript（前端网页）
3. Node.js（服务端网页）
4. Python（服务端网页）
5. Java（服务端网页）
6. PHP（服务端网页）

同时覆盖每种技术对应的“非网站脚本”或“离线产物”场景。

### 2.2 判定原则

只有当产物满足以下条件时，才应该被视为“可部署网站”：

1. 存在明确网页入口或 Web 服务入口
2. 产物目标是对外访问，而不是本地一次性执行
3. 部署后应当返回可访问公网地址

以下情况不应进入网站部署链路：

1. CLI / 批处理 / 数据处理脚本
2. 一次性工具脚本
3. 本地离线产物
4. 邮件模板、静态片段、非站点 HTML 资产

## 4. 每条测试用例设计

### 4.1 WD-HTML-01 纯静态 HTML 网站应成功部署

- 用户提示词：
  - “帮我做一个纯 HTML/CSS/少量原生 JS 的企业官网，需要首页、产品页、公司介绍页和联系页，并直接完成部署。”
- 关键验证：
  1. 会话完成后工作区存在站点入口，如 `index.html`
  2. 触发部署链路
  3. 部署接口返回公网地址
  4. 公网页面返回 200，正文包含企业官网核心内容
- 通过标准：
  - 成功发布到 Railway，且页面能正常访问

### 4.2 WD-JS-01 前端 JavaScript 网站应成功部署

- 用户提示词：
  - “用 JavaScript 做一个产品展示网站，使用 Vite 或同类前端工程化方式，完成后部署。”
- 关键验证：
  1. 工作区存在 `package.json`、前端入口和构建产物所需结构
  2. 部署工具被正确调用
  3. 部署成功后页面标题和正文符合提示词
- 通过标准：
  - 公网地址可访问，页面不是默认模板或空白页

### 4.3 WD-NODE-01 Node.js 网站应成功部署

- 用户提示词：
  - “用 Node.js 做一个带产品列表和联系表单的网站，完成后直接部署。”
- 关键验证：
  1. 生成 Express/Koa/Fastify 等 Web 服务代码
  2. 存在可识别的启动入口和健康检查能力
  3. 部署成功并能返回网页内容
- 通过标准：
  - 部署面板进入成功态，公网可访问

### 4.4 WD-PY-01 Python 网站应成功部署

- 用户提示词：
  - “用 Python 做一个公司官网，可以用 Flask/FastAPI/Django，完成后直接部署。”
- 关键验证：
  1. 生成 Python Web 框架项目结构
  2. 部署链路选择正确模板和运行方式
  3. 公网页面可访问且内容正确
- 通过标准：
  - 成功部署，不出现把 Python 项目误当成纯脚本的情况

### 4.5 WD-JAVA-01 Java 网站应成功部署

- 用户提示词：
  - “用 Java 做一个企业官网，完成后直接部署上线。”
- 关键验证：
  1. 生成 Java Web 项目，而不是单个 `main`
  2. 部署链路识别到 Java Web 服务
  3. 成功返回公网地址
- 通过标准：
  - 部署完成且线上页面可访问

### 4.6 WD-PHP-01 PHP 网站应成功部署

- 用户提示词：
  - “用 PHP 做一个展示型网站，包含首页、产品页和联系页，完成后直接部署。”
- 关键验证：
  1. 生成可对外访问的 PHP 网页结构
  2. 部署链路执行成功
  3. 公网页面包含业务内容
- 通过标准：
  - 不出现只生成若干 PHP 文件却无法发布的情况

### 4.7 ND-HTML-01 HTML 离线产物不应误部署

- 用户提示词：
  - “帮我写一个 HTML 邮件模板，只需要导出源码，不需要部署网站。”

  2. 不应触发部署工具
  3. 不应出现部署成功胶囊、部署公网地址或 deployment run
- 通过标准：

### 4.8 ND-JS-01 JavaScript 工具脚本不应误部署

  1. 交付的是工具脚本或模块
  2. 不应触发部署工具
  3. 不应出现 deployment panel 成功态
- 通过标准：

### 4.9 ND-NODE-01 Node.js CLI 不应误部署

  2. 不应生成站点部署结果
  3. 不应出现公网地址

### 4.10 ND-PY-01 Python 脚本不应误部署

- 用户提示词：

- 关键验证：
  1. 交付的是脚本 / notebook / 报表逻辑
  2. 不触发部署链路
  3. 不生成 deployment 信息
- 通过标准：
  - 只交付脚本成果，不发布

### 4.11 ND-JAVA-01 Java Console 程序不应误部署

- 用户提示词：

### 6.3 本轮新增修复结论

本轮真实回归暴露并修复了一个平台级判定缺口：

- 服务端模板项目（典型为 Flask/Jinja）原先只按固定 `index.html` 路径做 analytics 注入与合规检测
- 这会让 Python 网站在 deploy run 中反复触发 `missing_analytics_entry`
- 修复后改为“固定候选 + 服务端模板目录扫描”，部署链路已通过 `WD-PY-01` 与 `WD-PHP-01` 真实验证
2. 是否调用 `deploy_application` / `redeploy_application` / `rollback_application_deployment`
3. 是否生成公网地址或进入 deployment success 状态

## 6. 当前执行结论（2026-04-19）

截至当前，真实会话矩阵已验证出以下事实：

1. `WD-HTML-01` 已通过。
2. `WD-JS-01` 已通过。
3. `WD-NODE-01` 首次回归失败，失败原因不是 Railway 资源未创建，而是：
   - Railway 面板与平台 deployment panel 均进入 `SUCCESS / ready`
   - 但公网首页实际返回 500
   - Railway 运行日志明确报错 `layout is not defined`

这说明现有平台仍存在一条必须修复的主链缺口：

- “部署供应商状态成功” 被错误等同为 “最终用户交付成功”

因此本测试方案在实施阶段新增一条平台约束：

1. deploy / redeploy 成功必须同时满足：
   - Railway 返回成功终态
   - 公网 URL 健康验证通过，且不是错误页
2. 如果公网仍返回 4xx / 5xx 或明显错误页，平台必须保留失败态，让 Altus 继续修复，而不是提前 `complete_task`。
2. 是否出现 `deploy_application`
3. 是否出现 deployment 成功胶囊
4. `GET /deployment` 是否仍停留在未初始化态

5. 不返回公网地址

## 9. 当前建议

本轮实现优先级建议如下：

1. 先实现 12 条 case 的测试矩阵文档与 case 配置
2. 再落地两份 Playwright E2E 主脚本
3. 最后把报告输出汇总成单独 JSON 目录，便于后续回归比较

这样可以先把“判定规则”固定下来，再进入真实脚本实现，避免测试先写死错误业务假设。
