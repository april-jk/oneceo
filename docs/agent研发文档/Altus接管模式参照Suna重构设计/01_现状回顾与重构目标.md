# 01 现状回顾与重构目标

## 1. 当前 Altus managed 链路

当前 managed mode 的主链路由以下模块组成：

- 前端入口：`apps/web/client/src/hooks/useTaskCreationAgent.ts`
- WebSocket 入口：`apps/api/src/agents/task-creation/websocket-service.ts`
- 主编排服务：`apps/api/src/agents/task-creation/task-creation-service.ts`
- 三层 Agent：
  - `intent-recognition-agent.ts`
  - `planning-agent.ts`
  - `execution-plan-agent.ts`
- 状态与消息：
  - `taskCreationFileMemoryStore`
  - `taskCreationSessionDAO`

现状流程：

1. 前端发送 `user_input`
2. WebSocket 服务进入 `handleUserMessage`
3. `TaskCreationService.createTask` 串行执行三层 Agent
4. 如果进入执行阶段，再通过现有 sandbox / OSAC / OpenCode 体系继续执行
5. 前端通过 WebSocket + SSE + 历史拉取混合恢复界面

## 2. 当前架构的核心问题

### 2.1 会话对象职责混杂

当前 `task_session` 同时承担：

- 对话容器
- 规划过程容器
- sandbox runtime 绑定容器
- executor 绑定容器
- UI 恢复容器

这导致 managed mode 无法像 Suna 一样形成清晰的：

- `thread`
- `run`
- `stream`

三层分工。

### 2.2 没有独立的 run 对象

Suna 的核心是 `thread 上可反复启动 agent_run`。

当前 oneceo managed mode 没有独立 run：

- 用户一条消息直接把整个 `TaskCreationService` 跑到底
- 中断、恢复、重试只能围绕 `session` 打补丁
- 无法表达多次运行、并行运行、失败运行、重试运行

### 2.3 状态源不单一

当前 managed mode 同时依赖：

- `file-memory-store`
- `taskCreationSessionDAO`
- WebSocket 实时消息
- SSE 补流

这会造成：

- 页面刷新恢复复杂
- 权威状态难判断
- 中断与续跑边界不清晰

### 2.4 三层 Agent 不是对话型执行架构

当前三层 Agent 更像“任务创建表单自动化”：

- Layer 1：分类
- Layer 2：结构化任务描述
- Layer 3：执行计划

它不是 Suna 那种围绕一个 thread 做连续 reasoning、tool call、streaming、artifact 交付的运行形态。

### 2.5 managed 与 direct 模式耦合过深

当前 managed 与 direct 共用：

- session
- WebSocket 入口
- 部分 runtime 恢复逻辑
- 前端消息合并逻辑

这让 managed 重构时非常容易误伤 direct。

## 3. 重构目标

本次设计的目标是把 Altus managed mode 改造成：

1. **Suna 风格的 thread/run 架构**
   - `task_session` 作为 thread-like session
   - 新增 `managed run`

2. **单一权威状态体系**
   - `DB` 存消息与会话状态
   - `run stream` 仅负责实时推送

3. **工具驱动执行**
   - 不再以“三层 Agent 结果 + OpenCode 执行补充”作为核心
   - 改为 `Altus runner + tool runtime + E2B sandbox`

4. **直通模式完全隔离**
   - direct mode 保持现状
   - managed mode 新链路不侵入 direct executor

5. **E2B 替代 Suna sandbox**
   - 参照 Suna 的 agent architecture
   - 但 sandbox 执行底座固定为 oneceo 的 E2B

## 4. 重构后的高层口径

重构完成后，Altus managed 的一句话定义应变为：

> 用户在一个会话里发起一条 managed 消息，后端创建一个 Altus run，run 读取该会话历史与连接器上下文，装配工具与 E2B sandbox，持续产生 assistant/tool/event 流，直至 run 完成。

这与当前“发一条消息就进入 TaskCreationService 三层串行流程”的定义完全不同。

## 5. 不在本次范围内的内容

以下内容明确不纳入本次重构：

1. OpenCode / Codex / ClaudeCode 直通模式
2. 连接器 profile 体系的重新设计
3. Admin 管理后台的全面改版
4. CEO View / Task Detail 等旧业务 Agent 的重构

本次只改：

- Altus 接管模式的对话体系
- Altus 接管模式的命令执行体系
- Altus 接管模式对应的前后端接口与状态流

## 6. Suna 代码参照

本篇关于“为什么要从 `session-only` 改成 `session + run`”的判断，开发时优先回查以下 `suna` 源码：

- `referance/suna/backend/core/threads/repo.py` -> `create_thread_with_message_and_run(...)`
  - 说明 `thread` 与 `run` 是同时创建但彼此独立的两个对象。
- `referance/suna/backend/core/threads/repo.py` -> `create_message_full(...)`、`get_thread_messages(...)`
  - 说明历史消息属于 `thread` 容器，而不是执行态缓存。
- `referance/suna/backend/core/agents/repo.py` -> `create_agent_run_with_id(...)`、`update_agent_run_status(...)`
  - 说明 run 是一等实体，拥有独立状态流转。
- `referance/suna/backend/core/agents/api.py` -> `start_agent_run(...)`、`_background_setup_and_execute(...)`
  - 说明用户输入落库与 run 启动是两步，不是一次 WebSocket 请求里同步串完全部流程。
- `referance/suna/backend/core/agents/runner/executor.py` -> `execute_agent_run(...)`
  - 说明真正执行围绕 run 展开，而不是围绕 thread/session 本身展开。
- `referance/suna/backend/core/agents/api.py` -> `stream_agent_run(...)`
  - 说明实时流绑定 run，不绑定 executor session 或 WebSocket 进程态。
