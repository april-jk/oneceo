# AGENTS Git 协作开发指南

本文用于指导 `oneceo/` 仓库内的多人协作、分支边界、冲突处理与跨系统协作原则。

## 多人多系统协作前提

这是一个多人同时开发、并且跨 `macOS / Windows / Linux` 的仓库，Git 协作目标不是“我本地能提交就行”，而是：

1. 不干扰其他开发者正在进行的改动
2. 不盲目覆盖别人的文件
3. 不盲目合并自己没看懂的冲突
4. 不把本机环境差异误提交成业务改动

因此必须额外遵守下面这些规则。

## 分支与工作方式

- 当前主集成分支是 `task-creation-agent`，日常开发成果默认先汇入该分支。
- `develop` 是研发测试分支，所有协作者可推送。
- `staging` 是预发布分支，仅 `april-jk` 可管理和推送，且只能由 `task-creation-agent` 推进。
- `product` 是产品分支，仅 `april-jk` 可管理和推送，且只能由 `task-creation-agent` 推进。
- 不要把旧 worktree、旧分支或别的机器路径当成当前事实。
- 若需新建临时分支，建议围绕单一主题命名，避免泛化名称。
- 如果发现工作区里有你未创建的变更，先判断是否和当前任务同文件、同主题：
  - 同文件或强相关：先读懂，再决定是否继续
  - 无关文件：不要回退、不要整理、不要顺手修

## 受保护分支协作要求

- 非 `april-jk` 不得直接向 `staging`、`product` 推送。
- 即使是 `april-jk`，也不得从个人分支、临时分支或 `develop` 直接推进到 `staging`、`product`。
- `staging`、`product` 的更新来源必须是 `task-creation-agent`，这样才能保证预发布与产品分支都基于同一条已集成主线。

## 修改边界规则

- 只修改与你当前任务直接相关的文件。
- 不得为了“顺手统一风格”批量改动无关文件。
- 不得提交以下高风险噪音：
  - 本机路径
  - 系统特有换行符噪音
  - 无意义格式化
  - `.DS_Store`
  - 临时日志
  - 本地缓存
  - 构建产物，除非任务明确要求
- 修改前如果文件已经有未提交改动，先看清楚这些改动是否可能属于其他人或其他任务。

## 禁止事项

- 禁止 `git reset --hard`
- 禁止 `git checkout -- <file>`
- 禁止无理解地解决冲突后直接提交
- 禁止把整份文件用自己的版本直接覆盖掉别人的改动
- 禁止因为本机能运行就替换掉别人的跨平台写法
- 禁止把 rebase / merge 过程中自己没看懂的冲突块直接删掉

## 处理冲突的原则

- 冲突不是“选一边”，而是恢复两边真实意图。
- 解决冲突时至少检查三件事：
  1. 对方改了什么
  2. 你改了什么
  3. 最终结果是否同时保留两边必要逻辑
- 如果冲突涉及以下内容，不能凭感觉处理：
  - 认证
  - Sandbox 生命周期
  - OSAC / MCP
  - 连接器
  - 会话状态机
  - Redis key / stream / TTL

## 跨系统注意事项

- 注意 `macOS / Linux / Windows` 的差异：
  - 路径分隔符
  - 大小写敏感性
  - 换行符
  - shell 命令可用性
  - 本地绝对路径
- 提交前要确认没有把某个平台专用写法误改成只适配你当前系统。
- 文档示例若写绝对路径，必须确保是当前仓库真实需要，不要把本机历史路径提交进去。

## 不应做的事

- 不要为了“看起来兼容”保留明显过时的文档叙述。
- 不要在未核对代码现状前复用旧提交模板或旧接口说明。
- 不要把 KVM 历史链路误当作当前主执行方案提交进去。
- 不要把“多人协作仓库”当成单人本地仓库使用。
