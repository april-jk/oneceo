## 1.1 当前已落地范围

本轮已落地的最小实现范围如下：

1. `task_creation_sessions.metadata_json.sessionSkillState` 作为 DB 真相源
2. Redis 仅在显式启用时承担会话级 skill state 热缓存
3. sandbox workspace 内引入 `.oneceo/session-memory/skills-memory.json` 作为运行时文件记忆
4. Altus 直通链路在用户多轮输入时，不再依赖当前轮重复传入 `metadata.skills`
5. Altus 直通链路改为优先读取 session resident skills，并按当前上下文重新决定是否继续挂载 contextual skills
6. `source=agent` 的内部追问/续跑沿用既有 resident selections，不在中途错误洗掉 skills

本轮暂不额外扩展新的持久化介质，也不引入 DB delta stream / 高频回写机制。

## 2. 问题定义

当前 `oneceo` 的 skills 主链问题有两个：

1. 首轮主要依赖 `metadata.skills`、`managedSkillCatalog`、`managedSkillContext`
2. 后续澄清、resume、retry 如果当前轮没有再次携带完整 skill metadata，就会丢失执行态 skill

更底层的问题是，当前实现容易把下面三件事混成一件事：

1. 用户显式选中了哪些 skills
2. 当前轮 prompt 真正注入哪些 skills
3. sandbox 当前驻留哪些 skills 文件

这会导致：

1. 多轮对话里 prompt 约束不稳定
2. direct / managed 行为不一致
3. sandbox skill sync 和 prompt 激活状态耦合，造成不必要的 OpenCode 重启
4. 一旦 sandbox 丢失，skills 的恢复路径不够明确

## 3. oneceo 项目约束

本方案必须服从下面这些项目事实，不能照搬 ClaudeCode 的纯本地文件系统模型。

### 3.1 skills 是平台化对象，不是本地目录真相源

当前 skills 来源于：

1. 平台 skill + published revision
2. 用户启用绑定
3. 用户 custom skill
4. governance 配置

所以 session 中只能保存“轻量引用状态”，不能把大块 skill markdown 当真相源长期塞进 session metadata，也不能假设 API 本机磁盘上永远有一份可复用的 skill 目录。

相关代码：

1. [user-skill-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/user-skill-service.ts#L186)
2. [platform-skill-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/platform-skill-service.ts#L180)

### 3.2 API 服务侧本地文件存储明确不允许

这是本次方案的硬约束：

1. `oneceo` 的 API 服务部署形态是无状态
2. API 容器本地文件不可作为会话恢复依据
3. 任何新的 skills 会话状态都不能落到 API 本机文件
4. 不能把 `file-memory-store.ts` 继续扩展成 skills 真相源

因此：

1. `sessionSkillState` 必须进入数据库
2. Redis 只能作为显式启用时的热缓存
3. API 本地文件只能用于临时调试，不能进入正式方案

### 3.3 sandbox 内文件可以使用，作为“运行时物化副本 + 会话文件记忆”

Altus 实际运行在 sandbox 中，OpenCode / ClaudeCode 运行时真正消费的是 sandbox 内的 skill 文件。

当前 `sandboxSkillSyncService` 会把 skills 物化到类似下面的位置：

1. `/home/user/.config/opencode/skills/platform/<slug>/SKILL.md`
2. `/home/user/.config/opencode/skills/user/<user>/<slug>/SKILL.md`

这类文件的定位必须明确为：

1. 供 sandbox 内执行器读取的运行时副本
2. 供 sandbox 内 runtime 保存当前 session 的文件记忆
3. 这份文件记忆必须跟随项目文件一起归档
4. 归档恢复后可以重新作为当前 session 的工作记忆
5. 它不是 API 服务侧的持久化真相源，真正真相源仍然是 DB

相关代码：

1. [sandbox-skill-sync-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/sandbox-skill-sync-service.ts#L282)
2. [sandbox-skill-sync-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/sandbox-skill-sync-service.ts#L348)

### 3.4 sandbox 侧文件记忆必须在“保存触发点”回写数据库

如果运行过程中 sandbox 内新增了下面这些状态：

1. 新命中的 resident skill
2. tool auto activation 产生的新 binding
3. resident eviction / resident replacement
4. skill runtime 生成的结构化记忆摘要

这些状态都不能只留在 sandbox 文件里，必须在“保存触发点”回写到 API。

本方案不采用“每次变化都直刷 DB”，也不采用“Redis delta stream 再折叠进 DB”的复杂机制。

更合适的原则是：

1. 运行时先写 sandbox 内部的结构化记忆文件
2. 该文件与项目文件一起存在 workspace / archive 中
3. 在明确的保存触发点，把这份文件记忆整体回写 DB
4. Redis 只缓存 DB 中已保存的最新快照，不承担未保存增量日志职责

这样既保留 sandbox 内快速读写能力，也避免把每次细粒度变化都变成 DB / Redis 协议问题。

### 3.5 Redis 只在显式启用时可用，而且不是主真相源

项目已有 Redis 规则：

1. 只有 `ONECEO_REDIS_ENABLED=true` 且 `REDIS_URL` 有效时才允许启用 Redis
2. 未显式启用时，主流程必须继续走 DB / 非 Redis 路径

因此 skills 会话保持的 Redis 角色只能是：

1. DB 快照热缓存
2. 恢复加速层
3. 已保存 sessionSkillState 的读取加速

不能是：

1. 唯一真相源
2. 唯一恢复来源
3. 未保存工作记忆的唯一承载层

2. [task-session-redis-cache-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/task-session-redis-cache-service.ts)

## 4. 明确说明：这里的“文件记忆”到底怎么使用

这一节直接回答本轮新增要求。

### 4.1 三种介质的职责边界

| 介质 | 位置 | 是否持久 | 存什么 | 谁来读 | 丢失后怎么恢复 |
| --- | --- | --- | --- | --- | --- |
| 数据库 | `task_creation_sessions.metadata_json.sessionSkillState` | 是 | 会话级轻量 skill 引用状态 | API 编排层 | 不需要恢复，本身就是真相源 |
| Redis | 现有 session 级 cache namespace 下新增 skill cache | 否，可清空 | DB 中已保存 sessionSkillState 的热缓存、最近一次 resolved resident snapshot | API 编排层 | 命中则直接加速，未命中则回退 DB |
| sandbox 文件 | workspace 内隐藏记忆文件 + skill 物化目录 | 否，随 sandbox 消失；但可随 archive 恢复 | 给 sandbox 内执行器读取的 `SKILL.md`、必要资源物化副本、当前会话文件记忆 | sandbox 内 OpenCode / ClaudeCode / OSAC | 先尝试从 archive 恢复文件记忆，再与 DB 对齐 |

结论：

1. 真正的“会话记忆”必须在数据库
2. Redis 只是已保存状态的可选加速层
3. sandbox 文件既是执行器消费形态，也是当前会话的工作记忆载体
4. API 本地文件不在正式方案内
5. sandbox 内文件允许短时持有“比 DB 更新一点点”的工作记忆，但必须在保存触发点回写

### 4.2 一次首轮运行时，文件记忆如何被使用

首轮流程应该是：

1. 用户输入到达 API
2. API 根据显式选择、governance、intent 生成或更新 `sessionSkillState`
3. 该状态先写入 `task_creation_sessions.metadata_json`
4. 如果 Redis 启用，则同步写入 skill state cache / resolved snapshot cache
5. 同时把 resident manifest 和 session 文件记忆初始化到 sandbox workspace
6. run entry 基于 `sessionSkillState + availableSkills` 解析出：
   - `activeSkillsForTurn`
   - `residentSkills`
7. `sandboxSkillSyncService` 根据 `residentSkills` 把对应 `SKILL.md` 物化到 sandbox
8. sandbox 内 OpenCode / ClaudeCode 只读取这些文件副本执行

也就是说，文件不是记忆本体，文件只是记忆在 sandbox 内的投影。

### 4.3 多轮 continuation / clarification 时，文件记忆如何被使用

后续轮次不再依赖前端是否重复传入完整 `metadata.skills`。

正确流程应该是：

1. API 先从 DB 取回 `sessionSkillState`
2. 如果 Redis 有 cache，可优先命中，但命中失败必须回退 DB
3. run entry 根据“当前轮上下文”重新决定哪些 skill 继续 active
4. 只有 resident 集发生变化时，才重新同步 sandbox 文件
5. 如果 resident 没变化，sandbox 内文件可继续复用，不需要重写也不需要重启 OpenCode
6. sandbox runtime 在本轮内的新增记忆先写入 workspace 内的结构化记忆文件
7. 遇到保存触发点时，再把该文件整体刷回 DB

### 4.4 sandbox 被销毁、重建、恢复时，文件记忆如何被使用

这是本方案必须明确支持的关键场景。

当 sandbox 非持久、文件丢失时：

1. API 不尝试从旧 sandbox 抽取 skill 文件作为恢复真相源
2. API 从 DB 读取 `sessionSkillState`
3. 如果有 archive，可先恢复 workspace 内的文件记忆
4. 再与 DB 中的 `sessionSkillState` 做版本对齐
5. 重新解析 `residentSkills`
6. `sandboxSkillSyncService` 将 resident skills 重新物化到新 sandbox
7. sandbox 内执行器继续工作

所以：

1. 已保存进 DB 的 skills 记忆不会因为 sandbox 丢失而丢失
2. 已归档的文件记忆可以在 restore 后继续使用
3. 只要 DB 里的 `sessionSkillState` 在，resident 文件就可重建

### 4.5 runtime 中 tool 自动激活 skill 时，文件记忆如何被使用

当运行期命中了某个工具自动挂载规则时：

1. sandbox runtime 先在本地 runtime state 文件中登记本次变化
2. 当前 run 内立即把该 skill 视为 active
3. 若该 skill 需要 resident，则增量同步到 sandbox 文件
4. 同时更新 workspace 内的结构化记忆文件
5. 遇到保存触发点时，由 API 把该文件记忆刷回 DB
6. 如果 Redis 启用，则保存成功后刷新 Redis cache

这意味着：

1. runtime 的新增 skill 不会只活在内存里
2. 下一轮 continuation 可以继续恢复

### 4.6 保存触发点定义

本方案把 DB 写入压到明确的保存触发点，而不是每个细粒度变化。

建议初版保存触发点固定为：

1. 用户显式保存 / 明确提交当前阶段
2. run 正常结束
3. sandbox archive 前
4. sandbox replace / restore 切换前
5. 用户显式替换 skills

可选补充：

1. 长运行任务每 `60-120s` 自动保存一次

原则：

1. 平时只更新 sandbox 内文件记忆
2. 到保存触发点时再整体刷 DB
3. Redis 只在保存成功后刷新

## 5. 目标行为

实现完成后，必须满足：

1. 用户首轮显式选择的 skill，可以跨 `user_response`、resume、retry、auto continue 正确延续
2. 同一 session 内如果用户切换到明显不同主题，旧 skill 不再继续进入当前轮 prompt
3. managed / direct 两条链路使用同一套 skill 解析逻辑
4. sandbox resident skill 不会随着每轮 prompt 激活轻微变化而频繁删改
5. OpenCode 不会因为 skills 每轮波动而频繁重启
6. sandbox 丢失后，resident skill 文件可以由 DB 状态重新物化
7. Redis 关闭时，skills 会话保持仍能完整工作

## 6. 最终设计结论

### 6.1 必须同时区分“三层状态”和“三类存储”

#### 三层状态

1. `availableSkills`
   - 当前用户当前会话可解析的 skill catalog
2. `activeSkillsForTurn`
   - 当前轮 prompt 真正注入的 skills
3. `residentSkills`
   - 当前 session 在 sandbox 中保持驻留的 skills

#### 三类存储

1. DB
   - 持久化 `sessionSkillState`
2. Redis
   - 缓存 `sessionSkillState` 和最近一次 resolved resident snapshot
3. sandbox 文件
   - resident skill 的运行时物化副本与当前会话文件记忆

结论：

1. `activeSkillsForTurn` 和 `residentSkills` 允许不相同
2. prompt 激活和 sandbox 驻留必须解耦
3. 会话记忆属于 DB / Redis，不属于 API 本机文件
4. sandbox 文件既属于运行态物化层，也承担当前会话文件记忆

### 6.2 session 中只存轻量 skill state

DB 中只存：

1. skill 选择引用
2. skill 绑定状态
3. resident 集引用
4. 最近命中上下文
5. 最近一次 sandbox materialization 摘要
6. 最近一次已保存的文件记忆摘要
7. 最近一次保存时间 / archive 来源信息

DB 中不存：

1. 全量 catalog 快照
2. 全量 resolved markdown 正文
3. 当前轮 prompt 拼接后的最终 skill body
4. API 本机文件路径

### 6.3 Redis 只缓存两类内容

如果 Redis 启用，建议缓存：

1. `sessionSkillState` 镜像
2. 最近一次 `residentSkills` resolve 结果
3. 最近一次已保存版本的 cache key / version

不建议缓存：

1. 超大 markdown 正文
2. API 本机文件路径
3. 未保存的工作记忆

### 6.4 run entry 是唯一的“当前轮 skill 解析入口”

当前轮到底激活哪些 skills，统一由 run entry 计算。

不能分散在：

1. 前端 metadata
2. websocket 恢复逻辑
3. direct 特判
4. tool runtime 的纯内存临时状态

## 8. 核心读写流程

### 8.1 首轮输入

1. `altus-managed-input-service.ts` 解析显式选择与输入阶段自动挂载
2. 写入 DB `sessionSkillState`
3. 可选写入 Redis cache
4. 初始化 sandbox 文件记忆文件
5. `altus-managed-run-entry-service.ts` 读取 state，解析：
   - `activeSkillsForTurn`
   - `residentSkills`
6. `altus-run-coordinator.ts` 用 `activeSkillsForTurn` 组织 prompt
7. `sandbox-skill-sync-service.ts` 用 `residentSkills` 物化 sandbox 文件

### 8.2 continuation / clarification / retry / resume

1. 不再要求前端重复传完整 `metadata.skills`
2. API 先读 DB state，再用 Redis 做可选加速
3. 如存在已恢复的 workspace 文件记忆，则先读取文件记忆并与 DB 版本对齐
4. run entry 结合当前轮上下文重新解析 active / resident
5. resident 未变化则不重写 sandbox 文件
6. resident 变化时才触发 sync / restart
7. runtime 新增的结构化记忆只更新 sandbox 文件记忆
8. 遇到保存触发点时，再整体刷回 DB

### 8.3 sandbox 丢失 / 重建 / restore

1. sandbox 内 skill 文件与文件记忆文件都视为可重建副本
2. 新 sandbox 建立后，先尝试恢复 workspace archive
3. 如 archive 中存在文件记忆，则加载该文件记忆
4. 再与 DB 中已保存的 `sessionSkillState` 做版本对齐
5. 重新解析 resident
6. 再次物化到 sandbox
7. 不依赖旧 sandbox 剩余文件恢复会话状态

### 8.4 tool 自动激活

1. tool 命中 autoActivation rule
2. runtime 先更新 sandbox 本地文件记忆
3. 当前 run 即时激活该 skill
4. 需要 resident 时再增量同步到 sandbox
5. 同步更新 workspace 内的文件记忆
6. 遇到保存触发点时，由 API 将文件记忆刷回 DB
7. 保存成功后刷新 Redis cache

### 8.5 Redis 关闭时的降级路径

当 `ONECEO_REDIS_ENABLED` 未显式开启时：

1. 所有读取直接走 DB
2. 所有 resident 解析都实时计算
3. sandbox runtime 变化只更新文件记忆
4. sandbox 重建仍由 DB state + archive 文件记忆驱动
5. 功能正确性不受影响，只损失读缓存收益

### 8.6 sandbox -> API 回写协议

本方案要求新增一个明确的“保存型回写”协议，而不是扫文件夹倒灌数据库。

建议保存时回写内容只包括轻量结构化状态：

1. `residentSelections`
2. `bindings` 增量变化
3. `lastToolActivations`
4. `snapshotVersion`
5. `savedAt`
6. `sandboxId`

不回写：

1. 任意 sandbox 路径下的所有文件正文
2. 未建模的大块临时产物
3. 依赖文件扫描推断出的模糊状态

建议由 OSAC / runtime service 在下面时机触发：

1. 用户显式保存
2. run 结束前保存
3. sandbox archive 前保存
4. sandbox replace / restore 切换前保存
5. 用户显式替换 skills 时保存

补充规则：

1. 文件记忆必须带 `snapshotVersion`
2. DB 中必须记录最近一次已保存版本
3. archive 恢复时，只有比 DB 更新的文件记忆才允许覆盖 DB 工作态
4. 同一 session 的保存必须串行执行，避免并发覆盖

## 10. 本轮继续激活与 resident 规则

### 10.1 候选集来源

本轮候选 skills 固定来自：

1. `explicitSelections`
2. `availableSkills` 中 `governance.required === true`
3. `availableSkills` 中命中 `taskIntentProfile` 的 autoActivation trigger
4. runtime 过程中命中 toolName 的 autoActivation skill

### 10.2 进入 `activeSkillsForTurn` 的条件

满足以下任一条件即可：

1. 当前轮显式选择
2. 来源为 `explicit`，且当前轮属于 continuation
3. 来源为 `required`
4. 当前轮 `taskIntentProfile` 仍命中该 skill 的 autoActivation trigger
5. 当前工具调用命中该 skill 的 autoActivation toolName

### 10.3 退出 `activeSkillsForTurn` 的条件

任一成立即退出：

1. 当前轮不是 continuation，且该 skill 既不是 explicit current，也不是 required，也未命中当前 autoActivation
2. 当前 session 已明显切换主题
3. 当前 binding / revision / user binding 已失效

### 10.4 resident 回收规则

只在下面场景回收：

1. 用户显式替换 skills
2. 新 session
3. resident 数量超阈值，淘汰最久未使用的 `cached`
4. revision 失效或 binding 失效
5. sandbox 已重建且旧 resident 集不再需要重新物化

不在下面场景回收：

1. 当前轮 prompt 暂时不用该 skill
2. 某个 tool auto activation 本轮没再次命中
3. 一次普通澄清回复

建议初版阈值：

1. `residentMode = pinned` 不因数量被淘汰
2. `residentMode = cached` 最多保留 6 个

## 12. 验收标准

开发完成后，以下必须全部成立：

1. 同一 task session 内，skills 能跨多轮、澄清、resume、retry 正确恢复
2. 本轮 active skill 由统一 resolver 决定，不再依赖当前输入 metadata 是否完整
3. managed / direct 两条链路行为一致
4. session metadata 中只保存轻量 skill state
5. prompt active skill 与 sandbox resident skill 解耦
6. OpenCode 不会因为 prompt 层 skill 波动频繁重启
7. sandbox 文件丢失后，可由 DB state 重新物化
8. API 服务侧不引入任何新的本地文件持久化
9. Redis 关闭时功能正确，Redis 开启时只提升读取性能，不改变正确性
10. sandbox runtime 新增的结构化 skill 记忆会在保存触发点回写到 DB，不会长期只留在本地
11. 文件记忆随项目文件一起归档，restore 后可继续恢复

## 14. 结论

`oneceo` 的正确优化方向不是“让旧 skills 永远 sticky”，也不是“每轮重新猜”。

更准确的说法是：

1. 会话级 skill 记忆必须持久化在 DB
2. Redis 在显式启用时只承担已保存快照的热缓存
3. sandbox 文件既是 resident skill 的运行时物化副本，也是当前会话的文件记忆
4. 文件记忆和项目文件一起存储、一起归档
5. 在保存触发点，从 sandbox 文件记忆写回 DB
6. run 前统一解析 `activeSkillsForTurn`
7. resident skill 惰性同步到 sandbox
8. managed / direct / runtime 共用同一套状态与解析逻辑

这份文档即为后续重新实现的开发基线。
