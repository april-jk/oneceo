# 01 目标与范围 [尚未采用]

## 更新时间

2026-05-04

## 1. 问题现状

### 1.1 旧审计日志已失效

- 存储方式：`data/audit-log.json` 文件，最多 2000 条
- 记录内容：仅 KVM VM 的 start/stop/reboot 等电源操作
- 数据字段：`operator`、`action`、`targetVmId`、`result` 等，与现代业务无关
- 前端页面：独立的审计日志表格 + 详情弹窗，所有代码已在前一阶段清除

### 1.2 用户行为不可追溯

- 用户端 Web App 调用 API 时，没有任何持久化记录
- 无法回答："某用户在什么时间调用了什么接口？传了什么参数？返回了什么？"
- 无法回答："某用户发起了几次会话创建？失败了几次？"

### 1.3 AI 执行细节分散

- `session_api_traces` 表已存在，记录了 LLM 请求、工具调用、连接器 API 等
- 但目前只能通过 `sessionId` 正向查询，缺少按用户反向检索的入口
- 管理后台的「对话管理」页面虽有 API Trace 面板，但嵌套在会话详情内，不能跨会话聚合

## 2. 目标定义

### 2.1 核心目标

| 优先级 | 目标 | 说明 |
|---|---|---|
| P0 | 用户前端 API 请求可观测 | 所有用户态 HTTP 请求（`req.user.id` 存在）被持久化记录，支持按用户、时间、路径筛选 |
| P0 | 会话 AI 执行细节可追溯 | 在审计日志页面内，从用户入口进入其会话，查看该会话的完整 `session_api_traces` 时间线 |
| P0 | 页面用户友好 | 同时提供结构化阅读视图（表格、时间线、卡片）和原始 JSON 展开视图 |
| P1 | 敏感信息脱敏 | 请求/响应中的密码、token、authorization、api_key 等字段在入库前自动脱敏 |
| P1 | 数据保留策略 | HTTP 请求日志保留 30 天（可配置），超期自动清理 |

### 2.2 非目标

- 不记录管理后台（`admin_management`）自身的 HTTP 请求（管理端操作通过独立审计入口）
- 不记录 WebSocket 消息流（WebSocket 已有独立事件日志）
- 不做实时告警/异常检测（属于监控系统范畴，非审计日志）
- 不做用户行为分析/漏斗统计（属于运营分析系统）

## 3. 范围边界

### 3.1 后端范围

- `apps/api/src/index.ts`：新增请求记录 middleware
- `apps/api/src/db/schema.ts`：新增 `api_request_logs` 表
- `apps/api/src/db/dao/`：新增 `api-request-log.dao.ts`
- `apps/api/src/services/`：新增 `api-request-log-service.ts`
- `apps/api/src/routes/internal-trace-routes.ts` 或新增路由：提供 HTTP 请求日志查询 API
- `apps/admin_management/server/routes/`：新增审计日志相关路由，代理到 API 侧

### 3.2 前端范围

- `apps/admin_management/web/src/App.tsx`：恢复「审计日志」导航入口
- 新增/重构审计日志页面组件（用户索引 → HTTP 请求 → 会话 → AI Trace）
- 复用现有 `ApiTraceItem` 类型和 API Trace 展示组件

### 3.3 不涉及范围

- `apps/web`（用户端 Web）：不做任何修改
- `session_api_traces` 表结构：不做修改，仅新增查询接口
- 现有计费、积分、用户管理等功能：不做修改
