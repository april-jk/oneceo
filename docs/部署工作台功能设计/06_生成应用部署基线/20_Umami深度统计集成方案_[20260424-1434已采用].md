# 20 Umami 深度统计集成方案 [20260424-1434已采用]

## 1. 背景与方向纠偏

用户明确确认：

- `https://analytics.oneceo.ai/teams/ebd4ca20-a8de-43ff-af76-e1709c9020d6/websites/6af729e4-2cdb-4a46-9c15-ee7e2fe8438a`
- 是 OneCEO 平台自身的 Umami 监测地址。
- 该 website 是 OneCEO 平台运营分析源，不是用户部署应用的统计源。

因此本方案必须从 COO / 平台运营官视角出发，服务 OneCEO 后续运营决策，而不是优先给用户部署网站增加更多监控指标。

当前正确方向：

1. 把 Umami 深度集成进 OneCEO 平台运营体系。
2. 用该 website 监测 OneCEO 平台自身页面、功能、路径和转化。
3. 建立管理后台里的“平台运营数据中心”。
4. 支撑获客、激活、核心功能使用、部署转化、留存、商业化意向和运营复盘。

当前明确不做：

- 不把该 websiteId 用作所有用户部署应用的统计站点。
- 不优先做“用户部署网站多维统计详情页”。
- 不把 Umami 后台页面简单 iframe 到 OneCEO。
- 不把用户 prompt、代码、邮箱、token、密钥等敏感数据送入 Umami。

## 2. 统计源定位

### 2.1 固定平台级统计源

本次 OneCEO 平台运营统计源固定为：

```text
UMAMI_HOST_URL=https://analytics.oneceo.ai
UMAMI_PLATFORM_TEAM_ID=ebd4ca20-a8de-43ff-af76-e1709c9020d6
UMAMI_PLATFORM_WEBSITE_ID=6af729e4-2cdb-4a46-9c15-ee7e2fe8438a
```

该 website 对应 OneCEO 平台自身。

所有平台运营总览、渠道分析、页面分析、功能使用分析，默认读取该 website。

注意：

- 该 website 是平台运营流量与前端行为的主数据源。
- 注册成功、会话创建成功、agent run 完成、部署成功等强业务事实仍以 OneCEO DB 为准。
- 管理后台运营看板需要合并 Umami 与 OneCEO DB，而不是只读取 Umami。

### 2.2 用户部署应用统计不是本次主目标

用户生成应用仍可保留现有独立 Umami website 绑定规则，但这不是本次实现重点。

本次第一优先级是回答：

- OneCEO 自己有没有增长？
- 用户从哪里进入 OneCEO？
- 哪些入口让用户注册、创建任务、完成生成、完成部署？
- 哪些产品路径正在流失？
- 哪些功能有真实使用价值？
- 哪些运营渠道带来的用户质量更高？

### 2.3 数据源分工与归因口径

平台运营数据分三类：

| 数据类型 | 主数据源 | 用途 |
| --- | --- | --- |
| 匿名访问与页面路径 | Umami | 获客、入口页、来源、设备、跳出、停留 |
| 前端功能点击与轻行为 | Umami | CTA、tab、panel、preview、copy、open 等行为趋势 |
| 强业务事实 | OneCEO DB | 注册成功、任务创建成功、agent 完成、部署成功、连接器绑定成功、计费状态 |

跨数据源归因原则：

1. 不把 Umami `distinctId` 当成 OneCEO 用户身份。
2. 不把邮箱、用户 ID 明文、session ID 明文写入 Umami。
3. 首次访问到注册的归因，使用短期、匿名、不可逆的 attribution key 或 OneCEO DB 内部映射表完成。
4. 管理后台只展示聚合结果，不展示可反推出单个用户的原始事件链。
5. 如果无法可靠归因，宁可展示“未归因 / direct / unknown”，不做猜测性归因。

这解决一个关键问题：COO 需要看“访问 -> 注册 -> 使用 -> 部署”的连续漏斗，但这个漏斗不能靠 Umami 单独完成，也不能靠把用户身份塞进 Umami 完成。

## 3. COO 视角的运营问题

### 3.1 获客质量

COO 需要回答：

- 访问来自哪些渠道？
- 哪些 referrer、campaign、入口页面带来高质量用户？
- 哪些页面流量高但跳出严重？
- 哪些市场动作只带来访问，没有带来注册和使用？

指标：

- visits
- visitors
- pageviews
- bounce rate
- avg session duration
- top referrers
- channels
- entry pages
- exit pages
- UTM campaign breakdown

### 3.2 激活转化

COO 需要回答：

- 访问者是否注册或登录？
- 注册后是否创建第一个任务？
- 用户是否理解 OneCEO 的核心入口？
- 哪一步让用户放弃？

指标与事件：

```text
signup_click
signup_start
signup_success
login_success
task_session_create_start
task_session_create_success
first_prompt_submit
first_agent_response_received
```

核心漏斗：

```text
landing/page visit
-> signup_click
-> signup_success
-> task_session_create_success
-> first_prompt_submit
-> first_agent_response_received
```

该漏斗是平台运营聚合漏斗，不等同于 Umami 原生 funnel。前两步主要来自 Umami，注册成功及之后的业务事实来自 OneCEO DB，再由管理后台聚合服务按隐私安全归因规则合并。

### 3.3 核心产品使用

COO 需要回答：

- 用户是否真的在用 Altus / task creation，而不是只浏览页面？
- 用户是否持续提交 prompt？
- Agent 是否能完成一次有价值输出？
- 哪些执行阶段最容易失败？

指标与事件：

```text
prompt_submit
agent_run_start
agent_run_complete
agent_run_failed
file_change_generated
preview_open
artifact_download
```

只记录分类和桶，不记录 prompt 原文、生成代码或文件内容。

### 3.4 部署链路转化

COO 需要回答：

- 多少生成会话进入部署？
- 多少部署真正成功？
- 哪些用户完成“从想法到上线”的闭环？
- 哪些部署失败阶段需要产品或工程优先修复？

指标与事件：

```text
deploy_panel_open
deploy_start
deploy_success
deploy_failed
redeploy_start
redeploy_success
rollback_start
rollback_success
public_url_open
public_url_copy
```

核心漏斗：

```text
task_session_create_success
-> prompt_submit
-> agent_run_complete
-> deploy_panel_open
-> deploy_start
-> deploy_success
-> public_url_open
```

`public_url_open` 在本方案中指 OneCEO 登录用户从平台内打开自己生成应用的公网地址，用于衡量“发布后是否继续验证 / 分享”。它不是外部访客访问生成应用的数据。

### 3.5 留存与复用

COO 需要回答：

- 用户是否第二天、七天后还回来？
- 用户是否回到同一个任务继续修改？
- 用户是否复用部署、重新部署或回滚？
- 哪些用户行为预示长期留存？

指标与事件：

```text
task_session_reopen
project_reopen
prompt_submit_returning
redeploy_success
connector_bind_success
```

留存分析第一阶段可在 OneCEO DB 中按登录用户聚合，不直接依赖 Umami distinctId 作为用户身份。

### 3.6 商业化与高意向信号

COO 需要回答：

- 哪些用户表现出付费或升级意向？
- 哪些页面和功能带来更强商业线索？
- 哪些 connector、部署、团队协作功能代表高价值用户？

指标与事件：

```text
pricing_view
billing_page_open
upgrade_click
connector_bind_start
connector_bind_success
team_invite_click
settings_payment_open
```

## 5. 数据产品设计：平台运营数据中心

### 5.1 入口位置

建议新增管理后台一级入口：

```text
管理后台 -> 运营数据
```

该入口只对管理态用户开放。

用户侧部署工作台不展示平台级运营总览。

### 5.2 总览页

目标：让 COO 每天 3 分钟判断平台健康状态。

模块：

- 今日访问、7 日访问、30 日访问
- 新增注册
- 活跃访客
- 活跃登录用户
- 新建任务会话
- prompt 提交数
- agent 成功完成数
- 部署开始数
- 部署成功数
- 高意向事件数

核心看板：

```text
访问 -> 注册 -> 创建任务 -> 首次 prompt -> agent 完成 -> 部署成功
```

术语约定：

- “活跃访客”来自 Umami active visitors / visitors。
- “活跃登录用户”来自 OneCEO DB 的登录用户或业务动作聚合。
- 两者不能混用，也不能直接相加。

### 5.3 获客分析页

模块：

- referrer 排行
- channel 排行
- entry page 排行
- exit page 排行
- UTM source / medium / campaign
- 各渠道注册率
- 各渠道任务创建率
- 各渠道部署成功率

目标：判断运营渠道质量，而不是只看访问量。

### 5.4 产品漏斗页

模块：

- 注册漏斗
- 首次任务创建漏斗
- prompt 到 agent 完成漏斗
- agent 完成到部署成功漏斗
- 部署成功到公网链接打开漏斗

每个漏斗必须展示：

- 每步人数 / 次数
- 转化率
- 流失率
- 对比上一周期变化

### 5.5 功能使用页

模块：

- prompt 提交趋势
- agent run 成功 / 失败趋势
- preview 使用
- artifact download
- connector 绑定
- deploy / redeploy / rollback
- settings / billing / team invite

目标：判断哪些功能是真实核心功能，哪些只是入口曝光。

### 5.6 留存与复用页

模块：

- D1 / D7 登录用户回访
- D1 / D7 task session reopen
- 项目 reopen
- 二次 prompt
- 二次部署
- connector 复用

留存以 OneCEO 登录用户和业务事件聚合为准，Umami 只提供页面访问和行为事件辅助。

### 5.7 异常与阻塞页

模块：

- auth_failed
- agent_run_failed
- deploy_failed
- connector_bind_failed
- sandbox / provider error category
- 失败阶段排行

目标：让 COO 能看到影响增长和转化的系统性阻塞。

## 6. 技术集成边界

### 6.1 Umami 负责什么

Umami 负责：

- 页面访问
- 来源渠道
- 入口 / 退出页面
- 设备 / 浏览器 / 国家
- 前端行为事件
- dashboard / reports / funnel / cohort 的原生分析能力

限制：

- Umami 原生 funnel / cohort 只能覆盖已进入 Umami 的页面和事件。
- 如果某一步是后端事实事件但没有同步为安全事件进入 Umami，则不能声称由 Umami 原生 funnel 完成。
- OneCEO 的核心运营漏斗应优先由管理后台聚合层完成，Umami reports 作为流量和前端行为分析能力补充。

### 6.2 OneCEO 自有 DB 负责什么

OneCEO DB 负责强业务事实：

- 用户注册成功
- 会话创建成功
- agent run 真实开始 / 完成 / 失败
- 部署真实开始 / 完成 / 失败
- connector 绑定真实成功 / 失败
- 计费、团队、权限等敏感业务状态

原因：

- 这些事件不能只依赖浏览器在线。
- 这些事件必须可审计。
- 这些事件不能因为广告拦截或脚本失败而丢失。

### 6.3 平台运营接口聚合

管理后台运营数据接口应合并两类数据：

1. Umami API：流量、来源、页面、前端事件。
2. OneCEO DB：注册、任务、agent、部署、连接器、计费等业务事实。

对外接口建议：

```text
GET /api/admin/operations/analytics/overview?range=7d
GET /api/admin/operations/analytics/acquisition?range=7d
GET /api/admin/operations/analytics/funnels?range=7d
GET /api/admin/operations/analytics/features?range=7d
GET /api/admin/operations/analytics/retention?range=30d
GET /api/admin/operations/analytics/blockers?range=7d
```

这些接口只服务管理后台，不开放给用户侧。

聚合接口必须返回字段来源标记，例如：

```ts
type MetricSource = 'umami' | 'oneceo_db' | 'joined';
```

这样 COO 看报表时能知道某个数字来自流量统计、业务事实，还是跨源归因后的结果。

## 8. 隐私与数据治理

禁止进入 Umami 的内容：

- prompt 原文
- 用户上传文件内容
- 生成代码
- 用户邮箱、手机号
- token、密钥、连接器凭据
- 支付信息
- 原始错误堆栈
- 第三方 API 返回内容

允许进入 Umami 的内容：

- 稳定事件名
- 页面类型
- 入口类型
- 功能模块名
- provider 类型
- executor 类型
- template 类型
- duration bucket
- count bucket
- error category

所有高基数字段必须桶化或分类化。

## 9. 分阶段实施

### 9.1 P0：平台运营基础看板

目标：

- 固定读取 OneCEO 平台 Umami website。
- 管理后台新增运营数据总览。
- 接入平台关键路径前端事件。
- 后端补最关键的业务事实事件聚合。

P0 的最小闭环是“一个总览页 + 一组关键指标 + 一条主漏斗”，不是一次做完所有运营分析页。获客分析、产品漏斗、留存、异常页可以在 P1/P2 拆开。

实施：

1. 增加 `UMAMI_PLATFORM_WEBSITE_ID` 配置读取。
2. 扩展 Umami service 读取平台 website 的 stats、pageviews、metrics、events。
3. 建立 OneCEO 业务事实事件聚合口径，优先复用现有业务表；缺口再补事件表。
4. 增加匿名访问到登录用户的隐私安全归因方案，不把用户身份写入 Umami。
5. 新增管理后台运营总览接口。
6. 管理后台新增“运营数据”入口和总览页。
7. 前端接入 landing、auth、task creation、deploy、billing、connector 关键事件。
8. 后端接入 signup success、task session create success、agent run complete / failed、deploy success / failed 的事实聚合。

### 9.2 P1：渠道与漏斗

目标：

- 让 COO 能判断渠道质量和主路径流失。

实施：

1. 获客分析页。
2. 产品漏斗页。
3. UTM campaign 分析。
4. 周期对比。
5. 支持按入口页、渠道、用户类型、项目类型过滤。

### 9.3 P2：留存、商业化与周报

目标：

- 形成运营复盘闭环。

实施：

1. D1 / D7 留存。
2. 高意向用户行为分析。
3. 失败阻塞分析。
4. 自动生成运营周报。
5. 将关键指标沉淀到管理后台首页。

## 10. 验收标准

P0 完成后必须满足：

1. 管理后台可以看到 OneCEO 平台级运营总览。
2. 数据源固定为 `websiteId=6af729e4-2cdb-4a46-9c15-ee7e2fe8438a`。
3. 前端不允许传入任意 websiteId。
4. 总览至少包含 visits、visitors、pageviews、active visitors、top referrers、top pages、核心事件趋势。
5. 总览明确区分“活跃访客”和“活跃登录用户”。
6. 核心路径至少覆盖注册、任务创建、prompt、agent 完成、部署开始、部署成功。
7. 后端事实事件和 Umami 前端事件边界清晰，并在接口字段中标记来源。
8. 匿名访问到登录用户的归因方案不泄露用户身份。
9. 不采集敏感原文。
10. 用户部署应用统计不作为本次 P0 主目标。
