# 20260328 Office 正式任务模式设计

## 1. 背景

当前项目已经具备以下能力：

- `PPT / Word / Excel` 已经可以通过任务创建页入口触发
- `PPT / Word / Excel` 已经可以联动 `web_search / web_extract`
- `pptx / docx / xlsx` 已经可以走交付物闭环并提供下载
- `PPT / Word` 已经开始具备内容感知型生成约束

但这些能力目前仍然主要挂靠在“skill 附件模板”路径上，本质上仍是：

- 用户选择一个预设说明
- 前端把说明附加到消息
- Altus 根据说明临时组织生成策略

这条链路可以工作，但还不等同于正式产品层能力。当前主要问题是：

- `PPT / Word / Excel` 仍然是“技能入口”，不是“正式模式入口”
- 模式边界不够清晰，办公任务与通用技能还混在同一入口层
- 生成契约主要依赖 prompt 和 skill 文本，缺少共享的模式定义
- 办公交付标准没有被抽成正式 completion contract

因此，下一步最合适的方向不是继续堆更多 skill 文案，而是把 `PPT / Word / Excel` 升级为真正的 **Office 正式任务模式**。

## 2. 问题结论

当前 Office 相关能力已经不适合继续停留在 skill 体系内，原因有三点：

### 2.1 skill 适合“加说明”，不适合“承载正式产品模式”

当前 `apps/web/client/src/lib/skill-attachment-templates.ts` 中的 Office 条目已经非常重，但它们依然只是模板文本。

这意味着：

- 前端识别不到“这是正式 PPT 任务模式”
- 后端也只能把它当一段附加说明，而不是模式级输入
- 模式差异没有正式数据结构承载

### 2.2 办公能力已经有独立交付逻辑，不该再和通用 skill 同层

`PPT / Word / Excel` 已经有自己的：

- 产物类型
- 联网策略
- 交付验证
- 下载链路

这说明它们已经不是“辅助提示”了，而是完整任务类型。继续挂在 skill 菜单下，只会让结构越来越混。

### 2.3 目前缺少统一的 Office Mode 定义层

现在 Office 的核心规则分散在：

- `skill-attachment-templates.ts`
- `altus-managed-prompt-service.ts`
- 运行时隐式约束

缺少一层统一定义：

- 模式 key
- artifact 类型
- 支持的 archetype
- style pack
- 证据模式
- 完成标准

这会导致后续继续演进时，前后端规则越来越容易漂移。

## 3. 目标

本轮目标是把 `PPT / Word / Excel` 从“Office skills”升级为“Office 正式任务模式”。

最终效果应是：

- 用户明确选择某个 Office 模式，而不是只加一段 skill 说明
- 前端把 Office 选择作为结构化模式输入传给后端
- 后端根据模式定义构造正式的 Office execution contract
- Altus 在生成前先形成模式级 brief，再执行
- completion 阶段按 Office 模式自己的标准校验交付

## 4. 非目标

本轮不做以下事项：

- 不新增数据库表
- 不新增模板市场
- 不引入复杂多步骤表单编辑器
- 不更换生成引擎
- 不新增新的联网 connector
- 不保留“Office 既是 skill 又是 mode”的双轨兼容

最后一条是强约束：

**PPT / Word / Excel 升级为正式模式后，不再继续保留在通用 skill 列表里。**

## 5. 最短实现路径

最短正确路径是：

1. 抽出 Office Mode 共享定义
2. 前端新增“办公模式”入口并移出 Office skills
3. 前端将 Office 选择改为结构化 metadata，而不是 skill markdown
4. 后端根据 Office mode metadata 注入正式模式契约
5. completion 按 mode-specific gate 校验交付物

换句话说，本轮的关键变化是：

**skill -> mode**

而不是继续：

**skill -> 更长的提示词**

## 6. 设计方案

### 6.1 新增 Office Mode 定义层

新增共享定义文件，建议位置：

- `packages/shared/src/office-modes.ts`

定义内容至少包括：

- `modeKey`
  - `office_ppt`
  - `office_docx`
  - `office_xlsx`
- `label`
- `description`
- `artifactType`
- `contentArchetypes`
- `stylePacks`
- `evidenceModes`
- `retrievalPolicy`
- `completionCriteria`

这层是 Office 的正式产品定义，不再写在 skill 文案里散落维护。

### 6.2 前端入口升级为“办公模式”

当前 [AttachmentPickerButton.tsx](/D:/oneceo-task-creation-agent-fresh/apps/web/client/src/components/AttachmentPickerButton.tsx) 里，`PPT / Word / Excel` 混在“使用技能”菜单中。

本轮改为：

- 保留“使用技能”给通用 skill
  - `需求拆解`
  - `实现方案`
  - `测试清单`
- 新增“办公模式”
  - `生成 PPT`
  - `生成 Word`
  - `生成 Excel`

也就是说：

- Office 不再是 generic skill
- Office 成为 first-class mode entry

### 6.3 Office 选择改为结构化输入

当前 office 入口本质上还是生成 `skill-*.md` 或 inline skill 内容。

本轮应改为结构化输入，例如：

- `attachmentKind: "office_mode"`
- `officeModeKey`
- `label`
- `artifactType`
- `modeConfigVersion`

并在消息 metadata 中明确传递：

- `officeMode`
- `officeModeSelection`

这样后端可以明确知道：

- 当前任务是正式 PPT 模式
- 而不是“用户附加了一段 PPT 相关说明”

### 6.4 Office Mode 专属 execution brief

后端不再只依赖 skill 文本，而是根据 Office mode 定义生成标准化 brief。

建议新增：

- `apps/api/src/services/office-mode-service.ts`

职责：

- 根据 `officeModeKey` 读取 mode 定义
- 生成 mode-specific prompt block
- 补齐默认 archetype / style pack / completion gate

Office execution brief 至少包含：

- `modeKey`
- `artifactType`
- `contentArchetype`
- `stylePack`
- `audience`
- `goal`
- `tone`
- `structureStrategy`
- `visualStrategy`（PPT）
- `sheetStrategy`（Excel）
- `evidenceMode`
- `completionCriteria`

### 6.5 三种正式模式的职责边界

#### 6.5.1 PPT 正式模式

`office_ppt` 负责：

- 演示结构
- 视觉表达
- 图文比例
- 图表与图片策略
- speaker notes / 来源保留

必须要求：

- 使用有限 archetype 集合
- 使用有限 `stylePack`
- 使用页面原型库
- 至少满足视觉页和图文页数量要求

#### 6.5.2 Word 正式模式

`office_docx` 负责：

- 正式文档结构
- 章节层级
- 语气与文风
- 论证方式
- 引用与来源保留

必须要求：

- 使用有限 archetype 集合
- 使用有限 `stylePack`
- 不同 archetype 必须使用不同 section order

#### 6.5.3 Excel 正式模式

`office_xlsx` 不再只看作“生成表格”，而是正式的工作簿交付模式。

职责包括：

- workbook 结构设计
- sheet 分工
- 公式与可复算性
- 数据来源说明
- 汇总视图与图表

必须要求：

- 明确区分读取分析 / 新建工作簿 / 编辑现有工作簿
- 外部数据任务必须保留 `sources` 或 `raw_data`
- 分析型交付和制作型交付要有不同 completion gate

## 7. completion contract

正式模式必须有自己的完成标准。

### 7.1 PPT completion gate

至少验证：

- 最终 `.pptx` 已存在
- 结构完整
- 至少包含封面页
- 至少包含图文/图表类内容页
- 如使用外部资料，已保留来源

### 7.2 Word completion gate

至少验证：

- 最终 `.docx` 已存在
- 标题层级清晰
- 章节结构与 archetype 匹配
- 如使用外部资料，已保留引用或来源

### 7.3 Excel completion gate

至少验证：

- 最终 `.xlsx` 已存在
- workbook/sheet 结构完整
- 关键数值优先公式化
- 若使用外部数据，已保留来源 sheet 或说明区

## 9. 验证方式

### 9.1 前端结构验证

验证：

- Office 三项不再出现在 generic skill 列表中
- 办公模式入口单独展示
- 选择模式后发送的是结构化 metadata，而不是 skill markdown

### 9.2 Prompt/模式验证

验证：

- Altus 可以识别 `office_ppt / office_docx / office_xlsx`
- 模式 prompt block 能根据 `modeKey` 正确变化
- `complete_task.attachments` 仍保留现有交付物闭环

### 9.3 真链路 smoke

至少验证以下三条：

- `office_ppt` -> 生成职业规划 PPT
- `office_docx` -> 生成商业计划书 DOCX
- `office_xlsx` -> 生成学习规划或预算工作簿 XLSX

并确认：

- run 成功完成
- deliverable 正常落库
- 下载可用

## 10. 结论

这次升级的关键不是“继续增强 Office skill”，而是：

- 让 Office 从 skill 升级为 mode
- 让 `PPT / Word / Excel` 成为正式产品能力
- 让前后端都围绕 mode 这个中心概念工作

最短正确路径就是：

- 移除 Office 在 generic skill 中的地位
- 新增 Office mode 定义层
- 让前端发送结构化 mode 选择
- 让后端按 mode 执行和交付

这是当前项目最符合现状、最不绕路、也最容易继续演进的一步。
