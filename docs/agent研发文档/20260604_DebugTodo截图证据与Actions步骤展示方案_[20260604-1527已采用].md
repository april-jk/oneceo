# 20260604 Debug Todo 截图证据与 Actions 步骤展示方案 [20260604-1527已采用]

## 背景

`task-creation-agent` 已恢复 `debug_todo_write` 机制，用于在 Altus 明确进入调试、测试、验证或诊断前生成结构化调试 todo。当前实现已经能让模型在调试前写出测试单元清单，但它还没有把“调试步骤执行证据”闭环到平台界面。

现有已采用方案已经建立了浏览器截图证据链：

1. `debug_open_page` 成功后会连接同一个 n.eko Chromium CDP，触发 Playwright 截图。
2. `browser_interact` 每次显式浏览器动作成功后也会截图。
3. 截图通过 `ManagedToolResult.evidence` 和 run event metadata 中的 `browserScreenshot` 进入平台。
4. Web 端 `buildManagedReplayData()` 会把 `browserScreenshot` 挂到对应 `AltusReplayAction`。
5. `AltusRunReplayDrawer` 的 Actions 详情区已经可以展示 `BrowserScreenshotEvidence`。

因此，这次不新增第二套截图、上传或预览接口；目标是把 debug todo 与现有 Action 截图证据链做绑定。

## 现有 Debug Todo 机制检查结论

当前实现可用但还不完整：

1. `debug_todo_write` 已在 `AltusManagedToolRuntime` 中注册并执行，能接收 `triggerReason`、`debugDepth`、`relatedDocument` 和 `items`。
2. `debug-todo-service.ts` 已能生成、保存、更新和格式化 `DebugTodo`，并能查询相关项目文档。
3. `altus-managed-prompt-service.ts` 已通过 `[DEBUG_TODO_ANCHOR]` 要求调试前必须调用 `debug_todo_write`。
4. 目前的 todo 存储是进程内 Map，适合 run 内即时使用，不适合作为跨进程或重启后的长期真相源。
5. `debug_todo_write` 只建立计划，不会在后续 `debug_open_page` / `browser_interact` 发生时更新 item 状态。
6. `debug_open_page` / `browser_interact` 虽然已经产生截图，但截图只属于工具 Action，没有显式归属到某个 debug todo item。
7. Actions 页面目前能显示浏览器截图，但不能告诉用户“这张截图对应 debug todo 的第几项测试单元”。

结论：现有 debug todo 机制作为“调试计划生成入口”是 OK 的；需要补的是 item 级证据关联和 Actions 展示。

## 目标

1. 调试 todo 中的页面类测试单元必须能驱动后续页面截图证据。
2. `debug_open_page` / `browser_interact` 的截图继续走现有平台截图链路，不新增截图服务。
3. 后续浏览器动作产生的 `browserScreenshot` 必须能关联到一个 debug todo item。
4. Actions 页面对应步骤上显示 debug todo item 信息和截图状态。
5. 用户能在 Actions 中复核：本步骤对应哪个测试单元、执行了什么浏览器动作、截图是否捕获、视觉诊断是否通过。
6. 不把截图路径、R2 key、内部 raw error 当成用户主要文案；用户界面只显示可复核证据和简明状态。

## 非目标

1. 不新增长期 debug todo 数据库表。
2. 不改变 `debug_open_page` / `browser_interact` 的截图上传逻辑。
3. 不新增第二套浏览器、Playwright 或 n.eko 运行时。
4. 不让模型写自定义截图脚本。
5. 不改交付卡片最终预览截图逻辑。

## 方案

### 1. Debug Todo Item 增加执行关联字段

在 `DebugTodoItem` 增加可选字段：

```ts
latestToolName?: 'debug_open_page' | 'browser_interact';
latestAction?: string;
latestScreenshot?: {
  status: 'captured' | 'capture_failed' | 'storage_failed';
  storageKey?: string;
  capturedAt?: string;
  visualStatus?: 'passed' | 'failed';
  reasonCode?: string;
  message?: string;
};
```

这些字段只作为 run 内投影，不作为长期状态源。它们用于把 todo item 和具体 Action 绑定起来。

### 2. `debug_todo_write` 返回当前 active item

`debug_todo_write` 成功后，在工具返回内容中增加：

```json
{
  "debugTodo": {
    "activeItemId": "debug-004-web",
    "items": [...]
  }
}
```

规则：

1. 如果有 `unitType="page_action"` 的 item，优先把第一条 page action 作为 `activeItemId`。
2. 否则使用第一条 pending item。
3. 返回内容中要求模型后续调用 `debug_open_page` / `browser_interact` 时带上 `debugTodoItemId`。

### 3. 浏览器工具参数增加 `debugTodoItemId`

在 `debug_open_page` 和 `browser_interact` 工具定义中增加可选参数：

```json
{
  "debugTodoItemId": {
    "type": "string",
    "description": "The debug todo item id this browser action verifies."
  }
}
```

这不是兼容兜底，而是明确的计划关联协议：

1. 当本 run 已调用 `debug_todo_write` 后，浏览器调试工具应传 `debugTodoItemId`。
2. 没有传时，工具仍可执行，但不会标记 todo item。
3. 若传入不存在的 item id，工具结果记录 `debugTodoLink.status="unmatched"`，不阻塞截图。

### 4. 截图完成后更新 Debug Todo

在 `AltusManagedToolRuntime` 的 `debug_open_page` / `browser_interact` 分支中：

1. 截图完成后读取 `rawArgs.debugTodoItemId`。
2. 如果存在对应 todo item：
   - 将 item 状态更新为 `passed` 或 `failed`。
   - `browserScreenshot.status="captured"` 且 `visualCheck.status="passed"` 时为 `passed`。
   - 截图捕获失败、存储失败或视觉诊断失败时为 `failed`。
   - 写入 `latestScreenshot` 所需的投影数据。
3. 工具结果中返回：

```json
{
  "debugTodoLink": {
    "status": "linked",
    "itemId": "debug-004-web",
    "itemStatus": "passed",
    "testUnit": "验证页面可访问性和基本渲染"
  }
}
```

这里不需要新增数据库事务，因为当前 debug todo 本身就是 run 内临时计划。

### 4.1 浏览器工具失败后更新 Debug Todo

如果 `debug_open_page` / `browser_interact` 在截图前就执行失败，例如 Playwright locator 超时、页面不可达或动作参数错误，则该步骤没有 `browserScreenshot`，但仍必须根据 `debugTodoItemId` 写回 debug todo：

1. 对应 item 状态更新为 `failed`。
2. `actualResult` 记录用户可读的失败摘要。
3. `tool_call_failed` event metadata 写入 `debugTodoLink`。
4. Actions 失败步骤显示对应 debug todo item 和失败原因。

这类失败不应被后续成功重试“抹掉”在时间线中的证据；后续成功重试可以把最终 item 状态更新为 `passed`，但失败 Action 本身仍保留失败关联。

### 5. Run event 透传 debug todo 投影

`AltusManagedToolExecutor` 已经会透传 `browserScreenshot`。本次只需要让 runtime result content 中的 `debugTodoLink` 在 `tool_call_completed` metadata 中有用户可见投影：

```ts
debugTodoLink: {
  status: 'linked' | 'unmatched';
  itemId?: string;
  itemStatus?: 'pending' | 'in_progress' | 'passed' | 'failed' | 'skipped';
  testUnit?: string;
}
```

实现位置优先放在 coordinator 的 `onResult` eventPayload 投影里，避免前端解析 `toolResultEnvelope.contentForModel`。

### 6. 前端 Actions 展示

`AltusReplayAction` 增加：

```ts
debugTodoLink?: {
  status: 'linked' | 'unmatched';
  itemId?: string;
  itemStatus?: string;
  testUnit?: string;
};
```

`buildManagedReplayData()` 从 event metadata 读取 `debugTodoLink`，挂到对应 action。

`AltusRunReplayDrawer` 在 Actions 列表和选中详情中展示：

1. 列表行：
   - 小号标签：`Debug Todo · debug-004-web`
   - 状态使用现有 badge 语义：通过 / 失败 / 未匹配
2. 选中详情：
   - 在截图上方显示测试单元标题。
   - 如果截图捕获成功，继续展示现有 `BrowserScreenshotEvidence`。
   - 如果捕获失败或未匹配，展示简短原因。

UI 保持任务塔台风格：紧凑、可扫描、证据优先，不新增大卡片。

## 全链路流程

1. Altus 遇到调试/验证需求，先调用 `debug_todo_write`。
2. 平台保存 debug todo，并返回 active item。
3. Altus 启动或定位页面服务。
4. Altus 调用 `debug_open_page({ url, debugTodoItemId })`。
5. 平台打开页面、截图、上传截图、视觉诊断。
6. 平台更新对应 debug todo item，并在 run event 上写 `browserScreenshot` + `debugTodoLink`。
7. 前端 Actions 对应步骤显示 todo item 和截图。
8. 后续每次 `browser_interact({ action, description, debugTodoItemId })` 都重复上述证据绑定。

## 验收标准

1. `debug_todo_write` 后的浏览器调试工具可携带 `debugTodoItemId`。
2. `debug_open_page` 成功截图后，对应 Action metadata 同时有 `browserScreenshot` 和 `debugTodoLink`。
3. `browser_interact` 成功截图后，对应 Action metadata 同时有 `browserScreenshot` 和 `debugTodoLink`。
4. Actions 列表能看到该步骤关联的 debug todo item。
5. Actions 选中详情能看到测试单元标题和截图证据。
6. 截图捕获失败、视觉诊断失败或浏览器工具执行失败时，todo item 标记为 failed，Actions 显示失败原因。
7. 没有 `debugTodoItemId` 的普通浏览器工具调用仍保持现有截图展示，不被误标成 debug todo。
8. 后端 `pnpm --filter api type-check` 通过。
9. 前端 `pnpm --filter web check` 通过。
10. `managed-run-status-dialogue.test.ts` 覆盖 debug todo link + browser screenshot 同步显示。

## 风险

1. 当前 debug todo 是内存 Map；如果 run 跨 API 进程或服务重启，todo item 状态会丢失。短期接受，因为 Actions 仍保留 run event 投影；长期可再设计 DB 真相源。
2. 模型可能忘记传 `debugTodoItemId`。本方案通过工具返回 nextSteps 和 prompt 约束提高稳定性，但不阻塞普通截图链路。
3. 如果一个 item 需要多张截图，只记录 latest screenshot 可能不够。短期通过 `linkedToolCallIds` 保留多个 Action 的索引，前端仍按 Action 逐步展示。
