## 1. 背景

当前 oneceo 的新建会话主链已经具备：

1. 提问/澄清能力；
2. 前端 Todo 卡片展示能力；
3. `clarifying -> waiting_user` 的状态收口能力。

但现状仍存在两个关键偏差：

1. 用户刚发送需求后，系统经常会在关键信息不足时直接开始执行；
2. 即使任务已经明显进入多步骤实现，也没有把 Todo 作为“开始工作前的默认前置动作”强制下来。

这会带来两个直接问题：

1. 在需求边界、交付形态、技术栈、运行环境、验收标准还不清楚时，执行链路容易盲目启动；
2. 多步骤任务缺少稳定的显式 Todo，用户无法清楚看到系统打算如何推进，也不利于后续恢复、继续执行和验收。

用户明确要求参照 `claudecode` 的实现方式来改进，因此本方案必须把 `claudecode_src` 作为直接设计依据，而不是只基于我们自己的直觉补规则。

## 2. 目标

本次目标只做两件事：

1. 让新会话在真正开始工作前，优先做“必要澄清”，避免信息不足时盲目执行；
2. 让适用 Todo 前置的正式工作在开始执行前先写 Todo，并在执行过程中持续更新。

## 3. 非目标

本次明确不做：

1. 不重做整个 Altus agent 架构；
2. 不引入新的多轮采访引擎或复杂计划模式；
3. 不把所有任务都强制变成多轮问答；
4. 不把 Todo 升级成独立数据库产品；
5. 不在本轮加入搜索式问题推荐、问题模板编辑器、Todo 看板等增强能力。

## 6. 设计原则

本次方案遵守以下原则：

1. 参照 `claudecode`，保留现有 `ask_user`，并只新增一个最小 `todowrite` managed 工具，不引入独立 Todo 子系统；
2. 先把“规则前置化”，再谈体验增强；
3. 澄清优先只在“信息不足时”触发，不打断明显的简单请求；
4. Todo 前置只在“进入实际工作阶段”触发，不污染纯闲聊与纯问答；
5. Todo 的状态真相源与执行真相源必须区分：
   - 用户界面展示真相源：现有 managed 工具回放链路中最新一次成功完成的 `todowrite`
   - 模型续跑真相源：run 启动时从上述成功快照提取并注入 prompt / memory context
6. 不单独开数据库表，但也不能把“只在 UI 可见的回放事件”误当成模型可恢复状态；
7. 产品上要让用户看到“系统正在先澄清、再列 todo、再开始做”，而不是黑箱跳转。

## 7. 方案设计

### 7.1 首轮消息处理改为四段门禁

新会话首轮消息进入后，统一走以下顺序：

1. 判断是否属于纯问答/纯记忆/纯身份问题；
2. 若不是，判断是否存在关键缺失信息；
3. 若缺信息，先进入澄清；
4. 澄清完成后，重新回到“信息已足够”分支再判断一次，不允许跳过后续分流；
5. 若信息足够，再判断是否进入实际工作；
6. 若属于单步、低歧义、低风险执行，请直接执行；
7. 若属于多步骤正式工作，先写 Todo；
8. Todo 建立完成后，才允许开始执行。

即：

`direct_answer OR clarify_first OR direct_execute OR todo_first_then_execute`

### 7.2 “必须先澄清”的判定范围

本轮不做开放式语义平台，只做最短路径的门禁判定。

优先级约束：

1. 已有 adopted prompt contract 的场景优先按现有合同执行；
2. 其中最重要的特例是 Office 生成任务：
   - 对于“生成一个 PPT / DOCX / XLSX，主题已经明确”的请求，默认视为信息已足够；
   - 这类请求应直接进入执行或 Todo，不应先问泛化问题；
3. 只有在关键缺口已经阻塞“有意义的首个动作”时，才进入澄清。

当满足以下任一类缺口时，要求优先 `ask_user`：

1. 交付形态不清楚
   - 例如：网页、脚本、PPT、文档、API、移动端不明确
2. 技术路线不清楚
   - 例如：前端框架、语言、运行环境、是否接现有系统不明确
3. 范围边界不清楚
   - 例如：只做页面还是含后端、只做 demo 还是可部署版本不明确
4. 验收标准不清楚
   - 例如：是否需要测试、部署、数据接入、登录、响应式等未明确
5. 用户明显表达“先别假设”“先问清楚”“先确认需求”

如果请求属于以下类型，则直接回答，不强制进入澄清：

1. 纯解释/纯知识问答；
2. 纯身份/记忆问题；
3. 单步、低歧义、低风险修改；
4. 用户已经给出了完整且可执行的约束；
5. 已命中 Office 类“可用默认值直接开始”的 adopted contract。

### 7.2.1 首轮澄清硬门禁

2026-04-23 的 Playwright 回归已经证明：仅靠 prompt 约束并不足以阻止模型对宽泛业务系统需求直接开工。

因此本方案追加一个最小硬门禁：

1. managed 路径构建 `taskIntentProfile` 时，除现有部署意图字段外，同步携带：
   - `needsClarification`
   - `clarificationQuestion`
2. 这两个字段不新造判定器，直接复用 [task-intent-shape-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/task-intent-shape-service.ts) 的现有确定性规则。
3. 在 [altus-run-coordinator.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-run-coordinator.ts) 中增加前置门禁：
   - 当本轮输入类型是 `user_input`
   - 且 `needsClarification === true`
   - 且 `clarificationQuestion` 非空
   - 则直接进入 `requestClarification`
4. 命中该门禁时：
   - 不创建 sandbox
   - 不调用模型
   - 不允许先 `todowrite`
   - 不允许直接进入执行工具链
   - 不应先把 session 生命周期推进到 `executing`
5. `user_response` 不命中这个硬门禁；用户答复澄清后，继续走现有“重新分流”逻辑。

### 7.3 “开始工作前必须写 Todo”的判定范围

参照 `claudecode`，本轮将 Todo 前置规则明确为：

以下情况必须先写 Todo，再进入执行：

1. 多步骤任务；
2. 涉及 3 个及以上明确动作；
3. 涉及多个文件或多个子系统；
4. 涉及调试 + 修改 + 验证串联；
5. 涉及部署、迁移、运行环境、联调；
6. 用户明确要求 todo；
7. 首轮澄清完成后，重新判定为多步骤正式工作。

以下情况不强制 Todo：

1. 纯问答；
2. 单条简单信息回复；
3. 明显的一步式小改动；
4. 单个命令即完成的操作；
5. 首轮澄清完成后，如果需求收敛为一步式小改动，仍允许直接执行。

### 7.4 Todo 的最小执行契约

参照 `claudecode`，Todo 在 oneceo 内收敛为以下最小契约：

1. Altus managed 新增一个最小 `todowrite` 工具，最小载荷直接使用 `todos` 数组；
2. `todos` 内部约束保持最小集合：
   - `todos: [{ content, status, activeForm? }]`
   - `status ∈ pending | in_progress | completed`
3. 开始正式工作前必须先调用一次 `todowrite`；
4. 处于“尚未完成、仍会继续执行”的最新成功 `todowrite` 载荷里，必须有且仅有一个 `in_progress` 项；
5. 每次完成关键步骤后立即再次调用 `todowrite` 更新状态；
6. Todo 的真相源定义为：
   - UI / 回放使用：当前 managed 工具回放链路中最新一次 `tool_call_completed + toolName=todowrite` 的载荷
   - 模型续跑使用：run 启动时读取同一份最新成功快照，并以内联 context 形式注入 prompt
   - 不把 `tool_call_started` 或失败的 `todowrite` 事件当成真相源
   - phase 1 不扩展独立 Todo 表
7. 当所有步骤都已完成、且下一动作紧接 `complete_task` 时，允许最后一次成功 `todowrite` 载荷中 `in_progress = 0`；
8. 若因为澄清阻塞，则可以先不写 Todo；一旦澄清完成并进入多步骤正式工作，第一步就是写 Todo；
9. Todo 至少覆盖：
   - 澄清后理解收口
   - 实现
   - 验证
   - 收尾/交付

### 7.5 前端交互口径

前端不新增独立模块，而是在现有消息流能力上收口：

1. Altus managed 的执行前澄清继续以 `clarification_request` 作为标准呈现；
2. `question` 卡片本轮不作为 Altus managed 的标准语义，只保留兼容展示；
3. `ask_user` 在 Altus managed 下只通过 `clarification_request` 对用户可见，不再额外投影一张 `ask_user` 的 managed tool 卡；
4. `todowrite` 卡片作为“开始工作”的标准起点呈现；
5. 由于 managed 路径当前实际渲染的是 `managed_tool` 卡片，`todowrite` 不能只依赖通用 tool summary：
   - 必须在 managed card 渲染链中读取 `metadata.arguments.todos`
   - 并复用现有 Todo 列表视觉，而不是只显示 `todowrite` 字样或原始 JSON
6. 在用户体验上，必须呈现出：
   - 用户发消息
   - 系统先提澄清问题或先建立 Todo
   - 然后才进入执行态
7. 不允许在用户刚发消息后立刻出现大量执行日志，但此前没有任何澄清或 Todo 建立痕迹；
8. 不允许同一轮既渲染 `clarification_request`，又再额外补一份重复语义的澄清工具卡。

## 9. 与 ClaudeCode 的对齐边界

## 10. 风险与规避

### 风险 1：澄清过度，导致本来能直接做的小任务被卡住

规避：

1. 保留纯问答/简单任务直达路径；
2. 只对关键缺失信息触发澄清。

### 风险 2：Todo 过度泛化，导致每个小任务都先写一堆待办

规避：

1. 只对多步骤/复杂任务强制 Todo；
2. 单步 trivial 任务继续允许直接执行。

### 风险 3：前端消息顺序仍然让用户感觉“已经开工了才来补问题”

规避：

1. 首轮澄清与 Todo 建立都必须在执行日志前出现；
2. 测试里明确校验首轮消息顺序。

## 11. 验证计划

至少补以下验证：

1. 纯身份/记忆问题
   - 预期：直接回答，不进入澄清，不写 Todo
2. 需求明显缺关键边界的实现请求
   - 预期：先 `ask_user`，不直接执行
3. 澄清后进入复杂实现
   - 预期：先 `todowrite`，再进入执行
4. 明显复杂但信息已充分的任务
   - 预期：首轮直接写 Todo，再执行
5. 单步小改动
   - 预期：允许直接执行，不强制 Todo
6. 澄清后收敛为单步小改动
   - 预期：重新走 `direct_execute`，不强制 Todo
7. Office 创建请求（例如“生成一个关于 AI 行业趋势的 PPT”）
   - 预期：不先问泛化问题；直接进入 Todo 或执行
8. Todo 全部完成后准备收尾
   - 预期：允许最后一次 `todowrite` 把所有项置为 `completed`，随后立即 `complete_task`
9. 会话中断后继续执行
   - 预期：模型可从最新成功 `todowrite` 快照恢复当前 Todo 状态，而不是只在 UI 中可见
10. 首轮触发 `ask_user`
   - 预期：用户只看到 `clarification_request`，不会再多出一张重复的 `ask_user` tool 卡
11. managed `todowrite` 展示
   - 预期：用户能直接看到 Todo 列表与状态，不会只看到工具名或原始 JSON
