# 2026-04-09 对话管理消息开发者视图重构方案 [20260409-2149已采用]

## 1. 背景

当前 `apps/admin_management` 的 `对话管理 -> 消息` 页签仍采用“按时间顺序平铺所有 message”的方式展示：

1. 每条消息只显示 `role`、时间、正文和原始 `metadata JSON`。
2. `opencode_event`、`executor_event`、`status_update`、`clarification_request`、`assistant_message` 等语义完全不同的消息被放在同一视觉层级。
3. 真实会话里大量执行过程事件会淹没用户真实交互，开发人员难以直接判断：
   - 用户当时输入了什么；
   - 系统是在正常执行、等待补充信息，还是被 runtime 阻塞；
   - 本轮 run 做了哪些关键动作；
   - 哪个阶段最值得继续优化。

本次需求要求把管理端消息展示重构成“类用户态交互”的阅读体验，但又要比用户态多保留调试信息，服务开发人员排障和产品优化。

## 2. 真实数据观察（基于 2026-04-09 只读连库抽样）

本方案已按 `apps/.env` 中的 `DATABASE_URL` 只读连接当前数据库，抽样最近会话与消息结构，作为设计依据。

### 2.1 最近 7 天消息类型分布

近期消息主类型呈现明显长尾不均衡：

1. `opencode_event` / `agent`：1859 条
2. `user_input` / `user`：101 条
3. `executor_event` / `agent`：93 条
4. `clarification_request` / `agent`：67 条
5. `status_update` / `system`：55 条
6. `assistant_message` / `agent`：38 条

结论：

1. 真实排障时，当前平铺视图会被 `opencode_event` 空正文消息严重污染。
2. 真正代表用户体验的消息只占少数，必须被提到主视图。

### 2.2 典型会话样本

#### 样本 A：执行事件淹没主线

- 会话：`862172d6-...-1353d36`
- 最近 3 天消息构成：
  - `user_count = 1`
  - `agent_count = 677`
  - `system_count = 1`
  - `opencode_event_count = 677`

结论：

1. 当前消息页几乎不可读。
2. 对这类会话不能继续逐条显示 `opencode_event`，必须按轮次/事件簇聚合。

#### 样本 B：等待用户补充信息

- 会话：`e7e70675-...-d8734a2`
- 典型序列：
  1. `user_input`：`你好`
  2. `clarification_request`：问候
  3. `user_response`：`帮我查查现在外贸建站工具有哪些`
  4. `executor_event`：`web_search` 完成
  5. `clarification_request`：带长正文回答与后续引导

结论：

1. `clarification_request` 在真实数据里不只是“一个问题”，也可能承载完整回答与下一步引导。
2. UI 不能简单把它当作单行“待澄清问题”，而应作为主对话消息展示，并附加“当前等待用户”的状态解释。

#### 样本 C：多轮 managed 正常开发

- 会话：`4899da74-...-3dae6cf`
- 可见稳定模式：
  1. `user_input` / `user_response`
  2. 多条 `executor_event`（`read_file`、`write_file`、`shell_execute`、`complete_task`）
  3. `assistant_message`
  4. `status_update`（`deliverables_ready` / `run_completed`）

结论：

1. 一个用户轮次内部包含大量工具动作，但开发人员真正先看的应是“用户要求 -> 系统做了什么 -> 是否完成/失败”。
2. `executor_event.outputPreview` 很有价值，但应进入折叠调试区而不是直接铺满主视图。

#### 样本 D：runtime 阻塞失败

- 会话：`110f0acd-...-c8847fe`
- 典型序列：
  1. 前置若干 `opencode_event`
  2. `session_started`
  3. `user_input`
  4. `opencode_user_input`
  5. `opencode_error`：订阅事件失败 / sandbox 端口未打开

结论：

1. 开发人员最关心的是“用户已经输入，但执行器没有真正开始工作，阻塞在 runtime”。
2. 失败原因必须被提升为显式告警卡片，不能埋在原始 JSON 中。

## 3. 目标与非目标

### 3.1 目标

1. 把消息页重构成“主交互可快速阅读、调试信息可按需展开”的双层视图。
2. 让开发人员在 10 秒内判断当前会话属于：
   - 正常执行中
   - 等待用户回复
   - 已完成并交付
   - runtime / tool / orchestrator 异常
3. 在不依赖单一历史版本数据结构的前提下，对近期真实消息形态提供稳定展示。
4. 保留原始消息流入口，避免管理员因聚合视图丢失排障细节。

### 3.2 非目标

1. 不改数据库表结构。
2. 不新增管理端专用后端 API 作为前置条件。
3. 不在本轮重写 `ConversationManagementService` 的会话详情聚合逻辑。
4. 不把消息页改造成与用户端一模一样的 UI；管理端仍以排障和治理为第一目标。

## 5. 现状问题

### 5.1 视觉层级错误

当前消息 Tab 中，以下内容权重相同：

1. 用户输入
2. 澄清问题
3. 助手正式回答
4. 工具调用成功/失败
5. OpenCode 流式事件
6. 原始 metadata JSON

结果是“真正需要先看”的内容不突出。

### 5.2 交互轮次不可见

当前 UI 看不到：

1. 一次用户输入对应哪一轮 run；
2. 这一轮最终是成功、失败还是等待用户；
3. 中间做了几次工具调用、失败了几次；
4. 哪些系统消息只是执行器转发，不应被当作用户体验主线。

### 5.3 历史数据版本不稳定

从抽样可见，历史会话存在以下差异：

1. 有的消息只有 `messageType + metadata.eventType`，正文为空。
2. 有的消息有 `runId`，有的没有。
3. 有的用户输入同时存在 `user_input` 和执行器转发的 `opencode_user_input`。
4. 有的 `clarification_request` 是单纯问题，有的是“回答 + 下一步引导”。

因此新 UI 不能依赖某一个版本的完整字段存在。

## 6. 方案总览

保留现有 `消息` Tab，但重构为三层结构：

1. `会话状态摘要条`
2. `交互视图`（默认）
3. `原始消息流`（开发者回退视图）

其中：

1. `交互视图` 负责模拟用户态阅读路径，但带开发者增强信息。
2. `原始消息流` 保留当前“一条一条消息 + 原始 metadata”的排障能力。

## 7. 详细方案

### 7.1 顶部增加消息级会话摘要条

位于消息区最上方，固定显示当前最需要判断的状态：

1. 最近用户输入摘要
2. 当前会话状态：
   - 进行中
   - 等待用户
   - 已完成
   - 已失败
3. 最近一轮执行结果：
   - 成功完成
   - 等待补充
   - runtime 异常
   - 工具失败
4. 最近关键阻塞：
   - 最近失败工具
   - 最近 `opencode_error`
   - 最近 `clarification_request`
5. 本页统计：
   - 用户消息数
   - 助手主回复数
   - 执行事件数
   - 失败事件数

### 7.2 消息页增加二级模式切换

在 `消息` Tab 内部增加切换：

1. `交互视图`
2. `原始流`

默认进入 `交互视图`。

原因：

1. 开发人员平时看主线，不应先被原始事件噪音冲击。
2. 需要深挖时仍可一键切回当前原始视图，不丢治理能力。

### 7.3 交互视图的基本模型：按“轮次”组织

#### 7.3.1 分组优先级

消息按以下优先级归并为“交互轮次”：

1. `metadata.runId`
2. `metadata.orchestratorSessionId`
3. 相邻用户消息之间的时间窗口
4. 若都不存在，则退化为单条展示

#### 7.3.2 每个轮次包含三块

1. `主对话区`
2. `执行摘要区`
3. `调试抽屉`

### 7.4 主对话区：类用户态阅读体验

主对话区按聊天气泡展示，但只展示“用户真正会感知到”的消息：

#### 7.4.1 作为主气泡展示的消息

1. `user_input`
2. `user_response`
3. `assistant_message`
4. `agent_message`
5. `clarification_request`
6. `error` / `opencode_error`（升级为错误卡片）
7. `status_update`（升级为状态条，而不是普通气泡）

#### 7.4.2 默认不直接逐条展示的消息

1. `opencode_event`
2. `opencode_status`
3. `executor_event`
4. `opencode_user_input`
5. `codex_user_input`

这些消息进入“执行摘要区”或“调试抽屉”。

#### 7.4.3 去重策略

同一轮次里如果出现：

1. `user_input.content`
2. `opencode_user_input.content`

且正文相同、时间接近，则：

1. 主对话区仅保留 `user_input`
2. 执行器转发版本放入调试抽屉并标记“已转发到执行器”

### 7.5 执行摘要区：开发者增强信息

每个轮次在主气泡下增加一块紧凑摘要，不再把所有工具消息直接铺出来。

执行摘要区包含：

1. 执行器类型：`Altus` / `OpenCode` / `Codex`
2. 轮次结果：
   - 完成
   - 处理中
   - 等待用户
   - 失败
3. 工具统计：
   - 成功数
   - 失败数
   - 关键工具名列表
4. 关键输出摘要：
   - `complete_task.outputPreview.summary`
   - `deliverables_ready`
   - `run_completed`
5. 阻塞信息：
   - 最近失败工具
   - 最近 runtime 错误
   - 最近 sandbox / opencode 错误

### 7.6 调试抽屉：展开看原始轨迹

每个轮次提供一个 `查看执行细节` 折叠面板，包含：

1. 原始工具事件列表
2. `outputPreview` 摘要与截断 JSON
3. `runId / orchestratorSessionId / opencodeSessionId / workspacePath`
4. 失败原因原文
5. 轮次内原始消息计数

显示原则：

1. 重要字段结构化展示
2. 原始 JSON 继续保留，但默认折叠

### 7.7 空正文事件的聚合展示

对 `opencode_event` 这类“正文为空、主要依赖 metadata.eventType”的消息，不再逐条渲染。

改为在执行摘要区显示：

1. 总事件数
2. 时间跨度
3. `eventType` 分布
4. 最近一个异常事件（若有）

对于“全轮次只有 `opencode_event`”的极端会话，显示：

1. “执行器事件密集，暂无可读主回复”
2. “已收到用户输入 / 已转发执行器 / 尚未产出回复”之类状态文案

### 7.8 状态消息升级为显式状态条

`status_update` 不再当普通消息显示，而是显示为阶段条：

1. `collecting / planning / executing / reviewing / completed / failed`
2. `tone`
3. `eventType`
4. 时间

并对以下状态加高亮：

1. `deliverables_ready`
2. `run_completed`
3. `failed`
4. `waiting_user`

### 7.9 错误消息升级为阻塞卡片

对以下消息类型统一升级为错误卡片：

1. `error`
2. `opencode_error`
3. `executor_event` 且 `eventType = tool_call_failed`

卡片中直接展示：

1. 错误来源
2. 工具名 / 执行器名
3. 是否发生在 runtime 建立前
4. 对用户体验的影响：
   - 用户已输入但未开始执行
   - 中途执行失败
   - 已完成部分结果但终态失败

### 7.10 原始流保留当前能力，但补两点增强

`原始流` 视图保留现有列表式结构，同时补充：

1. 消息类型标签中文化
2. metadata 关键字段首屏摘要

这样当开发人员切回原始流时，不需要先展开 JSON 才知道这条消息大概是什么。

## 8. 历史不稳定数据兼容策略

由于数据库中存在历史迭代版本，本轮必须显式兼容以下情况：

1. `metadata` 缺失
   - 退化为普通原始消息卡片
2. `runId` 缺失
   - 使用时间窗口归组
3. `messageType` 为空
   - 进入 `原始流`
4. `clarification_request` 没有 `options`
   - 仍按助手主消息显示
5. `outputPreview` 过大
   - 首屏仅摘要 + 截断，完整 JSON 进入折叠区

原则：

1. 不因为缺少字段而整轮消失
2. 优先“可读 + 可回退”，不追求旧数据 100% 完美语义还原

## 9. 实施路径（最短路径）

### 9.1 第一阶段：纯前端重构

不改接口，直接基于 `conversationDetail.messages`、`conversationDetail.session`、`conversationDetail.runtime`、`conversationDetail.trace` 做客户端派生。

实现内容：

1. 新增消息归组与归类 helper
2. 新增 `交互视图 / 原始流` 切换
3. 新增轮次卡片、状态条、错误卡片、执行摘要、调试抽屉
4. 保留现有原始 JSON 能力

### 9.2 第二阶段：仅在第一阶段证明信息不足时再考虑后端补充

只有当第一阶段无法稳定判断轮次或阻塞原因时，才考虑：

1. 管理端详情接口补充轻量派生字段
2. 但不作为本轮前置条件

## 11. 验收标准

1. 开发人员进入 `消息` 页签后，默认先看到“用户主线交互”，而不是几百条执行事件。
2. 至少能从 UI 一眼判断：
   - 最近一次用户输入是什么
   - 当前是否等待用户
   - 最近一轮是否完成/失败
   - 若失败，卡在什么环节
3. `opencode_event` 不再逐条污染首屏。
4. 原始流仍可查看全部消息，不丢失排障能力。
5. 对近期真实样本中的四类场景都能正确表达：
   - 事件洪流
   - 等待用户
   - 多轮正常执行
   - runtime 异常失败

## 15. popup 承载与用户端对齐补充（2026-04-09）

为配合新的入口位置，本方案补充以下已采用约束：

1. `对话消息` 不再作为独立 popup 存在，而是必须并入统一 `会话详情` popup 的主 Tab 之一。
2. popup 内默认进入“类用户端回放”模式，视觉与交互尽量贴近 `3000` 端口真实聊天页：
   - 顶部保留 `Dialogue / 对话` 风格标题区；
   - 用户输入采用右侧深色气泡；
   - 智能体回复采用左侧正文块；
   - 状态、等待用户、执行中提示采用胶囊 / notice 形态，而不是普通表格行；
   - `交互回放` 必须直接复用用户态对话页的消息原子结构与样式语言，而不是仅做“近似风格”。
3. popup 内部保留开发者切换入口：
   - `概览` 置于第一列并作为统一会话详情的首个入口；
   - `交互回放` 对应类用户端主视图；
   - `关联信息` 承载原右侧运行绑定、Sandbox 分组与 OSAC 排障信息；
   - `详细日志` 对应原始流 / 调试流，且内容只允许以 JSON 表示；
   - `LLM 调用` 不再保留独立 Tab，必须并入 `详细日志`；
   - `状态流转` 与两者并列存在；
   - 全部共享同一份会话详情数据，不新增接口。
4. `交互回放` 中至少需要与用户态前端保持一致的消息层级：
   - 用户消息胶囊；
   - 智能体正文块；
   - `clarification_notice` 等等待继续提示；
   - managed run 的工具调用胶囊 / 写文件展开卡；
   - OpenCode / Codex 原子工具调用卡片（如命令执行、文件修改、补丁、搜索等）。
5. `clarification_request`、`error`、`opencode_error` 必须在交互回放中保留显式语义：
   - 澄清请求视为主对话的一部分；
   - 阻塞错误升级为显式告警块；
   - 执行器噪音只在需要时进入 `详细日志`。
6. popup 仍服务开发者，因此可以保留摘要 chips、运行标识、时间戳和必要的调试摘要，但不允许回退为“整屏 metadata JSON 平铺”。
7. `概览` 只保留摘要型信息，不再重复内嵌“最近状态流转 / 最近时间线 / 最近 LLM 调用”三块预览卡；保留下来的诊断内容应分别回到对应专用 Tab 或 `详细日志` 中查看。

该补充只调整承载方式与视觉优先级，不改变消息聚合和诊断口径。
