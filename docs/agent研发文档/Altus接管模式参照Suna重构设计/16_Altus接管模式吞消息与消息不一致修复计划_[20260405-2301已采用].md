# 16_Altus接管模式吞消息与消息不一致修复计划_[20260405-2301已采用]

日期：2026-04-05  
关联事项：Issue [#31](https://github.com/april-jk/oneceo/issues/31)  
目标会话：`/session/f563bf1e-596b-4393-a4ce-a83ff78f06ad`

## 1. 背景与范围

本方案仅处理 **Altus 接管模式（managed mode）** 下的“消息不一致/疑似吞消息”问题，不改直通模式主链（OpenCode/Codex/ClaudeCode）。

本次定位以用户提供会话和截图为准，重点覆盖：

1. managed run 流式消息消费与最终消息落盘的一致性
2. `messages/recent` / `messages/history` 的恢复一致性
3. 前端渲染层在 mixed timeline 下的稳定显示

## 2. 约束与前提

1. 测试环境按用户说明为 **Redis 禁用模式**（`ONECEO_REDIS_ENABLED=false`），不能把 Redis 作为主因。
2. 方案遵循“最短路径修复”，不引入额外兜底、降级或兼容分叉逻辑。
3. 修复必须做链路验证：消息入库、API 回放、前端渲染三层一致。

## 3. 复核结论（按优先级）

### 3.1 P0：managed 流式增量与最终消息存在同 key 覆盖风险

现状：

1. Altus run 中 `assistant_delta` 与最终 `assistant_message` 共用 `managed:${runId}:assistant`。
2. 前端 `mergeRealtimeMessage` 按相同 key 进行替换更新。
3. 若最终消息内容短于流式拼接内容，会表现为“先看到长内容，后被短内容覆盖”，形成“吞消息”体感。

关键代码：

1. `apps/api/src/services/altus-run-coordinator.ts`
2. `apps/web/client/src/hooks/useTaskCreationAgent.ts`

### 3.2 P1：managed history 读取优先 file-memory，存在与 DB 事实不一致风险

现状：

1. `resolveRenderableTimelineMessages()` 在非 opencode 分支下优先 `taskCreationFileMemoryStore.getMessages()`。
2. 仅在 file-memory 空时才 fallback DB。
3. file-memory 是单文件读写模型，属于热态缓存实现，不应长期作为 managed 消息事实源。

关键代码：

1. `apps/api/src/routes/task-creation-routes.ts`
2. `apps/api/src/agents/task-creation/file-memory-store.ts`

### 3.3 P2：前端渲染路径切换条件过宽，可能误切 direct 渲染

现状：

1. 只要消息列表中存在任意 `opencode_event`，`Home` 会进入 direct 渲染。
2. direct 渲染主逻辑会跳过非 `opencode_event` 消息。
3. 若 managed timeline 被混入少量历史 `opencode_event`，可能出现 managed 消息“在 state 存在但 UI 不显示”。

关键代码：

1. `apps/web/client/src/pages/Home.tsx`

### 3.4 P3：终态回放依赖 recent，非空但陈旧时不会自动回退 history

现状：

1. `run_completed` 后触发 `loadHistory(...managed_recovery)`。
2. 仅当 recent 为空或报错时才回退 history。
3. recent 非空但陈旧时，页面会保留旧视图，造成同会话不同刷新结果不一致。

关键代码：

1. `apps/web/client/src/hooks/useTaskCreationAgent.ts`
2. `apps/web/client/src/lib/task-creation-client.ts`

## 4. 修复目标

1. 同一 run 的 assistant 文本不再出现“先长后短被覆盖”的消息丢失体感。
2. managed 模式消息回放以 DB 事实为主，file-memory 仅作为补偿数据源。
3. mixed timeline 场景下，managed 消息可稳定展示，不被渲染路径误切换吞掉。
4. `run_completed` 后刷新与重进页面，`recent/history/detail` 结果一致。

## 5. 逐项修复计划

### 5.1 修复项 A（先做）

**主题：managed assistant 消息覆盖修复**

改动点：

1. 调整 managed 流消息合并策略：同 key 更新时优先保留“更完整内容”，避免终态短文本覆盖已拼接长文本。
2. 为 `assistant_delta` 与 `assistant_message` 补充分型元数据，确保合并判定可区分“增量中间态”和“终态”。
3. 增加前端单测，覆盖“delta 长文本 + final 短文本”不丢内容场景。

### 5.2 修复项 B

**主题：managed history 事实源修正（DB 优先）**

改动点：

1. `resolveRenderableTimelineMessages()` 在 `mode=altus` 下改为 DB 优先读取。
2. file-memory 仅用于补齐缺失元数据，不再作为 managed 主消息事实源。
3. 增加 API 侧回归测试，覆盖 DB/file-memory 内容冲突时的返回一致性。

### 5.3 修复项 C

**主题：Home 渲染路径判定收紧**

改动点：

1. `buildChatItems()` 增加 managed 模式识别，避免因少量 `opencode_event` 误进入 direct-only 渲染。
2. mixed timeline 下保留 managed `agent_message/status_update/executor_event` 可见性。
3. 增加前端单测，覆盖“managed + opencode_event 混合列表”展示正确性。

### 5.4 修复项 D

**主题：终态回放一致性校正**

改动点：

1. `run_completed/run_failed/run_stopped` 后，增加一次 history 对账逻辑。
2. recent 非空但落后时自动补拉 history 并纠正首屏消息。
3. 增加前端测试，覆盖“recent 非空但陈旧”场景。

## 6. 验证与验收

### 6.1 代码级验证

1. `pnpm --filter api type-check`
2. `pnpm --filter web check`
3. 新增/更新的单测必须覆盖 A/B/C/D 对应场景。

### 6.2 链路验收

1. 复现会话或等价会话中，managed run 结束后 assistant 文本不再发生可见丢失。
2. 刷新前后消息条数与最终 assistant 内容一致。
3. `messages/recent` 与 `messages/history` 对同一时刻返回的 newest cursor 不逆行。

## 7. 实施顺序

1. A：先修复覆盖问题（直接对应“吞消息”主感知）。
2. B：再修正 managed 历史事实源。
3. C：收口渲染路径误判。
4. D：补终态回放对账与测试收尾。

### 8.5 补充修复 E 已完成：工具事件与 assistant 流文本时序完整性

1. 问题现象：同一 run 内 `assistant_delta/assistant_message` 使用同 key 时，工具调用事件插入后，后续 assistant 文本会回写到前段消息位置，导致 UI 时序被打乱（看起来“先说后做”）。
2. 修复策略：在 `useTaskCreationAgent.ts` 对 managed assistant 消息引入“分段 key”机制：
   - assistant 连续输出时沿用当前段；
   - 一旦被工具/状态等非 assistant 消息打断，后续 assistant 自动进入新段 `managed:{runId}:assistant:segment:{n}`；
   - 从而保证“工具事件前后的 assistant 文本”保持时间顺序，不再覆盖回写到旧段位置。
3. 覆盖测试：
   - `apps/web/client/src/tests/managed-message-stream-identity.test.ts`
   - 新增 realtime + history 两条链路的“assistant/tool/assistant”时序回归。

### 8.6 补充修复 F 已完成：managed 流式 chunk 前导换行/空格被吞导致 Markdown 乱行

1. 问题现象：Altus `assistant_delta` 某些 chunk 以 `\n` 或空格开头时，前端在 SSE 消费层使用 `trim()` 提取内容，导致换行与空格被去掉，出现 `...。 -技术规划：` 这类应换行却未换行的问题。
2. 根因：`apps/web/client/src/hooks/useTaskCreationAgent.ts` 的 managed stream 内容提取逻辑通过 `asText()` 获取 `payload.content/payload.delta`，`asText()` 会 `trim()`。
3. 修复策略：
   - 新增 `resolveManagedStreamDisplayContent()`，按候选字段顺序返回“原始字符串”（仅过滤空串，不做 trim）；
   - `handleManagedRunStreamEvent` 改为调用该函数，确保流式 chunk 的前导换行和空格完整保留；
   - 澄清问题文本同样改为原始字符串读取，避免不必要的空白裁剪。
4. 覆盖测试：
   - `apps/web/client/src/tests/managed-message-stream-identity.test.ts`
   - 新增断言覆盖 `\n-技术规划...` 与仅空格 chunk 的保留行为。

### 8.7 补充修复 G 已完成：完成态卡片路由按产物类型判定（网站任务优先网页预览卡）

1. 问题现象：`buildManagedCompletionCardItem` 只要检测到 `deliverables` 就立即返回 `managed_deliverable_card`，导致网站任务即使产出 `html` 文件也被渲染成“交付文件卡片”。
2. 根因：卡片判定顺序是“deliverables 优先，run_completed 的 web artifact 兜底”，网站类 `deliverables` 在第一层就被短路。
3. 修复策略：
   - 在 `apps/web/client/src/pages/Home.tsx` 增加 `collectManagedWebArtifacts`，从 `deliverables.path` 和 `managedArtifactsByRun` 聚合 `web` 产物；
   - 当处于“完成态上下文”（`deliverables` 存在或 `run_completed`）且存在 `web` 产物时，优先返回 `managed_artifact_card`；
   - 仅在无 `web` 产物时才返回 `managed_deliverable_card`。
4. 覆盖测试：
   - `apps/web/client/src/tests/managed-deliverable-card-timing.test.ts`
   - 新增“deliverables 含 html -> 网站预览卡”与“非 web deliverables -> 交付文件卡”两条回归用例。

### 8.8 补充修复 H 已完成：`write_file` 代码生成过程增加 SSE 可视化进度（Issue #37）

1. 问题现象：`write_file` 生成代码时，前端对话长期只看到“运行中”而没有可感知的代码生成进度，用户容易误判为卡死。
2. 根因：
   - 后端 `tool_call_progress` 仅输出“正在准备工具 write_file”，缺少对 `arguments.content` 增长过程的可视化投影；
   - 前端 `managed_tool` 文案未消费代码生成片段，无法在对话中显示“正在生成了多少字符、正在写什么内容”。
3. 修复策略：
   - 在 `apps/api/src/services/altus-run-coordinator.ts` 增加 `write_file` 增量参数提取：从流式 `rawArguments` 解析 `path/content` 片段，输出 `writeFileProgress`（`path/generatedChars/preview`）；
   - `tool_call_progress` 对 `write_file` 改为带进度语义的 `content`（如“正在生成文件 xxx（已生成 N 字符）”）并附带 `writeFileProgress`；
   - 在 `apps/web/client/src/pages/Home.tsx` 增加 `readManagedWriteFileProgress`，将进度映射到 `managed_tool` 的 summary/preview/detail，使代码生成过程在对话区可见。
4. 覆盖测试：
   - `apps/web/client/src/tests/managed-write-file-progress-visibility.test.ts`
   - 覆盖“summary 显示生成字符进度”与“detail 显示代码预览”。
