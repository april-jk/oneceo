## 关联背景

1. 当前后台管理审计日志页面已过时，依赖 JSON 文件存储，最多保留 2000 条，数据结构陈旧（仅记录 KVM VM 操作），与现有业务完全脱节
2. 用户端 Web App → API Server 的 HTTP 请求没有任何持久化记录，无法追溯用户行为
3. API 侧已有 `session_api_traces` 表，记录会话内 LLM 请求、工具调用、服务 API 等，但缺少按用户索引的入口
4. 需求来源：后台管理需要以用户为索引，查看其前端 API 调用和会话内 AI 执行细节

## 1. 目标

建立一套以用户为中心的审计观测体系，覆盖：

1. **用户前端 API 请求日志**：在 API 服务端记录所有用户态 HTTP 请求，支持按用户检索、筛选、查看详情
2. **会话 AI Trace 详情**：复用现有 `session_api_traces`，在管理后台以用户为入口，按会话展示 AI 回复、工具调用、LLM 请求等执行细节
3. **管理后台审计日志页面重构**：替换过时的审计日志页面，提供用户友好的分层导航（用户 → HTTP 请求 → 会话 → AI Trace）

## 2. 采用边界

本组设计默认：

1. HTTP 请求日志由 API 服务端 Express middleware 统一采集，不依赖前端上报
2. req/res body 仅保留关键信息（脱敏后），完整原始数据不存入数据库
3. HTTP 请求日志保留 30 天（可配置），与现有 `session_api_traces` 保留策略对齐
4. 页面展示同时保留结构化阅读视图和原始 JSON 视图

## 4. 当前结论

这组文档的核心落点：

1. 新增 `api_request_logs` 表，在 `apps/api/src/index.ts` 中挂载请求记录 middleware
2. 复用现有 `session_api_traces` 表，补充按用户 JOIN 查询能力
3. 管理后台新增「审计日志」独立页面，导航结构：用户索引 → HTTP 请求列表 → 请求详情 → 关联会话 → AI Trace 时间线
4. 所有敏感字段（密码、token、authorization 等）在记录前自动脱敏
5. 页面展示支持「结构化阅读视图」和「原始 JSON 面板」双模式切换

## 5. 增强（2026-05-05）

用户确认新增需求：

1. **Tab 区块形式**：选中用户后，页面内用 4 个 Tab 切换展示：
   - **HTTP 请求日志**：已有的请求记录
   - **会话列表**：用户的 task_creation_sessions，点击可展开查看会话消息/对话内容
   - **工具调用**：用户的 session_api_traces（trace_type='tool_call'），按时间排序
   - **交易记录**：同时显示充值、消费（扣费）记录 + Token 使用明细
2. **会话详情展开**：在会话列表 Tab 中，点击会话直接展开展示该会话的消息/对话内容
3. **交易记录整合**：充值（recharge）+ 消费（consume）+ Token 使用明细统一在「交易记录」Tab 展示
