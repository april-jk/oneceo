# 20260327 交付物出 Sandbox 闭环设计

## 1. 背景

当前任务创建链路里，智能体已经可以在 E2B sandbox 内生成 `pptx/docx/xlsx/pdf` 等办公文件，但用户侧仍然经常出现“任务看起来做完了、文件也生成了、自己却拿不到”的体验断层。

这不是单一 UI 问题，而是当前系统对“交付物”缺少完整定义：

- 生成文件只发生在 sandbox workspace 内。
- Altus managed run 的最终完成态没有把“文件可下载”作为必要条件。
- 前端当前更偏向 `html/code` 预览，缺少对 `pptx/docx/xlsx` 这类下载型交付物的稳定展示入口。
- 现有 R2 能力主要用于 workspace 归档/恢复，不等于“最终交付物已持久化并可下载”。

这会直接削弱办公类 skill 的产品价值。对于 `PPT 办公 / Word 文档 / Excel 表格` 这类任务，用户真正需要的不是“sandbox 里有文件”，而是“当前会话里可以直接拿到文件”。

## 2. 现状问题

### 2.1 当前真实故障表现

- 智能体在 sandbox 内成功创建了 `职业规划.pptx` / `职业规划演示文稿.pptx`。
- 但文件只存在于 `/home/user/opencode/workspaces/<sessionId>/...`。
- run 后续又继续执行，最终状态被标记为 `failed`。
- 前端没有把该文件稳定呈现成最终交付物，因此用户无法直接下载。

### 2.2 根因拆解

当前主链路至少有 4 个断点：

1. `complete_task` 没有正式的 `attachments` 契约  
   Altus managed run 目前只把 `summary / verification` 作为完成工具参数，缺少结构化的最终交付物字段。

2. 产物识别过窄  
   当前前端 run replay 对 artifact 的识别主要围绕 `write_file / read_file / html`，对 `shell_execute` 生成的二进制文件不稳定。

3. 交付物没有单独持久化  
   文件生成后仍只留在 sandbox workspace 内，没有被提升成“用户交付物对象”。

4. 成功语义不正确  
   现在 run 可以出现“文件已生成，但 run 最终 failed”的结果，系统没有把“交付物可下载”当成最终完成条件。

## 3. 目标

本次设计只解决一个核心问题：

**当 Altus managed run 生成了面向用户的最终文件时，文件必须脱离 sandbox，成为当前会话内可直接下载的正式交付物。**

具体目标如下：

- 办公类任务完成后，用户可以在当前会话中直接下载 `.pptx/.docx/.xlsx/.pdf`。
- 交付物即使在 sandbox 关闭后仍然可访问。
- run 只有在交付物已持久化成功后，才允许进入 `completed`。
- 前端把“代码预览文件”和“最终交付物”分开呈现。

## 4. 非目标

本次不做以下内容：

- 不新增一套独立于 Altus managed run 之外的办公引擎。
- 不把完整 workspace archive 直接暴露成用户交付物下载入口。
- 不扩展旧的项目管理/交付物页面，只聚焦任务创建主链路。
- 不做兼容性补丁或降级方案；只做正式闭环。

## 5. 总体方案

### 5.1 完成定义重置

从本次设计开始，办公类和文件型任务的“完成”定义调整为：

**文件已生成 + 文件已从 sandbox 读出 + 文件已上传到持久化存储 + 文件记录已入库 + 前端可展示下载入口**

任一环节失败，run 不能标记为 `completed`。

### 5.2 主链路

最终闭环采用以下唯一方案：

1. 智能体在 sandbox 内生成交付文件。
2. 智能体调用 `complete_task` 时必须声明 `attachments`。
3. 服务端在完成前校验 `attachments.path` 对应文件确实存在于当前 workspace。
4. 服务端直接从 sandbox 读取文件内容。
5. 服务端将文件上传到 R2。
6. 服务端写入交付物记录表。
7. 前端根据交付物记录展示“Task complete / 下载文件”卡片。
8. 用户点击下载时，走后端下载接口，不再依赖 sandbox 存活。

## 6. 详细设计

### 6.1 `complete_task` 协议升级

`complete_task` 从当前的：

- `summary`
- `verification`

升级为：

- `summary`
- `verification`
- `attachments`

建议结构：

```json
{
  "summary": "已生成职业规划演示文稿",
  "verification": ["已检查幻灯片结构", "已输出 .pptx 文件"],
  "attachments": [
    {
      "path": "职业规划演示文稿.pptx",
      "name": "职业规划演示文稿.pptx",
      "mimeType": "application/vnd.openxmlformats-officedocument.presentationml.presentation"
    }
  ]
}
```

约束：

- `path` 必须是 workspace 相对路径。
- `attachments` 中的每个文件都必须真实存在。
- 对于明确要求交付文件的任务，`attachments` 不能为空。

### 6.2 服务端交付物校验与持久化

Altus managed run 收到 `complete_task` 后，不立即结束，而是进入“交付物收口”阶段：

1. 解析 `attachments`
2. 校验文件存在
3. 读取文件字节
4. 计算 `sha256 / size / mimeType`
5. 上传到 R2
6. 写入数据库
7. 回写最终 assistant message / run event metadata
8. 持久化全部成功后，run 才能完成

这里不复用整包 workspace archive 作为交付物来源，原因是：

- archive 面向恢复，不面向用户下载
- archive 粒度过粗
- archive 时机与 run 完成时机不严格绑定

### 6.3 数据模型

新增正式交付物表，建议名：

`task_session_deliverable_artifacts`

最小字段：

- `id`
- `session_id`
- `run_id`
- `sandbox_id`
- `source_path`
- `display_name`
- `mime_type`
- `size_bytes`
- `sha256`
- `storage_key`
- `created_at`

说明：

- 这张表只记录“最终交付物”，不记录普通中间文件。
- run replay 的文件流仍然保留原有逻辑，两者职责分离。

### 6.4 R2 存储组织

交付物单独存储到 R2，而不是混入 archive key。

建议 key 规则：

`deliverables/<sessionId>/<runId>/<sha256>-<filename>`

这样可以：

- 与 workspace archive 隔离
- 支持同名文件多次产出
- 支持后续按会话或 run 清理

### 6.5 文件发现策略

本次不把“完全依赖模型自觉声明 attachments”当作唯一保障。

服务端需要补一层基于 workspace baseline 的新增文件识别，用于两件事：

1. 在 `shell_execute` 之后补充发现新生成的文件
2. 在 `complete_task` 时校验是否存在“明显的最终文件已生成但未声明”的情况

策略：

- 如果 `complete_task.attachments` 已声明且文件存在，按声明文件持久化。
- 如果 run 已生成新的办公型文件，但 `attachments` 为空，则拒绝完成，并要求模型显式声明交付物。

这里不做兜底自动猜测最终文件并直接完成，因为这会造成交付语义漂移；系统只允许“声明并验证”。

### 6.6 下载接口

新增两个用户态接口：

- `GET /api/task-creation/sessions/:sessionId/deliverables`
- `GET /api/task-creation/sessions/:sessionId/deliverables/:artifactId/download`

约束：

- 必须校验会话归属。
- 下载走后端转发或预签名方案，但对前端暴露为稳定下载 URL。
- 下载来源以已持久化交付物记录为准，不再直接读 sandbox。

### 6.7 前端呈现

前端做两层区分：

1. `Run Replay / Files`  
   面向过程调试，继续展示 workspace 里的各类文件。

2. `Task Complete / Deliverables`  
   面向最终结果，只展示正式交付物。

交互要求：

- 完成卡片显示 `Task complete (N files)`。
- 对 `.pptx/.docx/.xlsx/.pdf/.zip` 显示下载按钮。
- 对可预览类型如 `pdf/image/html` 可额外提供预览。
- 不再把所有产物都塞进现有 `web/code` 二分逻辑。

### 6.8 成功/失败语义

run 状态规则统一如下：

- 只有交付物已持久化成功，状态才是 `completed`
- 文件生成了但持久化失败，状态必须是 `failed`
- assistant 最终文案不能宣称“已完成”，除非交付物下载入口已经可用

这样可以消除“日志说生成成功，但用户拿不到”的语义冲突。

## 8. 实施步骤

### 阶段 1：协议与入库

- 扩展 `complete_task.attachments`
- 新增交付物表与 DAO
- 在 run 完成前完成交付物校验与入库

### 阶段 2：下载链路

- 新增交付物列表与下载接口
- 前端完成卡片接入下载入口

### 阶段 3：产物识别收口

- 接入 workspace baseline 扫描
- 对 `shell_execute` 生成的办公文件进行完成前校验

### 阶段 4：办公 skill 对齐

- 更新 `PPT / Word / Excel` skill brief
- 明确要求“真实生成文件后，再通过 `complete_task.attachments` 宣告完成”

## 9. 验收标准

- 用户让智能体生成一份 `pptx/docx/xlsx/pdf` 后，完成消息中必须出现正式交付物卡片。
- 用户点击下载后，可以在本机直接获得文件。
- sandbox 关闭后，交付物仍可下载。
- 如果文件已生成但未完成持久化，run 必须失败而不是伪完成。
- `shell_execute` 生成的办公文件不能再因为未被 `write_file` 捕获而丢失。

## 10. 本次设计结论

这次不做“让用户去 sandbox 找文件”的补丁，也不做“只在 UI 上多放一个路径”的伪修复。

唯一正确的闭环是：

**把最终文件从 sandbox 内部产物，升级为平台正式交付物。**

只有做到这一点，办公类 skills 才真正具备产品意义。
