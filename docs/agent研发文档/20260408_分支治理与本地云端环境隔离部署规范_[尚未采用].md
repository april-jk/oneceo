# 20260408 分支治理与本地云端环境隔离部署规范 [尚未采用]

## 1. 背景与目标

当前 oneceo 需要同时满足两类运行场景：

1. 本地开发：开发效率优先，允许通过 `.env` 快速联调。
2. 云端部署（Railway）：稳定与安全优先，必须由平台环境变量驱动，并通过前端 BFF 避免后端公网暴露。

同时，团队需要稳定的分支流转机制，保证：

1. 日常开发持续在 `task-creation-agent` 进行。
2. `develop` 始终用于 Railway 可部署集成环境。
3. 后续 `production` 可从稳定的 `develop` 收敛上线。

## 1.1 术语统一

为避免分支命名歧义，本规范统一以下术语：

1. `task-creation-agent`：开发主分支（你口述中的 test 分支职责归并到此分支，不再额外保留长期 `test`）。
2. `develop`：Railway 开发环境部署分支（你口述中的 development/develop 统一为 `develop`）。
3. `production`：生产部署分支。

## 2. 范围与非目标

### 2.1 范围

1. Git 分支职责与合并策略。
2. 本地/云端环境变量优先级规范。
3. Web BFF 反向代理与前端请求策略。
4. Railway 三服务（`oneceo-web`、`oneceo-api`、`oneceo-admin`）部署约束。
5. 发布检查、回滚与日常操作流程。

### 2.2 非目标

1. 不在本规范内新增第四个常驻服务。
2. 不引入双写或灰度分叉配置体系。
3. 不保留“旧直连后端公网域名”的并行主路径。

## 3. 分支治理规范

### 3.1 分支角色定义

1. `task-creation-agent`：主开发分支，所有功能开发与缺陷修复先进入此分支。
2. `develop`：集成与预发布部署分支，Railway 开发环境仅部署该分支。
3. `production`：生产部署分支，仅接收通过 `develop` 验证的版本。

### 3.2 标准流转

1. 功能分支（可选）：`feature/*` -> `task-creation-agent`。
2. 周期性发布到测试站：`task-creation-agent` -> `develop`。
3. 测试站验收通过：`develop` -> `production`。
4. 若 `develop` 上有应急修复，必须回灌到 `task-creation-agent`，禁止长期漂移。

### 3.3 合并原则

1. 禁止将“未验证的大杂烩提交”直接从开发分支推进到 `develop`。
2. 每次推进 `develop` 前必须通过第 7 节检查项。
3. 与部署无关的实验性改动，不得进入 `develop`。

## 4. 环境变量与 `.env` 优先级规范

### 4.1 总体策略

1. `.env` 是否存在是唯一门控条件。
2. 若存在 `.env`：仅使用 `.env` 作为业务配置来源。
3. 若不存在 `.env`：仅使用进程环境变量作为业务配置来源。
4. 禁止 `.env` 与进程环境变量并用作为业务配置来源。

### 4.2 判定条件（统一到三端）

1. 检测到 `.env` 文件：视为 `.env` 模式（通常用于本地开发与本地调试）。
2. 未检测到 `.env` 文件：视为环境变量模式（通常用于云端部署）。

### 4.3 端侧落地要求

1. API：`apps/api/src/config/load-env.ts` 先判断 `.env` 是否存在，再选择单一来源。
2. Web（Node server/BFF）：`apps/web/server/index.ts` 使用同样门控，不做“按环境混合补值”。
3. Admin：`apps/admin_management/server/load-env.ts` 与 API/Web 保持同策略。

### 4.4 配置准则

1. 本地允许使用 `apps/*/.env` 或工作区 `.env`。
2. Railway 禁止依赖仓库内 `.env` 作为真实配置来源。
3. 敏感信息只放 Railway Variables，不写入仓库文档示例中的真实值。

### 4.5 行为矩阵（必须满足）

1. 本地 `task-creation-agent`：默认存在 `.env`，仅使用 `.env`。
2. Railway `develop`：默认不放置 `.env`，仅使用 Railway Variables。
3. Railway `production`：与 `develop` 保持一致，仅使用 Railway Variables。

## 5. Web BFF 与网络暴露策略

### 5.1 目标

1. 浏览器侧仅访问 Web 同源路径（`/api`、`/ws/task-creation`、`/socket.io`）。
2. API 服务优先仅保留内网访问（Railway private domain）。

### 5.2 BFF 路由约束

`oneceo-web` 服务端必须转发：

1. `HTTP /api/*` -> API。
2. `HTTP /socket.io/*` -> API。
3. `WS /ws/task-creation` -> API。
4. `WS /socket.io/*` -> API。

### 5.3 目标地址解析顺序

1. `WEB_BFF_API_TARGET`（最高优先）。
2. `ONECEO_API_URL`。
3. 默认 `http://127.0.0.1:4000`（仅本地兜底）。

说明：本地与云端需要不同域名时，通过 `.env`（本地）与 Railway Variables（云端）分别配置同名键实现，不通过代码分支硬编码域名。

### 5.4 本地与云端兼容要求

1. 本地：保持开发体验，可继续通过本地地址联调。
2. 云端：前端不得拼接 API 公网地址，统一同源走 BFF。
3. 结果：避免 Mixed Content/CORS/域名漂移。

## 6. Railway 部署拓扑规范

### 6.1 固定三服务

1. `oneceo-web`
2. `oneceo-api`
3. `oneceo-admin`

### 6.2 域名策略

1. `oneceo-web`：开发域名（例如 `dev.oneceo.ai`）或 Railway 随机域名。
2. `oneceo-admin`：可先使用 Railway 随机域名，不强制独立自定义域名。
3. `oneceo-api`：优先不暴露公网，供 `web/admin` 内网调用。

### 6.3 服务间变量注入（示例）

1. `oneceo-web` 注入 `ONECEO_API_URL=http://${{oneceo-api.RAILWAY_PRIVATE_DOMAIN}}`。
2. `oneceo-api` 注入数据库、Redis 等核心变量。
3. `oneceo-admin` 注入其后端访问所需变量，不复用无关变量。

## 7. 从 `task-creation-agent` 推进到 `develop` 的发布检查单

每次推进前必须完成：

1. 构建通过：
   - `pnpm --filter @oneceo/shared build`
   - `pnpm --filter api build`
   - `pnpm --filter web build`
   - `pnpm --filter oneceo-admin-management build`
2. 关键链路验证：
   - 注册/登录接口可用。
   - `task-creation` WebSocket 建连可用。
   - `settings/skills` 与 session 详情接口无 4xx/5xx 异常回归。
3. 前端网络验证：
   - 浏览器请求走同源 `/api/*`。
   - 无 `https 页面 -> http 资源` Mixed Content 报错。
4. 变量验证：
   - `.env` 模式下不依赖进程环境变量补值。
   - 环境变量模式下不依赖 `.env` 文件。

## 8. 日常操作 SOP

### 8.1 开发节奏

1. 在 `task-creation-agent` 开发并自测。
2. 按主题整理提交（避免混入无关变更）。
3. 定期合并到 `develop` 并触发 Railway 部署。
4. 在 `develop` 完成真实环境回归。

### 8.2 推进门禁（合并前必须满足）

1. `task-creation-agent -> develop`：必须满足第 7 节全部检查项。
2. `develop -> production`：除第 7 节外，必须补充一次线上回归记录（关键页面、关键接口、关键 WebSocket）。
3. 任一门禁未通过时，禁止“先合并后修复”。

### 8.3 发布节奏

1. 当 `develop` 稳定后再合并到 `production`。
2. `production` 只接受已在 `develop` 验证过的提交集合。

### 8.4 异常回滚

1. 云端回滚优先采用分支回退或部署回滚到上个稳定提交。
2. 回滚后必须把修复计划先落文档，再回到 `task-creation-agent` 修正。

## 9. 验收标准

满足以下条件即认为本规范可采用：

1. 团队按此流转后，`develop` 可持续稳定部署。
2. 本地开发无需破坏现有 `.env` 使用习惯。
3. 云端部署不再依赖 `.env` 覆盖平台变量。
4. Web 通过 BFF 成功隐藏 API 公网暴露并保持联调与部署一致性。
