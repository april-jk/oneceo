# 12_用户注册默认会员与积分初始化收口修复 [20260505-1458已采用]

## 1. 背景

在用户态 Google/GitHub 社交登录接入后，`app_users` 的首次创建已经不再只来自邮箱注册。

排查 staging 后确认：

1. 邮箱注册链路会尝试执行“默认会员绑定”
2. Google/GitHub 首次注册链路只创建 `app_users` 和 session，没有执行默认会员绑定
3. 用户积分页在 `user_credits` 不存在时直接返回 `0`
4. 因此 OAuth 首次注册用户会出现“已成功登录，但没有默认会员，也没有默认积分”的不一致状态

这不是环境配置问题，而是注册入口初始化逻辑分叉导致的实现缺口。

## 2. 目标

本次修复只收口一件事：

1. 所有“首次创建 `app_users`”的注册入口，必须共享同一套注册后初始化逻辑

覆盖范围：

1. 邮箱注册
2. Google 首次注册
3. GitHub 首次注册

## 3. 采用规则

### 3.1 单一初始化入口

新增统一的新用户初始化入口，负责处理“注册完成后的默认权益落账”。

约束：

1. 邮箱注册不得再单独写一套默认会员逻辑
2. OAuth 首次注册不得绕过该入口
3. 后续若新增新的用户态注册方式，也必须复用该入口

### 3.2 默认积分来源唯一

新用户默认积分只能来自默认会员计划，不允许再保留独立的“注册固定送 N 积分”并行逻辑。

原因：

1. 会员方案已经定义“默认积分由默认会员决定”
2. 两套赠送来源并存会让后台配置和真实到账结果不一致
3. 继续保留固定赠送值会让运维误以为默认会员配置失效

### 3.3 无默认会员时的行为

如果当前没有启用中的默认会员计划：

1. 注册流程仍可完成
2. 用户不会自动获得会员和积分
3. 系统行为以后台当前默认会员配置为准，不额外追加兜底赠送

## 4. 实现要求

### 4.1 代码入口

统一初始化入口至少要被以下调用点复用：

1. `apps/api/src/services/app-auth-service.ts`
2. `apps/api/src/services/app-auth-oauth-service.ts`

### 4.2 初始化内容

本次入口只负责：

1. 绑定默认会员
2. 通过会员默认积分发放路径写入积分账本
3. 以事务方式与首次用户创建一起提交，禁止出现“`app_users` 已创建但默认会员初始化失败、客户端仍收到注册失败”的半成功状态

本次不做：

1. 新增独立注册奖励表
2. 新增兼容旧逻辑的双写方案
3. 新增常驻后台补偿入口

### 4.3 历史异常 OAuth 用户回填

对于修复上线前已经创建完成、但漏掉默认会员初始化的 OAuth 用户，采用一次性脚本回填，不走常驻路由或自动重试主链。

回填命中条件必须同时满足：

1. 存在 `app_user_oauth_accounts` 绑定
2. `user_memberships` 中不存在任何会员记录
3. `user_credits` 中不存在任何积分账户

回填排除条件：

1. 已有任意会员记录的用户不得重复回填
2. 已有积分账户的用户不得重复回填
3. 不通过“再次登录自动补偿”修复历史脏数据，避免把注册主链和历史修复链路混在一起

执行约束：

1. 脚本默认 dry-run，只输出候选用户，不改数据
2. 只有显式 `--apply` 时才真正补发默认会员与积分
3. 实际补发必须复用 `membershipService.assignDefaultMembershipForNewUser()`，保证审计日志、会员记录和积分账本来源一致

## 5. 验证要求

至少覆盖以下回归：

1. 邮箱注册时会调用统一初始化入口
2. Google/GitHub 首次注册时会调用统一初始化入口
3. OAuth 绑定到已存在邮箱用户时，不应把该用户误判为“首次注册”
4. 移除“固定 500 积分赠送”后，默认积分来源仍然可解释且唯一
5. 如果默认会员初始化抛错，事务必须整体回滚，不能留下“已创建用户但未完成初始化”的脏状态
6. 历史 OAuth 回填脚本 dry-run 只命中“有 OAuth 绑定且没有会员记录、没有积分账户”的用户
7. 历史 OAuth 回填脚本 apply 后，补发结果必须通过既有会员分配主链落会员、积分和审计日志

## 6. 结论

从本文件采用开始，用户态“注册成功后的默认会员与积分初始化”以统一入口为准；任何新增注册方式都不能再各自实现一份初始化逻辑。
