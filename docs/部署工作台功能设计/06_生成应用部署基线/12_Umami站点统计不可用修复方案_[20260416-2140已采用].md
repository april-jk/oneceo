# Umami 站点统计不可用修复方案 [20260416-2140已采用]

## 1. 背景

当前 OneCEO 已经完成：

- 私有 Umami 实例接入
- 部署前模板 bootstrap 注入
- 部署时 Railway 环境变量写入
- 首次部署时 Umami website 自动绑定
- 部署工作台中的站点统计面板读取

但线上实际表现是：

- 网站可以成功部署并访问
- Umami website 也能被创建
- 部署面板显示 analytics 已绑定
- 实际访问网站后，站点统计长期不可用或没有真实数据

这说明问题不在“平台是否接入了 Umami”，而在“部署产物是否真的成功加载 tracker，并且 tracker 是否与最终公网域名正确绑定”。

## 2. 问题定义

本次要解决的是一个明确的主链问题：

1. 用户部署成功后，访问站点必须能被 Umami 正确采集。
2. 部署工作台中的站点统计必须来自真实访问数据，而不是只展示绑定状态。
3. 首次部署、重新部署、回滚后，统计绑定都必须与最终公网访问地址保持一致。

本次不做：

- 不更换 Umami 供应商
- 不新增第二套统计 SDK
- 不做兼容性补丁或多套注入逻辑并存
- 不把“统计不可用”降级成仅显示未启用提示

## 3. 根因结论

### 3.1 根因一：bootstrap 依赖 `%VITE_*%` 占位符，但主链没有统一替换闭环

当前平台注入到 HTML 的 analytics bootstrap 使用的是：

- `%VITE_ANALYTICS_ENABLED%`
- `%VITE_ANALYTICS_HOST%`
- `%VITE_ANALYTICS_WEBSITE_ID%`
- `%VITE_ANALYTICS_TAG%`

问题在于，这些占位符只有静态兜底模板的 `server.js` 明确在响应 HTML 时做了替换；普通部署项目的通用链路里，并没有统一保证 HTML 或运行时脚本会把这些占位符替换成真实值。

这会导致浏览器最终拿到的仍可能是字面量：

- `%VITE_ANALYTICS_HOST%/script.js`
- `%VITE_ANALYTICS_WEBSITE_ID%`

结果是 tracker 脚本并没有被正确加载，页面访问也不会进入 Umami 统计。

### 3.2 根因二：首次部署前绑定的是预估域名，部署成功后没有用最终公网地址回写

当前 `deploy` 路径会在真正发布前先做一次 analytics binding。此时使用的域名来源优先是：

- sandbox metadata 中已有值
- 账号默认 `serviceDomain`

但首次部署后，用户真正访问的通常是：

- `latestStaticUrl`
- `latestUrl`
- `domains[0]`

也就是部署完成后 Railway 给出的最终公网地址。

当前首次部署成功后，没有再用最终公网地址执行一次 analytics rebind，因此会出现：

- Umami website 绑定的是旧域名或预估域名
- 用户访问的是最终公网域名
- Umami 不会把这次访问记到正确 website 下

### 3.3 根因三：现有 smoke 只验证“绑定存在”，没有验证“真实埋点生效”

当前验收脚本只验证：

- Umami website 创建成功
- Railway 环境变量存在
- 页面可以打开
- 能从 Umami API 查询 metrics

但没有验证：

- 页面里是否真的加载了有效的 tracker script
- tracker 请求是否真的发到了 `analytics.oneceo.ai`
- 访问页面后 metrics 是否发生增量

因此这个回归被现有 smoke 漏掉了。

## 4. 修复目标

本方案落地后，必须满足：

1. 平台注入的 analytics 配置在所有可部署网站上都能稳定生效。
2. 首次部署成功后，analytics 绑定域名与最终公网地址一致。
3. redeploy / rollback 后，同样能继续维持正确绑定。
4. 回归脚本必须能证明“真实访问 -> tracker 请求 -> Umami 指标增长”。
5. 部署工作台展示的统计状态必须与真实采集状态一致。

## 5. 方案原则

- 不做兼容性补丁
- 不保留“占位符注入”和“运行时拼接”两套长期并行机制
- 以平台统一注入契约为唯一事实来源
- 先修主链正确性，再补验收
- 以最短路径修复，不额外引入新供应商、新 SDK 或新模板体系

## 6. 修复方案

## 6.1 收敛 analytics 注入契约，去掉对 `%VITE_*%` 直接字面量的依赖

### 现状问题

当前 bootstrap 直接把 `%VITE_*%` 写入 HTML 片段，默认假设部署运行时一定会替换这些值。

但这不是平台统一成立的保证。

### 目标状态

平台必须输出一个统一且真实可读取的 analytics runtime config，bootstrap 只读取这个 config，不再依赖裸 `%VITE_*%` 占位符是否会在最终产物中被替换。

### 推荐实现

统一改成以下结构：

1. 平台在部署导出阶段生成固定注入片段，例如：
   - `window.__ONECEO_ANALYTICS__ = { enabled, host, websiteId, tag }`
2. bootstrap 只读取 `window.__ONECEO_ANALYTICS__`
3. 如果配置缺失，bootstrap 直接退出，不再拼接字面量 `%VITE_*%`

这样无论网站最终是：

- 静态模板
- Vite
- React 单页
- Node 静态服务

只要 HTML 入口被平台注入，就能拿到真实配置。

### 修改范围

- `apps/api/src/services/deployment-template-bootstrap-service.ts`
- 如有必要，同步收敛 `apps/api/src/services/task-creation-deployment-source-service.ts` 里的静态模板兜底逻辑，避免两套注入语义长期分叉

## 6.2 首次部署成功后追加一次 analytics rebind

### 现状问题

首次 `deploy` 只在发布前做 analytics binding，部署完成后没有用最终访问地址回写。

### 目标状态

部署成功且拿到最终公网地址后，再执行一次 analytics binding：

1. 优先取：
   - `panel.latestStaticUrl`
   - `panel.latestUrl`
   - `panel.domains[0]`
2. 用该地址重新计算规范化域名
3. 若与当前 metadata 中记录的域名不同，则：
   - 更新 Umami website domain
   - 重新写入部署变量
   - 更新 sandbox metadata 中的 analytics 记录

### 修改范围

- `apps/api/src/services/task-session-deployment-runtime-service.ts`
- `apps/api/src/services/task-session-deployment-analytics-service.ts`
- 如 Umami API 当前没有 update website 能力，则在 `apps/api/src/services/umami-analytics-service.ts` 增加 website 更新接口

## 6.3 统一 deploy / redeploy / rollback 的 analytics 收敛时机

### 目标状态

三个动作都统一遵守：

1. 动作前允许做一次预绑定，保证变量和 website 先准备好
2. 动作完成并拿到最终公网地址后，必须做一次最终绑定确认
3. 前后两次绑定若域名一致，不做多余写入

这样可以避免：

- 首次部署绑定不准
- redeploy 后地址变化但统计没跟上
- rollback 后站点恢复了但统计仍指向错误域名

## 6.4 升级 smoke，必须验证真实埋点

### 新验收要求

部署 smoke 不能只验证“变量存在”，必须增加：

1. 请求部署页面 HTML，确认已存在有效 analytics runtime config
2. 断言页面中最终 tracker 地址是 `https://analytics.oneceo.ai/script.js` 或当前配置 host 对应地址
3. 用无头浏览器真实访问页面
4. 轮询 Umami metrics，确认 `pageviews` 或 `visits` 出现增长

### 修改范围

- `apps/api/scripts/_tmp/_tmp_deployment_e2e_smoke.ts`
- 如现有脚本不适合做浏览器访问，应补一个专门的 deployment analytics smoke

## 6.5 工作台状态语义同步调整

部署工作台当前的 analytics 面板应明确区分：

- `bound`：已完成 website/变量绑定
- `tracking`：最近一次真实验证通过，已检测到有效访问数据
- `error`：绑定存在但真实追踪失败

不能继续把“websiteId 已生成”视为“统计可用”的充分条件。

### 修改范围

- `apps/api/src/services/task-session-deployment-analytics-service.ts`
- 部署工作台对应前端展示逻辑

## 7. 实施步骤

1. 收敛 analytics bootstrap 配置结构
2. 增加 Umami website domain update 能力（若当前缺失）
3. 改造首次 deploy 成功后的 analytics rebind
4. 统一 redeploy / rollback 的最终绑定确认
5. 升级 deployment smoke，补真实 tracker 验证
6. 调整工作台 analytics 状态语义
7. 用真实样例完成端到端回归

## 8. 验收标准

以下条件必须同时满足：

1. 首次部署成功后，页面 HTML 中可读到真实 analytics config，而不是 `%VITE_*%` 字面量
2. 页面访问时能实际请求 `analytics.oneceo.ai/script.js`
3. Umami 后台对应 website 的 `pageviews` 或 `visits` 在访问后发生增长
4. 部署工作台中 analytics 状态为“tracking”
5. redeploy / rollback 后同样成立

## 9. 风险与边界

### 风险一：仅修 rebind，不修 bootstrap

如果只在部署成功后回写域名，但页面里依然没有有效 tracker 配置，统计仍然不会生效。

### 风险二：仅修 bootstrap，不修最终域名回写

如果 tracker 能加载，但 Umami website 绑定的仍是旧域名，最终公网域名访问仍可能不计入目标站点。

### 风险三：继续沿用现有 smoke

如果不补真实埋点验证，后续同类问题还会再次漏进主分支。

## 11. 评审结论

- 当前状态：`[20260416-2140已采用]`
- 已确认方向：
  1. 废弃“把 `%VITE_*%` 直接当作长期稳定契约”的实现假设，改为平台统一 runtime config 注入语义
  2. 将“部署成功后按最终公网地址做最终 rebind”纳入 deploy 主链
  3. 提升 deployment smoke，至少阻断未替换 analytics 占位符再次进入主链
