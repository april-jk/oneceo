# 20260418 部署主链 Railway / Umami / Agent 执行层真实复跑测试方案

## 测试目标

验证当前部署主链在真实会话下是否能够稳定完成以下链路：

1. 用户注册并创建真实任务会话
2. 启动 Altus managed runtime，并在 E2B sandbox 内生成可部署项目代码
3. 部署到 Railway
4. 在部署面板中拿到真实部署数据
5. Umami 模板注入为具体配置值而不是占位符
6. 真实线上页面可访问，并具备可观察的埋点绑定状态
7. 测试结束后回收本次产生的 sandbox 与测试会话

## 测试边界

本次只验证当前已采用修复方案覆盖的主链，不扩展到：

1. 多项目并发部署
2. 手工 connector 绑定联调
3. 历史归档恢复后的二次部署
4. 管理端后台观测页面

## 测试单元清单

### 1. 用户态鉴权与会话建立

#### 单元 1.1 `POST /api/auth/register`

- 预期输入：
  - 唯一邮箱
  - 合法密码
  - `displayName`
- 预期输出：
  - 返回 `success: true`
  - 返回用户信息
  - 响应头写入 `app_session_id`
- 边界条件：
  - 邮箱必须唯一
- 失败条件：
  - 未写入 cookie
  - 返回用户为空
- 验证方式：
  - 脚本读取响应 JSON
  - 脚本校验 `set-cookie`

#### 单元 1.2 `POST /api/task-creation/sessions`

- 预期输入：
  - 已登录 cookie
  - `mode=altus`
  - `title`
- 预期输出：
  - 返回 `sessionId`
  - 会话状态可查询
- 边界条件：
  - 必须归属当前用户
- 失败条件：
  - 返回会话为空
  - 后续查询 404/403
- 验证方式：
  - 脚本读取返回值
  - 随后调用 `GET /api/task-creation/sessions/:sessionId`

### 2. Runtime 启动与 sandbox 绑定

#### 单元 2.1 `POST /api/task-creation/sessions/:sessionId/runtime/start`

- 预期输入：
  - 有效 `sessionId`
  - 当前用户 cookie
- 预期输出：
  - 返回 runtime 信息
  - `orchestratorSessionId` 存在
- 边界条件：
  - 会话必须属于当前用户
- 失败条件：
  - 返回执行环境未就绪
  - 无 `orchestratorSessionId`
- 验证方式：
  - 脚本断言 runtime 字段
  - 随后调用 `GET /api/task-creation/sessions/:sessionId`

#### 单元 2.2 `GET /api/task-creation/sessions/:sessionId`

- 预期输入：
  - 有效 `sessionId`
- 预期输出：
  - `runtime.orchestratorSessionId` 与启动返回一致
  - `runtimeStatus.status` 最终进入可执行态
- 边界条件：
  - 启动初期允许短暂非 ready
- 失败条件：
  - 持续为空或进入 failed
- 验证方式：
  - 脚本轮询查询

### 3. Agent 编码执行

#### 单元 3.1 `POST /api/altus-managed/inputs`

- 预期输入：
  - 当前用户 cookie
  - `sessionId`
  - 明确的生成指令：创建一个最小可部署页面，并在页面内渲染唯一文本标识
- 预期输出：
  - 返回 `run.id`
  - run 进入 `queued/running`
- 边界条件：
  - 指令必须包含唯一标识，便于后续校验部署页面
- 失败条件：
  - 未创建 run
  - 直接报错结束
- 验证方式：
  - 脚本记录 `runId`
  - 轮询 `GET /api/altus-managed/sessions/:sessionId/runs/latest`

#### 单元 3.2 `GET /api/altus-managed/sessions/:sessionId/runs/latest`

- 预期输入：
  - 当前用户 cookie
  - `sessionId`
- 预期输出：
  - run 最终进入 `completed` 或明确的 `waiting_user`
- 边界条件：
  - 运行中允许经过 `queued/running/waiting_tool`
- 失败条件：
  - `failed/stopped`
  - 长时间无状态推进
- 验证方式：
  - 脚本轮询状态
  - 如失败，抓取最近消息与部署面板辅助定位

#### 单元 3.3 `GET /api/task-creation/sessions/:sessionId/workspace/tree`

- 预期输入：
  - 当前用户 cookie
  - `refresh=1`
- 预期输出：
  - 工作区存在部署项目关键文件
- 边界条件：
  - 不强依赖固定框架，但必须存在入口文件与依赖清单
- 失败条件：
  - 工作区为空
  - 无可部署项目结构
- 验证方式：
  - 脚本校验 `package.json` 与入口文件存在

### 4. 模板与部署前检查

#### 单元 4.1 `GET /api/task-creation/sessions/:sessionId/deployment/template`

- 预期输入：
  - 当前用户 cookie
  - `sessionId`
- 预期输出：
  - 返回模板检查数据
  - 不存在 `%VITE_...%` 这类占位符残留
- 边界条件：
  - 若未配置 analytics，也必须生成 disabled 的具体配置对象
- 失败条件：
  - 检查结果显示占位符未替换
- 验证方式：
  - 脚本读取模板检查响应
  - 必要时读取工作区内 bootstrap 文件原文

#### 单元 4.2 `sandbox_execution_environments.metadata.deploymentState`

- 预期输入：
  - 本次会话对应的 `orchestratorSessionId`
- 预期输出：
  - 部署触发后 metadata 内存在 `deploymentState`
  - 状态与 deployment panel 一致
- 边界条件：
  - 进行中允许为 `provisioning`
- 失败条件：
  - 面板有值但 metadata 无状态
  - provider error 未写入 metadata
- 验证方式：
  - E2E 脚本直接通过 DAO 读取环境 metadata

### 5. Railway 部署与部署面板

#### 单元 5.1 `POST /api/task-creation/sessions/:sessionId/deployment/deploy`

- 预期输入：
  - 当前用户 cookie
  - `sessionId`
- 预期输出：
  - 返回 deployment panel
  - `bindingState` 不为空
  - 若平台资源异常，必须返回明确 repair/provider 状态，而不是空白首发状态
- 边界条件：
  - 首次部署允许先进入 `provisioning`
- 失败条件：
  - 返回空面板
  - provider error 未被分类
- 验证方式：
  - 脚本断言面板关键字段

#### 单元 5.2 `GET /api/task-creation/sessions/:sessionId/deployment`

- 预期输入：
  - 当前用户 cookie
  - `sessionId`
- 预期输出：
  - 最终返回可解释的部署状态
  - 成功时存在 `primaryUrl` 或可访问 deployment URL
  - 失败时存在 `bindingState/providerErrorCode/providerErrorMessage`
- 边界条件：
  - 轮询期间允许 `provisioningPhase` 递进
- 失败条件：
  - 页面持续空白/无 deployment 数据
- 验证方式：
  - 脚本轮询 deployment panel
  - 记录 phase 变化

### 6. 线上访问与 Umami 绑定

#### 单元 6.1 公网部署地址可访问

- 预期输入：
  - 部署面板返回的公网地址
- 预期输出：
  - 返回 200
  - 页面内容包含本次 run 指令中的唯一文本标识
- 边界条件：
  - 初次访问允许短暂冷启动
- 失败条件：
  - 长时间不可访问
  - 页面内容不是本次生成内容
- 验证方式：
  - 脚本 HTTP 轮询
  - Playwright 打开页面并截图

#### 单元 6.2 部署面板 analytics 状态

- 预期输入：
  - 同一 `sessionId`
- 预期输出：
  - `analytics.status` 至少为 `bound`
  - 如果访问产生统计信号，可提升到 `tracking`
- 边界条件：
  - Umami 聚合可能存在延迟
- 失败条件：
  - 一直停留在错误的未配置状态
- 验证方式：
  - 脚本在公网页面产生访问后轮询 deployment panel

### 7. 回收与清理

#### 单元 7.1 sandbox 回收

- 预期输入：
  - 本次真实复跑产生的 `orchestratorSessionId`
- 预期输出：
  - E2B sandbox 被 kill 或明确进入关闭态
- 边界条件：
  - 删除会话不等于一定关闭 sandbox，因此必须显式回收
- 失败条件：
  - sandbox 遗留继续计费
- 验证方式：
  - E2E 脚本在 `finally` 中执行回收
  - 记录回收结果

#### 单元 7.2 测试会话删除

- 预期输入：
  - 当前用户 cookie
  - `sessionId`
- 预期输出：
  - 会话删除成功
- 边界条件：
  - 即使部署成功也必须清理测试会话
- 失败条件：
  - 会话残留
- 验证方式：
  - 脚本执行 `DELETE /api/task-creation/sessions/:sessionId`

## 实施方式

1. 新增真实 E2E 脚本，放在现有测试目录下，避免改变测试目录结构。
2. 脚本执行顺序固定为：
   - 注册用户
   - 创建会话
   - 启动 runtime
   - 发起 managed run 生成代码
   - 校验工作区与模板
   - 触发部署
   - 轮询部署面板
   - 访问公网页面
   - 轮询 analytics 状态
   - 清理 sandbox 与会话
3. 页面访问阶段同时做 HTTP 校验与 Playwright 校验，避免仅凭接口返回判断成功。

## 通过标准

同时满足以下条件才算通过：

1. managed run 成功生成可部署代码
2. 部署面板返回真实部署数据，不再空白
3. 部署结果要么成功上线可访问，要么给出明确的 provider repair 状态
4. 公网页面内的 analytics bootstrap 不含 `%VITE_...%` 占位符
5. analytics 状态至少达到 `bound`
6. sandbox 与测试会话已清理

## 失败判定

任一情况出现即判定本轮真实复跑失败：

1. run 进入 `failed/stopped`
2. 工作区未产出可部署项目
3. 部署接口返回空白或无可解释状态
4. 线上地址不可访问或内容不匹配
5. Umami 注入仍为占位符
6. 测试清理未执行成功
