# 05 Altus三级记忆实施步骤、验证与风险方案 [20260421-1629已采用]

更新时间：2026-04-21

---

## 1. 实施顺序

建议按下面顺序做，避免一上来同时改三层。

### 第一步：用户级

1. 扩展 `AppUserPersonalization`
2. 扩展设置页表单
3. 做旧字段兼容读取
4. 增加用户级记忆 Redis 读缓存与写后刷新

### 第二步：项目级

1. 扩展项目 create / update / detail
2. 项目创建 / 编辑弹窗增加 4 个记忆字段
3. 删除项目时增加“存在关联 session 则拒绝删除”的校验
4. 增加项目级记忆 Redis 读缓存与写后刷新

### 第三步：session 与项目归属

1. 扩展 `POST /sessions`，支持创建时直接带 `projectId`
2. 收紧 session 绑定 / 解绑项目接口，只允许未进入有效运行的 session 变更归属
3. 前端 session 菜单增加“加入项目 / 移出项目”
4. 首版禁止直接跨项目切换已有活跃 session

### 第四步：session 级 Altus memory

1. 新增 `task-session-altus-memory-service.ts`
2. 定义 `altusSessionMemory` 结构和 normalize 逻辑
3. 接入 DB、Redis 可选缓存、sandbox 文件

### 第五步：运行时组装

1. 新增 `altus-memory-context-service.ts`
2. 接入 managed run 入口
3. 接入 direct run 入口
4. 接入 prompt assembling

### 第六步：项目显示一致性

1. 项目改名时批量同步 session `projectName`
2. 校验 `metadata_json` merge 更新不会覆盖 `pinned` 等现有字段

## 2. 验证清单

至少覆盖：

1. 用户级记忆保存后，新 session 可被 Altus 读取
2. 新建 session 时直接指定 `projectId`，首轮 `initialMessage` / run 即可继承项目记忆
3. 项目创建时填写项目记忆，项目内 session 可继承
4. session 不绑定项目时，不应错误注入项目记忆
5. 未进入有效运行的无项目 session 可加入项目
6. 未进入有效运行的已归属项目 session 可移出项目
7. 已进入有效运行的 session 不能再修改项目归属
8. 已归属项目的活跃 session 不能直接迁到别的项目
9. 项目下仍有关联 session 时，不允许删除项目
10. 项目改名后，session 列表和侧边栏显示的新名称一致
11. session 级记忆在多轮 continuation 后仍可恢复
12. sandbox 丢失后，session 级记忆可从 DB 恢复
13. sandbox 文件缺失或损坏时，服务会保留 DB 当前值并重建文件副本
14. 项目记忆更新后，从下一轮运行开始生效
15. 用户级记忆更新后，从下一轮运行开始生效
16. 旧的 `role / about` 数据不会丢失
17. 三层记忆同时存在时，冲突优先级符合文档定义
18. 项目级记忆写入不会覆盖 `metadata_json` 中现有非 Altus 字段
19. session 级 Altus memory 的 flush 点、收口方式和 skills memory 保持同一复杂度级别
20. 用户级 / 项目级 Redis 失效时，运行链路自动回退 DB
21. 用户级 / 项目级写入后，下一次读取能命中新值，不读到旧缓存
22. session 级 memory 在单次 run 内不会因为多轮工具执行而反复读写 DB
23. session 级 memory 的回写流程与 skills memory 保持一致：读文件、normalize、写 DB、刷新 Redis

## 3. 风险点

## 3.1 旧数据兼容风险

当前已有：

1. `role`
2. `about`

如果兼容读取没做好，用户已有个性化资料会“看起来丢失”。

## 3.2 session 脏状态风险

如果没有限制跨项目迁移，session memory 会混入旧项目事实。

首版通过“禁止直接迁移”规避。

补充：

1. 如果允许已进入有效运行的 session 先解绑再重新绑定，本质上仍是变相跨项目迁移
2. 首版通过“项目归属锁定窗口”一起规避这条路径

## 3.3 文件回写倒退风险

如果 session memory 的文件回写机制比 skills memory 额外复杂，很容易引入新的隐藏竞态和状态机 bug。

首版通过“单 service 收口 + 受控 flush 点 + 单有效 sandbox 前提”规避。

## 3.4 高频 DB 访问风险

如果 session 级记忆在 run 过程中频繁读写 DB，会同时带来两类问题：

1. 数据库负载被多轮工具执行放大
2. 运行中状态更容易出现前后读写竞争

首版通过以下约束规避：

1. run 启动时装载一次
2. 运行态以内存快照和 sandbox 文件为主
3. 只在受控 flush 点写 DB
4. 写 DB 后再刷新 Redis

## 3.5 prompt 膨胀风险

三层记忆一起注入，容易让 prompt 变长。

首版通过：

1. 字段长度约束
2. prompt 总量预算
3. session memory 紧凑化

来控制。

## 3.6 项目显示漂移风险

如果项目改名后不刷新 session `projectName`，侧边栏和会话摘要会显示旧名称。

首版通过“项目改名时批量同步 session 展示缓存”规避。

## 3.6 Redis 一致性风险

如果把用户级 / 项目级 Redis 做成第二真相源，容易出现旧缓存覆盖新 DB 的问题。

首版通过以下约束规避：

1. Redis 只做读缓存
2. 先写 DB，再刷新或失效 Redis
3. Redis 异常时直接回退 DB
4. 不允许仅写 Redis

## 4. 本次明确不做

1. 向量检索
2. 用户级 / 项目级 Redis
3. 用户级 / 项目级 sandbox 文件副本
4. session memory 手工编辑 UI
5. 自动跨 session 聚类总结
6. 活跃 session 跨项目迁移
7. 强制删除带 session 的项目
8. 已进入有效运行的 session 修改项目归属
9. 比 skills memory 更复杂的额外回写协议
10. 把用户级 / 项目级 Redis 设计成独立真相源
