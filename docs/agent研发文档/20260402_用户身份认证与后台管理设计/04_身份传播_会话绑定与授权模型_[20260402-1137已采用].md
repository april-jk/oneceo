# 04 身份传播、会话绑定与授权模型 [20260402-1137已采用]

更新时间：2026-04-09

## 1. 目标

把“用户登录”真正落到业务数据归属上，确保以下对象都绑定到个人身份：

1. 对话 session
2. Altus run / stream
3. 用户 skills
4. connector profile
5. connector OAuth 授权
6. connector guide 的 session 级生效结果

同时把“管理员登录”单独落到后台治理链路上，且与普通用户身份物理分离。

## 2. 统一身份对象

### 2.1 AppUser

```ts
type AppUser = {
  id: string;
  email: string;
  passwordHash: string;
  displayName: string;
  status: 'active' | 'disabled';
  createdAt: string;
  updatedAt: string;
};
```

### 2.2 AdminUser

```ts
type AdminUser = {
  id: string;
  loginName: string;
  passwordHash: string;
  displayName: string;
  role: 'admin' | 'super_admin';
  status: 'active' | 'disabled';
  createdAt: string;
  updatedAt: string;
};
```

### 2.3 AppSessionAuthContext

```ts
type AppSessionAuthContext = {
  userId: string;
  tenantKey: string;
  role: 'user';
};
```

规则：

1. 用户端默认 `tenantKey = userId`
2. 后续即使支持团队空间，也不能破坏 `userId` 作为授权主键

### 2.4 AdminSessionAuthContext

```ts
type AdminSessionAuthContext = {
  adminUserId: string;
  role: 'admin' | 'super_admin';
};
```

## 3. 数据归属规则

### 3.1 对话 session

规则：

1. `task_session.userId` 必填，且指向 `app_users.id`
2. session 创建时直接写入当前登录用户
3. 不允许再出现匿名创建、后续补绑用户

### 3.2 用户 skills

规则：

1. 平台 skills 与用户启用记录分离
2. 用户自有 skill revision 只属于创建者
3. 当前用户只能读取自己的 user skill 绑定与启用状态

### 3.3 connector profile

规则：

1. connector profile 属于具体 `userId`
2. OAuth 回调完成后，把授权结果写入该用户的 profile
3. session attach 只能引用当前用户拥有的 profile

### 3.4 Altus run / stream

规则：

1. run 必须由 `sessionId -> userId` 归属推出
2. stream 订阅必须由服务端从登录态获取 `userId`
3. 不再允许前端 query 里明文拼接 `userId` 作为正式授权方式

### 3.5 其他需要补入用户态鉴权的能力

本轮检查后，以下能力也必须明确绑定到 `app_users.id`：

1. 会话详情读取
2. 会话消息 recent/history
3. workspace tree / dir / file / raw
4. 交付物下载
5. 运行时配置读取与更新
6. 附件拉取与上传
7. 会话标题、收藏、分享、删除
8. connector OAuth start / callback / detach

## 4. API 传播规则

### 4.1 用户端 API

由 cookie session 自动带身份。

服务端：

1. 解析 cookie
2. 注入 `currentUser`
3. 各业务 service 只接收已解析上下文

### 4.2 后台 API

同样由后台管理员 cookie session 驱动。

差异：

1. 需要额外校验 `role`
2. 需要写审计日志
3. 不允许复用用户态 cookie

## 5. 需要改造的现有链路

### 5.1 `client-identity`

现状：

1. 历史上浏览器本地会生成并传递 `X-User-Id`

改造：

1. 已移除 `X-User-Id` 身份注入
2. 正式主链固定为 cookie + `/auth/me`

### 5.2 `current-user-resolver`

现状：

1. 只从正式认证上下文解析用户身份

改造：

1. 用户态路由统一调用 `require(req)` 获取真实登录用户
2. 未登录直接返回 401，不再接受手工身份头

### 5.3 connector / skill / session service

统一要求：

1. 不再接受匿名用户
2. 不再使用本地随机 userId
3. 所有对象必须有可追溯的真实归属

### 5.4 后台全部管理路由

统一要求：

1. 后台路由全部走管理员登录态
2. 不允许通过网络层“能访问到后台端口”就直接管理平台

## 6. 数据表建议

首批新增：

1. `app_users`
2. `app_user_sessions`
3. `admin_users`
4. `admin_user_sessions`
5. `admin_audit_logs` 或扩展现有审计表

需要扩展：

1. `task_creation_sessions`
2. `user_skill_*`
3. `user_connector_accounts`
4. `task_session_connector_bindings`

## 7. 迁移策略

### 7.1 老数据

现有以匿名 `X-User-Id` 或本地 userId 生成的数据，需要区分：

1. 可明确归属的
2. 无法明确归属的

规则：

1. 能映射到真实用户的，做一次性回填
2. 无法确认归属的，标记为历史匿名数据，不进入新主链

### 7.2 新数据

从新认证体系上线后，所有新增数据必须只走正式登录态。

管理端所有新增审计和治理动作必须只走管理员登录态。

## 8. 验收标准

1. 用户登录后创建的 session、skills、connector profile 都能在 DB 中追溯到同一 `userId`
2. connector OAuth 回调后不会写到匿名用户或错误用户名下
3. run stream 不再靠 query 里的 `userId` 作为唯一授权依据
4. 后台可以看到资源归属，但后台身份不等于资源所有权
5. 用户态和管理端在数据库层、session 层、cookie 层都完全分离
