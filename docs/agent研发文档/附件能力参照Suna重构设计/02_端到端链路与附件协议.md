# 02 端到端链路与附件协议

## 1. 目标链路总览

```mermaid
sequenceDiagram
  participant U as User
  participant FE as Web Chat Input
  participant API as Task Input API
  participant PARSE as Attachment Parse Service
  participant E2B as e2bConnector
  participant RUN as Altus Managed Run
  participant SB as Sandbox(workspaceRoot/uploads)

  U->>FE: 添加本地/拖拽/粘贴/远程附件
  FE->>FE: pending attachments 状态管理
  U->>FE: 发送 content + attachments
  FE->>API: multipart(input content + files[])
  API->>PARSE: 规范化文件名 + 快速解析文本类内容
  API->>E2B: 确保 runtime/sandbox 就绪
  E2B->>SB: 上传文件到 workspaceRoot/uploads
  API->>API: 生成标准附件引用并持久化 user_input
  API->>RUN: 启动 managed run
  RUN->>RUN: Prompt 装配 file context
  RUN->>SB: Agent 读取 uploads 下文件
```

## 2. 目标用户流

### 2.1 输入阶段

用户可通过以下方式把文件加入当前待发送输入：

- 本地选择文件
- 拖拽文件到输入框
- 粘贴图片到输入框
- 输入公开分享链接导入远程文件
- 选择技能模板生成虚拟附件
- 选择 zip 文件时，按规则解包并导入内部文件

### 2.2 提交阶段

前端发送的不是“文本请求 + 附件上传请求”两条链，而是统一的“用户输入请求”：

- 文本内容
- 文件数组
- 客户端消息 key
- 可能的展示元信息

### 2.3 服务端处理阶段

服务端处理顺序固定为：

1. 解析输入
2. 校验文件类型、数量、大小
3. 规范化文件名
4. 解析文本类文件内容
5. 确保 session runtime/sandbox
6. 上传到 `workspaceRoot/uploads`
7. 生成标准附件引用
8. 写入 `user_input` 消息
9. 启动 managed run

### 2.4 Agent 使用阶段

Agent 获得两类附件上下文：

1. 用户消息中的标准附件引用
2. Prompt assembly 注入的文本类附件摘录
3. 用户消息中的多模态图片块

## 3. 标准附件落点

统一使用：

- `uploads/` 作为 workspace 内的相对目录
- 实际绝对路径为 `${workspaceRoot}/uploads`

原因：

1. 与 `suna` 的“工作区 uploads 目录”心智一致。
2. 保持 `oneceo` 现有 `workspaceRoot` 机制，不把 Altus/Sandbox 根目录错误写死成 `/workspace`。
3. 用户与 Agent 都容易理解。
4. 工作区内可直接访问，不需要隐藏目录心智转换。
5. 后续文件树、预览面板、下载链接都可直接复用。

明确废弃：

- `workspaceRoot/.attachments`

## 4. 标准附件引用协议

### 4.1 用户消息中的 canonical 格式

每个已成功处理的附件，统一写入消息内容：

```text
[Attached: product-spec.pdf (2.4 MB) -> uploads/product-spec.pdf]
```

如果发生自动重命名：

```text
[Attached: product-spec.pdf (2.4 MB) -> uploads/product-spec_20260327_101530_1.pdf]
```

### 4.2 协议要求

1. `Attached` 为固定关键字。
2. 左侧保留用户原始文件名。
3. 右侧保留 Sandbox 内实际路径。
4. 只写相对 `workspace` 的路径，即 `uploads/...`。
5. 该协议由服务端生成，前端不自行拼接。

### 4.3 为什么不能继续用自然语言列表

当前 `oneceo` 的：

- “已添加以下附件，可直接在工作区中访问”

有三个问题：

1. 不稳定，容易被模型当成普通说明文本。
2. 不利于前端后续做统一解析。
3. 不利于做引用去重、文件追踪、消息比对。

## 5. 消息元数据协议

除消息文本中的 canonical 引用外，仍保留结构化元数据，供前端渲染与业务追踪使用。

建议在 `user_input` 消息中写入：

```json
{
  "attachments": [
    {
      "sourceName": "product-spec.pdf",
      "storedName": "product-spec.pdf",
      "path": "uploads/product-spec.pdf",
      "size": 2516582,
      "mimeType": "application/pdf",
      "uploadedAt": "2026-03-27T10:15:30.000Z",
      "status": "ready"
    }
  ],
  "attachmentContext": [
    {
      "path": "uploads/product-spec.pdf",
      "sourceName": "product-spec.pdf",
      "size": 2516582,
      "mimeType": "application/pdf",
      "parsedText": "......"
    }
  ],
  "originalInput": "请根据附件梳理 PRD",
  "attachmentContextIncluded": true
}
```

### 5.1 元数据用途

- 前端显示附件 chips
- 消息回放
- run 诊断
- 后续产物引用
- Prompt assembly 的稳定输入来源

### 5.2 权威性规则

权威顺序定义为：

1. Sandbox 中的实际文件
2. 消息元数据中的结构化附件记录
3. 消息内容中的附件引用块

其中：

- 用户界面渲染优先使用元数据
- Agent/审计可同时依赖消息文本中的 canonical 引用
- 图片类附件的多模态输入来源于 `metadata.attachments`
- `conversation_messages` 与 `task_session_recent_messages` 的元数据存储白名单必须保留 `attachments / attachmentContext / attachmentContextIncluded / originalInput / question / options / runId`，否则历史回放会丢失图片外链所需的 `externalObjectKey`

## 6. 文本类附件内容上下文

### 6.1 设计目标

与 `suna` 对齐，文本类附件不能只上传路径，必须让 Agent 在本轮执行时拿到核心内容。

### 6.2 处理规则

服务端在收到文件后：

1. 识别文件类型。
2. 对文本、Markdown、JSON、CSV、代码、常见文档文本提取类文件做快速解析。
3. 对单文件解析文本做长度上限截断。
4. 生成本轮 `file context`。
5. 将截断后的解析结果持久化到该条 `user_input` 消息的 `metadata.attachmentContext` 中。

### 6.3 注入方式

不把解析全文直接塞进用户消息正文。

统一由 managed prompt assembly 从最近相关 `user_input.message.metadata.attachmentContext` 中读取并注入：

```text
--- ATTACHED FILE CONTENTS ---
### product-spec.md (12,431 bytes)
...
--- END OF ATTACHED FILES ---
```

### 6.4 图片类规则

图片类附件：

1. 继续保留 canonical 附件引用和结构化元数据。
2. 不走“先生成视觉描述，再把描述文本注入 prompt”的链路。
3. 在 managed prompt assembly 阶段，按消息级别把图片附件重新组装成多模态消息块。
4. 图片的 `image_url` 不再使用 `data:` URL，而是使用 Cloudflare R2 的短时签名下载 URL。
5. 该 R2 存储空间必须是“图片外链专用桶”，与当前内部归档桶彻底隔离。

多模态消息块形态：

```json
[
  { "type": "text", "text": "看看这个图讲了什么\n\n[Attached: exported_image.png -> uploads/...]" },
  {
    "type": "image_url",
    "image_url": {
      "url": "https://<account>.r2.cloudflarestorage.com/<bucket>/<key>?X-Amz-Algorithm=AWS4-HMAC-SHA256&..."
    }
  }
]
```

6. 多模态图片块的 URL 在模型调用前临时生成，不持久化签名 URL。
7. 若同一 run 存在多轮模型调用，则每轮调用前都要重新刷新签名 URL，避免处理中途过期。
8. 数据库存储的仅是 R2 object key、mimeType、size、uploadedAt 等稳定元数据。
9. 只有模型兼容的图片格式进入多模态块：`image/png`、`image/jpeg`、`image/gif`、`image/webp`。
10. 图片过大或格式不兼容时，不生成多模态块；此时仍保留附件引用和结构化元数据。
11. 如果当前 managed 默认模型不支持视觉输入，则运行时必须自动切换到支持视觉和工具调用的模型，不能继续使用纯文本模型再回退到 OCR/本地图像工具链。

### 6.5 为什么不能把图片先转成说明文本

这样做会重复踩 `suna` 已经绕开的坑：

1. 视觉信息在预解析阶段被降维，细节会丢失。
2. 同一张图在后续追问时无法稳定复用原始像素信息。
3. 预解析描述和实际图片可能出现偏差，Agent 会在错误前提上继续推理。

因此，图片的主链路必须是“文件上传成功后，在模型调用阶段直接作为视觉输入传递”。

### 6.6 R2 外链安全边界

图片外链能力必须满足以下强约束：

1. 不复用当前内部归档桶 `R2_BUCKET_NAME`。
2. 单独创建图片外链专用桶，例如 `R2_MANAGED_IMAGE_BUCKET_NAME`。
3. 单独使用图片桶专属 AK/SK，不与归档桶共用凭证。
4. 桶本身不设为公开读，不暴露 bucket public URL。
5. 对模型只提供短时签名 `GET` URL，默认有效期应极短，例如 5 分钟。
6. 数据库和消息元数据中禁止保存签名 URL，只保存 object key。
7. 对象 key 必须按 session 隔离，例如：

```text
managed-images/<sessionId>/<messageKey>/<timestamp>-<safeName>.png
```

8. 图片对象不允许列目录、不允许匿名访问、不允许覆盖写。
9. 归档桶中的工作区归档、状态文件、会话恢复数据绝不能通过任何签名图片接口被访问到。

## 7. 文件名规范化与重名处理

### 7.1 规范化

服务端统一做：

- 路径分隔符剔除
- Unicode 规范化
- 非法字符替换
- 长度截断

### 7.2 重名处理

若 `${workspaceRoot}/uploads` 下已存在同名文件，则自动改名，不覆盖原文件。

规则与 `suna` 保持一致：

- 优先保留原文件名
- 冲突时追加时间戳和序号

## 8. 约束与限制

建议沿用并整理为统一配置：

- 单文件大小上限
- 单次消息附件数量上限
- 压缩包内文件数量上限
- 压缩包解压总大小上限
- 允许类型白名单

这些限制由：

- 前端先行校验
- 服务端二次校验

## 9. 与当前 oneceo 的替换关系

需要替换的当前做法：

1. `appendAttachmentsToPrompt(...)` 生成自然语言附件列表。
2. 先调用 `/sessions/:sessionId/attachments`，再单独发文本。
3. 默认写入 `.attachments/`。
4. 图片附件只作为路径存在于消息文本中，不进入模型的视觉输入。

替换后的目标做法：

1. 发送统一的 `content + files[]` 输入请求。
2. 服务端生成 canonical 引用块。
3. 文件统一落到 `${workspaceRoot}/uploads`，消息中只记录相对路径 `uploads/...`。
4. prompt assembly 从消息元数据中的 `attachmentContext` 注入文本类附件上下文。
