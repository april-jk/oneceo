# AGENTS Git 协作开发指南

本文用于指导 `oneceo/` 仓库内的协作开发与提交。

## 基本约定

- 修改前先执行：
  - `git branch --show-current`
  - `git status --short`
- 提交前再次执行：
  - `git status --short`
  - `git diff --stat`
- 不要跨系统误改，遵循目录边界。
- 大范围改动请拆分提交，避免把多个主题混在一个提交里。
- 改文档时要同时清理过时引用、失效接口和错误路径。
- 若本次修改依赖已采用设计文档，应在提交说明或文档里体现依据。

## 多人多系统协作前提

这是一个多人同时开发、并且跨 `macOS / Windows / Linux` 的仓库，Git 协作目标不是“我本地能提交就行”，而是：

1. 不干扰其他开发者正在进行的改动
2. 不盲目覆盖别人的文件
3. 不盲目合并自己没看懂的冲突
4. 不把本机环境差异误提交成业务改动

因此必须额外遵守下面这些规则。

## 分支与工作方式

- 当前常见工作分支是 `task-creation-agent`，但实际以你当前所在分支为准。
- 不要把旧 worktree、旧分支或别的机器路径当成当前事实。
- 若需新建临时分支，建议围绕单一主题命名，避免泛化名称。
- 如果发现工作区里有你未创建的变更，先判断是否和当前任务同文件、同主题：
  - 同文件或强相关：先读懂，再决定是否继续
  - 无关文件：不要回退、不要整理、不要顺手修

## 修改边界规则

- 只修改与你当前任务直接相关的文件。
- 不得为了“顺手统一风格”批量改动无关文件。
- 不得提交以下高风险噪音：
  - 本机路径
  - 系统特有换行符噪音
  - 无意义格式化
  - `.DS_Store`
  - 临时日志
  - 本地缓存
  - 构建产物，除非任务明确要求
- 修改前如果文件已经有未提交改动，先看清楚这些改动是否可能属于其他人或其他任务。

## 禁止事项

- 禁止 `git reset --hard`
- 禁止 `git checkout -- <file>`
- 禁止无理解地解决冲突后直接提交
- 禁止把整份文件用自己的版本直接覆盖掉别人的改动
- 禁止因为本机能运行就替换掉别人的跨平台写法
- 禁止把 rebase / merge 过程中自己没看懂的冲突块直接删掉

## 拉取与同步原则

- 开始开发前，先确认当前分支是否需要同步最新远端。
- 如果需要拉取最新改动，优先做法是：
  1. 先看 `git status --short` 是否干净
  2. 再决定 `fetch`、`rebase` 或 `merge`
  3. 发生冲突时逐块理解，不允许机械选择 `ours` 或 `theirs`
- 如果当前工作区已经有未提交改动，不要直接执行会改写工作树的大动作。

## 处理冲突的原则

- 冲突不是“选一边”，而是恢复两边真实意图。
- 解决冲突时至少检查三件事：
  1. 对方改了什么
  2. 你改了什么
  3. 最终结果是否同时保留两边必要逻辑
- 如果冲突涉及以下内容，不能凭感觉处理：
  - 认证
  - Sandbox 生命周期
  - OSAC / MCP
  - 连接器
  - 会话状态机
  - Redis key / stream / TTL

## 跨系统注意事项

- 注意 `macOS / Linux / Windows` 的差异：
  - 路径分隔符
  - 大小写敏感性
  - 换行符
  - shell 命令可用性
  - 本地绝对路径
- 提交前要确认没有把某个平台专用写法误改成只适配你当前系统。
- 文档示例若写绝对路径，必须确保是当前仓库真实需要，不要把本机历史路径提交进去。

## 提交规范

- 提交信息必须使用中文。
- 提交信息要清楚说明“做了什么”和“为什么做”。
- 推荐格式：`[提交类型] 修改内容；修改目的`

## 提交信息生成规则

- 提交 Git 时，不能只参照“当前这一轮对话最后一句要求”来写提交信息。
- 提交信息必须参照以下两个维度共同归纳：
  1. 最近几次对话中，实际连续完成了什么
  2. 从“上一次 commit”到“这一次 commit”之间，代码和文档真实发生了什么变更
- 如果一个提交里包含的是连续几轮对话共同完成的结果，提交信息必须覆盖这些连续变更的共同主题，不能只写最后一次对话的表面动作。
- 如果用户在几轮对话中逐步补充要求，而你一直没有提交，那么提交信息必须按“这整个未提交区间的最终结果”来写。
- 判断提交信息时，优先级应是：
  1. `git diff --stat`
  2. `git diff --cached`
  3. 相关文件实际内容
  4. 最近几次对话上下文
  5. 最后一句用户消息
- 最后一句用户消息只能帮助你理解“当前收口动作”，不能替代对实际改动内容的归纳。

## 提交前的提交说明检查

- 写提交信息前，至少回答这几个问题：
  1. 这次暂存区里一共改了哪些主题
  2. 这些改动是一次对话完成的，还是几次对话累计完成的
  3. 自上次提交以来，最主要的结果是什么
  4. 提交信息是否遗漏了暂存区里已经存在的重要改动
- 如果暂存区包含多个不应混在一起的主题，不要靠一个模糊提交信息硬包住，应该拆分提交。
- 如果提交信息只能描述“最后一次对话做了什么”，但不能准确描述暂存区全部改动，说明你还不应该提交。

提交类型至少包含以下之一：

- `新功能`
- `修复`
- `重构`
- `文档`
- `测试`
- `构建`
- `杂项`

示例：

- `[修复] 修正 task session 恢复后连接器绑定未重建；避免恢复后 MCP 工具缺失`
- `[文档] 更新 AGENTS_GUIDE 执行链路说明；清理旧三智能体接口描述`
- `[重构] 统一 Altus managed run 状态写入链路；避免最近几轮调整后事件状态不一致`
- `[文档] 更新 AGENTS 与 Git 协作规范；反映当前架构并约束多人协作提交流程`

## 合并前检查

- 至少做一次最小可行验证。
- 确认 `git diff` 里没有混入无关改动。
- 确认不会覆盖别人已在当前文件中做出的未合并调整。
- 涉及 Sandbox / OSAC / MCP / 连接器 / 认证时，优先附上：
  - 本地验证命令
  - 请求路径
  - 日志关键词
  - 是否依赖外部环境

## 不应做的事

- 不要为了“看起来兼容”保留明显过时的文档叙述。
- 不要在未核对代码现状前复用旧提交模板或旧接口说明。
- 不要把 KVM 历史链路误当作当前主执行方案提交进去。
- 不要把“多人协作仓库”当成单人本地仓库使用。
