# Altus 智能体能力测试体系设计 [20260420-1327已采用]

## 1. 目标

建立一套可以长期维护、可重复执行、可回溯对比的 Altus 智能体能力测试体系，用于回答以下问题：

1. 当前 Altus 在不同能力域下是否稳定达标。
2. 模型、prompt、tool schema、skill 挂载策略变更后，能力是提升还是退化。
3. 某次失败究竟是意图识别、澄清、工具选择、执行闭环还是结果表达的问题。
4. 同一题目能否在未来继续复跑，并保持可横向对比。

## 2. 设计原则

### 2.1 长期可用

- 题目优先考察能力本身，不绑定短期产品文案。
- 题目编号长期稳定，允许内容迭代但不随意改 `case_id`。
- 同一题库允许多版本并存，使用 `suite_version` / `case_version` 管理。

### 2.2 可重复执行

- 每个题目必须包含明确的输入、前置条件、预期行为、禁止行为、必备证据。
- 每次执行必须记录代码版本、模型版本、配置摘要、执行时间、环境标签。
- 分数必须能依据原始证据回放，不接受“只看主观印象”的结论。

### 2.3 可归因

- 评分拆成硬失败项与质量分。
- 失败时必须能定位到能力域，而不是只有一个总分。
- 结果存储必须保留 run 级别与 case 级别明细。

### 2.4 低耦合

- 题目不直接依赖某个短期 UI 文案。
- 优先考察可观察行为，例如：
  - 是否进入 `waiting_user`
  - 是否触发指定 tool
  - 是否出现工作区产物
  - 是否发生误部署
  - 是否声明完成却无证据

## 4. 能力域划分

首期统一按以下能力域组织：

1. 意图识别
2. 澄清追问
3. 计划与任务拆解
4. 工具选择
5. 执行闭环
6. 修复与重试
7. 边界控制与误调用拦截
8. 多轮连续性

后续新增题目时，只能挂到现有能力域，或先补一份新的能力域说明。

## 5. 题目设计约束

每个题目必须包含：

1. `case_id`
2. `case_version`
3. 能力域
4. 用户输入
5. 前置条件
6. 预期行为
7. 禁止行为
8. 必备证据
9. 评分维度
10. 是否包含硬失败门槛

禁止出现以下不可复用写法：

1. 只写“回答得更像人”
2. 只写“效果更好”
3. 不写证据来源
4. 不写失败判定
5. 把多个能力混成一个无法归因的大题

## 6. 版本管理

### 6.1 题库版本

- `suite_id`：稳定题库编号，例如 `altus-general-v1`
- `suite_version`：题库版本，例如 `1.0.0`

### 6.2 单题版本

- `case_id`：稳定题目编号，例如 `ALTUS-CLARIFY-001`
- `case_version`：题目版本，例如 `1.0.0`

### 6.3 变更规则

- 修正错别字、补充说明但不改变验收口径：仅更新文档，不改 `case_id`
- 改变预期行为或评分逻辑：提升 `case_version`
- 删除旧题或重构大范围题库：提升 `suite_version`

## 7. 使用流程

### 7.1 新增题目

1. 先补 Markdown 文档中的题目定义
2. 同步补 `题库种子/altus_eval_seed_v1.json`
3. 如果评分或存储规则变化，先改对应规范文档

### 7.2 执行评测

1. 固定本次使用的 `suite_id` 与 `suite_version`
2. 记录模型、配置、代码提交、执行环境
3. 输出 run 级别结果与 case 级别结果
4. 存档到统一结果路径

### 7.3 结果复盘

1. 先看硬失败数量
2. 再看能力域均分
3. 最后看单题失败原因与证据链接
