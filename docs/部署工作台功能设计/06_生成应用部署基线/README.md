# 生成应用部署基线设计 [20260415-1005已采用]

## 1. 背景

这组文档用于回答一个具体问题：

- 参照 Manus 已经跑通的“生成应用后直接可部署”的体验，
- 在 OneCEO 里如何形成一套统一、稳定、可复用的生成应用部署基线，
- 让生成出来的网站默认具备：
  - 可部署
  - 可统计
  - 可识别用户
  - 可接数据库
  - 可被平台工作台与 agent 正确识别和管理

本专题已经进入实施阶段，当前文档同时承担设计基线与接入执行索引。

## 2. 结论先行

基于对参考项目 `referance/game-2048` 的拆解，本专题的核心结论是：

1. 要复用 Manus 的“模板化 + 运行时注入 + 平台统计”思路。
2. 不能照搬 Manus 的供应商私有能力。
3. OneCEO 第一阶段必须收敛到一套官方模板，而不是让 agent 每次从零拼栈。
4. 数据库默认应围绕 Railway Postgres，而不是沿用参考项目里的 `mysql2`。
5. 统计能力必须由平台在部署导出阶段强制注入，而不是只做弱提示或让项目自行选择分析 SDK。
6. Railway 资源模型收敛为“每用户固定一个 project，每个生成应用绑定一个独立 environment / service / repo / project token”。
7. 生成链路必须增加“模板合规检查”，否则部署成功率和复用性都会失控。
8. agent 侧改造重点不在“多加提示词”，而在“强制模板、补部署清单、自动注入、部署前校验”。

## 4. 推荐审阅顺序

1. 先看 [01_Manus参考项目拆解.md](./01_Manus参考项目拆解.md)，确认我们从参考项目里到底要学什么、不学什么。
2. 再看 [02_OneCEO默认模板与包选型.md](./02_OneCEO默认模板与包选型.md)，确认官方模板与默认包。
3. 再看 [03_运行时注入_环境变量_统计采集.md](./03_运行时注入_环境变量_统计采集.md)，确认注入方案与埋点采集。
4. 接着看 [04_站点统计_用户统计_数据面板.md](./04_站点统计_用户统计_数据面板.md)，确认工作台要看的数据和后端模型。
5. 再看 [05_Agent_生成链路_部署编排改造.md](./05_Agent_生成链路_部署编排改造.md)，确认 agent 与平台链路怎么改。
6. 再看 [06_稳定性_复用性_验证与灰度.md](./06_稳定性_复用性_验证与灰度.md)，确认上线方式与验收口径。
7. 最后看 [07_第三方能力复用与Umami接入.md](./07_第三方能力复用与Umami接入.md)，确认哪些 Manus 依赖可复用、哪些必须替换，以及 Umami 接入方式。
8. 再结合 [08_私有Umami实例接入与初始化方案_[20260414-1931已采用].md](./08_私有Umami实例接入与初始化方案_[20260414-1931已采用].md)，落地自托管 Umami 的双 team 结构、website 归属、平台账号与注入契约。
9. 执行阶段统一参考 [09_OneCEO私有Umami接入执行计划_[20260415-1005已采用].md](./09_OneCEO私有Umami接入执行计划_[20260415-1005已采用].md)，按顺序推进并在每一步完成后回填状态。
10. 验收、回归和资源回收统一参考 [10_部署链路验收_回归与清理手册_[20260415-1245已采用].md](./10_部署链路验收_回归与清理手册_[20260415-1245已采用].md)。
11. 若要把发布能力收敛成 Altus managed tools，并让 Altus 在部署前自动修复模板不适配问题，参考 [11_Altus部署工具化与自修复发布链路方案_[20260416-1105已采用].md](./11_Altus部署工具化与自修复发布链路方案_%5B20260416-1105%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)。
12. 若要修复“部署成功但 Umami 统计不可用”的主链问题，参考 [12_Umami站点统计不可用修复方案_[20260416-2140已采用].md](./12_Umami站点统计不可用修复方案_%5B20260416-2140%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)，按其中的注入契约、最终域名回写和回归验收要求实施。
13. 若要继续修复“Railway 资源失效导致 deploy 不稳定、部署标签卡无数据、Umami 注入与 agent 执行层状态分叉”的主链问题，统一参考 [13_部署主链稳定性与Railway_Umami_Agent执行层修复方案_[20260417-2327已采用].md](./13_部署主链稳定性与Railway_Umami_Agent执行层修复方案_%5B20260417-2327%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)，按其中的资源修复顺序与验收口径实施。
14. 若要把部署状态改成后台持续同步，并扩展部署基线到 HTML / JS / Node / Python 等多形态项目，统一参考 [14_部署状态后台同步与多形态模板发布支持方案_[20260418-1025已采用].md](./14_部署状态后台同步与多形态模板发布支持方案_%5B20260418-1025%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)。
15. 若要继续消除“后台同步队列仅驻留内存”的最后风险项，把 deployment sync 升级为 DB 持久化 job，统一参考 [15_部署状态持久化同步队列方案_[20260418-1645已采用].md](./15_部署状态持久化同步队列方案_%5B20260418-1645%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)。
16. 若 deploy tool 在 `retryable_repair_required` 与 `public/index.html` 改写之间来回循环，并最终触发 `managed_run_tool_round_limit_exceeded`，统一参考 [16_部署工具模板修复循环终止方案_[20260418-1558已采用].md](./16_部署工具模板修复循环终止方案_%5B20260418-1558%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)。
17. 若要把部署流程封装成平台 skill，并在 deploy / redeploy / rollback / status 请求时自动挂载给 managed run，统一参考 [17_部署编排Skill与自动挂载方案_[20260418-1612已采用].md](./17_部署编排Skill与自动挂载方案_%5B20260418-1612%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)。

20. 若要把 Umami 从基础访问计数扩展为平台运营数据中心，统一参考 [20_Umami深度统计集成方案_[20260424-1434已采用].md](./20_Umami深度统计集成方案_%5B20260424-1434%E5%B7%B2%E9%87%87%E7%94%A8%5D.md)，固定读取 OneCEO 平台自身 website，并与 OneCEO DB 业务事实合并展示。

## 5. 与现有部署工作台文档的关系

- 本专题不替代 `01_发布与访问`、`02_仪表盘`、`03_数据库` 这些已有功能文档。
- 本专题解决的是“这些功能如何在生成应用上天然成立”的底座问题。
- 其中：
  - `01_发布与访问` 会直接依赖这里的模板契约、部署清单和健康检查契约。
  - `02_仪表盘 / 站点数据` 会直接依赖这里的埋点模型与聚合接口。
  - `03_数据库` 会直接依赖这里的默认数据库接入方式与环境变量注入策略。

## 6. 当前建议的审查重点

- 是否同意先收敛到“一套官方模板”而不是多模板并行。
- 是否同意第一阶段把统计能力做成平台注入，而不是每个项目自由接入分析 SDK。
- 是否同意数据库默认围绕 Railway Postgres。
- 是否同意 agent 必须输出 `oneceo.manifest.json` 之类的部署契约文件。
- 是否同意先做“页面与用户统计基线”，把更重的 cohort、漏斗、A/B 试验放到后续阶段。
- 是否同意网站访问统计默认使用 Umami，而不是继续绑定参考项目里的 Manus 私有运行时能力。
- 是否同意生成应用在首次成功部署时由平台自动创建 Umami website，而不是让 agent 在模板里硬编码 websiteId。
- 是否同意将 `analytics.oneceo.ai` 中指定的 `websiteId=6af729e4-2cdb-4a46-9c15-ee7e2fe8438a` 作为平台级统计源，而不是所有用户部署应用共享的 website。
