# 20260328 PPT 多阶段协同技能设计

## 1. 背景

当前项目里的 `PPT 办公` 已经具备以下能力：

- 可以通过任务创建入口触发 PPT 生成
- 可以联动 `web_search / web_extract` 做联网检索
- 可以把最终 `.pptx` 作为交付物下载
- 已经有 `content_archetype / style_pack / slide_type` 等基础约束

但用户反馈仍然很明确：

- 做出来的 PPT 容易千篇一律
- 视觉和排版不够丰富
- 不能根据内容类型自动决定生成路线
- 现在更像“一个长 prompt”，还不是“多个能力协同工作”

因此，本轮目标不是继续堆长 `PPT 办公` 文案，而是把 PPT 生成升级成 **一个主技能统一编排、多个阶段子技能协同执行** 的正式链路。

## 2. 参照项目结论

本轮直接参照 MiniMax `pptx-generator` 设计：

- [MiniMax README](https://github.com/MiniMax-AI/skills/blob/main/README.md)
- [pptx-generator/SKILL.md](https://github.com/MiniMax-AI/skills/blob/main/skills/pptx-generator/SKILL.md)
- [slide-types.md](https://github.com/MiniMax-AI/skills/blob/main/skills/pptx-generator/references/slide-types.md)
- [design-system.md](https://github.com/MiniMax-AI/skills/blob/main/skills/pptx-generator/references/design-system.md)
- [pitfalls.md](https://github.com/MiniMax-AI/skills/blob/main/skills/pptx-generator/references/pitfalls.md)

参照结论如下：

### 2.1 MiniMax 不是靠一个更长的 prompt 做出更好的 PPT

它的主流程是：

1. 研究需求
2. 选配色与字体
3. 选视觉风格
4. 规划逐页结构
5. 逐页生成
6. 编译与 QA

这说明 PPT 质量来自 **阶段化工作流**，而不是“直接写成品”。

### 2.2 它把创意拆成了可执行资产

MiniMax 明确提供了：

- 设计系统：颜色、字体、风格 recipe
- 页面原型库：封面、目录、分隔页、内容页、收尾页
- 内容子类型：text / mixed media / data visualization / comparison / timeline / image showcase
- QA 规则：反同质化、反占位符、反纯文字、反重复版式

这说明它的不千篇一律，核心不是“模型自由发挥”，而是 **设计资产 + 规则约束 + QA 回路**。

### 2.3 对本项目的高精度借鉴方式

本项目当前是 `python-pptx` 路线，不是 MiniMax 的 `PptxGenJS + per-slide JS file` 路线。  
因此本轮不做技术栈照搬，而做 **工作流和设计契约照搬**：

- 照搬“多阶段决策”
- 照搬“slide type library”
- 照搬“design system / palette / style recipe”
- 照搬“QA gate”
- 不照搬 `slides/slide-01.js` 这套生成结构

## 3. 问题结论

当前项目 PPT 产出同质化的根因，不是缺少 Tavily，也不是单纯缺图，而是：

1. `PPT 办公` 仍然是单体 skill brief，没有真正拆成阶段协作
2. prompt 里虽然有 archetype 和 style pack，但还缺正式的阶段输入输出契约
3. 目前没有设计系统资产库，导致风格仍然偏保守和重复
4. 目前没有强约束 QA gate，无法系统性阻止“纯文字页”“重复版式”“整份 deck 一个结构”

因此，本轮必须把 PPT 升级成：

**一个 PPT 主技能 + 多个阶段子技能协同工作**

而不是继续：

**一个 PPT skill + 更长的规则说明**

## 4. 目标

本轮目标：

- 保留用户侧单一入口 `PPT 办公`
- 在内部把 PPT 生成拆成多阶段协同链路
- 让每个阶段都有明确输入、输出和退出条件
- 引入正式的 `slide type` 库、`palette` 库、`style recipe` 库
- 加入 QA gate，直接约束“不能做成一套模板”

本轮完成后，目标效果应为：

- 职业规划、融资路演、培训课件、咨询汇报生成路线明显不同
- 同一主题多次生成时，视觉和版式不会完全相同
- deck 至少具备视觉层次、版式变化和内容驱动的结构差异

## 5. 非目标

本轮不做以下事项：

- 不改 Word / Excel 流程
- 不新增新的连接器
- 不引入浏览器自动化截图生成
- 不改成 MiniMax 的 `PptxGenJS` 技术栈
- 不新增前端复杂多步骤表单
- 不让用户手动选择多个 PPT 子技能

## 6. 设计方案

## 6.1 总体原则

用户看到的仍然是一个入口：

- `PPT 办公`

内部执行改为 6 个阶段子技能协同：

1. `ppt_task_router`
2. `ppt_research_curator`
3. `ppt_storyboard_designer`
4. `ppt_visual_system_designer`
5. `ppt_builder`
6. `ppt_qa_reviewer`

这 6 个子技能不直接暴露给用户，而是由 PPT 主技能统一编排。

## 6.2 阶段子技能定义

### 6.2.1 `ppt_task_router`

职责：

- 判断任务属于新建 / 改写 / 重组材料
- 选择唯一 `contentArchetype`
- 判断 audience / goal / tone / evidenceMode
- 决定是否需要联网检索、图片、图表、案例

输出契约：

- `PptGenerationBrief`

最少字段：

- `artifactType`
- `contentArchetype`
- `audience`
- `goal`
- `tone`
- `structureStrategy`
- `visualGoal`
- `evidenceMode`
- `requiresWebResearch`
- `requiresImages`
- `requiresCharts`

### 6.2.2 `ppt_research_curator`

职责：

- 在需要时执行一次受控检索
- 补充事实、案例、数据、候选图片和来源
- 只保留真正会进入 deck 的材料

约束：

- 默认只做一轮 focused `web_search`
- 默认只做一轮 targeted `web_extract`
- 图片最多选择 3 张
- 不允许无限补材料

输出契约：

- `PptEvidenceBundle`

最少字段：

- `factHighlights`
- `caseHighlights`
- `candidateImages`
- `chartCandidates`
- `sourceUrls`

### 6.2.3 `ppt_storyboard_designer`

职责：

- 先规划 deck，再写正文
- 为每页选择 `pageType`
- 为内容页再选择 `contentSubtype`
- 明确每页结论、视觉元素和内容密度

直接借鉴 MiniMax 的页面分类，但按本项目简化成：

- `cover`
- `toc`
- `section_divider`
- `content`
- `summary`

其中 `content` 再细分为：

- `text_enhanced`
- `mixed_media`
- `data_viz`
- `comparison`
- `timeline_process`
- `image_showcase`

输出契约：

- `PptStoryboard`

最少字段：

- `slides[]`
- 每页包含：
  - `index`
  - `pageType`
  - `contentSubtype`
  - `title`
  - `coreMessage`
  - `visualNeed`
  - `sourceRefs`

### 6.2.4 `ppt_visual_system_designer`

职责：

- 选择 palette、字体、style recipe
- 决定整份 deck 的视觉语言
- 限制 deck 的版式重复度

直接参照 MiniMax `design-system.md`，但本项目第一版收敛成有限库，不开放无限自创：

#### `paletteKey`

第一版限定为：

- `business_authority`
- `vibrant_tech`
- `education_charts`
- `forest_eco`
- `luxury_mysterious`
- `platinum_white_gold`

#### `styleRecipe`

第一版限定为：

- `sharp`
- `soft`
- `rounded`
- `pill`

#### `fontPairing`

第一版限定为：

- `yahei_arial`
- `yahei_calibri`
- `yahei_cambria`

输出契约：

- `PptVisualSystem`

最少字段：

- `paletteKey`
- `styleRecipe`
- `fontPairing`
- `titleScale`
- `bodyScale`
- `spacingScale`
- `pageBadgeStyle`

### 6.2.5 `ppt_builder`

职责：

- 按 `PptGenerationBrief + PptStoryboard + PptVisualSystem + PptEvidenceBundle` 生成 `.pptx`
- 下载需要的图片到 workspace
- 写入 speaker notes 或附录来源

实现约束：

- 仍使用当前项目已验证过的 `python-pptx`
- 不再直接从用户 prompt 临场拼 deck
- 先把阶段产物确定，再生成最终文件

为了让 QA 更稳定，`ppt_builder` 必须额外输出：

- `presentation_manifest.json`

其中记录：

- slide 数量
- 每页 `pageType`
- 每页 `contentSubtype`
- 是否使用图片 / 图表
- 是否保留来源
- palette / style recipe

这样后续 QA 不需要只靠肉眼和文件存在判断。

### 6.2.6 `ppt_qa_reviewer`

职责：

- 验证 deck 不同质化
- 验证最小视觉要求
- 验证来源保留
- 验证最终交付路径

第一版 QA gate 强制检查：

1. 存在最终 `.pptx`
2. 至少 1 页 `cover`
3. 至少 1 页 `summary`
4. 至少 2 页非纯文字内容页
5. 至少 2 种不同 `contentSubtype`
6. 不允许连续 3 页使用同一种布局
7. 如果使用外部资料，必须保留 `sourceUrls`
8. 不允许占位词、明显空页和纯模板标题

只有 QA 通过，才允许 `complete_task.attachments` 完成。

## 6.3 协同顺序

PPT 主技能内部执行顺序固定为：

1. `ppt_task_router`
2. `ppt_research_curator`
3. `ppt_storyboard_designer`
4. `ppt_visual_system_designer`
5. `ppt_builder`
6. `ppt_qa_reviewer`

这条链路是强约束，不允许跳步直接生成最终文件。

## 6.4 反同质化规则

本轮需要直接把以下规则写进 prompt 和 QA，而不是停留在“建议”层：

- 不允许整份 deck 主要由“标题 + 三条 bullet”组成
- 不允许全是纯文本页
- 不允许相邻内容页连续复用同一版式
- 不允许默认蓝白商务模板作为所有主题的通用风格
- 不允许把职业规划、路演、培训、方案建议写成同一结构
- 不允许标题下加一条装饰横线冒充设计感

这些规则直接参照 MiniMax `pitfalls.md` 的思路，但改造成适合本项目的交付 gate。

## 8. 实现路径

最短正确路径如下：

1. 抽出 PPT 阶段定义、archetype、pageType、contentSubtype、palette、styleRecipe 常量
2. 重写 `PPT 办公` skill brief，使其显式要求按 6 阶段推进
3. 重写 Altus PPT prompt，使其遵守固定协同顺序与输出契约
4. 增加 PPT QA gate 规则
5. 用 3 条 smoke 验证不同 archetype 的差异化

## 9. 验证方式

至少验证以下 3 条：

1. `职业规划 PPT`
   - 目标 archetype：`roadmap_plan`
   - 重点看时间轴、阶段目标、成长路径

2. `商业路演 PPT`
   - 目标 archetype：`pitch_deck`
   - 重点看机会、方案、优势、增长与 CTA

3. `内部培训 PPT`
   - 目标 archetype：`training_material`
   - 重点看知识点、流程步骤、案例和复盘

验证项：

- 三条任务不能生成相同结构
- palette / style recipe 至少有明显差异
- slide type 组合明显不同
- 不再退化成整份文字页
- 最终 `.pptx` 可以下载

## 10. 风险与取舍

### 10.1 为什么不直接拆成多个独立用户可选 skills

因为那会导致：

- 用户学习成本变高
- 风格容易冲突
- 调度轮次变长
- 结果更不稳定

因此正确做法不是“用户手动选多个 skills”，而是：

**一个 PPT 主技能，内部多个阶段子技能协同**

### 10.2 为什么不直接照抄 MiniMax 的技术实现

因为本项目当前已经围绕 `python-pptx + managed run + deliverable pipeline` 形成闭环。  
本轮最短正确路径是借鉴 MiniMax 的 **工作流与资产设计**，而不是重做底层生成技术栈。
