# 01 现状差异、目标与范围

## 1. 背景

`oneceo` 当前已经有“添加附件”入口，但仍缺少一套完整的一致性处理链路。

当前用户附件的核心流程是：

1. 前端把文件保存在浏览器态。
2. 发送前先确保 session 存在。
3. 调 `/api/task-creation/sessions/:sessionId/attachments` 单文件上传。
4. 文件写入 Sandbox 的隐藏目录 `.attachments/`。
5. 再把路径以自然语言形式拼进 prompt。

当前代码位置：

- `apps/web/client/src/components/AttachmentPickerButton.tsx`
- `apps/web/client/src/lib/task-attachments.ts`
- `apps/web/client/src/components/TaskCreationChat.tsx`
- `apps/web/client/src/pages/Home.tsx`
- `apps/web/client/src/lib/task-creation-client.ts`
- `apps/api/src/routes/task-creation-routes.ts`

其中关键现状：

- 前端入口已支持本地文件、远程链接、技能模板。
- 前端发送时仍调用 `appendAttachmentsToPrompt(...)`，把附件路径追加到自然语言文本中。
- 服务端上传接口只负责写文件，不负责解析文件内容，不负责生成标准消息协议。
- Sandbox 落点是 `.attachments/`，不是用户/Agent 都可直观理解的工作区上传目录。

## 2. Suna 参照结论

`suna` 的附件能力是完整协议，而不是单独的上传能力。

参照代码位置：

- 前端输入与文件状态
  - `referance/suna/apps/frontend/src/components/thread/chat-input/chat-input.tsx`
  - `referance/suna/apps/frontend/src/components/thread/chat-input/file-upload-handler.tsx`
- 新线程/首条消息启动
  - `referance/suna/apps/frontend/src/components/thread/ThreadComponent.tsx`
  - `referance/suna/apps/frontend/src/hooks/dashboard/use-agent-start-input.ts`
- 启动接口与服务端解析
  - `referance/suna/apps/frontend/src/lib/api/agents.ts`
  - `referance/suna/backend/core/agents/api.py`
  - `referance/suna/backend/core/files/upload_handler.py`
- Sandbox 上传与命名
  - `referance/suna/backend/core/sandbox/api.py`
  - `referance/suna/backend/core/utils/sandbox_utils.py`
- 消息渲染与附件展示
  - `referance/suna/apps/frontend/src/components/thread/content/ThreadContent.tsx`
- Agent 使用附件内容
  - `referance/suna/backend/core/agents/runner/prompt_manager.py`

`suna` 的核心做法：

1. 附件属于“消息输入协议”的一部分。
2. 发送时不只是上传文件，还会把附件引用写入消息内容。
3. 服务端会快速解析可读文件内容，供 Agent prompt 使用。
4. 文件统一落到当前 session 的 `workspaceRoot/uploads/`。
5. 重名文件自动改名，不覆盖已有文件。
6. 前端有清晰的 `pending / uploading / ready / error` 状态。

## 3. oneceo 当前问题

相对于 `suna`，`oneceo` 当前缺失以下能力：

### 3.1 消息协议缺失

当前只是在 prompt 中追加：

- “已添加以下附件，可直接在工作区中访问”

这不是标准协议，导致：

- 前端渲染依赖消息元数据而不是统一消息内容格式
- Agent 只能依赖自然语言描述，不利于稳定识别
- 后续多轮消息、引用追踪、删除规则不清晰

### 3.2 服务端解析能力缺失

当前上传接口只写文件，不做：

- 文件名规范化
- 文本类附件内容解析
- 解析结果注入 prompt
- 附件引用标准化

### 3.3 Sandbox 落点不合理

当前写入 `.attachments/`，这会带来两个问题：

- 用户与 Agent 心智不一致，不像工作区可见文件
- 与 `suna` 的 `/workspace/uploads` 使用方式不一致

### 3.4 输入态体验不完整

当前未形成完整输入态附件模型，缺少或不统一：

- 拖拽添加
- 粘贴图片
- 上传中状态
- 错误状态
- 可解析压缩包处理
- 本地预览 URL 生命周期

### 3.5 Agent 使用链路不完整

当前 Agent 能拿到的主要是“附件路径提示”，而不是：

- 明确的附件引用块
- 文本类附件摘录
- 系统化文件上下文

## 4. 本次设计目标

本次文档定义的目标是：为 `oneceo` 建立一套与 `suna` 对齐的完整附件能力。

### 4.1 目标结果

用户在 `oneceo` 中添加附件后，应具备以下行为：

1. 输入框能够统一处理本地、拖拽、粘贴、远程链接、技能模板等附件来源。
2. 前端有明确的附件状态机和预览状态。
3. 服务端在“发送消息”时统一接收 `content + files[]`。
4. 服务端负责：
   - 文件名规范化
   - 可读文件内容快速解析
   - Sandbox 上传
   - 标准附件引用写入消息
5. 文件统一落到当前 session 的 `workspaceRoot/uploads/`。
6. Agent 既能看到附件引用，也能获得文本类附件的解析内容。
7. 会话历史中，附件是稳定可展示、可追踪、可复用的。

### 4.2 非目标

本次不做：

- 对所有历史消息做自动迁移补写
- 管理后台上传能力统一化
- Sandbox 内图片 OCR / PDF 深度结构化解析
- 大文件对象存储体系

## 5. 本次设计边界判断

为了避免范围漂移，本次设计只面向“会话输入附件”。

包括：

- 新任务首页输入框
- 任务创建对话页输入框
- managed run 的消息发送链路
- Agent 对附件的消费与使用

不包括：

- 任务交付物产出的附件规范
- 外部知识库导入
- 部署模块的文件存储功能

## 6. 关键结构性决策

1. 不再把附件视为“普通提示词补充文本”，而是视为“消息协议的一部分”。
2. 不再以 `.attachments/` 作为默认落点，统一改为“当前 session workspaceRoot 下的 `uploads/` 目录”。
3. 不再由前端负责把附件路径拼成自然语言说明，改为后端生成标准附件引用。
4. 文本类附件的内容解析由服务端完成，并通过 prompt assembly 注入 Agent。
5. managed mode 的用户输入主入口要支持 `multipart/form-data` 的 `content + files[]`，并允许在没有现成 sessionId 时一次性完成“创建 session + 提交输入 + 启动 run”。
6. 文本类附件的解析结果不能只存在请求内存中，必须有可供 prompt assembly 在重试、恢复、再次执行时稳定读取的持久来源。
