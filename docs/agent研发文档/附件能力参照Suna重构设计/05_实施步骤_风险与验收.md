## 2. 明确不采用的方案

### 2.1 不继续沿用 `.attachments`

原因：

- 与 `suna` 不一致
- 用户和 Agent 心智差
- 会持续制造隐藏目录语义

### 2.2 不继续沿用“前端先上传、再拼 prompt”

原因：

- 输入协议分裂
- 失败处理复杂
- Agent 看到的是自然语言说明而不是标准附件协议

### 2.3 不做兼容性双主链路长期并存

原因：

- 这会让后续消息处理、UI 展示、Prompt assembly 永远存在双套规则
- 与仓库对“不要补丁式方案”的要求冲突

## 3. 主要风险

### 3.1 风险：Hook 改造范围较大

原因：

- `useTaskCreationAgent.ts` 目前承担了较多职责

控制方式：

- 将附件输入提交逻辑集中到一个新的 client API 和 dispatch service
- 不把附件处理散落在多个组件里

### 3.2 风险：Prompt 注入过长

原因：

- 文本类附件可能很大

控制方式：

- 单文件解析内容截断
- 只注入可读摘要，不注入全量原文

### 3.3 风险：文件名冲突与引用不一致

原因：

- 用户可能多次上传同名文件

控制方式：

- 以服务端最终写入路径为准
- canonical 引用块永远写实际路径

### 3.4 风险：发送失败后前端状态不一致

原因：

- 附件上传与消息持久化属于一组复合动作

控制方式：

- 由统一输入接口返回结果
- 前端只根据接口结果统一切换状态

### 3.5 风险：首条消息无 session 时出现双入口竞争

原因：

- 当前前端先 `createTaskCreationSession(...)` 再 `startTaskCreationManagedRun(...)`
- 如果新增附件输入接口但不收敛入口，会同时存在两套 run 启动主链路

控制方式：

- 统一由 `POST /api/altus-managed/inputs` 作为 managed 用户输入唯一入口

### 3.6 风险：附件解析结果只存在请求期内存，导致恢复时丢失

原因：

- prompt assembly 在 run 重试、刷新、再次执行时需要稳定来源

控制方式：

- 把截断后的 `attachmentContext` 持久化进 `user_input.metadata`
- prompt service 只从消息存储读取，不依赖请求期对象

### 3.7 风险：图片外链与内部归档共用桶，导致敏感对象进入外部可达面

原因：

- 当前仓库已有 R2 client 默认面向 archive bucket
- 如果直接复用同一个桶做签名 URL，边界会被破坏

控制方式：

- 必须单独图片桶、单独凭证、单独 service
- 图片签名服务只接受 `managed-images/` 命名空间下的 key
- 归档桶代码和图片桶代码在实现层分离，不共用 bucket name

### 3.8 风险：签名 URL 长期有效，导致图片外链泄露窗口过长

原因：

- 图片 URL 会被发给外部模型服务

控制方式：

- 使用短时签名 URL
- 默认 TTL 控制在 5 分钟量级
- 每轮模型调用前现签，不缓存旧签名 URL

## 4. 验收场景

### 4.1 本地文件

1. 添加 `md / pdf / png / ts` 等允许类型文件。
2. 发送后消息卡片显示附件。
3. Sandbox 中能在当前 session 的 `${workspaceRoot}/uploads` 看到实际文件。

### 4.2 重名文件

1. 连续上传两次同名文件。
2. 第二次不覆盖第一次。
3. 消息中显示实际重命名后的路径。

### 4.3 远程链接导入

1. 通过网站 / Google Drive / OneDrive 导入公开文件。
2. 导入后与本地文件走同一套发送链路。

### 4.4 粘贴图片

1. 从剪贴板粘贴图片到输入框。
2. 图片作为待发送附件出现。
3. 发送后消息正确展示附件。
4. 消息 metadata 中持久化的是 object key，而不是签名 URL。

### 4.5 文本类附件上下文

1. 上传 Markdown/代码文件。
2. Agent 在第一轮执行中能够理解文件内容，而不是只看到路径。

### 4.6 失败场景

1. 文件超限。
2. 格式不支持。
3. 上传过程中断。
4. 前端能明确展示失败，不出现“消息已发出但附件丢失”的假成功。

### 4.7 安全隔离场景

1. 图片桶签名接口只能为图片桶对象签名。
2. archive bucket 中的 `sessions/.../workspace.tar.gz` 不能通过任何图片 URL 生成逻辑访问。
3. 删除或失效签名后，外部 URL 不再可读。
4. 即使拿到图片桶 AK/SK，也无法访问 archive bucket。

## 5. 最终验收定义

满足以下条件才算本次附件能力设计落地完成：

1. 用户输入附件已成为统一消息协议的一部分。
2. 文件统一落到当前 session 的 `${workspaceRoot}/uploads`。
3. managed run 能消费文本类附件内容。
4. 前端存在清晰可见的附件状态机。
5. 远程导入、本地选择、拖拽、粘贴至少四类输入方式能够统一工作。
6. 不再依赖“自然语言附件列表拼 prompt”的旧方案。
7. 图片通过图片外链专用 R2 桶和短时签名 URL 提供给模型。
8. 内部归档 R2 桶与图片外链桶严格隔离，不能交叉访问。
