# 当前 Agent 状态机自省反馈

日期：2026-03-02

## 结论概览
当前状态机存在**分层状态驱动不一致**与**时序触发点分散**的问题，可能导致在错误阶段触发不匹配的功能（如过早测试、重复修复、错误澄清），进而出现执行时序混乱。

---

## 主要不合理点与风险

### 1) Stage 与 Phase 双状态并行但缺少硬性同步
- **现象**：`TaskCreationService` 控制 `stage`，`OpencodeRemoteService` 控制 `phase`，两者分布在不同服务中，彼此只通过消息/存储间接同步。
- **风险**：出现 `stage=executing` 但 `phase=analysis/testing` 的组合，从而触发不该发生的测试/修复动作。
- **表现**：在实际运行中可能出现“开发还未产出但已进入测试”、“测试失败后又触发开发提示”等混乱行为。

### 2) 关键状态切换触发点过于依赖事件回放
- **现象**：`OpencodeRemoteService` 依据 OpenCode 事件流决定 phase 转移，例如 `session.diff` / `file.edited` / `message.final`。
- **风险**：若事件丢失或出现在异常顺序，容易造成“误判已产出 → 进入测试”或“未产出 → 阻断测试”。
- **表现**：出现“未生成交付物却进入测试阶段”或“已生成交付物却卡在开发阶段”的错位。

### 3) 审查（Review Gate）耦合 phase 跳转
- **现象**：测试阶段结束后由 Review Gate 决定进入修复/交付。
- **风险**：当 Review Gate 输入来自不完整产物或错误上下文时，可能多轮进入修复或反复测试。
- **表现**：出现“修复阶段重复触发，且未解决真实问题”的循环。

### 4) 执行模式差异（command vs opencode_remote）未完全收敛
- **现象**：`TaskCreationService` 有两种执行模式，但状态机设计更倾向 `opencode_remote`。
- **风险**：在 `command` 模式下可能出现跳过测试或测试触发时机不一致。
- **表现**：某些任务完成后未进入测试，或测试只在 remote 模式触发。

### 5) 恢复与重入逻辑可能打乱阶段
- **现象**：`resumeTask` 可能重新生成计划或重新触发执行，而阶段信息仅依赖 DB / file-memory-store。
- **风险**：恢复后阶段跳回 planning 或 development，但实际已在 testing/reviewing 阶段。
- **表现**：恢复时触发重复启动环境或错误的执行提示。

---

## 可能造成“时序混乱执行错误功能”的场景

1. **过早测试**：
   OpenCode 事件误判产出 → phase 跳转到 `testing` → 自动触发 Playwright 测试，但实际尚未完成开发。

2. **修复循环**：
   Review Gate 基于空输出判定失败 → 进入 `repair` → 再次触发测试 → 无限循环。

3. **阶段错乱提示**：
   `TaskCreationService` 仍在 `planning`，`OpencodeRemoteService` 已广播 `testing` 状态，用户看到的阶段提示不一致。

4. **恢复后误触发**：
   resume 时重新发起开发/测试，导致多次重复启动 sandbox / neko。

---

## 初步改进方向（仅记录想法）

1. **统一状态源**：
   将 `stage` 与 `phase` 合并为统一状态机（单一源），或通过“强同步规则”保证一致。

2. **明确状态跃迁条件**：
   例如：只有当“产物存在 + 执行完成 + review ready”才允许进入 testing。

3. **事件驱动增加校验**：
   对 OpenCode 事件加入幂等与上下文校验，避免误触发。

4. **恢复逻辑加入状态锁**：
   resume 时必须检查当前 phase，再决定是否允许回退。

---

## 结语
现有状态机能跑通流程，但在高并发 / 异常事件顺序下易产生阶段混乱。下一步需要根据真实场景补充“强约束状态迁移条件”，否则会频繁出现“错误阶段执行错误功能”的情况。
