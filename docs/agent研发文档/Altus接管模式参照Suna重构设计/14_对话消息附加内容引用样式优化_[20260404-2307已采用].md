# 14 对话消息附加内容引用样式优化 [20260404-2307已采用]

日期：2026-04-04

关联事项：

- GitHub Issue `#26`

## 1. 背景

当前任务对话中，用户发送消息时可以附加两类能力：

1. 文件附件
2. Skills

发送链路已经把这些附加内容写进消息 `metadata`，但消息渲染层仍存在两个明显问题：

1. 只对 `metadata.attachments` 做了展示，`metadata.skills` 没有在消息卡片中稳定呈现。
2. 已展示的附件仍然只是“贴在消息正文后面的一排 chip”，没有明确表达“这些内容是附加在这条消息上的引用项”。

结果是：

1. 用户无法快速判断某条消息是否携带了 skill / 附件。
2. 同一条消息的正文与附加能力之间缺少结构层级。
3. 当消息正文较短或为空占位文案时，附加内容归属感更弱。

## 2. 当前实现与问题定位

当前发送侧：

- `apps/web/client/src/components/TaskCreationChat.tsx`
  - 会把 `selectedSkills` 写入 `metadata.skills`
  - 会把上传后的文件写入 `metadata.attachments`
  - 会补充 `metadata.originalInput`

当前渲染侧：

- `apps/web/client/src/components/TaskCreationChat.tsx`
  - `MessageCard` 只读取 `message.metadata.attachments`
  - `MessageCard` 不读取 `message.metadata.skills`
- `apps/web/client/src/components/AttachmentChipList.tsx`
  - 已具备文件 / skill 两种 chip 视觉基础
  - 但当前主要用于输入区或简单横向列举，不具备“消息引用块”语义

结论：

这不是数据缺失问题，而是消息层 UI 语义缺失问题。最短路径应当直接重构消息卡片中的“附加内容展示层”，而不是补丁式继续往正文后堆 chip。

## 3. 本次目标

将对话消息中的附加内容重构为轻量“上下文标记 + 文件条”。

目标效果：

1. 用户一眼能看出“这条消息附加了什么”。
2. `Skills` 与连接器引用进入用户消息气泡内部，用彩色文字显示，不再额外生成大引用框。
3. 文件附件显示在用户消息气泡下方，以文件条形式展示，不放进深色气泡内部。
4. 同一条消息同时存在多种附加内容时，结构清晰，不与正文混排。
5. 只改消息展示层，不改发送协议、不改历史消息存储结构、不引入兼容分支。

## 4. 非目标

本轮不做以下事项：

1. 不调整附件上传协议。
2. 不改 `metadata` 的持久化结构。
3. 不新增全局附件面板或独立消息详情页。
4. 不改输入区 `AttachmentChipList` 的交互模式。
5. 不扩大到 direct / managed 以外的其它页面。

## 5. 目标交互与视觉结构

每条存在附加内容的用户消息按两层展示：

1. 气泡内部
   - `Skills` 使用绿色系彩色文字展示。
   - 连接器 / MCP 引用使用蓝色系彩色文字展示。
   - 不再显示 `已附加`、数量、分组边框或独立引用卡片。
2. 气泡下方
   - 文件附件以独立文件条展示。
   - 2 个以内直接展示文件。
   - 超过 2 个时，前 2 个直接展示，第三个位置展示 `+X`。
   - 鼠标 hover 到 `+X` 时显示三点图标，点击后可查看剩余文件。

建议视觉原则：

1. Skills / 连接器是消息语义的一部分，应轻量进入气泡。
2. 文件是独立对象，应位于气泡外侧，避免撑大用户消息。
3. 多文件场景默认收敛，避免短消息下面出现过长附件瀑布。
4. 历史消息与实时消息使用同一套展示，不引入兼容分支。

## 6. 数据口径

消息展示只依赖现有 `message.metadata`：

1. `metadata.skills`
2. `metadata.attachments`
3. `metadata.mcpReferences`
4. `metadata.originalInput`

数据约束：

1. `skills` 直接按现有 `TaskCreationPlatformSkill` 的快照信息渲染。
2. `attachments` 直接按现有 `TaskCreationUploadedAttachment` 渲染。
3. `mcpReferences` 直接按现有 `TaskCreationMcpReference` 渲染。
4. 不额外请求详情接口。
5. history replay 与实时消息统一走同一解析函数。

## 7. 组件拆分建议

最短路径建议将消息专用引用组件拆成两个只读部件，而不是继续复用输入区 attachment list 作为主容器。

建议拆分：

1. `TaskCreationChat.tsx`
   - `MessageCard` 内新增对 `metadata.skills` 的读取
   - `MessageCard` 内统一组装引用数据
2. 消息引用组件
   - 建议文件：`apps/web/client/src/components/MessageAttachmentReference.tsx`
   - 责任：渲染气泡内 `MessageInlineReferences` 与气泡下方 `MessageAttachmentFiles`
3. `AttachmentChipList.tsx`
   - 保持输入区现有职责
   - 若复用其单项 chip 样式，只抽取底层 item renderer，不让它继续承担“消息引用块容器”职责

原因：

1. 输入区 attachment list 的横向拖动和移除按钮语义不适合消息历史区。
2. 消息区需要只读引用语义和文件折叠查看，职责已经不同。
3. 独立组件更容易覆盖测试与后续扩展。

## 8. 具体展示规则

### 8.1 仅附加 Skills

1. 在用户消息气泡内显示 `Skills` 标签与 skill 名称
2. skill 名称使用绿色系彩色文字
3. 不显示独立引用块、revision 信息或数量头部

### 8.2 仅附加附件

1. 在用户消息气泡下方显示文件条
2. 每个文件条显示：
   - 文件名
   - 文件大小
   - 文件图标
3. 2 个以内直接显示，超过 2 个时收敛为 `+X` 查看更多

### 8.3 同时附加 Skills 与附件

1. Skills 留在气泡内部
2. 文件附件留在气泡下方
3. 不出现额外大引用框

### 8.4 正文为空占位文案

当正文是“已添加附件”这类占位输入时，不允许让附加内容看起来像唯一内容来源。

要求：

1. 占位文案继续保留在正文区。
2. Skills / 连接器仍在气泡内独立成行展示。
3. 文件仍在气泡下方展示。

### 8.5 连接器 / MCP 引用

1. 连接器引用和 Skills 一样进入用户消息气泡内部。
2. 连接器名称使用蓝色系彩色文字。
3. 不额外生成独立聊天框或引用卡片。

### 8.6 消息区文件展示

消息区文件附件放在用户消息气泡下方，不进入气泡内部。展示形态从细长 pill 收敛为固定高度、略偏横向的简洁文件块。

展示规则：

1. 单个文件块保持稳定高度，宽度略长，用于承载文件名，但不拉成长条。
2. 文件块内部只展示文件图标、文件名与大小，扩展名不再单独做醒目徽标。
3. 最多直接展示 2 个文件。
4. 第 3 个位置用于 `+X` 聚合入口，但它使用更小的紧凑按钮，不占用完整文件块面积。
5. 鼠标移入 `+X` 时显示更多操作的点状图标，点击后打开页面居中的文件清单浮窗。
6. 文件清单浮窗展示当前消息的全部文件，只做清单确认，不提供预览或下载入口。

消息区文件条不提供点击预览能力。

原因：

1. 已上传文件当前落在 session sandbox workspace。
2. 如果消息区点击预览再回读 sandbox，会拉长链路并放大图片、PDF 等大文件的等待时间。
3. 对用户而言，消息区附件最重要的是确认“这条消息带了哪些文件”，不是在历史消息中重新打开文件。

约束：

1. 文件条只做只读展示，不发起 workspace file/raw file 请求。
2. `+X` 只用于展开剩余文件列表，不承担预览或下载入口。
3. 不改变上传协议、不改变消息 metadata、不改变 sandbox 文件路径。

### 8.7 输入区待上传文件展示

输入区附件展示从正文下方的 pill 列表调整为正文上方的紧凑预览区。

展示规则：

1. 图片文件在输入区左上方显示 64px 缩略图。
2. 非图片文件使用文件图标与扩展名占位，不拉长输入框。
3. 选择文件后立即开始预上传，正在上传的文件保持在输入区内，显示暗态、轻微缩放和 spinner。
4. 上传成功后附件恢复正常颜色，发送时直接复用已上传记录。
5. 消息发送成功后清空输入区附件，并在消息气泡下方展示文件条。
6. 上传失败时保留附件选择，允许用户重试或删除。

## 9. 测试与验收

至少补齐以下前端验证：

1. 仅 skill 消息能在气泡内显示彩色 skill 文本
2. 仅附件消息能在气泡下方显示文件条
3. 同时存在 skill 与附件时，skill 在气泡内、文件在气泡下
4. 超过 2 个附件时出现 `+X` 更多文件入口
5. 连接器引用能在气泡内显示彩色连接器文本
6. 不带附加内容的消息，不显示引用标记
7. history 恢复后的消息与实时发送后的消息表现一致

建议新增测试方向：

1. `TaskCreationChat` 消息渲染单测
2. `managed-session-resolution` 之外，补消息 metadata 渲染测试

## 10. 实施顺序

1. 调整消息级引用组件，拆出气泡内标记与气泡下方文件条
2. 在消息解析层补齐 `skills + attachments + mcpReferences`
3. 用统一样式替换当前“气泡内大引用块”的展示
4. 补齐渲染测试
5. 本地执行最小前端校验

## 11. 风险与约束

风险点只有两个：

1. 现有历史消息中 `metadata.skills` 结构可能存在少量不完整数据
2. 输入区复用组件若抽取不当，容易把“可移除 chip”交互误带入消息区

处理原则：

1. 消息区只做只读展示，不出现 remove 行为。
2. 对 `skills / attachments` 做最小字段守卫，字段不全就跳过当前项，不新增兼容兜底分支。

## 12. 采用后拟修改文件

- `apps/web/client/src/components/TaskCreationChat.tsx`
- `apps/web/client/src/components/AttachmentChipList.tsx`
- `apps/web/client/src/components/MessageAttachmentReference.tsx`
- `apps/web/client/src/tests/*` 中对应消息渲染测试文件

## 13. 结论

本事项的本质不是“把附件样式做得更好看”，而是：

1. 让消息与附加能力之间形成稳定的引用关系表达
2. 把 `skills` 与附件从“零散元数据”提升为消息级可识别结构
3. 用最短路径完成现有对话体验中的信息归属修复
