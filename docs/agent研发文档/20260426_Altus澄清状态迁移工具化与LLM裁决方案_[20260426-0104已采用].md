# 20260426 Altus 澄清状态迁移工具化与 LLM 裁决方案 [20260426-0104已采用]

## 1. 背景

当前 Altus managed 已有执行前澄清能力，主链路参考：

1. [20260423_Altus任务复杂度判定与结构化澄清优化方案_[20260423-1751已采用].md](/Users/watson/codingProj/oneceo/docs/agent研发文档/20260423_Altus任务复杂度判定与结构化澄清优化方案_[20260423-1751已采用].md)
2. [20260406_Altus澄清问题重复发送修复方案_[20260406-1931已采用].md](/Users/watson/codingProj/oneceo/docs/agent研发文档/20260406_Altus澄清问题重复发送修复方案_[20260406-1931已采用].md)

真实问题是：

1. 用户说“帮我想想，我想做个用户管理系统，应该怎么做”；
2. Altus 进入“需要补充信息”，询问交付物类型；
3. 用户说“先帮我想想就行 / 方案 / 交付方案”；
4. Altus 继续重复补充信息；
5. 用户回答“网页应用”后，又继续追问技术栈。

此前尝试用规则/关键词补丁识别“方案”“你推荐”“网页应用”等表达。这个方向不够合理，因为用户自然语言表达无法靠平台硬编码覆盖，后续仍会不断漏判。

本方案改为：

> LLM 负责理解用户回复并提出状态迁移；后端只负责校验状态迁移是否合法、是否越过平台底线、是否存在外部副作用。

## 2. 核心原则

### 2.1 LLM 做语义裁决

用户回复属于以下哪一种，不再由后端关键词判断：

1. 已经回答上一轮澄清；
2. 把选择权委托给 Agent；
3. 切换为“先咨询 / 先给方案 / 先想想”；
4. 换了一个新问题；
5. 仍然没回答；
6. 请求继续执行。

这些属于“人话理解”，应交给 LLM。

### 2.2 后端不做语义理解

后端不应再通过大量规则判断：

1. “方案”是不是 advisory；
2. “你推荐”是不是委托；
3. “网页应用”是不是回答了 artifact type；
4. “帮我查查”是不是新任务。

这些判断会形成没有泛化能力的关键词系统。

### 2.3 后端只做状态迁移守卫

后端守卫只处理稳定、不依赖表达方式的约束：

1. 当前状态是否允许切到目标状态；
2. 这个迁移是否会清理未解决的 pending clarification；
3. 是否涉及外部副作用；
4. 是否需要显式确认；
5. 是否缺少授权、凭证或绑定；
6. 是否属于旧 pending 污染新 turn；
7. 是否违反平台能力元数据声明。

这不是“规则理解用户”，而是“状态机不允许进入非法或危险状态”。

## 3. 设计目标

### 3.1 产品目标

1. 让 Altus 在补充信息阶段像人一样理解用户回复；
2. 用户说“你推荐 / 按你想法 / 先给方案 / 先别写代码”时，Altus 能自然衔接；
3. 避免重复追问同一个问题；
4. 避免把咨询型请求误判成执行型任务；
5. 风险动作仍然可靠阻断，不能因为 LLM 判断而直接越权。

### 3.2 技术目标

1. 把补充信息回复处理从“规则分类”升级为“LLM tool transition proposal”；
2. 所有状态变化都通过结构化工具表达，不解析自然语言输出；
3. 后端 reducer 只接受工具事件，不接受模型自由文本直接改状态；
4. policy guard 基于 capability metadata 和状态机约束，不基于关键词；
5. 保持现有 `clarification_request` 前端协议不变。

## 4. 非目标

1. 不允许 LLM 直接写 `pendingClarificationType`、session stage 或 run status；
2. 不让后端硬编码大规模语义关键词；
3. 不重写 Altus managed runner；
4. 不改变前端消息渲染协议；
5. 不引入多问题采访式需求收集；
6. 不让 LLM 绕过部署、删除、授权、支付等风险确认。

## 5. 总体架构

当前问题应拆成三层：

```text
用户回复
  -> Clarification Transition Agent（LLM 语义裁决）
  -> Transition Tool Call（结构化迁移提议）
  -> Clarification Policy Reducer（状态迁移守卫）
  -> taskIntentProfile / clarification_request / continue
```

职责边界：

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| LLM transition agent | 理解用户自然语言，选择迁移工具 | 直接改状态、绕过权限 |
| transition tool schema | 把意图变成结构化事件 | 做最终安全判断 |
| policy reducer | 校验迁移是否合法、安全、可执行 | 理解用户表达含义 |
| coordinator/run entry | 根据 reducer 结果继续、澄清或切换模式 | 自己重新解释用户语义 |

## 6. 状态模型

### 6.1 ClarificationState

建议内部表达：

```ts
type ClarificationState = {
  status:
    | 'none'
    | 'clarifying'
    | 'advisory'
    | 'ready_to_execute'
    | 'risk_confirmation'
    | 'new_turn';
  pendingClarificationType?: TaskClarificationType;
  pendingQuestion?: string;
  pendingOptions?: string[];
  turnId: string;
};
```

第一阶段不需要新增数据库字段，可以从现有文件记忆和会话历史组装：

1. `pendingClarificationType`
2. `pendingQuestion`
3. `pendingOptions`
4. 最新用户输入
5. 最近历史消息

### 6.2 TransitionAction

LLM 不返回自由文本判断，而是调用工具提出以下迁移：

```ts
type ClarificationTransitionAction =
  | 'answer_clarification'
  | 'delegate_to_agent_default'
  | 'switch_to_advisory_mode'
  | 'restart_as_new_turn'
  | 'request_followup_clarification'
  | 'request_risk_confirmation'
  | 'continue_execution';
```

## 7. LLM 可调用工具设计

### 7.1 `answer_clarification`

用于用户已经回答上一轮补充信息。

```ts
answer_clarification({
  clarificationType: 'artifact_type' | 'tech_stack' | 'scope_boundary' | 'integration_target' | 'acceptance_requirement',
  answer: string,
  confidence: 'low' | 'medium' | 'high',
  rationale: string
})
```

例子：

```text
用户：网页应用
```

LLM 调用：

```json
{
  "clarificationType": "artifact_type",
  "answer": "网页应用",
  "confidence": "high",
  "rationale": "用户直接选择了交付物类型"
}
```

### 7.2 `delegate_to_agent_default`

用于用户把选择权交给 Agent。

```ts
delegate_to_agent_default({
  clarificationType: TaskClarificationType,
  assumedDefault: string,
  confidence: 'low' | 'medium' | 'high',
  rationale: string
})
```

例子：

```text
用户：你推荐就行
```

LLM 调用：

```json
{
  "clarificationType": "tech_stack",
  "assumedDefault": "按当前仓库或平台默认技术栈继续",
  "confidence": "high",
  "rationale": "用户明确把技术选型委托给 Agent"
}
```

### 7.3 `switch_to_advisory_mode`

用于用户不想马上执行，而是先咨询、先规划、先听方案。

```ts
switch_to_advisory_mode({
  reason: string,
  expectedResponseShape: 'strategy' | 'proposal' | 'analysis' | 'scope_discussion'
})
```

例子：

```text
用户：先帮我想想就行
用户：交付方案
用户：先别写代码，先聊聊思路
```

### 7.4 `restart_as_new_turn`

用于用户换了话题，旧 pending clarification 不应继续污染当前轮。

```ts
restart_as_new_turn({
  reason: string,
  newUserIntentSummary: string
})
```

例子：

```text
用户：你帮我查查最近半导体行业年报
用户：你是谁开发的
```

### 7.5 `request_followup_clarification`

用于 LLM 认为仍需要追问，但追问必须比上一问更具体。

```ts
request_followup_clarification({
  clarificationType: TaskClarificationType,
  question: string,
  options?: string[],
  rationale: string
})
```

约束：

1. 不允许原样重复上一条问题；
2. 必须说明缺失字段；
3. 只允许在确实无法继续时使用。

### 7.6 `request_risk_confirmation`

用于存在外部副作用或平台能力风险。

```ts
request_risk_confirmation({
  riskCapability: string,
  riskLevel: 'medium' | 'high',
  question: string,
  rationale: string
})
```

注意：

1. LLM 可以主动调用这个工具；
2. 即使 LLM 不调用，policy reducer 也可以把其他迁移改写成风险确认。

### 7.7 `continue_execution`

用于用户回复已经足够继续，并且无风险阻塞。

```ts
continue_execution({
  reason: string,
  assumptions?: string[]
})
```

## 8. Policy Reducer 设计

### 8.1 Reducer 的真正职责

Reducer 不理解用户自然语言。

Reducer 只处理：

1. 当前状态；
2. LLM tool call；
3. capability metadata；
4. 当前 session/run/env 是否具备执行条件；
5. 是否需要显式确认。

输出：

```ts
type ClarificationReducerResult =
  | {
      accepted: true;
      nextState: 'advisory' | 'ready_to_execute' | 'new_turn' | 'clarifying';
      clearedPending: boolean;
      assumptions?: string[];
    }
  | {
      accepted: false;
      nextState: 'clarifying' | 'risk_confirmation';
      clarificationType?: TaskClarificationType;
      question: string;
      options?: string[];
      reason: 'invalid_transition' | 'risk_requires_confirmation' | 'missing_capability' | 'stale_turn' | 'low_confidence';
    };
```

### 8.2 状态迁移 allowlist

Reducer 使用状态迁移表，不使用自然语言关键词：

| 当前状态 | 工具动作 | 允许结果 |
| --- | --- | --- |
| `clarifying` | `answer_clarification` | `ready_to_execute` 或 `clarifying` |
| `clarifying` | `delegate_to_agent_default` | `ready_to_execute` 或 `risk_confirmation` |
| `clarifying` | `switch_to_advisory_mode` | `advisory` |
| `clarifying` | `restart_as_new_turn` | `new_turn` |
| `clarifying` | `request_followup_clarification` | `clarifying` |
| `clarifying` | `request_risk_confirmation` | `risk_confirmation` |
| `none` | `switch_to_advisory_mode` | `advisory` |
| `none` | `continue_execution` | `ready_to_execute` |

### 8.3 Capability metadata

风险不是靠关键词判断，而是靠平台能力元数据：

```ts
type CapabilityPolicy = {
  capability: string;
  sideEffect: 'none' | 'local_write' | 'external_read' | 'external_write';
  riskLevel: 'low' | 'medium' | 'high';
  requiresExplicitConfirmation: boolean;
  requiresCredential: boolean;
  requiresBoundResource?: boolean;
};
```

例子：

```ts
{
  capability: 'deploy.production',
  sideEffect: 'external_write',
  riskLevel: 'high',
  requiresExplicitConfirmation: true,
  requiresCredential: true,
  requiresBoundResource: true
}
```

```ts
{
  capability: 'project.local_scaffold',
  sideEffect: 'local_write',
  riskLevel: 'low',
  requiresExplicitConfirmation: false,
  requiresCredential: false
}
```

### 8.4 Guard 规则

这些规则不是语义关键词，而是平台底线：

1. `external_write + high risk` 必须有显式确认；
2. 需要 credential 的 capability 必须存在可用授权；
3. 需要 bound resource 的 capability 必须有明确目标；
4. LLM 不能清除不属于当前 turn 的 pending；
5. LLM 不能把 `risk_confirmation` 直接切到 `ready_to_execute`；
6. `confidence=low` 时不允许清理 hard pending；
7. `request_followup_clarification` 不允许与上一问完全相同；
8. 如果 tool call schema 不完整，拒绝迁移并生成安全澄清。

## 9. 与现有链路的接入

### 9.1 新增服务

建议新增：

1. [altus-clarification-transition-agent.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-clarification-transition-agent.ts)
   - 调用 LLM；
   - 提供工具 schema；
   - 只返回 tool call，不直接改状态。
2. [altus-clarification-policy-reducer.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-clarification-policy-reducer.ts)
   - 接收 tool call；
   - 做状态迁移守卫；
   - 输出 reducer result。
3. [altus-capability-policy-service.ts](/Users/watson/codingProj/oneceo/apps/api/src/services/altus-capability-policy-service.ts)
   - 集中维护 capability metadata；
   - 第一阶段可以是静态表，后续可接平台 skill/governance 配置。

### 9.2 改造 `buildTaskIntentProfile(...)`

当前：

```text
history + currentInput
  -> classifyTaskIntentShape
  -> resolveClarificationDecision
  -> taskIntentProfile
```

改造后：

```text
history + currentInput + pendingClarification
  -> 如果存在 pending clarification 或高歧义输入：
       call clarification transition agent
       reducer 校验 tool call
       reducer result -> taskIntentProfile
  -> 否则沿用现有快速路径
```

### 9.3 改造 run entry / coordinator

保持外部行为不变：

1. reducer 输出 `risk_confirmation` 或 `clarifying`：
   - `taskIntentProfile.needsClarification=true`
   - 继续写入 `clarification_request`
2. reducer 输出 `advisory`：
   - `needsClarification=false`
   - 不进入执行型硬澄清；
   - prompt 引导 Altus 先给方案/分析。
3. reducer 输出 `ready_to_execute`：
   - `needsClarification=false`
   - 继续现有 Todo / direct execute 分流。
4. reducer 输出 `new_turn`：
   - 清理旧 pending；
   - 用当前输入重新构造 profile。

## 10. LLM Prompt 要求

Transition agent 的 system prompt 必须明确：

1. 你只负责选择一个状态迁移工具；
2. 不要输出普通 assistant 文本；
3. 不要尝试执行任务；
4. 不要编造授权、环境、凭证；
5. 如果用户只是要方案，调用 `switch_to_advisory_mode`；
6. 如果用户把选择权交给你，调用 `delegate_to_agent_default`；
7. 如果涉及真实外部副作用，优先调用 `request_risk_confirmation`；
8. 如果用户换了任务，调用 `restart_as_new_turn`；
9. 如果用户已经回答，调用 `answer_clarification`。

LLM 输出必须是 tool call，不接受自然语言裁决。

## 11. 失败与降级策略

### 11.1 LLM 调用失败

如果 transition agent 调用失败：

1. 不进入关键词兜底理解；
2. 保持当前 pending clarification；
3. 使用一个更自然的通用追问：

```text
我没有准确判断你是要继续执行、让我默认决定，还是先听方案。你可以直接说“先给方案”或“你来定后继续”。
```

### 11.2 LLM 输出非法 tool call

如果工具参数缺失或 schema 不合法：

1. reducer 拒绝；
2. 记录 debug log；
3. 返回安全 follow-up；
4. 不改变 pending 状态。

### 11.3 LLM 试图越权

例如：

```json
{
  "tool": "delegate_to_agent_default",
  "assumedDefault": "部署到生产环境"
}
```

Reducer 必须改写为：

```json
{
  "accepted": false,
  "nextState": "risk_confirmation",
  "reason": "risk_requires_confirmation"
}
```

## 13. 分阶段实施

### Phase 1：只做 transition tool + reducer，不改前端

1. 新增 transition agent；
2. 新增 policy reducer；
3. 新增 capability metadata 静态表；
4. setup service 接入；
5. 补单元测试和最小集成测试。

### Phase 2：观测与调试

1. 在 managed run metadata/debug log 记录：
   - selected tool；
   - reducer result；
   - rejected reason；
   - capability policy；
2. 管理后台后续可展示“为什么继续/为什么追问”。

### Phase 3：能力元数据平台化

1. 将 capability policy 从静态表迁到平台 skill/governance；
2. 部署、连接器、文件、外部 API 能力都声明 side effect 与 risk level；
3. reducer 不需要知道业务细节，只读 capability metadata。

## 14. 验收场景

### 14.1 咨询先行

```text
帮我想想，我想做个用户管理系统，应该怎么做
```

预期：

1. LLM 调 `switch_to_advisory_mode`；
2. reducer 接受；
3. 不出现“需要补充信息”；
4. Altus 直接给方案。

### 14.2 用户委托 Agent

```text
Altus：这次希望使用哪种开发语言或框架？
用户：你推荐就行
```

预期：

1. LLM 调 `delegate_to_agent_default`；
2. reducer 判断低风险；
3. 清理 pending；
4. Altus 按默认技术栈继续，并自然说明假设。

### 14.3 用户换问题

```text
Altus：这次希望使用哪种开发语言或框架？
用户：你帮我查查最近半导体行业年报
```

预期：

1. LLM 调 `restart_as_new_turn`；
2. reducer 接受；
3. 清理旧 pending；
4. 新 turn 按研究任务处理。

### 14.4 风险不能绕过

```text
Altus：要部署到预览环境还是生产环境？
用户：你决定
```

预期：

1. LLM 可能调 `delegate_to_agent_default`；
2. reducer 读取 `deploy.production` capability；
3. 因 `requiresExplicitConfirmation=true` 改写成 `risk_confirmation`；
4. 不直接部署。

## 15. 风险与控制

### 15.1 LLM 裁决不稳定

控制：

1. 工具 schema 固定；
2. temperature 设低；
3. reducer 不接受自由文本；
4. 关键路径有 fixture 回归。

### 15.2 reducer 退化成关键词系统

控制：

1. reducer 禁止读取 raw user text 做语义关键词判断；
2. reducer 只读 tool call、state、capability metadata；
3. 需要业务扩展时扩 capability metadata，不扩关键词。

### 15.3 能力元数据不全

控制：

1. 未声明能力默认按更保守处理；
2. external write 类能力必须显式声明；
3. 缺 metadata 时不允许静默放行高风险动作。

### 15.4 成本和延迟

控制：

1. 只在存在 pending clarification 或高歧义输入时调用 transition agent；
2. 普通明确输入继续走现有快速路径；
3. 后续可缓存相同 pending + user response 的裁决结果。

## 16. 结论

建议采用“LLM transition proposal + deterministic state guard”。

这不是全面 LLM 化，也不是关键词规则系统：

1. LLM 负责理解用户自然语言；
2. 工具调用负责把理解变成结构化迁移；
3. reducer 负责状态一致性；
4. capability policy 负责平台底线；
5. coordinator 继续复用现有 `clarification_request` 与 managed run 主链。

这能解决“像人一样理解补充信息回复”的问题，同时避免让 LLM 直接拥有危险状态切换权限。

### 17.1 ClaudeCode 参考结论

ClaudeCode 的关键做法不是靠关键词判断，而是：

1. 保留 typed message stream，在发起模型调用前统一投影成 API messages；
2. 工具调用和工具结果保持成对结构，不把工具事件随意拼成自然语言历史；
3. 附件、skills、MCP guide、用户命令等动态内容作为可插拔的上下文块注入；
4. 稳定系统提示与当前轮 volatile state 分离，减少高频变化内容污染 prompt cache；
5. 当前用户消息仍保持在最后，运行态提示插入在最新用户消息之前，避免模型把状态说明误当成用户新指令。

### 17.2 OneCEO 落地边界

本轮不重写 managed runner，而是新增一个统一上下文投影边界：

1. `altus-managed-context-service.ts` 负责从历史消息、pending clarification、当前用户输入投影出 managed conversation entries；
2. `AltusManagedSetupService` 不再自行拼接零散历史，统一消费 context service 的投影结果；
3. pending clarification 的问题会被放回用户回答之前，确保模型看到的是“问题 -> 回答”的相邻结构；
4. `AltusRunCoordinator` 将 memory、skill catalog、active skill、connector guide、runtime context 合并为 turn state prompt；
5. `AltusManagedPromptService.buildSystemPrompt()` 支持稳定前缀模式，当前时间、connector 状态、澄清状态、todo gate 等高频变化内容改由 `buildRuntimeContextPrompt()` 注入；
6. `ask_user` 工具增加 `clarificationType`，让用户层确认能力以结构化方式进入 pending state，而不是靠问题文本反推。
