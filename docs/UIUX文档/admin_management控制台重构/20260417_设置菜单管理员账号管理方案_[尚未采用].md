# 2026-04-17 设置菜单管理员账号管理方案 [尚未采用]

## 1. 需求理解

本方案将当前需求理解为：

1. 在管理后台顶栏 `设置` 中新增 `管理员账号` 能力；
2. 面向当前已登录管理员本人提供账号维护，而不是新建一个独立的 `admin_users` 列表页；
3. 第一阶段允许管理员修改：
   - 显示名称
   - 头像
   - 登录密码
4. 同时补上最基本、最顺手的账号安全能力，例如：
   - 查看当前账号基本信息
   - 查看最近一次登录
   - 退出其他登录中的设备

如果后续需要做“多管理员列表、创建管理员、分配角色、禁用其他管理员”，应单独立项，不和本方案混在设置弹层里。

## 2. 现状

### 2.1 数据与鉴权现状

当前代码里：

1. `admin_users` 只有：
   - `login_name`
   - `password_hash`
   - `display_name`
   - `role`
   - `status`
   - `created_at`
   - `updated_at`
   - `last_login_at`
2. `admin_user_sessions` 已记录：
   - `user_agent`
   - `ip_address`
   - `last_seen_at`
   - `expires_at`
   - `revoked_at`
3. 管理员内部接口目前只有：
   - 登录
   - 登出
   - 会话解析
4. 顶栏 `设置` 当前只有外观主题，没有账号设置入口。

这意味着本次能力需要同时补：

1. `admin_users` 的头像字段；
2. 管理员资料修改接口；
3. 管理员改密接口；
4. 管理员会话管理接口；
5. 设置面板中的账号页。

### 2.2 现有可复用能力

当前仓库已经具备：

1. 独立的 `admin_users` / `admin_user_sessions` 模型；
2. 管理后台 BFF 结构：
   - `apps/admin_management/server/routes/*`
   - `apps/admin_management/server/connectors/oneceo-api-connector.ts`
3. 顶栏 `设置` 弹层与主题保存逻辑；
4. 项目内既有的 R2 对象存储链路。

因此本次不应新起一套账号系统，而是沿用现有管理员鉴权链路和设置入口扩展。

## 3. 本次范围

### 3.1 包含

1. 将顶栏 `设置` 从单一主题面板扩展为居中的 `设置` 浮层；
2. 浮层内提供两个标签：
   - `外观`
   - `账号`
3. `账号` 标签内提供：
   - 头像上传与移除
   - 显示名称修改
   - 登录名只读展示
   - 角色、状态只读展示
   - 上次登录时间展示
   - 当前登录状态与当前设备信息展示
   - 修改密码
   - 退出其他设备
4. 修改成功后，同步刷新顶栏、侧边栏底部等管理员身份展示。

### 3.2 不包含

1. 新增单独的 `管理员管理` 一级导航；
2. 多管理员列表、搜索、排序、增删改；
3. 修改管理员角色；
4. 禁用其他管理员；
5. 管理员邮箱体系；
6. 忘记密码找回流程。

## 4. 目标

### 4.1 产品目标

1. 管理员在任何页面都能直接从顶栏进入自己的账号设置；
2. 改资料、改密码、处理其他登录中的设备都能在一个地方完成；
3. 交互要简单，不堆字段，不讲术语；
4. 二级面板保持居中、克制、清晰，避免把设置做成拥挤的小下拉框。

### 4.2 技术目标

1. 不绕开现有 `admin-auth-service`；
2. 所有管理员资料修改都走现有内部鉴权链路；
3. 不把头像文件塞进数据库；
4. 不引入新的身份源。

## 5. 信息架构与交互方案

### 5.1 入口

保留现在顶栏右上角的设置图标，但点击后不再展开狭窄下拉菜单，而是打开一个居中的浮动设置窗。

理由：

1. 主题和账号放在一起后，顶部小下拉框承载不了完整交互；
2. 居中浮层更符合后台二级窗口的一致性要求；
3. 改密码、上传头像这种操作需要更稳定的布局和更明确的焦点。

### 5.2 面板结构

设置浮层建议分为两栏：

1. 顶部：标题、当前管理员简述、关闭按钮；
2. 内容区：标签切换
   - `外观`
   - `账号`

桌面端使用 680px - 760px 的居中浮层；中小屏切为贴边抽屉式全宽面板，但结构保持一致。

### 5.3 `账号` 标签布局

`账号` 页建议分为三块，按用户最常见的操作顺序排布：

1. `账号概览`
   - 头像
   - 显示名称
   - 登录名
   - 角色
   - 账号状态
   - 上次登录
2. `基本资料`
   - 上传头像
   - 移除头像
   - 显示名称输入框
   - 保存资料按钮
3. `登录与安全`
   - 当前设备摘要
   - 退出其他设备按钮
   - 修改密码表单

这样排的原因很简单：

1. 先让人确认“我是谁、现在是什么状态”；
2. 再改资料；
3. 最后处理密码和设备这种更敏感的动作。

### 5.4 文案要求

后台这里统一说人话，避免技术腔：

1. `display name` -> `显示名称`
2. `login name` -> `登录账号`
3. `session` -> `登录中的设备`
4. `revoke other sessions` -> `退出其他设备`
5. `active` / `inactive` -> `可用` / `已停用`

## 6. 数据与存储设计

### 6.1 数据库变更

在 `admin_users` 增加：

1. `avatar_url TEXT`

第一阶段只增加一个头像地址字段，不拆额外 profile 表，也不把头像原始内容写进数据库。

### 6.2 头像存储策略

头像文件采用现有 R2 链路存储，后台数据库只保存最终可访问的头像地址。

建议规则：

1. 仅允许上传 `png` / `jpg` / `jpeg` / `webp`
2. 大小限制 `2MB`
3. 后端统一生成对象 key，例如：
   - `admin-avatars/{adminUserId}/{timestamp}-{random}.webp`
4. 替换头像时，新头像写入成功后再更新 `avatar_url`
5. 点击 `移除头像` 时，仅清空 `avatar_url`，界面退回首字母头像

本次不做头像裁剪工作台，避免把一个简单设置项做成复杂图片编辑器。

## 7. API 方案

### 7.1 oneceo API 内部接口

建议新增以下内部接口，统一仍走内部 token 认证：

1. `GET /api/internal/admin-auth/account`
   - 返回当前管理员资料与当前设备摘要
2. `PATCH /api/internal/admin-auth/account/profile`
   - 入参：
     - `displayName`
     - `avatarUrl`
3. `POST /api/internal/admin-auth/account/avatar`
   - multipart 上传头像
   - 返回 `avatarUrl`
4. `POST /api/internal/admin-auth/account/password`
   - 入参：
     - `currentPassword`
     - `nextPassword`
5. `POST /api/internal/admin-auth/account/logout-others`
   - 基于当前 session token，仅撤销“其他设备”的 session

### 7.2 管理后台 BFF 接口

在 `apps/admin_management/server/routes` 对应增加：

1. `GET /api/admin/account`
2. `PATCH /api/admin/account/profile`
3. `POST /api/admin/account/avatar`
4. `POST /api/admin/account/password`
5. `POST /api/admin/account/logout-others`

约束：

1. BFF 继续使用现有管理员 cookie；
2. 前端不直接拿内部 token；
3. 头像上传沿用已有 `multipart/form-data` 方式；
4. 修改资料成功后返回最新 `adminUser`，避免前端自行拼状态。

## 8. 服务层改动建议

### 8.1 `apps/api`

建议在现有 `admin-auth-service` 基础上扩展：

1. `getAccountProfileBySessionToken`
2. `updateAccountProfileBySessionToken`
3. `changePasswordBySessionToken`
4. `logoutOtherSessions`

同时补 DAO 方法：

1. `adminUserDAO.updateProfile`
2. `adminUserDAO.updatePassword`
3. `adminUserSessionDAO.listRecentByAdminUserId`
4. `adminUserSessionDAO.revokeOthers`
5. `adminUserSessionDAO.getById`

### 8.2 `apps/admin_management`

建议保持和现有结构一致：

1. `server/connectors/oneceo-api-connector.ts` 扩展账号相关请求；
2. `server/routes` 增加管理员账号设置路由；
3. `web/src/api.ts` 增加账号设置 API；
4. `web/src/App.tsx` 只保留设置弹层状态编排；
5. 新增独立组件承载账号设置内容，避免继续膨胀 `App.tsx`。

建议新增组件：

1. `apps/admin_management/web/src/components/AdminSettingsDialog.tsx`
2. `apps/admin_management/web/src/components/AdminAccountSettingsPanel.tsx`

## 9. 前端交互细节

### 9.1 账号概览

概览区只保留关键信息：

1. 头像
2. 显示名称
3. 登录账号
4. 角色
5. 账号状态
6. 上次登录

不要再塞说明性长段落，也不要堆管理术语。

### 9.2 头像交互

1. 点击头像区域可上传新头像；
2. 上传中显示进度条和遮罩；
3. 上传完成后立即刷新头像预览；
4. 失败用右上角 toast 提示；
5. 可用单独按钮 `移除头像` 恢复默认首字母头像。

### 9.3 密码交互

密码区只保留三项：

1. 当前密码
2. 新密码
3. 再输入一次新密码

保存按钮文案使用 `更新密码`。

修改成功后：

1. 清空密码输入框；
2. toast 提示成功；
3. 当前设备保持登录；
4. 不自动踢掉当前设备。

### 9.4 设备交互

账号页显示一条简洁设备摘要，例如：

1. 当前设备最近活跃时间
2. 当前 IP
3. 浏览器 / 终端标识

同时提供一个动作：

1. `退出其他设备`

不做繁杂设备列表，保持设置页短路径。

## 10. 校验与安全规则

### 10.1 基本资料

1. `displayName` 长度建议 1 - 40；
2. 只做首尾空白裁剪；
3. 空值不允许提交。

### 10.2 密码

1. 必须输入当前密码；
2. 新密码长度至少 `10` 位；
3. 新密码不能和当前密码相同；
4. 两次新密码输入必须一致；
5. 后端校验必须和前端校验同时存在。

### 10.3 头像

1. 仅接受图片格式；
2. 拒绝超出体积限制的文件；
3. 存储前统一校验 mime type；
4. 不允许把任意外链脚本地址当头像写入。

## 11. 对现有 UI 的影响

实施后会同步影响以下位置：

1. 顶栏管理员标识
2. 侧边栏底部管理员头像
3. 设置图标弹层
4. 登录后初始化 `adminUser` 的前端状态

其中：

1. 若管理员设置了头像，顶栏和侧边栏都使用真实头像；
2. 若未设置头像，则继续使用首字母占位；
3. 修改显示名称后，页面上所有管理员昵称展示立即更新。

最小验证范围建议包括：

## 13. 建议的实施顺序

1. 先补数据库字段与 API 服务
2. 再补 BFF 路由
3. 再改设置浮层结构
4. 最后补交互细节、视觉收口与截图验证

## 14. 结论

这个方案的核心不是再造一个“管理员管理系统”，而是把当前登录管理员最常用的账号维护动作收进顶栏 `设置`，并且做得足够顺手。

按这个方向推进后，管理员后台会得到一个更完整的闭环：

1. `外观` 放在设置里；
2. `账号` 也放在设置里；
3. 资料、头像、密码、设备处理都在同一个入口完成；
4. 不再需要到处找零散入口。
