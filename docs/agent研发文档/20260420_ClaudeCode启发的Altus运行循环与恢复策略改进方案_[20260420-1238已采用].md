# 20260420 ClaudeCode启发的Altus运行循环与恢复策略改进方案 [20260420-1238已采用]

## 1. 背景

当前 `Altus managed run` 主链已经具备以下基础能力：

- `AltusRunCoordinator` 负责模型调用、工具调用、终态收口。
- `AltusRunLifecycleService` 负责 `queued/running/waiting_user/completed/failed/stopped` 状态落库。
- `AltusRunRedisStateService` 负责运行态快照、恢复快照、heartbeat、active runs。
- `AltusManagedToolRuntime` 负责工具执行与部分错误语义收敛。
- 事件流已经能向前端提供 `assistant_delta`、`tool_call_started/completed/failed`、`run_completed` 等事件。

这条链路已经“能跑”，但从运行时设计角度看，当前 Altus 仍存在一个明显短板：

> 系统知道 run 现在是什么状态，但不够清楚“它为什么走到这一步、为什么继续、为什么重试、为什么被阻断”。

这会导致以下问题：

1. `AltusRunCoordinator.runModelLoop()` 里混合了正常推进、澄清、plain text 恢复、部署完成阻断、工具失败吞回上下文、轮次耗尽等多类分支，但这些分支没有统一命名和状态表达。
2. 当前 `stopReason` 主要承担终态解释，不足以表达运行中间的“转移原因”。
3. 恢复快照聚焦 sandbox / connector runtime / stream 进度，但缺少“下一步恢复时该如何继续”的显式策略信息。
4. 部署场景已经出现专门的修复回路语义（如 `deployment_completion_blocked`、`retryable_repair_required`），但它仍是单点特判，没有抽象成通用恢复策略层。
5. 工具返回内容已开始做局部压缩，但上下文预算治理仍然分散在各处，缺少统一策略。

本方案不重写 Altus，也不照搬 ClaudeCode 的完整实现；只吸收其中最有价值、且与 oneceo 当前架构兼容的部分。

## 2. 来自 ClaudeCode 的核心借鉴点

对参考代码的静态分析后，最值得借鉴的不是某个 prompt 技巧，而是下面四个运行时思想。

### 2.1 显式“运行转移原因”

ClaudeCode 的运行时不是只记录 `status`，而是在 query loop 内把“为什么继续下一轮”表达成明确的 transition reason，例如：

- 为什么触发 compact
- 为什么重试模型
- 为什么阻断 stop hook
- 为什么把异常转成 synthetic tool result

需要注意：

1. ClaudeCode 的 `transition.reason` 更接近“本轮循环继续原因”，不是产品级 task status。
2. 因此 oneceo 不应该机械复制成另一套大而全的生命周期状态机，而应把它落成 Altus managed run 内部的 loop reason / recovery reason。

这让系统从“黑盒循环”变成“可解释状态机”，同时不会破坏 oneceo 已有 `status + stage/phase` 体系。

### 2.2 恢复策略与主循环解耦

ClaudeCode 会把：

- 模型输出异常
- 工具执行中断
- token / output 超限
- stop hook 阻断
- 远程会话断连

统一落到“恢复策略”层处理，而不是散在主循环里直接 if/else 结束。

### 2.3 工具执行结果是运行时一等公民

ClaudeCode 对工具执行的处理中，有两个很关键的工程特点：

1. 工具失败不会简单丢弃，而会变成后续循环可消费的结构化结果。
2. 中断、失败、流式返回、并发安全边界，都属于工具编排层职责，不直接塞给模型循环本身。

### 2.4 上下文治理是独立能力，不是零散截断

ClaudeCode 对上下文长度的处理不是单次 `truncate`，而是分层治理：

- 工具结果预算
- 局部裁剪
- compact
- auto compact / reactive compact

这意味着“上下文治理”本身是一个运行时模块，而不是每个工具各自裁一点。

## 3. 不照搬的部分

以下做法不适合直接带入 oneceo：

1. **不照搬 ClaudeCode 的完整 feature-gate / runtime 分叉体系。** oneceo 当前服务边界已经比较复杂，再叠一层同级开关会继续放大复杂度。
2. **不引入新的全局进程态上下文。** oneceo 已经有 DB + Redis + session/sandbox 体系，运行事实应继续落在现有持久化链路中。
3. **不在本轮引入复杂并发工具执行。** Altus 当前工具大多对 workspace 有写影响，贸然并发会先破坏正确性。
4. **不做“把 Altus 改造成 ClaudeCode”式重构。** 本方案目标是改进当前 managed runtime，不是替换系统。

## 4. 本次改进目标

本方案只解决 Altus managed runtime 的运行循环表达与恢复策略问题，目标如下：

1. 给 Altus 补齐“运行转移原因（transition reason）”这一层表达。
2. 把部署修复阻断、plain text 恢复、模型重试、轮次耗尽前收敛等逻辑收敛成统一恢复策略。
3. 为 Redis 恢复快照补充“运行语义”，使恢复不仅知道 run 在哪，还知道 run 为什么停在那。
4. 为后续上下文治理预留独立模块边界。
5. 在不改变现有对外接口的前提下，提高调试、自省、回放、故障定位能力。

补充约束：

1. 不替换现有 `ManagedRunStatus`。
2. 不替换会话维度 `stage / phase`。
3. Redis 中新增的 loop 语义只能作为运行投影与恢复辅助，不能反向成为 DB 真相源。
4. `why continue / why retry / why blocked` 这类 transition / recovery 调试原因仅允许保留在后台原始 run event、Redis recovery snapshot、后台诊断查询中，不能直接透传到用户 SSE 流或会话投影消息元数据。

## 5. 非目标

以下不在本轮范围内：

1. 不改三层 task creation agents 的任务创建链路。
2. 不改 `AltusManagedToolRuntime` 的工具集合边界。
3. 不引入新依赖。
4. 不修改前端主交互协议。
5. 不在本轮做完整 context compact 系统实现。

## 6. 当前问题拆解

### 6.1 运行状态有了，但中间语义缺失

当前 `AltusRunState` 只有：

- `status`
- `stopReason`
- `startedAt/completedAt`
- sandbox / workspace 信息

这足够表达终态，但不足以表达：

- 本轮为什么继续
- 为什么向模型发送 continuation reminder
- 为什么允许或阻止 `complete_task`
- 为什么等待用户
- 为什么进入失败

### 6.2 `runModelLoop` 承担了过多职责

当前 `AltusRunCoordinator.runModelLoop()` 同时承担：

- 构建系统 prompt
- 处理模型重试
- 处理 plain text 恢复
- 处理 deployment 完成阻断
- 处理 deliverable 持久化
- 处理工具事件写入
- 处理终态 assistant message 落库

这导致每新增一种“回路分支”，都只能继续堆在主循环里。

### 6.3 恢复快照缺少“恢复策略提示”

当前 Redis recovery snapshot 已记录：

- sandbox
- connector runtime
- stream latest sequence

但没有记录：

- 最近一次转移原因
- 是否正处于恢复路径
- 下一轮建议动作类型

API 重启或 run 对账后，只能知道“有个活动 run”，不知道它是正常推进中、恢复中、还是被特定策略阻断。

### 6.4 修复回路仍然是特判

现在部署链路已有“整改回路”雏形：

- 工具返回 `retryable_repair_required`
- `complete_task` 受 `deployment_completion_blocked` 阻断
- prompt 会提醒优先修复发布问题

但这套能力只覆盖 deployment，没有抽象成统一的 recovery policy，因此：

- 类似问题无法复用到其他工具族
- 无法清楚区分“工具失败”“可修复失败”“需用户介入失败”

## 7. 方案总览

本方案建议在 Altus managed runtime 中新增三层轻量抽象：

1. **Transition Reason（转移原因）**
2. **Recovery Policy（恢复策略）**
3. **Context Budget Policy（上下文预算策略，先建边界）**

三者都不替代现有 `status`，而是在其之上补充“为什么”和“接下来如何继续”。

## 8. 详细设计

### 8.1 新增 `AltusRunTransitionReason`

新增一个运行时转移原因枚举或字面量联合类型，用于表达 Altus managed loop 每一次关键继续/阻断/结束的原因。

建议首批枚举值：

- `initial_execution`
- `tool_result_continue`
- `plain_text_continuation_prompted`
- `plain_text_continuation_failed`
- `clarification_requested`
- `tool_failed_but_recoverable`
- `tool_failed_user_action_required`
- `deployment_completion_blocked`
- `deployment_repair_required`
- `model_retryable_error`
- `model_non_retryable_error`
- `tool_round_limit_near`
- `tool_round_limit_exceeded`
- `completed_with_deliverables`
- `completed_without_deliverables`
- `user_interrupt`

要求：

1. 它不是替代 `status`，而是补充运行语义。
2. 每次关键转移都要在事件流和恢复快照中可见。
3. 终态 `stopReason` 保留，但尽量由 transition reason 派生出更一致的 stop reason。
4. 它的抽象粒度应贴近 ClaudeCode 的 continue reason，而不是重新发明产品级状态树。

### 8.2 新增 `AltusRunLoopSnapshot`

在不推翻现有 `RunRecoverySnapshot` 的前提下，增加 loop 语义快照：

```ts
type AltusRunLoopSnapshot = {
  lastTransitionReason: string | null;
  recoveryMode: 'none' | 'model_retry' | 'tool_repair' | 'awaiting_user' | 'context_pressure';
  currentRound: number;
  maxRounds: number;
  plainTextRecoveryUsed: boolean;
  lastToolName: string | null;
  lastToolCallId: string | null;
  updatedAt: string;
};
```

设计要求：

1. 写入 Redis recovery snapshot 的扩展字段，而不是新开一套孤立存储。
2. 允许前端或恢复服务知道“这个 run 当前处于哪种运行语义”。
3. 允许后续诊断工具用统一视角回放“为何失败/为何阻断/为何要求用户补充”。
4. 它仍然只是 recovery projection；DB 中已有 run/session/binding 事实仍然是权威来源。

### 8.3 引入 `AltusRunRecoveryPolicy`

把当前散落在 `runModelLoop()` 内的恢复分支抽象成一个轻量策略层：

```ts
type AltusRunRecoveryDecision =
  | { action: 'continue'; userReminder?: string; transitionReason: string }
  | { action: 'retry_model'; delayMs: number; transitionReason: string }
  | { action: 'ask_user'; question: string; options?: string[]; transitionReason: string }
  | { action: 'fail'; reason: string; transitionReason: string };
```

首批接管场景：

1. 模型返回纯文本且未调用工具。
2. 部署工具证据不足时调用 `complete_task`。
3. 工具失败但错误属于“可继续让模型修复”的范围。
4. 模型上游错误属于可重试错误。
5. 工具轮次接近上限时，主动向模型施加收敛提醒。

### 8.4 部署整改回路泛化为“可修复失败”

当前部署场景中的整改逻辑，不应再只作为 deployment 特判，而应上升为统一语义：

- `retryable_repair_required`
- `completion_blocked`
- `user_action_required`

部署仍然可以保留自身分类（如 `resource_binding` / `deployment_pending`），但要映射进统一恢复策略。

这样未来其它工具族也能复用：

1. 文件生成链路缺少依赖，可修复。
2. MCP 连接器运行态丢失，需恢复。
3. 调试链路 URL 非法，需用户补充。

### 8.5 为工具失败引入“结构化回注”语义

当前工具失败时，模型收到的是：

```json
{ "error": "..." }
```

这可以继续保留，但建议收敛为更稳定的结构。

这里借鉴的是 ClaudeCode “异常也要变成后续循环可消费结果”的思想，而不是要求 Altus 完整复制其 streaming executor。

建议结构：

```json
{
  "ok": false,
  "errorCode": "deployment_completion_blocked",
  "errorMessage": "...",
  "recoverable": true,
  "recoveryHint": "..."
}
```

好处：

1. 模型能更稳定地区分“继续修”和“该问用户”。
2. 事件流、日志、回放、测试都能围绕统一字段断言。
3. 与 ClaudeCode 的 synthetic tool result 思路一致，但不需要重做全部工具执行框架。

### 8.6 引入轻量 `Context Budget Policy`

本轮不实现完整 compact 系统，但应先把边界立住。

建议新增一个轻量策略模块，统一负责：

1. 单次工具结果写回对话的最大长度。
2. 特定工具的结构化压缩策略。
3. 轮次接近上限时的上下文收敛提示。
4. 后续真正做 compact 时的扩展点。

首批只做两个原则：

1. 保持现有工具结果压缩行为不回退。
2. 把零散 `truncate`/`compactSearchContent` 的策略性部分逐步迁到统一入口。

## 9. 代码落点建议

建议改造时优先收敛在以下文件：

- `apps/api/src/services/altus-run-coordinator.ts`
- `apps/api/src/services/altus-run-state.ts`
- `apps/api/src/services/altus-run-redis-state-service.ts`
- `apps/api/src/services/altus-run-recovery-service.ts`
- `apps/api/src/services/altus-run-lifecycle-service.ts`
- `apps/api/src/services/altus-managed-tool-runtime.ts`

如需新增文件，建议控制在：

- `apps/api/src/services/altus-run-transition.ts`
- `apps/api/src/services/altus-run-recovery-policy.ts`
- `apps/api/src/services/altus-context-budget-policy.ts`

要求：

1. 主循环只负责推进，不直接承载越来越多策略细节。
2. 运行语义必须可测试。
3. 不改现有 API 路由与前端协议。
4. 新增 recovery 字段时，必须同步补齐 `AltusRunRecoveryService.buildRecoverySnapshot()`，否则 reconcile 后会把新语义覆盖掉。

## 10. 分阶段实施建议

### 阶段一：补齐运行语义，不改主行为

目标：

- 新增 `AltusRunTransitionReason`
- 在事件流与 Redis recovery snapshot 中写入 `lastTransitionReason`
- 为关键分支补齐统一命名
- 同步补齐 recovery reconcile 逻辑，保证重建快照时不丢 loop 语义

这一阶段应做到“只增强可观测性，不改变行为”。

### 阶段二：抽离恢复策略

目标：

- 把 plain text continuation
- deployment completion blocked
- retryable model error
- clarification requested

从 `runModelLoop()` 中抽为统一 `AltusRunRecoveryPolicy`。

这一阶段行为允许微调，但不能改动最终对外语义：

- 正常完成仍然只能靠 `complete_task`
- 等待用户仍然落为 `waiting_user`
- 用户中断仍然落为 `stopped`

### 阶段三：收敛工具失败与上下文预算

目标：

- 统一工具失败结构
- 统一工具结果压缩入口
- 给后续 compact/summary 留出扩展点

这一阶段仍不引入复杂并发执行。

## 11. 测试与验证要求

### 11.1 单元测试

至少补齐以下断言：

1. plain text 无工具调用时，第一次进入 `plain_text_continuation_prompted`。
2. 再次 plain text 无工具调用时，进入 `plain_text_continuation_failed` 并失败。
3. 部署证据不足时，`complete_task` 被标记为 `deployment_completion_blocked`。
4. 可重试模型错误进入 `model_retryable_error`。
5. `waiting_user` 前能正确记录 `clarification_requested`。

### 11.2 恢复链路验证

至少验证：

1. Redis recovery snapshot 能读到最近一次 transition reason。
2. run 处于 `running/waiting_user` 时，恢复快照仍保留 loop 语义。
3. run 终态后 recovery snapshot 正常清理。
4. `AltusRunRecoveryService.reconcileRunById()` 重建 snapshot 后，不会回退或抹掉新增 loop 字段。

### 11.3 回归链路

至少覆盖：

1. 普通文件生成任务
2. 办公型交付物任务
3. 部署任务
4. 需要用户澄清的任务
5. 上游模型短暂失败后的重试任务

## 12. 风险与控制

### 风险 1：运行语义过度设计

控制方式：

- 第一阶段只补齐已有分支，不新增大量新状态。

### 风险 2：把恢复策略抽象得过头

控制方式：

- 只抽当前已经存在的真实分支，不预建空架子。

### 风险 3：调试信息增加但行为不一致

控制方式：

- 先做“可观测增强”阶段，再做行为收敛阶段。

## 13. 最终结论

ClaudeCode 最值得 oneceo 学的，不是“多高级的 agent prompt”，而是：

> 把 agent loop 当成一个可恢复、可解释、可诊断的运行时状态机，而不是一个只靠 `status + stopReason` 粗粒度收口的黑盒循环。

对 oneceo 来说，最短正确路径不是重写 Altus，而是：

1. 先补齐 transition reason；
2. 再把已有整改回路收敛成 recovery policy；
3. 最后再处理工具结果预算与上下文治理。

这样可以在不破坏当前主链的前提下，逐步把 Altus managed runtime 提升到更可解释、更可恢复、更容易迭代的状态。
