# 20260423 首轮澄清优先与 Todo 前置方案 [尚未采用]

更新时间：2026-04-23

## 1. 背景

当前 oneceo 的新建会话主链已经具备：

1. 提问/澄清能力；
2. Todo 展示能力；
3. `clarifying -> waiting_user` 的状态收口能力。

但现状仍存在两个关键偏差：

1. 用户刚发送需求后，系统经常会在关键信息不足时直接开始执行；
2. 即使任务已经明显进入多步骤实现，也没有把 Todo 作为“开始工作前的默认前置动作”强制下来。

这会带来两个直接问题：

1. 在需求边界、交付形态、技术栈、运行环境、验收标准还不清楚时，执行链路容易盲目启动；
2. 多步骤任务缺少稳定的显式 Todo，用户无法清楚看到系统打算如何推进，也不利于后续恢复、继续执行和验收。

用户明确要求参照 `claudecode` 的实现方式来改进，因此本方案必须把 `claudecode_src` 作为直接设计依据，而不是只基于我们自己的直觉补规则。

## 2. 目标

本次目标只做两件事：

1. 让新会话在真正开始工作前，优先做“必要澄清”，避免信息不足时盲目执行；
2. 让任务一旦进入实际工作阶段，先写 Todo，再开始执行，并在执行过程中持续更新。

## 3. 非目标

本次明确不做：

1. 不重做整个 Altus agent 架构；
2. 不引入新的多轮采访引擎或复杂计划模式；
3. 不把所有任务都强制变成多轮问答；
4. 不把 Todo 升级成独立数据库产品；
5. 不在本轮加入搜索式问题推荐、问题模板编辑器、Todo 看板等增强能力。

### 5.1 AskUserQuestion 是正式工具，而不是普通文案提问

参考：

1. [AskUserQuestionTool.tsx](/Users/watson/codingProj/oneceo/referance/claudecode_src/tools/AskUserQuestionTool/AskUserQuestionTool.tsx)
2. [constants/prompts.ts](/Users/watson/codingProj/oneceo/referance/claudecode_src/constants/prompts.ts)

可以明确看到：

1. `AskUserQuestion` 是正式工具，不是普通 assistant 文本；
2. `claudecode` 会在 prompt 中明确规定：
   - 需要澄清时用 `AskUserQuestion`
   - 不要用普通文本去问计划审批或关键澄清
3. 某些 skill 甚至写明：
   - “Use AskUserQuestion for ALL questions! Never ask questions via plain text.”

结论：

1. `claudecode` 的核心不是“允许问问题”，而是“把提问收口成明确的结构化工具路径”；
2. oneceo 现在的 `ask_user` 已有基础，但还没有被提升到与 `claudecode` 同等级的主链约束。

### 5.2 TodoWrite 是“开始工作前”的默认动作之一

参考：

1. [TodoWriteTool/prompt.ts](/Users/watson/codingProj/oneceo/referance/claudecode_src/tools/TodoWriteTool/prompt.ts)
2. [TodoWriteTool.ts](/Users/watson/codingProj/oneceo/referance/claudecode_src/tools/TodoWriteTool/TodoWriteTool.ts)

其中关键约束非常直接：

1. “After receiving new instructions - Immediately capture user requirements as todos”
2. “When you start working on a task - Mark it as in_progress BEFORE beginning work”
3. “Ideally you should only have one todo as in_progress at a time”
4. 系统还会在长期未使用 TodoWrite 时注入 `todo_reminder`

结论：

1. `claudecode` 不是把 Todo 当成“可选附加信息”，而是当成复杂任务的默认组织机制；
2. oneceo 当前 prompt 虽然提到 complex task 要先 form todo，但还没有做到：
   - 收到新指令后先捕获为 Todo
   - 开始工作前先把首个 Todo 标记为 `in_progress`
   - 长时间未写 Todo 时做运行态提醒

## 6. 设计原则

本次方案遵守以下原则：

1. 参照 `claudecode`，优先加强现有 `ask_user` / `todowrite` 路径，不另造新工具；
2. 先把“规则前置化”，再谈体验增强；
3. 澄清优先只在“信息不足时”触发，不打断明显的简单请求；
4. Todo 前置只在“进入实际工作阶段”触发，不污染纯闲聊与纯问答；
5. 产品上要让用户看到“系统正在先澄清、再列 todo、再开始做”，而不是黑箱跳转。

## 7. 方案设计

### 7.1 首轮消息处理改为三段门禁

新会话首轮消息进入后，统一走以下顺序：

1. 判断是否属于纯问答/纯记忆/纯身份问题；
2. 若不是，判断是否存在关键缺失信息；
3. 若缺信息，先进入澄清；
4. 若信息足够，再判断是否进入实际工作；
5. 一旦进入实际工作，先写 Todo；
6. Todo 建立完成后，才允许开始执行。

即：

`direct_answer OR clarify_first OR todo_first_then_execute`

### 7.2 “必须先澄清”的判定范围

本轮不做开放式语义平台，只做最短路径的门禁判定。

当满足以下任一类缺口时，要求优先 `ask_user`：

1. 交付形态不清楚
   - 例如：网页、脚本、PPT、文档、API、移动端不明确
2. 技术路线不清楚
   - 例如：前端框架、语言、运行环境、是否接现有系统不明确
3. 范围边界不清楚
   - 例如：只做页面还是含后端、只做 demo 还是可部署版本不明确
4. 验收标准不清楚
   - 例如：是否需要测试、部署、数据接入、登录、响应式等未明确
5. 用户明显表达“先别假设”“先问清楚”“先确认需求”

如果请求属于以下类型，则直接回答，不强制进入澄清：

1. 纯解释/纯知识问答；
2. 纯身份/记忆问题；
3. 单步、低歧义、低风险修改；
4. 用户已经给出了完整且可执行的约束。

### 7.3 “开始工作前必须写 Todo”的判定范围

参照 `claudecode`，本轮将 Todo 前置规则明确为：

以下情况必须先写 Todo，再进入执行：

1. 多步骤任务；
2. 涉及 3 个及以上明确动作；
3. 涉及多个文件或多个子系统；
4. 涉及调试 + 修改 + 验证串联；
5. 涉及部署、迁移、运行环境、联调；
6. 用户明确要求 todo；
7. 首轮澄清完成后进入正式实现阶段。

以下情况不强制 Todo：

1. 纯问答；
2. 单条简单信息回复；
3. 明显的一步式小改动；
4. 单个命令即完成的操作。

### 7.4 Todo 的最小执行契约

参照 `claudecode`，Todo 在 oneceo 内收敛为以下最小契约：

1. 开始工作前必须先创建 Todo；
2. 必须有且仅有一个 `in_progress` 项；
3. 每次完成后立即更新状态；
4. 若因为澄清阻塞，则可以先存在 `pending` 项，但真正开始执行前必须切出一个 `in_progress` 项；
5. Todo 至少覆盖：
   - 澄清后理解收口
   - 实现
   - 验证
   - 收尾/交付

### 7.5 前端交互口径

前端不新增独立模块，而是在现有消息流能力上收口：

1. `question` 卡片作为“执行前澄清”的标准呈现；
2. `todowrite` 卡片作为“开始工作”的标准起点呈现；
3. 在用户体验上，必须呈现出：
   - 用户发消息
   - 系统先提澄清问题或先建立 Todo
   - 然后才进入执行态
4. 不允许在用户刚发消息后立刻出现大量执行日志，但此前没有任何澄清或 Todo 建立痕迹。

## 10. 风险与规避

### 风险 1：澄清过度，导致本来能直接做的小任务被卡住

规避：

1. 保留纯问答/简单任务直达路径；
2. 只对关键缺失信息触发澄清。

### 风险 2：Todo 过度泛化，导致每个小任务都先写一堆待办

规避：

1. 只对多步骤/复杂任务强制 Todo；
2. 单步 trivial 任务继续允许直接执行。

### 风险 3：前端消息顺序仍然让用户感觉“已经开工了才来补问题”

规避：

1. 首轮澄清与 Todo 建立都必须在执行日志前出现；
2. 测试里明确校验首轮消息顺序。

## 11. 验证计划

至少补以下验证：

1. 纯身份/记忆问题
   - 预期：直接回答，不进入澄清，不写 Todo
2. 需求明显缺关键边界的实现请求
   - 预期：先 `ask_user`，不直接执行
3. 澄清后进入复杂实现
   - 预期：先 `todowrite`，再进入执行
4. 明显复杂但信息已充分的任务
   - 预期：首轮直接写 Todo，再执行
5. 单步小改动
   - 预期：允许直接执行，不强制 Todo
