# 09 实施步骤、风险与验收

## 1. 实施顺序

按最短路径实施，顺序固定如下：

### 阶段 A：后端基础对象

1. 新增 `managed run` 数据模型
2. 新增 `run event` 数据模型
3. 新增 managed API

当前落地：

- 已落地 `taskSessionRuns / taskSessionRunEvents / taskSessionSandboxBindings / taskSessionConnectorSnapshots`
- 已落地 `apps/api/src/routes/altus-managed-routes.ts`
- 已落地 `apps/api/src/services/altus-managed-stream-service.ts`
- API 启动前必须确认整套 schema 已就绪，不能只预热连接器表；否则 `task_session_runs` 等 managed 新表会缺失
- 2026-03-26 起，启动策略改为：
  - 先做一次快速 schema 探测，检查 managed / recent-message / connector 相关表、列、关键索引是否都已存在
  - 只有探测发现缺项时才执行整套 `runMigration()`
  - 若 schema 已是最新，则直接跳过迁移，不再在每次 `pnpm dev` 时重复跑 `DELETE + INSERT + backfill` 型 SQL

### 阶段 B：managed runner

1. 建立 `AltusConversationManager`
2. 建立 `AltusManagedRunner`
3. 建立 `PromptManager / ToolRegistry / ConnectorMcpManager`

当前落地：

- 已落地 `apps/api/src/services/altus-managed-run-entry-service.ts`
- 已落地 `apps/api/src/services/altus-run-coordinator.ts`
- 已落地 `apps/api/src/services/altus-run-state.ts`
- 已落地 `apps/api/src/services/altus-run-lifecycle-service.ts`
- 已落地 `apps/api/src/services/altus-run-event-writer.ts`
- 已落地 `apps/api/src/services/altus-managed-setup-service.ts`
- 已落地 `apps/api/src/services/altus-managed-prompt-service.ts`
- 当前 `apps/api/src/services/altus-managed-run-service.ts` 已退化为兼容出口，外部接口保持不变，内部主逻辑已开始从单体 service 向 `entry + coordinator + state + lifecycle + setup` 分层迁移

### 阶段 C：E2B tool runtime

1. 建立 `E2BSandboxManager`
2. 建立 `E2BSandboxToolRuntime`
3. 建立 OSAC only-if-needed 的服务桥接

当前落地：

- 已落地 `apps/api/src/services/altus-managed-tool-runtime.ts`
- 当前 managed shell/file/search 工具全部通过 `apps/api/src/connectors/e2b-connector.ts` 访问 E2B
- 这符合 oneceo 的 sandbox 边界要求，没有把 managed mode 接回 OpenCode direct executor

### 阶段 D：前端 managed 对话页

1. 新建 managed hooks
2. 接 run stream
3. 清理 managed 对 direct 状态的依赖

当前落地：

- `apps/web/client/src/lib/task-creation-client.ts` 已接入
  - `POST /api/altus-managed/sessions/:sessionId/runs`
  - `GET /api/altus-managed/sessions/:sessionId/runs/latest`
  - `GET /api/altus-managed/runs/:runId/stream`
  - `POST /api/altus-managed/runs/:runId/stop`
- `apps/web/client/src/hooks/useTaskCreationAgent.ts` 已把 managed mode 改成 `HTTP + SSE run` 主链
- direct mode 的 `WebSocket + runtime + OpenCode/Codex SSE` 保持不动
- managed stream 已补齐基于 `session.userId` 的订阅校验；前端订阅 URL 显式携带当前客户端 `userId`

### 阶段 E：删除旧 managed 主链路

1. managed 模式不再走 `TaskCreationService`
2. managed 模式不再使用 `file-memory-store`
3. 保留 direct mode 原链路

当前状态：

- 前端 managed 写入口已不再走旧的 `WS user_input`
- managed 读/流入口已不再走 direct `opencode/events`
- 后端旧 `TaskCreationService` 仍然保留在代码库中，但新的 managed mode 主链已经从入口侧绕开它
- `file-memory-store` 当前仅保留为 session 元信息与历史兼容层，还不是 managed 的权威运行状态源

## 2. 风险点

### 2.1 最大风险

最大风险不是 E2B，而是：

- managed 模式与 direct 模式长期共用一套前端 hook 与消息协议

因此实现时必须优先拆模式边界。

### 2.2 次级风险

1. sandbox tool schema 设计不统一
2. connector snapshot 与 run 生命周期耦合不清
3. 历史消息与新 run event 的展示口径不统一
4. 当前 run orchestration 仍集中在 `AltusManagedRunService`，后续还需要继续向 `coordinator / manager` 分层靠拢

## 3. 明确不采用的方案

以下方案本设计明确拒绝：

1. 在现有 `TaskCreationService` 上继续叠加 run 对象
2. managed mode 同时跑“旧三层 Agent + 新 run”
3. managed mode 继续依赖 `file-memory-store` 热状态
4. managed mode 继续复用 direct mode 的 executor 回流协议

这些都属于补丁式方案，不符合本次重构要求。

## 4. 验收标准

### 4.1 架构验收

满足以下条件才算完成：

1. managed mode 有独立 `run` 实体
2. managed mode 有独立 `run stream`
3. managed mode 不再依赖三层 TaskCreationService 主链路
4. managed mode 命令执行基于 E2B tool runtime
5. direct mode 不受影响
6. managed run stream 不能绕过当前 session 用户校验

### 4.2 用户侧验收

用户在 managed 模式下应体验到：

1. 一条消息对应一轮明确运行
2. 页面刷新后能恢复当前运行
3. 工具调用和命令执行有清晰流式展示
4. 停止后下一条消息自然开启新轮

### 4.3 工程侧验收

1. managed 与 direct 的接口和前端状态彻底分离
2. managed 历史与实时状态只依赖 `DB + run stream`
3. sandbox 调用全部符合 E2B / OSAC 边界约束

## 5. 最终结论

本次 Altus 接管模式重构不是“优化 TaskCreationService”，而是：

> 以 oneceo 的 session 为 thread，以 managed run 为执行单元，以 E2B 为 sandbox runtime，重建一套参照 Suna 的对话智能体与命令执行体系。
