# 20260522 网站生成检查 Playwright 截图证据链优化方案 [20260522-2216已采用]

## 背景

网站生成完成后的检查不能只停留在文字说明，也不能只在交付后补一张最终截图。用户需要看到 Altus 在 n.eko 调试浏览器里打开了目标网站，并且每一步 Playwright 检查都有可回放的截图证据，方便在 Actions 中复核“当时页面长什么样、操作到了哪一步”。

现有链路已经具备：

1. `debug_open_page`：打开目标 URL 到 sandbox 内 n.eko 正在回传的 Chromium。
2. `browser_interact`：通过 Playwright 连接同一个 CDP 9222 浏览器执行显式动作。
3. Actions 回放：按 `tool_call_started/completed/failed` 展示 Altus 工具动作。

缺口是：浏览器检查动作没有稳定截图证据，用户点开某个 Action 时只能看文字结果；并且旧流程容易把代码写完后的高层一致性检查当作交付前检查，导致没有真正进入浏览器视觉检测就调用 `complete_task`。

## 目标

1. 网站/网页应用类任务的完成顺序固定为：代码实现 -> 运行或构建验证 -> 视觉检测 -> `complete_task`。
2. 面向用户的状态文案使用“正在进行视觉检测”，不再使用“宏观自检”作为产品流程名称。
3. `debug_open_page` 成功后必须立刻用 Playwright 对同一个 n.eko Chromium 页面截图。
4. 每次 `browser_interact` 成功后必须截图，作为该操作的视觉证据。
5. 截图上传到平台对象存储，事件 metadata 保留 `browserScreenshot`。
6. 前端 Actions 选中某个浏览器操作时展示对应截图，并允许点开查看原图。
7. 网站/网页应用类任务如果没有成功捕获至少一条视觉检测截图证据，`complete_task` 必须被拦截并要求 Altus 回到视觉检测流程。
8. 截图证据不能只证明“截图文件存在”，还必须带有通用视觉健康诊断，能识别白屏、近似纯色、空 DOM、根节点无内容、Chrome 错误页、HTTP 错误页等页面不可用状态。

## 非目标

1. 不新增第二套浏览器服务。
2. 不把截图能力安装进用户项目依赖。
3. 不改变 n.eko 调试页转发和锁定机制。
4. 不把最终交付预览截图和逐步 Action 截图混成一个字段。

## 实现方案

### 后端工具运行时

`AltusManagedToolRuntime` 增加浏览器截图证据：

1. `debug_open_page` 校验目标 URL 和 CDP tab 就绪后，调用 Playwright `chromium.connectOverCDP(http://127.0.0.1:9222)` 复用同一个 n.eko Chromium。
2. `browser_interact` 执行动作成功后，复用同样的 CDP 页面截图。
3. 截图临时落在 sandbox `/tmp/oneceo-browser-action-*.png`，读取后上传 R2，随后删除临时文件。
4. 工具结果中返回 `browserScreenshot`，并在 `ManagedToolResult.evidence` 里保留结构化证据。
5. 截图同时返回 `visualCheck`：
   - `status`: `passed` / `failed`
   - `reasonCode`: 例如 `app_runtime_error`、`app_root_empty`、`visible_text_too_short`、`no_visible_content`、`screenshot_low_entropy`、`chrome_error_page`、`http_error_page`
   - `diagnostics`: URL、标题、body 文本长度、可见文本长度、可见元素数量、页面高度、最大可见元素面积、截图采样色彩数量、近白/近黑/主色占比、OneCEO app status、根节点渲染状态与浏览器运行时错误等。
6. `visualCheck` 是通用页面可用性信号，不包含某个具体任务或页面文案的专用规则。
7. 平台工具固定注入 sandbox 浏览器默认值：`ONECEO_PLAYWRIGHT_CDP_URL=http://127.0.0.1:9222`、`PLAYWRIGHT_BROWSERS_PATH=/opt/ms-playwright`、`NODE_PATH=/usr/local/lib/node_modules`、`playwright-mcp=/usr/local/bin/playwright-mcp`、`browser-use=/usr/local/bin/browser-use`、`browser-use venv=/opt/browser-use`、`neko=/usr/local/bin/neko`、`n.eko static root=/opt/neko/client/dist`。Altus 不需要也不允许在任务过程中搜索全局路径、安装 Playwright 或写自定义截图脚本。
8. 截图命令和浏览器动作命令必须用结构化标记输出成功/失败结果。即使 E2B 对非零退出只返回 `exit status 1`，运行时也应尽量保留 `reasonCode`、阶段、CDP 地址、Playwright 模块路径和错误信息，供 Action 详情和模型恢复使用。
9. Action 截图使用有明确超时的视口截图，不使用 `fullPage: true` 作为默认策略；整页截图在白屏、异常布局或远端浏览器状态不稳定时可能拖到 E2B 命令超时，导致用户看不到任何图片证据。视口截图成功后再做 DOM 与 PNG 像素诊断，即使页面是白屏，也必须优先保留可查看的截图，再由 `visualCheck.status="failed"` 阻止完成。
10. 嵌入 sandbox 的 Node/Playwright 脚本必须保持正则转义在生成后的脚本里仍然正确，例如 `\\s`、`\\b` 和 `\\/\\/` 不能在 TypeScript 模板字符串阶段被提前消费；相关测试需要覆盖生成命令文本，防止再次出现 `node_process` 类截图失败。
11. `debug_open_page` 失败必须结构化分类，至少区分 `debug_target_unreachable`、`debug_target_file_missing`、`debug_target_bad_status`、`debug_target_tab_not_ready`、`debug_service_not_ready`、`sandbox_browser_capability_unavailable`。同一 URL 同一失败原因连续出现时，coordinator 必须写入 `debug_open_page_repeat_blocked` 并停止继续喂模型重复打开同一目标，直到出现 `shell_execute` 或 `write_file` 等实际修复动作。
12. OpenCode / Codex 的 Playwright MCP 配置必须直接使用模板内固定命令 `playwright-mcp --cdp-endpoint http://127.0.0.1:9222`，禁止在运行期使用 `npx @playwright/mcp@latest` 触发包解析、下载或路径搜索。
13. 所有平台内部错误码、rawError、堆栈、端口探测详情和 `debug_open_page_repeat_blocked` 等诊断串只能进入内部 run event / 后台排查视图，不能直接进入用户会话、Actions 用户详情、交付卡片或 SSE 用户 payload。用户端必须看到端到端闭环文案，例如说明“视觉检测暂时无法继续、平台已停止重复尝试以避免继续消耗积分、已保留过程记录、下一步应检查预览服务/端口/文件路径”，而不是内部错误原文。

### 视觉检测完成门禁

`AltusRunCoordinator` 在 run 内维护视觉检测证据状态：

1. 只有 `debug_open_page` 或 `browser_interact` 成功事件中出现 `browserScreenshot.status="captured"` 且 `browserScreenshot.visualCheck.status="passed"`，才计为有效视觉检测证据。
2. 网站/网页应用类任务在 `complete_task` 前必须至少有 1 条有效视觉检测证据。
3. 如果缺少证据，coordinator 把该次 `complete_task` 写成可恢复失败，并把工具结果返回给模型，提示继续执行：启动/打开页面 -> `debug_open_page` -> Playwright/n.eko 浏览器操作 -> 重新提交。
4. 非网页类交付物不走该门禁，避免影响 DOCX、XLSX、PPTX、脚本等任务。
5. 如果最近一次视觉检测已经截图但 `visualCheck.status="failed"`，拦截原因应明确提示“页面已打开但未渲染出有效内容”，并带上 reasonCode，要求模型修复页面渲染或启动入口后重新检测。
6. 如果最近一次视觉检测动作成功但截图为 `capture_failed` / `storage_failed`，该动作不能计入 `capturedCount`，但需要记录为最近一次视觉检测尝试，拦截错误中保留失败原因，要求模型继续恢复截图链路或重新打开页面。
7. 如果截图已经成功上传但视觉诊断失败，Actions 仍然展示这张失败截图；失败截图是用户复核和模型修复的证据，不能因为未通过视觉健康检查而丢弃。

最低证据要求是一次通过视觉健康诊断的页面截图；对有交互、翻页、按钮、表单、响应式布局等要求的网站，模型提示词要求继续用 `browser_interact` 拆成可审计步骤，每步一个 Action 截图。

### 最终交付预览截图

`TaskSessionWebsitePreviewSnapshotService` 生成交付卡片截图时，也复用同一类视觉健康诊断：

1. `previewSnapshot.status="captured"` 只表示图片已保存，`previewSnapshot.visualCheck.status="passed"` 才表示预览页面有有效可视内容。
2. 如果最终预览截图为白屏或错误页，返回 `capture_failed`，`reasonCode="preview_visual_check_failed"`，并把具体诊断原因写入 `message`，避免用户在交付卡片里看到空白但系统仍标记完成。
3. 对固定 shell / Vite 类项目，交付预览应优先验证运行态入口；如果交付卡片打开的是 raw HTML，而视觉检测打开的是本地服务 URL，二者不应互相替代，需要在 metadata 中保留实际检测 URL 供排查。
4. 固定 shell / Vite 类项目还必须读取 `window.__ONECEO_APP_STATUS__` 与 `#root/#app[data-oneceo-app-status]`。如果 build、healthcheck、静态资源请求都成功，但浏览器运行时报错导致根节点没有挂载，应归类为 `app_runtime_error` 或 `app_root_empty`，不能被 CLI 截图兜底或健康检查通过状态掩盖。
5. DOM 诊断只能基于可见 DOM 判断错误兜底，不能扫描 `<script>` / `<style>` 源码中的模板字符串。固定 shell 会在启动脚本里内置 `OneCEO browser runtime error` 文案，若直接对原始 `--dump-dom` HTML 做字符串匹配，会把正常渲染页面误判为 `app_runtime_error`。
6. 最终交付快照不是唯一视觉真相源。如果完成前的 `debug_open_page` / `browser_interact` 已经在 Actions 中产生 `visualCheck.status="passed"` 的截图，而收口阶段独立启动/截图失败，则交付卡片应复用最近一次通过的浏览器视觉检测截图作为 `previewSnapshot`，并保留失败快照只作为排查信息，避免后置探测覆盖已通过的用户可见检测证据。

### 事件与回放

`AltusManagedToolExecutor` 在 `tool_call_completed` 事件中透传：

1. `evidence`
2. `browserScreenshot`

`AltusRunEventWriter` 继续按现有投影机制写入 timeline；该字段不是 debug-only 字段，允许进入用户可见 Actions。

管理后台读取调试状态时不能只依赖内存态 session runtime。Altus managed run 的 sandbox 绑定以 `task_session_sandbox_bindings` 和 `sandbox_execution_environments` 为准；管理端 debug 接口应优先读取 DB 绑定和 n.eko metadata，避免已存在 sandbox 时仍显示“执行环境未启动”。

用户可见投影和 SSE 必须通过统一的 debug payload 脱敏：移除 `transitionReason`、`currentRound`、`maxRounds`、`recoveryMode`、`debug`、`internalDebug`、`internalView`、`debugOpenPageFailure`、`rawError`，并递归清理 `toolResultEnvelope.contentForModel` / `toolResultEnvelope.errorMessage`。这些字段仍可保留在原始 `task_session_run_events.payload_json` 或后台内部视图中，供平台排查，但不能流到普通用户界面。

### 前端 Actions

`buildManagedReplayData` 从 executor event metadata 读取 `browserScreenshot`，挂到对应 `AltusReplayAction`。

`AltusRunReplayDrawer` 在选中 Action 详情区域展示截图：

1. captured：通过 `/api/task-creation/sessions/:sessionId/runs/:runId/tool-calls/:toolCallId/browser-screenshot.png` 加载图片。
2. capture/storage failed：展示失败原因。
3. 图片点击打开原图。

## 验收标准

1. 网站生成检查中出现 `debug_open_page` 或 `browser_interact` 后，对应 Action 有截图。
2. 截图来自同一个 n.eko Chromium CDP 9222，不启动独立浏览器。
3. Actions 列表仍按原逻辑显示，选中步骤后能看到截图证据。
4. 弱约束官网/落地页生成提示词不再引导“宏观自检后即可完成”，而是要求运行/构建验证后进入视觉检测。
5. 网站/网页应用类任务没有通过视觉健康诊断的截图时，`complete_task` 会被拦截为可恢复失败；单纯 `browserScreenshot.status="captured"` 不再足够。
6. 白屏、近纯色截图、空根节点、Chrome/HTTP 错误页不会被判定为视觉检测通过。
7. 最终交付预览截图如果视觉健康诊断失败，不再以正常 captured 预览进入交付卡片。
8. 如果最终交付快照失败但 Actions 中存在同 run 已通过的浏览器截图，交付卡片仍能展示通过截图，不显示“交付预览未通过视觉检测”的阻断状态。
9. 内部诊断错误不会原样展示给用户；重复打开失败、远程浏览器能力异常、预览不可达等终止场景都必须显示用户闭环文案，并在 Actions / SSE 用户 payload 中移除 raw diagnostic 字段。
10. 后端和前端相关单元测试通过。

## 风险

1. 如果 sandbox 缺失 Playwright 或 Chromium，截图会记录为 `capture_failed`，但不应覆盖原工具动作结果。
2. R2 配置异常时会记录 `storage_failed`，前端显示不可用原因。
3. 截图数量随浏览器检查步骤增加，需要后续按存储策略清理旧 run 证据。
4. 视觉健康诊断是通用启发式，不替代具体业务验收；它负责拦截“明显没渲染出可用页面”的问题，具体内容是否满足需求仍由后续交互步骤和模型检查承担。
