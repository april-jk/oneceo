# 20260422_Altus工具间延时体感最小修复方案_[20260422-1751已采用]

## 1. 背景

在用户态真实会话 `616aa39a-16d1-48b6-970e-9ccac24ea537` 中，用户明确感知到：

1. 每一个工具调用之间存在明显空窗；
2. 工具失败后，下一步动作迟迟不开始；
3. 整体观感更像“卡住”，而不是“仍在继续思考和执行”。

本方案目标不是泛化重构整个 loop，而是基于本次真实样本，做一轮**最小、可解释、低风险**的体感修复。

## 2. 样本事实

基于该会话最新 run `8c3cff7e-65ef-46e7-93f1-75c52f4bee24` 的 `task_session_run_events`，可以直接观察到以下关键时序：

1. `write_file completed`：`17:38:45.068`
2. 下一次 `shell_execute` 准备开始：`17:39:02.830`
3. 两者之间空窗约 `17.8s`

随后又连续出现：

1. `shell_execute` 第一次失败耗时约 `20.0s`
2. 失败后到下一次 `shell_execute` 准备开始，空窗约 `43.3s`
3. 第二次 `shell_execute` 再失败，又耗时约 `20.0s`
4. 再到第三次 `shell_execute` 准备开始，空窗约 `32.2s`

此外：

1. `debug_open_page` 自身执行约 `35.2s`
2. `write_file` 的 tool result 很小，仅回传 `path/bytes`
3. 但 assistant 上一轮 `tool_call.arguments.content` 中实际携带了完整 HTML，字符数约 `11271`

因此，本次“体感慢”并不是单一点故障，而是两类延迟叠加：

1. **工具完成后，下一轮模型决策本身耗时长**
2. **误用 `shell_execute` 启动前台常驻命令后，稳定吃满默认 timeout**

## 3. 根因判断

### 3.1 根因 A：assistant tool call 大参数被原样带入下一轮模型输入

当前 `Altus managed` 在工具执行完成后，会把 assistant 上一轮的 `tool_calls` 连同 arguments 一起留在消息数组里，再进入下一轮模型调用。

在本次样本中：

1. `write_file` 的实际 tool result 很小；
2. 但真正拖慢下一轮模型的是 assistant 的 `tool_call.arguments.content`；
3. 当前 budget policy 主要压缩 `role='tool'` 的消息；
4. 对 assistant message 内部的大 `tool_calls.arguments` 没有做等价压缩。

这会导致：

1. `write_file` 虽然已经执行完；
2. 但下一轮模型仍然要重新读取大段 HTML；
3. 于是出现 `write_file completed -> 下一工具 started` 的长空窗。

### 3.2 根因 B：`shell_execute` 默认 timeout 对前台常驻命令过于昂贵

当前 `shell_execute` 默认 `timeoutMs=20000`。

本次样本中模型尝试了：

1. `python3 -m http.server 8080`
2. `timeout 10s python3 -m http.server 8080 &`
3. `python3 -m http.server 8080 &` 且显式 `timeoutMs=5000`

前两次都稳定吃满约 `20s` 才失败，第三次也吃掉约 `5s`。

这类命令的问题不在“真的需要 20 秒”，而在于：

1. 它们是明显的前台常驻服务命令；
2. 对 managed 工具来说，这类误用不应该让用户为 timeout 全额买单；
3. 继续放行只会把错误路径做得更慢。

### 3.3 根因 C：模型思考空窗期缺少可感知反馈

当前前端主要在以下时刻看到明显进展：

1. assistant text delta
2. tool call delta / progress
3. tool start / complete / fail

但在“工具已完成，模型正在决定下一步工具”的这段时间里，缺少持续反馈。

因此即使系统实际上还在工作，用户感官也更容易把它理解成：

1. 卡住
2. 没继续执行
3. 下一步迟迟没开始

## 4. 设计约束

本方案必须满足以下约束：

1. 不重构主 loop 架构
2. 不引入通用命令语义系统
3. 不引入并发调度框架
4. 不修改 `write_file` 运行中放大卡片与现有 progress 语义
5. 不修改历史消息事实源，只允许修改“发给模型前”的输入投影
6. 不做自动 shell 命令改写，避免隐式业务偏移

## 5. 最小修复方案

### 5.1 修复 A：在 model input projection 中压缩 assistant tool call 的大 `write_file` 参数

修改范围：

1. `apps/api/src/services/altus-managed-context-budget-service.ts`
2. `apps/api/src/services/altus-run-coordinator.ts`

方案：

1. 保留现有对 `role='tool'` 消息的 budget policy
2. 额外增加一条很小的 assistant 投影规则：
   仅当 assistant message 中的 `tool_calls` 包含 `write_file`，且 `arguments.content` 超过阈值时，才在“发给模型前”的投影视图中压缩它
3. 压缩后仅保留：
   - `path`
   - `contentChars`
   - `head/tail` 小片段
   - `budgetApplied=true`
4. 不改原始 assistant message，不改 run event，不改历史持久化
5. 只影响下一轮 `callModel(...)` 时真正送给 LLM 的 payload

预期收益：

1. `write_file completed -> 下一工具 started` 的长空窗明显下降
2. 长文件生成类任务的后续轮次模型决策成本下降

为什么只做 `write_file`：

1. 本次真实样本最明显的拖慢点就是 `write_file.arguments.content`
2. 先做这一条，收益高，边界清晰
3. 不提前扩成通用 assistant tool-call 压缩框架，避免过度设计

### 5.2 修复 B：对明显的前台常驻 shell 命令做快速失败

修改范围：

1. `apps/api/src/services/altus-managed-tool-runtime.ts`

方案：

1. 不做通用分类器
2. 只拦截一小组“非常明确的前台常驻命令”，例如：
   - `python -m http.server`
   - `python3 -m http.server`
   - `npm run dev`
   - `pnpm dev`
   - `vite`
3. 命中后直接快速报错，错误信息明确告诉模型：
   - 当前命令属于前台常驻服务
   - `shell_execute` 不适合直接以前台方式启动
   - 请改用后台方式或专用调试/部署工具
4. 不自动为命令补 `&`
5. 不偷偷改写用户/模型命令

预期收益：

1. 避免误用前台常驻命令时稳定烧掉 `20s`
2. 错误更快回给模型，后续修正动作更快开始

为什么不直接全局调小 timeout：

1. 会误伤真实长命令
2. 不能把“错误命令路径”的优化变成“正常命令路径”的回归

### 5.3 修复 C：在模型决策空窗期补轻量状态反馈

修改范围：

1. `apps/api/src/services/altus-run-coordinator.ts`

方案：

1. 每轮调用 `callModelWithRetry(...)` 前，补一个轻量 `run_status`
2. 文案明确表达：
   - 正在分析上一步结果
   - 正在决定下一步操作
3. 若单次模型决策持续超过一个小阈值，例如 `3~5s`，可再补一次同类状态
4. 优先复用现有 run event / SSE 结构，不新增新的消息模型

预期收益：

1. 即使真实性能没有完全变快，前端也不会长时间无反馈
2. 用户对“系统仍在工作”的感知更稳定

为什么这条也属于最小修复：

1. 它不改业务决策
2. 不改工具执行路径
3. 只改善用户对长思考空窗的可见性

## 6. 不做的事

本轮明确不做：

1. 工具并发调度
2. 通用 shell 语义引擎
3. 全量 assistant tool_calls 压缩框架
4. 自动命令改写 / 自动后台化
5. deployment / debug 工具链重构

原因：

1. 这些都不是本次体感问题的最短路径
2. 会显著增加不可预料的回归风险

## 7. 验收标准

修复后，需要至少验证以下三项：

1. 在含大 `write_file` 参数的任务里，`tool_call_completed(write_file)` 到下一次 `tool_call_started` 的空窗显著缩短
2. 误用 `python3 -m http.server 8080` 这类命令时，不再稳定卡满 `20s`
3. 模型决策超过数秒时，前端能持续看到“继续分析中”的状态，而不是只有静默空窗

## 9. 实施顺序

严格按以下顺序做：

1. assistant `write_file` tool_call 参数 budget
2. `shell_execute` 前台常驻命令快速失败
3. 模型决策空窗轻量状态反馈

原因：

1. 第 1 步解决最大的结构性体感延迟
2. 第 2 步解决最浪费时间的错误路径
3. 第 3 步解决剩余的“静默等待”观感问题
