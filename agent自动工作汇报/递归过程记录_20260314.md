## 2026-03-14

- 问题：新电脑缺少 Node / pnpm 环境，项目无法启动。
- 已做：
  - 用 Homebrew 安装 `node@22`。
  - 用 `corepack` 激活 `pnpm@10.4.1`。
  - 执行 `pnpm install --frozen-lockfile` 完成依赖安装。
  - 分别启动 `pnpm --filter api dev` 与 `pnpm --filter web dev`，确认端口 `4000/3000` 可访问。
- 新发现：
  - `start-mac.sh` 的后台启动在本机不稳定，脚本返回成功后进程会退出。
  - shell 代理会影响 `curl localhost` 的验证结果。
- 下一步：
  - 如用户需要长期本地一键启动，再继续修复 `start-mac.sh`。
  - 如只需开始开发，当前环境已满足继续工作条件。

- 问题：直通模式新会话看起来“没有实时回复”。
- 已做：
  - 复核 SSE 建连，确认 `/api/task-creation/sessions/:id/opencode/events` 可正常返回 `bridge/ready`。
  - 复核新会话执行链路，确认并非纯前端问题，而是 OpenCode 启动后很快遇到上游 `422 Unsupported request body`。
  - 修复 `opencode_error` 在历史消息重建时被前端直接过滤的问题。
  - 后端失败路径新增主动下发 `error` 消息，避免用户只看到“执行已结束”或无感知失败。
  - Sandbox 生成的 `opencode.json` 改为优先写入字面 `baseURL/apiKey`。
- 新发现：
  - 当前 OpenCode `1.2.6` 对 `opencode.json` 中 `{env:...}` 占位的兼容性不稳定。
  - 真正阻断 assistant 文本流的是 OpenCode 到上游网关的请求体兼容性，而不是历史消息存储逻辑。
- 下一步：
  - 先验证错误消息可见性修复是否生效。
  - 继续定位 OpenCode 发往上游的请求体细节，确认 `422` 的具体触发字段。
  - 继续验证直通模式在冷启动窗口内的重试是否足以覆盖 sandbox / OpenCode 启动时延。

- 问题：`service_manager_gui` 自动刷新太频繁时会持续占住状态链路，导致按钮操作体感上无法点击或长时间无响应。
- 已做：
  - 将后台状态刷新、日志刷新、用户动作分别放入受控线程池，不再每次直接起裸线程。
  - `all_statuses()` 改为并行采样 4 个服务，缩短单轮状态刷新耗时。
  - 为状态和日志刷新加入请求序号，旧刷新结果回到主线程时直接丢弃。
  - 用户触发启动/停止/重启/强杀端口时，短暂停掉低优先级自动刷新。
- 新发现：
  - 之前的“按钮优先”只是在新轮询启动前做让路，已经跑起来的刷新任务仍可能和用户动作争抢资源。
  - 关闭 Tk 窗口时还需要处理线程池关闭后的提交失败，否则可能留下锁或按钮 busy 状态。
- 下一步：
  - 跑最小验证，确认脚本语法正确且 `--self-check` 不报错。
  - 若还有卡顿，再继续压缩单次状态探测里的命令超时和日志刷新频率。
