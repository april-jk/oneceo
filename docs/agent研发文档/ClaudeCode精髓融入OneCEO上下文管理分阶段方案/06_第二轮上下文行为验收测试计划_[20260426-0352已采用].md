# 06 第二轮上下文行为验收测试计划 [20260426-0352已采用]

## 1. 目标

本计划用于验证 Altus managed 上下文管理改造是否真正改善用户体感和缓存稳定性。

第一轮阶段 1-5 已完成结构建设，第二轮不继续堆新结构，而是把真实链路沉淀为可回归测试，重点回答四个问题：

1. 用户已经回答过的边界问题，后续是否不会重复追问；
2. 用户用自然表达继续推进时，agent 是否能承接前文而不是机械补充信息；
3. 工具调用、补充信息、附件、动态能力上下文是否能被稳定恢复；
4. context 编译、round trip、cache observation 是否有可解释证据。

## 2. 非目标

本计划不处理以下问题：

1. 不修复 `preview_snapshot_capture_failed / exit status 1`；
2. 不重写预览截图链路；
3. 不改变 sandbox preview 的启动、截图和 UI 展示逻辑；
4. 不扩大到 direct mode；
5. 不把 Redis、UI projection、prompt cache 变成事实源。

预览截图失败已单独记录为 GitHub issue #57，后续独立优化，不阻塞本轮上下文验收。

## 3. 验收分层

| 层级 | 目标 | 产物 | 通过标准 |
| --- | --- | --- | --- |
| L1 单元回归 | 锁住 context compiler、ask_user pairing、tool envelope、recovery/cache | API test files | 本地测试稳定通过 |
| L2 行为用例 | 锁住用户体感，不重复追问，不机械补充信息 | 题库 case 或专项 fixture | 每个 case 有明确 pass/fail 证据 |
| L3 真实浏览器链路 | 验证用户真实体感、web + managed run 实际闭环 | Playwright / browser 记录 | 以页面可见对话、输入框、URL、完成态为准，真实会话可复现通过 |
| L4 context-debug 摘要 | 验证排障证据可读、可解释 | debug summary | 只作为诊断辅助，不能替代浏览器层验收结论 |
| L5 缓存稳定观察 | 验证 prompt 结构可稳定命中缓存 | hash 观测记录 | stable block 不随动态上下文漂移 |

## 4. 必测用例

### 4.1 已回答边界不重复追问

输入链路：

```text
用户：帮我做一个管理后台系统
agent：需要补充信息：这次要交付的是网页应用、后端 API、本地脚本，还是完整业务系统？
用户：网页应用
```

预期：

1. 后续模型调用不能再次问同一个交付形态问题；
2. `pendingAskUser` 被关闭；
3. ledger 中保留 clarification request 和 user response；
4. 浏览器页面只出现一次该 clarification，`context-debug` 可作为辅助证据；
5. run 继续进入执行或合理的下一步澄清。

禁止：

1. 用户回答 `网页应用` 后再次问“网页应用、后端 API、本地脚本，还是完整业务系统？”；
2. 把 `网页应用` 当成新的独立任务；
3. 因 pending clarification 未关闭导致后续普通对话被卡住。

### 4.2 后续自然委托能承接前文

输入链路：

```text
用户：帮我做一个管理后台系统
用户补充：网页应用
agent：完成一个管理后台网页应用
用户：按你的想法，先帮我做个方案
```

预期：

1. agent 明确承接“管理后台系统 + 网页应用”的上下文；
2. 不重新追问交付形态；
3. 可直接产出方案或说明将基于前文方案化；
4. 浏览器页面能看到前文需求、补充答案、完成结果、后续方案请求；`context-debug.compiled.messages` 只用于失败后定位。

禁止：

1. 回到“这次要交付的是网页应用、后端 API、本地脚本，还是完整业务系统？”；
2. 把“方案”当作完全无上下文的新任务；
3. 只输出模板化追问，不推进用户目标。

### 4.3 低信息继续表达

输入样例：

```text
继续
按你说的来
方案
先帮我想想
先别写代码，先聊聊方案
```

预期：

1. 如果上一轮目标明确，agent 应承接上一轮目标；
2. 如果上一轮存在未关闭的必要用户确认，agent 才继续要求补充；
3. 当用户明确“先别写代码”时，不进入代码执行；
4. 澄清问题要解释为什么需要补充，而不是裸问固定模板。

### 4.4 用户中途改变目标

输入链路：

```text
用户：帮我做一个管理后台系统
用户补充：网页应用
用户：不要网页了，改成本地脚本
```

预期：

1. 新目标覆盖旧交付形态；
2. context ledger 保留变更事实；
3. agent 不因旧答案 `网页应用` 强行继续网页实现；
4. 如涉及能力边界变化，可以提出一次合理确认。

### 4.5 工具失败进入上下文

输入链路：

```text
用户：生成一个网页应用并运行检查
工具：shell_execute 失败
agent：换一种方式继续或解释失败
```

预期：

1. 失败工具结果进入下一轮上下文；
2. agent 不能表现得像没有看到失败；
3. `tool_result_envelope` 中有 `status=failed` 或等价结构；
4. retry/recovery 后不重复旧 clarification。

### 4.6 动态上下文不污染 stable prompt

覆盖对象：

1. attachments；
2. skills；
3. MCP providers；
4. memory snapshot；
5. budget replacement。

预期：

1. dynamic context 通过 typed block 注入；
2. stable system hash 不随普通消息变化；
3. dynamic block hash 只在对应能力变化时变化；
4. reload 后上下文语义等价。

## 5. context-debug 摘要视图验收

当前 `context-debug` 原始 JSON 可证明问题，但不适合日常排查。第二轮应补一个摘要输出，建议字段如下：

```json
{
  "sessionId": "...",
  "runId": "...",
  "recoveryState": "recoverable",
  "factsSource": {
    "messages": "task_creation_session_messages",
    "runEvents": "task_session_run_events",
    "redis": "not_fact_source",
    "uiProjection": "not_fact_source",
    "promptCache": "not_fact_source"
  },
  "clarification": {
    "pending": [],
    "answered": [
      {
        "question": "这次要交付的是网页应用、后端 API、本地脚本，还是完整业务系统？",
        "answer": "网页应用",
        "closed": true
      }
    ],
    "duplicates": []
  },
  "recentIntent": [
    "帮我做一个管理后台系统",
    "网页应用",
    "按你的想法，先帮我做个方案"
  ],
  "toolPairing": {
    "missingToolResults": [],
    "orphanToolResults": [],
    "duplicateToolResults": []
  },
  "cache": {
    "stableSystemChanged": false,
    "toolSchemaChanged": false,
    "dynamicContextChanged": true,
    "cacheBreakReasons": []
  },
  "roundTrip": {
    "equivalent": true,
    "diffs": []
  }
}
```

验收标准：

1. 普通排障时先看摘要，不需要展开完整 ledger；
2. 摘要不能替代原始 debug JSON；
3. 摘要来自 DB-backed ledger 编译结果，不从 UI 文案反推；
4. 摘要可以解释“为什么这次问/不问补充信息”。

## 7. 执行顺序

建议按以下顺序推进：

1. 先写 API 行为回归测试，锁住不重复追问和上下文承接；
2. 再补 context-debug 摘要视图和测试；
3. 再写真实浏览器链路测试；
4. 最后把稳定 case 沉淀到长期能力题库；
5. 完成后再讨论是否进入缓存命中率优化。

## 8. 通过标准

本轮测试计划通过需要满足：

1. API 回归测试全部通过；
2. 本地真实浏览器链路至少通过 `ALTUS-CONTEXT-001` 和 `ALTUS-CONTEXT-002`；
3. 远程 `http://oneceo.ai:3000` 真实浏览器链路至少通过 `ALTUS-CONTEXT-001` 和 `ALTUS-CONTEXT-002`；
4. 失败排障时，`context-debug` 摘要能明确显示 answered clarification、pending clarification、facts source、round trip、cache observation；
5. 低信息表达 case 不出现机械固定追问；
6. 目标变更 case 不被旧上下文错误锁死；
7. 预览截图失败只记录为非阻塞旁路问题，不影响上下文验收结论。
