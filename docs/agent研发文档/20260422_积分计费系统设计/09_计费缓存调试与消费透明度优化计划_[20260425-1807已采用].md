## 1. 背景与目标

### 1.1 已确认事实

1. 当前主 LLM 上游为 DashScope OpenAI-compatible：
   - Base URL：`https://dashscope.aliyuncs.com/compatible-mode/v1`
   - Chat Completions：`POST /chat/completions`
2. 用户端展示边界：
   - 只能展示积分、会话、时间等用户可理解信息。
   - 不展示 token、model、provider、缓存命中 token、缓存创建 token。
3. 管理端展示边界：
   - 可以展示 token、模型、provider、缓存命中、缓存创建、定价快照、积分换算等审计信息。
4. 当前兑换比例：
   - `1 credit = ¥0.01`
   - `100 credits = ¥1`
5. qwen / DashScope 缓存字段：
   - 隐式缓存命中：`usage.prompt_tokens_details.cached_tokens`，部分 DashScope 场景可能是 `usage.cached_tokens`。
   - 显式缓存创建：`usage.prompt_tokens_details.cache_creation_input_tokens` 或 `usage.prompt_tokens_details.cache_creation.cache_creation_input_tokens`。
6. 实测基线：
   - `qwen3-vl-plus` 显式缓存可创建并命中。
   - 隐式缓存无需参数但命中不确定，不适合作为唯一稳定测试方式。
   - `qwen3-max-2026-01-23` 这类快照模型不宜作为缓存验证基准，官方隐式缓存说明中暂不支持快照与 latest 模型。

### 1.2 目标

在管理后台「计费管理」中新增一个面向管理员的调试页，用于主动发起模型 API 请求，查看原始 usage、归一化 usage、缓存字段、积分计算和兑换比例，帮助判断：

1. 上游是否真实返回缓存命中/创建字段。
2. 平台是否正确解析 DashScope / OpenAI-compatible usage。
3. 平台计费公式是否和当前定价、缓存比例、积分兑换比例一致。
4. 用户端最终应该看到多少积分消耗。
5. 管理端审计数据是否足以解释一次扣费。

### 1.3 非目标

1. 不把调试页做成通用模型 Playground。
2. 不允许浏览器直连 DashScope。
3. 不允许管理员输入任意 base URL 或 API Key。
4. 不在用户端展示 token、模型、provider、缓存明细。
5. 首版不做批量压测、自动定时 cache warm-up、价格配置编辑。
6. 首版不默认开放真实扣费；真实扣费需单独确认权限、幂等与审计策略。

## 3. 计费与兑换规则

### 3.1 用户端兑换比例

当前固定：

```text
1 credit = ¥0.01
100 credits = ¥1
```

该规则来自：`apps/api/src/services/conversion-service.ts`。

用户端只展示积分，例如：

```text
消耗 3 积分
```

不展示：

```text
prompt_tokens / cached_tokens / model / provider / cache ratio
```

### 3.2 管理端计费公式

设：

```text
P = promptPricePer1kTokens
C = completionPricePer1kTokens
H = cache hit ratio，例如 qwen 隐式缓存 20% = 0.2
K = cache creation ratio，例如 qwen 显式缓存创建 125% = 1.25
```

归一化 usage：

```text
prompt_tokens
cached_prompt_tokens
cache_creation_tokens
non_cached_prompt_tokens = prompt_tokens - cached_prompt_tokens - cache_creation_tokens
completion_tokens
```

积分计算：

```text
regular_prompt_credits = non_cached_prompt_tokens * P / 1000
cached_prompt_credits = cached_prompt_tokens * P * H / 1000
cache_creation_credits = cache_creation_tokens * P * K / 1000
completion_credits = completion_tokens * C / 1000

total_credits = ceil(
  regular_prompt_credits
  + cached_prompt_credits
  + cache_creation_credits
  + completion_credits
)
```

### 3.3 隐式缓存下如何知道具体消费

隐式缓存命中不由平台决定，只有上游响应回来后才能知道。判断依据：

```text
usage.prompt_tokens_details.cached_tokens
usage.cached_tokens
```

如果字段缺失或为 0，则本次按未命中处理。

## 4. 调试页面功能设计

### 4.1 页面定位

页面名称建议：`调试工具`。

页面目标：帮助管理员验证一次模型调用从「请求」到「usage 解析」再到「积分计算」的完整链路。

页面不是普通用户功能，也不是模型体验入口。

### 4.2 输入区

首版输入项：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| provider | select | 首版固定 DashScope / qwen，不开放任意 provider |
| model | select/input | 优先从已有定价与模型候选中选择 |
| cacheMode | select | `none` / `implicit` / `explicit` |
| stream | switch | 非流式 / 流式 |
| promptPreset | select | 短 prompt、长前缀、显式缓存样例 |
| systemPrompt | textarea | 可编辑，默认提供安全样例 |
| userPrompt | textarea | 可编辑，默认短问题 |
| maxTokens | number | 默认小值，例如 64 |
| temperature | number | 默认 0 |
| mode | select | `request_only` / `dry_run`，真实扣费不在首版默认开放 |

### 4.2.1 调试台交互与布局补充

根据 2026-04-25 实现反馈，调试工具不应采用普通后台表单堆叠布局，而应采用接近 Postman 的 API 调试工作台信息架构：

1. 顶部必须固定展示本次调试的管理端接口：`POST /api/internal/billing/debug/llm-request`。
2. 顶部必须展示实际上游接口地址：`https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`，但不得展示 API Key。
3. 顶部 URL 区应提供主要发送动作，避免管理员在长表单中寻找提交按钮。
4. 请求配置区按「参数」「请求体」分区；长 prompt 必须定高滚动或可折叠，不能撑爆页面。
5. 响应结果区按「概览」「Usage」「计费」「Raw JSON」分区；JSON 必须在固定高度代码区内滚动，不能撑爆外层布局。
6. 首屏应能看到接口 URL、发送按钮、关键请求参数和响应概览入口。
7. 页面仍然不是通用模型 Playground，不开放任意 base URL、API Key 或真实扣费。

### 4.2.2 计费管理响应式补充

计费管理页必须在正常浏览器缩放比例下可用，禁止依赖用户缩放到极低比例才能看到内容：

1. `user-management-filter-panel`、Tab 栏、筛选 grid、表格容器必须允许收缩，避免把父级撑出视口。
2. Tab 栏在窄屏下应横向滚动或自适应，不得裁切当前 Tab。
3. 调试工具桌面端可左右双栏，窄屏应自动堆叠为单栏。
4. 表格可以保留横向滚动，但外层页面不能被 `overflow: hidden` 直接裁切到无法操作。
5. 计费管理页面的摘要卡、表单 grid、表格和 JSON 区域都必须设置 `min-width: 0` / `max-width: 100%` 等收缩边界。

2026-04-25 复查补充：计费管理不能直接把多个 Tab 内容片段平铺为 `user-management-page` 的 grid 子项。`user-management-page` 原本只适用于「hero / filter / list」三段式页面，其 `grid-template-rows: auto auto minmax(0, 1fr)` 会把第三个子项压进可伸缩行；当计费页在 Tab 后继续平铺统计筛选条、KPI 卡、图表、表格等多个兄弟节点时，`sub-panel user-management-filter-panel` 会被压缩到远小于自身内容高度，表现为必须缩放到很小才能完整看到。采用方案：

1. 计费页保留三段式外层：hero、主 Tab、Tab 内容容器。
2. 所有 active Tab 内容必须放入单一 `billing-management-tab-content` 容器内。
3. `billing-management-tab-content` 自己负责滚动与不同 Tab 的行布局，避免内部筛选条成为外层 grid 的第三行压缩对象。
4. 顶部主 Tab 与 Tab 内筛选条都必须满足 `clientHeight >= scrollHeight`，除非该区域明确设计为可滚动容器。

### 4.3 模式语义

#### 4.3.1 只请求不扣费 `request_only`

默认模式。

行为：

1. 发真实模型请求。
2. 获取原始响应与 usage。
3. 做 usage 归一化。
4. 计算理论积分消耗。
5. 不扣用户积分。
6. 不写 `credit_transactions`。
7. 不写 `token_usage_logs`，或仅写单独的 admin debug audit，不混入正式账单。

风险提示：

```text
该模式不会扣用户积分，但会产生真实上游模型成本。
```

#### 4.3.2 模拟扣费 `dry_run`

行为：

1. 发真实模型请求。
2. 使用生产同源计费函数计算“如果扣费会扣多少”。
3. 展示 would_charge_credits。
4. 不改变用户余额。
5. 不写用户账单流水。

要求：

1. 必须复用 `pricingService.calculateCredits()`，禁止复制第二套公式。
2. 结果必须明确显示 `dry_run = true`。
3. 展示 pricing snapshot 与 cache ratio snapshot。

#### 4.3.3 真实扣费 `charge`

不作为首版默认功能。

如果后续采用，必须满足：

1. 仅 super admin 或特定 `billing_debug_charge` 权限。
2. 默认只允许选择测试用户。
3. 必须二次确认。
4. 必须有 idempotency key。
5. usage 缺失、字段冲突、定价缺失时禁止扣费。
6. 必须展示扣费前余额、扣费后余额、交易 ID、token usage log ID。

## 6. Usage 归一化规则

### 6.1 输入字段读取优先级

prompt tokens：

```text
usage.prompt_tokens
usage.input_tokens
```

completion tokens：

```text
usage.completion_tokens
usage.output_tokens
```

cached prompt tokens：

```text
usage.prompt_tokens_details.cached_tokens
usage.cached_tokens
usage.cache_read_input_tokens
```

cache creation tokens：

```text
usage.prompt_tokens_details.cache_creation_input_tokens
usage.prompt_tokens_details.cache_creation.cache_creation_input_tokens
usage.prompt_tokens_details.cache_creation.ephemeral_5m_input_tokens
usage.cache_creation_input_tokens
```

### 6.2 字段冲突处理

以下情况必须显示 warning：

1. 等价字段同时存在但数值不一致。
2. 字段为字符串但可转数字。
3. 字段为 null、负数、NaN、非数字对象。
4. `cached_prompt_tokens + cache_creation_tokens > prompt_tokens`。
5. 缺少 prompt/completion usage。
6. stream 请求最后没有 usage。

首版处理策略：

| 情况 | request_only | dry_run | charge |
| --- | --- | --- | --- |
| usage 完整 | 展示 | 可模拟 | 可扣费，若后续开放 |
| usage 缺失 | 展示错误 | 不模拟 | 禁止 |
| 字段冲突 | 展示 warning | 可模拟但标 warning | 禁止 |
| 定价缺失 | 展示 usage | 不计算积分 | 禁止 |
| cache tokens 超过 prompt tokens | 展示错误 | 不模拟 | 禁止 |

## 7. 缓存测试矩阵

### 7.1 缓存模式

| 场景 | 预期 | 验证点 |
| --- | --- | --- |
| none | 不主动加 cache_control | 观察是否有隐式缓存字段 |
| implicit 未命中 | `cached_tokens = 0` 或缺失 | 按未缓存输入计费 |
| implicit 命中 | `cached_tokens > 0` | 按 qwen 20% 计费 |
| explicit 创建 | `cache_creation_input_tokens > 0` | 按 qwen 125% 计费 |
| explicit 命中 | `cached_tokens > 0` 且 creation 为 0 | 如果定价未区分显式/隐式，需在页面提示当前采用的 provider 缓存比例 |
| explicit 过期 | 5 分钟后可能重新创建 | 展示 TTL 提示 |

### 7.2 模型支持

| 模型类型 | 风险 |
| --- | --- |
| qwen3-vl-plus | 可作为显式缓存测试基准 |
| qwen3-max | 官方支持，适合作为后续验证候选 |
| qwen3-max-2026-01-23 | 快照模型可能不支持隐式缓存，不作为首选基准 |
| 不支持 cache_control 的模型 | 可能忽略字段或报错 |
| 非 qwen provider | 不应套用 qwen 比例 |

### 7.3 stream / non-stream

| 场景 | 处理 |
| --- | --- |
| non-stream 返回完整 usage | 标准验证路径 |
| stream 最后一帧返回 usage | 需要收集最终 usage |
| stream 未返回 usage | 不允许 dry-run/charge，只展示缺失 |
| stream 中途取消 | 不允许真实扣费 |
| stream 错误后返回部分内容 | 不允许真实扣费 |

### 7.4 请求内容变化

| 场景 | 预期 |
| --- | --- |
| 完全相同长前缀，尾部问题不同 | 更容易命中缓存 |
| 改动 system prompt 开头 | 大概率不命中 |
| prompt 小于 256 token | 隐式缓存不会触发 |
| 显式缓存内容小于 1024 token | 显式缓存不会创建 |
| 超过 20 个 content 块间隔 | 显式缓存可能无法命中 |
| 超过 4 个 cache_control | 仅最后 4 个生效 |

## 9. 审计与安全

### 9.1 必须记录的审计字段

即使 `request_only` 不扣费，也建议写管理端审计：

1. admin user id
2. 操作时间
3. mode
4. provider / model
5. cache mode
6. stream
7. prompt length
8. prompt hash
9. 是否保存完整 prompt，默认否
10. upstream request id
11. response status
12. raw usage
13. normalized usage
14. pricing snapshot
15. credit exchange ratio snapshot
16. calculated credits
17. warning / error

### 9.2 禁止项

1. 禁止返回或保存上游 API Key。
2. 禁止前端传入 API Key。
3. 禁止管理员输入任意 base URL，避免 SSRF。
4. 禁止自动保存完整 prompt/output。
5. 禁止 usage 缺失时真实扣费。
6. 禁止绕过现有 admin auth。
7. 禁止将调试日志混入用户消费记录。

```text
billing_debug_runs
```

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 调试记录 ID |
| admin_user_id | 操作管理员 |
| mode | request_only / dry_run / charge |
| provider | dashscope/qwen |
| model | 模型名 |
| cache_mode | none/implicit/explicit |
| stream | 是否流式 |
| prompt_hash | prompt 哈希 |
| prompt_chars | prompt 字符数 |
| upstream_request_id | 上游 request id |
| response_status | 上游状态 |
| raw_usage_json | 原始 usage |
| normalized_usage_json | 归一化 usage |
| pricing_snapshot_json | 计费快照 |
| calculated_credits | 计算积分 |
| charged_credits | 实扣积分，首版为空 |
| warnings_json | warning 列表 |
| created_at | 创建时间 |

首版若不落库，也必须保证前端不会把调试结果误当作正式账单。

## 11. 实施计划

### 11.1 第一阶段：只请求 + 模拟扣费

1. 在 `internal-billing-routes.ts` 新增调试接口。
2. 封装 usage normalizer，复用 `llm-proxy-connector.ts` 已有字段读取逻辑。
3. 后端通过现有 LLM proxy/connector 发请求。
4. 复用 `pricingService.getActivePricing()` 和 `pricingService.calculateCredits()` 计算 dry-run 结果。
5. 返回 raw usage、normalized usage、pricing snapshot、credits 计算分解、warning。
6. 管理后台 `BillingManagementSection.tsx` 增加 `debug` Tab。
7. 新增 `BillingDebugPanel.tsx`，完成请求表单和结果展示。
8. 管理后台 server 补代理路由。
9. 增加单元测试覆盖 usage normalizer 和计费公式。
10. 使用真实 DashScope 做一次手动 smoke：显式缓存创建、显式缓存命中、隐式未命中。

### 11.2 第二阶段：审计记录

1. 决定是否新增 `billing_debug_runs`。
2. 如果新增，先补迁移与内部查询接口。
3. 仅记录摘要、hash、usage、pricing snapshot，不保存完整 prompt/output。

### 11.3 第三阶段：真实扣费，待单独确认

真实扣费不进入首版。

如后续需要，必须先补：

1. 权限模型。
2. 测试用户限制。
3. 幂等键。
4. 二次确认。
5. 余额前后展示。
6. 严格审计。

## 12. 验证标准

### 12.1 后端

1. non-stream qwen 请求能返回 raw usage。
2. 显式缓存第一次请求显示 `cacheCreationTokens > 0`。
3. 显式缓存第二次请求显示 `cachedPromptTokens > 0`。
4. 隐式缓存未命中时能明确显示 `cachedPromptTokens = 0`。
5. 字段缺失时不给出错误扣费结果。
6. 定价缺失时仍展示 usage，但不计算积分。
7. 计费结果与 `pricingService.calculateCredits()` 一致。

### 12.2 前端

1. 调试页默认模式为“只请求不扣费”。
2. 页面有真实上游成本提示。
3. 不展示 API Key。
4. 不允许输入任意 base URL。
5. 结果区同时展示 raw usage、normalized usage、积分计算、用户端展示预览。
6. warnings 明显可见。

### 12.3 安全

1. 非管理员不能访问调试接口。
2. 浏览器不能直连 DashScope。
3. 调试请求不写用户消费记录。
4. 用户端不暴露 token/model/provider/cache 明细。

## 13. 待确认事项

1. 调试页首版是否只支持 `qwen3-vl-plus` 与当前已有 qwen 定价模型，还是允许所有已定价模型。
2. 首版是否需要落库 `billing_debug_runs`，还是只返回当前调试结果。
3. 是否需要显示完整上游 response，还是只展示 `usage`、request id、状态、截断输出。
4. 是否允许管理员手动输入 prompt，还是首版只提供 preset，减少成本和泄露风险。
5. 真实扣费模式是否完全不做，还是隐藏在 feature flag 后仅测试用户可用。
