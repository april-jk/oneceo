# 稳定性、复用性、验证与灰度设计 [尚未采用]

## 1. 目标

这份文档解决最后一个问题：

- 即使模板和注入方案设计对了，怎样保证它真的稳定、可复用、可逐步上线。

## 2. 稳定性原则

## 2.1 单模板优先于多模板

在没有把第一套模板跑稳之前，不引入第二套官方模板。

原因：

- 模板一多，agent 选择和平台注入都会复杂化
- 统计契约和部署诊断也会被分叉

## 2.2 统计失败不能阻塞业务

统计采集必须遵守：

- 上报失败只影响统计
- 页面渲染、表单提交、业务请求不能被统计阻塞
- 统计 SDK 不得持有关键业务依赖

## 2.3 缺能力要前置失败，不要线上失败

以下缺失应在部署前就被挡住：

- 没有 manifest
- 没有 `build/start/check` 脚本
- 没有健康检查入口
- manifest 声明要数据库，但项目没有数据库契约
- 没有统计注入入口

## 3. 复用性策略

## 3.1 模板版本化

`oneceo.manifest.json` 中必须带 `templateVersion`。

目的：

- 平台知道当前项目基于哪一版模板
- 后续新增注入能力时可以做兼容

## 3.2 平台能力尽量放到 runtime package

不把平台能力复制到每个项目里，而是尽量收口到：

- `@oneceo/app-runtime`
- 平台注入环境变量
- 平台统一 analytics API

这样升级时不需要大面积改业务代码。

## 3.3 数据库契约收敛

第一阶段只收敛一条默认数据库路径：

- Railway Postgres
- `pg` + `drizzle`

不在第一阶段同时维护 MySQL、Supabase、SQLite 多条主线。

## 4. 失败场景与处理规则

| 场景 | 处理规则 |
| --- | --- |
| 统计写入失败 | 记录错误，丢弃或重试，不影响主功能 |
| 数据库未准备好 | 前置检查失败，不进入部署 |
| 平台变量注入不完整 | 部署前拦截 |
| 模板版本过旧 | 给出升级提示，不强制自动迁移 |
| Railway 部署成功但站点不可用 | 以健康检查为准，不以“有 URL”判成功 |
| 站点可用但没有统计数据 | 页面正常，工作台显示“没有数据 / 刚接入” |

## 5. 验证链路

## 5.1 模板级验证

每次模板变更至少跑：

- `pnpm check`
- `pnpm test`
- `pnpm build`
- 本地 `pnpm start` + 健康检查

## 5.2 sandbox 内验证

在任务生成阶段，建议默认跑：

- 项目安装
- 类型检查
- 最小冒烟运行
- 核心交互测试

这和当前已有的“在 sandbox 内生成并验证应用”的思路一致。

## 5.3 平台部署验证

建议直接复用并扩展当前已有的部署 E2E 思路：

- 参考 `apps/web/e2e/task-creation-deploy-e2e.mjs`

在现有“生成 2048 -> 部署 -> 打开线上地址”的链路上，再补两类验证：

1. 访问线上地址后，健康检查正常
2. 打开页面后，能够产生一条基础 `page_view` 统计

## 5.4 工作台验证

工作台验收至少包括：

- `发布与访问` 能看到真实部署状态
- `仪表盘 / 站点数据` 能看到真实空态或真实数据
- `数据库` 能在启用时读取真实连接信息

## 6. 灰度策略

建议三阶段灰度：

### 阶段 0：文档与契约确认

- 不改代码
- 确认模板、manifest、统计模型、agent 约束

### 阶段 1：官方模板 + 运行时注入

- 只保证生成项目统一可部署
- 只保证站点基础 page view
- 站点数据页先接真实空态和基础计数

### 阶段 2：完整站点统计 + 用户统计

- 接入聚合接口
- 工作台显示真实数据
- 用户统计在启用身份的应用中可用

### 阶段 3：更复杂的数据产品能力

- 漏斗
- cohort
- 更细的业务事件分析

这些都不属于第一阶段必做项。

## 7. 第一阶段的验收标准

建议把第一阶段验收标准压到最小闭环：

1. agent 生成的网站默认基于官方模板
2. 项目默认带 manifest、健康检查、统计入口
3. 平台能自动部署
4. 工作台能展示真实部署信息
5. 工作台能展示真实站点统计空态或基础计数

## 8. 当前已知风险

### 8.1 风险：agent 仍然绕开模板直接生成

处理：

- 在生成入口强制 materialize 模板
- 在部署前做合规检查

### 8.2 风险：统计字段泛滥

处理：

- 第一阶段只允许固定事件名集合
- 自定义业务事件统一走 `business_event`

### 8.3 风险：模板升级后老项目不兼容

处理：

- 用 `templateVersion` 做兼容分流
- 不强行自动重写老项目

## 9. 当前建议的审查点

- 是否同意用“单模板 + 版本号”控制复用性。
- 是否同意把验收压到“可部署 + 可统计 + 可识别”的最小闭环。
- 是否同意分阶段推进，而不是首轮就做重型分析产品能力。
