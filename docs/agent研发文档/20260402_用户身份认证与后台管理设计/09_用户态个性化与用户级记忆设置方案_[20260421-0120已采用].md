# 09 用户态个性化与用户级记忆设置方案 [20260421-0120已采用]

更新时间：2026-04-21

## 1. 背景

当前用户态设置弹窗虽然已经有“账户 / 模型设置 / 设置 / Skills / Connectors”结构，但仍缺少一个真正面向个人上下文的入口：

1. 侧边栏左下角“设置”只能打开通用设置，不能直接进入与用户自身相关的配置
2. 用户资料目前只有 `displayName`
3. 不存在“关于你是谁、做什么、希望系统如何回应”的用户级记忆存储
4. 账户页中的资料编辑仍然是假入口，没有真实保存链路

本次改动目标不是继续堆一个假表单，而是补齐“用户态个性化”最小闭环：有独立入口、有真实存储、有前后端读写链路。

## 2. 本次目标

本次只做最短路径实现：

1. 在设置弹窗中新增独立 `个性化` 页签
2. 让侧边栏左下角“设置”入口点击后默认打开 `个性化`
3. 为用户提供 4 个用户级记忆字段：
   - 称呼偏好
   - 职业 / 角色
   - 更多关于你的信息
   - 自定义指令
4. 通过用户身份主表 `app_users` 持久化这些字段
5. 提供真实的 `/api/auth/profile` 更新接口
6. `/api/auth/me` 返回当前用户的个性化信息，前端登录态可直接消费

## 3. 明确不做的内容

本次明确不做：

1. 不新增 `app_user_profiles` 子表
2. 不做 Redis / 向量库 / 多级记忆系统
3. 不在本轮把这些字段接入 Altus / OpenCode / Codex 的系统提示词注入
4. 不改管理后台用户列表与详情结构
5. 不新增头像上传、密码修改、删除账户等能力

## 4. 数据设计

### 4.1 存储位置

直接扩展 `app_users`，新增：

1. `profile_json JSONB NOT NULL DEFAULT '{}'::jsonb`

理由：

1. 现有用户资料事实源就是 `app_users`
2. 这组字段是轻量、低频编辑、结构会继续演进的数据
3. 用 JSONB 可以避免本轮引入多列扩散和额外 profile 子表

### 4.2 profile_json 结构

```json
{
  "personalization": {
    "preferredName": "Ada",
    "role": "AI 产品经理",
    "about": "长期做 AI Agent、工作流和 B2B SaaS。",
    "responsePreferences": "先给结论，再给执行步骤。重要结论给出处。"
  }
}
```

约束：

1. 未填写字段统一返回空字符串
2. 输入值在服务端做 trim
3. `preferredName`、`role` 最大 80 字
4. `about` 最大 1000 字
5. `responsePreferences` 最大 1500 字

## 5. 接口设计

### 5.1 `/api/auth/me`

继续保留现有接口，但补充返回：

```json
{
  "user": {
    "id": "...",
    "email": "...",
    "displayName": "...",
    "status": "active",
    "personalization": {
      "preferredName": "",
      "role": "",
      "about": "",
      "responsePreferences": ""
    }
  }
}
```

### 5.2 `PATCH /api/auth/profile`

请求体：

```json
{
  "displayName": "Watson",
  "personalization": {
    "preferredName": "Watson",
    "role": "Founder",
    "about": "长期在做 AI 产品与工程系统。",
    "responsePreferences": "回答直接，不要营销语气。"
  }
}
```

规则：

1. `displayName` 可选；若传入则按现有账户名更新
2. `personalization` 可选；若传入则整体更新为服务端归一化后的对象
3. 返回最新 `user`
4. 必须要求当前登录态

## 6. 前端交互

### 6.1 入口

调整后：

1. 侧边栏左下角主按钮文案保持为 `设置`，点击后默认打开 `个性化`
2. 侧边栏设置悬浮菜单不重复放置 `个性化` 项，避免和主按钮形成重复入口
3. Header 顶部设置按钮仍可保留打开通用设置

### 6.2 个性化页结构

页面只做一个页签，不再在首屏塞太多杂项。

结构：

1. 顶部标题区
   - 标题：`个性化`
   - 副标题：说明这些信息会作为用户级记忆保存
2. 身份信息区
   - 称呼偏好
   - 职业 / 角色
3. 用户背景区
   - 更多关于你的信息
4. 回应偏好区
   - 自定义指令
5. 底部操作区
   - 重置
   - 保存

### 6.3 样式要求

虽然可参考用户给出的布局层次，但本次样式必须重新设计，不直接照抄：

1. 保留简洁的顶部标题 + 分区结构
2. 采用更克制的 neutral surface，不走整页浅灰表单堆叠
3. 通过分割线、留白和标题层级建立节奏，不做大卡片套小卡片
4. 移动端和桌面端都要保持稳定排版

## 8. 验收标准

1. 侧边栏左下角按钮文案显示为 `设置`，点击后可直接进入 `个性化`
2. 鼠标悬浮左下角设置时，浮窗中不重复出现 `个性化` 项
3. 个性化页可看到四个真实输入项
4. 保存后刷新页面，输入内容仍存在
5. `/api/auth/me` 能返回个性化字段
6. `PATCH /api/auth/profile` 能更新 `displayName` 与个性化字段
7. 中英文文案完整
8. 用户态 web type-check 与相关后端测试通过

## 9. 当前实施决定

当前采用最小落地路径：

1. `app_users.profile_json` 作为个性化字段存储容器
2. 本轮先完成“设置页 + 用户资料存储”闭环
3. 后续如要把这些字段注入任务执行提示词，再在 Altus / direct mode 文档中单独设计，不在本方案里混做
