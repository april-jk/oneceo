# 11_用户头像全链路功能设计 [20260504-0341已采用]

更新时间：2026-05-04

## 1. 目标

1. 为用户端提供完整可用的头像能力：上传、预览、替换、删除、回退默认头像。
2. 头像能力必须绑定真实 `app_users.id`，并与当前用户态认证主链一致。
3. 保证前后端行为一致：登录后所有需要展示用户身份的位置都显示统一头像。
4. 覆盖主流程与异常流程：文件不合法、上传失败、权限错误、图片失效、并发更新。
5. 支持 Google/GitHub 社交登录自动获取头像并接入同一头像主链。

## 2. 范围与边界

### 2.1 本次纳入

1. 用户端账户设置页头像模块重构。
2. 用户头像上传与存储链路（对象存储 + 元数据）。
3. 头像 URL 下发与展示统一。
4. 删除头像与恢复默认头像。
5. 基础安全校验：类型、大小、鉴权、最小可见性控制。
6. 管理端只读查看用户头像（不开放管理端代替用户上传）。
7. 社交登录头像自动同步（首登自动写入，后续按覆盖策略执行）。

### 2.2 本次不纳入

1. AI 自动抠图、美颜、滤镜等增强能力。
2. 头像内容审核系统（本期预留接口位，不实现审核平台联动）。
3. 多版本历史回滚（本期仅保留当前有效头像）。

## 3. 用户体验设计

### 3.1 入口与展示

1. 账户设置页“账户”分组内提供头像卡片区域。
2. 右上角用户菜单、首页个人信息卡、会话侧栏头像统一读取同一字段。
3. 未设置头像时显示默认占位（优先姓名首字母 + 固定背景色）。

### 3.2 交互流程

1. 点击“上传头像”打开本地文件选择器。
2. 选中文件后进入前端裁剪预览弹窗（1:1 圆形预览，输出正方形）。
3. 确认后上传，显示进度与 loading 状态。
4. 上传成功后立即刷新当前用户信息并更新全局头像显示。
5. 点击“移除头像”后回退到默认头像，并清理服务器头像引用。

### 3.3 失败反馈

1. 文件类型不支持：提示“仅支持 JPG/PNG/WebP”。
2. 文件超限：提示“图片大小不能超过 5MB”。
3. 上传失败：提示“上传失败，请重试”并保留当前头像。
4. 鉴权失效：提示“登录已过期，请重新登录”并跳转登录页。

## 4. 数据模型设计

在 `app_users` 中新增头像字段（不新增平行用户体系）：

1. `avatar_url`：当前头像可访问 URL（短期兼容字段）。
2. `avatar_storage_key`：对象存储 key（主字段）。
3. `avatar_updated_at`：头像更新时间。
4. `avatar_source`：头像来源（`manual` | `oauth_google` | `oauth_github` | `default`）。

说明：

1. 以 `avatar_storage_key` 为真实来源，`avatar_url` 可作为下游展示兼容输出。
2. 若未来切换 CDN 域名或签名 URL 策略，只需调整 URL 组装逻辑，不改业务调用方。
3. `avatar_source` 用于防止社交登录回流覆盖用户手动上传头像。

## 4.1 社交登录头像同步规则

1. Google/GitHub 首次登录建号时：
   - 若 provider 返回头像 URL，自动写入头像字段；
   - `avatar_source` 标记为对应 OAuth 来源。
2. 已有账户再次社交登录时：
   - 当 `avatar_source` 为 `oauth_google` 或 `oauth_github` 时，允许用最新 provider 头像更新；
   - 当 `avatar_source` 为 `manual` 时，禁止自动覆盖。
3. 用户手动上传头像成功后：
   - `avatar_source` 强制切换为 `manual`；
   - 后续社交登录不再自动覆盖头像。
4. 用户移除手动头像后：
   - 回退默认头像并标记 `default`；
   - 下次社交登录可再次自动写入 provider 头像。

## 5. 存储与访问策略

### 5.1 对象存储

1. 头像文件统一存入平台对象存储（沿用现有存储组件能力）。
2. key 规则建议：`app-users/{userId}/avatar/{timestamp}-{rand}.webp`
3. 统一转换或约束输出为 webp（若转换失败，保留原格式但强制白名单后缀）。

### 5.2 可访问性

1. 默认使用受控访问 URL（推荐短期签名 URL）。
2. 前端通过 `GET /api/auth/me` 或 `GET /api/auth/session` 获取可显示头像地址。
3. 头像地址失效时前端自动回退默认头像，不影响主流程。

## 6. API 设计

### 6.1 新增接口

1. `POST /api/auth/avatar/upload`
2. `DELETE /api/auth/avatar`

### 6.2 请求约束

1. 必须登录态（`app_users`）。
2. 上传使用 `multipart/form-data`，字段名统一为 `file`。
3. 后端校验：
   - MIME：`image/jpeg`, `image/png`, `image/webp`
   - 大小：<= 5MB
   - 文件名与扩展名安全清洗

### 6.3 返回结构

统一复用现有 auth envelope：

1. 上传成功返回：
   - `user.avatarUrl`
   - `user.avatarUpdatedAt`
2. 删除成功返回：
   - `user.avatarUrl = null`

## 7. 鉴权与安全设计

1. 头像上传/删除只允许当前登录用户操作自己的头像。
2. 严禁通过 `userId` 参数越权操作，用户身份仅取服务端 session。
3. 上传前后记录审计日志（用户ID、时间、结果、失败原因，不记录原图内容）。
4. 对上传接口做基础频控（例如每分钟最多 10 次）。
5. 头像 URL 仅暴露必要信息，不泄露内部存储桶敏感结构。

## 8. 前端改造点

1. `AuthContext`：补充头像刷新能力（上传/删除后统一刷新 `user`）。
2. 账户设置页：新增头像上传组件与裁剪弹窗。
3. 用户菜单与全局用户展示组件：统一读取 `user.avatarUrl`。
4. i18n 文案补充：
   - 上传头像
   - 更换头像
   - 移除头像
   - 上传失败/格式不支持/大小超限

## 9. 后端改造点

1. `auth-routes` 增加头像上传与删除路由。
2. `appUserDAO` 增加头像字段更新方法。
3. `schema.ts` 与迁移脚本补充头像字段。
4. 存储服务层新增“用户头像上传”能力（复用现有对象存储客户端）。
5. `auth-service` 的用户返回 DTO 补充 `avatarUrl` 字段。
6. 社交登录服务（Google/GitHub）补充头像同步策略：
   - 读取 provider 返回头像 URL；
   - 按 `avatar_source` 决策是否更新。

## 10. 兼容与迁移策略

1. 老用户无头像字段时默认 `null`，前端显示默认头像。
2. 数据库迁移采用 `ADD COLUMN IF NOT EXISTS`，不阻塞现网。
3. 前端灰度时允许 `avatarUrl` 缺失，页面不报错。

## 11. 测试与验收

### 11.1 API 单测

1. 未登录上传头像返回 401。
2. 非图片类型返回 400。
3. 超过 5MB 返回 400。
4. 上传成功后 `app_users` 头像字段更新。
5. 删除头像后字段清空。
6. 社交登录首登时自动写入头像。
7. `avatar_source=manual` 时社交登录不覆盖头像。
8. `avatar_source=oauth_*` 时社交登录可更新头像。

### 11.2 前端交互测试

1. 上传成功后全局头像即时刷新。
2. 上传失败不覆盖旧头像。
3. 删除头像回退占位头像。
4. 不同页面头像展示一致。

### 11.3 回归关注

1. 不能影响现有登录、注册、社交登录链路。
2. 不能影响 `GET /api/auth/session` 的稳定性与响应时间。

## 12. 风险与决策

1. 风险：对象存储异常导致头像上传失败。
   - 策略：上传失败只影响头像操作，不影响账户主流程。
2. 风险：大图上传导致接口压力。
   - 策略：前后端双重大小限制 + 基础频控。
3. 风险：CDN 或签名 URL 失效导致头像间歇不可见。
   - 策略：前端默认头像兜底 + 后端刷新 URL 策略预留。

## 13. 实施拆分建议

1. 第一步：数据模型 + API 基础上传/删除（无裁剪）。
2. 第二步：前端裁剪与全局展示统一。
3. 第三步：频控、审计日志、错误码与文案细化。

## 14. 采用前确认清单

1. 是否确认头像最大 5MB。
2. 是否确认支持格式仅 JPG/PNG/WebP。
3. 是否确认本期不做内容审核平台联动。
4. 是否确认管理端仅只读展示，不可代用户编辑头像。
