# 多用户与 Redis 稳定性、回放与恢复测试方案 [20260403-1308已采用]

## 目标

在 `#9 ~ #13` 已完成的基础上，给 oneceo 当前主线补一份统一验收方案，覆盖：

1. 多用户隔离稳定性
2. Redis 热层与事件流稳定性
3. SSE / stream 回放正确性
4. Altus / session runtime / connector 的恢复正确性
5. 与 `#7` 的衔接边界

这份方案只定义“怎么测、测什么、通过标准是什么”，不新增业务功能，不引入新的恢复框架，也不扩成独立测试平台。

## 当前主线事实

基于当前已经落地和已验证的内容：

1. `#9`
   - `userId` 是授权主键
   - `tenantKey` 只做命名空间
   - `sessionId` 是会话和运行态隔离锚点
2. `#10`
   - Redis key / stream / TTL 规范已存在
3. `#11`
   - `workspace dir/tree/file`
   - `messages/recent`
   - `messages/history cursor`
   - `session-events stream`
   已接入 Redis 热层 / 回放链路
4. `#12`
   - Altus run `state / owner / heartbeat / stop / recovery / active-runs / run stream`
   已接入 Redis，并有 DB-first 恢复链路
5. `#13`
   - connector / guide / session runtime 的多用户隔离已做独立联调

所以 `#14` 不再重复发明新的对象模型，而是把这些已存在链路系统化验收。

## 非目标

本次不做：

1. 新增新的 Redis keyspace
2. 新增全局 chaos framework
3. 新增统一测试调度平台
4. 引入兼容模式、降级分支或额外兜底逻辑
5. 把旧 KVM 历史链路拉回当前主线

## 核心原则

1. 只测当前真实主线，不测已停用或未接入链路
2. 每条测试必须同时给出接口结果、DB 证据、Redis 证据
3. 任何 Redis / SSE / 恢复测试都必须有“故障前 -> 触发 -> 故障后 -> 恢复后”闭环
4. 判定必须以底层状态为准，不能只看 HTTP 200 或前端显示正常
5. 测试方案优先最短路径，不引入过度工程化工具链

## 测试范围

### 1. 多用户隔离稳定性

目标：

1. 用户 A 的会话、run、workspace、connector binding、guide 投影不能被用户 B 污染
2. 高并发下 Redis key 命名仍保持 `tenant -> session -> run` 隔离

覆盖对象：

1. `task-creation`
   - session detail
   - messages recent/history
   - workspace dir/tree/file
   - opencode/events
2. `altus-managed`
   - runs
   - latest run
   - run stream
   - stop
3. connector / guide / session runtime
   - attach / detach
   - guide projection
   - recovery

### 2. Redis 稳定性

目标：

1. Redis 可用时，热层命中正确
2. Redis 不可用或超时时，不破坏 DB facts，不引入跨用户脏状态
3. Redis 恢复后，链路可重新建立热状态

覆盖对象：

1. session cache
   - `cache:workspace:*`
   - `cache:messages:recent`
   - `cursor:history`
   - `stream:session-events`
2. run state
   - `run:state`
   - `run:owner`
   - `run:heartbeat`
   - `run:stop`
   - `run:recovery`
   - `ops:runs:active`
   - `run:stream`

### 3. 回放测试

目标：

1. SSE 断开后，客户端可从 Redis stream / DB fallback 正确补回事件
2. 不丢事件、不串事件、不重复注入跨用户内容

覆盖对象：

1. `task-creation` session events replay
2. `altus-managed` run stream replay
3. history cursor + recent window 协同

### 4. 恢复测试

目标：

1. DB facts 与 Redis hot state 一致
2. Redis 缺失时，能按 DB rebuild
3. terminal cleanup 后，不残留错误 live state
4. session runtime / connector recovery 永远回到 session owner

覆盖对象：

1. Altus run recovery
2. session MCP / connector runtime recovery
3. sandbox replace / runtime not ready / delayed recover

### 5. 与 `#7` 的衔接

`#7` 的 connector guide 测试补齐要建立在 `#14` 之上：

1. `#14` 先给出统一测试矩阵和证据口径
2. `#7` 再在这个口径内补 connector guide 的更细化场景
3. `#7` 不重复定义 Redis / DB / replay 的基础验收方法

## 验收矩阵

### 1. 多用户并发隔离矩阵

#### 1.1 task-creation

1. 用户 A / B 并发访问 `messages/recent`
   - 预期：只命中各自 `tenantKey + sessionId` 下的 recent cache
   - DB：`task_creation_sessions.user_id` 正确
   - Redis：`cache:messages:recent` 不串用户

2. 用户 A / B 并发访问 `workspace/tree`
   - 预期：只返回各自 session workspace
   - DB：session owner 正确
   - Redis：`cache:workspace:tree:*` 不串用户

3. 用户 A / B 并发重连 `opencode/events`
   - 预期：Redis replay / DB fallback 只回放各自 session event
   - Redis：`stream:session-events` 不串 session

#### 1.2 altus-managed

1. 用户 A / B 并发启动 run
   - 预期：`run:state / run:recovery / run:stream` 按各自 runId 隔离
   - DB：`task_session_runs.session_id`、session owner 正确
   - Redis：`run:*` 和 `ops:runs:active` 不串 tenant

2. 用户 A / B 并发 stop / latest-run / stream subscribe
   - 预期：不能跨 run 操作
   - Redis：stop flag、stream replay 只落本 run

#### 1.3 connector / guide / runtime

1. attach / detach / recovery
   - 预期：不能使用 foreign profile，不能污染 foreign session
   - DB：`task_session_connector_bindings.profile_id / task_session_id` 归属正确
   - Redis：当前链路无直接 Redis 状态时，必须验证 Redis key 数无新增副作用

### 2. Redis 不稳定矩阵

#### 2.1 Redis 不可用

1. `task-creation` 读取 recent / workspace / history cursor
   - 预期：回退 DB / 原有事实路径，不返回脏数据
2. `altus-managed` 写入 run state / stream
   - 预期：DB facts 仍成功；Redis 写入失败不回滚 DB

#### 2.2 Redis 暂时清空

1. 删除 `run:state / run:recovery`
   - 预期：`latest run` 可按 DB 重建
2. 删除 `stream:session-events / run:stream`
   - 预期：重连时回退 DB replay

### 3. 回放矩阵

#### 3.1 session events

1. Redis stream 有历史
   - 预期：优先 Redis replay
2. Redis stream 为空
   - 预期：回退 DB replay
3. cursor 使用 `sessionEventSeq`
   - 预期：不漏 `status_update`

#### 3.2 run stream

1. Redis run stream 有历史
   - 预期：优先 Redis
2. Redis run stream 为空
   - 预期：回退 DB
3. terminal 后重新订阅
   - 预期：能看到终态，不出现悬挂 processing

### 4. 恢复矩阵

#### 4.1 Altus run recovery

1. 启动后删 `run:state / run:recovery`
   - 预期：`runs/latest` 重建热状态
2. 终态后检查 cleanup
   - 预期：`run:stop / run:recovery / owner / heartbeat / active-runs` 清理正确

#### 4.2 connector runtime recovery

1. sandbox not ready 时 attach
   - 预期：binding 进入 `pending_recover`
2. `reconcileByOrchestratorSessionId`
   - 预期：按 session owner 恢复
3. foreign profile 脏 binding
   - 预期：进入 `failed`
