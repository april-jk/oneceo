## 1. 文档目标

为 oneceo 定义一套能直接支撑 `#11` 与 `#12` 的 Redis 规范，范围只覆盖当前主线真正需要的对象：

1. session 级热缓存
2. session / run 两级事件流
3. Altus run 的协调状态
4. 幂等与恢复辅助键

本文只做边界收口，不提前承诺复杂基础设施实现，避免把 `#10` 扩成独立平台工程。

## 2. 当前平台需求与范围

`#8` 的目标是先补齐“多用户 + Redis”主线，作为 connector guide / MCP 稳定化的前置条件。结合当前代码现状，`#10` 只需要为以下改造提供统一口径：

1. `workspace dir/tree/file` 缓存迁移到 Redis
2. `recent/history` 与页面恢复的短窗口热数据迁移到 Redis
3. `task session` 和 `Altus managed run` 的实时事件流迁移到 Redis
4. `Altus run` 的 owner / heartbeat / stop / recovery 迁移到 Redis

本阶段明确不纳入：

1. `user_context`、`kb_context`、`project_meta` 这类平台级上下文缓存
2. `tool guide`、`MCP toolkit`、`runtime-config` 的 Redis 共享缓存
3. “general pool / stream pool 分离” 作为强制前置条件
4. `StreamHub`、pool stats、hub stats、startup cleanup 等完整 Redis 基础设施工程
5. 独立 dead-letter 系统

这些内容可以作为后续优化候选，但不属于当前平台主线的最短路径。

## 3. 继承自 #9 的约束

本规范直接继承 `#9` 已采用结论：

1. `userId` 是授权主键
2. `tenantKey` 只做命名空间，不做授权主键
3. `sessionId` 是业务隔离锚点
4. `runId / orchestratorSessionId / executorSessionId` 都是 `sessionId` 的下游运行态键

因此 Redis 中禁止：

1. 只带 `tenantKey`、不带 `sessionId` 的会话态 key
2. 只按 `runId` 或 `orchestratorSessionId` 建运行态 key，却没有 `sessionId` 回链
3. `default` 这类匿名命名空间
4. 用 `tenantKey` 临时替代 `userId`

## 4. 命名规则

### 4.1 顶层前缀

统一前缀：

```txt
oneceo:v1:
```

规则：

1. `oneceo` 是产品级命名空间
2. `v1` 是 Redis 结构版本
3. 若未来 key 结构有破坏性变更，只能升级版本前缀，不能在原 key 上混改

### 4.2 层级顺序

session 相关对象统一使用：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:{domain...}
```

仅当对象天然属于用户、且还未进入 session 级时，才允许：

```txt
oneceo:v1:tenant:{tenantKey}:user:{userId}:{domain...}
```

禁止：

```txt
oneceo:v1:user:{userId}:session:{sessionId}
oneceo:v1:session:{sessionId}
oneceo:v1:tenant:default:...
```

### 4.3 命名细则

1. key 片段统一使用小写英文
2. 路径、查询条件、自由文本一律先哈希，不直接拼进 key
3. `tenantKey / userId / sessionId / runId` 保持原值
4. 哈希建议统一使用短 `sha1` 或短 `sha256`

## 5. 当前阶段必须定义的 key

### 5.1 用户级键

当前阶段只保留用户级幂等键，不额外引入新的用户级 Redis 模型。

推荐格式：

```txt
oneceo:v1:tenant:{tenantKey}:user:{userId}:idempotency:{operation}:{requestHash}
```

适用范围：

1. 首条消息触发建 session
2. 用户触发的重复提交防抖
3. connector attach / detach 这类需要防重入的写操作

### 5.2 session 级缓存键

推荐格式：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:workspace:dir:{pathHash}
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:workspace:tree:{pathHash}
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:workspace:file:{pathHash}
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cache:messages:recent
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:cursor:history
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:projection:connectors
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:projection:runtime
```

规则：

1. `workspace` 自由路径必须哈希
2. `recent` 只存短窗口热数据，不替代 DB 历史
3. `history cursor` 只做恢复辅助，不承担事实存储
4. `projection:*` 只保存投影，不替代 DB 主记录

### 5.3 run 协调键

推荐格式：

```txt
oneceo:v1:tenant:{tenantKey}:ops:runs:active
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:state
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:owner
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:heartbeat
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:stop
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:recovery
```

规则：

1. `ops:runs:active` 只记录活跃 `runId` 集合
2. `state` 存 run 当前快照，例如 `status / sequence / updatedAt`
3. `owner` 独立成键，不混入 `state`
4. `heartbeat` 只用于存活判断
5. `stop` 必须跨进程、跨重启可见
6. `recovery` 只保存恢复所需最小元数据，不堆大对象

当前阶段不额外拆 `started-at`、`status` 等单独键，避免把 run 状态模型拆散。

## 6. 当前阶段必须定义的 stream

### 6.1 session 级语义流

推荐格式：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:stream:session-events
```

用途：

1. task-creation 会话语义事件
2. 页面恢复时的短窗口回放
3. 多订阅者共享读取

### 6.2 run 级执行流

推荐格式：

```txt
oneceo:v1:tenant:{tenantKey}:session:{sessionId}:run:{runId}:stream
```

用途：

1. Altus managed run 事件
2. run 处理中状态、结果、错误、完成事件
3. SSE 恢复与断线续播

### 6.3 当前阶段不再定义第三类强制 stream

`executor raw stream`、`tool output raw stream` 等更细粒度流，当前阶段不纳入统一强制规范。

原因：

1. `#10` 先收敛 `session-events` 和 `run stream` 这两条主线即可支撑 `#11/#12`
2. OpenCode/Codex 原始事件如果需要进入 Redis，应在 `#11` 中作为内部投影写入现有两级流，而不是在 `#10` 先扩出第三套公共命名

## 7. TTL 与保留策略

### 7.1 TTL 原则

1. session 热缓存短 TTL
2. run 协调键中 TTL
3. 幂等与恢复键中长 TTL
4. stream 同时使用 `MAXLEN` 与 key TTL

### 7.2 推荐 TTL 表

| 对象 | 推荐 TTL | 说明 |
|---|---:|---|
| `workspace dir/tree/file` cache | 120 秒 | 高频读缓存，允许短期失效重建 |
| `messages:recent` | 600 秒 | 刷新与短时恢复使用 |
| `cursor:history` | 1800 秒 | 分页/恢复辅助键 |
| `projection:connectors` / `projection:runtime` | 1800 秒 | DB 为主，Redis 为恢复加速 |
| 用户级 `idempotency` | 24 小时 | 防重复提交 |
| `run:{runId}:state` | 24 小时 | 支持 run 完成后的短期恢复 |
| `run:{runId}:owner` | 30 秒，需续租 | worker owner 锁 |
| `run:{runId}:heartbeat` | 60 秒，需续写 | 僵尸 run 检测 |
| `run:{runId}:stop` | 24 小时 | stop 信号需跨重启保留 |
| `run:{runId}:recovery` | 72 小时 | 断线恢复与补偿使用 |
| `session-events` stream | 72 小时 | 配合 trim 保留短期回放窗口 |
| `run stream` | 72 小时 | 支持 run 恢复和 SSE 补拉 |

### 7.3 stream trim 规则

1. `session-events`：建议 `MAXLEN ~ 5000`
2. `run stream`：建议 `MAXLEN ~ 2000`

说明：

1. Redis 只保短窗口回放
2. 长期历史仍以 DB 为准
3. 不允许只 trim 不设 TTL，也不允许只设 TTL 不 trim

## 8. 恢复与事件字段规范

### 8.1 恢复原则

1. 先查 `run:{runId}:state`
2. 再按 `afterSequence` 从 `run stream` 或 `session-events` 补拉
3. Redis 无法完成恢复时，再回退 DB

这意味着：

1. Redis 是第一恢复面
2. DB 是最终补偿面
3. Redis 不能只负责实时推送，必须支持短窗口回放

### 8.2 SSE / WebSocket 续播要求

所有实时订阅必须支持：

1. `afterSequence`
2. `lastEventId`
3. 先补历史，再进入 live

### 8.3 统一事件字段

所有写入 Redis stream 的事件都必须带：

1. `tenantKey`
2. `userId`
3. `sessionId`
4. `runId`（如有）
5. `eventId`
6. `eventType`
7. `sequence`
8. `producedAt`
9. `producer`

规则：

1. `eventId` 用于去重
2. `sequence` 只在 `session` 或 `run` 作用域内单调递增
3. 前端续播按 `sequence`，重复写保护按 `eventId`

### 8.4 当前阶段不引入独立 dead-letter

当前平台主线还没进入多 worker 的复杂事件补偿阶段，`#10` 不要求先建独立 dead-letter 流。

本阶段规则是：

1. 写 stream 失败时必须明确失败，不静默吞掉
2. 错误必须带 `tenantKey / sessionId / runId / eventId`
3. 是否需要独立 `ops:dead-letter:*`，等 `#12` 落地后再根据真实失败面决定

## 9. 参照 Suna 后的取舍

### 9.1 本阶段直接采用的部分

参照 `referance/suna`，当前 oneceo 应直接吸收：

1. run 级 stream 作为 SSE 与恢复的统一事件源
2. `active runs + owner + heartbeat + stop` 这套最小 run 协调键
3. 热缓存短 TTL，长期历史回 DB

### 9.2 本阶段明确不跟进的部分

`Suna` 还把很多平台级对象放进 Redis，但 oneceo 当前阶段不应一并照搬：

1. `user_context`、`kb_context`、`project_meta`
2. `tool_guide`、`mcp_tools`、agent config 系列缓存
3. 强制 general pool / stream pool 双连接池
4. 强制 `StreamHub`
5. 强制 pool stats / hub stats / startup cleanup / zombie cleanup 脚本

原因：

1. 这些能力并不是 `#8` 当前主线的必需项
2. 现在直接纳入，只会放大实现面和验证面
3. 等 `#11/#12/#14` 落地后，如果出现真实瓶颈，再单独补最合适

## 13. 当前代码已落 Redis 的位置清单

截至 2026-04-03，当前代码里真正已经落到 Redis 的位置只有一组，集中在 Altus managed run：

1. run 状态快照
路径：`apps/api/src/services/altus-run-redis-state-service.ts`
键：`run:{runId}:state`
用途：保存 `status / sequence / model / updatedAt` 等热状态

2. run owner 锁
路径：`apps/api/src/services/altus-run-redis-state-service.ts`
键：`run:{runId}:owner`
用途：保存当前 worker / instance 占有者

3. run heartbeat
路径：`apps/api/src/services/altus-run-redis-state-service.ts`、`apps/api/src/services/altus-managed-run-entry-service.ts`
键：`run:{runId}:heartbeat`
用途：保存运行中心跳时间

4. 活跃 run 集合
路径：`apps/api/src/services/altus-run-redis-state-service.ts`
键：`ops:runs:active`
用途：保存当前 tenant 下活跃 `runId`

5. stop 信号
路径：`apps/api/src/services/altus-run-redis-state-service.ts`、`apps/api/src/services/altus-managed-run-entry-service.ts`
键：`run:{runId}:stop`
用途：保存用户发出的停止请求

6. run stream
路径：`apps/api/src/services/altus-run-event-writer.ts`、`apps/api/src/services/altus-run-redis-state-service.ts`
键：`run:{runId}:stream`
用途：保存 run 级短窗口事件流，供 SSE 恢复优先读取

7. run stream 读取优先级
路径：`apps/api/src/services/altus-managed-stream-service.ts`
读取顺序：先 Redis `run stream`，若 Redis 无历史，再回退 DB `task_session_run_events`

当前还没有真正落 Redis 的位置：

1. `workspace dir/tree/file` cache
2. `recent/history`
3. `session-events`
4. `projection:connectors`
5. `projection:runtime`

这些仍属于 `#11` 后续实现范围，不能误判为“已完成 Redis 化”。
