# 20260502 会员与Agent权益管理设计 [尚未采用]

## 1. 背景

当前 oneceo 已有积分计费与管理后台计费能力，但还没有“会员类型”这一层可管理的产品抽象。现在需要补一层平台级会员体系，用来统一管理：

1. 会员类型与默认积分
2. 会员可使用的 Agent 等级
3. 会员权益范围与后续扩展项
4. 管理后台的会员配置与分配能力

这套能力的目标不是单纯卖会员，而是让平台的“产品套餐”和“Agent 能力开放”有一个可治理、可审计、可扩展的中台。

## 2. 目标

### 2.1 必须实现

1. 管理后台新增「会员管理」页面
2. 支持创建、编辑、停用会员类型
3. 支持为会员类型配置默认积分
4. 支持为会员类型配置可用 Agent 等级
5. 支持为会员类型配置通用权益项
6. 支持将会员类型分配给用户
7. 用户侧能够感知当前会员等级与可用 Agent 范围

### 2.2 本次不做

1. 不做支付购买链路
2. 不做自动续费
3. 不做订单系统
4. 不做优惠券与促销中心
5. 不做复杂的按时长/并发/调用次数混合套餐计费

## 3. 核心原则

1. **会员是权限与权益层，不是账务层**：积分继续归积分体系管理，会员只定义“默认赠送多少积分”和“可用什么能力”。
2. **Agent 权限必须可配置**：普通用户默认只可用 `Agent lite`，付费会员可开放 `Agent pro`、`Agent max` 等更高等级能力。
3. **默认值要可审计**：会员类型的默认积分、Agent 范围、有效期规则都要在后台可见、可追踪。
4. **能力开放要向下兼容**：新会员类型上线后，不应影响已有用户的当前可用能力，除非管理员主动调整归属。
5. **前端只负责展示与拦截，服务端负责最终判定**：任何 Agent 选择和调用权限都必须以后端校验为准。

## 4. 角色与场景

### 4.1 普通用户

能力：

1. 查看当前会员类型
2. 查看会员权益与可用 Agent 范围
3. 查看会员默认积分是否已发放
4. 在可用范围内选择 Agent

限制：

1. 不能使用未授权的高等级 Agent
2. 不能自助变更会员类型

### 4.2 平台管理员

能力：

1. 创建和维护会员类型
2. 设定会员默认积分
3. 配置会员可用 Agent 等级
4. 配置会员权益文案与规则
5. 将会员类型分配给用户
6. 手动调整某个用户的会员归属与生效时间
7. 查看会员分布与权益使用情况

## 5. 会员模型定义

### 5.1 会员类型

会员类型是平台定义的套餐模板，例如：

1. `free`：免费用户
2. `pro`：付费专业版
3. `max`：高阶旗舰版
4. `team`：团队版（后续可扩展）

每个会员类型至少包含：

- `code`：唯一标识
- `name`：展示名称
- `status`：启用/停用
- `defaultCredits`：默认赠送积分
- `allowedAgentLevels`：可使用的 Agent 等级列表
- `benefitItems`：权益项集合
- `sortOrder`：前台/后台展示顺序
- `description`：说明文本

### 5.2 Agent 等级

Agent 等级用于控制可用能力边界，建议先统一抽象为三档：

1. `lite`
2. `pro`
3. `max`

规则：

- 免费会员默认仅开放 `lite`
- 付费会员可开放 `pro` 或 `max`
- 后端必须在任务创建、会话发起和 Agent 切换时校验该权限

### 5.3 权益项

权益项用于承载除 Agent 等级以外的能力描述，例如：

1. 默认积分赠送
2. 更高的模型额度或更高的默认上限
3. 更快的任务排队优先级
4. 更长的会话上下文保留时长
5. 更高的并发任务上限
6. 专属功能开关

本次建议先以“结构化 key + 文案”方式实现，不做过度复杂的权益引擎。

## 7. 权限规则

### 7.1 Agent 可用性

规则优先级建议如下：

1. 用户当前会员类型决定可用 Agent 上限
2. 如果用户被单独授予更高权限，可作为例外覆盖，但必须记录审计
3. Agent 页面只展示当前可选项，不能让用户绕过前端限制直接调用
4. API 最终返回必须以服务端校验结果为准

### 7.2 默认积分发放

当用户首次绑定某个会员类型时：

1. 若会员类型配置 `defaultCredits > 0`，系统发放对应积分
2. 发放动作必须进入积分交易记录，不能只改会员表
3. 如果同一用户重复分配同一会员类型，不应重复赠送，除非管理员明确发起“补发”动作

### 7.3 过期与回收

会员到期后建议采用：

1. 自动降级回 `free`
2. 已发放积分不回收
3. 已创建任务不强制中断
4. 新任务按降级后的权限重新校验

## 8. 管理后台设计

### 8.1 导航入口

在管理后台新增独立的「会员管理」导航组或在「平台配置」下新增子项：

- 会员类型管理
- 用户会员分配
- 权益配置预览
- Agent 权限矩阵

### 8.2 页面结构

建议页面分为四个 Tab：

1. **会员类型**：查看、创建、编辑、停用会员类型
2. **用户会员**：查看用户当前会员、手动变更归属、设置到期时间
3. **权益矩阵**：展示不同会员可用 Agent 与其他权益
4. **变更记录**：查看会员类型与用户会员的调整历史

### 8.3 会员类型编辑器

编辑器应包含：

- 名称与 code
- 状态
- 默认积分
- 可用 Agent 等级多选
- 权益项编辑器
- 排序
- 生效时间
- 说明

### 8.4 用户会员分配

用户详情页建议增加会员信息区：

- 当前会员类型
- 到期时间
- 可用 Agent
- 默认积分发放状态
- 手动变更按钮

## 9. 用户侧展示

用户侧至少需要展示：

1. 当前会员类型
2. 可用 Agent 列表
3. 会员剩余有效期
4. 默认权益说明
5. 若无权限，则明确说明“当前会员不可使用该 Agent”

推荐放置位置：

- 任务创建页的 Agent 选择器
- 账户/设置页的会员卡片
- 必要时在会话页做权限提示

## 10. 与积分系统的关系

这套会员体系要和现有积分体系解耦但联动：

1. 会员定义“默认送多少积分”
2. 积分体系负责余额、交易、消费记录
3. 会员升级/变更时可以触发积分赠送，但交易仍归积分表管理
4. 会员权限不等于积分余额，二者要分开判断

## 11. 风险与约束

1. **权限漂移风险**：前端展示和后端校验不一致会导致越权，必须以后端为准。
2. **会员与积分耦合过深**：如果把会员当余额表，会很难扩展套餐与权益，建议保持两层模型。
3. **过度复杂的权益引擎**：第一版只做结构化配置，不做规则 DSL。
4. **历史归属追溯**：会员变更要保留操作记录，否则后续审计困难。
5. **Agent 等级定义不稳定**：等级名称先固定为 `lite/pro/max`，后续如果扩展，只能通过映射层兼容。

## 12. 本次设计结论

这套方案建议采用“会员类型 + 用户会员归属 + 权益矩阵 + 服务端校验”的最小闭环：

1. 管理后台先能维护会员类型
2. 用户可以被分配到具体会员类型
3. 会员类型决定默认积分和 Agent 权限
4. 前后端共同拦截 Agent 越权
5. 会员与积分保持独立账本
