# 02 Altus三级记忆数据模型与存储方案 [20260421-1629已采用]

更新时间：2026-04-21

---

## 1. 目标

本文件只回答一件事：三级记忆分别存在哪里，字段是什么，长度如何控制。

---

## 2. 用户级记忆

## 2.1 真相源

`app_users.profile_json.personalization`

## 2.1.1 Redis 加速

用户级记忆允许增加 Redis 读缓存，但规则必须收紧为：

1. DB 仍然是唯一真相源
2. Redis 只缓存归一化后的用户级记忆快照
3. 写入流程始终先写 DB，再刷新或失效 Redis
4. Redis 不可用时直接回退 DB，不影响主链

## 2.2 建议结构

```json
{
  "preferredName": "",
  "occupation": "",
  "identity": "",
  "location": "",
  "background": "",
  "preferences": "",
  "responsePreferences": ""
}
```

## 2.3 字段说明

1. `preferredName`
   - 用户昵称 / 希望如何称呼
2. `occupation`
   - 职业
3. `identity`
   - 身份，例如创业者、产品负责人、律师、教师
4. `location`
   - 所在地
5. `background`
   - 更完整的个人背景
6. `preferences`
   - 一般性偏好，例如语言、表达结构、信息呈现方式
7. `responsePreferences`
   - 对 Altus 回应方式的明确要求

## 2.4 兼容策略

当前已有旧字段：

1. `role`
2. `about`

首版策略：

1. 读取时兼容：
   - `role -> occupation`
   - `about -> background`
2. 写入时统一写新字段
3. 不做离线批量回填

## 2.5 长度约束

1. `preferredName`：80
2. `occupation`：80
3. `identity`：80
4. `location`：120
5. `background`：1000
6. `preferences`：800
7. `responsePreferences`：1500

规则：

1. 服务端统一 trim
2. 超长直接报错，不做静默截断
3. 空字符串允许

## 3. 项目级记忆

## 3.1 真相源

`app_user_projects.metadata_json.altusProjectMemory`

## 3.1.1 Redis 加速

项目级记忆允许增加 Redis 读缓存，但规则与用户级一致：

1. DB 仍然是唯一真相源
2. Redis 只缓存归一化后的项目级记忆快照
3. 写入流程始终先写 DB，再刷新或失效 Redis
4. Redis 不可用时直接回退 DB，不影响主链

## 3.2 建议结构

```json
{
  "context": "",
  "guidelines": "",
  "operatingRules": "",
  "executionManual": "",
  "updatedAt": ""
}
```

## 3.3 字段说明

1. `context`
   - 项目背景
2. `guidelines`
   - 项目指引
3. `operatingRules`
   - 操作规范
4. `executionManual`
   - 执行手册

## 3.4 与现有项目字段关系

1. `name`
2. `description`

仍然保留原义：

1. `description` 用于项目列表的简述
2. `altusProjectMemory` 才是 Altus 运行时项目记忆

## 3.5 metadata_json 更新规则

项目级记忆写入时，必须按 merge 更新 `metadata_json`，不允许整块覆盖。

原因：

1. 当前 `metadata_json` 已承载 `pinned` 等现有字段
2. `altusProjectMemory` 只是 `metadata_json` 下的一个子键
3. 如果整块覆盖，现有项目能力会被误删

因此首版要求：

1. 保留已有非 Altus key
2. 仅更新 `metadata_json.altusProjectMemory`
3. `altusProjectMemory.updatedAt` 由服务端生成

## 3.6 长度约束

1. `context`：2000
2. `guidelines`：2000
3. `operatingRules`：2000
4. `executionManual`：3000

规则：

1. 服务端统一 trim
2. 超长直接报错
3. 空值允许

## 4. session 级记忆

## 4.1 真相源

`task_creation_sessions.metadata_json.altusSessionMemory`

补充说明：

1. session 与项目归属的真相源是 `task_creation_sessions.project_id`
2. session 上的 `projectName` 只是展示缓存，不是归属真相源
3. 项目改名时，需要同步刷新 session 的 `projectName`

## 4.2 Redis

仅在显式启用 Redis 时缓存 session memory 快照。

规则：

1. 读取时先查 Redis，未命中或 Redis 异常时回退 DB
2. 写入时不直接写 Redis 真相，仍然以 DB 写入为准
3. DB 写入成功后，再刷新 Redis 快照
4. run 进行中不依赖反复读取 DB / Redis

## 4.3 sandbox 文件

` .oneceo/session-memory/altus-memory.json `

这是 session 运行态副本，不是持久化真相源。

## 4.4 建议结构

```json
{
  "version": 1,
  "summary": {
    "goal": "",
    "latestOutcome": "",
    "openQuestions": []
  },
  "constraints": [],
  "decisions": [],
  "workingNotes": [],
  "sandboxMaterialization": {
    "snapshotVersion": 1,
    "lastSandboxId": null,
    "lastSyncedAt": null
  },
  "fileMemorySnapshot": {
    "snapshotVersion": 1,
    "savedAt": null,
    "sourceSandboxId": null,
    "archiveId": null,
    "workspaceMemoryPath": ".oneceo/session-memory/altus-memory.json"
  },
  "updatedAt": null,
  "lastWriterRunId": null
}
```

## 4.5 字段定位

1. `version`
   - service 内部修订号，单调递增
   - 仅用于有效运行判定、调试和摘要演进，不承担分布式冲突控制职责
2. `summary`
   - 当前会话核心摘要
3. `constraints`
   - 当前会话确认的约束
4. `decisions`
   - 当前会话确认的决定
5. `workingNotes`
   - 当前会话运行态工作记录
6. `fileMemorySnapshot.snapshotVersion`
   - sandbox 文件当前本地版本
7. `lastWriterRunId`
   - 最近一次成功写入 DB 的 run 标识

## 4.6 不存什么

1. 全量消息历史
2. 项目级全文副本
3. 用户级全文副本
4. 大体积原始工具日志
5. 项目归属真相源

## 4.7 长度与数量约束

1. `summary.goal`：500
2. `summary.latestOutcome`：1000
3. `summary.openQuestions`：最多 8 条，每条 300
4. `constraints`：最多 12 条，每条 300
5. `decisions`：最多 12 条，每条 300
6. `workingNotes`：最多 20 条，每条 300

规则：

1. 统一由 `task-session-altus-memory-service` 归一化
2. 老记录采用“保留最近有效项”的方式淘汰
3. sandbox 回写时也走同一 normalize 逻辑

## 5. session 文件回写策略

这部分首版明确对齐 skills memory 的实现风格，不再单独设计更重的版本竞争协议。

## 5.1 run / materialization 时

1. 由 `task-session-altus-memory-service` 先查 Redis
2. Redis 未命中或异常时，再读 DB 当前 `altusSessionMemory`
3. 读到的 session memory 在 run 启动时一次性装入运行态
4. 由 `task-session-altus-memory-service` 生成 sandbox 文件
5. 文件里只维护 `snapshotVersion`、`lastSandboxId`、`lastSyncedAt` 等运行态信息

## 5.2 运行时更新

1. sandbox 内可以更新本地 `snapshotVersion`
2. 本地更新不直接改 DB
3. 和 skills memory 一样，运行中的细粒度变化先留在 sandbox 文件
4. run 中需要读取 session memory 时，优先使用当前运行态内存快照，不重复打 DB

## 5.3 flush 回 DB 时

受控 flush 点读取 sandbox 文件并统一走 normalize 后写回 DB：

1. waiting_user
2. completed
3. failed
4. archive 前
5. restore 后

写回流程固定为：

1. 读取 sandbox 文件
2. 走 normalize
3. 一次性写 DB metadata
4. DB 成功后刷新 Redis

写回后同步更新：

1. `fileMemorySnapshot.snapshotVersion`
2. `fileMemorySnapshot.savedAt`
3. `fileMemorySnapshot.sourceSandboxId`
4. `fileMemorySnapshot.archiveId`

## 5.4 缺失或异常文件时

1. sandbox 文件不存在时，保留 DB 当前值
2. sandbox 文件无效时，保留 DB 当前值
3. 下一个 materialization 点重新由 DB 重建 sandbox 文件

## 5.5 首版不新增的复杂机制

1. 不新增 `baseVersion`
2. 不新增 compare-and-set 协议
3. 不新增额外冲突仲裁层

原因：

1. 当前平台已经要求一个 task session 只有一个有效运行态 sandbox
2. skills memory 也是在这个前提下通过受控 flush 保持稳定
3. Altus session memory 首版应优先复用同一复杂度级别，避免引入第二套更难验证的机制
4. 额外的高频 DB 读写会直接带来性能波动和更多隐藏竞态
