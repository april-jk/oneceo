# 01 现状差异、目标与范围

## 1. 当前 oneceo 的真实问题

当前 skill 能力不是“平台技能系统”，而只是“更长的 prompt 模板”。

核心表现为：

1. skill 定义写死在 `apps/web/client/src/lib/skill-attachment-templates.ts`
2. 前端选择 skill 后，实际生成的是伪附件
3. skill 内容最终直接拼到用户消息里
4. sandbox 内没有统一 skill 目录，也没有 skill 的启用/卸载状态
5. 后台没有 CRUD 能力，新增 skill 必须改前端代码再发版

这会直接带来三个问题：

1. 扩展性差：每加一个 skill 都要改前端源码
2. 运行时不真实：sandbox 并不知道有哪些平台 skill
3. prompt 膨胀：每次都把整段 skill markdown 塞进消息

## 2. 与 suna 的关键差异

我对照的不是 `suna` 的具体 UI，而是它的结构方式。

从 `suna` 中能抽出的关键点有三条：

1. 平台能力不写死在前端，而是由后端注册表/API 暴露
2. 用户/运行时拿到的是“配置引用”，不是把完整说明文本塞进每次请求
3. 真正的运行时加载发生在执行层，而不是发生在前端输入框

对应代码依据：

1. `backend/core/endpoints/tools_api.py`
2. `apps/frontend/src/hooks/tools/use-tools-metadata.ts`
3. `backend/core/agents/runner/prompt_manager.py`
4. `backend/core/tools/expand_msg_tool.py`

虽然 `suna` 这里管理的是 tools 而不是 OpenCode skills，但它解决的问题和 oneceo 现在遇到的是同一类问题：

1. 不把能力目录写死在前端
2. 不把完整能力说明每次都重复塞进 prompt
3. 运行时按需加载

## 3. oneceo 的目标方案

本次目标不是“把硬编码模板挪到后端文件里”，而是建立一套真正的平台 skill 系统。

目标定义如下：

1. skill 的唯一来源是平台数据库中的已发布版本
2. 前端只读取 skill 列表和元数据，不再内置模板正文
3. 发送消息时只上传 `skill 引用`，不上传/不内联 skill 正文
4. API 在 sandbox 内按 OpenCode skill 规范写入 `SKILL.md`
5. skill 的可见集合随当前消息选择热更新，而不是永久写死

## 4. 本次范围

本次只覆盖 task-creation 主链路和对应管理后台：

1. `apps/web/client`
2. `apps/api`
3. `apps/admin_management`
4. E2B sandbox 内 OpenCode skill 热加载

## 5. 本次不做的事

本次明确不做以下内容：

1. 不继续保留“静态模板 + 数据库技能”双轨并存
2. 不把 skill 继续当作普通附件文件上传
3. 不引入额外外部平台来管理 skill
4. 不在 sandbox 内增加人工配置入口
5. 不先做兼容补丁再逐步替换

也就是说，本次方案是直接把 skill 的定义、选择和加载链路全部收口。
