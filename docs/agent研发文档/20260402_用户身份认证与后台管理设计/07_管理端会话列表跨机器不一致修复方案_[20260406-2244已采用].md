# 07 管理端会话列表跨机器不一致修复方案 [尚未采用]

更新时间：2026-04-06

## 1. 问题定义

当前管理端 `对话管理`（用户口头称“绘画管理列表”）存在两类问题：

1. 列表不全。
2. 不同机器登录同一个管理账号时，看到的列表不一致。

用户怀疑点是“token 与用户绑定错误”。本次排查结论是：核心问题不是管理员 token 绑定到错误用户，而是后台数据源与回退机制设计不符合管理端语义。

## 2. 现状与根因

### 2.1 管理端误用了用户态会话接口

当前管理端 `ConversationManagementService` 通过 `OneceoApiConnector.listTaskCreationSessions()` 请求：

1. `/api/task-creation/sessions?limit=...`

该接口是用户态接口，服务端会按 `currentUser.userId` 做 owner 过滤，不是管理态全局查询。

影响：

1. 管理端拿到的不是“平台全量会话”，而是“某个用户上下文可见会话”或直接失败。

### 2.2 管理端调用不携带 app 用户身份

管理端到 API 侧主要使用内部 token（`x-oneceo-internal-token`），并不附带用户态 cookie 或 `X-User-Id`。

用户态会话接口在无用户上下文时会返回“无法识别当前用户”，导致管理端查询失败。

### 2.3 失败后默认回退到本机 local memory

`apps/admin_management/server/services/conversation-management-service.ts` 在查询失败时会回退读取：

1. `apps/api/data/task-creation-memory.json`

且 `ADMIN_MANAGEMENT_LOCAL_MEMORY_FALLBACK` 默认是 `true`。

影响：

1. 每台机器读到自己的本地文件快照。
2. 同一管理员在不同机器看到不同列表（这是跨机器不一致的直接来源）。

### 2.4 前端列表硬编码只拉 30 条

前端 `loadConversationSessions()` 当前固定请求 `listConversationSessions(30)`。

影响：

1. 即使后端返回正确数据，也会被 30 条上限截断，表现为“列表不全”。

## 3. 目标与约束

### 3.1 目标

1. 管理端会话列表与详情改为管理态数据源，消除用户态 owner 过滤。
2. 同一环境下不同机器登录同一管理员账号时，列表结果一致。
3. 移除管理端会话模块的本地文件回退，避免再次引入机器本地状态分叉。
4. 列表不再固定 30 条，支持可配置分页拉取。

### 3.2 约束

1. 严格遵守“用户态与管理态分离”。
2. 不提供兼容性补丁链路，不保留旧的 local memory 回退作为兜底。
3. 走最短主链实现，不引入与本问题无关的权限模型扩展。

## 4. 方案设计

### 4.1 API 侧新增管理态内部查询接口

在 `apps/api/src/routes/internal-task-creation-routes.ts` 新增管理态路由（内部 token 鉴权）：

1. `GET /api/internal/task-creation/admin/sessions`
2. `GET /api/internal/task-creation/admin/sessions/:sessionId`
3. `GET /api/internal/task-creation/admin/sessions/:sessionId/messages`
4. `GET /api/internal/task-creation/admin/sessions/:sessionId/intent`
5. `GET /api/internal/task-creation/admin/sessions/:sessionId/task-description`
6. `GET /api/internal/task-creation/admin/sessions/:sessionId/execution-plan`
7. `GET /api/internal/task-creation/admin/sessions/:sessionId/debug`

设计说明：

1. 这组接口只用于管理端，不复用用户态 owner 接口。
2. 查询结果包含 `session.userId`（可选附带用户展示字段），用于后台定位归属。
3. 列表接口支持分页参数（`limit` + `cursor`），默认 `limit=50`，上限 `200`。

### 4.2 DAO 侧新增管理态列表查询

在 `task_creation_sessions` 读取层新增“按更新时间倒序的管理态分页查询”，不带用户过滤条件。

要求：

1. 稳定排序键：`updated_at desc, id desc`。
2. 游标分页使用 `(updated_at, id)` 复合游标，避免 offset 在大表抖动。

### 4.3 管理端服务改造

改造 `apps/admin_management/server/connectors/oneceo-api-connector.ts` 和 `conversation-management-service.ts`：

1. 列表与详情全部改走新内部管理态接口。
2. 删除会话模块 local memory 回退逻辑。
3. 删除会话模块中 `ADMIN_MANAGEMENT_LOCAL_MEMORY_FALLBACK` 相关分支。
4. 上游失败时直接返回明确错误，不再返回本机快照数据。

### 4.4 管理端前端改造

改造 `apps/admin_management/web/src/api.ts` 与 `App.tsx`：

1. `listConversationSessions` 改为分页接口（`limit`, `cursor`）。
2. 首屏默认拉取 50 条，提供“加载更多”。
3. 现有筛选/搜索在“已加载集合”上保持不变，不额外改交互模型。

## 5. 实施步骤

1. API：补齐内部管理态会话查询接口与类型定义。
2. Admin server connector：接入新接口。
3. Admin conversation service：移除 local memory 回退并对齐新接口。
4. Admin web：从固定 30 条改为分页拉取。
5. 自动化测试与双机器一致性验证。

## 6. 数据与安全边界

1. 用户态接口保持原有 owner 校验，不做语义变更。
2. 管理态接口仅允许 `x-oneceo-internal-token` 访问，不对公网暴露匿名访问。
3. 管理态只提供治理可见性，不改变业务资源 owner（`session.userId` 仍是用户归属事实）。

## 7. 验收标准

1. 同一时刻，两台机器登录同一管理员账号，请求管理端会话列表前 N 条，`sessionId` 顺序一致。
2. 管理端会话列表不再出现“请求失败后展示本机旧数据”。
3. 管理端列表默认可见条目 > 30，且可继续加载后续分页。
4. 用户态接口仍保持跨用户不可读（403/401 行为不变）。
5. 内部管理态接口在 `ONECEO_INTERNAL_TOKEN` 缺失或错误时返回 403/401。

## 8. 风险与回滚

1. 风险：新增内部接口若缺分页边界，可能导致后台大流量拉取。
2. 控制：强制 `limit <= 200`，默认 50。
3. 风险：移除 local fallback 后，上游失败会直接暴露错误。
4. 控制：统一错误文案并在后台 UI 显示“管理数据源不可用”。
5. 回滚：仅回滚本次新增的管理态接口接入与前端分页改动，不回滚用户态鉴权主链。

## 10. 与现有采用文档关系

本方案是对“身份传播、会话绑定与授权模型”在管理端查询链路上的补全落地，保持以下已采用约束不变：

1. 用户态和管理态身份分离。
2. 用户态 owner 授权不被管理端查询链路绕过。
3. 管理端通过内部受控接口读取治理视图，而非伪装成用户态请求。
