# 会话标题首次明确锁定设计

## 1. 背景

当前 task creation / sandbox 直通会话的标题生成逻辑过于直接：

- 前端发送首条消息时，直接用 `text.slice(0, 80)` 作为 `title`
- `POST /api/task-creation/sessions` 也会优先使用请求里的 `title`
- 侧边栏收到 `task-creation-session-updated` 后会立刻覆盖显示标题

这会导致两个问题：

1. 用户先发送“你好”“在吗”“帮我一下”这类寒暄或探测消息时，会把会话标题误锁成无意义标题
2. 用户后续继续对话时，标题仍可能继续跟随最新输入变化，破坏会话识别稳定性

目标是把标题改成：

- 只在“第一次明确对话”时确定
- 一旦确定即锁定
- 后续多轮对话不再自动改标题

## 2. 目标

本方案只解决“会话标题锁定”问题，不调整消息流、executor、恢复逻辑。

验收目标：

- 用户先发“你好”“hello”“在吗”等弱意图消息时，不锁定最终标题
- 用户第一次发出明确任务/问题时，标题被确定
- 标题一旦确定，后续继续对话不会再被覆盖
- OpenCode / Codex / ClaudeCode / Altus 统一遵守同一套标题锁定规则

## 3. 非目标

- 不做 LLM 生成摘要标题
- 不做历史标题回溯重算
- 不修改用户手动重命名能力
- 不改变现有 sidebar 的展示结构

## 4. 核心概念

### 4.1 首次明确对话

“首次明确对话”指第一次满足下列条件的用户输入：

- 非空
- 去除空白后长度达到最小阈值
- 不属于常见寒暄/探测/弱意图短句
- 具有明确任务、问题、请求、目标或对象

### 4.2 标题锁定

“标题锁定”指 session 进入以下状态：

- `titleLocked = true`
- 后续自动标题更新逻辑全部失效
- 只有用户显式重命名时才允许变更

## 5. 判定规则

### 5.1 弱意图消息

默认视为“不能锁定标题”的消息示例：

- `你好`
- `hi`
- `hello`
- `在吗`
- `有人吗`
- `帮我一下`
- `开始`
- `继续`
- `ok`
- `好的`

规则特征：

- 长度很短
- 不包含明确任务对象
- 不包含明显动作词 + 目标词组合

### 5.2 明确对话消息

默认视为“可以锁定标题”的消息示例：

- `帮我开发2048小游戏，使用html实现`
- `继续优化css，使用nodejs重构`
- `请分析这个报错的根因`
- `把登录页改成双栏布局`

规则特征：

- 包含任务意图、操作动作、问题指向或具体对象
- 文本长度和语义密度足够形成会话识别标题

### 5.3 判定策略

采用“规则优先”的本地判定，不引入模型调用。

建议顺序：

1. 归一化文本
2. 命中弱意图词表则拒绝锁定
3. 长度低于阈值则拒绝锁定
4. 命中明确动作/问题模式则允许锁定
5. 未命中明确模式但长度足够时，按保守策略：
   - 允许首次锁定，但仅在不是纯寒暄、纯确认语的前提下

## 6. 数据模型

需要在 session 上增加标题状态字段。

### 6.1 File memory / runtime summary

新增字段：

- `titleLocked?: boolean`
- `titleSource?: 'placeholder' | 'first_explicit_user_input' | 'manual'`
- `titleResolvedAt?: string`

含义：

- `titleLocked=false` 表示仍处于等待首次明确对话阶段
- `titleSource='placeholder'` 表示仍是临时标题
- `titleSource='first_explicit_user_input'` 表示由首次明确对话锁定

### 6.2 默认初始态

新建 session 时：

- `title = '新建任务会话'`
- `titleLocked = false`
- `titleSource = 'placeholder'`

不再把首条用户输入无条件写成标题。

## 7. 行为流程

### 7.1 新建会话

前端创建草稿会话时：

- 不再默认用输入文本作为最终标题
- 只传占位标题，或直接省略标题让后端落默认值

### 7.2 发送用户消息

每次用户发送消息时：

1. 读取 session 当前标题状态
2. 若 `titleLocked=true`：
   - 跳过自动标题更新
3. 若 `titleLocked=false`：
   - 用本地规则判断当前消息是否属于“首次明确对话”
   - 若是，则更新标题并锁定
   - 若否，则保持原占位标题

### 7.3 后端兜底

后端也必须具备同样的锁定保护，避免前端绕过或旧客户端继续写错标题。

即：

- `createSession(existingSession)` 时，若 session 已锁定，禁止用新标题覆盖
- 专门提供 `resolveSessionTitleIfNeeded(sessionId, userInput)` 入口
- 只允许从 `placeholder -> first_explicit_user_input`

### 7.4 手动重命名

如果未来已有用户手动改标题入口：

- 手动改名后：
  - `titleLocked = true`
  - `titleSource = 'manual'`
- 后续自动逻辑永不覆盖

## 9. 兼容性要求

- 不影响 OpenCode / Codex 的 executor 分发
- 不影响消息持久化
- 不影响 session restore
- 不影响用户手动重命名

## 10. 风险与取舍

### 10.1 过早锁定

风险：

- 某些短句其实已经表达了明确任务，但规则误判为弱意图

取舍：

- 优先避免“你好/在吗”误锁定
- 接受少量“需要到第二句才锁定标题”的情况

### 10.2 规则不足

风险：

- 纯规则无法完美覆盖所有语言习惯

取舍：

- 第一版先用确定性规则落地
- 后续如果误判率高，再考虑引入更强摘要策略

## 11. 推荐实现顺序

1. 后端增加 `titleLocked/titleSource/titleResolvedAt`
2. 后端禁止已锁定标题被自动覆盖
3. 前端改为占位标题创建 session
4. 前端在首次明确对话时调用锁定更新
5. 回归验证：
   - `你好 -> 帮我开发2048小游戏`
   - `在吗 -> 继续优化css`
   - 已锁定标题后的多轮对话

## 12. 验收用例

### 用例 1

输入序列：

- `你好`
- `帮我开发2048小游戏，使用html实现`

预期：

- 第一轮后标题仍为占位标题
- 第二轮后标题锁定为 `帮我开发2048小游戏，使用html实现`

### 用例 2

输入序列：

- `帮我开发2048小游戏，使用html实现`
- `继续优化css`

预期：

- 第一轮后标题即锁定
- 第二轮后标题不变

### 用例 3

输入序列：

- `在吗`
- `ok`
- `请分析这个报错的根因`

预期：

- 前两轮不锁定
- 第三轮锁定标题

## 13. 当前结论

这项改动应作为一套全局 session 标题策略落地，而不是只修某一个 executor 的对话页显示。

硬约束：

- 首次明确对话前，不锁定最终标题
- 一旦锁定，后续自动逻辑不可再覆盖
- 前端和后端都必须具备同一套保护，避免状态分叉

  - `titleLocked = true`
  - `titleSource = first_explicit_user_input`
  - `titleResolvedAt` 有值
