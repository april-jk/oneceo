# 20260525 Sandbox 内部日志排查 SOP [20260525-1918已采用]

## 1. 使用场景

当用户要求“去 sandbox 内部查日志”“查某个会话对应的 sandbox 为什么失败”“从 env 里读 sandbox 密钥后检查日志”时，按本文档执行。

目标不是重新推方案，而是快速拿到同一条会话链路里的证据：

1. task session 对应哪个 sandbox。
2. 平台数据库里记录了哪些 sandbox / debug / run diagnostics。
3. sandbox 内部日志是否和平台 metadata 一致。
4. 失败到底发生在平台状态判断、sandbox runtime、用户服务、还是工具调用层。

## 2. 安全规则

1. 可以读取 `.env` / `.env.local` 判断 `E2B_API_KEY`、`DATABASE_URL` 等是否存在，但不能在回复里输出密钥原文。
2. 需要展示 env 状态时只写 `<set>` / `<missing>`。
3. 查询数据库或 E2B 时，优先使用项目已有依赖和连接器；不要把密钥硬编码进脚本。
4. 临时脚本只能写到 `/private/tmp`，并避免把密钥打印到 stdout / stderr。
5. 最终汇报只给证据摘要和结论，不贴完整敏感配置。

## 3. 必查入口

先在仓库根目录执行：

```bash
git branch --show-current
git status --short
```

确认 env 是否具备必要变量时使用脱敏输出：

```bash
awk -F= '/^(E2B_API_KEY|DATABASE_URL|DATABASE_SSL)=/ { print FILENAME ":" $1 "=<set>" }' .env .env.local 2>/dev/null
```

如果用户给的是页面 URL，例如：

```text
http://localhost:3000/session/<taskSessionId>
```

先提取 `<taskSessionId>`，后续所有查询都围绕这个 id。

## 4. 数据库优先查询

数据库是第一层事实源，因为很多 sandbox 内部日志已经由平台采集进了 metadata。优先查：

1. `task_sessions`
2. `sandbox_execution_environments`
3. `altus_runs`
4. run events / messages / tool event 表中与该 session 关联的最近记录

重点字段：

```text
taskSessionId
sandboxId / orchestratorSessionId
workspaceRoot
sandbox status
debug.neko.status
debug.neko.reasonCode
debug.neko.message
debug.neko.diagnostics
debug.neko.port / cdpPort / display
debug.neko.runtimeVersion / configVersion
recent run id / run status / stop_reason
最近 tool_call_failed / tool_call_completed payload
```

判读规则：

1. 如果 metadata 里的 manifest / listeningPorts 显示 Chromium CDP 和 n.eko 都 ready，但 `debug.neko.status=failed`，优先怀疑平台 ensure / lock wrapper 误判。
2. 如果 `startScriptError` 只有 lock diagnostic，没有 `chromium start failed` / `neko start failed` / `xvfb start failed`，不要直接下结论说浏览器没起来。
3. 如果 run events 里 Altus 试图 `pkill neko`、启动 `neko`、清理 X11 lock 或访问 9222，说明模型在越权修平台 runtime；应检查 shell guard 是否拦截并确认平台是否提供了正确恢复路径。
4. 如果 `browserScreenshot` 为空，要先看 `debug_open_page` 是否成功；没有成功就不是前端 Actions 展示问题。

## 5. 进入 E2B sandbox 查内部日志

只有数据库 metadata 不够用，或用户明确要求“sandbox 内部日志”时，再进入 E2B。

建议通过项目已有 `e2b` SDK 依赖和 env 加载创建临时脚本。脚本只打印脱敏后的诊断结果，常查命令如下：

```bash
ls -la /tmp/oneceo/debug-browser /tmp/oneceo/debug-browser/logs /tmp/oneceo/debug-browser/run /tmp/oneceo/debug-browser/state
sed -n '1,120p' /tmp/oneceo/debug-browser/state/manifest.json
tail -n 120 /tmp/oneceo/debug-browser/logs/neko-start.log
tail -n 120 /tmp/oneceo/debug-browser/logs/neko.log
tail -n 120 /tmp/oneceo/debug-browser/logs/chromium.log
tail -n 120 /tmp/oneceo/debug-browser/logs/xvfb.log
cat /tmp/oneceo/debug-browser/run/*.pid 2>/dev/null
cat /tmp/oneceo/debug-browser/run/ensure.lock.owner 2>/dev/null
ss -ltnup 2>/dev/null | grep -E ':(8081|8082|9222)\b' || true
ss -lunp 2>/dev/null | grep -E ':8083\b' || true
curl -fsS --max-time 2 http://127.0.0.1:9222/json/version
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/
ps -ef | grep -E 'Xvfb|chrome|chromium|neko' | grep -v grep
```

如果本地网络 sandbox 阻止访问 `api.e2b.app`，不要绕路泄露密钥；记录“E2B 直连被本地网络/审批阻止”，然后使用 DB 已采集 diagnostics 给出结论。

## 6. 结论输出格式

最终给用户的结论要短，但必须能回答“确切原因是什么”：

```text
结论：不是/是 sandbox 内浏览器进程失败。
证据：
1. DB metadata / manifest: ...
2. ports / logs: ...
3. run events: ...
原因链：
<A> 导致 <B>，所以 <C> 没有产生。
剩余不确定性：
<如果 E2B 直连未成功或某类日志缺失，明确说明>
```

示例判定：

```text
不是 Chromium/n.eko 没起来。manifest 显示 debug browser ready，9222 上有 Chrome，8081 上有 n.eko。失败来自 ensure wrapper 返回 exit status 2，metadata 被标记为 start_script_failed，导致 debug_open_page 被 debug_not_ready / repeat_blocked 拦住，因此没有 browserScreenshot。
```

## 7. 常见误判

1. `chromium.log` 里的 DBus / UPower warning 通常不是 CDP 失败原因，必须结合 `DevTools listening` 和 9222 probe 判断。
2. `debug_browser_lock_timeout` 不等于浏览器没起来；可能是第二个 ensure 被锁挡住，而第一个 ensure 已经启动成功。
3. `start_script_failed` 是兜底码，必须继续看 `startScriptStdout`、`startScriptStderr`、manifest、ports 和日志 tail。
4. Altus 被 guard 拦截管理 n.eko / Chrome 是正确行为；问题要回到平台 runtime 恢复路径，而不是放开 guard。
5. 没有 `browserScreenshot` 时，不要先查前端卡片渲染，先查 `debug_open_page` 是否完成。
