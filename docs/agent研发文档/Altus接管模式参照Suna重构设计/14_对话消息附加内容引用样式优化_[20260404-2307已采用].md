# 14 对话消息附加内容引用样式优化 [20260404-2307已采用]

日期：2026-04-04

关联事项：

- GitHub Issue `#26`

## 1. 背景

当前任务对话中，用户发送消息时可以附加两类能力：

1. 文件附件
2. Skills

发送链路已经把这些附加内容写进消息 `metadata`，但消息渲染层仍存在两个明显问题：

1. 只对 `metadata.attachments` 做了展示，`metadata.skills` 没有在消息卡片中稳定呈现。
2. 已展示的附件仍然只是“贴在消息正文后面的一排 chip”，没有明确表达“这些内容是附加在这条消息上的引用项”。

结果是：

1. 用户无法快速判断某条消息是否携带了 skill / 附件。
2. 同一条消息的正文与附加能力之间缺少结构层级。
3. 当消息正文较短或为空占位文案时，附加内容归属感更弱。

## 2. 当前实现与问题定位

当前发送侧：

- `apps/web/client/src/components/TaskCreationChat.tsx`
  - 会把 `selectedSkills` 写入 `metadata.skills`
  - 会把上传后的文件写入 `metadata.attachments`
  - 会补充 `metadata.originalInput`

当前渲染侧：

- `apps/web/client/src/components/TaskCreationChat.tsx`
  - `MessageCard` 只读取 `message.metadata.attachments`
  - `MessageCard` 不读取 `message.metadata.skills`
- `apps/web/client/src/components/AttachmentChipList.tsx`
  - 已具备文件 / skill 两种 chip 视觉基础
  - 但当前主要用于输入区或简单横向列举，不具备“消息引用块”语义

结论：

这不是数据缺失问题，而是消息层 UI 语义缺失问题。最短路径应当直接重构消息卡片中的“附加内容展示层”，而不是补丁式继续往正文后堆 chip。

## 3. 本次目标

将对话消息中的附加内容重构为消息级“引用块”。

目标效果：

1. 用户一眼能看出“这条消息附加了什么”。
2. `Skills` 与文件附件共享一套引用视觉语言。
3. 同一条消息同时存在多种附加内容时，结构清晰，不与正文混排。
4. 只改消息展示层，不改发送协议、不改历史消息存储结构、不引入兼容分支。

## 4. 非目标

本轮不做以下事项：

1. 不调整附件上传协议。
2. 不改 `metadata` 的持久化结构。
3. 不新增全局附件面板或独立消息详情页。
4. 不改输入区 `AttachmentChipList` 的交互模式。
5. 不扩大到 direct / managed 以外的其它页面。

## 5. 目标交互与视觉结构

每条存在附加内容的消息卡片，在正文上方新增一个引用块：

1. 引用块位于消息正文之前。
2. 引用块与正文属于同一张消息卡片内部。
3. 引用块有独立边框、浅背景和左侧强调条，明确表达“此消息引用了以下附加内容”。

建议结构：

1. 引用块头部
   - 文案：`已附加`
   - 若只有 skills：副标题显示 `Skills`
   - 若只有附件：副标题显示 `附件`
   - 若两者都有：副标题显示 `Skills 与附件`
2. 引用块内容区
   - 先显示 `Skills`
   - 后显示 `附件`
3. 每个分组都带分组标题与数量
4. 具体项使用紧凑 chip，但不再直接裸贴正文

建议视觉原则：

1. 引用块整体比正文更浅，不能喧宾夺主。
2. Skill 与附件在结构统一的前提下通过图标与标签区分。
3. 当消息为用户消息时，引用块需跟随用户消息气泡风格；当消息为系统或 agent 消息时，沿用中性色。
4. 多项内容换行展示，不强制单行横向滚动。

## 6. 数据口径

消息引用块只依赖现有 `message.metadata`：

1. `metadata.skills`
2. `metadata.attachments`
3. `metadata.originalInput`

数据约束：

1. `skills` 直接按现有 `TaskCreationPlatformSkill` 的快照信息渲染。
2. `attachments` 直接按现有 `TaskCreationUploadedAttachment` 渲染。
3. 不额外请求详情接口。
4. history replay 与实时消息统一走同一解析函数。

## 7. 组件拆分建议

最短路径建议新增一层消息专用引用组件，而不是继续复用输入区 attachment list 作为主容器。

建议拆分：

1. `TaskCreationChat.tsx`
   - `MessageCard` 内新增对 `metadata.skills` 的读取
   - `MessageCard` 内统一组装引用块数据
2. 新增消息引用组件
   - 建议文件：`apps/web/client/src/components/MessageAttachmentReference.tsx`
   - 责任：渲染消息级引用块
3. `AttachmentChipList.tsx`
   - 保持输入区现有职责
   - 若复用其单项 chip 样式，只抽取底层 item renderer，不让它继续承担“消息引用块容器”职责

原因：

1. 输入区 attachment list 的横向拖动和移除按钮语义不适合消息历史区。
2. 消息区需要分组、标题、数量和引用语义，职责已经不同。
3. 独立组件更容易覆盖测试与后续扩展。

## 8. 具体展示规则

### 8.1 仅附加 Skills

1. 展示引用块
2. 分组标题显示 `Skills`
3. 每个 skill 显示：
   - 名称
   - revision 信息
   - skill 图标

### 8.2 仅附加附件

1. 展示引用块
2. 分组标题显示 `附件`
3. 每个附件显示：
   - 文件名
   - 文件大小
   - 文件图标

### 8.3 同时附加 Skills 与附件

1. 只展示一个引用块
2. 引用块内部按两个分组展示
3. 顺序固定为：
   - `Skills`
   - `附件`

### 8.4 正文为空占位文案

当正文是“已添加附件”这类占位输入时，不允许让引用块看起来像唯一内容来源。

要求：

1. 占位文案继续保留在正文区。
2. 引用块仍独立展示。
3. 不把占位文案并入引用块头部，避免语义混乱。

## 9. 测试与验收

至少补齐以下前端验证：

1. 仅 skill 消息能显示 skill 引用块
2. 仅附件消息能显示附件引用块
3. 同时存在 skill 与附件时，能按分组显示
4. 不带附加内容的消息，不显示引用块
5. history 恢复后的消息与实时发送后的消息表现一致

建议新增测试方向：

1. `TaskCreationChat` 消息渲染单测
2. `managed-session-resolution` 之外，补消息 metadata 渲染测试

## 10. 实施顺序

1. 新增消息级引用块组件
2. 在 `MessageCard` 内解析 `skills + attachments`
3. 用统一样式替换当前“正文后直接挂 attachment chip”的展示
4. 补齐渲染测试
5. 本地执行最小前端校验

## 11. 风险与约束

风险点只有两个：

1. 现有历史消息中 `metadata.skills` 结构可能存在少量不完整数据
2. 输入区复用组件若抽取不当，容易把“可移除 chip”交互误带入消息区

处理原则：

1. 消息区只做只读展示，不出现 remove 行为。
2. 对 `skills / attachments` 做最小字段守卫，字段不全就跳过当前项，不新增兼容兜底分支。

## 12. 采用后拟修改文件

- `apps/web/client/src/components/TaskCreationChat.tsx`
- `apps/web/client/src/components/AttachmentChipList.tsx`
- `apps/web/client/src/components/MessageAttachmentReference.tsx`
- `apps/web/client/src/tests/*` 中对应消息渲染测试文件

## 13. 结论

本事项的本质不是“把附件样式做得更好看”，而是：

1. 让消息与附加能力之间形成稳定的引用关系表达
2. 把 `skills` 与附件从“零散元数据”提升为消息级可识别结构
3. 用最短路径完成现有对话体验中的信息归属修复

在你确认本方案后，再进入代码实现阶段。
