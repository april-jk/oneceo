## 1. 目标

围绕“开发一个网站 -> 将网站部署”的真实业务链路，补齐以下稳定能力：

1. 提供固定的 Playwright 用户态测试账号，避免后续每次临时造号。
2. 让 AGENTS 明确说明测试账号存放位置，便于后续测试复用。
3. 修复并验证以下链路问题：
   - 用户态真实登录与会话恢复
   - 网站生成 run 的自然收口
   - 部署工具触发后的 skill 自动挂载审计证据
   - 部署面板与 sandbox 元数据同步
   - Railway 发布后公网页面真实可用，而不是仅返回 200

## 3. 修复范围

### 3.1 登录与测试入口

1. 增加固定测试账号 provisioning 脚本。
2. Playwright 全链路脚本优先走真实登录页，不再依赖手动 cookie。
3. 允许测试前自动校准该固定账号密码，保证账号长期可复用。

### 3.2 skill 自动挂载审计

1. 工具触发 skill 自动挂载后，不能只停留在运行态内存和 prompt 拼接层。
2. 必须把“哪个工具触发了哪些 skill”写入可审计的时间线消息或等价持久化记录。
3. 后续测试与日志采集应能直接验证该证据。

### 3.3 部署状态同步

1. 部署面板不能长期停留在“后台正在同步部署状态”。
2. 当 sandbox metadata 已经存在 `deploymentState` 或 `deploymentPanel` 时，用户端查询必须优先返回可用快照。
3. 对 `provisioning` / `repair_required` 等中间态，应主动刷新 live panel，而不是死读旧快照。

### 3.4 Railway 发布产物正确性

当前已定位到的错误模式：

1. 含 `package.json + index.html + src/main.jsx` 的前端项目被错误套用静态 HTML 根目录兜底。
2. 发布后由兜底 `server.js` 直接服务源码入口，导致 `.jsx` 返回 `application/octet-stream`。
3. 浏览器最终白屏，但部署工具已提前宣称“成功”。

修复要求：

1. 前端构建型项目必须优先按“先 build，再服务 dist”处理。
2. 纯静态 HTML 项目才允许走静态根目录兜底。
3. 部署工具不能在明显仍处于 `INITIALIZING/DEPLOYING/BUILDING` 时直接给出最终成功结论。

## 4. 验收标准

使用固定账号 `test@test.com / testtest` 跑真实浏览器链路，必须同时满足：

1. 登录页登录成功，并可跳回用户态会话。
2. 网站生成 run 最终 `completed`，而不是卡住或人工 stop。
3. 同会话发送“帮我部署当前项目”后，确实调用部署工具。
4. skill 自动挂载有持久化审计证据。
5. 部署面板和 sandbox metadata 对外状态一致。
6. Railway 公网地址在浏览器中真实渲染成功，不白屏，且页面内容符合“亚克力外贸网站”主题。

最终交付必须包含：

1. 固定测试账号文件路径

4. 关键 runId / sessionId / URL
