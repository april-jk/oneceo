# 部署编排 Skill 自动强制挂载修复方案 [20260421-2308已采用]

更新时间：2026-04-21

## 1. 背景

当前 `deployment-orchestrator` 已经平台化，并参与 Altus managed run 的 skill 自动挂载链路。

但本轮真实排查发现，现网行为已经偏离原设计目标：

1. 用户仅发送普通消息，例如“你好”，managed run 仍会自动带上 `deployment-orchestrator`
2. 该 skill 当前不是“部署意图触发”挂载，而是因为治理元数据中 `required=true` 被无条件纳入 `requiredSelections`
3. skill 一旦进入 resident selections，后续 sandbox skill sync 会把它写入 sandbox，并触发一次 `opencode serve` 重启
4. 这直接抬高了“发送消息 -> 首轮 prompt ready”的冷启动耗时，即使当前消息与部署完全无关

本方案只修正一个问题：

**`deployment-orchestrator` 不应作为全局 required skill 自动强制挂载。**

## 2. 现象与证据

基于 2026-04-21 的真实会话排查，已经确认：

1. session `135688cb-bb93-43b3-a201-22d329a5f401` 的唯一用户输入是“你好”
2. 该 session 的 `sessionSkillState.bindings` 中仍出现了 `deployment-orchestrator`
3. 其 `activationSource` 为 `required`
4. 平台 skill 表中该 skill 的治理元数据为：
   - `slug = deployment-orchestrator`
   - `name = 部署编排`
   - `metadata_json.required = true`
5. managed run 在 `PROVISION_DONE -> ALTUS_RUN_SKILL_SYNC_READY` 之间额外消耗约 `4.84s`
6. 该时间段的主路径已定位到 `sandboxSkillSyncService` 写入 skill 并执行 `restartOpencodeServer()`

因此，本问题不是“部署意图识别太宽”，而是：

**部署 skill 被错误建模成了全局必选 skill。**

## 3. 问题定义

### 3.1 当前错误模型

当前链路把 `deployment-orchestrator` 作为：

1. 平台 deployment 系统 skill
2. 全局 `required` skill

这两个属性同时成立时，实际效果是：

1. 所有 managed run 都会带上它
2. 不再区分消息是否为部署请求
3. 新会话首轮也会执行 skill sync
4. 首轮 skill sync 又会强制重启 opencode server

### 3.2 正确模型

`deployment-orchestrator` 应该是：

1. 平台 deployment 系统 skill
2. 可治理、可发布 revision 的 deployment 专用知识层
3. 仅在“部署相关意图”或“部署相关平台动作”下自动挂载

它**不应该**是：

1. 所有 session 的全局 required skill
2. 非部署场景的默认 resident skill
3. 首轮普通问候、澄清、分析类消息的强制上下文

## 4. 修复目标

本次修复只追求以下结果：

1. 非部署消息不再自动挂载 `deployment-orchestrator`
2. 部署相关消息仍能稳定自动挂载 `deployment-orchestrator`
3. 已有 deployment skill 治理体系、revision 发布体系、管理后台可见性不被破坏
4. 不引入新的兜底通道，不增加第二套 deployment 注入逻辑

## 5. 非目标

本次不做：

1. 不调整 OSAC 启动链路
2. 不调整 workspace restore 判定
3. 不重做 skill sync 的 restart 机制
4. 不重构部署工具本身
5. 不把 deployment skill 从平台 skills 中移除

## 6. 修复方案

### 6.1 收敛治理语义

`deployment-orchestrator` 必须保留：

1. `systemRole = deployment_orchestrator`
2. `adminManaged = true`
3. `autoActivation.enabled = true`
4. `autoActivation.triggers = [deployment, deployable_web_app, deploy, redeploy, rollback, status]`
5. `autoActivation.toolNames = [deploy_application, redeploy_application, rollback_application_deployment, get_application_deployment_status]`

但必须去掉：

1. `required = true`

结论很明确：

**deployment skill 是“自动触发型系统 skill”，不是“全局必选 skill”。**

### 6.2 运行时判定口径

managed run 对 `deployment-orchestrator` 的挂载来源只允许保留两种：

1. 文本意图命中部署动作
2. 平台 deployment tool 运行时命中自动激活

不再允许第三种来源：

1. `requiredSelections`

补充约束：

- 文本意图预挂载必须识别动作型 trigger：`deploy / redeploy / rollback / status`，不能只识别抽象的 `deployment`。
- 对 `deployment-orchestrator`，即使 seed 包含 `deployable_web_app`，也必须要求当前轮确实是部署执行请求，不能因为普通网页生成请求就挂载部署 skill。

### 6.3 session resident 行为口径

deployment skill 可以在部署场景下进入 resident / active skill 范围，但其保持范围必须服从当前 intent：

1. 当前轮是部署请求，可以挂载
2. 当前轮是部署后的连续修复/状态跟进，可以继续保留
3. 新一轮普通聊天、普通分析、普通代码任务，不得因为历史上部署过而继续默认挂载

也就是说，deployment skill 的驻留必须是“场景相关驻留”，不是“会话永久驻留”。

## 7. 为什么不能继续保留 `required=true`

### 7.1 语义错误

`required=true` 的语义是：

1. 无论用户在做什么，这个 skill 都是当前 run 的基础前提

但 deployment 显然不是所有 run 的基础前提。

### 7.2 性能错误

在当前实现里，skill 进入 run state 后会导致：

1. sandbox skill sync
2. skill 文件写入 sandbox
3. opencode server 重启

所以把 deployment skill 设成 required，等于把“部署能力初始化成本”加到了所有 managed run 上。

### 7.3 治理错误

如果一个平台 skill 既是 `systemRole=deployment_orchestrator`，又是 `required=true`，后台治理上会制造错误信号：

1. 看起来像“部署是平台默认基础能力”
2. 实际上却把一个强场景能力混进了所有对话

这会让后续更多平台 skill 继续沿着“先做成 required 再说”的方向扩散，最终把 managed run 退化成一组永远挂载的重型 prompt 包。

## 8. 验收标准

修复完成后，必须满足：

1. 用户发送“你好”“帮我看下这个报错”“写一个页面”等非部署消息时：
   - `deployment-orchestrator` 不进入 `requiredSelections`
   - 不进入本轮 `residentSkillSelections`
   - 不触发 deployment skill sync
2. 用户发送“帮我部署这个项目”“重新部署”“回滚部署”“查看部署状态”时：
   - `deployment-orchestrator` 能自动挂载
   - deployment tool 链路不回归
3. 管理后台仍然能看到该 skill 的系统角色和自动激活治理字段
4. 不出现“去掉 required 后，部署请求反而挂不上 deployment skill”的回归

## 9. 风险与边界

### 9.1 主要风险

唯一需要重点防的回归是：

1. 去掉 `required=true` 后，部署请求未能自动挂载 skill

这个风险不应该通过保留 `required=true` 来规避，而应该通过补齐部署意图触发与 deployment tool 自动激活的验证来解决。

### 9.2 边界

本方案不接受以下“兼容性修复”：

1. 保留 `required=true`，同时在运行时再写一层“非部署时忽略”
2. 继续让 deployment skill 进入 run state，只是在 prompt 里不展示
3. 在 system prompt 里补一层“普通消息忽略部署 skill”

这些都属于补丁方案，不解决根因。

## 10. 实施后续

本方案采用后，后续还需要继续排查另外两类耗时问题：

1. `workspace_restore` 的空检查为什么会阻塞约 3 秒
2. OSAC binary 为什么没有稳定复用，导致每次冷启动仍有明显写入成本

但这两项属于独立问题，不应阻塞本方案先修 deployment skill 的自动强制挂载错误。

## 11. 结论

当前 `deployment-orchestrator` 的问题，不是“部署能力本身不该存在”，而是“挂载语义错了”。

正确修复方向是：

1. 保留它作为平台 deployment 系统 skill
2. 保留它的自动激活治理能力
3. 去掉它的全局 `required` 属性
4. 让它只在部署场景进入当前 run

这样才能同时满足：

1. 部署链路可治理
2. 普通消息不被无关 skill 污染
3. 首轮启动成本不再被部署 skill 平白放大
